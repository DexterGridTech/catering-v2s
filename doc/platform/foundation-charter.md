## 1 · 底座必须如何

规则原文见 `project-memory/kernel/`,此处只给**为什么**与**违反后果**。

### 1-A · 一个业务 deployable,一个库,多 schema,一条 Flyway history

`ONE_BUSINESS_DEPLOYABLE` · `ONE_DB_MULTI_SCHEMA` · `ONE_FLYWAY_HISTORY`

**为什么**:多 deployable 会立刻要求分布式事务、服务发现、跨进程重试;
多 history 会让「当前 schema 是什么」失去唯一答案。
**违反后果**:一次跨模块写变成需要补偿逻辑的分布式问题,而当前阶段没有任何东西需要这个代价。

### 1-B · 模块 owner 主权

`MODULE_OWNER_SOVEREIGNTY` · `COMMAND_REQUIRED_TRANSACTION` · `TASK_READ_JOIN` · `COORDINATOR_NO_ASSET`

**为什么**:owner 是「谁能改这张表」的唯一答案。绕过它直接写别人的表,
下一个人改那张表的语义时不会知道你在写。

```java
// ❌ 反例:协调器直接写别人的表
class SomeCoordinator {
    void doIt(UUID ref) {
        jdbc.update("UPDATE other_owner.some_table SET status=? WHERE id=?", "DONE", ref);
    }
}

// ✅ 正例:调用目标模块的公开 command API,加入同一 REQUIRED 事务
class SomeCoordinator {
    @Transactional                       // 传播默认 REQUIRED
    void doIt(UUID ref) {
        otherOwnerApi.markDone(ref);     // 由 owner 在自己的事务内复核授权与当前事实
    }
}
```

**判别式**:这条写入语句所在的类,和被写的表,属于同一个模块吗?不是就停。

### 1-C · owner 在命令事务内复核

`OWNER_RECHECKS_COMMAND`

**为什么**:客户端提交的 ref、版本、状态在到达 owner 之前可能已经过期。
在事务外校验等于没校验。

```java
// ❌ 反例:事务外读、事务内写
var current = read(ref);                 // 读完到写之间,别人可以改
if (current.version() != expected) throw conflict();
@Transactional void write() { ... }

// ✅ 正例:复核与写在同一事务内,且复核带 scope 谓词
@Transactional
void write(Scope scope, UUID ref, long expected) {
    var row = jdbc.query(
        "SELECT version FROM own.table WHERE ref=? AND tenant_key=? FOR UPDATE", ref, scope.key());
    if (row.isEmpty()) throw notFound();
    if (row.get().version() != expected) throw conflict();
    ...
}
```

⚠️ **`FOR UPDATE` 对不存在的行不加任何锁**(行锁是写在 tuple 上的标记,不存在的行无处标记)。
首次创建的并发互斥不能靠它 —— 要么 advisory lock,要么唯一索引 + insert-as-claim。

### 1-D · 契约与消费面

`X_CONSUMER_FACES_ONLY` · `TWO_ADMIN_APPS`

**为什么**:两个后台是两套用户、两套权限。合并会让「谁能看见这个操作」失去唯一答案。

### 1-E · Heritage 只读

`HERITAGE_READ_ONLY` · `NO_RUNTIME_FALLBACK` · `NEW_DECISION_FOR_DRIFT`

**为什么**:旧仓是历史事实,不是可协商的当前状态。回写它等于让「当时是什么样」也变得不确定。

### 1-F · 仓库控制权归 Dexter

`GIT_BY_DEXTER` · `NO_GIT_WRITE`

⛔ 不得要求、提醒、催促、等待、索取或暗示任何仓库控制动作,
也不得把它当作设计、实施、测试、评审或收口的前置条件。

---

### 1-G · 元数据还是实例数据,看它挂在谁身上

只挂在租户/工作区这一级、被众多实例引用、自身不指向任何具体实体 ⇒ **元数据**。
带着指向某个具体实体的外键、离开那个实体就没有意义 ⇒ **那个实体自己的数据**。

**判别式**:去掉某一个具体实体,这条数据还有意义吗?有 ⇒ 元数据;没有 ⇒ 实例数据。

**推论**:元数据通常不需要排序(它是值域),实例数据经常需要(它是用户看到的顺序)。

原文与正反例:`project-memory/practices/metadata-classified-by-attachment.md`

## 2 · 底座必须不能

### 2-A · 不为想象中的未来付费

**为什么**:当前阶段是一人 + 两个 AI 快速迭代,功能达预期后移交正式团队。
为「第四个 owner 出现时」建的抽象,在第四个 owner 出现前是纯负债,而它可能永远不出现。

```java
// ❌ 反例:只有一个实现,却先建策略接口
interface PricingStrategy { Money apply(Order o); }
class DefaultPricingStrategy implements PricingStrategy { ... }   // 唯一实现

// ✅ 正例:直接写,等第二个实现真的出现时再抽
class Pricing { Money apply(Order o) { ... } }
```

**判别式**:这个抽象**现在**有几个实现?只有一个 ⇒ 不建。
⚠️ **例外**:横切关注点(锁助手、回执样板)即使只有一处调用也该统一提供 —— 见 §2-B。

### 2-B · 但横切关注点必须统一提供

**为什么**:`2-A` 讲的是**业务抽象**,横切关注点相反 ——
它们分散写会产生「必须逐字节一致却没有任何东西保证一致」的地方。

```java
// ❌ 反例:同一把锁的键推导在两个模块各写一遍,靠注释维持一致
/** Must stay byte-for-byte compatible with OtherService's key derivation. */
int key1 = 0x43534B55 ^ (int) (ref.getMostSignificantBits() >>> 32);

// ✅ 正例:收进共享工具,namespace 是必填形参
SharedLock.acquire(jdbc, Namespace.PRODUCT_SKU, ref);
```

**判别式**:两处**必须逐字节一致才正确**吗?是 ⇒ 必须统一。只是**长得像** ⇒ 不统一。
⚠️ 注释不是保证。编译器不会检查「Must stay compatible」。

### 2-C · 不留向后兼容层、fallback、迁移期双写

**为什么**:当前无业务数据、每次 reset + seed。兼容层守护的那个「旧状态」不存在。

### 2-D · 不引入常态轮询、MQ、通用 outbox

`NO_NORMAL_POLLING`

**为什么**:它们是为「跨进程最终一致」准备的,而当前是一个进程一个库。
引入后真正的问题(同一事务内的正确性)会被掩盖。

## 3 · 判据与分母

**这一节是本文件最锋利的一节。** 它治的是「分析了子集,却按全集的语气下结论」。

### 3-A · 结论之前先建立分母,分母必须自建不得继承

**为什么**:接手上游报告列出的对象清单,等于接手它的盲区,
而下游所有处置、批次、判据都会建在那个盲区上。

```text
// ❌ 反例
「裸 string 有三类:字典 kind、problem code、testId」        ← 来自上游报告,没问「一共有几类」

// ✅ 正例
「枚举方法:按字面量形态分桶,再对每桶用『谁必须达成一致』切出跨界子集。
  实测八桶:JSON 字段名 455/4496 · 全大写下划线 740/5520 · schema.table 138/2078 …
  其中跨界且无编译器保护的最大一类是 JSON 字段名 304 个。」
```

**判别式**:这一节写完,能回答「**一共有多少**」吗?答不上来 ⇒ 分母没建立,结论不能下。

### 3-B · 否定式全称命题必须穷举后才能写

**为什么**:证明「存在」只需一个实例,证明「不存在」要穷举。
一种写法没命中**不等于**不存在 —— 该仓的 SQL、FK、字符串大量多行拼接,
单行匹配的否定结论一律无效。

```text
// ❌ 反例
grep 'ON CONFLICT (a,b) DO NOTHING'  → 0 命中 → 「全仓无此写法」
   ← 实际源码是 "... ON CONFLICT "  +  "(a,b) DO NOTHING",跨两个字面量

// ✅ 正例
换 2–3 种写法 + 去换行归一 + 检查上下游层,并写明穷举范围:
「在 apps/ scripts/ libraries/ contracts/ 下的 *.java *.sql *.mjs(排除 build/)中穷举」
```

**判别式**:我写的是「不存在 X」吗?是 ⇒ 我穷举了吗?穷举范围写出来了吗?

### 3-C · 存在性判据不算判据

**为什么**:「表行数 = 断言数」是同义反复 —— 漏登一条,行数依然等于表里的条数。
`green-by-existence-check` 这条 pitfall 记的就是它。

```text
// ❌ 反例
PROOF: 断言配置文件里存在 X 字段                  ← 断言我刚写的东西里有我刚写的东西

// ✅ 正例
PROOF: 交叉校验 —— 删掉 X 字段,确认对应的门变红;
       并对判「删除」的每一条构造反例实跑,反例能通过则该处置作废重判
```

**判别式**:这条 PROOF 有可能失败吗?想不出失败场景 ⇒ 它不是判据。

---

### 3-D · 跨界字面量按「谁必须达成一致」分类

⛔ **不要按「谁在用它」分类** —— 前后台都出现的就收、只在一边的就不收,会漏掉大量真正危险的字面量。

**判据**:**这个字面量写错了,谁会不一致?** 答案跨越模块/进程/语言边界 ⇒ 它是契约,
需要单一来源与编译期保护。

分类之前先自建分母(见 3-A):按字面量形态分桶,数出每桶多少个、其中多少跨界、生成物覆盖了多少。

原文与正反例:`project-memory/practices/cross-boundary-string-agreement.md`

## 4 · 声称 ≠ 行为

**这是最高频的错误类。**

**规则**:注释、字段名、类型名、契约声明、文档自述、测试方法名 —— 全部是**声称**。
判断行为必须打开真实的读写路径。

```java
// ❌ 反例:据注释下结论
/** Idempotent: duplicate requests are safely ignored. */
void save(...) { jdbc.update("INSERT ... ON CONFLICT DO NOTHING", ...); }
//                            ↑ 返回值被丢弃 ⇒ 第二次执行的业务写已经发生了,
//                              只是回执没存。注释说的「safely ignored」不成立。

// ✅ 正例:用返回值判所有权,这才是行为
int claimed = jdbc.update("INSERT ... ON CONFLICT DO NOTHING", ...);
if (claimed == 1) return null;        // 本事务拿到执行权
return readExisting(...);              // 否则读别人已落定的结果
```

**判别式**:我的依据是「它写着 X」还是「我打开读写路径看到 X」?前者 ⇒ 还没验。

⚠️ 同一个 `ON CONFLICT DO NOTHING`,**用返回值判所有权是安全的,丢弃返回值是缺陷**。
按关键字一刀切会同时改错两边。

## 5 · 变更的形态

### 5-A · 定位用锚点,不用行号

**为什么**:多数变更会改变文件长度。用绝对行号指认一个**自己即将移动的目标**,必然失效。

```text
// ❌ 反例
CP-1: 删除第 12 行
CP-2: 删除第 72-74 行           ← CP-1 执行后全文上移,这里实际命中 73-75,
                                   而第 75 行是必须保留的活表 teardown

// ✅ 正例
CP-1: 删除锚点 `'some_policy_name',` 所在整行
CP-2: 删除锚点 `ALTER TABLE x.y DISABLE ROW LEVEL SECURITY;` 所在整行
      (锚点在目标文件内唯一命中,已逐条验证)
```

**判别式**:这个定位,在前一步执行完之后还指向同一个东西吗?

⚠️ 锚点也有坑:**不要带前导空白**(源码缩进是 11 个空格,写 12 个就零命中);
锚点必须**在目标文件内唯一**,写之前数一遍命中数。

### 5-B · 改之前逐字核对现状

**为什么**:执行者无法判断「这里是不是已经被人改过」。逐字 BEFORE 把这个判断变成机械比对。
⚠️ 但**引文必须是源码里真实存在的连续片段** —— 把跨 `+` 拼接的 SQL 引成一整行,
那段文本改动前就搜不到,于是「负锚点消失」这个检查恒真,等于没检查。

### 5-C · 会同时坏的东西必须声明为原子组

**为什么**:典型场景是「删一个产出字段 + 删它的三个消费者」。
逐个做的话删完第一个仓库就红了。执行者见红会以为自己做错,于是回滚、
或者**自己发明一个兼容层** —— 这是「发明抽象」最常见的触发点。

**必须写明**:组内顺序 · 中间态**预期的报错原文** · 整组完成后才跑证据。
⚠️ 预期报错**必须验证过**。声明一个不会发生的报错,比不声明更坏 ——
执行者会因为「报错与声明不符」而停机,而那是误报。

### 5-D · 分清「今天更坏」与「今天也没保护」

**为什么**:把一个静默失败改成响亮失败,在有保护的路径上是改进,
在**无保护的路径**上可能是回归。

```text
// ❌ 反例的推理
「删掉这个吞掉冲突的子句,无事务路径上今天也没保护,所以不更坏」
   ← 「今天不保护」与「今天不报错」是两件事。
     删掉之后,原本静默丢弃的重复写入会抛异常;若该路径是生产代码,那就是新的 500。

// ✅ 正例的推理
先确认该路径是不是生产可达;是 ⇒ 先把它纳入保护(补事务/补注解),再删吞掉冲突的子句。
```

---

### 5-E · AFTER 状态必须先过一遍既有的门

规定一个目标形态之前,先验证它**同时满足所有适用的约束**,不只是你盯着的那一道。

**判别式**:我验证的是「它解决了我的问题」,还是「它同时满足所有约束」?

原文与正反例:`project-memory/pitfalls/after-state-not-checked-against-other-gates.md`

## 6 · 门的形态

### 6-A · 每道门四件套,缺一不算门

1. **不变量** —— 一句机械可判定的命题
2. **红夹具** —— 人为制造违反,**真跑,确认真的变红**。⛔ 不接受「应该会红」
3. **负控制** —— 声明一条它**预期抓不到**的变异
4. **反例栏** —— 「能通过这道门但违反命题的写法是 ____」

**⛔ 反例栏写不出「无」以外的东西,这道门就是纸糊的。**

```text
// ❌ 反例:判据与命题错位
命题:控件形态必须正确
门:  检查 testId 存在
反例:testId 存在但挂在错误的元素上 —— 门全绿,命题不成立

// ✅ 正例:承认门的边界,把命题交给能证明它的证据
命题:业务写之前取得唯一执行权
门:  (静态门抓不到顺序) ⇒ 明写「本命题由并发测试用例 ① 承载,静态门只是形态回归栅栏」
```

### 6-B · 禁止句不是唯一合法形态

**为什么**:「某文本不得出现」只在**违规物本身就是某段文本**时适用。
精确集合相等、配对断言、确值约束、编译器穷尽性**同样是合法门形态**,
为了凑成禁止句把它们改写成反向正则,是把有效控制换成易绕过的。

### 6-C · 冻结计数不是不变量

```text
// ❌ 反例
if (nodes.length !== 20) fail(...)          ← 加第 21 个就拒绝运行,而 20 不是任何命题

// ✅ 正例
if (nodes.some(n => n.kind !== 'A' && n.kind !== 'B')) fail(...)   ← 划分不变量
if (new Set(keys).size !== keys.length) fail(...)                  ← 唯一性
```

⚠️ 删冻结计数时**逐条判**:同一个 `if` 里可能既有冻结计数又有真不变量,
整条删会连真不变量一起删掉。

### 6-D · 门不是万能的,但问题该改还得改

**为什么**:门检查不出来,不等于问题不存在。
门的作用是**防回归**,不是**定义什么算问题**。

## 7 · 文档的形态

### 7-A · 每一条只能是两种状态

| 标记 | 含义 | 执行者做什么 |
|---|---|---|
| `[已定]` | 决定已下,给出可执行的目标形态 | **照做**,结果唯一 |
| `[未定]` | 决定未下 | ⛔ **不得改码**,按判定程序产出结论后回 Dexter |

**第三种合法状态**:`[已定 · 本轮不执行]` —— 目标形态已确定,执行归后续批次。

⛔ **不允许第四种** —— 看起来像指令、实际是没想清楚的描述。

**判别式**:**读完这一条,两个不同的人做出来的东西一样吗?** 不一样 ⇒ 失格。

⚠️ 典型失格句式:「需求是真的,但走 X」·「逐个判」·「须先判定」·「二选一,实施者定」。

### 7-B · 只用单义动词

⛔ 禁用:统一 · 优化 · 梳理 · 完善 · 处理 · 接入 · 增强 · 重构 · 清理 · 调整
✅ 只用:`删除` · `新增` · `替换` · `移动` · `改值` · `重命名`

**为什么**:「统一 X」至少有四种实现(抽函数 / 抽基类 / 复制成一致 / 建配置),
执行者会挑一个而不会问。

### 7-C · 未知分母不写精确计划

**为什么**:精确的形式会掩盖未知的内容。
给分母未知的批次写「10 条 CP」,读者会以为那 10 条是全集。

### 7-D · 动手写新规则、新方案、新裁决之前,先查仓内五处

`project-memory/`(**含 pitfalls**)· `doc/decisions/` · 两份 coding standard ·
`HANDOFF.md` · `doc/review/platform/`

**为什么**:「我知道这件事该怎么办」与「这件事仓内已经办过」是两件事。
后者成立时,新写一份就是制造第二个真相源。

⚠️ **裁决会在你写文档的过程中新增。** 按「写之前查一次」的节奏,必然漏掉写作期间新增的
⇒ **实施那一刻要再查一次**,这是唯一能兜住的机制。

**判别式**:这件事如果有人已经想过,他会写在哪?写不出候选位置 ⇒ 先查再写。

## 8 · 协作边界与停机

### 8-A · 谁定什么

| 类别 | 谁定 |
|---|---|
| 产品语义 · Journey · 页面操作 · 用户可见行为 | **Dexter**,不得代裁 |
| 技术方案 · 实现形态 · 门的判据 | 设计方 |
| 范围 · 批次切分 · 是否推迟 | **Dexter** |
| 实施中的等价选择(命名、文件位置) | 执行者 |

### 8-B · 什么时候必须停下问

BEFORE 对不上 · 照做后编译不过或既有测试变红且不在预告内 · 文档写错 ·
两条指令冲突 · **触及产品语义** · 需要新增依赖 ·
**与 `project-memory` 或 `doc/decisions` 冲突**

⛔ 不允许:自己选一个「合理的」做法继续 · 留 TODO 继续 · 缩小范围报完成 · 加兼容层绕过

⚠️ **停机是唯一能兜住「设计文档与仓内既有裁决冲突」的机制。** 设计方写文档时可能漏查,
执行者在实施那一刻撞上并停机,是最后一道防线。**停对了不是打断,是救场。**

### 8-C · 不得从现有接口、表结构或旧页面反推用户任务

**为什么**:实现事实不是用户需求。
「它属于另一个 owner」推不出「用户不该在这里看到它」——
把模块划分外化成用户的操作成本,是把我们的问题变成用户的问题。

```text
// ❌ 反例的推理
「这个 tab 指向另一个 owner 的数据 ⇒ 它是类型重载 ⇒ 该删」

// ✅ 正例的推理
先问:用户在这个页面做的是一件事吗?是 ⇒ 保留,后台归哪个 owner 是实现细节。
      界面按用户任务聚合,但不合并 owner 事实或命令。
```

## 10 · 每段收尾自查表

**每完成一段开发,逐条自问。答不上来的回正文对应节。**

**分母与判据**
1. 我下的结论,分母是自建的还是继承来的?能回答「一共有多少」吗?
2. 我写了「不存在 X」吗?穷举范围写出来了吗?换过几种写法?
3. 我的 PROOF 有可能失败吗?想不出失败场景就不是判据。

**声称与行为**
4. 我的依据是「它写着 X」,还是「我打开读写路径看到 X」?

**变更**
5. 定位用的是锚点还是行号?锚点在目标文件内唯一吗?数过命中数吗?
6. 前一步执行完之后,后面几步的定位还指向同一个东西吗?
7. 有会同时坏的东西吗?声明原子组了吗?预期报错验证过吗?
8. 我把静默失败改成响亮失败了吗?那条路径是生产可达的吗?

**门**
9. 这道门的反例栏,能写出「无」以外的东西吗?
10. 红夹具**真跑过**并**真变红**了吗?

**文档与协作**
11. 我写的每一条,两个人做出来会一样吗?
12. 用了多义动词吗(统一/优化/梳理/接入……)?
13. 这件事仓内已经办过吗?五处都查了吗(**含 `project-memory/pitfalls/`**)?
14. 这是产品语义吗?是 ⇒ 我在代 Dexter 裁决吗?
15. 我从表结构或现有接口反推用户任务了吗?

**收口**
16. 需求文档里的每一条,在详设里都指得到落点吗?
17. 我声称完成的,证据档位够吗?有没有用编译冒充行为?
18. 新踩的坑登记进 `project-memory/pitfalls/` 了吗?
