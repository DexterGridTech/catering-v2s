# 第三方库用法与官方依据规范

本规范适用于设计、实现或验证中，正确性依赖第三方库、框架或插件的 API、默认值、时序、资源上限、协议处理或其他运行行为的情况。只使用普通类型且不依赖其特定行为时，无需为此增加核验材料。

## 1 · 实际用到第三方行为时，先核准确版本的官方依据

- 从仓内构建定义和实际解析图确认依赖坐标与版本，包含 BOM、dependency management、直接覆盖和传递依赖；按实际运行或测试 classpath 核对，不以声明版本或最新版代替。
- BOM 中管理了某个模块的版本，不代表该模块已被解析进当前 classpath；只把解析图中有依赖边、且源码/构建实际需要的模块记作已选依赖。报告是生成物，相关 build/依赖字节改变后必须重新生成，不得把旧报告中的坐标当成当前证据。
- 查该版本的官方文档、API reference 或维护方发布说明。先核对页面标题、版本标识和最终跳转地址：`current`、`release`、仅含次版本号的路径或其他别名可能展示较新的补丁版；若页面所示版本与实际解析版本不一致，不能把该页当成精确版本证据。此时改查官方仓库的精确 release tag、对应版本的源码/Javadoc 发布归档或协议正本（如 RFC），并在审计记录中写明坐标、版本、来源路径和被核对的类/API。社区文章、模型记忆和其他版本的示例不能证明当前版本行为。
- 不得凭方法名、相近重载、其他库或其他版本推断 API 存在、参数含义、默认行为或管线位置。官方材料不足时，将依赖该行为的设计/实现点保持 `OPEN`；必要时用当前解析版本构造最小、可复现的聚焦实验后再定。

## 2 · 设计和实施必须保留可复核依据

- 详设应记录：依赖坐标及实际解析版本、经版本核对的官方来源链接、采用的 API/组件与其被依赖语义（含相关默认值、限制、异常/关闭行为及生命周期），以及仓内如何核验。版本别名不匹配时，链接精确版本的官方源代码/Javadoc 归档，不把别名文档标成版本匹配。
- 实施步骤应指向详设的核验依据，并用与目标相符的最低执行面做 focused proof。官方文档证明库的约定；它不能单独证明本仓装配、运行时依赖图或业务路径已按该约定工作。
- 若实施时实际解析版本、API 或限制与详设不一致，先停在受影响实现点，读取 owning source 和解析图，修正设计/计划后再继续；不得用手改生成物、跳过限制或未经授权升级依赖来迁就假设。

## 3 · 反例边界

本规范不要求每个普通类型引用都新增测试或复制整份上游文档；只核验本批确实依赖且可能影响正确性、资源、安全、生命周期或验收的第三方行为。已有稳定用法只有在本批实际复用同一解析版本和同一调用语义时才可引用，并仍须确认版本与上下文相符。
