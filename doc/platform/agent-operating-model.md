# Agent 协作模型 · 谁做什么、卡住时找谁

- 日期:2026-08-17 · 作者:Claude
- 触发:Dexter 问「以后 Codex 自己做详设自己实施,我们只 review,那他停下来问谁?」

---

## 0 · 一句话结论

**那些停机,一次都不需要「问人」。**

它们之所以变成往返,只有一个原因:**详设不是实施方的,他没有权限改。**
当他有权限时,停机从「停下来问」变成「**停下来改自己的产物、登记理由、继续**」。

---

## 1 · 证据:6 次停机是怎么发现的

2026-08-17 一个会话内,实施方停机 6 次。**6 次全部证明是上游(设计/评审方)错了。**
逐条看他**实际**靠什么发现:

| 停机 | 发现方式 | 需要问人吗 |
|---|---|---|
| 编码格式校验与裁决冲突 | **读仓内**(一条 pitfall + 当天的 `ACTIVE` 裁决) | 否 |
| 验收判据说不出失败条件 | **试着写失败条件**,写不出来 | 否 |
| 分母 `455 / 4496` 自相矛盾 | **做算术** | 否 |
| 盘点缺 26 项成员清单 | **试着用它**,发现没有 | 否 |
| 「该实例缺 `size="small"`」前提为假 | **打开文件看**,属性本来就有 | 否 |
| 目标形态撞 120 字节行长门 | **跑了那道门** | 否 |

**六次全部是「对着仓库和现实核对」发现的。** 没有一次的信息来自另一个 agent 或人。

⇒ **仲裁者是仓库,不是人。** 决策、pitfalls、门、源码 —— 它们不依赖「谁写的详设」。

---

## 2 · 两种配置示例（不固定角色分配）

### 2.1 需求作者与实施者分离

Dexter 指派一方写需求或详设、另一方实施 → 实施时发现冲突 → 作者与实施者按当前授权修正或升级裁决
⇒ 每一次发现都变成一次往返,而人是中转。

### 2.2 同一作者负责需求与实施

Dexter 也可以指派同一方起草需求或详设并负责实施；作者可以按当前授权修正自己的产物。
独立评审仍由未参与该对象创作的 fresh reviewer 完成。

**停机不消失,它变形。** 变形后的四类判据不变:

1. 不变量之间互相冲突
2. 不变量说不清(失败条件写不出来)
3. 不变量与源码不符
4. 满足不变量必须动 `FORBID` 的东西

前三类**自己改自己**;第四类才需要看 `FORBID` 是谁定的 —— 若是自己定的,同样自己改。

## 3 · 必须由 Dexter 指派或裁决的事项

| 类别 | 为什么只有他能定 |
|---|---|
| **需求作者** | 每份需求由 Codex 还是 Claude 起草，由 Dexter 在任务指派中决定 |
| **产品 / Journey 语义** | 用户该看到什么、这个操作在此时合不合理 —— 仓库里没有答案 |
| **范围与批次** | 这件事这一批做不做、值不值得现在做 |
| **破坏性 / 不可逆 / 外部影响** | reset · seed · 删除 · 任何影响仓外的动作 |

⛔ **其余问题先查仓库和真实源码。**
⛔ 尤其不得因为「上游是设计方或评审方」就采信 —— 上游是待验证输入,**以源码为准**。

## 4 · 自设计自实施的真风险,以及顶替它的东西

**当实施方就是上游时,没有任何东西会反驳他。**
设计错了、实现得很自洽、门全绿 —— 从外面看不出来。这是这个配置唯一的真风险。

顶替这个位置的只能是**独立盲审,而且必须在实施之前**。

**这个机制已经被验证有效**:2026-08-17 本批,实施方自己跑了独立 implementation review,
判 `NO-GO` 并抓出一条 `M` —— 而那条 `M` 恰恰是**设计方的疏漏**
(圈了四份入口文件,漏了那份仍然 `ACTIVE` 的决策)。

**他的盲审抓到了设计方的错。**

### 不可放松的三条

1. **必须在实施之前**,不是实施之后 —— 事后审只能证明「做出来的和设计一致」,证明不了设计对
2. **必须 fresh 独立子 agent 盲审**,作者会话不得自审自判
3. **缺一输入或先读作者材料,该轮无效**

## 5 · 各方角色与指派边界

| 角色 | 职责 |
|---|---|
| Dexter | 决定本轮范围与授权，并决定每份需求由 Codex 还是 Claude 起草；裁决未决的产品语义及其他需其决定的事项 |
| Codex | 按 Dexter 的指派起草或更新需求、编写详设、实施并完成授权范围内的核验；在当前 Codex 执行中承担主 agent 的文件写入责任 |
| Claude | 可按 Dexter 的指派编写需求；也可承担独立复核。Claude 编写的对象须由其他 fresh reviewer 独立复核 |
| Fresh 独立 reviewer | 按适用流程进行只读盲审或步骤对账；不得修改被审文件，也不得审查自己创作的对象 |

需求作者由 Dexter 按任务指派确定，不存在 Codex 或 Claude 的默认作者身份。作者身份不改变独立评审要求。

### 5.1 长任务的步骤级角色隔离

长任务不能把所有代码写完才第一次做代码—详设对账。主 agent 保持唯一实施责任：设计、写代码、跑每个实际改动点的 focused proof、按 RECALL 自己做前后读回；但独立三维对账只在完整 CP 阶段结束后、进入下一 CP 前，由 fresh 独立子 agent 完成。CP 内部的改动点、文件、focused proof 和修复不分别触发 review。其动作与输出唯一正本是 `doc/platform/review-standard.md` 的“CP 阶段级独立对账”。

这不是把实施拆给子 agent，也不是提前做整批 verdict：主 agent 是唯一编码与文件写入者；子 agent 不修改任何文件，只判整个 CP 的 `MATCHED / OPEN`；主 agent 修复 CP 级 `OPEN` 后再由另一 fresh 子 agent 复查同一 CP。最终整批 `REVIEW_TARGET=IMPLEMENTATION` 仍按既有正式流程单独进行。这样保留了主 agent 对完整上下文和实现闭包的责任，也能在进入后续 CP 前发现偏移。

---

## 6 · 为什么这样更省,不是更松

**不是放松,是把判断放在有能力判断的那一侧。**

实施方能跑门、能编译、能看到真实输出;设计方不能。本会话有两处直接证据:

- 设计方规定「必须用四条嵌套类 import」→ 撞 120 字节行长门,**设计方无法逐行预演行长**
- 裁定后改「必须用外层类限定名」→ **又**撞同一道门(算了类名,漏算了 `: exception instanceof ` 前缀)

**同一项往返三次,全部因为设计方在规定自己验证不了的东西。**

改成「设计方给不变量、实施方给形态」之后,第三次他自主选了排版方案并登记理由,
**零往返收敛。**

## 7 · 设计期盲审(切换的前提,现予固定)

**触发点:详设写完、实施开始之前。** 不是实施之后 ——
事后审只能证明「做出来的和设计一致」,证明不了设计对。

### 7.1 不可放松的四条

1. **fresh 独立子 agent**,作者会话不得自审自判
2. **两阶段**:先不读作者材料,自己从冻结输入独立推导结论;**再**打开作者材料逐条攻
3. **禁止派生子 agent**(prompt 里明写),否则责任链断裂
4. 缺一输入、或先读了作者材料 ⇒ **该轮无效**,重跑

### 7.2 prompt 必须包含的六样

本会话 5 轮盲审在设计方文档上逐轮抓出真错,有效形状固定如下:

| # | 内容 |
|---|---|
| 1 | **目标与判据**(不是任务描述)—— 让 reviewer 能独立判断「这个方案该不该这么做」 |
| 2 | **第一阶段的独立推导题** —— 让它先得出自己的答案,再看作者的 |
| 3 | **作者声称的每一个数字与事实**,逐条列出让它**独立复测** |
| 4 | **本轮特有的攻击面** —— 每轮不同(原创方案 / 修订稿 / 补丁堆 / 可执行性),重复用同一组会空转 |
| 5 | **环境陷阱**(本机无 `timeout` · 按 shebang 选解释器 · 判红绿用退出码 · zsh glob) |
| 6 | 「**如果确实没问题就直说没问题**」—— 只被要求找问题的审查者会凑数 |

### 7.3 轮次与收口

- **两轮上限只管 `REVIEW_TARGET=DESIGN`**(agent 自己的需求、详设或实施计划),第二轮 `SELF_DECIDED` 收口
- 换模型 / 换 agent / 改文件名 **不重置**轮次
- **不设轮次上限**:实施完成后整批 `REVIEW_TARGET=IMPLEMENTATION` 审查(必须依据详设文档)、实施过程中的对账(直到 `MATCHED`)、经 Dexter 中转的 Codex↔Claude review(轮次由 Dexter 定)。正本见 `doc/decisions/2026-07-25-v2s-independent-subagent-adversarial-review-governance.md` 第 1 节
- ⚠️ 该上限约束的是 **agent 自主发起**的轮次。Dexter 在对话中要求再审时不受它约束
  (见 `project-memory/pitfalls/repo-rule-cited-against-dexter.md`)

### 7.4 verdict 的处置

reviewer 的 finding 是**待验证输入**,不是新权威。
作者必须逐条重开 owning source 并标注:
`CONFIRMED` / `PARTIALLY_CONFIRMED` / `REJECTED_WITH_EVIDENCE` /
`UNVERIFIED_REQUIRES_EVIDENCE` / `DEXTER_DECISION`。

⛔ 不得全盘接受,也不得在信息不全时武断裁决。

## 8 · 评审方的事后复核:触发点与粒度

**触发点**:一批实施完成、作者自审通过之后。
**粒度**:整批,不逐项。

**评审正本是 `doc/platform/review-standard.md`,入口 skill 是 `cs-review`;本节不再自带清单。**
⚠️ 评审规范**只写动作**,判据一律回各自正本取(charter / 两份 coding-standard / 本批设计文档 / project-memory)。

⚠️ **原来的"只验四件"已被证明不够。** 那四件(不变量 · 范围外改动 · 证据档位 · 反向 PROOF)
**全是工程不变量**;2026-08-19 按它评审给出 `GO`,2026-08-20 Dexter 第一次打开页面
就发现 21 条问题,而那轮 5 条 finding **零条关于用户看到什么**。

现在是三层,缺一层等于没验:

1. **L1 工程不变量** —— 原四件,保持
2. **L2 用户可见事实对账** —— 从代码机械提取渲染事实,与 IA 可见维度逐条比
3. **L3 未验证清单** —— 哪些事实本轮无人验过;非空时结论只能是 `GO_WITH_UNVERIFIED_UI`

加一条贯穿全层的:**同族全集** —— 任何 finding 必须枚举本批该形态的全集并逐个判定。

⛔ **不再由评审方设计。** 评审方给不出「怎么做」,只给「这批做到没做到」。

⚠️ **这一道比设计期弱,而且弱得有理由**:它发生在成本已经花完之后。
把它当主要防线会让整个模型退回原样。**主要防线是 §7。**
