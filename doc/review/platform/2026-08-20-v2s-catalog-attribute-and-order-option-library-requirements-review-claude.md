## 0 · 方案合理性(先于闭环正确)

### 问题对不对 —— ✅ 对

「每个商品重复发明属性与点单组,导致同一业务事实口径漂移」是真实且经典的 catalog 问题,
且**产品语义由 Dexter 直接裁定 12 条**,不是作者臆造。成功判据具体可观察
(同一"过期时间"在面包填三个月、可乐填六个月;同一"蘸料"被多商品复用而各自决定加价与扣料)。

### 代价配不配 —— ✅ 与裁定相称

两个新定义族 + 商品赋值/覆盖 + 强制 BOM 模板 + 品牌复制闭包扩展 + 两步新建,
量不小,但**每一项都能追到一条 Dexter 裁定**;文档没有夹带裁定之外的能力扩张。
非目标清单(不做对客端、菜单发布、订单扣减、采购仓储)划得干净。

### 方案优不优 —— ⚠️ **唯一的方案,零替代比较**(见 S-1)

## ~~M-1 原始分析~~ · 把 Dexter 对「第一步」的裁定扩成了商品分类模型的 cardinality 变更

**位置**:正式文档第 94 行(§3.5.2)与第 175 行(BE-CAT-01)

**Dexter 原话**(讨论稿第 140 行):

> 8. **第一步**分类可不选、但只能单选,并使用树形选择器。

**文档写成**:

> 第 94 行:分类使用树形选择器,可不选,但只能选一个分类;**该单选规则适用于商品分类关联**,而非仅改变第一步文案。
> 第 175 行 BE-CAT-01 结论:**商品关联 cardinality 必须改为可空单选**。

**仓内事实**:`catalog_item_category` 是**真多对多表**,复合主键
`PRIMARY KEY (item_ref, category_ref)`(`V20260814_100000_000__catalog_p3_model.sql:39-43`);
前端 `categoryRefsDraft` 是 `string[]`;owner save 接受数组不限制。

**为什么是 M**:
① Dexter 裁的是**创建第一步的表单约束**;文档把它变成**商品与分类关系的模型基数**。
这是两件事 —— 完全可能「创建时先定一个主分类,进入详情后可再加」,那是常见产品形态,
Dexter 没有排除它,文档也没有给出他排除它的依据。
② 该结论被标为 `CONFIRMED — SUPERSEDED`,即**已定**,会被下游详设直接继承。
③ 它触发**破坏性数据迁移**:现存多分类商品要保留哪一个?
而 **§9 六条 `UNRESOLVED` 里零处提及分类**(实测 0 命中)—— 这个迁移问题**无人认领**。

**同族全集扫描**:本文档中「把 Dexter 的局部裁定扩成全局结论」的候选共 3 处,逐个判定 ——
- 分类 cardinality(第 94/175 行)⇒ **越权,本条**;
- FR-ATTR-04 属性定义 code 可改 ⇒ 对照裁定 3「编码可修改、同 scope 内唯一」,**逐字吻合**,且文档主动把它限制为
  `NARROW_EXCEPTION` 不外溢(DOC-06),✅ 不越权;
- FR-OPT-02 多选 min/max ⇒ 对照裁定 6,✅ 且 U-01 主动把「归属哪一层」留为未决,做得对。
⇒ **三取一,只有分类这条越了。**

**最小修复**:第 94 行改为「**第一步**只能单选」;BE-CAT-01 的结论列改为
「首步创建 command 需接受可空单分类;**商品与分类的整体 cardinality 是否随之收窄,属未裁定**」,
并在 §9 新增一条 `UNRESOLVED`(含既有多分类数据的处置)。

**是否需 Dexter 裁决**:**是**。这是产品语义:商品在详情页能不能挂多个分类?

## S-1 · §4 概要设计只给一个模型,零替代比较;且把「现状不是 X」当成「不能用现状做 X」

**位置**:§4(第 105-117 行)· BE-ATTR-03 · BE-OPT-04

**文档的论证形式**:
BE-ATTR-03「dictionary kind 是五值封闭集合……**现有 dictionary 不是新属性定义/选项定义库**」;
BE-OPT-04「`ORDER_OPTION_VALUE` 只验证无父……**不能改名复用为选项库**」。

**这两句描述的都是当前状态,不是"不能扩展"的论证。**

**我构造的替代方案(文档未列)**:扩展既有 dictionary,而非新建定义族。
仓内事实支持它值得一比 —— dictionary **已经具备 scope 感知的父子机制**:
`parent_entry_ref` + 同 scope 外键 `(parent_entry_ref, data_node_ref, brand_ref)`
+ kind CHECK + 校验 trigger(`V20260816_010000_000__...sql:196-229`)。
这正是「属性定义→选项」「选项组→选项值」需要的形状。

**诚实的取舍**(我做完比较后的结论,不是主张改方案):

| 维度 | 扩展 dictionary | 新建定义族 |
|---|---|---|
| 父子 + scope | **现成** | 重建 |
| code 可改 | 要改(现 update 只改 name) | 自由设计 |
| 级联删除 | 要改(现 `REFERENCE_BLOCKS_VOID`) | 自由设计 |
| `valueType`/`selectionMode`/min-max/顺序 | 要加列或塞 JSON,**会把 dictionary 撑成多态表** | 干净 |
| 商品赋值/覆盖/BOM 模板 | **两方案都要新建**,无差异 |

⇒ 我倾向新建定义族**可能确实更对**(dictionary 被撑成多态表是真风险),
但**这个比较必须由文档做出来**,而不是由下游详设默认继承一个从未被论证的前提。

**为什么是 S 不是 M**:结论很可能正确,Dexter 的 12 条裁定在两个方案下都成立;
但 §4 是「概念边界」,它一旦落定就锁死下游。CLAUDE.md 要求
「作者没有列出的替代方案要自己构造出来做比较,说清取舍」。

**最小修复**:§4 增一段方案比较(至少「扩展 dictionary」与「新建定义族」两案),
写明「我选了 X 而不是 Y,因为 Z」。BE-ATTR-03/BE-OPT-04 的结论列措辞由
「不是/不能复用」改为「若沿用需付出 A/B/C,故本需求选择新建」。
**不需 Dexter 裁决** —— 这是工程论证的补齐,不是产品语义。

## S-2 · ~~扣料前置未定~~ → **问题不成立,改为「已裁定但文档漏写」**

> **Dexter 2026-08-20 裁定**:「选项库建立的时候就会选择『黑松露酱』对应原材料商品『瓶装黑松露酱』,
> 而**选择『瓶装黑松露酱』的前提是它已经有 StockTarget**。」

⇒ **门在建库时,不在商品配置时。** 商品侧填 N 克时 target 必然已存在,
我原先推的「存不下 / 存下但未就绪 / 静默存下」三选一**不会发生**。**原 S-2 撤销。**

**我另验了两条绕开该门的路径,均不成立:**
1. **品牌复制撞上门店无 target** —— 已有解:inventory 复制引用计划先按 identity 在目标 scope
   匹配已有 target 并建 planned 映射,映射不上抛 `REFERENCE_MAPPING_UNRESOLVED` **拒绝整次复制**,
   不会静默产出坏配置(`InventoryOwnerService.java` 复制引用计划段)。
2. **target 被引用后作废** —— inventory 对 target **没有 void/delete/disable 动作**
   (只有读、盘点、增加、调整),该场景在当前模型中不存在。

### 但文档漏写了这条前置(保留为 S)

正式需求分析只写了**结果**(§3.3.1「实际扣料必须落到有效 `StockTarget`」),
**没写前置**(「选择原材料商品的前提是它已有有效 `StockTarget`」)。

**影响面**:实施者不知道门设在哪,很可能把校验放到**商品配置时**校验库存就绪度 ——
那正好回到被裁定排除的形态,并让配菜单被库存就绪度阻塞。

**最小修复**:在 FR-OPT-01 或 §3.3 增一句 ——
「点单选项库定义强制组件时,只能选择**已有有效 `StockTarget`** 的原材料商品;
该前置使商品侧配置不再需要判断库存就绪度」。
**是否需 Dexter 裁决**:否,已裁定,只需写入。
