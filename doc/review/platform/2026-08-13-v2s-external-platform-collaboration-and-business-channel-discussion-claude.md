## 2. Dexter 外部平台诉求（原始记录，最高权威）

> 以下按 Dexter 2026-08-13 口述整理，保留原始表述与强调。

**总述**：v2s 未来会对接**很多很多**外部平台——团购平台、外卖平台、外部库存系统、商场 ERP、外部各种会员或身份系统。

### 2.1 交易主数据类

集团、大区、项目、品牌、总公司、门店、运营用户、合同、商品——这些是**部分**交易前需要的主数据（非全部主数据），**可能是外部系统通过接口同步给我们的**。

### 2.2 订单权益类

- 狭义：外部团购平台、外部会员积分、外部营销卡券、活动平台。
- 广义：本系统的订单**在生成的过程中（注意，是过程中）**，判断消费者使用的权益——是抵扣订单的**部分金额**，还是抵扣**某个商品**（跟商品绑定，多用于团购；系统识别到这个权益后可以自动在订单或购物车中加入这个商品）。**该权益会作为支付单保存在订单中，用于后续的外部结算依据。**
- 三个核心要素及其获取依赖：

| 要素 | 例 | 获取依赖 |
|---|---|---|
| **消费者身份** | 美团用户 openid | 美团 ISV 身份 + 门店或其他授权 |
| **权益模版** | 万象城的团购券模版 | 项目信息 + 门店信息 |
| **权益行** | 万象城的代金券 | 项目信息 + 门店信息 + 消费者身份 |

- 商品关联两种方式（狭义团购券，如套餐商品团购，**交易前必须建立**）：
  - **硬关联**：在本系统拉取外部权益模版，手动建立与本系统商品的关联；
  - **软关联**：外部权益模版定义时写入本系统的商品编码；核销权益行时，读权益行→权益模版→找到对应商品。

### 2.3 订单创建类

订单在外部平台直接创建，然后同步到本系统来**履约生产**。一般指外卖平台：美团外卖、饿了么、淘宝闪购等。消费者通过这些外卖平台下单支付。

### 2.4 订单配送类

外卖订单不管来源哪里（外部平台或本平台），本平台生产完之后配送到消费者手上。配送服务可能使用**原外卖平台的配送**，也可能使用**其他第三方配送**。

### 2.5 商品库存同步类

本平台只记录**轻库存**（原话"清库存"，与仓内既有 `catalog-store-light-inventory` 概念一致），用于**交易前的判断**和**交易后的扣减**；**权威库存在店铺自己的 ERP 和供应链系统中**。为保证门店经营，本系统需要与外部系统同步库存。

### 2.6 交易结果同步类

本系统关注的业务范围是**交易**。交易后的业绩考核、资金结算等不在本系统范围内，但本系统需要把交易结果同步给门店和项目——**一个订单需要能同步给 N 个外部系统**。

## 3. 六类的结构特征（分析）

### 3.1 平台与类是正交的

同一外部平台**同时出现在多个类**：美团 = 2.2（团购权益）+ 2.3（外卖订单）+ 2.4（配送）；同一类**跨多个平台**：2.2 = 美团团购 + 万象城会员/卡券 + 抖音 + 各活动平台。

→ 模型必须分离三个概念，不能揉成一个"渠道"：

```text
外部系统是谁      （ExternalSystem：身份、授权、连接配置）
协作的是哪类业务  （六类之一：主数据 / 权益 / 订单入站 / 配送 / 库存 / 结果）
落在哪个业务坐标  （project / store 的绑定关系）
```

### 3.2 数据流向各不相同

| 类 | 方向 | 时机 |
|---|---|---|
| 2.1 主数据 | 外 → 内 | 交易前，批量/增量 |
| 2.2 权益 | 读外部（身份/模版/行）+ 核销写回 + **支付单落单** | **订单生成过程中，实时** |
| 2.3 订单入站 | 外 → 内 | 实时 |
| 2.4 配送 | 内 → 外（履约任务） | 生产完成后 |
| 2.5 库存 | **双向** | 周期 + 事件 |
| 2.6 交易结果 | 内 → 外，**一对 N** | 交易完成后 |

### 3.3 只有一部分是"渠道"

- **2.3 是订单来源渠道**——订单从哪来，经典渠道语义。
- **2.2 的权益来源是订单来源快照中的独立坐标**——v6 红线 2.3（团购平台不是订单入口）与 Dexter 广义定义一致：权益在订单**过程中**被消费，不是订单的入口。
- **2.1 / 2.5 / 2.6 与订单入口无关**——它们是纯协作关系（主数据供给、库存对账、结果分发），**不应被建成渠道**。
- **2.4 是履约服务选择**——配送商不是订单入口（v4 的 `DELIVERY_PROVIDER` providerKind 可参照，但归属履约侧）。

### 3.4 权益类是六类中建模最重的一类

Dexter 的广义定义把权益提升为一等业务对象：**身份解析 → 模版 → 行 → 核销 → 作为支付单落订单 → 外部结算依据**，横跨 订单 / 支付 / 营销权益 / 结算 / 外部协作 多域，且商品关联（硬/软）要求**交易前**的目录侧配套。这超出 v6 15/16 的原范围。

### 3.5 主数据类意味着 org / catalog / contract 需要"来源出处"

2.1 说组织节点、运营用户、合同、商品**可能由外部同步而来**——这些 owner 域的记录需要区分 externally-mastered 与 locally-created（出处、同步坐标、只读性），否则外部同步与本地编辑会互相覆盖。

## 4. 经营渠道到底是个啥（候选框架，待讨论裁定）

| 框架 | 内容 | 判断 |
|---|---|---|
| **A（窄）** | 渠道 = 订单入口坐标层，只覆盖"订单从哪来"（POS / 扫码 / 自营小程序 / 外卖平台） | 干净，但权益来源坐标没有归属 |
| **B（宽）** | 渠道 = 一切外部协作的业务坐标，六类都挂渠道 | **反对**：违反 v6 红线 2.1（渠道变万能能力矩阵）；把主数据同步、结果分发硬套"渠道"语义不合业务直觉 |
| **C（推荐）** | **双层**：通用**外部协作层**（外部系统 / 身份 / 授权 / 连接配置 / 同步任务，服务全部六类）＋ **经营渠道层**（订单来源业务坐标：内部入口 + 外卖平台入站 + 权益来源坐标引用） | v6 15/16 分界的推广——16 从"渠道防腐"生长为"六类通用协作层"，15 保持窄 |

按框架 C，六类的承接归属：

| 类 | 渠道层 | 协作层 | 主权域 |
|---|---|---|---|
| 2.1 主数据 | — | 同步通道 | org / catalog / store-contract（带出处） |
| 2.2 权益 | 权益来源**坐标** | 身份/授权/模版拉取/核销调用 | 权益域（模版/行/核销）+ 订单（支付单）+ 结算 |
| 2.3 订单入站 | **订单来源渠道** | 订单接收/确认/取消 | 订单域 |
| 2.4 配送 | — | 配送商调用 | 履约生产域 |
| 2.5 库存 | — | 双向同步 | inventory（轻库存） |
| 2.6 结果分发 | — | 一对 N 出站 | 订单/结算读侧 |

**渠道三层结构（kind 契约 / template / channel / providerConfig / binding）仍是可继承资产**，但只在框架 C 的"渠道层"内使用；all-v1 拍板中 Q1（kind 抽象名）、Q4（精简派生，且本轮升级为"存储精简+读时投影"）、Q5（软引用非 FK）继续有效；Q2（起步渠道范围）、Q6（美团接通范围与时序）按六类分类学与 v2s 阶段**重估**。

## 7. 第二轮裁定（Dexter 2026-08-13）

1. **channel 挂 PROJECT，binding 挂 STORE。**
2. **渠道 = 下单入口**，分两类：
   - **内部渠道**（内部小程序、POS 等）：需要维护渠道菜单或销售集合，**直接读取我们自己的数据并展示给消费者下单**；
   - **外部渠道**（美团外卖、饿了么等）：**外部自己维护数据并下单闭环**，菜单协作二选一——
     - **拉取映射**：拉取外部菜单，与本系统商品建立映射；
     - **推送**：本系统维护菜单，推送到外部平台。
3. **权益类本次迭代不做。** v6 里的权益定义不全；本讨论稿 §2.2 的记录是**未来迭代的重要依据**。
4. **本期顺序**：创建管理项目和门店的内外部渠道 → 内部渠道维护完整菜单（销售集合）→ 外部渠道两种维护方式。
5. **主数据出处要预留**（org / catalog / contract 的 external-source 出处）。

### 7.1 对既有语料的取代声明

**裁定 2 的"推送"模式取代 all-v1 的旧拍板。** all-v1 §4D 曾定「删 `EXTERNAL_DESIRED_STATE`——不向外部推菜单，外部菜单一律 external→catalog 拉取映射」。本裁定明确**推送是外部渠道两种维护方式之一**，该旧拍板不再有效。语料纳入时须以本裁定为准，避免两条相反结论并存。

## 8. 渠道定义（据两轮裁定收敛）

> **经营渠道 = 消费者完成下单所经过的经营入口。** 项目级 channel 声明项目支持哪些入口，门店级 binding 声明门店在哪些入口上落地。

| | 内部渠道 | 外部渠道 |
|---|---|---|
| 菜单数据 | **我们的**（销售集合发布到 binding） | **平台侧的** |
| 下单闭环 | 发生在本系统 | 发生在平台，订单**同步入站履约生产** |
| 菜单协作 | 发布（activation → binding） | **二选一**：拉取映射 / 推送 |
| 例 | POS、内部小程序、扫码点餐 | 美团外卖、饿了么、淘宝闪购 |

**明确不是渠道**（六类中的其余）：2.1 主数据同步、2.5 库存同步、2.6 结果分发是纯协作关系；2.4 配送是履约服务选择，归履约侧；2.2 权益是订单来源快照中的独立坐标，本次迭代不做、记录为未来依据。

继承资产照旧：kind 契约 / template / channel / providerConfig / binding 三层结构、v6 五条红线、存储精简+读时投影、软引用非 FK。

## 9. 第二轮待讨论问题

**Q6｜外部渠道第三步的深度**：「外部渠道两种维护方式」做到哪一层？
- (a) **数据模型 + 管理界面先行**：外部菜单条目、映射关系、推送意向都建模并可人工维护，真实平台连接器（授权/API/回调）后置——v2s 当前没有 mocks/meituan 可联调；
- (b) **同时建连接器**：需要先建协作层（外部系统/授权）+ mock 平台。
我的倾向：**(a)**——两种维护方式的业务价值在映射与推送的**数据正确性**，连接器是传输问题，可后置且不阻塞订单入站建模。

**Q7｜菜单协作模式挂在哪**：模式（拉取映射 / 推送）是 **channel 级**属性（项目对该平台统一定）还是 **binding 级**（各门店可不同）？我的倾向：**channel 级定模式，binding 级执行**（映射条目与推送目标本来就 per 外部店铺）；出现真实反例再放开。

**Q8｜映射关系的 owner**：外部菜单条目 ↔ 本系统商品的映射放哪个域？v6 归 16（协作域，带 bindingRef 坐标）；但 Q6 若选 (a)，本期没有协作域。候选：随渠道域先建（将来只迁传输不迁业务映射）/ 直接建协作域骨架只装映射。我的倾向：**先随渠道域**——映射天生是 binding 的业务事实近邻。

**Q9｜推送模式是否复用销售集合发布**：内部渠道的发布是 activation → binding；推送模式可否**同一套发布机制、不同发布路由**（内部=终端投影，外部=推送任务）？我的倾向：**是**——一个发布模型，路由不同，避免出现两套"菜单生效"语义。

## 10. 第三轮裁定（Dexter 2026-08-13）

- **Q6 = (a)**：数据模型 + 管理界面先行，连接器后置。
- **Q7 = binding 级**，且**店铺可根据经营需求动态切换**协作模式。（纠正我的 channel 级倾向。）
- **Q8 = 映射关系归销售集合（菜单域），不在协作域。** Dexter 原话逻辑：内部渠道的菜单和商品**本来就有映射关系**；拓展到外部渠道，**只是菜单的来源变了**，"映射商品"这个关系/属性照旧复用。（同时纠正我的"随渠道域"倾向与 v6 的"归 16 协作域"。）
- **Q9 = 复用**：推送模式复用销售集合发布机制，一个发布模型、不同路由。

### 10.1 Q8 的统一性含义

菜单条目 → 商品 的映射是**菜单域原生关系**，与来源无关：

```text
内部菜单条目（来源=本系统商品）────┐
                                  ├── 同一个"映射到商品"关系 ── 订单行解析 ── 履约生产
外部菜单条目（来源=外部平台）──────┘
```

- 外部菜单条目 = **来源为外部**的菜单条目（带外部标识 + 出处），与裁定 5 的 external-source 出处概念**同构**——菜单域是第四个需要出处的域；
- 订单解析因此**统一**：无论订单来自 POS 还是美团，订单行都经菜单条目→内部商品，一条链路；
- 协作域（未来）只承**传输级**对象同步（授权/API/回调/raw/游标），**业务映射永不迁入**。v6"外部对象映射归 16"仅剩传输语义。

## 11. 收敛后的模型形态（三轮裁定合并）

### 11.1 领域责任

| 域 | 拥有 | 备注 |
|---|---|---|
| **渠道域**（本期建） | kind 契约 / template 目录 / **BusinessChannel（挂 PROJECT）** / **BusinessChannelBinding（挂 STORE，含菜单协作模式，binding 级、可动态切换）** / 订单来源语义（定义+查询，不持久快照） | ProviderConfig 本期是否缓建见 §12-B |
| **销售集合/菜单域**（第二步建） | 菜单/销售集合 / **菜单条目↔商品映射（原生关系，来源无关）** / 外部菜单条目（外部来源+出处） / 发布 activation→binding，**路由由 binding 当前模式派生** | 内部=终端投影；外部推送=推送任务；外部拉取=不发布 |
| **订单域**（未来） | 订单行→菜单条目→商品的统一解析；订单来源快照冻结 | 快照应含 binding 当时的协作模式 |
| **协作域**（未来） | 授权 / API / 回调 / 同步任务 / 传输级对象映射 | 业务映射不迁入 |
| **org / catalog / contract / 菜单** | external-source 出处 | 裁定 5 + Q8 推论 |

### 11.2 三条业务流程

```text
内部渠道:   channel(PROJECT) → binding(STORE) → 销售集合发布 → POS/小程序读取展示 → 下单
外部·拉取:  binding 模式=拉取映射 → 外部菜单条目(本期人工维护) → 映射商品 → 订单入站解析 → 履约生产
外部·推送:  binding 模式=推送 → 本系统维护销售集合 → 发布路由=推送任务(本期生成意向,连接器后置)
```

## 13. 外部对接架构：适配器层（第四轮讨论）

### 13.1 Dexter 提案（原始记录）

主程序 `apps/backend/catering-business-server` **不与外部系统直接对接**，通过适配器连接：`apps/backend/adaptors/order/meituan`、`adaptors/order/eleme`、`adaptors/delivery/meituan`、`adaptors/delivery/fengniao` 等。**适配器左边与主程序内部模型统一，右边与外部平台统一，负责中间转换。**

### 13.2 判断：方向正确，且回答了"协作域在哪"

该结构就是防腐层/端口-适配器模式，与六类分类学**同构**：`adaptors/order/*` = 订单创建类(2.3)，`adaptors/delivery/*` = 订单配送类(2.4)；未来 masterdata(2.1)、benefit(2.2)、inventory(2.5)、result(2.6) 各成一类。**此前讨论的"协作域（未来，只承传输）"由此获得物理形态：协作域不是主程序里的模块，就是适配器层本身**——凭证、token、raw、游标、重试全部住在适配器，永不进主程序业务表（与 v6 §5.3 一致）。

### 13.3 关键精化一：左边不是"内部模型"，是"端口契约"

适配器左边对齐的必须是主程序**发布的端口契约**（per 能力类的稳定 DTO 边界，主程序拥有、入 contracts 版本管理），**不是主程序内部领域类**。若适配器直接编译依赖主程序内部模块，每次内部重构会波及全部适配器，防腐层反被腐蚀。

### 13.4 关键精化二：契约按能力类，进程按外部对手方（待 Dexter 确认）

原提案目录是 能力/平台 二级。张力在右边：美团的授权/token/回调基建是**一套**，order 与 delivery 共用；按 `order/meituan`、`delivery/meituan` 拆成两个进程会复制平台管线或被迫抽共享库。建议：

- **契约按能力类**（`order-inbound` / `delivery-outbound` / …，每类一份端口契约，全平台共用）；
- **进程按外部对手方**（一个"适配器应用" = 一个外部凭证/授权域，内含多个能力模块）：`adaptors/meituan/{order,delivery}`、`adaptors/eleme/{order}`、`adaptors/fengniao/{delivery}`；
- 拼好饭若走美团开放平台同一套授权，则是 `adaptors/meituan` 内的一条业务线，不是独立应用；独立 API 才独立应用。

### 13.5 调用模型（建议）

**方向原则：主程序永远不知道适配器的地址。** 主程序只发布端口；适配器是双向的客户端。

```text
出站（主程序 → 外部）:
  主程序把意图写成任务行(DB outbox,带幂等键+binding 坐标)
  → 适配器拉取本平台任务 → 调平台 API(重试/退避在适配器侧)
  → 回报结果(主程序端口,任务状态+回执)

入站（外部 → 主程序）:
  平台回调 → 适配器先落盘(自己的存储)再按平台时限 ack
  → 转换为统一入站模型 → 投递主程序入站端口(带外部事件标识,失败重试)
  → 主程序幂等去重、快速持久、后处理
```

- **加平台零主程序改动，加能力类才改主程序**——这是可扩展性的判据；
- 新平台上线 = 部署新适配器 + 在渠道数据里配置模板/ProviderConfig/binding 坐标，主程序代码不动。

> **裁定（Dexter 2026-08-13）**：§13.4「契约按能力类，进程按外部对手方」**已接受**。

### 13.6 任务表容量模型（回应 Dexter 的数据量之问）

**原则：任务表是队列不是台账。** 数据量失控的唯一原因是把终态行永久留在队列表里。

| 数据 | 落点 | 保留策略 |
|---|---|---|
| 出站任务行（主程序侧唯一队列表） | 主程序 DB，按天分区 | 终态后留 7–30 天诊断，**DROP PARTITION 清理**（O(1)，无 vacuum 风暴） |
| 入站业务事实（订单/配送状态） | **直接进订单域业务表**（带去重键），主程序侧**不设入站队列** | 业务数据正常增长，与对接机制无关 |
| 适配器入站暂存（未投递成功的事件） | 适配器自己的库/schema | 投递成功后短保留即清 |
| 平台 raw 报文（审计/重放） | **MinIO 对象**（仓内已有），适配器 DB 只存索引行 | 生命周期策略 90–180 天 |
| 结算/审计必须的业务回执（如权益支付单） | 主权域业务表 | 永久——那是业务数据不是队列开销 |

**工作集有界（Little 定律）**：队列表的活跃行数 ≈ 吞吐 × 处理时延。稳态 10 任务/秒、平均 2 秒完成 → 在途仅约 20 行；只有平台故障时积压增长——**而积压可见正是想要的故障表现**，恢复后自然排空。

**写入量级**：激进假设全国规模 1000 门店 × 日均 3000 对接行 ≈ 3M 行/天 ≈ 35 insert/秒——对 PostgreSQL 是平凡负载。

**实现要点**：`FOR UPDATE SKIP LOCKED` 拉取（多 worker 无锁争用）；status 部分索引（`WHERE status IN ('PENDING','RETRY')`，轮询索引恒小）；`LISTEN/NOTIFY` 消空轮询；热表保持小（终态行批量外移），vacuum 永远便宜。

**诚实的边界**：持续数千任务/秒或需要复杂扇出语义时，PG 队列才需要换消息中间件——比本业务乐观预估仍高一个量级以上。且**端口契约不变，届时只换任务 API 下面的传输**,现在选 PG 不是死路。

### 13.7 健壮性规则（清单）

1. **主程序 DB 事务内禁止任何适配器/外部调用**（与 backend-acceptance 的事务/连接纪律同源）；
2. **双向幂等**：出站任务 taskId 幂等键；入站事件 (platform, externalShopId, externalEventId/seq) 去重；at-least-once + 去重，不假装 exactly-once；
3. **入站缺映射 fail-closed**：外部订单行解析不到菜单条目/商品 → 进"缺映射治理"态，不静默丢弃、不阻塞其他订单；
4. 平台故障表现为**任务积压可见**，不是主程序线程池耗尽（超时、有界重试、按平台熔断都在适配器侧）；
5. 适配器自身状态仅限传输事实（token/游标/raw/重试队列），业务事实一律回主程序；
6. correlation id 从平台事件贯穿适配器到主程序（复用既有 correlation 基建）；
7. **入站端口是真实 HTTP operation → 自动进入 backend-acceptance 分母**，新端口缺 scenario 即 fail-closed——适配器对接面天然纳入统一测试能力；
8. 命名一致性：`adaptors`/`adaptor`、`order`/`orders` 需定一个规范形并机器门守住（建议 `adapters` + 单数能力名）。

### 13.8 适配器的存储与凭证（回应 Dexter 第五轮三问之一、二）

**适配器绝不读主程序数据库。** DB schema 一旦被适配器直读，就成了第二套集成契约——内部任何迁移波及全部适配器，防腐层在数据层被击穿（与"编译依赖内部类"是同一个陷阱，换了层面）。且适配器承接公网回调，是外露攻击面，不应持有主库凭证。**全部交互只走端口。**

**适配器有自己的持久层，右尺寸 = 同 PG 实例、独立 schema、独立 DB 账号、零跨 schema 访问**：

- 每个适配器应用一个 schema（`adaptor_meituan` / `adaptor_eleme` / …），独立 role，互相不可见，主程序 schema 对它们也不可见；
- 只放**传输事实**：入站暂存（先落盘再 ack）、投递重试队列、同步游标、raw 索引（raw 本体在 MinIO）、动态 token；
- 将来规模需要时整 schema 迁独立实例，只改连接串，零代码——现在不为未来多付钱。

**ISV 凭证分两层，都不在主程序**：

| 凭证 | 落点 | 理由 |
|---|---|---|
| 静态 ISV 应用身份（developerId / 签名密钥） | **部署配置注入**（env / secret 文件），不进任何数据库 | 极少变更，不应随 DB 备份扩散 |
| 动态授权 token（per 外部店铺 appAuthToken / 刷新 / 有效期） | **适配器自己的 schema**，加密列 | 量多、自动刷新，是纯传输状态 |

**主程序永远只有 opaque ref + 治理信号**（"授权存在、有效至"），token 值不落主库、不过端口。授权失效表现为任务 typed 失败（`AUTH_EXPIRED`）→ 治理信号展示，**不自动改渠道 / binding / providerConfig 的 status**（v6 红线保持）。

### 13.9 ProviderConfig 的落点与初始化（回应第五轮三问之三）

**落点：主程序渠道域，PROJECT 级实体，挂在 BusinessChannel 下。** 零机密，最小字段候选：`providerKind`、`externalSystemCode`（指向哪个对手方/适配器）、`businessLineCode`、`displayName`、`status`、授权 opaque ref（本期留空）。详细字段按裁定 B 待定。

**初始化（第六轮修正，回应 Dexter「怕项目管理员手搓创建错」）：ProviderConfig 由系统自动派生，管理员不手工编排接线。**

Dexter 的质疑成立：适配器接了哪些平台、持有哪个 ISV 身份，是**部署事实**；模板定了业务线；对项目管理员而言 ProviderConfig 的"接线"字段**没有任何自由度**——手搓只有出错的机会，没有选择的价值。据此修正：

```text
0. 对接能力目录(系统级,非项目数据) —— 本部署实际接了哪些外部对手方、
   各支持哪些 providerKind;本期四个外部平台登记为 CONNECTOR_NOT_DEPLOYED
1. 模板目录声明平台默认(业务线、走哪个 externalSystemCode)
2. 项目管理员从模板开通渠道 → BusinessChannel (PROJECT)
3. 系统自动创建 ProviderConfig —— 全部接线字段由 模板 × 对接能力目录 派生;
   仅当同一平台真实存在多个可选对接方(多 ISV/服务商)时,管理员才做选择
4. 门店 binding 选择 providerConfigRef + 外部店铺坐标(这是门店真实的业务选择)
5. 授权在适配器侧完成 → 回填 opaque ref + 治理信号(连接器迭代)
```

管理员对 ProviderConfig 剩下的**真实**操作面：启用/暂停、显示名，以及内部自营渠道的入口配置（扫码 URL 模板等，带模板默认）。**fail-closed**：ProviderConfig 不得引用能力目录中不存在的 `externalSystemCode`；外部渠道在连接器未部署时可开通为 DRAFT 并展示"连接器未部署"治理信号，不得 ENABLED。

模板是目录、能力目录是部署事实、ProviderConfig 是二者在项目上的**自动投影**（v6 §5.3"模板不是实例"保持，但实例的创建者从管理员改为系统）。本期：实体 + 派生逻辑 + 只读为主的管理界面，授权字段留空。

**对接能力目录的形态与初始化（第七轮，回应 Dexter「这是个啥、谁在哪初始化」）**：

它就是一份 **checked-in 契约数据文件**（与 kind / template 目录同族，`contracts/registry/` 下一份 JSON），不是数据库表，不是后台页面，没有"运营初始化"这个动作。

- **内容**：对手方清单 × 各自支持的 providerKind / 能力类 × 能力状态（本期四个外部平台全部如实登记为 `PLANNED`——本版本尚无连接器）。
- **谁写**：随代码交付。本期由 Codex 按定稿需求创建并过契约门；**以后每次部署新适配器,同一次变更里更新这份文件**——部署本来就是代码/配置事件,顺手且可评审。
- **为什么不是 DB 表**：DB 表意味着某个人在某个界面手工录部署事实——把刚堵住的"手搓风险"上移一层、换个人手搓。
- **机器门**：`template.externalSystemCode ⊆ 能力目录键集`；ProviderConfig 派生只读此目录——引用不存在的对手方在结构上不可能。
- **连接器迭代起的两层运行时核验**（目录本身仍是唯一声明源）：
  1. 适配器启动**自报**（announce 到主程序端口）→ 与目录交叉核对：**未声明而自报 = fail-closed 拒绝**；声明而长期未见 = 治理信号；
  2. **心跳** = 健康信号，只展示，不改任何业务 status。

一句话：**目录 = 版本能力（checked-in），自报 = 部署核验（runtime），心跳 = 健康（runtime）**；三者谁也不自动改渠道业务状态。

**生效方式（第八轮，回应「更新了 JSON 主程序要不要重启」）**：

**随发布生效，即主程序经历一次常规重启——这是刻意选择，不是缺陷。**

- 目录只在**上新平台**时变化，频率极低（年级别几次），且那本来就是一次发布事件（新适配器要部署）；目录行与适配器在**同一次发布**里到位，顺路。
- **不建热加载**：为年级别几次的事件建 reload 机制，买到的是省一次重启，付出的是缓存一致性、多实例同步、磁盘文件与已评审版本漂移三种新失败模式——不划算。
- 重启无业务影响：已派生的 ProviderConfig 实例不受目录更新影响（只有**新开通**读新目录）；渠道/binding/订单数据全部无关。
- **未来若真需要"不发版上平台"**（例如运营团队独立上平台）：正确形态不是热加载文件，而是目录**毕业为 platform-admin（运维管理后台）管理的运维数据**——录入者是部署适配器的运维团队而非项目管理员，手搓风险可接受且有校验。那是它的第二形态，**频率证明需要之前不建**。

扩展性判据据此精化：**加平台 = 部署新适配器 + 一行目录数据；主程序零代码改动，随下一次常规发布生效。**
