## 0. 分桶规则(先说清楚,免得逐条争)

| 桶 | 装什么 | 处理方式 |
|---|---|---|
| **第零** | 已 ✅ 亲验 + 修复面 ≤ 几行 + **不需要任何规范或产品决策** | 立即修,不等任何东西 |
| **第一** | 通用后端编码规范类 | **先沉淀规范,再按规范整改** |

**两条切分原则**(源于实际过一遍时发现的问题):

1. **按动作分,不按 finding 分。** 同一条 finding 常同时有规范面和 bug 面(最典型是 M-08),允许一条出现在两个桶里,但**必须标依赖顺序**。
2. **第零桶的准入是硬的**:⚠️ 未亲验的一律不进,哪怕看起来只改一行。本轮已有四条断言(M-05/M-06/M-07/S-06)因"没打开源码、靠命名和行号推断"被推翻。

## 2. 第一部分 · 通用编码规范

### 2.1 规范沉淀的两条约束(先定这个,再写内容)

1. **只写"判据自带反例"的规则。** 不写「应当避免过度设计」;写「网络 I/O 不得出现在 `@Transactional` 方法内。**反例:方法带 `@Transactional` 且方法体内出现 `objects.put` / HTTP client 调用,即不成立**」。
2. **一个权威源。** 规范文档是唯一权威;**门只实现其中机器能便宜验的子集**;skill 与项目记忆**只放指针,不放内容**。同一条规则写四份必然漂移——那正是 S-01 那 26 处多拼写回退的同构问题。

**上限提醒**:evidence / package / hash-chain 那 11070 行本质就是"把规范沉淀到门里",结果是**门全绿、功能是坏的**。这一轮的规范如果超过"半小时能读完 + 门跑在分钟级",就是在重建刚退役的东西。
