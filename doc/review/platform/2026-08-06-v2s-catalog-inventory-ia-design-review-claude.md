# IA 设计独立评审

## 0. 结论

**`NO-GO` — `M=1 / S=2 / N=3`。**

> **本轮内 Dexter 已即时裁决一条**：商品与菜单不属于标准表格，不受统一表格约束，无需单独编码列。
> 我原提的 `S-01` 据此撤销，降为 `N-03`（仅剩“把该设计例外登记进标准”这一动作）。计数按裁决后口径给出。

**这不是"质量差"的 NO-GO。** 这份 IA 的工程质量在我评审过的设计里属上乘：
89 个 IA-ID 的 exact-set 我独立复算为 **89/89、双向零 orphan**；
16 个被引用的 foundation API **全部真实存在**；
建议注册节点的字段形状与真实 `admin-catalog.json` **逐字段吻合**；
`HAS_SKU` 判据、复制闭包算法、九类兼容矩阵都与源码/需求**逐条可复算**。

判 NO-GO 的唯一原因是：**Dexter 明确裁定过的一条需求在 IA 中完整缺失，
而且它是被"需求→IA 映射表"整节跳过导致的**——这同时证伪了本文最核心的自我主张
（"所有需求要点都可以被实施过程跟踪和对账"）。修复量很小，但机制失效必须记名。

## 1. 方案合理性判断（Dexter 特别要求：先问这活儿到底解决什么业务问题）

我先不看 review 清单，独立回答三个问题。

**问题对不对？** 对。本期要解决的是：总公司为品牌维护标准商品与配方，门店把它们复制过来、
维护本店商品、配库存对象与 BOM、做入库盘点调整、并能反查"这个料为什么在掉"。
IA 的三页与这条链完全对应，没有夹带菜单、销售发布或交易。

**方案优不优？** 主体优。我特别认可三处：
其一，**先选左树结果域、再在域内搜索**（`IA-CAT-LIST-012`）——
它把"关键词到底搜哪儿"这个 v4 用户最容易误解的点显式化了，还把左树本地搜索与商品查询
在 state、placeholder、operationId、locator 四个层面强制分离；
其二，**形态准入先于 modeRules 的两层结构**（§9.2）——这解决了 v4 里隐式派生的那一层，
服务费/权益壳不会因为 `NO_SKU` 误获三态库存模式；
其三，**人工调整独立于库存增加**（`IA-INV-ACTION-ADJUST-001`），
并诚实声明"v2s 新增、不宣称继承 v4"，理由是"避免把纠错动作伪装成现场新增库存"——
这与 v6 的 `MANUAL_ADJUSTMENT` vs `STOCK_IN` 两个流水来源是对齐的，不是加戏。

**代价配不配？** 基本配。我原本认为有两处为继承 v4 密度而偏离双后台统一标准，
但 Dexter 当场裁定商品/菜单类工作台本就不在统一表格标准射程内——**该前提不成立，S-01 撤销**。
剩下 `S-02`（详情两列网格 fork 了 foundation 的布局常量）仍需处置。

**是不是只为了凑 GO？** 我判断不是。反证有三：
§13 明确写了 Round-2 的 GO 只覆盖旧 hash `120b69b2…`、`DEC-IA-03` 之后需另开 cycle，
**没有拿旧 GO 冒充当前字节通过**；`C-16/C-17/C-19` 三项老老实实标 `DEXTER_DECISION`
并把推荐项与影响面分开写；`IA-NAV-003` 主动点出"注册不是只加四个 JSON 节点"。
这些都是给自己加难度的写法。

## 3. Findings

### M-01｜需求 §5.6.4 整节未落地，「从品牌复制」按钮无条件渲染

**位置**：§5.1 `IA-CAT-LIST-009`（行 240）、线框行 244、§12.2 `C-03`；映射缺口在 §11.1。
**依据类型**：仓内事实（需求稿原文 + IA 全文扫描 + 映射表比对）。

需求稿 §5.6.4 有 Dexter 2026-08-06 的明确裁定：

> `head_company_id` **可空**，因此存在没有关联总公司的门店。
> 这类门店**不显示「从总公司商品库复制」这个按钮**——不是灰掉、不是点了报错，是**入口不出现**。

**IA 全文对此零命中**：「无总公司」「没有总公司」「未关联总公司」「head_company」四个检索词均 0 处；
「从品牌复制」出现 5 处，**每一处都是无条件渲染**。

`IA-STATE-007` 定义的隐藏规则只覆盖**权限**维度（无"编辑商品库"能力则写按钮不渲染），
而"门店没有总公司"是**数据条件**——用户有能力、按钮照渲染，点下去要么空来源列表要么报错，
**正是 Dexter 明令要避免的两种形态**。

**更严重的是机制失效**：§11.1 主需求映射表从「§5.6.3 九类兼容矩阵」直接跳到「§5.6.5 单一能力」，
**§5.6.4 整节没有任何一行**。本文 §0 与 §11 的核心主张是"所有需求要点可被实施过程跟踪和对账"，
而这条恰恰是被对账表本身漏掉的——说明映射不是从需求稿逐节推导出来的。

**影响**：实现者按当前 IA 会做出错误行为；且无法排除映射表还漏了别的（我逐节比对后认为
§5.6.4 是唯一整节缺失，但这个结论是我复算的，不是文档自证的）。

**最小修复**：
1. 给「从品牌复制」加一条数据条件渲染规则，分配稳定 IA-ID，并写明与 `IA-STATE-007`
   的权限隐藏是**两条独立规则**（一条看能力、一条看数据），不可互相替代；
2. 顺带落地 §5.6.4 的另一半——复制来源从 `organization.store` 的
   `head_company_id + brand_id` 直接读出，**无需来源选择器**；
3. §11.1 补 §5.6.4 行；并声明映射表是**逐节遍历需求稿**产出的，而不是按印象罗列。

### ~~S-01~~ → **N-03｜Dexter 已裁决：商品与菜单不属于标准表格，不受统一表格约束**

**但保留一条文档层面的最小残留**（不是设计问题，是白纸黑字的冲突）：

`crud-presentation-standard-catalog.json` 的 `scope` 目前写的是
**"Both administrative applications: CRUD list query, primary-entity columns and detail surfaces"**，
`rules.primaryListIdentity` 仍要求主实体编码独立成列。
**该标准的文本尚未反映"商品/菜单类工作台不在其射程内"这条裁决**。

**影响**：下一个评审者（人或 subagent）读到标准与 IA 会再次判定冲突，
重复消耗一轮；实施期若有人按标准原文对齐，也会把复合主列改回分列。

**最小修复（Dexter 2026-08-06 已同意：“商品管理这里可以加一下设计例外”）**：
在 `crud-presentation-standard-catalog.json` 中为商品管理登记**设计例外**——
声明该标准适用于组织、门店、合同等标准 CRUD 列表，

**这是一条文档登记动作，不改任何既有实现，也不影响本 IA 的设计结论。**

### S-02｜`CatalogItemFactGrid` 与 foundation 的详情布局是同一关注点的两份实现

**位置**：§10.2（行 884）。
**依据类型**：仓内事实（foundation 源码 + `CLAUDE.md` 约束）。

IA 以「foundation 的 `adminDetailDescriptionsProps` 固定单列」为由，
在 operations app 内新增 `CatalogItemFactGrid`，并声明"不是重复造 foundation"。

**单列这个事实我核实属实**（`overlay/drawerSurface.ts:19` `column: 1`，
`foundation.test.ts:78` 有断言）。**但结论我不同意。**

`adminDetailDescriptionsProps` 位于 `overlay/drawerSurface.ts`——它就是 **Drawer surface** 关注点，
而 `CLAUDE.md` 明令「禁止在 `apps/frontend/*` 重复实现相同的生命周期、**Drawer surface**、
overlay lock、列表上下文、HTTP protocol、observability 或 automation primitive」。
更关键的是，`column: 1` 是**被 foundation test 断言的常量**——
它是双后台共享的详情布局标准，不是一个偶然的默认值。
在 App 内另起一个两列网格，等于为本域 fork 了这个标准，
而 IA 用"不是重复造"一句话带过，没有登记这次 fork。

**影响**：商品详情与组织/合同详情的信息密度与布局分家；
未来第三个域再有两列需求时，会再 fork 一个。

**最小修复（二选一，都要显式登记）**：
① **推荐**——把列数参数化进 foundation（保持单一真相与双后台一致性，改动很小）；
② 若坚持 App-local，则必须按 `CLAUDE.md` 要求**说明 foundation 未覆盖的原因**，
并把"本域详情为两列"登记为对既有布局标准的显式偏离，而不是称其为非重复实现。

### S-03｜`PRODUCIBLE` 能力枚举位在 IA 中完全消失

**位置**：§9.1 `IA-CONTRACT-002` / `IA-CONTRACT-008`。
**依据类型**：仓内事实（需求稿 §5.3 事实 11 + IA 全文扫描）。

需求稿明确：

> **`PRODUCIBLE` 在当前七形态中不被任何形态派生**——按"模型必须完整"保留为枚举位，
> 等生产域进入时再由相应形态派生，本期不产生该值。

**IA 全文对 `PRODUCIBLE` 零命中。** `IA-CONTRACT-002` 只说"能力派生"，
`IA-CONTRACT-008` 只泛称"封闭集合"，都没有把这个枚举位钉住。

**影响**：实现者从七个形态反推能力闭集会得到
`{SELLABLE, STOCK_MANAGED, BOM_COMPONENT}` **三值**，`PRODUCIBLE` 被丢掉——
直接违反 Dexter「模型必须完整，不能因为场景未到就忽略」这条已冻结原则。
它是契约级闭集，后补要改契约。

**最小修复**：在 `IA-CONTRACT-002` 或 `008` 明写能力闭集为四值，
并注明 `PRODUCIBLE` 本期不被任何形态派生、UI 不展示、但**必须在契约枚举中存在**。

## 5. 对 Codex 四个问题的直接回答

**一、当前 IA 是否足以约束后续 implementation agent 不走偏？**
**大部分足够，一处不够。** 搜索语义、形态两层准入、复制闭包、九类兼容、owner 边界、
状态与恢复分母都定得很死，实现者没有发明空间。**但 M-01 那条会让实现者做出错误行为**，
因为 IA 里根本没有那个条件；修完之后我认为足够。

**二、"树节点结果域内搜索"是否从视觉、状态、请求参数、竞态、测试分母五层闭合？**
**五层都闭合了。** 视觉有"当前结果域"条（§5.1 线框）；
状态上左树本地搜索与商品查询不共用 state；
请求参数是 `selectedTreeNode(kind, ref) + keyword + 其余筛选 + cursor` 联合；
竞态由 scope/owner/tree-node identity/generation 携带 + 旧响应丢弃；
测试分母在 §5.3 的"查询事实—来源矩阵"逐行给了读回证明。
**一处可加强**：`IA-CAT-LIST-012` 说切换树节点"保留已输入关键词并立即重新查询"，
这个行为对用户是好的（同一关键词比较不同分类），但它意味着**一次点击触发一次查询**——
建议在 IA 里明确它与防抖/取消的关系，否则实现者可能连点树节点打出一串请求。

**三、是否存在更简单、更符合用户任务的替代方案？**
**有一处**，即 S-01 的"编码保留独立弱化列 + 名称/分类/标签复合"——
它同时满足既有产品标准与 v4 密度，且不需要修订标准。其余方案我没有找到更简的替代。

**四、当前结论是否只覆盖 IA DESIGN？**
是。本 `NO-GO` 只表示当前字节的 IA 尚不能进入 Dexter 终确认，
**不构成也不否定任何实施、契约、环境或数据授权**。

## C-16｜权益商品壳的本期 UI 暴露 —— **出现，但创建时置灰不可选**

> Dexter 原话：「界面上都要出现，但是新建的时候权益商品壳这个选项是灰的，不能选。」

**注意这不是我提的两个选项中的任何一个。** 我提的 ② 是"左树保留零计数、
新建对话框里**不出现**该形态"；Dexter 的裁决是**新建对话框里出现但置灰**。
后者更好，理由是它多传递了一层信息——"系统认识这类商品，只是还没开放"，
而不是让用户以为系统不支持。

**落地要点**：

1. 左树形态段列出「权益商品壳」并显示计数（本期恒为 0），与"零计数仍显示"的既有规则一致；
2. **新建商品的形态选择里该项可见但 disabled**；
3. **置灰必须带原因文案**——这是 `IA-STATE-007` 已确立的规则
   （"有写 capability 但因状态、引用、owner 或字段事实不可执行时，按钮 disabled 并显示具体原因"）。
   建议文案指向"权益域尚未开放"这一真实原因，不要用笼统的"不可用"；
4. 契约侧七形态全集不变，`itemKind` 枚举位保留。

## C-17｜规范编码创建后统一不可修改 —— **采纳**

> Dexter 裁决：统一不可修改。

覆盖商品、分类、标签、销售单位、SKU 销售属性与属性值、SKU、商品处理标签、库存对象。

**理由（评审期已论证）**：编码是门店从品牌复制的判同键。若可修改，
门店改码后下次复制会按新码判定"不存在"而**重复导入一份**，
静默产生重复商品并一路流进菜单。"未被引用时可改"挡不住这条路径——
新建对象天然未被引用，而复制判同不看引用。

**建议一并落地的配套**（降低"录错只能重建"的代价）：
创建时提供编码即时唯一性校验与格式提示（v4 帮助文案已是此思路），
并允许**未被任何对象引用的记录整体作废重建**——是作废重建，不是改码，
判同键因此始终未曾变化。

## C-19｜复制判同 tuple —— **采纳 ①（按对应商品/SKU 认，不另发编码）**

> Dexter 裁决：①。

即 IA §8.5 的推荐 tuple：库存对象按 `(targetType, itemCode, skuCode?)`；
SKU 按 `(itemCode, skuCode)`；属性值按 `(attributeCode, valueCode)`；
BOM 按 `(ownerType, itemCode, skuCode?/optionValuePath?)`；
其余对象按 `(objectType, code)`。**不为库存对象另设自身编码。**

**支持该裁决的实证**：v4 库存现状列表每行显示的是
「意大利面 / `ERP-MAT-SPAGHETTI` / 商品」——**那个编码是商品的编码，
库存对象在 v4 中根本没有独立编码**。这与用户心智一致：
运营者只会说"咖啡豆的库存"，不会说"编码 ST-001 的库存对象"。

**仍然生效的硬约束**（IA 已写明，此处重申）：界面、后端 owner、数据库唯一约束、
复制预检**必须使用同一套判同方式**。最怕的失效是 UI 按商品编码判"已存在"、
数据库却按另一套键建唯一约束——那会产生"界面说重复但写入成功"或反向的不一致。
