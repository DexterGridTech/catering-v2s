## 记录 001 · 2026-08-18 · Dexter 口述原文(逐字)

> ## 4.2 外部平台能力分类
>
> 原 “外部平台六类分类学” 定义需要做部分调整。该分类命名为**能力分类**，分类之间并非互斥，一个外部平台可同时具备多类能力；每一类代表一组标准动作与能力。分类划分如下：
>
> 1. 主数据同步
> 2. 用户与权益
> 3. 团购
> 4. 外卖
> 5. 库存
> 6. 外卖配送
> 7. 订单同步
>
> 每一类内部还会细分能力属性。例如团购：团购商品支持外部映射内部商品，还是必须内部映射外部商品。例如外卖：仅支持拉取外部菜单做内部映射，还是支持将本地菜单同步到外部平台。因此建议：外部平台类型以及其所具备的能力模型，应当在 contract 中提前定义（可以先占位，用到哪个加哪个，但成本要低，不能变化一个地方很多代码都要动）。
>
> 另外存在一个问题：当前经营渠道与外部平台对接绑定耦合过强，灵活性不足。例如现有 `BUSINESS_CHANNEL->BUSINESS_CHANNEL_PROVIDER_CONFIG->BUSINESS_CHANNEL_BINDING` 三层结构；后续做团购业务时，又会出现一套 `CHANNEL->PROVIDER_CONFIG->BINDING` 的三层结构，二者属性大概率相同。希望对这层关系做抽象解耦。
>
> 之前分析外部平台对接，调用链路为：`apps/backend/catering‑business‑server <-> apps/backend/adaptors/xxx <-> 外部平台`。
> adaptors 与 catering‑business‑server 共享两类契约：
>
> 1. TEMPLATE（外部平台声明等模板）契约；
> 2. 该 TEMPLATE 下 adaptor 当前可用的 PROVIDER_CONFIG（对接外部平台的身份凭证）契约；
>
> 该契约定义了 adaptor 可对接哪些外部平台、以及对接方式。
>
> BINDING 的作用：完成系统内部经营主体与外部平台经营主体之间的映射（分为需要授权、无需授权两种）。希望将以上三个对象做抽象，不再仅服务于经营渠道，所有外部平台接入均复用这套定义。示例对象：`xxx_outer_system`、`xxx_provider_config`、`xxx_owner_binding`（下文仅以此作为示意，你建议其他正式命名）。
>
> 1. `xxx_outer_system`（一对多能力分类，且能力分类携带具体能力属性值）与 `xxx_provider_config` 在系统启动时预制，**不区分集团空间**；`xxx_owner_binding` 由 catering‑business‑server 在运行时配置，**按集团空间隔离**。
> 2. 一个外部平台仅对应一个 `xxx_outer_system`，可同时承载外卖、团购、配送等多类业务，支持一对多能力分类。
> 3. `xxx_provider_config` 需要约定该 provider 支持的业务范围；例如 A provider 仅支持外卖，B provider 同时支持外卖 + 团购，支持一对多能力分类。（因为美团对ISV的能力授权是可能不一样的）
> 4. `xxx_provider_config` 还需要约定下属 `xxx_owner_binding` 允许绑定的组织节点类型。现有 5 类组织节点：集团、大区、项目、总公司、门店。
>
> > 该配置仅表达允许绑定的节点类型，**不用于权限、数据校验**。
> > 示例：交易主数据类外部平台，通常仅允许绑定集团节点；订单权益类外部平台，集团、大区、项目、总公司、门店五类节点均可绑定。例如集团统一会员卡券系统、项目专属会员卡券系统、门店自有会员卡券系统。
> > 以美团外卖、团购举例：项目可作为主体在美团开店，售卖各门店商品，绑定系统内项目节点；门店也可独立在美团开店，绑定系统内门店节点。
>
> 5. `xxx_provider_config` 需要约定下属 `xxx_owner_binding` 的认证类型：部分需要跳转外部平台完成授权才算绑定成功；部分仅需在系统内部完成内外主体映射；还有部分无需做主体映射（例如对接门店自有会员卡券系统，天然对应当前门店，无需额外映射）。
> 6. `xxx_provider_config` 可同时支持多项业务（如外卖、团购）；`xxx_owner_binding` 需要标识自身支持的业务集合，该集合必须是 `xxx_provider_config` 支持业务的子集。
>
> > 示例：同一个门店在美团开设两个店铺，分别专做外卖、专做团购，则对应两条 `xxx_owner_binding`。
> > 注意：美团：两项业务对应两个店铺 ID、两套授权；饿了么：两项业务共用一个店铺 ID、两套授权。
>
> ### 用户旅程（运维管理员‑platform admin）
>
> 1. 运维管理员在运维管理后台（platform admin）的【外部系统接入配置】页面（需先切换至指定集团空间），可查看该集团空间下全部 `xxx_outer_system`、`xxx_provider_config`、`xxx_owner_binding`。
> 2. 页面左侧以树形结构展示 `xxx_outer_system` 与 `xxx_provider_config`。
> 3. 在树节点点击 `xxx_outer_system`，右侧展示详情面板，支持控制该 `xxx_outer_system` 在当前集团空间是否启用。
> 4. 在树节点点击 `xxx_provider_config`，右侧包含两个 Tab：
>    - Tab1【详情】：支持控制该 `xxx_provider_config` 在当前集团空间是否启用；
>    - Tab2【绑定关系列表】：标准可搜索、可分页表格，展示当前集团空间下该 `xxx_provider_config` 的全部 `xxx_owner_binding`；点击表格首列，以抽屉弹窗展示该条 `xxx_owner_binding` 的详情。
> 5. 按 provider 的认证类型区分操作权限：
>    - 若 `xxx_provider_config` 对应的 `xxx_owner_binding` **不需要跳转外部平台授权**：platform‑admin 允许对 `xxx_owner_binding` 执行增、删、改；
>    - 若 `xxx_provider_config` 对应的 `xxx_owner_binding` **需要跳转外部平台授权**：platform‑admin 仅允许执行删除操作。
>
> > 以上为外部平台协作的配置管理部分。
>
> 回到经营渠道模块：需要由项目定义经营渠道模板，模板至少包含以下级联维度：
>
> 1. 渠道接入类型：内部、外部
> 2. 经营主体类型（菜单维护方）：项目（项目可作为统一主体在美团开设店铺，承接外卖或售卖团购券，后续由项目自行和门店结算）、门店
> 3. 渠道订单类型：到店（仅内部）、外卖（内部 / 外部）、团购（内部 / 外部）
> 4. 到店点餐形式（订单类型为到店点餐时生效）：POS、扫码、自助机
>
> ### 用户旅程（运营人员）
>
> 1. 运营管理后台（operation admin）提供两个页面：
> -【项目经营渠道管理】：集团、大区、项目节点角色可访问，数据节点定位到项目；
> -【门店经营渠道管理】：集团、大区、项目、门店节点角色可访问，数据节点定位到门店。
> 2. 在【项目经营渠道管理】页面，页面上半部分用于对经营渠道模板执行 CRUD；若创建的是外部渠道模板，则需要基于**能力分类**，从运维管理员已对当前集团空间开放的 `xxx_outer_system` / `xxx_provider_config` 中做选择。页面下半部分用于创建经营主体类型为**项目**的经营渠道实例。
> 3. 在【项目经营渠道管理】页面，若经营渠道模板为外部接入类型，则可初始化并维护对应的 `xxx_owner_binding`（行为受 `xxx_provider_config` 定义的认证类型约束）；`xxx_owner_binding` 状态有效（需授权的必须完成授权认证）后，该经营渠道方可生效。
> 4. 在【门店经营渠道管理】页面，支持对门店所属经营渠道执行 CRUD；选择模板时，仅展示上级项目维护、且经营主体类型为门店的全部经营渠道模板。若为外部接入类型，则可初始化并维护对应的 `xxx_owner_binding`（行为受 `xxx_provider_config` 定义的认证类型约束）；`xxx_owner_binding` 状态有效（需授权的必须完成授权认证）后，该经营渠道方可生效。
> 5. 经营渠道不做唯一性校验；同一个模板允许创建多条渠道实例。示例：某海底捞门店可在美团开设两家外卖店铺，分别命名为海底捞盖饭、海底捞冒菜。
> 6. 后续每个销售菜单（本期暂不实现）绑定一条有效的经营渠道。

## 记录 002 · 2026-08-18 · Claude 首轮判断

### A · 我认为对的三点

**A-1 · 能力分类取代平台分类,方向正确。**
2026-08-13 的记录里已经观察到「平台与类正交(美团横跨 2/3/4 类)」,但当时的模型仍是**给平台分类**。
现在改为**给能力分类、平台一对多持有**,模型终于和已观察到的事实一致。

新旧七类/六类还有一处实质变化:旧分类是**按数据流向**切的(订单创建 / 订单配送 / 交易结果同步),
新分类是**按业务形态**切的(团购 / 外卖 / 外卖配送)。后者更贴近商户心智
(「我在美团做外卖,也做团购」),也正好对上第 6 条 —— binding 声明自己的业务子集。

**A-2 · 三层抽象通用化,是正确的解耦。**
避免了团购再长一套同构的 `CHANNEL/PROVIDER_CONFIG/BINDING`。
判据是清楚的:这三层表达的是「外部系统是谁 / 我以什么身份接它 / 我的哪个经营主体对上它的哪个主体」,
**与"这是不是一条下单入口"无关**。经营渠道只是它的第一个消费者。

**A-3 · provider 承载 ISV 能力差异,抓到了真实约束。**
「美团对 ISV 的能力授权可能不一样」是本次最有价值的一条事实 ——
它决定了能力范围**不能挂在平台上**,必须挂在 provider 上。
美团(两业务 = 两店铺 ID + 两套授权)与饿了么(两业务 = 一店铺 ID + 两套授权)的对照,
正好证明 binding 的条数**不能由我们规定**,只能由 provider 的认证形态决定。这个反例应当进验收判据。

### B · 需要收紧的四点(建议,待 Dexter 裁决)

**B-1 · 「订单同步」与「外卖 / 团购」是否同一层?**
若外卖与团购各自都会产生订单回流,则「订单同步」会挂在几乎每个平台上,
该分类**不携带区分信息**。两种候选理解:
(a) 订单同步是**独立能力**(例如只做订单回传、不做菜单与履约的平台);
(b) 订单同步是外卖 / 团购的**产物**,应当降为能力属性而不是并列分类。
⚠️ 未裁决前不要写进契约枚举。

**B-2 · 「定义全局」与「启用按集团空间」是两套存储,必须显式分开。**
第 1 条说 outer_system 与 provider_config **不区分集团空间**;
但 platform-admin 旅程第 3、4 条要**按集团空间控制启用**。
⇒ **定义是全局的,启用状态是按集团空间的**。这是两个不同的对象与生命周期。
另需与 2026-08-13 已定的「对接能力目录是 checked-in 契约 JSON、不是 DB 表、随代码交付」对齐:
建议**定义仍走 checked-in 契约**,**只有启用状态与 binding 进数据库**。
这样"新增一个平台 = 部署适配器 + 一行目录数据 + 随下次发布生效"这条判据可以保持不变。

**B-3 · 「允许绑定的节点类型不用于权限、数据校验」——必须把这句话钉进契约字段语义。**
它是**展示与可选性约束**,不是授权。这类字段最容易在半年后被某个实现当成鉴权依据。
建议命名上就带出来(例如 `bindableNodeTypes` 并在 schema description 明写
「presentation constraint only; authorization is not derived from this field」),
并配一条机器判据:授权路径不得读取该字段。

**B-4 · 命名建议。**
`xxx_provider_config` 里的 **config 是误名** —— 它承载的是「支持哪些业务、可绑哪些节点类型、
认证形态如何」,这是**能力档案**不是配置。建议:

| 示意名 | 建议正式名 | 理由 |
|---|---|---|
| `xxx_outer_system` | `external_system` | 平台身份,全局唯一 |
| `xxx_provider_config` | `provider_profile` 或 `provider_capability` | 它声明能力与约束,不是配置项 |
| `xxx_owner_binding` | `owner_binding` | 语义已准确,保留 |

owner 模块建议独立命名(例如 `collaboration`),明确它不属于渠道域。

### C · 会推翻现有冻结结论的两处(必须显式作废,不能默默改)

**C-1 · 经营渠道模板从「预置 7 条目录」变成「由项目定义 + 四维级联」。**
现冻结文档 §10.2 的 `BusinessChannelTemplate` 是**预置目录**,含 7 个 `templateCode`
(`tpl_pos` / `tpl_mall_qr` / `tpl_mall_delivery` / `tpl_meituan_takeout` / `tpl_eleme_takeout` /
`tpl_douyin_takeout` / `tpl_pinhaofan`)。本次改为**项目自建、四维级联**
(接入类型 / 经营主体类型 / 订单类型 / 到店点餐形式)。
⇒ §10.2、FR-CT、FR-CH 的模板相关条目、以及 D 系列中「起步渠道清单」一并失效,需重写。
另注意:**到店点餐形式新增「自助机」**,原清单只有 POS 与商场扫码。

**C-2 · 「经营渠道不做唯一性校验」直接推翻 R-1。**
2026-08-13 Dexter 已裁定 R-1 **采纳**:「同项目同模板至多一条渠道(多经营点走多绑定)」。
本次原文:「经营渠道不做唯一性校验;同一个模板允许创建多条渠道实例」,并给出海底捞盖饭 /
海底捞冒菜的实例。⇒ **R-1 作废**,改由多渠道实例承载多经营点,binding 随渠道实例走。
这会影响 §10.4 的 `channelCode` 项目内唯一约束,需重新表述。

### D · 关于「成本要低,不能变化一个地方很多代码都要动」

这是本次最硬的一条非功能要求,建议把它落成**可检验的判据**而不是愿望:

- 能力分类与其能力属性,形态是**契约中的枚举 + 每类一份属性 schema**;
- **新增一个能力分类 = 加一个枚举值 + 一份属性 schema**,不新增表、不改 owner 代码、
  不改前端页面结构;
- **新增一个外部平台 = 加一条 external_system 定义 + 其 provider_profile**,主程序零代码改动;
- binding 的业务集合是该枚举的子集,子集校验由契约与 owner 共同保证。

⇒ 验收判据可以写成:「新增一个能力分类,改动面必须落在枚举与 schema 两处;
若需要改 owner 代码或页面结构,则该抽象未达标。」

## 记录 004 · 2026-08-18 · Dexter 澄清节点路径(逐字)

> 关于节点，有两类节点，一类是购物中心组织，集团->大区->项目，是一棵树。另一个是租户组织，总公司（可空）->门店。门店一定会有一个项目。所以集团->大区->项目->门店这个路径是唯一的，是能连起来的，至于现在有没有现成的service和接口不重要，逻辑关系在那里，后面需要再加呗。
>
> 关于规则，是的，千万不要过度设计，现在需要的就是各种属性或常量的定义。有个地方能描述其名称、业务含义就好了。

**Claude 更正**:先前以 `OrganizationHierarchyService` 只把 `REGION`/`PROJECT` 建成树为由,
提出「不是纯树、不能按父链遍历」。该表述**混淆了实现现状与业务模型**,已按 Dexter 更正撤回。
业务关系是确定的,service 后补即可。

**保留的有效结论:路径是两条,不是一条。**

- 购物中心侧:集团 → 大区 → 项目
- 租户侧:总公司(可空) → 门店
- 连接点:门店 → 项目
