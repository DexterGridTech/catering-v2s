# catalog 整改:方法、优先级与维度清单(冻结)

- 性质:方法约定。Dexter 2026-08-13 确认。后续三步产出均以本文为判定基准。
- 范围:catalog 一个 feature(Dexter 裁定),含 operations-admin 前端、契约、edge/owner、数据库。

---

## 1. 三方输入与冲突优先级

输入:**IA**(`doc/plans/platform/2026-08-06-…-information-architecture-codex.md`,89 IA-ID)、**详设**(`…-three-stage-implementation-design-codex.md`)、**v4**(`../catering-server-v4/frontend/apps/catering-operations-admin/src/resources/catalog-items` 及 2026-08-05 活环境复核记录)。

**核心规则(Dexter 原话)**:三方之间**没有明确的功能或模型定义冲突**时,**以做得最好的方案作为整改标准**;**v2s 自身的模型缺陷不算冲突**。

| 情形 | 判定 |
|---|---|
| IA **明确否决**过 v4 做法(导入导出、菜单/渠道引用列、总部来源禁用等) | **以 IA 为准**——已裁决,不进"取最优" |
| IA 未定义、v4 有成熟做法 | **以 v4 为准** |
| IA 与详设冲突 | **以 IA 为准**,详设标为待修 |
| v4 好做法需要 v2s 模型/接口/契约支撑而当前缺失 | **不是冲突,是 v2s 缺陷** → 纳入整改补建 |
| 三方均未定义 | **`DEXTER_DECISION`**,不自行发明 |

## 2. 分层(六层)

Dexter 指定:**模型、业务逻辑、接口、契约、控件、交互**。

**追溯方向(第二步用)**:从用户任务倒推,逐层验证支撑是否存在——

```text
用户任务 → 交互形态 → 控件 → 契约(请求/响应形状) → 接口(operation)
        → 业务逻辑(owner 语义/校验/事务/幂等) → 模型(表/约束/类型)
```

理由(Dexter):「交互选择最好的了,但是后台跟不上也不行。」任一层缺失,交互都落不了地;整改单元必须**跨层绑定**,不得前端先做、后台后补。
