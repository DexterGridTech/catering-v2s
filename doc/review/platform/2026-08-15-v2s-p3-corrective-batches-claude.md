# 批次 C1 · 后台建模矫正

## C1-1 · 无销售属性的 SKU 被堵死(已落地,最急)

**业务场景**:店家新建「宫保鸡丁」,**不建任何销售属性**,直接加两条规格:
「小份 ¥28」「大份 ¥38」——名字自己打。
`STANDARD_SALE_COUNTED`(普通计数销售)、`STANDARD_SALE_WEIGHED`(称重销售)、`COMPOSITE`(套餐)
**三个最常用形态的 `skuMode` 都是 `OPTIONAL_TABLE`,字面意思就是"属性表可选"。**

**缺陷事实** ✅ 三个构件交叉造成:
`variant_combination_digest TEXT NOT NULL`(`V20260814_100000_000:15`)+
偏索引 `(item_ref, variant_combination_digest)` **无空值豁免**(`:27`)+
空组合返回同一个常量(`skuVariantCombinationDigest`)。

**用户遭遇**:加「小份」成功;加「大份」**被拒**——两条 digest 相同撞唯一约束。**店家什么都没做错。**

📗 v4 把该列做成**可空**、偏索引带 `is not null`,所以没属性的 SKU digest 为空、互不冲突。

**要成立的**:同一商品可以有**任意多条不带属性值的 SKU**;有属性值的仍然组合唯一。

**判别性测试**

| 用例 | 断言 | 挡住什么 |
|---|---|---|
| 无属性多 SKU | 同一商品连建 3 条无属性 SKU,**全部成功**且各自可独立改名改价 | 现状:第二条就被拒 |
| 有属性仍唯一 | 同一商品两条 SKU 属性组合完全相同 → **拒绝** | 放开空组合时顺手把有属性的唯一性也放开了 |
| 混合 | 一个商品同时有"无属性 SKU"与"有属性 SKU" → **需产品裁定是否允许**,见下 |

> **`DEXTER_DECISION`**:一个商品能不能同时存在"无属性 SKU"和"有属性 SKU"?
> 我倾向**不允许**——那意味着同一个商品处在两种模式里,用户看到的规格列表会一半自动一半手填。
> 未裁定前按**不允许**实施(切换模式时走 C4-1 的确认流程)。

## C1-2 · 字典的属性→值从属关系,归 P3-1,不再推诿

**缺陷事实** ✅ `catalog.dictionary_entry` 是**扁平表**:`entry_ref` / `data_node_ref` / `brand_ref` /
`dictionary_kind` / `code`,唯一键 `(data_node_ref, brand_ref, dictionary_kind, code)`,**没有父列**。
`SKU_ATTRIBUTE_VALUE` 的条目**不知道自己属于哪个 `SKU_ATTRIBUTE`**。

> ⚠️ **这条是"掉在缝里"的标本**:P3-2 §3.2 写"这是 P3-1 前置";P3-1 §9 写"字典不拆,修法在 P3-2"。
> **两边都以为对方会做**,而 P3-2 §5 里我**亲手给这个模式起过名字**。
> **本文认领它:归 P3-1 建模,不在 P3-2。**

**而且这个 kind 装了两种东西** ✅ `SKU_ATTRIBUTE_VALUE` 同时承载:
**SKU 维度值**(有父属性,如 口味→甜)与**点单选项值**(没有父属性,如 加珍珠)。
引用矩阵 `R06` / `R12` / `R17` 三条都指向它。

**所以不能简单"加个父列"**:实现成 `NOT NULL` → 现有点单选项值全部建不了;
实现成可空 → 属性值选择器必须额外排掉 `parent IS NULL`,否则选项值污染属性值候选。

## ✅ Dexter 已裁定(2026-08-15):**现在补,而且拆 kind**

> **裁决一**:C1-2 **现在排期实施**,不再挂着。
> **裁决二**:`SKU_ATTRIBUTE_VALUE` **拆开**,不用"可空父列 + 每处查询记得过滤"。

### 零 · 拆的依据:底下的表本来就是分开的

✅ **亲验** `contracts/policy/catalog-inventory-reference-path-matrix.json`:

| entry | storage | 语义 |
|---|---|---|
| **R06** | `catalog.catalog_sku_variant_axis_value.value_ref` + `catalog.catalog_sku_attribute_value.attribute_value_ref` | **SKU 维度值 —— 有父属性** |
| **R12** | `catalog.catalog_order_option_value.attribute_value_ref` | **点单选项值 —— 无父属性** |
| **R17** | `inventory.stock_bom.option_value_ref` | 同上,被 BOM 消费 |

⛔ **两种东西的存储早就是分开的,只有 dictionary kind 把它们混成了一个。**
**拆 kind 不是新增抽象,是让 kind 追上存储已经表达的事实。**

### 一 · 拆法

| kind | 含义 | 父属性 |
|---|---|---|
| `SKU_ATTRIBUTE_VALUE`(**保留原名**) | SKU 维度值,R06 的那一批 | ⛔ **必填** |
| `ORDER_OPTION_VALUE`(**新增**) | 点单选项值,R12 / R17 的那一批 | ⛔ **必须为空** |

**保留原名给有父的那一批**,因为它对这个名字是准确的;**改名的是没有父的那批** ——
这样 R06 的引用不用动,只有 R12 / R17 换 kind。

### 二 · 建模:一条双向 CHECK,让模型自己说真话

`catalog.dictionary_entry` 增加 `parent_entry_ref UUID NULL`,并加:

> `CHECK ((dictionary_kind = 'SKU_ATTRIBUTE_VALUE') = (parent_entry_ref IS NOT NULL))`

⛔ **必须是双向的**。单向只保证"属性值有父",挡不住"别的 kind 也挂了个父"。
**双向写法一句话说清:有且只有 SKU 维度值带父属性。**
**这比"每处查询都记得排 `parent IS NULL`"强的地方在于:它不依赖任何人记得。**

外键指向同 scope 的 `SKU_ATTRIBUTE` 条目。

### 三 · ⛔ 拆 kind **不能取代**父过滤,两件事都要做

**这一条最容易被当成拆完就完事。**
拆 kind 解决的是**污染**(选项值不再混进属性值候选);
但「属性 A 只能选属于 A 的值」**仍然需要按 `parent_entry_ref` 过滤** ——
同一个 kind 里还有属性 B、C 的值。

**所以还要**:
- `CatalogDictionaryQuery` 增加 `parentEntryRef`(可选),owner 查询据此过滤
- 字典条目响应**外发 `parentEntryRef`**,让前端能验证归属而不是只能相信顺序
- 前端 descriptor 的 `contextBindings.attributeRef` **必须真的发出去** ——
  ✅ 现状是它只参与 fingerprint 计算,请求里只带 `dataNodeRef`

### 四 · 存量数据的再分类:⛔ 有一类分不出来,必须先查

再分类靠引用反查:被 R12 / R17 的 storage 引用的 → `ORDER_OPTION_VALUE`;
被 R06 引用的 → 留 `SKU_ATTRIBUTE_VALUE` 并回填父属性。

⚠️ **两边都没被引用的条目,数据本身分不出它是哪一种。**
**实施第一步:先查这类条目有多少。**
- 若为 0(dev / seed 数据大概率如此)→ 迁移可以无损完成
- 若非 0 → **停下报数,不要默认归到某一类** —— 猜错会让一批属性值变成选项值或反之 `DEXTER_DECISION`

### 五 · 判据与红夹具

| 判据 | 红夹具 |
|---|---|
| 属性 B 的值**不出现在**属性 A 的候选里 | 造一条属于 B 的值 → 查 A 的候选 → **不得出现** |
| 点单选项值**不出现在**任何属性值候选里 | 造一条 `ORDER_OPTION_VALUE` → 查任一属性候选 → **不得出现** |
| 模型自我保护 | 直接 INSERT 一条 `parent_entry_ref` 为空的 `SKU_ATTRIBUTE_VALUE` → **CHECK 必须拒**;给 `ORDER_OPTION_VALUE` 挂父 → **CHECK 必须拒** |
| 未选属性时 | 属性值选择器整个 `disabled`,**且不发请求** |
| 切换属性 | 旧属性值**被清空**,候选**重新取** |
| 已停用值 | 当前已选的**仍出现且 disabled**,带「(已停用)」后缀;未选中的不出现 |
| 写回 | 保存请求里是 **UUID**,不是 code 或 name |

### 六 · 归属与顺序

**C1-2 是 P3-1 建模范围**(本文早已认领),**不是 P3-2 的批次**。
它现在作为**补丁批次**插在 F5b 之前。

⛔ **F5b 的属性值那一处必须等它**;
✅ **其余四处 picker 不依赖它,可以先做** —— 见 P3-2 工单 F5b 的订正。


**要成立的**:两类值**在模型上可区分**(拆 kind 或父列可空 + 明确的过滤规则);
且 `catalog_sku_attribute_value` 能保证"这个值确实属于这个属性"。

📗 v4 用**复合外键** `(sales_attribute_id, sales_attribute_value_id)` 一次解决——
**数据库直接保证从属关系**。我们现在是两个各自独立的 FK,而且 `attribute_ref` **连 `dictionary_kind` 都不约束**:
把一个销售单位条目写进去,数据库照收。

**判别性测试**:① 把「份量」的值挂到「口味」轴上 → **数据库拒绝**(不是应用层)· ② 把一个 `SALES_UNIT`
条目当属性写入 → 拒绝 · ③ 点单选项值仍可正常创建与引用。

## C1-3 · 加料模型:料全店共享,每商品选范围(**比 v4 强的一项**)

**Dexter 2026-08-15 裁定**:「肯定是全店统一的那些料,要改也是一起改的,但每个商品可以选不同料的范围,
比如奶茶可以选加珍珠加椰果,咖啡可以选择加奶加浓缩。」

| 层 | 归属 | 例 |
|---|---|---|
| **料**(选项值) | **全店共享**,各自带加价 | 珍珠 +3 · 椰果 +3 · 奶 +2 · 浓缩 +5 |
| **每商品的选项组** | **每商品自己配** | 奶茶:「加料」多选、最多 3、可选 {珍珠, 椰果}<br>咖啡:「加料」多选、最多 2、可选 {奶, 浓缩} |

改「珍珠」的名字或加价 → **所有卖珍珠的商品一起变**。而奶茶与咖啡各选各的范围。

> 📗 **v4 做不到这个,这是我们的真实优势不是追平。** v4 的选项值**绑死在组上**
> (`catalog_option_value` 属于 `catalog_option_group`),两个商品挂同一个组**只能拿到完全一样的一套值**;
> 要不一样就得建两个组,"全店统一"当场破掉。

> ⚠️ **当前实现与本裁定不符**:`catalog_order_option_group.item_ref NOT NULL` +
> `UNIQUE(item_ref, group_code)` → 组与值都是商品私有,**每个商品重打一遍**。
> 这正对着 Dexter 最初那句「不能每次让用户新建」——**我把复用只解决在了"值"层的一半,组层原样保留,
> 而且这个取舍两份工单一个字没写,等于没给裁的机会。**

**判别性测试**:① 改共享料的加价 → 所有引用它的商品的展示与计价**同时变** · ② 奶茶与咖啡各自的可选范围
**互不影响** · ③ 把一个商品从某个料上摘掉,**不影响其他商品**。

## C1-4 · 统一引用表缩到三族,媒体两族各自建表

**缺陷事实** ✅ `catalog_item_reference` 主键 `(item_ref, kind, ref)`,六个 kind。
但 `ITEM_IMAGE` 与 `SKU_MEDIA` **都是有序列表**,而且 SKU 媒体的父亲是 SKU 不是商品;
商品图片的顺序还承载语义(owner 投影的 `primaryImageAssetRef` 取的就是**数组第 0 项**)。
已有测试构造**同一 assetRef 被同一商品两个 SKU 同时引用**。

**根因是我的归类错了**:我把五族归成一类的依据是"它们都是 ref"——**那是表面属性**。
实际是两类:标签/生产标签/销售单位是**无序集合**(三列刚好);图片与 SKU 媒体是**有序列表**。
**集合表和列表表是不同形状,一张表装两种必然对其中一种是 NULL。**

**裁定**

| 表 | 内容 |
|---|---|
| `catalog_item_reference` | 保留 `PRODUCTION_TAG` / `CATALOG_TAG` / `SALES_UNIT` 三个 kind |
| 商品图片表 | 挂 `catalog_item`:`item_ref` · `asset_ref` · `display_order`,`unique(item_ref, asset_ref)` |
| SKU 媒体表 | 挂 `catalog_sku`:`product_sku_ref` · `asset_ref` · `display_order`,`unique(product_sku_ref, asset_ref)` |

**两张而不是一张**,因为父亲不同;合成一张要多态 owner 列,**建不出真外键**——我们刚花力气把跨 owner 引用
做成显式声明,不该同批引入一个连 FK 都建不了的多态关系。

**同一 SKU 不允许重复引用同一 assetRef**(图库里两张一样的图没有业务含义)。
`display_order` **不加唯一约束**(否则每次重排要先腾位置),确定性靠 `ORDER BY display_order, asset_ref`。
**主图保持"第一张即主图",但要写成显式规则**,不再依赖 `images.get(0)` 这个隐式约定。

**`ORDER_OPTION_ATTRIBUTE_VALUE` 这个 kind 是残留,同批从 CHECK 里删除**(该引用已由选项值表承接)。

## C1-6 · 位置当身份、编码当身份(**我亲手列进拒绝形态,写路径又用了**)

**缺陷事实** ✅ `replaceComponents` 把已有组件按 **`display_order` 当 key**,`sameIdentity()` 字面就是
比较 `displayOrder` → **重排即换 ref**;组按 **`group_code` 匹配** → **编码当身份**。

**这两种写法都在 P3-1 §1.1-F 的拒绝形态清单里。拆表买到的稳定身份,写路径上只兑现了一半。**

**要成立的**:组与组件的匹配一律按 **ref**;重排不改变任何 ref;改编码不改变任何 ref。

**判别性测试**:① 把组内两个组件对调顺序 → 两者 ref **都不变** · ② 改组编码 → 组 ref **不变**,
其下组件全部保持挂载。

## C1-7 · 关键词搜索加文本索引(**唯一真正的性能问题**)

**缺陷事实** ✅ 搜索是 `i.name ILIKE '%' || ? || '%' OR ... shortName ILIKE ... OR i.code ILIKE ...`
—— **前导通配,索引用不上**。

**为什么分页救不了它**:用户搜「鸡」,数据库要把整个品牌的商品**全扫一遍**才能决定哪 100 个进第一页。
**分页发生在扫完之后。** 商品越多线性越慢,**与展示多少行无关**。

**裁定:给 `name` / `shortName` / `code` 建 GIN + trigram 索引。一条迁移,没有 worker,没有不一致窗口。**

> ⚠️ **明确撤回"投影表"与"JSON 汇总列"两个方案。**
> Dexter 的质疑成立:列表分页之后每页最多百来行,**渲染从来不是成本**;
> 而拆表之后每行的 SKU 计数、价格区间、分类名都是走索引的聚合,**几毫秒**;分类树计数是一次 `GROUP BY`。
> 📗 v4 有投影表 + worker,是因为它 22 张表拼一行要 join 一大片——**它的答案配它的问题,不配我们的**。
> 我之前把"v4 有投影层"直接搬成了"我们需要投影层",没问它解决的是不是我们的问题。

# 批次 C2 · 接线矫正(建了表但没用)

## C2-1 · `catalog_item_reference` 零写者零读者

**缺陷事实** ✅ 两种写法交叉搜,命中只有迁移文件本身和一个做 DDL 文本正则匹配的测试。
**没有任何生产代码写它或读它。**

## C2-2 · 资产反查仍是全表扫,而且没有 scope 谓词

**缺陷事实** ✅ 资产引用汇总仍是 `SELECT sections::text` 全表扫;
其中一条**至今没有任何 scope 谓词** —— **这是 P3-1 §1.1-E 用例 E-1 的原始缺陷,从头到尾没修。**

**要成立的**:反查走关系表;每条带 `data_node_ref` + `brand_ref`;跨租户**与同租户跨品牌**都不互相阻挡。

## C2-3 · 编码释放与血缘按编码记,直接冲突

**缺陷事实** ✅ `catalog_item.source_item_code` 是**按编码**记血缘,而 P3-1 §3.3 要求
**转正后的临时行置 VOIDED**(即释放编码)。

**后果**:临时行的编码被新商品复用之后,**正式商品的 `source_item_code` 指向谁,在库里不可判定**。

**两条决定互相冲突,而两份工单都没有交叉检查。**

**要成立的**:血缘改按 **ref** 记(或明确放弃血缘可追溯,二选一,**不接受"先这样"**)。

## C3-2 · 记账不实:SKU 三条唯一约束是追平不是超越

📗 v4 早已有 `unique(item, sku_code)`、单一默认 SKU 偏索引、变体组合 digest 偏索引三条。
P3-1 把它们写成"新不变量"**而未标注 v4 已有**。**不是我们更好,是追平。** 文档措辞订正。

**真正的增量是 `display_order`** —— v4 的 SKU 无排序列,商家排不了序。

## C3-3 · 已知的能力净损失,登记而非假装没有

**SKU 行级 `version` 撤回**:自洽(我们没有 SKU 级写命令),但代价是**冲突时说不出是哪条 SKU**,
两人同时编辑同一商品的不同 SKU 会整单冲突。📗 v4 可以只冲突到行。**登记,不掩饰。**

**不存属性值快照的真实成本**:`inventory.stock_bom.option_value_ref` 指向 catalog 字典,
而 inventory 不得跨 schema 读 catalog。📗 v4 在 `stock_target` 上存了名称快照。
**将来 inventory 侧要显示选项值名,只能回调 catalog。** 两份工单都没提这个成本。

# 批次 C4 · 交互(前置 P3-2,由 C1 的模型改动驱动)

## C4-1 · 无销售属性 SKU 的四种操作形态

由 C1-1 驱动。**每一种都有"用户会不会丢东西"这个坎。**

| 场景 | 形态 |
|---|---|
| **① 没有属性** | 规格维度区为空;SKU 区是「新增规格」按钮,每条自己填名字与价格 |
| **② 有属性** | 建轴之后 SKU 区**从手工切换成矩阵生成**;选几个值出几行,名字自动拼,用户只补价格。**此时"新增规格"按钮应消失** —— 手工加一条不属于任何组合的 SKU,会让商品同时处在两种模式里 |
| **③ 从"没属性"变成"有属性"** | **必须问用户,不能自动决定。** 默认走"把已有的映射过去"(让他指认「小份」对应 份量=小),价格保住;另给一个"重新生成"入口,并明确提示"原有 N 条规格将被替换" |
| **④ 换轴 / 删轴** | 删「份量」后 口味×份量 4 条会合并成 2 条。**必须先列出"以下 N 条的价格与图片将被丢弃:……"逐条列名,让他确认。**📗 **v4 在这里做得不好**——它按 digest 匹配,组合一变就对不上,**原有内容直接丢且无提示**。这条做好就是真的比它强 |

## C4-2 · 加料的交互形态

由 C1-3 驱动。料的**维护**在字典页(全店一处);商品页只做**选范围**——
从共享料里勾选本商品提供哪些,并配本商品的组规则(单选/多选、min/max、顺序)。
