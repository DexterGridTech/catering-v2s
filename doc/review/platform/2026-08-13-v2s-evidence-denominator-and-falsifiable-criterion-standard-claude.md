# evidence 失效的根因与判据规范(附 catalog 完整反例)

- 性质:规范提案 + 反例记录。触发:Dexter 2026-08-13「我们现在要求实施 agents 提供做完的 evidence,这套机制完全没有用」。
- 结论:evidence 机制**不是没用,是被用于它无法承担的类别**。修法是**分母外部化 + 判据可证伪**,两者缺一不可。
- 本文的反例全部来自本次 catalog 审计,均为亲验。

---

## 1. 现象:所有 evidence 都是真的,功能却是坏的

catalog 交付时的证据链**没有一处造假**:

| 当时的 evidence | 它证明的(真) | 它被用来主张的(伪) |
|---|---|---|
| 逐控件对账 / locator binding exact-set | 每个控件有 testId,且与 scenario 分母相等 | "交互符合 IA" |
| L2 18 definitions / 43 cases 全绿 | 流程可走通 | "交互可用" |
| `crud-presentation-standard-catalog.json` 门 | 列表名称/编码分列 | "名码规范落实" |
| 前端单测 | 运行时模型契约正确 | (未主张,该项诚实) |

同一时刻的真实状态:描述属性是 JSON 文本框、SKU 属性手打三个编码、BOM 让用户手打 UUID、六个生命周期按钮凭空消失、**商品分类根本无法绑定**、幂等键 12/19 处失效。

**没有人撒谎。** 假绿发生在**从机械事实跨越到语义结论**的那一步,而当时的评审(含我)接受了这个跨越。

---

## 2. 根因分两层,只修一层不够

### 2.1 第一层:分母由谁定

「逐控件对账」的分母是 **testId**——由实施者自己定。凡实施者能自选分母的对账,必然只覆盖它能满足的事实。这与被 Dexter 否决的「196 测试」是同一种病。

**但这一层在 catalog 上其实没出问题。**

### 2.2 第二层:满足判据由谁定、是否可证伪 ← **真正的失效点**

三阶段详设 §5.4 定的是:

```text
89 IA-ID 每条有最终实现与 evidence,零 orphan
```

分母 **89 IA-ID 来自 IA 文档,不是实施者能定的**,完全符合"外部分母"要求(盲审独立复算确认该数准确)。

**然后缺陷仍然全绿通过。** 因为「每条有实现与 evidence」是**存在性判据**:

| IA 要求 | 实现 | 按存在性判据 |
|---|---|---|
| `IA-CAT-TAB-005` 属性为自由 map **键值表**,逐项维护 | JSON 文本框 | 指着它说"实现在这" → **通过** |
| `IA-CAT-LIFECYCLE-001` 不可执行时 **disabled 并显示具体原因** | 四个按钮不渲染 | 指着按钮说"实现在这" → **通过** |
| `IA-CAT-TAB-001` 基础资料含分类/标签/销售单位/标准价 | 只有名称/短名/图片 | 页签存在 → **通过** |

**分母外部化解决了"该查多少条",没解决"每条查什么才算过"。** 后者才是实施者事实上的自由裁量空间。

---

## 3. 修法:判据必须自带反例

| 判据写法 | 能否被没写它的人检验 |
|---|---|
| `IA-CAT-TAB-005 有实现与 evidence` | ✗ 指个组件即满足 |
| `IA-CAT-TAB-005 满足 = 属性编辑为逐行 key/value 表格`<br>`反例:该页签提交路径存在 JSON.parse 即不成立` | ✓ 机器可查、人可查,**且无法用文本框满足** |

**说清"什么情况下这条就是没做到",判据才不依赖判定者的善意。**

### 3.1 这个仓已有正确样板:backend-acceptance 的 red mutation

`scenario` 六字段中的 `businessOracle`,以及 25 族红变异——**每条控制都必须说明"什么变异会让它红"**。那套纪律是对的。

**问题只是它从未被用到前端与 IA 符合性上**:后台要求"必须有真实红变异证明能拒绝错误行为",前端只要求"有实现与 evidence"。

---

## 4. 规范(建议采纳)

### 4.1 三条

1. **分母由详设定,且必须来自实施者控制不了的源**(IA-ID、generated route registry、assertion matrix 等)。凡实施者可自定义分母的"对账",不计为 evidence。
2. **每行的满足判据与反例,由评审方在 DESIGN GO 时产出**,该表进 GO 条件。
   *理由*:本仓详设与实施常为同一 agent(时间分离、人未分离);设计时定的判据,实施时若变贵会有"澄清"压力。评审方本就要做 DESIGN review,附带产出判据表成本很低而分离为真。
3. **收口按该表逐行核;判据未写反例的行不得标"通过"。**

### 4.2 一条禁令(本次假绿的发生点)

**禁止用机械 evidence 主张语义结论。**

任何声称"功能已完成 / 交互符合设计"的收口,evidence 必须显式写明**它证明的是哪个机械事实**,并**不得由该事实推导语义结论**。语义结论只能来自独立方的直接检视记录(读了哪些行、对了 IA 哪几条、结论是什么)。

### 4.3 判据模板

```text
IA-ID / 分母行
  满足判据:  <可观察的具体形态>
  反例:      <出现什么即判不成立>
  检验方式:  机器门 | 独立检视(读 file:line 对 IA 第 N 行)
```

## 6. 我自己也犯了同一个错(必须记录)

我在本次审计中**定了自己的 37 个维度、自己判 CONFORM**,两轮盲审把我打回:

- 第一轮:证明我的 CONFORM 是"看到组件存在就收口"(F-39 破坏性操作确认判错——启用/停用/归档三个按钮就在我引证的那条旁边,全无确认);
- 我随后自我更正四次(F-51 撤销、F-06 两次精确化并升 M、F-38 翻转、F-32 降级),更正原因均为**没把基准文本取全**(第一次漏 IA 头部 supersede,第二次漏线框脚注)。

**结论:自定义判据 + 自我判定,无论由谁执行都会失效,包括评审方。** 故 §4.1 第 2 条的判据表本身也必须经独立盲审攻击,不能由产出者自证。

## 7. 补充(Dexter 2026-08-13 追加诊断):检查发生在什么模式下

Dexter 的三条观察:①agent 不是恶意偷懒,是上下文不够才"简化";②evidence 代价高且不一定奏效;③**每轮让他拿源码对详设比对,他都能找出问题并做出没那么偷懒的修改**。

### 7.1 诊断修正:不是"上下文不够",是"生产模式不做交叉检查"

**反例**:`tagRef` 与 `code` 是契约里**紧挨着的两个字段**;owner 校验旁边就写着注释「The reference matrix is deliberately path-based: **do not infer a relationship from a field name**」。这不是上下文不足,是产出时没有回头对另一侧。

**更准的机制**:处在**产出模式**时,满足的是脑中当前那个要求的形状。JSON 文本框满足"用户能填属性";`productSkuRef: ''` 满足"这个类型需要这个字段"。两者局部自洽,都没跟另一侧(IA 的确切形态 / owner 的校验)对过。

**Dexter 的观察③正是该机制的证明**:同一个 agent 在**检查模式**下能找出自己在产出模式下漏的东西。**不是能力问题,不是上下文问题,是模式问题。**

### 7.2 本次会话即"多 review"的实验,结论带一个硬限定

| 谁 review | 结果 |
|---|---|
| Claude 首轮(检查模式) | 40 条,**漏掉最大空洞,4 条判错** |
| Claude 自我复核修订 | **未抓出自己的 CONFORM 错误** |
| 盲审一(独立) | 打掉 CONFORM 列 |
| Claude 再修订 | **仍然错** |
| 盲审二(独立) | 打掉核心结论,挖出 5 条 BROKEN(运行时必 422) |

**自审无效,独立盲审有效。** 机制同上:重读自己的产出时仍持有"我当时的意思",于是复述而非证伪。

→ **结论不是"多 review",是"多**独立盲**review"。该限定不可省,否则加轮次只是加成本。**

### 7.3 evidence 不废,但缩到它真正能承担的范围

本次**唯一经住两轮盲审的正是 evidence**:89/42/114 分母、SHA-256、route registry 双向差集——这些读代码重算不出来。

| | evidence | review |
|---|---|---|
| **能做** | 机器可判事实;可重复、低成本复算 | 语义符合性 |
| **不能做** | 语义符合性 | 替代哈希/分母对账 |

### 7.4 三层检查(替代"evidence vs review"二选一)

| 层 | 谁 | 模式 | 产出 | 成本 |
|---|---|---|---|---|
| **一 · 机器事实** | 实施者 | — | evidence(分母须来自实施者控制不了的源,且机器可判) | 低 |
| **二 · 实施者自查 pass** | 实施者本人 | **检查模式** | "拿产出对详设逐条读,报告哪里对不上"的差异清单 | **低,性价比最高** |
| **三 · 独立盲审** | 未参与产出者 | **对抗模式** | 立场为"证明它不成立";禁读作者推理过程 | 高,但单位缺陷成本最低 |

**第二层的关键约束**:必须是**显式独立的一步,与实施分开执行**。混在实施里等于仍在产出模式,无效。

**三层的判据都必须自带反例**(§3)。否则 review 同样停在"看起来对"——**本次 Claude 两轮正是如此**。

### 7.5 成本账(诚实)

两轮盲审各约 25–30 万 token;Codex 当时产出的 evidence(locator binding、L2 43 cases)成本未必更低。

**但单位缺陷成本天差地别:evidence 找到 0 条,盲审找到全部。**

### 7.6 停止条件(防止 review 变仪式)

**某一轮独立盲审未产出 M 级 finding,即停。**

本次两轮均出 M,且**第二轮比第一轮更重**(第一轮打判定,第二轮打核心结论并挖出 5 条运行时中断),故尚未到停止点。
