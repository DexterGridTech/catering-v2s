## 0 · 方案合理性(先于文档完整性)

### 0.1 问题对不对 —— 对,而且我在 owning source 上独立坐实了三处病灶

不采信稿子的 gap 描述,我直接打开当前契约
`contracts/openapi/components/catalog/catalog-item.schemas.json`:

1. **识别码是自由三元组**:`CatalogItemDetail` 与 `CatalogItemSaveRequest` 的 `identifiers`
   均为 `{kind, code, value}` 三个**无枚举、无格式、无唯一约束**的 `string`。
   ⇒ 契约层面无法阻止同一条码指向两个商品,也无法反查。
2. **制作信息无身份**:`productionProfiles` 是 `{item, sku, optionValue}` 三份
   `additionalProperties: true` 的 generic map ——
   **`sku` 与 `optionValue` 分支里没有任何 `skuRef` / `optionValueRef` 字段**。
   ⇒ 所有 SKU 共享一份"SKU profile",所有选项值共享一份"option profile"。这是结构性缺陷,不是文案问题。
3. **SKU 只有单值 `skuBarcode`**:`skus[].skuBarcode` 是单个 `string`,一个 SKU 无法有多个识别码。

⇒ 稿子 §3 的 gap 陈述**属实**,且比它自己写得更严重的是第 2 条 —— 那不是"混入了额外字段",
是**目标身份根本不存在**。

### 0.2 方案优不优 —— 主体优,而且消解了我预先构造的最强反例

我在冻结预期时构造的最强反例是:**多个选项值同时修改制作信息时没有确定的合并顺序**
(如"少冰 + 加珍珠 + 打包"三者都改 stationTags,谁覆盖谁?)。

稿子 §5.4 的处理消解了它:把选项影响限定为 `OptionValuePreparationEffect`
(`addProductionTagRefs[]` / `instruction?` / `preparationSecondsDelta?`),并且
- 标签**只增不减**(D-09 选 A)⇒ 集合并集,**可交换**;
- 时长**非负增量求和**(D-08 选 A)⇒ 加法,**可交换**;

两者都被做成了**可交换运算**,顺序不再影响结果。这比"完整 profile + 优先级"更小也更可判定,
**我的反例被正当地消解,不构成 finding**。⚠️ 但残余的顺序敏感面见 S-01。

我另构造两个替代并比较:
- **替代 A:三层完全独立(item/SKU/option 各自完整 profile)** —— 稿子 §5.4 首句已给出拒绝理由
  「多个完整 Profile 没有可靠覆盖顺序」,成立。**淘汰正确。**
- **替代 B:逐字段隐式合并(D-03 的 C)** —— 我自己推:`stationTags[]` 是集合,
  "逐字段合并"在集合字段上没有确定语义(并集?替换?),会把不确定性从选项层挪到 SKU 层。
  **SKU 用完整覆盖 + 可清除恢复(D-03 选 A)确实更可判定。**

### 0.3 代价配不配 —— 配

§5.1 明确「不建立新的 PreparationProfile 表」,而是给现有事实补身份;
识别类型收窄到三值闭集而不是照搬 V6 六值(理由见 §1.1)。
没有为未来可能的打印规则、设备路由提前建模。**无过度设计迹象。**

## 1 · 五个核验目标的独立判定

### 1.1 ProductIdentifier 是否应为可反查、可唯一约束的关系子实体 —— **是,且闭集收窄成立**

- **来源直接支持的事实**:V6 `05-商品目录域.md` 第 391–414 行 §4.7 定义
  `identifierType = INTERNAL_CODE | BARCODE | PLU | SKU_CODE | MNEMONIC | EXTERNAL_MASTER_CODE`,
  带 `scope` 与 `status`,并明确外部平台商品/SKU/选项 ID **不属于** `ProductIdentifier`。
- **我先前的疑虑**:稿子 D-01 只收 `BARCODE/PLU/MNEMONIC` 三值,相对 V6 六值是**收窄**。
  我冻结预期时标记「必须给理由,否则 SKU_CODE/INTERNAL_CODE 会静默丢失」。
- **判定:收窄成立,理由充分。** D-01 给的理由是后三者已分别有 owner ——
  我独立复核:`INTERNAL_CODE` ≡ `catalog_item.code`(owner 字段)、
  `SKU_CODE` ≡ `catalog_sku.skuCode`(owner 字段)、
  `EXTERNAL_MASTER_CODE` ≡ `ExternalCatalogIdentity`(V6 §4.14 独立聚合)。
  三者若再进 identifier 表就是**同一事实两个住址**,正是仓内一直在防的模式。
  ⇒ 这不是丢失能力,是**拒绝双写**。稿子的判断优于机械照搬 V6。
- **反查与唯一**:§4.4 第 1 条给出 `dataNodeRef + brandRef + identifierType + normalizedValue`,
  第 5 条给出「同一 normalized value 不能指向两个 owner」——
  这两条合起来才是"可反查"的充分条件(唯一 + 规范化),写得完整。

### 1.2 「商品默认 + SKU 继承/完整覆盖 + 选项值增量 effect」是否符合真实差异 —— **符合**

- **来源支持**:V6 §4.13 `PreparationProfile` 的键本来就是
  `catalogItemRef / skuRef / optionValueRef` 三重身份,四字段
  `stationTags[] / estimatedDuration? / printTags[] / preparationNotes?`。
  ⇒ 三层身份是**领域设计给的**,不是作者发明。
- **SKU 与选项的真实差异(我独立推导)**:SKU 是**互斥的规格单元**(一次只能是一个),
  所以"完整覆盖"有确定语义;选项值是**可多选的做法**(一次可选多个),
  所以只能用可交换的增量。**稿子的模型正好对上这个差异**,不是套模板。
- **无法确定合并的反例**:我构造的反例已被 D-08/D-09 的可交换设计消解(见 §0.2)。
  残余一处见 S-01。

## 2 · Findings

### S-01 · 选项 effect 的 `instruction` 是唯一残余的顺序敏感面,而排序键选错了 —— `CONFIRMED`

- **事实**:稿子第 310–311 行写「按 `optionValueRef` **稳定排序**,叠加每个选项值的 effect
  → 去重标签、**按稳定顺序追加制作说明**、求和时长影响」。
- **问题**:标签(并集)与时长(求和)**可交换**,顺序不影响结果;
  但 `instruction` 是**有序文本追加**,顺序直接决定制作人员读到的句子次序。
  而排序键 `optionValueRef` 是 **UUID** —— 我在
  `contracts/openapi/catalog-inventory.openapi.json` 亲验:选项值字段为
  `definitionValueRef`(`format: uuid`),与它**并列的 `displayOrder` 才是业务序**
  (契约中 `displayOrder` 出现 48 次,选项值 required 字段含它)。
- **失败场景**:"先萃取"与"最后加冰"两条 instruction,按 UUID 排序得到的先后是随机的,
  可能输出"最后加冰。先萃取。"——制作人员按顺序执行就错了。
- **区分**:契约字段为【事实】;"制作人员会按顺序执行"为【推论】(合理:instruction 是给人读的短说明)。
- **最小修复**:排序键从 `optionValueRef` 改为
  `(选项组 displayOrder, 选项值 displayOrder, definitionValueRef)` ——
  前两项给业务序,末项只作确定性兜底。**改一行排序依据,不改模型。**
- **更大方案的成本**:另一种做法是给每条 effect 加显式 `instructionOrder` 字段 ——
  多一个用户要维护的字段,而 `displayOrder` 本来就存在且用户已在维护,**不采用**。
- **需 Dexter 裁决?** 否(用既有业务序,不新增语义)。

### S-02 · D-02/D-15 删除 identifier 状态是相对 V6 的削减,稿子未标为"相对领域设计的收窄" —— `CONFIRMED`

- **事实**:V6 `05-商品目录域.md` 第 391–402 行 §4.7 的字段清单**明确含 `status`**。
  稿子 §4.4 第 6–7 条与 D-02 推荐"不暴露状态",理由是"当前没有临时停用的真实用户任务"。
- **判定:理由本身合理**(不照搬 V4 生命周期是对的),**但呈现方式有缺陷** ——
  D-01 的收窄稿子明确说明了"后三者已有 owner"这一**来源级理由**;
  D-02 的收窄只给了"没有真实任务"这一**假设**,却与 D-01 并列呈现为同类推荐。
  两者的确定性等级不同,不应同形呈现。
- **影响面**:Dexter 逐轮裁定时,容易把 D-02 当成与 D-01 同样"来源可定"的项目一并通过,
  而它实际是在删一个领域设计已声明的字段。
- **最小修复**:D-02/D-15 合并表述,并显式标注「**相对 V6 §4.7 的字段收窄,须产品确认**」;
  同时补一句反例边界:若未来出现"临时停用后恢复"任务,当前模型需要新增字段而非改语义。
- **需 Dexter 裁决?** **是**(D-02 与 D-15 本就是同一裁决点)。

## 5 · Dexter 裁定(2026-08-23,八项全部收口)

正式需求收敛时按此执行,`D-01..D-16` 全部有结论。

| 编号 | 裁定 | 依据与执行要点 |
|---|---|---|
| **D-02 + D-15** | **不建立 identifier 独立状态** | ⚠️ 理由**替换**稿子原写的"没有真实用户任务"(那是假设):改为套用**已裁定的单位模型语义** —— 停用只影响后续候选,已绑定值与历史快照不动。识别码同理:移除即不再用于新识别,历史订单/工作单按已冻结快照解释。过渡期用"删旧码 + 加新码"表达,两步均可逆。 |
| **D-08** | **选项时长影响只允许非负增量** | 允许负数会引出"多减项叠加为负"的下限保护新规则;且制作时长用于排产与告知等待,**高估安全、低估致投诉**。 |
| **D-09** | **选项只允许增加 production tag,不允许移除** | 保住多选合并的**可交换性**(并集)。⚠️ 已知代价并已接受:**"改变制作岗位"类做法本期无法用选项表达**;若确有此业务,正确形态是**用 SKU 表达**(SKU 是完整覆盖,天然可换标签),而不是放开移除。 |
| **D-11** | **用户术语为「制作单显示名称」** | "打印名称"会让用户误以为打印规则已配置,而打印规则归打印规则域、本期不做。 |
| **D-12** | **服务/费用商品:保留助记码(MNEMONIC),隐藏条码(BARCODE)** | 服务类无实体包装 ⇒ 不可能有条码;助记码是收银台真实录入需求。⚠️ 比稿子原推荐(两者皆可选)**更收敛**,contract 侧对该 shape 直接拒绝 `BARCODE` 与 `PLU`。 |

### 5.1 D-16 的适用边界(已披露,Dexter 接受)

加入 `brandRef` 意味着:**同一 dataNode 下,两个不同 brand 可以用同一个 normalized value 指向不同商品。**

- 该组合在"一个门店只经营一个品牌"时与 `dataNodeRef + type + value` **等价**,无差别;
- 在"同一门店同时经营多品牌"(如美食广场档口)时,物理扫码枪不携带 brand 上下文,
  **会出现一码两物无法消歧**。
- ⇒ **登记为已知边界**:若未来出现多品牌同址经营,**扫码解析入口必须携带 brand 上下文**
  (由销售入口决定当前品牌),否则需重开唯一域裁定。
  ⛔ 不得在 catalog 侧用"猜一个品牌"止血。
