## 0 · 写法(与 P3-1 不同,先读这一段)

### 0.1 机制换了,因为测试挡不住形态

P3-1 用的是 **不变量 + 拒绝形态 + 判别性测试**。那套在这里**不够用**:

> **用例能断言 testId 存在、能断言提交成功,断言不出"这里该是选择器不是输入框"。**

逐控件对账核的是控件**类型**与**数据来源**,不是"有没有这个 testId"。所以本文每条是:

| | 要求 |
|---|---|
| **现在是什么** | ✅ 亲验,写到文件与行,含控件类型、绑定数据、`disabled` 条件、文案 |
| **用户实际遭遇** | 这个形态让用户经历什么。**不是"不符合 IA",是"用户会怎样"** |
| **应该是什么** | 控件类型、数据来源、文案、交互、边界 |
| **依据** | IA 条款编号 / 已批准 Journey / 📗 v4。**"应该是什么"不是我的意见,是 IA 的授权** |
| **怎么确认** | **诚实分开:哪些能测、哪些只能看** |

### 0.2 四类内容必须分清(P3-1 二十五条 M 几乎全出在这里)

| 类别 | 标记 |
|---|---|
| **当前仓内事实** | 精确落点(文件 + 组件/行),标 ✅ |
| **IA 要求** | 引用条款编号或原文 |
| **产品裁定** | 标明是**新加的规则** + **业务后果**理由。**不得用命名论证** |
| **待建能力** | 标"新增",写清跨越的边界与量级 |
| **未来验收** | 标明依赖哪项未获授权,**不计入本轮分母** |

### 0.3 P3-1 踩过的坑,本文不再踩

1. **声称已存在的组件、接口、operation、字段,必须有精确落点** —— P3-1 三次引用了不存在的命令
2. **不发明已有的机制,也不声称不存在的源** —— 引用矩阵早就存在;枚举源当时不存在
3. **不让 grep 的形状定义答案** —— `Set.of` 扫不到 `List.of`
4. **不拿命名当证据** —— 形态名、注释、字段名、提示语都骗过人。**提示语与控件冲突时,冲突本身就是 finding**
5. **横切消费方要列全** —— P3-1 的"读路径"被读窄成"详情投影",漏了另外五个
6. **每个分母要有 before/after 映射**
7. **批次表不得混"范围批次"与"逐族批次"**

### 0.35 判据必须带的两个维度(**本文第一版都漏了**)

**维度一 · `surface`**:工作台有**门店面与品牌面**两套行为(代码里到处是 `surface === 'brand'` 守卫)。
同一条 IA 在两个面上的期望**可能不同**——品牌面列表显示"库存对象/BOM 定义",门店面显示"库存/BOM";
品牌面有品牌切换器,门店面没有。**每条形态要求必须说明适用哪个面,或明确写"两面相同"。**

**维度二 · 关系是否存在**:核一个能力时,不能只核**实体**在不在,还要核**关系**在不在。

### 0.36 绝对断言的证据纪律(**本文第一版犯了两次**)

### 1.1 治理维度整套删除

> ⚠️ **本节的依据换过一次,前一版的依据是错的,记在这里防止有人回头引用它。**
> 前一版写"v4 的 catalog 域 governance 零命中"。**那是假的。** ✅ v4 有 `catalog_item.governance_status`,
> 六值 check 约束、投影表同列、两条索引带它、受控 optionSet「商品治理状态」`owner: CATALOG`。
> catalog 范围内 `governance` 命中 **43 个文件**。
> **我犯的错**:第一次 grep 词对了但没限范围且 `head -5` 截断,前五条恰好全是 IAM;第二次限了 catalog 范围
> 却把 `governance` 这个承重词漏在模式外。**两次一叠加就成了"零命中"。**

**真正的依据** ✅ 亲验 v2s 的实现——`governanceStatus(row, sections)` **没有任何完整性计算**:

```java
String governance = firstText(sections, "governanceStatus", "governanceState");  // 客户端写什么回显什么
...
return "TEMPORARY".equals(sourceFact(row, sections)) ? "GOVERNANCE_TODO" : row.status();
```

取值只有三种来路:① 客户端原样回显(还是两种拼写)· ② 临时的就叫 `GOVERNANCE_TODO`——**这是 `source` 的重述** ·
③ 否则回显 `row.status()`——**这是「状态」列的重述**。

**它是 `source` 与 `status` 两个字段的复读,零新增信息。**
三方词表对不上(前端 `READY/NEEDS_ATTENTION/BLOCKED`、owner 受理 `DRAFT/ENABLED/DISABLED/ARCHIVED/VOIDED/GOVERNANCE_TODO`)
**是症状不是病**——一个没有真实语义的字段,必然积累谁写谁的值。

**为什么"表达内容是否完整"这条路也走不通**:`source` 已经能回答"这是不是临时商品"
(✅ 智能视图靠 `sections.source = 'EXTERNAL_ORDER_TEMPORARY'` 计数,**它是智能视图不是分类**)。
治理要有独立价值,只能表达"临时商品里哪些还缺必填内容不能转正"——**而 v2s 没有任何地方在算这个**。

**Dexter 2026-08-14 裁定:去掉。**

> ⚠️ **IA 冲突必须同批处理。** ✅ IA §5.1 线框里筛选行有 `[治理]`、左树有 `·待治理 2`、固定列有 `状态治理`,
> 全文「治理」出现 28 次。**删掉控件而不改 IA,IA 立刻变成不符合。**
> 本文其余章节把这份 IA 当权威,这里不能例外——**IA §5.1 同批修订,不是可选项。**

**现在是什么** ✅
- 工作台治理筛选下拉写死 `['READY','NEEDS_ATTENTION','BLOCKED']`,**后台一个都不接受**,选任意一个必 422
- 而 422 被渲染成通用的「商品工作台暂时无法获取…请重试」——**重试永远失败**
- 列表治理列渲染的 `governanceStatus`,取值域与筛选词表**零重叠**
- 智能视图含「待治理」`GOVERNANCE_PENDING`

**用户实际遭遇**:点一下治理筛选就白屏报错,而提示告诉他重试。**这是 89 条里用户唯一"用不了页面"的一条。**

**前端要删的**:治理筛选下拉 · 列表治理列 · 智能视图的「待治理」项 · `smartLabels` 里对应的中文。

**后端与契约侧的删除在 P3-1 §4.4**,前端不要等它——**前端删掉之后不再发这些参数,后端删除是独立的**。

**怎么确认**:能测——工作台无任何路径能发出 `governanceStatus` 参数;智能视图可选集合不含 `GOVERNANCE_PENDING`。只能看——删掉之后列宽与工具行的视觉是否还合理。

### 1.2 `ordering` 页签删除 —— **不是纯前端,依赖 manifest 改动**

**依据**:✅ 它不在 IA §6.2 的形态 × 页签矩阵里。**Dexter 裁定:不知道是什么就不能要。**

> ⚠️ **前一版把它排进"批次 1 · 不依赖 P3-1",那是错的。** 三条亲验事实:
> ① 页签由 **manifest `tabRules` 声明可见**——`STANDARD_SALE_COUNTED` 与 `STANDARD_SALE_WEIGHED` 的
> `visible` 都含 `ordering`,而前端页签是 `detail.tabs.filter(visible)` 从 owner 拿的;
> **只删前端映射,只会渲染出一个标题叫 `ordering`、内容是"尚未维护"的页签,页签集合根本没变**,
> 本节自订的判据"页签集合与 IA 矩阵逐形态相等"当场不通过。
> ② 它是 `STANDARD_SALE_COUNTED` / `STANDARD_SALE_WEIGHED` 这**两个最常见形态唯一的商品级定价入口**
> (全仓只有两个价格编辑控件:这个和 SKU 矩阵里的)。
> ③ 提交门 `if (visibleTabs.has('ordering') || visibleTabs.has('sku-specifications-pricing'))` 决定
> `catalogDraft.ordering` 发不发——**删了页签,标准价就不再提交**。

**所以本节是三件事,缺一不可**:

1. manifest `tabRules` 与 owner 投影**同步删除** `ordering`
2. **标准价与挂牌价按 IA §6.3 迁入基础资料**(IA 那一段线框写着 `标准价 [按粒度激活]`)
3. 提交门跟着改,确保迁移后价格仍然发得出去

**从批次 1 移出**,依赖 manifest 改动。

**怎么确认**:能测——页签集合与 IA §6.2 矩阵**逐形态相等**;`STANDARD_SALE_COUNTED` 商品**仍能编辑并保存标准价**。
**这第二条是防止"删干净了但用户不能定价了"的唯一守门。**

## 3 · 前端控件形态

### 3.1 主列复合形态

**现在是什么** ✅ 工作台主列里名称与编码是**两个独立元素**,不是 `名称(编码)`;
**同文件的左树节点与 SKU 展开行都用了 `NameCodeText`,唯独主列没用**;`shortName` 在契约与解码层都有,**工作台无读取点**。

**用户实际遭遇**:用短名搜出一批行,**看不到任何命中理由**——搜到的字串一个都没显示出来。

**应该是什么**:主列内部用 foundation 的 `NameCodeText`;短名参与渲染并在命中时可见。

**依据**:IA §5.3 明写复合主列内部必须用 foundation `NameCodeText`。

**怎么确认**:能测——主列渲染路径经过 `NameCodeText`;短名有读取点。只能看——三行信息的视觉层级是否还是"名称主、编码弱"。

### 3.2 字典选择器(五处 picker 接线)

**现在是什么** ✅ 五处全是手打:BOM 的库存对象手打 UUID(**而组件自己的提示语写着「必须引用已有库存对象」**)· SKU 属性与属性值四个自由文本框 · 套餐组件的 SKU 手打编码 · BOM 所属选项值手打编码 · 制作影响与生产提示 tags 是逗号分隔字符串。

**用户实际遭遇**:配一个「口味:甜/辣/微辣」要点三次新增、填十二个框;打错一个字符就多一个属性。

**应该是什么** 📗 照 v4:

| 控件 | 目标形态 |
|---|---|
| 属性 | `Select` + 搜索,数据源 `dictionaries/{kind}/entries` 的 `SKU_ATTRIBUTE` |
| 属性值 | **`Select mode="multiple"`**,`SKU_ATTRIBUTE_VALUE`,**按已选属性过滤**;未选属性时整个 `disabled` |
| 切换属性 | **自动清空已选值**(值从属于属性,换属性旧值不合法) |
| 选中之后 | 编码与名称**从字典带出、只读**;要改去字典页 |
| 停用项 | **默认不出现,但当前已选的仍出现且 `disabled` + 「(已停用)」后缀** |
| 新建 | quick-manage 按钮在选择器**旁边**,带权限门控。**用户的默认动作是选,不是建** |
| BOM 库存对象 | `Select`,数据源 `inventory-targets` |
| 套餐组件 SKU | 选中商品后取 `items/{itemCode}` 详情的 SKU 列表 |
| BOM 所属选项值 | **不需要接口**,候选就在同一抽屉的点单选项页签里 |
| 制作影响 / 生产 tags | 多选,候选前端**已经在传** |

**⚠️ 两处明确不抄 v4** ✅:
① v4 的 per-item 维度表**没存"选了哪些值"**,重开商品时该属性下全部值显示为已选;
② v4 的选择器与矩阵是**两套判定**,停用一个值会让已有 SKU 整批掉。

**依据**:Dexter 2026-08-14「SKU属性需要拆表,因为很多属性是类似,比如口味:甜和辣,不能每次让用户新建」。

> ⚠️ **前一版写"表已存在,缺的是选择器不是模型"——那是错的,而且 Dexter 最初的判断才是对的。**
> ✅ `catalog.dictionary_entry` 是**一张扁平表**:`entry_ref` / `data_node_ref` / `brand_ref` /
> `dictionary_kind` / `code`,唯一键 `(data_node_ref, brand_ref, dictionary_kind, code)`,**没有父列**。

> 表在,**关系不在**。
>
> **这是 P3-1 §1.0 刚补的判据乙原样再犯**:我核了"实体在不在",没核"**关系在不在**"。
>
> **所以本节有一个 P3-1 前置**:`dictionary_entry` 必须能表达 属性 → 值 的从属
> (加父引用列,或给属性值单独的结构)。**这是建模改动,不是选择器改动。**
> **该前置不落地,本节的属性值选择器只能做成"列出全部值不分属性",那不是 IA 要的形态。**

**怎么确认**:能测——候选来自上述端点;提交 payload 带 ref **不带手打编码**;未选属性时值选择器不可用;已停用项可见但不可选。**只能看**——选择器位置、搜索顺不顺手、"新建"藏得够不够深。

### 3.3 SKU 矩阵引擎(本文最大的一块)

**现在是什么** ✅ `skus[].attributeValueRefs` 有独立的手工编辑控件,「新增属性值引用」push 的是
**两个空串 ref + 四个空文本框**,**每个 SKU 都要重打一遍**。

**v4 根本没有这个控件** —— 它的 SKU 属性值是从维度笛卡尔积**推导**的。**所以 v2s 这个控件是错的存在,它存在只是因为没有引擎。**

**应该是什么** 📗 照 v4 的矩阵引擎:

1. SKU 矩阵**由维度笛卡尔积生成**,不由用户逐行手填
2. **停用/归档的属性值排除出新组合**,但**已存在的 SKU 不因此消失**(⚠️ v4 在这里不一致,不抄)
3. 改维度重建时,**digest 未变的组合保留已填内容**(编码、名称、价格、图片)
4. SKU 编码与名称**自动生成默认值并避开已用编码**,用户可改
5. 默认 SKU **跨重建保持**
6. **手工属性值控件消失**

**依赖 P3-1**:digest 稳定性、组合唯一约束、空组合规则的后端侧,以及 SKU 的 `displayOrder` 与
`variantCombinationDigest` 两个新契约字段。**P3-1 那一批不落地,本节做不了。**

**怎么确认**:能测——加一根维度重建后,原组合的 SKU 仍带原编码名称价格;停用一个值后新组合不含它而老 SKU 仍在;不存在"逐 SKU 手填属性值"的入口。**只能看**——重建时的过渡是否让用户看懂发生了什么。

### 3.4 生产提示改为每商品一条
