## 0 · 一句话结论

规则早就有了，而且写在五处；没做到位的是**动态运行之前的准入没有真正执行**，而运行器在"按下运行键"那一刻也不拦。结果 L2 被当成发现问题的工具，一次失败修一处、再跑一次。与此同时，交付状态报告把旧字节上的通过当成了"最近一次"。

## 1 · 已确认事实（均来自落盘产物与仓内源码）

### 1.1 L2：36 次运行，只通过 1 次，当前字节上的结论是失败

- 在 `.runtime/browser-l2` 及 `.runtime/browser-l2-codex-terminal*` 下，属于门店终端的 L2 运行共 36 次，时间在 2026-09-24T10:43Z 到 14:57Z 之间。只有 14:35Z 那一次六个场景全部通过。
- 失败的分布：
  - 「新建配置」一个场景失败约 18 次：10:59Z 到 12:33Z 基本连续，14:25Z、14:57Z 又各一次。
  - 控制面自身失败 13 次：历史运行绑定不匹配 8 次（其中 14:29Z、14:30Z、14:32Z 三分钟内连续三次同码）、源码字节漂移 5 次。
  - 另有进程身份漂移 1 次、看门狗超时 1 次、「新建基础」失败 2 次、只读场景失败 1 次。
- **最近一次 L2（14:57Z，完整六场景）是失败**：「新建配置」场景里选了「全部桌台区」，下拉框仍显示「请选择桌台区」；其余 3 个场景没有跑到。
- 这次与 14:35Z 那次通过之间，改动了 7 个文件，其中有两个 UI 组件和 L2 脚本本身。
- 当前源码与 14:57Z 那次运行绑定的 1923 个文件逐字节相同。

所以，Codex 报告里「最近一次 L2 已是 6 个场景 business=PASS」**不成立**：那次通过是旧字节上的结果。

## 3 · 根因分层

- **第一根因（执行 + 控制，属 F 类，以 B、C 为主）**：跳过了已有的动态前准入，把 L2 当成发现工具。促成它的，是入口处没有任何拦截：五处规则都是文字，在按下运行键的那一刻没有一处生效。
  - 直接证据：同一失败 3 分钟内连续 3 次；同一场景约 18 次失败；一张准入、CP、P9 记录都没有。
- **设计问题（A）**：
  - 详设缺模板必填的 §3a 表；
  - 约 120 KB 的验证控制面（L2 策略、脚本、生成器、seed 后置与父流程集成、角色授权）不是设计交付物，所以实施前没有人能审它；
  - 审计持久化漏设计（已补方案）。
- **执行纪律问题（B）**：
  - 没有准入记录、CP 复核记录与 P9 记录；
  - 失败族反复出现却没有停下来；
  - L2 持有运行期间改源码，漂移 5 次；
  - 在上一次 Testcontainers 运行未结束时又启动新的运行，2 次；
  - 状态报告与当前字节不符（M-2）。
- **规范控制不足（C）**：
  - L2 运行器与 reset/seed 流程在入口处没有拦截；
  - 父 seed 报告丢失子阶段的失败原因；
  - 评审规范没有给「过程回溯」准备对应的动作变体（N-2）。
- **环境或资源（E）**：不是主因。看门狗超时 1 次、进程身份漂移 1 次，可能与环境有关；「运行已在进行中」2 次是自己并发启动造成的，不算环境。
- **不应被误认为整体闭合的局部结果**：
  - 14:35Z 的 L2 通过：旧字节；
  - 14:54Z 的后台验收通过：只证明后台；
  - 设计文档的多轮修订；
  - 审计持久化方案：只是方案，尚未实现与验证。

## 5 · 最小改进方案

### 5.1 硬阻断：放进工具入口，机械、便宜，只拦昂贵步骤

1. **L2 不许无变更重跑**：上一轮同一场景失败、且该场景绑定的文件字节没变时，`browser-l2-runtime.mjs` 拒绝启动，并打印失败族规则。这一条能直接消掉「3 分钟 3 次同码」这类循环。它只比较运行器自己已有的字节绑定，不新建台账。
2. **执行配置只由运行器当场生成**：运行器在同一个运行里自己调用唯一的 P1 生成器，拒绝外部传入或历史留下的执行配置。这样消掉双入口，也消掉「历史运行绑定」这类失败。
3. **reset 之前先做 seed 试运行**：受管的 reset→seed 流程先在当前字节上跑 `r5-complete-seed-executor` 的试运行；试运行失败就不执行 `DROP DATABASE`。
4. **父 seed 报告带上子阶段的首败原因**：本次 49 毫秒的失败，因为缺了这一项而无从定位。

### 5.2 独立复核：仍由 fresh 子 agent 判断，但把顺序写死

5. 实施任务模板增加一个有序阶段「动态前整体准入」，退出条件如下；这个阶段没完成，不得进入 L2、reset 或 seed：
   - CP 级复核全部 MATCHED；
   - 全批三维对账 MATCHED；
   - 详设 §3a 表填写完整，且 `L2_SCRIPT_ADMISSION=PASS`；
   - seed 试运行 PASS。

   这些记录落在 `doc/review/platform/*-codex`，让 Dexter 与 Claude 看得见。
6. 是否让 L2 运行器去读 §3a 的准入状态行、以此硬阻断：**Dexter 2026-09-25 裁定「要」**。运行器在启动前读取本批详设 §3a 的准入状态与独立复核记录，没有 `L2_SCRIPT_ADMISSION=PASS` 就拒绝启动；准入覆盖的 L2 控制面文件与 UI 目录在准入之后若有改动，准入即失效，需重新复核。

### 5.3 模板与规范：放在各自唯一的正本里

7. **详设模板 §3a**：写明表内必须列出本批 L2 控制面文件的全集，包括场景、blueprint、定位绑定、执行配置、fixture 与时间预算，以及 case 分母。**缺这张表，设计评审即 NO-GO。**

   **§10b**：增加 seed 父流程集成、角色矩阵、读回判据与试运行步骤。
8. **状态报告**（实施任务模板的报告节）：固定写两行，一行是「当前字节上的最新运行」（run id、时间、结果），另一行是「最后一次通过」（run id、时间、与当前字节是否一致）。
9. **评审规范**：补一个「过程回溯」的动作 1 变体，内容是提取运行产物、过程记录与规则出处（对应 N-2）。
10. **项目记忆**：`execution-economics-and-failure-family-closure.md` 追加本次复发的实测，说明只靠文字没能阻止复发，并指向 5.1 的工具门。不新增重复条目。

### 5.4 如何避免「失败一次修一个」

- 第一次动态运行之前，完成 5.2 的全部退出条件，再加上 5.1 的第 3 条。
- 运行中同一失败族第二次出现，由 5.1 的第 1 条机械拦下，逼出静态根因分析：按 `playwright-results.json` 的错误与堆栈 → UI 源码命中 → 渲染条件的顺序定位，不再靠重跑找原因。
- L2 持有运行期间不改源码。运行器已经能发现字节漂移，这一条是纪律。
- 同一时间只允许一个受管运行。
