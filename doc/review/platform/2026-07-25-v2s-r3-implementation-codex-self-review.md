## 用户任务

业务用户是受部署期外部身份控制的系统服务提供者，真实任务是在既有集团空间中独立录入商业集团编码和名称，并从 owner readback 看到唯一的商业集团。operations-admin 不属于本 Journey 的真实用户行为闭环。

## Dexter 立场

Dexter 要求 R3 只完成 C-01 与 R3-TECH，保留一个业务 deployable，同时把未来 TDP 物理隔离为无运行时占位；不得创建 root/default 账号、不得 seed 业务前提、不得把 operations-admin 伪装为真实登录。实现的阶段成本必须支持 fresh 运行证据与后续小批 review。

## 替代方案

替代方案是先做 UI mock 或把 backend 留在单一 app 目录，成本更低但会失去真实 owner/transaction/edge 证明，也不能承接未来 terminal-data-server 并列边界；不选。当前方案用一个 Spring deployable、两个并列 app 目录、模块 API 与一份 Flyway history，复杂度集中在可验证的 contract、owner 和运行证据，取舍与 C-01 收益匹配。

## 方案合理性

当前问题是既要最小真实 C-01，又要 future TDP 不污染当前业务 app。方案把 `catering-business-server` 作为唯一运行后台，把 `terminal-data-server` 保持空 placeholder；platform-workspace 只做 task read/coordinator，organization 持有 commercial group fact/command/audit/idempotency。代价是需要显式 component scan、Flyway lifecycle 和 edge context verifier，收益是模块物理边界、单库单 history、typed conflict 和可重放 owner readback 可以被真实运行验证。没有引入 MQ、outbox、内部 HTTP client、账号 seed 或第二数据库，避免阶段过度设计。

## UI 与交互

APPLICABLE：platform-admin 的页面操作严格来自批准的 C-01 Journey：list → detail → 初始化 Drawer → owner readback detail；列表不直接初始化，初始化表单独立录入编码/名称，失败保留当前页面，operations-admin 只显示 boundary。页面不提供 operations 登录、空间创建/编辑/启停或下游对象动作。接口限制由外部 edge context、既有空间前提和 generated Problem code 归因；未知提交结果仍要求先重读 detail，未扩展产品语义。
