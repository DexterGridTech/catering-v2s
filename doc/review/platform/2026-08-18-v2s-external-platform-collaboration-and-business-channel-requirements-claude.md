## 1. 背景与业务目标

### 1.1 背景

旧规格有两处结构性错位,本次修订针对它们:

**其一,分类学给错了对象。** 旧的「外部平台六类分类学」是**给平台分类**,
但同一个平台(美团)横跨多类。真实结构是**能力可分类,平台一对多持有能力**。
继续给平台分类会把不是渠道的东西建成渠道。

**其二,三层结构与经营渠道耦合过强。** 现有
`BUSINESS_CHANNEL → BUSINESS_CHANNEL_PROVIDER_CONFIG → BUSINESS_CHANNEL_BINDING`
只服务于经营渠道。做团购业务时会再长出一套属性几乎相同的
`CHANNEL → PROVIDER_CONFIG → BINDING`。这三层表达的其实是
「外部系统是谁 / 我以什么身份接它 / 我的哪个经营主体对上它的哪个主体」,
**与"这是不是一条下单入口"无关**。经营渠道只是它的第一个消费者。

### 1.2 业务目标

1. 外部平台接入能力**按能力分类描述**,一个平台可同时具备多类能力,每类携带能力属性。
2. 外部协作的三层对象**通用化**,所有外部平台接入复用同一套定义,不再为每种业务复制一套。
3. 运维管理员能在集团空间维度**开放/关停**外部系统与 provider,并管理绑定关系。
4. 运营人员能**自建经营渠道模板**并创建渠道实例;外部渠道通过绑定生效。
5. 能力模型能**随业务迭代低成本扩展**——新增能力或属性不引起大面积代码改动。

### 1.3 不追求

- 不建规则引擎、条件 DSL 或配置化谓词表(判断规则尚未确定,本期只建声明)。
- 不做权益/团购券的核销与结算建模(能力分类占位,业务留待未来迭代)。
- 不做菜单发布与销售集合(本期只定义渠道,菜单绑定是后续迭代)。
- 不镜像外部主数据(商场 ERP 的门店记录是外部对接语境,不是本系统主数据,G-04)。
- **不做任何外部协作运行时**:订单同步分发、异步投递、重试/死信、适配器进程、
  订单来源与节点路径快照,全部不在本期。
- **不做项目与门店之间的结算**。项目以自身主体开店售卖各门店商品后,结算由项目自行处理(S-04)。

## 3. 术语表

| 术语 | 含义 | 不得混淆 |
|---|---|---|
| **外部系统**(`external_system`) | 一个外部平台的身份。全局预制,不区分集团空间。一对多持有能力分类 | 不是「渠道」;一个平台只有一条 |
| **接入档案**(`provider_profile`) | 以某 ISV 身份接入某外部系统的能力档案。全局预制 | **不是配置项**;它声明能力与约束 |
| **主体绑定**(`owner_binding`) | 系统内经营主体与外部平台经营主体的映射。运行时配置,按集团空间隔离 | 不是渠道实例;一条渠道可对应一条绑定 |
| **能力分类** | 一组标准动作与能力的分类。七类,非互斥 | 不是平台分类;不是渠道订单类型 |
| **能力属性** | 某能力分类下的细分属性(如团购的映射方向、外卖的菜单协作方向) | 不是判断规则 |
| **经营渠道模板** | 项目定义的渠道形态,四维级联 | **不再是预置目录** |
| **经营渠道实例** | 按模板创建的具体渠道 | 同模板允许多条,不做唯一性校验 |
| **渠道订单类型** | 模板维度之一:到店 / 外卖 / 团购 | 与能力分类同名者见 §4.3 R1 |
| **经营主体类型** | 模板维度之一:项目 / 门店。即菜单维护方 | 不是组织节点类型 |

## 4. 业务背景知识

### 4.1 两层分工

**外部协作层**(通用):描述「外部系统是谁、我以什么身份接它、我的哪个主体对上它的哪个主体」。
它服务所有外部平台接入,与业务种类无关。

**经营渠道层**(消费者之一):描述「用户从哪个入口下单」。
外部渠道**消费**协作层的绑定;内部渠道**不涉及**协作层。

⛔ 协作层不得反向依赖渠道层。任何"因为渠道需要所以协作层加个字段"的诉求,
必须先证明该字段对**其他**外部接入同样成立,否则它属于渠道层。

### 4.1A 模块边界(按域拆,不按后台拆)

本次涉及两个**不同的域**,应当是两个模块:

| 模块 | 域 | 拥有 |
|---|---|---|
| `collaboration` | **对外对接关系** | `enablement_state`、`owner_binding` |
| `business-channel` | **经营入口** | 渠道模板、渠道实例 |

**判据一 · 独立存在**:有绑定无渠道(集团会员卡券、主数据同步)、
有渠道无绑定(POS/扫码/自助机全部内部渠道)—— 两边都能独立存在且语义完整。

**判据二 · 变化原因不同**:协作层因接入新平台、平台改授权机制而变;
渠道层因新增下单形态(如本次新增「自助机」)、经营主体规则变化而变。

**判据三 · 依赖单向**:渠道**引用**绑定;绑定不知道渠道存在。

**仓内先例**:`store-contract` 独立于 `organization` —— 合同基于门店、耦合紧、单向引用,
但属不同域,故独立模块与独立 schema。**渠道 : 绑定 ≈ 合同 : 门店**。

⛔ **不按管理后台拆**(Dexter 2026-08-18 明确)。后台是消费面,不是域。

**依赖形态(E-27;修正早期表述)**:

- **模块间依赖单向**:`business-channel → collaboration`(读)。⛔ `collaboration` **不得** import
  `business-channel` 的任何类 —— 否则构成 Gradle 循环依赖。
- **级联写不由 collaboration 发起**。凡跨两域的写(绑定删除 ⇒ 渠道落回草稿;
  外部系统停用 ⇒ 渠道停用),一律由 **edge 的 operation policy 显式列出两个 owner 的 command**,
  在同一 `REQUIRED` 事务内依次调用,两个 owner 谁也不调谁。
  依据 `PLATFORM-BLUEPRINT.md`:「跨 owner 的 whole-save 只能由 **operation policy 明确列出
  有限 owner command、同一 `REQUIRED` 事务**与精确 originating requirement」。
  仓内 `contracts/registry/generated/operation-handler-bindings/` 已是该形态。
- 目标 owner 仍须复核 grant 的 workspace、group、target type、target reference、
  capability 与 operation purpose,不得把一个 grant 泛化。

⚠️ **早期表述「级联写由 `collaboration` 调 `business-channel` 的公开 command API」是错的**
(它与"反向禁止"自相矛盾,按字面实施 Gradle 会因循环依赖失败),已作废。

### 4.1B 两类外部平台的分野(E-26;模型的基础分界)

**这是本模型的第一分界,后续多条规则由它派生。**

| | **开放平台类** | **非开放平台类** |
|---|---|---|
| 成员 | **外卖、团购**、(后续)独立配送 —— 互联网平台 | 其余全部:商场 ERP、会员卡券系统、主数据同步… |
| 授权形态 | 有**开放授权体系**(跳转 + 回调) | **不是开放式授权** |
| 谁维护 | **运营自己授权** | **运维管理员在运维管理后台手工配置** |
| binding 基数 | **一业务线一条** | **一条 binding 搞定该 provider 的全部能力** |
| `externalOwnerId` | **授权的结果**,由适配器回填 | 运维**手工填写** |
| 承载字段 | `authenticationKind = EXTERNAL_GRANT` | `INTERNAL_MAPPING` / `NO_MAPPING` |

⇒ **该分野无需新增字段**,由既有 `authenticationKind` 承载。
⇒ 与 E-18(非渠道对象归运维)完全对齐:**渠道绑定 ≡ 开放平台类 ≡ 运营维护**;
**非渠道绑定 ≡ 非开放平台类 ≡ 运维维护**。

### 4.2 能力分类(七类,非互斥)

| # | 能力分类 | 方向 | 是否构成下单入口 |
|---|---|---|---|
| 1 | 主数据同步 | 入站(外部→本系统) | 否 |
| 2 | 用户与权益 | 双向 | 否(参与下单过程,不是入口)。**本期仅占位**,业务留未来迭代 |
| 3 | **团购** | **进单** | **是** |
| 4 | **外卖** | **进单** | **是** |
| 5 | 库存 | 双向 | 否 |
| 6 | 外卖配送 | 出站(履约) | 否 |
| 7 | **订单同步** | **出状态**(一对 N) | 否 |

**每类携带能力属性**,属性是该类内部的细分事实。已知例子:

- **团购**:团购商品是「外部映射内部商品」还是「必须内部映射外部商品」;
- **外卖**:「仅支持拉取外部菜单做内部映射」还是「支持将本地菜单同步到外部平台」;
- **订单同步**:⚠️ 本期**不定义**其属性 —— 判断规则未定,连声明位置也不建(§2.2)。

**进单与出状态是相反方向,两者正交。** 判别反例(Dexter 提供):
购物中心 ERP **只有订单同步,没有外卖/团购**;美团**两者都要才完整**。

### 4.3 关系总表(本次修订的核心;每条都必须可判定)

> ⚠️ 本节回答「模板里的『外卖』和能力分类里的『外卖』是不是一个东西」这类问题。
> 每条关系给出**约束式**与**判定时机**,设计与实施不得自行解释。

**R1 · 渠道订单类型 ↔ 能力分类 —— 同名不同层,由包含链约束**

它们**不是同一个对象**,而是同一事实的两侧:
渠道订单类型是**我们的经营意图**,能力分类是**平台的能力**。

```
渠道订单类型(单值) --§10.3 映射--> owner_binding.capabilityClass(单值)
                                  ∈ provider_profile.businessScope
                                  ⊆ external_system.能力分类
```

⚠️ 第一段是**相等**(经映射),不是包含 —— 因为 binding 只承载一个业务线(§10.7A)。

- **接入类型 = 外部**:渠道订单类型必须落在该渠道所绑 `owner_binding` 的业务覆盖面内;
- **接入类型 = 内部**:不涉及外部系统,**不做该校验**;
- 「到店」**仅内部**,因此它**没有**对应的能力分类——不存在「到店」这个能力;
- 因此:**渠道订单类型的外部可取值 = 能力分类中"构成下单入口"的那两类(外卖、团购)**。

⛔ 不得因为名字相同就把二者合并成一个枚举。合并会导致「订单同步」「库存」这类
**不构成入口**的能力被误当作渠道订单类型。

**R2 · 经营主体类型 ↔ 可绑节点类型**

渠道的经营主体类型(项目 / 门店)决定其绑定挂在哪一类组织节点上。
约束:该节点类型必须 ∈ `provider_profile.可绑节点类型`。

**场景依据**:S-02(三级会员卡券系统:集团/项目/门店三层各有系统)、S-03(交易主数据类通常仅绑集团)、
S-04(项目开店与门店开店两种主体都成立)。

⚠️ `可绑节点类型` **仅表达允许绑定的节点类型,不用于权限与数据校验**(Dexter 明确)。
它是**展示与可选性约束**。授权真相在 workspace-IAM(G-05A),不得从该字段推导。

**R3 · 认证类型 ↔ 渠道生效条件**

`provider_profile.认证类型` 有三态:

| 认证类型 | 绑定完成条件 | platform-admin 可执行 |
|---|---|---|
| 需跳转外部授权 | 跳转外部平台完成授权 | **仅删除** |
| 仅内部映射 | 在系统内完成内外主体映射 | 增、删、改 |
| 无需映射 | 天然对应当前节点(如门店自有卡券系统) | 增、删、改 |

**场景依据**:S-07 —— 对接门店自有卡券系统时天然对应当前门店,无需额外映射,
因此「无需映射」必须是独立一态,不能并入「仅内部映射」。

**渠道生效条件**:外部渠道当且仅当其 `owner_binding` 状态有效时生效;
需授权者必须已完成授权认证。

**R4 · 能力属性 ↔ 菜单协作方向**(旧文 `menuCollaborationOptions` 的新落点)

旧规格把菜单协作模式挂在 `channelKind` 上。**现改为由能力属性推导**:
外卖/团购能力的属性(仅拉取外部菜单 / 支持推送本地菜单)决定该渠道可用的协作方向。

理由:同为「外卖」,美团与饿了么的菜单协作能力可能不同;挂在 kind 上无法表达平台差异。
**场景依据**:S-09。

**R5 · binding 基数 ↔ 平台类别**(见 §4.1B;场景 S-05)

| 平台类别 | 一条 binding 覆盖 | 实例 |
|---|---|---|
| 开放平台类 | **一个业务线** | 美团外卖店铺一条、美团团购店铺一条 |
| 非开放平台类 | **该 provider 的全部能力** | 商场 ERP 的主数据同步 + 订单同步,一条即可 |

⇒ 基数由**平台类别**决定,不由本系统统一规定;`externalOwnerId` **不设唯一约束**
(饿了么两业务共用一个店铺 ID)。

**R6 · 订单同步等协作运行时 —— 本期不做**

「订单同步」等能力分类**保留在分类枚举中**(provider 声明业务范围需要它),
但其**运行时行为一律不在本期范围**:不做分发收集、不做组织路径向上遍历、
不做订单来源与节点路径快照、不做重试/死信/治理信号、不做适配器联调。
未来实现时须重开需求,并接上已有的**货号**机制(G-09:货号即「订单上报商场 ERP 映射」)。

**R7 · 品牌 / 实际经营租户 ↔ 路径**(语料已定,不再讨论)

品牌与实际经营租户是**门店的属性**,不是路径层级:

- G-02:门店和总公司不是组织树节点;
- G-03:可见门店范围只来自 `Store.headCompanyRef`,**不从品牌授权反推**;
- G-04:每个门店必须且只能引用一个实际经营租户,项目+经营租户+品牌创建后锁定;
- G-05A:门店可读后可返回其品牌、实际经营租户、项目与总公司(关联事实)。

⇒ **可绑节点类型恰为五类:集团、大区、项目、总公司、门店。** 不含品牌与经营租户。

### 4.4 业务场景集(Dexter 口述的真实案例;后续作为验收夹具来源)

> 本节全部来自 2026-08-18 讨论中 Dexter 给出的**真实业务案例**,不是推演。
> 每个场景标注它验证的是哪条规则——它们既是需求的来源,也是验收夹具的来源。

**S-01 · 购物中心 ERP 只要订单同步**(验证 §4.2 能力正交)

购物中心的 ERP 从不产生订单,只需要知道发生了什么,因此**只具备「订单同步」能力,
不具备外卖/团购**。而美团**两者都要才完整**——既是订单来源,又要被告知状态变化。

⇒ 这是「订单同步」必须与「外卖/团购」分列的判别反例。若二者合并,购物中心 ERP 无法建模。

**S-02 · 三级会员卡券系统**(验证 R2 可绑节点类型 + R6 两条路径)

同一集团空间内可能同时存在:
- **集团统一**会员卡券系统 → 绑集团节点
- **项目专属**会员卡券系统 → 绑项目节点
- **门店自有**会员卡券系统 → 绑门店节点

⇒ 一张门店订单在判断权益时,可能**同时命中三层**。这直接决定了:
可绑节点类型必须支持五类全部。(⚠️ 分发收集属**本期不做**范围,§2.2)

**S-03 · 交易主数据类只绑集团**(验证 R2)

交易主数据类外部平台(如商场 ERP 同步组织/商品主数据)**通常仅允许绑定集团节点**。

⇒ 说明可绑节点类型是**按接入档案逐个声明**的,不是所有平台一视同仁。

**S-04 · 项目开店 vs 门店开店**(验证 R2 经营主体类型)

以美团外卖、团购为例,**两种经营主体都成立**:
- **项目**可作为主体在美团开店,售卖各门店商品,**后续由项目自行和门店结算**;
- **门店**也可独立在美团开店。

⇒ 因此模板必须有「经营主体类型(菜单维护方)」这一维;绑定要能挂在项目或门店。
⚠️ **项目与门店之间的结算是项目自行处理,不进本系统本期范围**(Dexter 明确)。

**S-05 · 同门店在美团开两个店铺**(验证 R5 绑定条数)

**Dexter 2026-08-18 的完整实例**:万象城海底捞一个门店,在美团有三个外部店铺 ——
外卖「海底捞拌饭」、外卖「海底捞冒菜」、团购「海底捞万象城店」。
⇒ 系统里建**三条经营渠道**,**每条渠道做一次授权绑定** —— 因为**每个渠道的菜单都不一样**。

平台形态差异:
- **美团**:两项业务 = 两个店铺 ID + 两套授权 ⇒ 2 条渠道、2 条绑定,`externalOwnerId` **不同**
- **饿了么**:两项业务 = **共用一个店铺 ID** + 两套授权 ⇒ 2 条渠道、2 条绑定,`externalOwnerId` **相同**

⇒ **驱动基数的是菜单粒度,不是平台形态**(§10.7A)。
`externalOwnerId` 因此**不设唯一约束**;而"一业务一绑定"恰恰是正确的。

**S-06 · 同模板多渠道实例**(验证 BR-15 不做唯一性校验)

某海底捞门店可在美团开设两家外卖店铺,分别命名为**海底捞盖饭**、**海底捞冒菜**。

⇒ 同一模板必须允许创建多条渠道实例。这推翻了旧规格 R-1「同项目同模板至多一条渠道」。

**S-07 · 门店自有卡券系统无需映射**(验证 R3 认证类型第三态)

对接**门店自有**会员卡券系统时,该系统**天然对应当前门店,无需额外做主体映射**。

⇒ 认证类型必须有「无需映射」这一态,不能只有「需授权」与「内部映射」两态。

**S-08 · 同平台不同 ISV 能力不同**(验证 §10.5 业务范围挂在档案上)

**美团对 ISV 的能力授权是可能不一样的**:A 接入档案仅支持外卖,
B 接入档案同时支持外卖 + 团购。

⇒ 能力范围**不能挂在外部系统上**,必须挂在接入档案上。这是三层拆分的真正理由。

**S-09 · 能力属性的两个已知例子**(验证 §11.1 声明字典)

- **团购**:团购商品支持「外部映射内部商品」,还是必须「内部映射外部商品」;
- **外卖**:仅支持「拉取外部菜单做内部映射」,还是支持「将本地菜单同步到外部平台」。

⇒ 同为「外卖」能力,不同平台的属性取值不同。这是 R4 把菜单协作方向从 `channelKind`
移到能力属性的直接理由。

**S-10 · 订单状态变化的分发**(⚠️ **本期不做**,仅作未来依据)

Dexter 原话:「订单状态变化了,找到所有需要订单同步的外部系统,一起丢过去,就好了。」
后台会根据**各种配置和订单信息的组合**判断要不要发给某个外部系统,
但**具体要定哪些属性、如何判断,当前尚未确定**。

⇒ **本期完全不做订单同步运行时**。该场景保留在此,只为说明「订单同步」为何必须作为独立能力分类存在(S-01),不构成本期需求。

### 4.5 预制与运行时的分界

| 对象 | 生命周期 | 集团空间 |
|---|---|---|
| `external_system` 定义(含能力分类与属性值) | **预制 · checked-in 契约** | **不区分** |
| `provider_profile` 定义 | **预制 · checked-in 契约** | **不区分** |
| 上述两者的**启用状态** | 运行时 | **按集团空间** |
| `owner_binding` | 运行时 | **按集团空间隔离** |

⚠️ **定义与启用状态是两个不同对象。** 定义全局唯一;启用状态按集团空间各自持有。

**定义的存储形态(Dexter 2026-08-18 裁定 Q-02)**:定义走 **checked-in 契约**,
随代码交付、随发布生效,与既有「对接能力目录」同族;**只有启用状态与绑定进数据库**。
由此保住判据:**新增一个平台 = 部署适配器 + 一行目录数据,主程序零代码改动**。

| 页面 | 可访问的节点角色 | 数据节点定位到 |
|---|---|---|

这与 G-05/G-05A 一致 —— 数据可见、页面准入与 capability 三者不得相互推导,
capability 只控制写操作。⛔ 不得再按对象或动作细分出更多写能力。

### UC-01 · 只读浏览(树、详情、绑定列表)

- **主角**:运维管理员 · **前置**:已切换到目标集团空间 · **后置**:无写入
- **本用例只有两条非显然的要求**,其余(树、Tab、抽屉、搜索、空态)由既有实现承担(§12):

## 10. 领域模型

### 10.0 记法与两类存储

| 记法 | 含义 |
|---|---|
| **契约态** | checked-in 契约,随代码交付。**没有** ref/version/审计字段 —— 它不是数据库行 |
| **运行态** | 数据库行,按集团空间隔离,有 ref/version/审计 |
| 「不可变」 | 创建后不得修改;需变更时新建 |

⚠️ 契约态对象**不要**照搬运行态的字段习惯去设计。定义没有 `createdAt`,它有的是**发布版本**。

### 10.1 关系总图

```
external_system  (契约态;全局)
   │  capabilities[]  ── 每项 = 能力分类 + 该类属性取值
   │
   └─ provider_profile  (契约态;全局)
         ├─ businessScope[]      ⊆ external_system.capabilities 的能力分类
         ├─ bindableNodeTypes[]  ⊆ {集团,大区,项目,总公司,门店}   ← 仅展示约束
         ├─ authenticationKind   ∈ {需跳转授权, 仅内部映射, 无需映射}
         │
         └─ owner_binding  (运行态;按集团空间隔离)
               ├─ 组织节点   nodeType ∈ provider_profile.bindableNodeTypes
               ├─ capabilityClass  ∈ provider_profile.businessScope(单值)
               └─ 外部主体标识 / 授权引用 / 状态

enablement_state  (运行态;集团空间 × 定义 → 启用/停用)

business_channel_template  (运行态;项目自建)
   └─ business_channel  (运行态;同模板可多条)
         └─ (外部时) → owner_binding    绑定有效 ⇒ 渠道生效
```

### 10.2 `external_system`(契约态)

| 字段 | 类型 | 必填 | 可变 | 业务含义 |
|---|---|---|---|---|
| `externalSystemCode` | 编码 · 全局唯一 | ✓ | **不可变** | 平台稳定标识,跨版本对账与 evidence 的锚 |
| `displayName` | 名称 | ✓ | 可改 | 界面展示名(如「美团」) |
| `capabilities[]` | 能力声明数组 → 10.3 | ✓ | 可改 | 该平台具备的能力分类集合,一对多 |
| `catalogStatus` | 枚举 `PLANNED` / `AVAILABLE` | ✓ | 可改 | 适配器是否已部署可用;`PLANNED` 时不得进入可选列表 |

⛔ 一个外部平台**恰对应一条**。不得为同一平台的不同业务建多条。

### 10.3 能力声明(契约态;`external_system.capabilities[]` 的每一项)

| 字段 | 类型 | 必填 | 业务含义 |
|---|---|---|---|

| `capabilityClass` | 中文名 | 构成下单入口 | 对应 `orderKind` |
|---|---|---|---|
| `MASTER_DATA_SYNC` | 主数据同步 | 否 | —— |
| `MEMBER_BENEFIT` | 用户与权益 | 否 | —— |
| `GROUP_BUY` | 团购 | **是** | `GROUP_BUY` |
| `TAKEAWAY` | 外卖 | **是** | `TAKEAWAY` |

| `providerCode` | 编码 · 全局唯一 | ✓ | **不可变** | 接入档案稳定标识 |

| `businessScope[]` | 能力分类数组 | ✓ | 可改 | 以该 ISV 身份可用的业务范围。**⊆ 所属系统的能力分类**(S-08) |

### 10.5A 关于引用形态的显式说明(不透明引用红线的反例登记)

`PLATFORM-BLUEPRINT.md`「不透明引用与复制闭合红线」要求:

> 持久化的跨事实关系必须存 owner 分配的不可变不透明 `*Ref`(UUID),
> 不得把人可读、可修改或可复用的业务编码伪装成引用。

本模型中 `enablement_state.targetCode` 与 `owner_binding.providerCode` **持久化的是业务编码**,
表面上与该红线冲突。**这是显式登记的反例,理由如下**:

1. 它们指向的是**契约态对象**(checked-in 定义),该对象**没有 owner 分配的 UUID** ——
   它不是数据库行,没有可分配 ref 的 owner(§10.0);
2. 这些编码由**契约定义并冻结**,是**不可修改、不可复用**的(§10.2 / §10.5 标注不可变),
   因此不具备红线所防范的「人可修改、可复用」特征;
3. 红线本身已列出反例形态(「已由 owner 定义为 UUID 的字段是反例,不得因本规则重新建模」),
   本项属对称情形:**没有 owner 也就没有 owner 分配的 UUID**。

⛔ 但**运行态之间**的引用一律用 UUID:`owner_binding.bindingRef`、`business_channel.channelRef`、
`business_channel.templateRef`、`business_channel.bindingRef`、`owner_binding.nodeRef` 均为 UUID。
⚠️ 若详设认为该反例不成立,应回来改需求,**不得默默给契约态对象编造 UUID**。

### 10.5B 两段式解绑协议(E-24;**主程序不知道任何平台规则**)

各外部平台的解绑机制与链接各不相同(美团要商家自己跳转到平台操作并异步回调,
其他平台可能完全不同)。**这些差异一律由适配器吸收**,主程序只见一个统一协议:

| 段 | 主程序动作 | 适配器返回 / 通知 | 主程序据此做什么 |
|---|---|---|---|
| **第一段** | 向适配器**申请解绑**,记 `unbindRequestedAt`,绑定进入**解绑中** | 二选一:① **已直接完成**;② **需用户自行操作**,附一个操作载荷;③ **失败/被拒**,附不透明原因载荷 | ① 主程序**在同一事务内自置 `externalRevokedAt`**,随即可标记删除;② 把载荷**原样展示**给用户,停留在解绑中;③ 退回原状态并展示原因 |
| **第二段** | 等待(绑定停在**解绑中**) | 用户在外部平台操作完成后,**适配器先收到消息**,再**通知主程序解绑成功**;或通知**失败** | 成功 ⇒ 回填 `externalRevokedAt`,方可标记删除;失败 ⇒ 退回原状态 |

⚠️ **无超时自动放弃**。解绑中可长期停留 —— 外部操作由商家决定何时做。
运营/运维可**撤销解绑申请**(退回原状态,清空 `unbindRequestedAt`),这是唯一的主动退出路径。

⛔ **主程序不得解析该操作载荷的结构**,不得据其内容分支,不得实现任何平台特定的解绑逻辑。
它是**不透明载荷**:主程序只负责展示与透传。
⛔ 主程序**不得**自行拼装解绑 URL、签名或平台参数 —— 那是适配器的职责。

⚠️ **本期不实现适配器**,因此 `REQUIRES_ADAPTER_UNBIND` 的绑定本期无法完成解绑,
停留在有效或失效态。这是合法状态(§2.2)。

⚠️ **未来 adaptor 通知语义需覆盖的一种情形(本期不实现,先登记)**:
外部平台的商家可能**单方面**解除授权,不由本系统发起。届时适配器同样先收到消息并通知主程序,
但结果应是**绑定失效**而非已删除 —— 因为没有人在本系统发起过删除。
该情形的完整语义待适配器批次定义。

### 10.7A 绑定的基数由**菜单粒度**决定(E-25)

**`owner_binding` 是扁平三元组,不是数组**:

```
owner_binding = (providerCode, capabilityClass, externalOwnerId) @ 组织节点
                 接入档案      单个业务线        外部店铺
```

**推导链**:菜单 ↔ 经营渠道 **1:1**(记录 001 第 6 条)→ 每个外部店铺有自己的菜单
→ **外部店铺 ↔ 渠道 1:1** → **渠道 ↔ binding 1:1**。

**实例(Dexter 2026-08-18)**:万象城海底捞一个门店,在美团有三个外部店铺 ——
外卖「海底捞拌饭」、外卖「海底捞冒菜」、团购「海底捞万象城店」。
⇒ 建**三条经营渠道**,**每条各做一次授权绑定**,因为三者菜单不同。

**两个平台反例**:

| 平台 | 渠道 | binding | `externalOwnerId` | `capabilityClass` |
|---|---|---|---|---|
| 美团 | 2 | 2 条 | **不同** | 外卖 / 团购 |
| 饿了么 | 2 | 2 条 | **相同** | 外卖 / 团购 |

⇒ 饿了么「共用一个店铺 ID + 两套授权」= 两条 binding 的 `externalOwnerId` 相同、业务线不同,
各自持有自己的授权与状态。**因此 `externalOwnerId` 不设唯一约束。**

**基数**:外部渠道 → **恰好 1 条** binding;binding → **0 或 1 条**渠道
(非渠道用途的 binding,如集团级会员卡券、主数据同步,**无渠道**)。

⛔ 不得把多个业务线塞进一条 binding —— 那样它们会共用一个 `externalOwnerId`、
一个授权与一个状态,而三个都应当各自独立。

### 10.10 状态机

| 对象 | 状态 | 迁移条件 |
|---|---|---|
| `enablement_state` | 启用 / 停用 | 运维管理员操作;停用 ⇒ 相关对象置灰且**级联停用依赖它的渠道**(E-21),数据一律保留 |
| `owner_binding` | 待授权 → 有效 → 失效 → **已删除** | 进入有效:`EXTERNAL_GRANT` 授权成功后;`INTERNAL_MAPPING` 映射完成后;`NO_MAPPING` 创建即有效。进入已删除:`LOCAL_ONLY` 直接标记;`REQUIRES_ADAPTER_UNBIND` **须走 §10.5B 两段式,适配器通知成功并回填 `externalRevokedAt` 后**方可 |
| `business_channel` | 草稿 → 生效 → 停用 | 内部渠道可直接生效;外部渠道须绑定为**有效**。**被动迁移**:绑定被删 ⇒ 落回草稿(E-20);模板停用 ⇒ 停用(E-21);外部系统/档案停用 ⇒ 停用(E-21) |

**级联规则(E-20 / E-21)**:

| 触发 | 连带 | 跨 owner? | 恢复语义 |
|---|---|---|---|
| 绑定被标记删除 | 引用它的渠道 **落回草稿**,`bindingRef` 置空 | **是**(协作域 → 渠道域) | 无自动恢复;运营重新选绑定 |
| 模板停用 | 其渠道实例 **停用**,`stopReasons` 含 `CASCADE_TEMPLATE` | 否(同为渠道域) | 模板重新启用 ⇒ 仅恢复 `CASCADE_TEMPLATE` 的 |
| 外部系统 / 接入档案停用 | 依赖它的渠道 **停用**,`stopReasons` 含 `CASCADE_EXTERNAL` | **是**(协作域 → 渠道域) | 重新启用 ⇒ 仅恢复 `CASCADE_EXTERNAL` 的 |

⚠️ **跨 owner 级联必须走目标模块的公开 command API,并加入同一 `REQUIRED` 事务**
(AGENTS.md 红线:跨模块写只调用目标模块公开 command API)。
⛔ 协作域不得直接写渠道域的表。

**恢复规则(C-01,Claude 技术决定;Dexter 只裁了级联停用未裁恢复)**:

恢复不是"翻转某个标志",而是**重新求值全部停用来源**:

1. 触发恢复的那个来源从 `stopReasons[]` 中移除;
2. 若 `stopReasons[]` **仍非空** ⇒ 渠道**保持停用**;
3. 仅当 `stopReasons[]` **变为空** ⇒ 渠道恢复。

⇒ 由此:模板恢复但外部系统仍停用 ⇒ 渠道不恢复(不违反 BR-31);
`MANUAL` 永不被级联覆盖或清除,只能由运营自己移除(不违反 BR-32 立意)。

## 15. 错误与异常语义

> 每条 BR 违反时必须返回**确定的 typed problem**,不得降级为泛化错误。
> 详设需把下表逐条落到 owner 的判定点;问题码集合与操作契约必须精确相等。

| problem code | HTTP | 触发 | 对应 BR |
|---|---|---|---|
| `BUSINESS_SCOPE_EXCEEDED` | 422 | 绑定业务覆盖面越出档案范围 | BR-03 |
| `NODE_TYPE_NOT_BINDABLE` | 422 | 绑定节点类型不在档案允许范围 | BR-04 |
| `ORDER_KIND_NOT_IN_BINDING` | 422 | 外部渠道订单类型不在绑定业务覆盖面内 | BR-05 |
| `DINE_IN_MUST_BE_INTERNAL` | 422 | 到店订单类型选了外部接入 | BR-06 |
| `DINE_IN_FORM_MISMATCH` | 422 | 到店未填点餐形式,或非到店却填了 | BR-07 |
| `PROVIDER_NOT_ENABLED` | 422 | 选用未对本空间启用或 `PLANNED` 的档案 | BR-08 |
| `BINDING_NOT_EFFECTIVE` | 409 | 绑定未生效即试图使渠道生效 | BR-09 |

| `IMMUTABLE_FIELD` | 422 | 修改模板四维或绑定的不可变字段 | BR-19 / BR-20 |
| `ADAPTER_UNBIND_REQUIRED` | 409 | `REQUIRES_ADAPTER_UNBIND` 绑定未完成两段式解绑即请求标记删除 | BR-29 |
| `VERSION_CONFLICT` | 409 | CAS 冲突 | 通用 |
| `ACCESS_DENIED` | 403 | 缺少所需写能力 | §17 |

**未配拒绝码的 BR,逐条给出理由(不得留白)**:

| BR | 为何无拒绝码 |
|---|---|
| BR-01、BR-02 | **目录发布期**校验,不在请求路径上。违反时**契约发布失败**,不产生 HTTP 响应 |
| BR-13、BR-15、BR-16 | 「出现即为缺陷」型:正确实现下不会有对应请求。**由红夹具证明其不发生** |
| BR-17 | 候选**查询结果**约束,越权模板不出现在候选中即可;不构成拒绝 |
| BR-18、BR-25 | **设计期判据**,不是运行时行为。见下方说明 |
| BR-24 | 保密约束,由响应体与 DOM 的红夹具证明,不是拒绝码 |

**关于 BR-18 与 BR-25 的验证方式**:二者是**设计期判据**,
不能用红夹具构造运行时反例。CLAUDE.md 明令「不得用关键词/字段匹配把语义伪装成 checker」,
因此也**不得**用「grep 到 `bindableNodeTypes` 出现在授权文件里」冒充判据。
正确形态是**评审期人工核验**:打开授权路径源码,证明其读取的事实集合中不含该字段;
以及打开 capability 注册表,证明渠道相关写能力恰为两个。

|---|---|---|---|
| OP-04 / OP-05 启停 | 集团空间(`groupWorkspaceKey`) | 运维管理员 | 启停是集团空间级事实 |
| OP-08 / 09 / 10 绑定(渠道所属) | **该绑定所挂组织节点** | 项目页:项目;门店页:门店 | target 由 owner 首读绑定行得出,**不取请求体** |
| OP-08 / 09 / 10 绑定(非渠道) | 该绑定所挂组织节点 | **仅运维管理员**(BR-27) | 运营侧无入口 |
| OP-11 授权回填 | 该绑定所挂组织节点 | **仅适配器身份** | 唯一可置为有效的入口(BR-10) |
| OP-13 模板 | **`PROJECT`** | 项目 | 模板是项目级资产;⛔ 不得以 `STORE` target 扩权 |
| OP-16 渠道(项目主体) | **`PROJECT`** | 项目 | —— |
| OP-16 渠道(门店主体) | **`STORE`** | 门店 | ⛔ 门店主体渠道**不得**以 `PROJECT` target 放宽 |

**运营侧写授权走既有机制,不新造**:edge 解析出 **server-minted `OperationsOwnerScopeGrant`**
传入事实 owner;owner 必须在 CAS、审计或 receipt replay 前,复核 grant 的
**workspace、group、target type、target reference、capability 与 operation purpose**
(PLATFORM-BLUEPRINT「运营写权限与范围解析红线」)。

⛔ 前端 session 投影、页面可见性、客户端 capability 字面量或请求 body 中的 scope/target
**不得**成为写授权真相(G-05A)。
⛔ 不得把一个渠道 grant 泛化成任意绑定写;门店主体渠道**不得**以 `PROJECT` target 放宽。

**两个写能力符合红线,不是偏好**:红线要求「**不同独立用户任务或不同目标数据节点类型的写入
必须有不同 capability**」。项目渠道(target = `PROJECT`)与门店渠道(target = `STORE`)
恰是两种目标节点类型,故恰为两个。
**读不设 capability 也是红线要求**:「operations capability 只表达用户发起的写工作流,
**不得作为页面访问或任何 GET 的读取权限**」「普通 scoped GET 只受页面/会话/owner scope 约束,
不新增 read capability」。

### 17.2 platform-admin 无 capability 模型(红线,非本文裁定)

`PLATFORM-BLUEPRINT.md`「平台授权模型红线」:平台管理员均为同级 `platform-super-admin`;
平台端写授权 = **有效平台 session + platform owner 对已启用状态的最终复核**;
**不得进入运营角色、页面准入或动作 capability 模型**;契约用
`x-required-platform-authorization`,**生成链与不变量门必须拒绝 platform-admin 的 `capabilityKey`**。

亲验:`modules/platform-admin-iam` 下无 capability 模型,与红线一致。
⇒ OP-04/05 与非渠道绑定的写授权走该形态。⛔ 详设不得为 platform-admin 引入任何 capability。

### 17.3 集团空间上下文(G-10)

运维管理后台 URL **不携带**集团空间编码;所选空间是**端内会话上下文**,
只在生成运营端链接时使用。因此 OP-01～OP-10 的集团空间来自会话上下文,
**不来自 URL 段,也不回退默认空间**。

**读取范围**按 G-05A:主对象读取的唯一范围真相是**角色节点**,不得用 capability 代替或补充。
**写授权**必须以 workspace-IAM 的实时任职、角色 capability 与 owner 首读事实生成 grant;
`bindableNodeTypes` **不参与**任何授权判定(BR-18)。
