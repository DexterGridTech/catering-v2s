## A1 · 角色与此刻任务(源:v6 用例 06/07 + 语料 G-05/G-11/G-12)

| 角色 | 此刻要完成的业务任务 |
|---|---|
| 总部品牌商品运营 | 维护品牌模板库:建分类/标签/单位/属性/选项库,建商品作为门店候选来源;**模板不是强继承** |
| 门店商品运营 | 维护本店商品:找→看→建→改→整理;从品牌库复制;治理外部订单临时商品 |
| 门店店长 | 审视与放行:批量停用、价格、生命周期动作的确认者;看比改多 |
| 后厨/出品 | **纯读**:这道菜怎么做(制作信息、处理标签、时长、做法加料对出品的影响) |
| 库存员 | **纯读为主**:这个商品扣不扣库存、扣什么、单位是什么;维护动作在库存页不在商品库 |
| 治理处理人 | 外部临时商品补全转正、重复商品映射、AUTO_SYNC 冲突处置 |

⚠️ 关键推论:**至少两类角色(后厨/库存员)只读不写** —— 详情面必须是他们能读懂的业务陈述,
而不是给编辑者准备的表单的禁用态。这从角色分析就能推出,与截图无关。

## A2 · 完整用户场景(主动找齐,含截图未点名者)

1. **查找与比较**:按分类树/关键字/智能视图(临时、未启用、最近更新)定位;在列表横向比较价格、形态、状态、用途。
2. **查看(纯只读)**:回答"这是什么/怎么做/扣什么库存/被谁引用"。消费者含不写库的角色。
3. **新建**:选形态→填最少必要事实→保存;快速路径,不应被完整编辑面拖住。
4. **完整编辑**:跨九类事实族(基础/条码标识/SKU 规格价格/点单选项/属性/制作信息/库存 BOM/套餐内容/引用关系)。
5. **维护复用配置(六类库)**:标签、计量单位、SKU 销售属性、商品处理标签、商品属性库、点单选项库 —— 长期管理任务,不是商品编辑的附属。
6. **批量整理**:批量状态流转(已裁定:逐项尽力+逐项报告)、批量分类/标签。
7. **品牌导入**:preflight→冲突呈现→执行→结果对账。
8. **本库复制**:同上,范围不同。
9. **生命周期**:启用/停用/归档/作废;被引用时的阻断与解释。
10. **临时商品治理**:预检(编码可用性、形态映射)→补全→转正;队列视图(智能视图承担)。
11. **失败恢复**:版本冲突、校验失败、批量部分失败、RESULT_UNKNOWN 先读回再决定。
12. **媒体维护**(截图未点名):图片上传、排序、主图;查看侧的图集浏览。
13. **分类树维护**(截图未点名):建/改名/挪父/排序 —— 它是"查找"的地基,坏了全库不可找。
14. **候选选择**(截图未点名):单位/标签/属性值/选项值/BOM 组件五类选择面,当前三种形态并存。
15. **规格子任务**(截图未点名):从销售属性生成 SKU 矩阵、逐 SKU 覆盖(条码/单位/制作/价格)。

**反例搜索**:导入导出(v4 有 `CatalogImportExport`)在 v2s 无对应且四批需求均未要求 —— 判为非目标,不算 gap;
称重标签秤参数(UC-TENANT-CATALOG-002)属终端投影,不进商品库 UI。

## A3 · 每场景 Journey 要点(触发/前提/步骤/成功/失败仍成立/返回/owner 边界)

以最关键四条为代表(其余同构,不逐条铺开):

- **查看**:触发=列表点名称。前提=读权限。步骤=打开只读详情→按事实族浏览→(可选)进入编辑。
  成功=问题被回答。失败读取=保留列表位置,给重试。返回=列表原位置、原筛选、原滚动。
  owner=聚合读(catalog+inventory 投影),**零写**。
- **完整编辑**:触发=详情"编辑"或列表行动作。前提=写 capability。步骤=进入编辑面→改任意事实族→**一次整单保存**。
  成功=readback 回显。失败=校验定位到字段+Tab、冲突保草稿提示重载、UNKNOWN 先读回。
  返回=编辑前来源(列表或详情)。owner=whole-save 经 coordinator 同一 REQUIRED 事务,UI 不拆多次保存。
- **六类库维护**:触发=独立入口(不经过某个商品)。前提=库写权限。步骤=选库→列表→行内/子面编辑。
  成功=库变更,已绑定值不动(单位/标签批已裁语义)。失败=引用阻断给"正在使用"解释。
  返回=库列表。owner=catalog(五类)+ fulfillment-production(处理标签)。
- **临时商品治理**:触发=智能视图"外部订单临时商品"。前提=治理权限。步骤=选商品→预检→补全→转正。
  成功=正式商品,历史订单仍按旧快照。失败=预检报告留在面上。owner=catalog(promotion),不触发布。

## A4 · 我独立推荐的信息架构与交互(未读稿件时的答案)

```text
商品库(左树保留)
├─ 目录树 + 结果表(查找/比较主枢纽;智能视图并列)
│    行动作:查看 · 编辑 · 状态 · 复制入口;批量=选择后动作条
├─ 只读详情 = Drawer(从列表进,保上下文;业务陈述式,零表单零禁用态)
│    消费角色含后厨/库存员;含图集、有效制作信息、BOM 摘要、引用关系
├─ 完整编辑 = 独立可路由工作区(全页,/catalog/items/:code/edit)
│    九类事实族做区段导航;一次整单保存;草稿刷新可存活
├─ 新建 = 轻量向导(选形态→最少事实→保存),完成后跳编辑工作区继续补
├─ 商品配置 = 独立配置页(六类库左侧导航;不再是 Modal)
│    简单字典=列表+行内/小弹层;父子字典=主从两栏;复杂定义=主从+详情编辑器
├─ 复制(品牌/本库)= 向导式(选源→预检冲突→执行→逐项结果)
└─ 批量结果 = 逐项结果 Modal(沿用已裁定 B-05 形态)
```

**核心裁断与理由:**

1. **查看与编辑必须是两个不同性质的面**。禁用表单当详情有三重罪:
   读者要在输入框噪音里找事实;"为什么不能改"与"这是什么"两个问题混在一处;
   禁用态天然缺"谁在用/有效值合成"这类**只读才需要**的衍生信息。
2. **完整编辑放弃 Drawer,改独立可路由工作区**。5,677 行 Drawer 是症状不是原因 ——
   原因是九类事实族 × 跨 owner 区段 × 深层子编辑(SKU 矩阵、BOM 树、选项值物料)
   在一个抽屉宽度里只能靠 Modal 叠 Modal(当前 27 个 surface 大半由此而来)。
   工作区给出:URL 可达(可分享"改到哪了")、浏览器后退、刷新存草稿、双栏空间(BOM 左树右详情天然放得下)、
   弹层层级从 3 降到 ≤1。
3. **六类库升为独立配置页**。它们是被全库引用的长期资产,管理它们是独立任务(v6 用例的入口就是"品牌后台/商品库"平级),
   2,031 行六 Tab Modal 无 URL、无深链、复杂定义(选项库带值+强制物料)在 Modal 里没有主从空间。
4. **形态按复杂度分层**:简单字典(标签/单位/处理标签)列表+行内;父子(SKU 属性→值)主从两栏;
   复杂定义(点单选项:定义→值→物料)主从+专用编辑器。**一刀切是当前混乱的来源之一**。
5. **列表列 = 可比较事实**:名称(进详情)、编码、形态、状态、价格摘要、分类、用途徽标(SKU 数/库存方式/引用)、更新时间。
   徽标点开即详情对应区段,不在列表里展开编辑。

## A5 · 替代方案比较(独立完成)

| 决策点 | 候选 | 我的选择与放弃理由 |
|---|---|---|

## A6 · 列表比较 / 只读详情 / 编辑 / 长期入口的归属判据

**列表**=横向比较用的少量标量+徽标;**详情**=单对象全事实的业务陈述(含衍生:有效制作、BOM 摘要、被引用);
**编辑**=会改变事实的一切,含子任务(SKU 矩阵、选项配置、BOM 配置);
**长期入口**=被多商品引用的共享资产(六库、分类树、复制、治理队列)。
判别式:**"读它需不需要商品上下文"分列表/详情,"改它影响一个还是多个商品"分编辑/长期入口。**

## A7 · v4 可借鉴 / 必须拒绝

**借鉴**:`ReadonlySections` 与 `EditableFields` 的**文件级分离**(v4 早已证明查看≠编辑可以分开写);
列表的 summary cell 族(价格/形态/风险徽标);`BatchActionBar`;ordering-options 的主从 Workbench;
`ImportPreview` 的预检呈现。
**拒绝**:`ModalsHost` 集中叠弹层;六值 identifier 枚举 UI(已被三值闭集取代);
销售单位当消耗单位;HAS_SKU 动态粒度;OPTION_TARGET;自由文本 station/print tags;
以及 v4 详情里仍存在的禁用输入段。

## A8 · 当前 v2s 全量交互 gap(独立枚举,超出 14 标注)

1. 禁用表单冒充详情(查看=编辑面禁用);2. 六库挤在 2,031 行 Modal,无 URL 无主从;
3. 弹层叠三层(Drawer→Modal→confirm);4. 候选选择三种形态并存(DescriptorPicker / 原生 Select / cursor hook);
5. SKU 矩阵生成与逐 SKU 覆盖埋在 5,677 行文件的区段里,无子任务导航;
6. 两个复制 Drawer 内部结构不同构,冲突呈现不一致;7. 分类树维护动作(挪父/排序)confirm 化,无预览;
8. 媒体主图/排序的查看侧呈现缺失;9. 批量分类/标签走逐项 save 循环,结果面与状态批量不同构;
10. 治理预检报告与编辑面耦合;11. 焦点归还/键盘路径无系统约定(仅新批次逐条写);
12. 空态文案不统一;13. 确认面(8 处 confirm)无风险分级;14. 错误定位到 Tab 有了、定位到区段内锚点没有。

## A9 · owner 边界与禁止反推(独立陈述)

catalog 拥有商品结构五族+条码标识+制作信息+分类/标签/单位/属性/选项定义;
inventory 拥有 StockTarget/BOM/余额/流水;asset 拥有媒体绑定;处理标签归 fulfillment-production;
菜单/可售归销售集合域(未建)。
**禁止**:从商品状态推可售;从库存推菜单;在商品 UI 直写库存事实(必须经 whole-save typed 区段);
从渠道/价格反推商品;UI 猜准入(必须消费 manifest,owner 终判)。

## C2 · 承载设计(裁定内的最优解)

### C2.1 商品配置(U-CATUI-01 授权我定):**全高抽屉,内部左导航**

**选抽屉不选弹窗**,三个理由:
1. 六类配置内容量差异巨大(标签一屏、点单选项要主从),**抽屉全高**天然给主从两栏空间;
   弹窗居中限高,内容少时空、内容多时滚,两头不讨好 —— 这正是现状 1200px Modal 的病;
2. 抽屉从侧面推入,工作台仍在视野里,符合"一个工作区"的心智;
3. 复杂定义的编辑可以在**同一抽屉内**的右栏完成,不再需要"Modal 上叠宽 Drawer"。

形态:
```text
商品配置抽屉(全高,宽度=工作台可用宽的上限档)
├─ 左栏:六库导航(商品标签/计量单位/规格维度/制作处理标签/商品属性/点单选项)
└─ 右栏:按三层形态
    简单字典 → 列表即详情,新建/编辑用小弹窗(允许的唯一一层)
    父子字典 → 右栏内再分主从两列(维度|值)
    复杂定义 → 右栏内列表↔详情编辑切换(同栏切换,不叠新抽屉)
```
⛔ 配置抽屉之上只允许一层小弹窗(新建/改名/确认);**禁止在它之上再开任何抽屉**。

### C2.2 商品完整编辑(U-CATUI-02):**超宽编辑抽屉 = "抽屉里的工作区"**

选抽屉不选弹窗:编辑是长任务,抽屉全高 + 可到最宽档(现有 `adminWideDrawerSurfaceProps` 上限),
空间最接近全页;弹窗的居中框对九分区长表单没有任何优势。

旧抽屉的三宗病,逐条在抽屉内解:

| 旧病 | 抽屉内的解法 |
|---|---|
| 查看/编辑同壳靠禁用切换 | **查看抽屉与编辑抽屉是两个不同 surface、不同组件**。查看=业务陈述零表单;点"编辑"关查看开编辑 |
| 弹层叠三层 | **嵌套上限=1**:编辑抽屉之上只允许一层"子任务面"(SKU 矩阵行详情、BOM 组件选择、套餐组件选择、选项值物料),子任务面之上只允许 confirm。⛔ 子任务面内不得再开选择抽屉 —— 候选选择在子任务面内完成 |
| 无 URL ⇒ 刷新即丢 | **草稿持久化到 sessionStorage**(键=商品编码+版本):意外关闭/刷新后重开该商品,提示"检测到未保存草稿:恢复/放弃"。⚠️ 深链与浏览器后退**随裁定放弃**,登记为已知边界,不再以此为由重提工作区 |
| 5,677 行宿主 | 见 C3 工程结构 |

编辑抽屉内部:左侧**区段锚点导航**(九类事实族按 shape 裁剪,标脏/错误徽标),右侧区段内容;
底部保存栏常驻;一次整单保存语义不变。

### C2.3 "一个工作区"的叠层总规则(全库统一)

```text
工作台(唯一页面,树+表)
 └─ 第一层:查看抽屉 | 编辑抽屉 | 配置抽屉 | 复制向导抽屉 —— 同层互斥,同时只开一个
     └─ 第二层:子任务面(编辑抽屉专属)| 小弹窗(新建/编辑简单对象)
         └─ 第三层:仅 confirm
```
- **同层互斥 + 切换保草稿**:编辑中需要去配置(如缺一个单位),关编辑抽屉(草稿已持久化)开配置抽屉,
  配置完成后工作台出现"继续编辑〈商品名〉"回入口,一键恢复原区段原草稿。
- 判据改写(替换本评审 S-1 的两条):
  ①「编辑抽屉意外关闭或页面刷新后,重开同一商品可恢复草稿与所在区段」;
  ②「任意时刻叠层深度 ≤3(抽屉→子任务面/小弹窗→confirm),且第一层永不并存两个抽屉」。

## C3 · 工程结构要求(Dexter 硬要求的落地形)

进入正式需求的验收条款,不是建议:

1. **一文件一职责**:宿主文件只做装配与生命周期(目标 ≤300 行);
   九类事实族各自独立文件,且**查看组件与编辑组件分文件**
   (`XxxSectionView.tsx` / `XxxSectionEditor.tsx`)—— v4 的 ReadonlySections/EditableFields
   分离已证明此路可行;
2. **hook 按业务命名并集中设计**,一次成套,不逐次补:
   - `useCatalogItemDraft`:整单草稿的唯一 state(typed 区段、每区段 dirty/error、sessionStorage 持久化、恢复);
   - `useCatalogConfigLibrary`:六库的列表/选中/筛选状态;
   - 候选选择收敛为**两种标准形态**(有限候选 `useBoundedCandidates`、搜索候选沿用 cursor hook),
     五类选择面归入其一 —— 同时闭合本评审 N-2;
   - 提交/幂等/刷新沿用 foundation 既有件(`useSubmissionLifecycle`、`useDrawerFormLifecycle`、
     `useRefreshVersion`),⛔ 不自造平行生命周期;
3. **state 分层成文**:服务端事实只住 RTK `currentData`;草稿只住 draft store;
   UI 瞬态(展开/选中/滚动)只住组件本地 —— 三层各一个住址,详设必须画出这张表;
4. **可证伪判据**:新增一个区段字段时,改动只落在该区段的 View/Editor 与 draft 类型,
   宿主文件零改动 —— 做不到即结构未达标。

## C5 · 体验一致性规范(Dexter 2026-08-23 追加硬要求)

**病因先记录**:商品管理历经多批各自出交互稿,每批文案/按钮位/提示方式各裁各的 ——
批内一致、批间漂移。**解法不是再写一份"商品工作区规范"**(那会成为第二住址),
而是把跨批通用的交互约定**沉到唯一正本 `doc/platform/frontend-coding-standard.md`**(新增一节),
本批交互稿只做逐字引用与逐 surface 应用;后续任何批次的交互稿必须先读它,禁止重新发明。

正本新节至少覆盖(每条都要能被 review 证伪,写不出反例的不收):

| 族 | 必须定死的约定 |
|---|---|
| 表单 | label 位置与对齐;必填标记;帮助文案用 `extra` 还是 tooltip 的判别式;错误显示位置;字段宽度档位(短/中/长/满);分组标题层级 |
| 弹层 | 标题结构(对象名在前);按钮位置(主右次左、右下固定);关闭三径(X/Esc/遮罩)的 dirty 行为;宽度档位与内容匹配规则 |
| 动作命名 | **统一动词表**:新建/编辑/保存/取消/停用/启用/移除(解除关系)/删除(消灭事实)/作废并重建 —— 一词一义,禁止同义混用 |
| 提示 | 成功用 message 还是原位回显的判别式;失败一律定位到字段/区段,禁止只弹全局错误;说明性文字 vs tooltip 的选择判据 |
| 空态 | 统一句式「还没有 X」+ 当前任务的下一步动作(呼应稿件判据 8) |
| 确认 | 普通/危险两级;危险确认必须说明影响与不可恢复部分;确认面内禁止嵌表单 |
| 状态 Tag | 用色语义全库统一(草稿/启用/停用/归档/作废各一色,不得挪用) |

**防漂移判据**:任取两个不同批次交付的 surface,上表七族逐项对照零差异;有差异即缺陷,
不接受"该批交互稿是这么写的"作为豁免 —— 交互稿与正本冲突时正本赢。

### C6.2 L2 脚本设计要求(「不是点一下看一下」的成文化)

1. **双分母,双清零**:
   - 业务分母 = 本轮八类 Journey × 各自的成功/失败/恢复路径(含:批量部分失败、
     编辑抽屉刷新恢复草稿、配置绕行返回、复制冲突、治理预检拒绝、无权限只读);
   - 控件分母 = C6.1 的 testId 全集。
   - **覆盖门**:`声明 testId 集合 − L2 实际触达集合 = ∅`,差集非空即 FAIL 并列出漏网控件;
     业务场景侧同理,blueprint 里每个 scenario 必须映射到 Journey 清单,无主场景即 FAIL。
2. **oracle 必须是业务结果,不是可见性**:每个 case 的 `businessOracle` 至少断言一项
   状态变化(readback 值、列表行变化、草稿恢复内容、错误文案逐字、焦点归还位置);
   「元素存在/页面打开」不算 oracle —— 这类 case 一律打回;
3. **负路径与不变量**:每个写场景配一个失败 case(校验/冲突/无权限),断言
   **事实未变**(版本、列表值)与错误定位;
4. **一致性抽查进 L2**:按 C5 的七族约定,跨两个不同 surface 各取一例做逐项断言
   (按钮位置、动词、空态句式),把"批间漂移"变成会红的测试;
5. **执行边界不变**:L2 属受管动态动作,按既有边界另行授权执行;
   本要求只把"设计与分母"前置到详设,⛔ 不得用 focused/静态测试冒充 L2 结果。

### C6.3 判据汇总(并入正式需求验收)

- 常量模块与组件引用/locator bindings 三方一致(门断言);
- L2 双分母清零门存在且红夹具真红(删一个 case 或一个 testId 绑定即红);
- blueprint 每 case 有非可见性 oracle;每写场景有负 case;
- 一致性七族在正本落位,且 L2 含跨 surface 抽查 case。
