## 3 · 部分裁定（主问题已答，附带问题还悬着）

### 3.1 `Q-11` 性能问题的真实来源 —— **主问题已答，量级未给**

- ✅ 已裁：**不引入 React Compiler**（"当前 POC 没什么具体业务，还不慢，后面建设时再针对性优化"）→ `T-4`
- ❌ 仍未知：**一家门店的主数据量级**（多少商品 / SKU / 菜单，投影多大）

**为什么它还重要**：这个数字决定三件事 ——
`persist-sqlite` 什么时候真的需要、列表要不要虚拟化、TDP 投影要不要批处理。
现在不需要答（业务未定），但**第一次做业务 UI 之前必须答**。

### 3.2 `X-08` 安全边界 —— **一半已裁，一半未裁**

- ✅ 已裁：automation 面**必须编译期剔除**，不靠运行期开关 → `TR-08`
- ❌ 未裁：**`scripts.execute`（任意脚本执行）要不要带到 TER**

**现状**：它只在 `TR-08` 里作为"要被剔除的能力之一"出现，
但"TER 到底要不要这个能力"本身**从未被回答**。
它同时是 workflow 的动态表达式求值基础（`T-?` / 台账 `FIX-18`）——
若 workflow 不采纳，脚本执行可能整条不需要。

### 4.1 ~~`Q-04` 双终端拓扑边界~~ —— **已裁定（2026-08-28）**

> **裁定**：仍是"一主一副"，**与一机双屏能力保持一致**；
> 只是跨机拓扑允许副屏（一般是平板）**可以拿下来（监听接电状态）当成主屏使用**。

⇒ POC 的 pair 模型**原样继承**，"多 peer 图网络"仍是已被证伪的方向。
"拿下来当主屏"正是 POC 已实现的 `standalone slave` + `powerDisplaySwitch`
（`DevicePort.addPowerStatusChangeListener` → `eligibility` → 确认请求 command → UI bridge → 执行）。
批次影响见 `00-ter-build-order` §4B.11。
