## 3. S1 ｜`RP-12` 的两层分母**单位混用**，`357` 不是任何集合的基数

**位置**：`plan.md:88`

> "`316` 是……必须逐处人工归类……的 Java 分支逻辑；`673` 仅是全仓业务枚举字面量 discovery inventory。
> ……**其余 357 项**须记录是否活代码、所属集合及纳入/不纳入后续实施的理由"

**我实测的真实口径**：

```
五类节点字面量：出现 477 次，分布在 320 行（SQL 4 行 + 逻辑 316 行）
全部业务枚举字面量：出现 673 次（含 ENABLED/DISABLED/ACTIVE/PENDING/COMPLETED… 等状态枚举）
```

- **`316` 是「五类节点的逻辑**行数**」**（我终稿的口径）
- **`673` 是「全部业务枚举的出现**次数**」**
- `673 − 316 = 357` 是**行数减次数**，**不对应任何真实集合**

**影响面**：`RP-12` 是 `RP-12a..n` 的**唯一输入**，分母定义不自洽会直接传导到全部后续实施单元。
更实质的问题是：`673` 里绝大多数是**状态枚举**（`ENABLED`/`DISABLED`/`PENDING`…），
它们与"节点类型集合归类"**不是同一语义域**，把它们当作归类工作的"其余项"会让
RP-12 的产物混入无关对象。

**最小修复**：把 RP-12 的分母改写为同单位、同语义域：

- **归类对象**：五类节点字面量的 **477 次出现 / 320 行**（其中 SQL 4 行、逻辑 316 行）；
  Dexter 已裁定的"全量收敛 316"对应其中的**逻辑行**部分。
- **discovery 面**：`673` 次全业务枚举**单列**为 RP-12 的第二产物，
  用于发现"是否存在第 6、第 7 个封闭集合"，**不与 316 相减**。

**是否需要 Dexter 裁决**：否（口径修正，不改变已裁定的收敛范围）。

## 4. S2 ｜让诊断重新可跑被阻塞在一个只影响**防复发手段**的决策上

**位置**：`plan.md:72-73`（RP-02 依赖 RP-01；RP-01 需 D4）、`:115`（S1 阶段）

`RP-01` 要 Dexter 在 **"runner 迁 TS" vs "runtime generated validator"** 之间选（D4）；
`RP-02` 声明**依赖 RP-01**。

但 `RP-02` 实际包含两类互不相干的工作：

| RP-02 的内容 | 是否真的需要 D4 |
| --- | --- |
| 删除硬编码 `147` | **否** |
| 移除两个 store 请求的废弃 `projectId` | **否** |
| 补齐缺失 operation 的 scenario fact / disposition | **否** |
| root/registry/report/catalog/facts/assertion 的 set equality | **否** |
| runner request body 的**可执行约束**接入 | **是** |

**影响面**：诊断 workload 目前**在首个请求前就失败**（`HTTP_DIAGNOSTIC_SCENARIO_FACT_SET_INVALID`），
而它是**其余所有单元动态证据的前提**。把"让它重新能跑"整体挂在一个
只决定**未来防复发形态**的选择上，会让 D4 的等待时间直接变成全程序的关键路径。

**最小修复**：把 RP-02 拆为两个单元：

- **RP-02a（不依赖 D4）**：分母对账 + 删除 `147` + 移除已删字段 + 补齐 fact/disposition
  → 目标是**诊断能越过首请求**；
- **RP-02b（依赖 D4）**：按选定路径接入 request body 的可执行约束
  → 目标是**让"契约删字段"在编译期/构建期变红**。

这不改变计划的任何结论，只解除一条不必要的关键路径耦合。

**是否需要 Dexter 裁决**：否。

## 5. S3 ｜防复发缺三块，其中一块正是**结构性根因本身**的预防

`§7`（`:136-146`）的防复发映射**全部是测试/门形态**，是"建完之后能被抓住"。
我终稿 `§4.5` 里三项**设计期/机制层**的预防未被纳入：

**(1) 缺"门必须接线或显式豁免"的自指 check —— 这一条最重要**

我终稿 `§4.5.0` 的核心实测事实是：**38 道门只有 10 道进了 `scripts/verify`**，
`logging-boundaries` 长期为红没人知道**正是因为它不在任何人会跑的命令里**。

`RP-00b` 做的是**一次性接线**。计划里**没有任何机制**阻止
"下一道新建的门又不接线" —— 即**结构性根因本身没有被预防**。

**最小修复**：在 RP-00b 内补一条极小 check：
`scripts/check/` 下每个真门要么在 verify 中、要么在显式豁免清单中，二者必居其一。
这是一行机械事实，成本极低，且正是本次最大教训的对症预防。

**(2) 缺三条设计期 project-memory 条目**

我终稿 `§4.5.2` 建议且**只建议**三条：
`observability-contract`、`closed-set-single-source`、`typed-failure-taxonomy`。
它们的作用是让**未来新增功能时**必须回答"它如何被追踪""规范源在哪""依赖失败与不存在是否不同 typed outcome"。

计划 `:24`/`:120` 只要求实施者"回读六维 project-memory"——
**但要回读的那三条内容并不存在**。没有它们，防复发是纯反应式的：
要等功能建完、测试没覆盖到，才可能被发现。

**最小修复**：把这三条的建立挂到对应单元
（`observability-contract` → RP-03 产物；`closed-set-single-source` → RP-12 产物；
`typed-failure-taxonomy` → RP-09/RP-15/RP-16 的共同产物）。

**(3) 缺周期性 sweep**

我终稿 `§4.5.4` 建议每个 R 收口时跑**全部**门（而非 verify 的子集）+ 一次跨 App 重复符号扫描。
本次正是这两个手工动作暴露了 `logging-boundaries` 长期红与 14 个同名 helper。
计划未纳入。**建议采纳，但保持最小** —— 只加这一条节奏，不新建流程。

**是否需要 Dexter 裁决**：否，三项都在既有边界内。

## 6. N

**N1 ｜一处 5 行的 fail-closed 安全修复被折进大批次**

`plan.md:89` 把 `WorkspaceAuthenticationService.enterable(...)` 的静默
`default -> false` 改为 fail-closed 放在 `RP-12a` 内。

我终稿 `§4.5.3b` 与批次表都写明**该处可先于全量收敛单独落地** ——
它是全仓**唯一**真正静默的节点类型分支（其余 6 处 `switch` 都是 `default -> throw`，
3 处是无害的 SQL 字段默认），改动极小。

从"批次内聚"角度计划的选择可辩护（它确实属于服务节点集合），
但从"风险暴露时长"角度不如单独先落。**建议至少在 RP-12a 内标为最先执行项。**

**N2 ｜`RP-12` 的"至少五种语义集合"表述可再收紧一档**

我实测确认的是**恰好 5 个**（服务节点、组织树、audit entityType、业务实体、extension host，
其中 extension host 有 8 值）。计划 `:88` 写"至少五种……及实测新增集合"是安全的开放表述，
但可直接写明这 5 个的**当前已知取值**，让归类工作有确定起点而非从零发现。
