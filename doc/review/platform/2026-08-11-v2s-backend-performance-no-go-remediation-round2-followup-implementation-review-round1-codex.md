## Independent findings and counterexamples

### M-01 — duplicate GET transport envelope — REJECTED_WITH_EVIDENCE

Current bytes have one explicitly classified owner per GET, not a frontend method-only wrapper:

| Owner | GET count | Operations |
| --- | ---: | --- |
| `MODEL` | 6 | workbench context, dictionary, production tags, local-copy candidates, brand-copy candidates, inventory targets |
| `P1` | 3 | catalog navigation, item page, item detail |
| `P3` | 7 | six inventory detail/read models plus catalog shape manifest |

The P3 generator derives this from both `read-models` and current OpenAPI required fields:
model-owned envelopes remain direct model types; P1-owned and P3-owned envelopes do not receive a
second wrapper. Generated edge and RTK types match this classification exactly. The six previous
counterexamples now consume one `.data`: `CatalogItemDrawer` uses
`productionTagsQuery.data?.data.entries`, and `CatalogDictionaryDrawer` uses each query's
`.data?.data`; the forbidden `.data.data` and query-response casts are mechanically rejected across
all six catalog-management GET consumers. The rerun red mutation proves the control rejects an
envelope-shaped model receiving a second P3 wrapper.

### N-01 — entry/current/exit hash semantic ambiguity — REJECTED_WITH_EVIDENCE

The remote input now distinguishes immutable `entrySnapshot.entries[*].entrySha256` from current
`inputs[*].sha256`; the latter must equal current bytes and the exit's
`observedInputState.entries[*].exitSha256`. The source inventory and shape matrix current hashes
are respectively `3ed5…6507` and `0650…f0bd`, match both input and exit, and their different
immutable entry hashes are covered by the exact two-member
`legalEntryDriftDispositions` set with `ALLOWED_IN_PACKAGE_SCOPE_CHANGE`. The self-test proves both

### N-02 — command response semantic double envelope — REJECTED_WITH_EVIDENCE

The same classifier protects mutations. Of 26 mutation responses, 24 are model-owned transport
