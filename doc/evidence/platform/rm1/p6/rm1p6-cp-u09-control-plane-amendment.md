# RM1 P6 observability and acceptance extension admission control

## 1. Problem and Dexter authorization

P6-1 must let an unauthenticated person authenticate or recover a password without leaking credentials,
OTP, cookies, grants, flow tokens or personal data. Dexter additionally requires that development and
acceptance work remains diagnosable: long-running verification has bounded lifecycle evidence, and public
authentication/recovery uses a safe, structured, correlation-aware diagnostic design rather than audit rows
or RFC7807 responses as substitutes.

Dexter explicitly authorized (a) the P6-1 runner/security-observability extension and (b) landing the
corresponding project-memory/development standard. This CP-U09 package is the least-scope admission
interlude for that authorization. The authorization source is Dexter's direct session instruction delivered
to Codex before this package was activated; it is not inferred from historical P6 design bytes.

## 2. Exact scope and non-business boundary

CP-U09 may modify only the nine surfaces named in its control-plane manifest: `AGENTS.md`, the named
observability decision, the named project-memory kernel/inventory/index derivation files,
`tools/project-memory/cli.mjs`, `tools/compliance-control/cli.mjs`, and its own evidence directory.

The package may create the normative standard and its deterministic memory route, and may strengthen the
existing admission verifier so both `serialPredecessor.exitSha256` and active
`predecessorExitSha256` equal the actual predecessor package-exit hash. The focused red mutation is a
one-character predecessor hash drift; the admission checker must fail before any implementation claim.

This package does **not** alter `scripts/test/r5-remote-testcontainers.mjs`, backend foundation or public
authentication/recovery source, OpenAPI, generated outputs, migrations, frontend, DEV, seed, reset, or
Roadmap state. Those paths remain excluded until a subsequent implementation-facing extension design
names exact files, owner boundaries, safe fields/redaction, lifecycle/cleanup semantics and focused red
tests. No unknown backend path is pre-authorized here.

## 3. U01 preservation and handback

`RM1P6-U01` is unfinished and cannot be used as CP-U09's serial predecessor. CP-U09 instead uses the
already-PASS `RM1-U08` exit with its pinned SHA-256. Its active-pointer predecessor is the exact U01 byte
whose SHA-256 is `f319e1974205ea5316ef64c1e56d1df2935fece982a140365e2e8077cd7cd91e`.

CP-U09 has its own baseline, hook receipts, source-compliance disposition and package exit. After the
control exit passes, it restores the exact U01 active pointer; it does not rewrite U01's input, baseline,
hook receipts, delta, business evidence or cleanup evidence.

## 4. Exit

The exit requires exact actual-change/incremental-receipt equality, two CP source-disposition rows, the
predecessor-hash red/green proof, standards coverage, `business: NOT_APPLICABLE`, `cleanup: PASS`, and
the U01 active-pointer byte-for-byte handback readback. It cannot claim the runner or backend observability
implementation is complete.
