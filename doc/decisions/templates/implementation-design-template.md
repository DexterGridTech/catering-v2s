# implementation-facing 详设模板

- 建立:2026-08-19 · 作者:Claude
- 由 `cs-writing-plans` / `cs-spec-to-plan` 引用。派活话术见 `doc/platform/implementation-task-template.md`。
- **本模板是给作者填的表,不是给脚本判的门。** 价值全在"写详设时照着填",
  ⛔ 不得为它新建 compliance-control、分母台账或机器扫描(那一整套已退役)。

## 收录尺度(新增维度前先过这三关)

一个维度值得存在,必须满足三条之一:**这次真的坏在它上面** · **漏了不报错** ·
**实施者必然要做这个决定而本仓只有一个正确答案**。
⛔ 反过来:**漏了会编译失败的不收** —— 编译器管得比文档好,写进来只是噪音。

## 1 · 真实业务目标与方案比较(必填,不可省)

**§1.1 这一批要解决的结构性问题** —— 写"不做会怎样",不写"要做什么"。

**§1.2 方案比较**(至少三个,含被否的):

| 方案 | 结果 | 结论 |
|---|---|---|
| A | | 拒绝,因为… |
| B | | 拒绝,因为… |
| C | | **采用** |

必须有一句:**「我选了 C 而不是 A/B,因为 …」**

> 为什么必填:没有它,评审只能验"闭环对不对",验不了"方案对不对"。
> 而闭环正确、方向错误是最贵的一类缺陷。

## 3 · 横切机制对照表(主结构 · 逐实现步骤填三列)

**行集由本表给定,作者只能填值、不得删行**;不适用写 `N/A` 并给理由。
⚠️ 整组不适用时(纯后端批次对前端组、纯前端批次对后端组),**该组写一次 `N/A` + 理由即可**,
不必逐行重复 —— 逐行仪式会让人停止阅读,那正是本表要避免的。

> 中间一列标出的规范条目是**已登记的正本位置**,填表时打开它读判别式,
> ⛔ 不要凭印象;其中多条明确「不能做成门」,只能靠人写下来。

**三列各自的红线:**

- **① 写精确路径或符号名**,⛔ 不写「参考 foundation」「沿用既有做法」。
  查表入口(按顺序):
  `doc/platform/backend-coding-standard.md` / `frontend-coding-standard.md`(**各自领域的唯一权威**) ·
  `project-memory/practices/frontend-capability-lookup.md` · `backend-capability-lookup.md` ·
  `doc/platform/foundation-charter.md`。
  ⚠️ 两份 coding-standard 都把规则分成「**能变成门的**」和「**只能靠 review 的**」两类;
  后一类**没有任何机器会替你检查**,是本表存在的主要理由。
- **② 写一个能做的观察,并标出它在哪一档执行**(静态 / focused test / acceptance / 浏览器),
  选**能证伪它的最低档**。⛔ 不写属性描述;⛔ 不写只有跑起来应用才能做的动作 ——
  多数批次不授权 DEV/L2,那样的观察在本批无法执行,规则就退化成仪式。档位表见 IA 模板 §2.2。
- **③ 最容易漏的一列。** 凡「本仓只有代码先例、没有成文规范」的机制,
  必须指出**那个先例的精确路径**,并写清新代码要与它同形的哪几点。
  不写它,实施期一定自己发明。
- **④ 全集不是举例,是清单。** 写"对 X 这样做"时,先枚举本批**全部**的 X。
  写不出全集 ⇒ 同族还没扫完,先扫再写。

## 4 · 每个 CP 的门控

- **可证伪失败条件** —— 点名**错误的形状**,使空实现会红。
  ⛔ 「不破坏现有行为」这类条件等于没写。
- **不变量** —— 必须同时满足什么。
- **FORBID** —— 明确不许做什么。
- **比例验证** —— 与风险相称的验证手段,不追加与风险不匹配的机制。
- **形态理由** —— 「我选了 X 而不是 Y,因为 Z」。
- **RECALL** —— 本项开工前要重开的原文。
  ⚠️ **它是阅读清单,不是合规机制** —— R5 曾点名同一份规范两次仍被违反。
  真正起作用的是 §3 和 §7,不要指望 RECALL 兜底。

## 5 · operation / path / face / 集合形态

| 业务意图 | operationId | method/path | consumer face | 集合形态 | **预期规模与增长驱动** |
|---|---|---|---|---|---|

- 每条 route **只有一个** `x-consumer-faces`。
- `platform-admin` 无 capability 模型:用 `x-required-platform-authorization`,
  生成链必须拒绝它的 `capabilityKey`。

- operationId 用能力命名;⛔ 流程/Journey/业务规则编号不得进入 runtime 或测试的目录、包、文件、类名。

> 不是 ⇒ 必须进本节。上表是常见项,按批次增减。

## 9b · 变更定位

凡指认「要改哪一处」,**用锚点不用行号**(charter §5-A):行号在前一步执行后就失效。
锚点必须在目标文件内**唯一命中**,写之前数一遍;⛔ 不要带前导空白。

## 11 · 验收场景设计

| scenario id(能力命名) | owner 文件 | identity | fixture | request | businessOracle |
|---|---|---|---|---|---|

- 每条四要素非空;businessOracle 必须点名**真实业务字段或副作用**。
  ⛔ 路径字符串、只看状态码、`response.ok`、无异常 —— 都不是业务断言。
- 场景放**正确的业务 domain 文件**;⛔ 不新增 provider 壳、共享 SPI、scenario registry、自动分母。
- **夹具必须造出超过单页/超过边界的数据量** —— 不过量的场景必然假绿。
- 红夹具单列:哪些"出现即缺陷",怎么证伪。

## 12 · 未决项处置

| 项目 | 当前状态 | 本批允许 | 本批禁止 |
|---|---|---|---|

未决项**只作为依赖存在**;⛔ 不得被固化成契约字段、DB 约束或状态枚举。

## 13 · 停机条件

必须停下来单条求裁的情形;以及**上游(含规格、评审 finding、给定数字)都是待验证输入,以源码为准**。

## 14 · 交付前自查

| 检查 | 判据 |
|---|---|
| §3 行完整 | 无删行;`N/A` 都有理由 |
| §3 ④ 列 | 每条机制都有全集清单,不是举例 |
| §7 机制行 | 凡跨层履行的机制都有行,且逐层写了具体值 |
| **详设 ↔ IA 交叉对账** | **同一事实逐字一致**;不一致即缺陷,不许留给实施期弥合 |
| 计数自证 | 文中自称的数字 = 实际条数(先跑搜索再写) |
| 证据档位 | 编译 / 静态门 / 容器 / 浏览器,⛔ 低档不得说成高档 |
