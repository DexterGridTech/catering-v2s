# implementation-facing 详设模板

- 建立:2026-08-19 · 作者:Claude
- 由 `cs-writing-plans` / `cs-spec-to-plan` 引用。派活话术见 `doc/platform/implementation-task-template.md`。
- **本模板是给作者填的表,不是给脚本判的门。** 价值全在"写详设时照着填",
  ⛔ 不得为它新建 compliance-control、分母台账或机器扫描(那一整套已退役)。
- ⚠️ **唯一例外(Dexter 2026-09-25 裁定)**:§3a 的 `L2_SCRIPT_ADMISSION` 状态与独立复核记录由 L2 运行器在启动前读取,
  缺失、未 PASS 或准入后控制面有改动即拒绝启动。运行器只核对准入是否存在且覆盖当前字节,不做语义判定;
  其余各节仍只给作者填、给评审读。

## 收录尺度(新增维度前先过这三关)

一个维度值得存在,必须满足三条之一:**这次真的坏在它上面** · **漏了不报错** ·
**实施者必然要做这个决定而本仓只有一个正确答案**。
⛔ 反过来:**漏了会编译失败的不收** —— 编译器管得比文档好,写进来只是噪音。

| 方案 | 结果 | 结论       |
| ---- | ---- | ---------- |
| A    |      | 拒绝,因为… |
| B    |      | 拒绝,因为… |

## 3a · L2 脚本开发前 UI/testId 前置复核（UI-bearing 或 L2 适用时强制）

本节必须在写或修改 L2 spec、runner adapter、locator binding、blueprint action 控件声明之前完成。若本批
没有 UI-bearing screen 或不执行 L2，填写 `NOT_APPLICABLE_WITH_REASON` 并回指业务/授权边界；不能留空。

```text
UI_DESIGN_REVIEW=NOT_APPLICABLE_WITH_REASON:<...> | OPEN | PASS
TESTID_REVIEW=NOT_APPLICABLE_WITH_REASON:<...> | OPEN | PASS
L2_SCRIPT_ADMISSION=BLOCKED | PASS
```

先重开批准需求、IA、交互工件、前端规范、当前 screen owning source，并查看同类模块与
`libraries/frontend/admin-ui-foundation` 的实际消费者。逐项确认 UI 的形态、动作、位置、文案、状态/控制、
失败/恢复、可访问性/焦点和数据来源/invalidation；然后按每个 case/action 穷举实际会被操作的控件，不能只
盘点页面上“看起来像按钮”的元素。

| case/action | 用户控件与动作                     | UI owning source | `*TestIds.ts` 常量 | 实际动作节点（含 wrapper/native 区分） | L2 binding/touch   | UI focused/static proof | fresh 独立复核      | 结论           |
| ----------- | ---------------------------------- | ---------------- | ------------------ | -------------------------------------- | ------------------ | ----------------------- | ------------------- | -------------- |
| `<...>`     | `<click/fill/select/upload/press>` | `<path#anchor>`  | `<path#symbol>`    | `<selector/DOM ownership>`             | `<binding/action>` | `<path + result>`       | `<review evidence>` | `MATCHED/OPEN` |

判定规则：每个实际操作控件必须有 app `*TestIds.ts` 唯一源、稳定业务身份和挂在真实动作节点的 testId；Modal/
Drawer 动作、动态行、分页及 native file/input 不能用外层 wrapper 代替。L2 binding 只能消费该常量源，spec
不得用 role/label/placeholder/text/index/CSS/XPath 或散写 `data-testid` 补偿缺口。任一缺失或 UI 对账 OPEN，
`L2_SCRIPT_ADMISSION` 必须保持 `BLOCKED`；先修 UI、完成 focused/static proof 和 fresh 独立复核，再允许脚本。

**L2 控制面全集(强制)**：本节还必须列出本批将新增或修改的全部 L2 控制面文件——场景、blueprint、定位绑定、
执行配置、fixture、时间预算、spec、P1 生成器——以及 case 分母。它们与 UI 源码一样是被设计、被复核的交付物。
⛔ UI-bearing 批次缺本节控件分母表或缺该清单，设计评审即 NO-GO。

**准入失效**：准入之后，上述任一文件或本批 UI 目录发生改动，`L2_SCRIPT_ADMISSION` 自动回到 `BLOCKED`，
须重新复核后再运行；L2 运行器按此拒绝启动（见 `doc/platform/browser-l2-execution-standard.md` §4.1）。

> 实证：2026-09-24 门店终端批的详设 §3a 只有一段文字、没有控件分母表，约 120 KB 的 L2 控制面在详设与计划中
> 零提及；实施时 L2 跑了 36 次只通过 1 次。

复合控件窄例外：仓内已有且组件 API 不暴露 option-level `data-*` 的复合控件（如 `Segmented`），可把 testId
挂在可见 option label/anchor；但必须在分母注明 `COMPOSITE_OPTION_ANCHOR`、同一点击语义与 focused/static
proof。该例外不适用于可直接标记的 Button、MenuItem、Checkbox、Radio、输入框或 file input，也不允许以
外层 wrapper、文本或宽 locator 替代真实动作节点。

## 4 · 每个 CP 的门控

- **可证伪失败条件** —— 点名**错误的形状**,使空实现会红。
  ⛔ 「不破坏现有行为」这类条件等于没写。
- **不变量** —— 必须同时满足什么。
- **FORBID** —— 明确不许做什么。
- **比例验证** —— 与风险相称的验证手段,不追加与风险不匹配的机制。
- **形态理由** —— 「我选了 X 而不是 Y,因为 Z」。
- **RECALL** —— 本项开工前要重开的原文。
  ⚠️ **它是阅读清单,不是合规机制** —— R5 曾点名同一份规范两次仍被违反。
  真正起作用的是 §3 和 §7,不要指望 RECALL 兜底。

## 9a · 实施前全链同步变更清单（每个业务事实必填）

本节不是影响面举例，而是每一个待变更事实的**完整同步分母**。实施前必须用搜索建立清单；实施后
必须以同一清单回读。没有本节，不得先改 owner、界面或任一主程序。

| 变更事实 | 契约 / 唯一生成源 / 生成物 | 后端 owner / edge / migration | 前端 model / surface / state | focused / 静态 / HTTP / L2 测试 | fixture / seed 唯一来源 / executor | 结论：同步修改 / 生成派生 / N/A（反例） |
| -------- | -------------------------- | ----------------------------- | ---------------------------- | ------------------------------- | ---------------------------------- | --------------------------------------- |

**判别式**：任何一格不能只写“无影响”。只有明确反例证明它不消费该事实，才可写 `N/A`；生成物只能
写“由哪条生成链派生”，不得手改。测试、fixture 与 seed 的旧断言或旧物化形状必须在同一变更内
同步退休/改写；主程序已变而它们尚未对齐，实施即未完成，不得把失败留给动态验收。

⚠️ **验证控制面也是变更事实**：L2 控制面文件、seed 执行器与父流程接线、seed 角色授权，都要各占一行，
不得只列业务主程序。

## 10b · seed 数据(**新功能与旧功能调整都必填**)

⚠️ **seed 不是 acceptance fixture。** acceptance 自带 fixture 并在真实 HTTP 里造数;
seed 是 `reset` 之后让 DEV/体验环境**有一套可用业务数据**的东西。
两者独立,填了 §11 不等于填了本节。

**为什么必填**:seed 坏了**不报错** —— 代码照编译、acceptance 照绿,
直到有人 `reset + seed` 才发现数据造不出来或语义已经错了。

> 实证:2026-08-20 R5 批的 seed 设计被查出两处缺陷(把契约态数据塞进**别的域**的 seed plan、
> 夹具缺三族);2026-08-21 单位批实施前,`catalog-inventory-seed-executor.mjs` 仍在写
> `salesUnitRefs` 数组 —— 该批一落地,seed **立刻产出非法数据**。

### 10b.1 受影响的 seed 全集(精确路径,不是举例)

| seed 文件 | 本批为什么受影响 | 处置 |
| --------- | ---------------- | ---- |

**判别式**:本批改了哪些**业务事实的形状**?每一个形状的改动都要回答
「哪个 seed 文件在造这个事实」。写不出全集,就是还没扫。
⛔ 不得把新业务的 seed 塞进**别的域**已有的 plan 文件 —— 既有形态是**每域一份 plan**。

### 10b.2 两类改动分开写

| 类型           | 必答                                                                                                      |
| -------------- | --------------------------------------------------------------------------------------------------------- |
| **新功能上线** | 新增的业务事实在 seed 里的**落点与覆盖清单**:哪些新对象、哪些状态分支、哪些边界值                         |
| **旧功能调整** | 既有 seed 中**会变成非法或语义错误**的部分,逐条列出并给处置。⚠️ 这一类最容易漏,因为旧 seed "看起来还在跑" |

### 10b.3 覆盖判据

seed 夹具必须覆盖**本批新增/改变的每一个状态分支与边界值**,不是只造一条"正常数据"。
⛔ 只造 happy path 的 seed 等于没有覆盖 —— 体验时撞到的恰恰是分支。

### 10b.4 同步项

- seed 的 **static test** 必须同批更新(它通常断言旧形状,不改就是红或假绿);
- **清库原则下不写迁移**:seed 直接按新模型重新物化,⛔ 不做兼容层、不做旧数据转换。

### 10b.5 边界

本节只**设计** seed,**不执行**。`reset`/`seed`/`start` 是独立、显式、破坏性动作,
须另获授权并走受管入口。

### 10b.6 执行前提、父流程与角色(新功能必填)

- **前提**:seed 只在 reset 后的空库上运行;任何创建冲突一律失败,并在报告里写明需先 reset。
  ⛔ 不设计「冲突后读详情比对、判断是不是重跑」一类分支(完整 seed 已声明 `resetRequiredBeforeRerun`)。
- **试运行**:reset 之前,必须在当前字节上跑通完整 seed 的试运行(`r5-complete-seed-executor.mjs` 已有 dry-run);
  试运行未通过不得执行 reset。
- **父流程**:写明新 seed 步骤在父流程中的位置,计数进入哪些 `COUNT_KEYS` / `expectedCounts`,
  以及父报告如何带出子步骤的首败原因。
- **角色与操作人**:新增页面或写权限时,写明哪些 seed 角色获得页面与写权限、seed 执行器用哪个会话写入;
  同步 `owner-command-seed-executor.mjs` 的 `GROUP_SEED_CAPABILITIES` 与 `r5-seed-plan.mjs` 的角色断言
  (先例:门店桌台与二维码)。

> 实证:2026-09-24 门店终端批的设计没有给 seed 操作人写权限;两次完整 seed 都在 reset 之后因静态计划失败,
> 父报告没有子步骤的失败原因。

## 13b · 实施节奏 · 三维对账(软约束,但不得省略)

**⛔ 不得等到全部实施完再对账,也不得用测试代替对账。**

### 三个维度(缺一维即未完成)

| 维  | 对账对象                                                                  |
| --- | ------------------------------------------------------------------------- |
| 一  | **需求文档** —— 业务目标、已裁定事项、明确不做的边界                      |
| 二  | **详设与 IA** —— 本步骤的条款、字段、owner 判定点、交互工件               |
| 三  | **项目记忆里的设计规范** —— 六维路由命中的全部条目,含通用判据与已登记陷阱 |

### 两个时点

**阶段性对账**:每个 CP / 实施步骤完成、进入下一步骤**之前**,对该步骤范围做三维对账。逐条给 `MATCHED` / `OPEN`;任一 `OPEN` 先做同根修复再复查,**不得启动下一步骤**。

**整体对账**:全部步骤完成、**进入整体测试之前**,对**全批范围**再做一次逐条三维对账。它不是阶段对账的汇总,是重新逐条走一遍 —— 阶段对账只看得见本步骤,跨步骤的偏移(同一事实在两步里被改成两个样、后一步推翻了前一步的判定、某条设计规范在合并后不再成立)只有整体对账能发现。

### 为什么两个时点都要

- **只做阶段对账**:每步都绿,合起来是错的。
- **只做整体对账**:偏移已经跨步骤累积,定位成本极高。
- **靠测试发现**:测试暴露的是**症状**,不是**偏离了哪一条**;而且它只覆盖被测到的路径。⛔ **本应在开发阶段解决的问题,不得留给测试发现。**

### 边界

三维对账**不产出整批 `GO` / `NO-GO`**,不消耗正式 `REVIEW_TARGET=IMPLEMENTATION` 对抗 review 的轮次上限,也**不替代**它。

## 13c · 逐代码与详设对账(Dexter 2026-09-06,强制交付前置门)

> 「实施计划里,要有逐代码与详设对账,对账成功后才可以交付给我和 Claude 做实施后 review。」

这是**本详设派生的实施计划必须写有**的一个显式交付步骤,并且**对账成功是交付前置门**。

| 项 | 规定 |
| --- | --- |
| 落点 | **实施计划文档里**必须有这一步,写清范围、执行者、判据、结论形态;⛔ 不是收尾备注 |
| 范围 | **逐代码**,不是抽样 |
| 对账对象 | **本详设**(代码 ↔ 详设两方对齐) |
| 结论 | 只有 `MATCHED` / `OPEN` |
| 门 | 任一 `OPEN` 未闭 ⇒ **不得交付** Dexter 与 Claude 做实施后 review,只能报「实施未就绪」;⛔ 不得声称「已交付 review」 |
| 记录 | 对账记录随交付一并给出;⚠️ **没有对账记录的实施交付,评审方直接判交付不成立,不进入内容评审** |

⚠️ **与 §13b 三维对账不是同一件事,不得互相替代**:
§13b 在**整体测试之前**,三个维度(需求 ＋ 详设/IA ＋ 项目记忆规范);
本节在**交给人评审之前**,只对 代码 ↔ 详设。前者守测试,后者守人。

逐代码对账由 fresh 独立子 agent 执行,并显式检查两类:① 零调用者的新增代码;② 详设点名却未产出的文件。
⛔ 按章节抽查不算逐代码。

### ⚠️ 本条对**详设写法**的反向要求

被逐代码对账的是**本文**。⇒ 详设里每一条都必须写成**能与代码逐条比对**的形态:

| ❌ 对不了账的写法 | ✅ 可对账的写法 |
| --- | --- |
| 「按 foundation 的既有形态处理」 | 写出精确路径或符号名,以及新代码必须与它同形的哪几点 |
| 「做好错误处理」 | 写出失败条件、typed problem、恢复路径与用户可见结果 |
| 「参考同类模块」 | 指出那个先例的精确路径与被参考的具体点 |
| 属性描述(「安全」「高效」「一致」) | 一个能做的观察,带反例 |

⚠️ 凡写不成可对账形态的条款,交付前必须改写或标 `N/A ＋ 理由` ——
⛔ 不得留给实施期弥合,那正是对账门要拦住的东西。
