## 0 · 术语

| 术语 | 本文含义 |
|---|---|
| 终端 | 门店终端管理里预先建好的一条终端规则（`store_terminal.terminal`），带永久激活码 |
| 设备 | 安装了 TER 应用的一台物理机器，由平台端口的 `deviceId` 识别 |
| 集团空间编码 | corpus G-10 的业务叫法，技术拼写 `groupWorkspaceKey` |
| 绑定 | 一台设备与一台终端之间的有效关联；一台终端同一时刻至多一个 |
| 绑定代次 | 每台终端的绑定序号，每次成功激活加一，编进终端凭证（D-15） |
| 激活 | 设备凭「集团空间编码 + 激活码」找到一台终端，并建立绑定 |
| 同一次激活操作 | 设备取得身份之前、同一次 JS 运行内、针对同一集团空间编码与激活码的全部激活请求，包括 command 失败后的再次调用、并发调用与换地址重发 |
| 取消激活 | 结束绑定，作废对应的终端凭证 |
| 终端凭证 | 激活成功时发给设备的长期密钥，设备凭它认证长连接与后续终端接口 |
| 身份 | 设备本地保存的、重连所需的信息：集团空间编码、终端 ref、门店 ref、终端凭证 |
| 关闭原因 | TDS 关闭连接、拒绝首帧，或业务后端拒绝终端接口时给出的机器可读原因，取自一个闭集 |
| 业务后端 | `apps/backend/catering-business-server` |
| TDS | `apps/backend/terminal-data-server`，本期只承载终端长连接 |
| 长连接 | 设备与 TDS 之间的一条 WebSocket 会话 |
| 心跳 | 设备发 `PING`、TDS 回 `PONG`，用于保活与测延时 |
| server-config | TER 新包 `kernel/base/server-config`，管理终端要连接的服务地址 |

## 1 · 要解决的问题与本期范围

**问题**：门店终端管理已经能在后台配置终端规则，但设备还无法成为其中一台终端，后台也无从知道哪台设备在用哪台终端、是否在线。本期打通三方：业务后端（终端与激活）、TDS（长连接）、TER（终端程序）。

**本期让这些事实被记录下来**：绑定状态可以在运营面读回（R-3.7）；连接与在线的事实本期只记录，读取与展示留到以后（R-6.2）。

**本期交付**：

1. 设备激活、设备主动取消激活、离线取消激活、后台取消激活与绑定读回（后台只做接口，不做页面）；
2. 设备与 TDS 的长连接：认证、心跳、超时、断线重连、多地址切换、踢线，以及每种关闭原因下设备的反应；
3. 终端、门店与集团空间的状态在激活与（重）建连时的校验（D-21）；
4. 最新状态存 PostgreSQL，历史存 Doris；
5. TER 新包 `terminal-data-client` 与 `server-config`；transport 补 HTTP 多地址切换、长连接的无限重连与网络恢复即重连，并让长连接按当时的有效配置建连；`platform-ports` 新增网络状态端口（只建端口，D-25）；
6. 门店终端创建后不能改设备类型（D-18）；
7. 双端联动测试脚本；TDS 与 Doris 进入 DEV 拓扑。

**本期不交付**：见 §5。

## 2 · 架构分工（已裁决）

- **业务后端负责全部 HTTP 操作**：激活、设备主动取消激活、后台取消激活、绑定读回，并记录绑定的最新值与历史（D-1）。
- **TDS 只做长连接**：认证建连、会话、心跳、超时、跨节点踢线，并记录连接、断开与延时的最新值与历史（D-1）。TDS 用 Spring WebFlux WebSocket（原始需求第 3 条）。
- **Doris 历史的写入方**：绑定类历史由业务后端写，连接类历史由 TDS 写，两边共用一个写入模块（D-1）。
- **共享存储**：两者共用一个 PostgreSQL，保持单一 Flyway history；另加 Doris 存历史（D-4、D-9）。
- **部署**：TDS 可独立部署，两者都可横向扩展。
  - 原话「terminal-data-server目前不做主从同步」有两种读法：TDS 节点之间同步，或终端主机与副机之间经 TDS 同步。本期两种都不做。
  - 双机拓扑下副机是否单独激活，本期不涉及。
- **跨节点信号**：PostgreSQL `LISTEN/NOTIFY`（D-8）。
- **状态校验的时点**（D-21）：门店、终端与集团空间的可用性，只在激活与（重）建连时校验；不据此管理已建立的连接。后续业务由业务自己判断门店状态。
- **治理**：以上改变了多处现行边界，Dexter 已裁决同意（D-4）。要落成的新 decision 和要改写的门见 R-12。

## 3 · 行为要求

### 3.1 激活（业务后端）

- **R-1.1 入口**：公开接口，不需要登录会话。路径带集团空间编码，形如 `/api/terminal/group-workspaces/{groupWorkspaceKey}/...`（D-3）。
- **R-1.2 设备提交**：路径中的集团空间编码，以及激活码（8 位数字字符串）、`deviceId`、设备形态（`laptop` 或 `mobile`）、应用版本。
  - 集团空间编码与激活码由激活 command 的调用方提供；本期没有 UI 入口（R-9.2）。server-config 只保存与集团空间无关的服务地址。
  - 设备形态取装配层输入的 `surfaceForm`，与界面渲染同源。Android 上它由原生层按屏幕最小宽度判定（`TerminalDualScreenActivityHandler.kt` 的 `classifySurfaceForm`）。
- **R-1.3 查找**：只在路径所指的集团空间内按激活码查找。激活码在集团空间内唯一（门店终端需求 R-8.4）。
- **R-1.4 拒绝条件**：每种返回可区分的原因。多种同时成立时，按下列顺序返回第一种：
  1. 集团空间已停用；
  2. 集团空间不存在，或其中没有这个激活码（两者返回同一个原因）；
  3. 门店已作废；
  4. 门店已停用，且提交激活的不是当前绑定的设备。D-19 的原文是门店停用后「不能再激活新设备」，所以同一设备再次激活（R-1.5）照常成功；
  5. 终端已作废；
  6. 终端已停用；
  7. 设备形态与终端的设备类型不一致（D-18）；
  8. 终端已绑定另一台设备（D-5）。
- **R-1.5 同一设备再次激活**：`deviceId` 与当前绑定相同，例如应用重装、本地数据丢失后。视为成功：重新签发凭证，作废旧凭证；仍在使用旧凭证的连接一并断开（R-7.2）。TER 在已有身份时不发起激活（R-9.2），所以这条只针对已经没有身份的设备。
- **R-1.6 激活可以安全重试**：同一次激活操作（§0）的多次请求之间，必须同时满足：
  - 首次成功建立的绑定仍然有效时，响应丢失后的重试总能拿到一份有效凭证；
  - 较早发出、却在较晚发出的请求成功之后才到达的请求，不得使设备已收到的凭证失效；
  - 首次成功建立的绑定已经不再有效时（例如随后被后台取消激活），重试按当时的状态应答，不得重新建立绑定；
  - 服务端不得用不含凭证的回放结果答复激活重试（§8 第 3 条）。
- **R-1.7 成功返回**：终端 ref、门店 ref、集团空间编码、终端凭证。凭证原值只出现在同一次激活操作的成功应答中。
- **R-1.8 不做防穷举**（D-13）。
- **R-1.9 并发**：以下保证在业务后端多实例部署下同样成立。
  - 两台不同设备同时激活同一终端，只能有一台成功，另一台得到「终端已绑定另一台设备」。
  - 激活与终端作废并发：作废的终端上不留下有效绑定。
  - 激活与终端停用并发：停用提交之后开始的激活一律被拒；与停用重叠的激活，要么被拒，要么成功，成功时绑定保留，此后建连被拒（R-8.1）。
- **R-1.10 一台设备可以同时持有多台终端的绑定**，例如离线取消激活后又激活了另一台终端。本期不自动释放旧绑定（§6 第 6 条）。

### 3.2 终端凭证与秘密

- **R-2.1 形态**：高熵随机值，不可由终端 ref、激活码或时间推导；带绑定代次（D-15）。
- **R-2.2 识别**（D-15）：
  - 服务端只存每台终端的当前绑定代次与该代次的凭证摘要，仍是最新值；
  - 绑定结束之后，保留该代次的凭证摘要，只用于判定；
  - 认证时读取当时的绑定状态，不得使用可能接受已作废凭证的缓存；
  - 判定规则见 R-4.7。
- **R-2.3 秘密的范围**：终端凭证与激活码都按秘密对待，依据门店终端需求 R-8.9 与 `PLATFORM-BLUEPRINT.md` 对凭证类值的口径。
  - 服务端只存凭证摘要；激活码只存在终端自身的记录里，DEV 种子的固定激活码是例外（门店终端需求 R-8.9、D-29）。
  - 凭证与激活码都不得进入日志、审计、幂等回执、Doris、诊断产物，也不得进入测试脚本的报告与错误输出。
  - 原始 `deviceId` 不得进入日志、审计、幂等回执与运营面读回；最新值与 Doris 可以保存它。
  - 设备把凭证存入 `persistSecure`。
- **R-2.4 不轮换**（D-6）。只在取消激活、终端作废或同一设备再次激活时作废。

### 3.3 取消激活与绑定读回

- **R-3.1 设备主动取消激活**（业务后端，终端凭证认证）：
  - 请求携带与首帧相同的身份字段：终端 ref、终端凭证、`deviceId`。只按 R-4.7 的第 1、2 步判定；集团空间停用、终端停用都不阻止设备主动取消激活（§10）。
  - 不使用幂等回放；重复调用按当时的状态应答。
  - 应答闭集与设备反应：
    - 成功，或「已取消激活」（包括门店已作废）：执行本地取消激活（R-9.6）；
    - 「凭证无效」：command 以失败返回，设备保留身份并报告；
    - 其他业务拒绝（例如参数错误）、网络错误、服务端错误：command 以失败返回，设备保留身份，不自动改走离线取消激活。
  - 成功后，绑定结束、凭证作废，并通知 TDS 断开（R-7.2）。
- **R-3.2 后台取消激活**（业务后端，运营后台暴露面）：
  - **权限**：门店终端页面权限，加写权限 `EDIT_STORE_TERMINAL`，按所选门店授权。依据是 D-1 原文「复用 `EDIT_STORE_TERMINAL` 与审计」，以及门店终端需求 R-9.6「覆盖本页面的全部写操作」。
  - **作用对象**：调用方指明它读回时看到的绑定代次（R-3.7）。判定顺序：
    1. 终端当前没有绑定：返回「终端未激活」；
    2. 当前绑定代次与指明的不同：以「绑定已变化」拒绝；
    3. 否则执行取消激活。
  - **幂等**：成功的请求用同一幂等键重放，返回首次结果；首次被拒的请求，重放时按当时的状态重新判定。
  - **门店状态**：门店不在启用状态时不可用，沿用门店终端的现有规则（D-17、D-21）。
  - **效果**：同 R-3.1 的成功效果。
  - **范围**：本期只做接口与验收，不做页面（原始需求第 9 条）。
- **R-3.3 终端被作废**：视同取消激活，自动结束绑定、作废凭证并踢线。
- **R-3.4 设备收到「已取消激活」**：来源可能是 TDS 的关闭原因、首帧认证拒绝，或终端接口的响应。只要它针对的是设备当前的连接或当前的身份，设备就执行一次本地取消激活（R-9.6，D-10）。
- **R-3.5 离线取消激活**：单独的显式操作（D-10「离线时终端能单方面清空」）。只执行本地取消激活，服务端绑定不变（§6 第 1 条）。
- **R-3.6 审计**：每一种绑定变化都写审计，包括激活、同一设备再次激活、设备主动取消激活、后台取消激活、作废导致的解绑。
  - 发起方只有两类：设备，或运营人员。作废导致的解绑，记为执行作废的运营人员，原因注明「终端作废」。
  - 审计不含凭证、激活码与原始 `deviceId`。
  - 依据是 D-14：「门店所有信息的变动需要审计记录，以前没做的都要加上。」
- **R-3.7 绑定读回**（运营后台暴露面，只做接口）：门店终端的读取返回绑定状态，二选一：
  - 未激活；
  - 已激活：激活时间与绑定代次。
  - 读回不含原始 `deviceId`，也不含任何由它派生的值，更不含凭证。调用方凭读回的绑定代次发起后台取消激活（R-3.2）。
  - 门店不在启用状态时不可用，沿用现有规则（D-21）。页面展示留到以后。

### 3.4 长连接（TDS）

- **R-4.1 地址**：`/tdp/{groupWorkspaceKey}/ws`（D-3）。
- **R-4.2 认证**（D-2）：
  - 连接建立后，设备的第一帧携带终端 ref、终端凭证、`deviceId` 与应用版本；
  - 不使用单独的连接令牌；凭证不得出现在 URL 中；
  - TDS 在认证时限内（本稿写法 10 秒）收不到有效首帧，就关闭连接；
  - 一个连接从被接受到收到 `SESSION_READY` 或被拒绝，总时限为 15 秒（本稿写法），超过即作废，不登记会话；
  - 客户端已经关闭的连接，TDS 不为它登记会话；
  - 每个节点限制同时处于未认证状态的连接数，上限由详设定；达到上限后，新连接被拒。
- **R-4.3 认证结果**：
  - **通过**：TDS 回 `SESSION_READY`，携带会话号、节点号、服务器时间、心跳间隔与超时时长。
  - **不通过**：按 R-4.7 的顺序，以 R-4.6 闭集中的原因关闭。
- **R-4.4 同一终端出现第二条连接**（D-23）：
  - 新连接必须能成功：服务端还没发现旧连接已断（半开连接）时，设备重连的新连接认证通过后，照常建立会话，不因「已在线」被拒；
  - 只有认证通过的会话才能取代旧会话，旧会话随即以「被新连接取代」关闭（与 MQTT 规范的 session takeover 同理）；没有新连接来取代时，旧连接由心跳超时淘汰（R-5.3）；
  - 旧会话同时满足「被取代」与「凭证已作废」时，关闭原因取「已取消激活」；
  - 认证失败的连接不影响现有会话：现有会话照常心跳，不收到任何关闭原因，最新值不变；
  - 会话的先后，与 R-6.3、R-7.2 共用同一个由数据库给出的顺序，不比较节点时钟；
  - 两个节点之间的取代属于批次 ③。
- **R-4.5 节点下线**：节点优雅下线时，先对新连接以「请改连其他节点」拒绝，再在下线窗口内（由详设定）以同一原因关闭现有连接。设备按重连节奏重连（R-10.3），并改连下一个地址；重连节奏里的随机量把设备的重连错开，避免同时涌向剩下的节点。
- **R-4.6 关闭原因与设备反应**：
  - 原因是机器可读的闭集，Java 与 TS 共用同一份定义，住址由详设定。
  - 关闭原因只对它所在的那条连接生效；那条连接已不是设备的当前连接时，忽略。首帧拒绝与终端接口的响应同理，只对发出请求时所用的身份生效。
  - 除「已取消激活」外，设备对每种原因都保留身份，并按 R-10.3 的重连节奏无限重连（D-22）。

| 原因 | 何时出现 | 设备反应 |
|---|---|---|
| 已取消激活 | R-4.7 第 2 步；凭证作废类事件（R-7.2） | 本地取消激活（R-9.6） |
| 凭证无效 | R-4.7 第 1 步 | 保留身份，按重连节奏重连，并报告；不清空 |
| 集团空间已停用 | R-4.7 第 3 步 | 保留身份，按重连节奏重连 |
| 终端已停用 | R-4.7 第 4 步 | 保留身份，按重连节奏重连 |
| 被新连接取代 | 同一终端有了更新的、认证通过的会话 | 保留身份，按重连节奏重连，并报告 |
| 请改连其他节点 | 节点下线：已建立的会话被关闭，或新连接被拒 | 按重连节奏重连，改连下一个地址；这个地址不再作为首选 |
| 认证超时、心跳超时、网络错误、服务端错误（包括数据库不可用）、未知原因 | — | 保留身份，按重连节奏重连 |

- **R-4.7 认证判定顺序**：TDS 建连与业务后端的终端接口共用这张表，按顺序取第一个成立的结果。
  1. **凭证无效**：凭证格式不合法；凭证所指的终端在路径所指的集团空间里不存在（包括 reset 之后，以及路径的集团空间与终端不符）；代次晚于当前；代次等于当前但秘密不符；代次等于当前但请求中的 `deviceId` 与绑定设备不一致。
  2. **已取消激活**：代次早于当前；代次等于当前但绑定已结束；终端已作废；门店已作废。
  3. **集团空间已停用**。
  4. **终端已停用**。
  - 门店停用不影响建连（D-19）。
  - 这张表只在建连与终端接口被调用时使用，不用来检查已建立的连接（D-21）。
  - 设备主动取消激活只用第 1、2 步（R-3.1）。

### 3.5 心跳（D-7）

- **R-5.1 参数由服务端下发**：心跳间隔默认 30 秒、超时默认 90 秒，由 TDS 配置，经 `SESSION_READY` 下发。设备按下发值执行，不用本地常量。
  - TDS 启动时校验配置：超时时长至少为间隔的 2 倍，否则拒绝启动。
  - 例外：会话建立之前的时限只能用设备本地值，包括每个地址的建立时限、等待 `SESSION_READY` 的 20 秒与重连节奏（R-10.3）。
- **R-5.2 消息**：设备每个间隔发 `PING{seq, clientTs, lastRttMs}`，TDS 回 `PONG{seq, serverTs}`，设备据此计算往返延时。
- **R-5.3 双向超时**：
  - 设备超过超时时长收不到 `PONG`，就判定断线并重连；TDS 超过超时时长收不到 `PING`，就关闭会话。
  - 判定时刻不早于超时时长，不晚于超时时长加一个心跳间隔。现有的 `createTransportHeartbeat` 按节拍检查，默认参数下最迟在第 120 秒判定。

### 3.6 最新状态与历史（原始需求第 8 条，D-9）

- **R-6.1 PostgreSQL 只存最新值**：
  - 绑定：当前绑定的设备、绑定代次、激活时间，以及结束时间与结束方式；
  - 连接：所在节点与会话、最近连接与断开时间、最近活动时间、最近往返延时。
- **R-6.2 在线本期只记录，不提供读取**：
  - 记录要让以后的读取能按「最近活动时间 + 时限」判定在线；
  - 最近活动时间取数据库时间；会话存续期间，它的更新间隔不超过心跳超时时长（§10）；
  - 不得只靠一个「已连接」标志表示在线。节点被强制终止、来不及写断开记录时，这个标志会一直留着。
- **R-6.3 最新值不被旧事件覆盖**：
  - 非当前会话的写入，以及同一会话断开之后迟到的写入，都不改变最新值；
  - 先后按 R-4.4 所说的数据库顺序判定，不比较节点时钟。
- **R-6.4 心跳不得每次写库**：最新延时与最近活动时间按节拍合并写入，节拍不超过 R-6.2 的上界。稳态心跳期间，TDS 不读业务表。
- **R-6.5 Doris 存历史**（批次 ③）：
  - 绑定类，由业务后端写：激活、同一设备再次激活、取消激活，注明发起方（设备或运营人员）与原因（主动、后台、作废、再次激活）；
  - 连接类，由 TDS 写：连接、断开（注明原因）、每次心跳的往返延时。
- **R-6.6 历史写入失败不影响主流程**（批次 ③）：
  - 不影响激活、取消激活与长连接，也不拖慢它们的响应；Doris 挂起（接受连接但不应答）时同样如此；
  - 有界重试后丢弃；重试次数与内存中待写历史的上界由详设定。
- **R-6.7 部署与重置**（批次 ③）：Doris 与 PostgreSQL 一样部署与测试（D-9），是必选组件，不可跳过。
  - DEV：与 PostgreSQL 一样常驻，reset 时一起清空；
  - 验收：与 PostgreSQL 一样随每次运行启动、随运行回收，零残留。

### 3.7 跨节点（D-8）

- **R-7.1 接入**（批次 ③）：任何 TDS 节点都能接任何终端，节点之间不同步会话。
- **R-7.2 通知**：以下事件经 `LISTEN/NOTIFY` 通知所有 TDS 节点，节点按事件类型关闭本节点上的相关会话。
  - **凭证作废类**：设备或后台取消激活、终端作废、同一设备再次激活。只关闭用该终端被作废代次及更早代次凭证认证的会话，原因为「已取消激活」；用新凭证建立的会话不受影响。
  - **新会话**（批次 ③）：某个节点为该终端新建了会话；其他节点上更早的会话以「被新连接取代」关闭。
  - 业务变更提交成功，就一定发出对应通知。
  - 门店、终端与集团空间的停用不发通知，也不关闭已建立的连接（D-21）。
- **R-7.3 通知丢失、竞态与数据库不可用**：不得为此引入定时轮询业务状态，改用以下事件触发的兜底：
  - **监听中断**：节点的监听连接中断后，在 30 秒内发现并重建（本稿写法，与心跳参数无关）；存活探测不高于每 10 秒一次。重建后，对本节点全部会话核验一次，只核验凭证代次是否已被作废；批次 ③ 加核验是否仍是该终端最新的会话。不因门店、终端、集团空间的状态关闭会话（D-21）。
  - **竞态**：凭证作废类事件与认证并发时，结果只能是两种之一：认证失败，或认证成功后随即以「已取消激活」被关闭。
  - **数据库不可用**：已建立的会话保持，心跳照常；新连接的首帧以「服务端错误」拒绝；最新值的待写内容有上界；数据库恢复后，在 30 秒内重建监听并按上面的方式核验。

### 3.8 终端、门店与集团空间状态的影响（D-21：只在激活与建连时校验）

- **R-8.1 终端停用**：
  - 不能激活；建连被拒，原因为「终端已停用」；
  - 已建立的连接不关闭（D-21）；
  - 设备保留身份，按重连节奏重连；终端重新启用后，下一次建连成功。
- **R-8.2 终端作废**：按 R-3.3 处理，凭证作废，已建立的连接以「已取消激活」关闭。
- **R-8.3 门店与集团空间状态**：
  - **门店停用**（D-19）：只阻断新设备的激活；已激活的设备照常建连、照常在线。
  - **门店作废**（D-17）：不能激活；设备下次建连时收到「已取消激活」，执行本地取消激活；已建立的连接不关闭。
  - **集团空间停用**（D-17）：不能激活；下次建连被拒，原因为「集团空间已停用」，设备保留身份、按重连节奏重连，恢复后自动连上；已建立的连接不关闭。
- **R-8.4 设备类型创建后不能修改**（D-18，批次 ①）：取代门店终端需求 R-1.4「设备类型可以修改」。
  - 无论终端是否已激活，改变设备类型的请求都不生效；如果修改契约仍带这个字段，以可区分的原因拒绝；
  - 运营后台编辑终端时，设备类型不可修改（§7）；
  - 建错了设备类型，只能作废终端、重新新建（§6 第 10 条）。

### 3.9 TER · `kernel/base/terminal-data-client`（原始需求第 5、10、11 条）

- **R-9.1 包的性质**：
  - 新建的 owner 包，按终端编码规范声明 owner、带中文 README（TR-09、TR-10），并按 2-C 登记依赖图（`apps/terminal/skeleton-graph.ts`）；
  - 本期只做 node 测试，不做 UI（原始需求第 5 条），也不把两个新包接进任何 `ui/integration` 或 `application` 包；
  - TR-16 本期不触发：不在虚拟机或真机上运行 application 包。node 测试不冒充 Expo Web 验证。以后接 UI 或上设备时按 TR-16 执行；Web 端缺设备身份、安全存储与 `appControl` 的问题见 §6 第 7 条。
- **R-9.2 command**：激活（输入集团空间编码与激活码）、取消激活、离线取消激活、建连、断连。WebSocket 与 HTTP 的事件一律转成 command（TR-11）；网络状态的变化由 transport 处理（R-10.4）。
  - 已有身份时，激活 command 拒绝，返回明确原因；要换终端，先取消激活。
  - 同一次激活操作内，激活 command 可以重试（R-1.6）。
- **R-9.3 持久化的身份**：集团空间编码、终端 ref、门店 ref、终端凭证，存入 `persistSecure`；按 TR-04 提供重启测试。
- **R-9.4 不持久化的连接状态**（原始需求第 11 条）：
  - 内容：连接状态、会话号、节点号、最近一次关闭原因，以及往返延时样本；
  - 延时样本按设备本地时间只保留最近 2 小时，断线重连不清空，JS 重启后为空。
- **R-9.5 网络注入**：HTTP 与 WebSocket 的实际连接由装配层注入 transport。node 测试注入 Node 自带的实现；foundations 不触达网络（TR-06）。
- **R-9.6 本地取消激活**（原始需求第 10 条）：
  1. 经 command → actor 请求应用重置（`requestApplicationReset`），由 state runtime 清空持久化数据；
  2. 重置成功后，再调用 `appControl.resetRuntime`，只重启 JS。
  - **server-config 保留**（D-16）：
    - 取消激活完成后，无论 `resetRuntime` 是否成功，JS 重启后读回的 server-config 都与取消激活开始时生效中的配置一致；
    - 取消激活在任何中途失败之后（包括 state 重置只删掉了部分存储），或者进程在中途终止之后，同样一致；
    - 其余 owner 的持久化全部清空。
  - 按 D-16 所选项的说明，state 的重置增加由 owner 声明的「保留范围」；只有 server-config 声明保留。发起重置的一方不指定保留什么；不得出现绕过 command → actor 的公开重置入口（TR-09 例外第 5 条）。
  - 每次取消激活恰好执行一次；开始时先叫停 transport 的重连，之后不再发起任何建连；离线取消激活同样如此。
  - state 重置失败时不调用 `resetRuntime`，以失败报告。要避免这样的循环：重启 → 再次收到「已取消激活」→ 再次重置失败。
- **R-9.7 重连策略**（D-22、D-26）：重连的机制在 transport（R-10.3、R-10.4），本包只管策略。
  - 除「已取消激活」外，任何原因下都让 transport 继续无限重连；收到「已取消激活」时，叫停重连并执行 R-9.6；
  - 把 D-22 的节奏参数交给 transport：从 10 秒起每次加 1 秒，最长 5 分钟；等待就绪的时限为 20 秒；
  - 收到 `SESSION_READY` 时，告知 transport 连接已就绪，用于重置节奏与记首选地址；
  - 业务拒绝（R-4.7 的结果）不是地址的问题，告知 transport 时与地址类失败区分开；「请改连其他节点」按地址类告知；
  - 每次建连都读取 server-config 当时的有效配置（R-10.2）。
- **R-9.8 设备身份不可用**：`deviceId` 取不到时不发起激活，返回明确原因。
- **R-9.9 重启后自动建连**：JS 启动时如果已有身份，自动建连。
- **R-9.10 首选地址**：已移到 R-10.3（transport，D-26）。
- **R-9.11 建连时限**：已移到 R-10.3（transport，D-26）。
- **R-9.12 网络状态**：已移到 R-10.4（transport，D-26）。

### 3.10 TER · transport（原始需求第 6 条）

- **R-10.1 HTTP 多地址执行器**：
  - 请求确定没有送达（连接被拒、DNS 失败）时，换下一个地址；
  - 无法确认是否送达的网络错误与等待超时，按「送达后失败」处理：调用方声明为可安全重试的请求换下一个地址，其他请求原样返回；
  - 2xx 与带业务后端错误形状（typed problem）的 4xx，算作业务应答：立即返回，不再尝试其他地址，并把该地址记为首选；
  - 5xx，以及不带业务错误形状的 4xx（例如代理返回的 404 页面），按「送达后失败」处理，且不把地址记为首选（TR-02 登记过的缺陷：坏地址被记为首选）；
  - 每个地址的等待超时取 server-config 中该地址的 `timeoutMs`；没有配置时用 §10 的缺省值；
  - 全部地址都失败时，有界地失败，并给出最后一次失败的类别；
  - 与 WebSocket 多地址能力共用同一套地址选择；
  - 本期的激活与设备主动取消激活，都声明为可安全重试的请求（R-1.6、R-3.1）。
- **R-10.2 按当时的有效配置**：每一次 HTTP 请求、每一次 WebSocket 建连尝试，都读取 server-config 当时的有效配置（D-11「transport包的每次新请求就会变化了」）。
  - 配置变化不断开已建立的长连接，也不要求使用方做任何事。
  - 首选只能是当前有效配置中、在该配置下得到过业务应答（HTTP）或 `SESSION_READY`（WebSocket）的地址。
  - 现有的 WebSocket 控制器（`createTransportWebSocketController.ts`）不满足本条，需要改：它注册时保存配置快照，而且 `replaceServers` 会先断开当前连接。
- **R-10.3 长连接保持**（D-22、D-26）：transport 的 WebSocket 能力提供以下机制。使用方只给参数、报告就绪与业务拒绝，并决定何时叫停。
  - **无限重试**：使用方没有叫停时，一直重连；
  - **重连节奏**：参数由使用方给出。首次建连（JS 启动、显式建连 command、网络恢复）立即尝试；会话断开或尝试失败之后，第 n 次重连之前等待一段时间，TDS 连接用 D-22 的参数 min(10 + (n − 1), 300) 秒；n 在使用方报告就绪后归零；
  - **随机量**：每次等待在计算值上增加 0～20% 的随机量，且不超过上限（§10），把大量设备的重连错开；
  - **重置**：使用方报告连接就绪之后，节奏回到起点；网络恢复时也回到起点（R-10.4）；
  - **一次尝试分两段**：
    - 建立阶段：每个地址以该地址的 `timeoutMs` 为上限（缺省值见 §10），超时即在同一次尝试里改试下一个地址；
    - 等待就绪：从连接在设备侧打开时起算，时限由使用方给出（TDS 为 20 秒），超时就放弃这次尝试，并关闭这条连接（R-4.2）；
  - **地址轮转**：因地址类原因（建立超时、等待就绪超时、网络错误、服务端错误、「请改连其他节点」）结束的尝试，下一次从下一个地址开始，这个地址不再作为首选；使用方报告的业务拒绝不影响地址选择；
  - **首选地址**：只能是当前有效配置中、在该配置下被使用方报告为就绪的地址。现有控制器在连接一打开就记为首选（`createTransportWebSocketController.ts` 的 `markSuccessful`），需要改；
  - **本包边界同步修改**：README 现写「本包不提供……永不放弃的业务策略」，改为「提供无限重试的机制，何时停止由使用方决定」（TR-10）；
  - 拓扑连接（topology）现有的重连配置本期不迁移。这套机制做成通用的，拓扑以后可以直接使用。
- **R-10.4 网络状态**（D-25、D-26）：
  - `kernel/base/platform-ports` 新建一个网络状态端口：读取当前是否有网络，并在变化时发出通知；默认实例声明「不可用」，与现有端口的能力声明方式一致；
  - 本期只建端口与默认实例，Android 与 Web 的真实实现不做（D-25）；
  - transport 订阅这个端口，网络变化在 transport 内部转成 command（TR-11）：网络从不可用变为可用、而连接正在等待重连时，立即尝试一次，并把节奏重置到起点；已有尝试在进行时不重复发起；
  - 端口不可用时，只按重连节奏无限重试，行为与没有这个端口时相同。

### 3.11 TER · `kernel/base/server-config`（原始需求第 7 条，D-11）

- **R-11.1 包的性质**：新建的 owner 包，拥有持久化 slice、command 与 actor。目标是以后做 admin console 时，本包零改动。
- **R-11.2 模型**：
  - 沿用 contracts 现有的 `TransportServerConfig` 与 `ResolveTransportServerConfigOptions`（环境选择、按服务覆盖），不另立地址模型；
  - 默认值由装配层提供，覆盖值优先于默认值；
  - 覆盖按服务生效，不区分环境，沿用现有模型。因此被覆盖的服务不随环境切换而变化。
- **R-11.3 持久化 slice**：
  - 内容：当前选中的环境，以及每个服务的地址覆盖；默认值本身不持久化；
  - 持久化的环境在新版本里已不存在时，回退到装配默认，并报告。
- **R-11.4 command**：切换环境；对某个服务的地址做新增、修改、删除、调整顺序；清除某个服务的覆盖；恢复全部默认。command 写出的每个地址都带显式的名称与超时，不按下标继承默认地址的属性。
- **R-11.5 selector**：生效中的完整配置、某个服务的有效地址列表、默认值、哪些服务被覆盖了。
- **R-11.6 变更通知**：配置变化后只发出 command 通知，不负责、也不强制使用方重连（D-11）。
- **R-11.7 不放进本包**：「测试某个地址能否连通」这类网络动作。
- **R-11.8 本地取消激活不清空本包的数据**（D-16）：环境选择与地址覆盖都保留（R-9.6）。给已激活设备换环境：
  - **推荐流程**：在原环境在线取消激活 → 切换环境 → 在新环境激活。不遗留绑定。
  - **兜底流程**（原环境已不可达时）：
    1. 切换环境；
    2. 下一次建连（显式断连再建连，或 JS 重启）时，新环境认不出凭证，回「凭证无效」，设备保留身份并报告；
    3. 操作者执行离线取消激活，环境选择保留；
    4. 在新环境激活。这条流程会在原环境遗留绑定（§6 第 1 条）。

## 4 · 验收判据

- 每条判据都要有正向与反向用例。「断言」指对真实行为或真实读回内容的断言，不是对存在性的断言。
- 数值以 §10 为准；每条判据注明所属批次。
- **竞态判据**：只接受确定性的交错，优先用测试持有的数据库锁或栅栏制造；不接受重复次数一类的概率判据。
- **泄漏判据**：每个被搜索的来源，先证明能搜到本次运行写入的一个已知非秘密标记，再断言秘密搜不到。
- **对照会话**：凡断言「某会话被关闭」的判据，同一节点上另有一台终端的对照会话，全程照常收到 `PONG`，不收到任何关闭；被关闭的会话要断言同一会话号与关闭原因。

### 4.1 业务后端（backend-acceptance，真实 HTTP）

- **V-B1 激活成功**（批次 ②；Doris 部分在批次 ③）：后台验收不加载 DEV 种子，所以在场景内手填激活码新建终端，再激活。
  - 返回终端 ref、门店 ref、集团空间编码与凭证；
  - 绑定已建立，库里只存凭证摘要；
  - 按 §4 的泄漏判据，用已知的凭证原值、激活码与原始 `deviceId` 搜索业务后端日志、审计与幂等回执；用凭证原值搜索 PostgreSQL（激活码只允许出现在终端自身的字段里）。批次 ③ 加搜 Doris 里的凭证与激活码。
- **V-B2 激活的拒绝**（批次 ②）：
  - R-1.4 的每种情况各发一次，断言返回的正是该情况对应的原因；
  - 两种拒绝条件同时成立时，返回顺序在前的那一种（至少一例）；
  - 每次都没有建立绑定、没有签发凭证；
  - 「已绑定另一台设备」被拒后，原设备的绑定与凭证仍然有效；
  - 门店停用时（D-19）：另一台设备来激活，得到「门店已停用」；当前绑定的设备清空身份后再次激活，成功。
- **V-B3 同一设备再次激活**（批次 ②）：没有身份的设备（例如清空了本地数据）用同一 `deviceId` 再次激活。
  - 成功，拿到新凭证；
  - 旧凭证的在线连接以「已取消激活」被断开；旧凭证再建连，得到「已取消激活」；
  - 新凭证建连成功。
- **V-B4 设备主动取消激活**（批次 ②）：
  - 成功后，绑定结束、凭证作废；再调用一次，返回「已取消激活」；该凭证之后在 TDS 得到「已取消激活」；
  - 当前代次、秘密错误的凭证：返回「凭证无效」，绑定不变，没有审计写入；
  - 当前代次、`deviceId` 与绑定设备不一致：返回「凭证无效」，绑定不变；
  - 别的终端或别的集团空间的有效凭证打到本终端路径：返回「凭证无效」，没有写入；
  - 集团空间停用、终端停用时，设备主动取消激活照常成功；
  - A 在 B 激活同一终端之后重试取消激活：返回「已取消激活」，B 的绑定不受影响。
- **V-B5 后台取消激活**（批次 ②）：
  - 有写权限的运营账号，凭读回的绑定代次调用成功，并产生审计：操作者、终端、结果都正确，不含秘密与原始 `deviceId`；
  - 没有写权限，或门店不在授权范围内：被拒，且没有写入；
  - 指明的绑定代次已不是当前代次（例如同一设备已再次激活，或已换机）：以「绑定已变化」被拒，当前绑定不受影响；
  - 终端未激活：返回「终端未激活」；
  - 成功的请求用同一幂等键重放，返回首次结果；首次被拒的请求重放时，按当时的状态重新判定；
  - 门店停用时：读回与后台取消激活都不可用，且没有写入（D-21）。
- **V-B6 作废与停用**（批次 ②）：
  - 作废已激活的终端：绑定结束；审计的发起方是执行作废的运营人员，原因为「终端作废」；在线连接以「已取消激活」被断开（V-S5）；
  - 停用终端：之后的激活被拒；已建立的连接不被关闭（D-21）；
  - 激活与作废交错（按 §4 的竞态判据）：作废的终端上从不留下有效绑定；
  - 激活与停用交错：结果要么是激活被拒，要么是激活成功、绑定保留、此后建连被拒。
- **V-B7 并发激活**（批次 ②）：两台不同设备的激活请求分别发往两个业务后端实例，按 §4 的竞态判据交错。
  - 恰好一台成功，另一台得到「终端已绑定另一台设备」；
  - 该终端始终只有一个有效绑定。
- **V-B8 集团空间隔离**（批次 ②）：
  - 激活码只存在于另一个集团空间时，返回「没有这个激活码」；
  - 两个集团空间有同一个激活码时，各自激活到各自的终端。
- **V-B9 绑定类历史**（批次 ③）：
  - 激活、同一设备再次激活、设备与后台取消激活、作废之后，Doris 能读回对应记录，发起方、原因、终端与时间都正确；
  - Doris 挂起（接受连接但不应答）期间：测试把 Doris 写入超时配成 §10 的值，激活与取消激活照常成功，响应时间都低于 §10 的阈值。
- **V-B10 审计**（批次 ②）：R-3.6 列出的每一种绑定变化各产生一条审计，发起方与原因正确，不含凭证、激活码与原始 `deviceId`。
- **V-B11 绑定读回**（批次 ②）：
  - 激活后，运营后台读取该终端，返回「已激活」，激活时间与绑定代次正确；
  - 取消激活或作废后，返回「未激活」；
  - 同一设备再次激活后，绑定代次加一，激活时间更新；
  - 读回里（包括只读账号的读回）搜不到原始 `deviceId`、任何由它派生的值，以及凭证。
- **V-B12 设备类型不可修改**（D-18；未激活部分在批次 ①，已激活部分在批次 ② 作为回归）：
  - 对未激活和已激活的终端，各提交一次改变设备类型的修改：设备类型都不变；如果修改契约仍带这个字段，以可区分的原因拒绝；终端的功能与版本都不变；
  - 反向：不改设备类型的其他修改照常成功；
  - 门店终端现有验收里「改设备类型成功」的用例，改为断言不生效。
- **V-B13 激活重试**（批次 ②，R-1.6）：
  - 响应丢失：服务端已完成激活但丢弃响应，设备重试后拿到有效凭证，能在 TDS 认证；
  - 迟到的原请求：服务端扣住第一次激活请求；设备超时后重试（同一次激活操作内的第二次 command 调用，或换地址重发）并成功。放行第一次请求之后，重试拿到的凭证仍能在 TDS 认证，绑定代次不变，没有会话被以「已取消激活」关闭；
  - 绑定已不再有效：首次成功、应答丢失后，执行后台取消激活，再重试：读回仍是「未激活」，没有签发新凭证。
- **V-B14 一台设备绑多台终端**（批次 ②，R-1.10）：同一 `deviceId` 已绑定 T1 时激活 T2，成功，T1 的绑定不变。

### 4.2 TDS（backend-acceptance，真实 WebSocket）

- **V-S1 认证与会话**（批次 ②）：
  - 有效首帧得到 `SESSION_READY`，其中的心跳参数等于 TDS 的配置值；把配置改为非默认值后重测，下发值随之改变；
  - 未认证连接数达到上限后，新连接被拒；
  - 超过 15 秒总时限还没完成的认证，不登记会话；
  - 「超时小于间隔 2 倍的配置使 TDS 拒绝启动」放在 TDS 的单元测试里验证。
- **V-S2 认证拒绝的原因**（批次 ②）：以下每种情况，都断言得到的正是 R-4.7 对应的原因。
  - 不发首帧，超过认证时限：连接被关闭；
  - 格式合法但从未签发的凭证：「凭证无效」；
  - 当前代次、秘密错误：「凭证无效」；
  - 当前代次、首帧 `deviceId` 与绑定设备不一致：「凭证无效」；
  - 路径中的集团空间与终端不符：「凭证无效」，与「从未签发」无法区分；
  - 已取消激活的凭证、终端作废、门店作废：「已取消激活」；
  - 集团空间停用：「集团空间已停用」；终端停用：「终端已停用」；
  - 组合：凭证已作废且集团空间已停用，得到「已取消激活」；凭证认不出且门店已作废，得到「凭证无效」；凭证已作废且终端已停用，得到「已取消激活」；
  - 反向（D-19）：门店停用时，已激活设备建连成功。
- **V-S3 心跳与超时**（批次 ②）：
  - `PING` 得到同一 `seq` 的 `PONG`；
  - 停止发 `PING` 后，TDS 在「超时时长」到「超时时长 + 一个间隔」之间关闭会话，之前不关闭；
  - 持续发 `PING` 超过两倍超时时长，会话一直保持。
- **V-S4 会话取代**：
  - 同一节点（批次 ②）：
    - 同一终端第二条认证通过的会话建立后，第一条以「被新连接取代」关闭；第二条仍能收到 `PONG`，最新值指向第二条；
    - 终端已有有效会话时，分别用错误秘密、已作废凭证、从未签发的凭证发首帧：全部被拒；现有会话照常收到 `PONG`，不收到任何关闭原因，最新值不变；
    - 在 TDS 前放一个转发器：把第一次尝试的首帧扣到设备等待 `SESSION_READY` 超时、放弃并关闭之后才送达，关闭按原顺序转发；设备随后用第二次尝试建立会话。第一次尝试不登记会话，第二次尝试的会话不收到「被新连接取代」。
  - 两个节点（批次 ③）：
    - 同一终端先在节点 A、后在节点 B 认证通过：A 上的会话被取代；让 B 的时钟比 A 慢，结果不变；
    - 两个节点几乎同时完成认证：最终恰好保留一条，另一条收到「被新连接取代」。
- **V-S5 踢线**：以下事件都由业务后端的真实接口触发，每种一例，按 §4 的对照会话要求断言。
  - 批次 ②：设备取消激活、后台取消激活、终端作废、同一设备再次激活。持有连接的节点在下一次心跳之前，以「已取消激活」关闭该会话；
  - 批次 ③：至少一例的连接在另一个节点上；
  - 反向（D-21）：终端停用、门店停用、门店作废、集团空间停用，都不关闭已建立的连接；随后断连再建连，得到 R-4.7 对应的结果（门店停用时建连成功）。
- **V-S6 最新状态**：
  - 批次 ②：
    - 连接、断开后，最新值随之更新；
    - 会话存续期间，最近活动时间每隔不超过 R-6.2 的上界就前进一次；断开后停止前进；
    - 会话断开之后迟到的心跳写入，不改变最新值；最近活动时间取数据库时间。
  - 批次 ③：
    - 从节点 A 换到节点 B 后，A 上旧会话迟到的断开与心跳写入，不覆盖最新值；
    - 强制终止持有连接的节点，使它来不及写断开记录；设备改连其他节点后，最新值指向新会话。
- **V-S7 连接类历史**（批次 ③）：
  - Doris 能读回连接、断开与延时记录，断开原因正确，延时与客户端测得的值一致；
  - Doris 挂起期间：测试把 Doris 写入超时配成 §10 的值，长连接与心跳不受影响，建连与心跳的响应时间低于 §10 的阈值，内存中待写的历史不超过上界。
- **V-S8 高效**（批次 ②，原始需求第 12 条）：§10 规定的连接数，心跳间隔配成 1 秒，持续 30 个间隔；再把心跳间隔减半、超时不变，持续同样时长。
  - 没有意外断线；
  - 统计窗口内业务后端不发请求；窗口前后，数据库表级统计的差值即为 TDS 的读写；
  - 稳态期间，TDS 对业务表的读取为 0；监听连接的存活探测单独计数，频率不超过 R-7.3 的上限；
  - 对最新值的写入次数大于 0；心跳频率加倍后，写入次数不随之增加；
  - WebFlux 事件循环线程上一出现阻塞调用，即判失败；阻塞检测的放行名单也属于这条判据，要随判据一起评审。
- **V-S9 节点下线**（批次 ②）：
  - 优雅下线开始后，新连接以「请改连其他节点」被拒；
  - 在下线窗口内，现有连接以同一原因关闭；
  - 对照会话在关闭之前照常收到 `PONG`。
- **V-S10 通知丢失与竞态**（批次 ②）：
  - **监听中断**：用数据库侧手段终止节点的监听连接，并确认「取消激活提交的时刻，节点没有在监听」。之后，节点在 30 秒内重建监听，并以「已取消激活」关闭该会话（断言同一会话号）；对照会话不受影响；
  - **状态不触发关闭**（D-21）：门店作废、集团空间停用、终端停用之后，令监听中断再重建：已建立的会话都不被关闭；
  - **竞态**：用栅栏卡在「凭证核验通过」到「会话登记完成」之间，让设备取消激活、后台取消激活、终端作废、同一设备再次激活各发生一次：结果只能是认证失败，或 `SESSION_READY` 之后随即以「已取消激活」被关闭；
  - **迟到的作废通知**：同一设备再次激活后，针对旧凭证的迟到通知，不关闭用新凭证建立的会话。
- **V-S11 秘密不外泄**（批次 ②；Doris 部分在批次 ③）：跑完上述场景后，按 §4 的泄漏判据，用已知的凭证原值、激活码与原始 `deviceId` 搜索 TDS 日志；批次 ③ 用凭证原值与激活码加搜 Doris。
- **V-S12 数据库不可用**（批次 ②）：让 PostgreSQL 整体不可用 30 秒。
  - 期间：已建立的会话保持，心跳照常；新连接的首帧以「服务端错误」被拒；对照会话不受影响；
  - 恢复后：30 秒内重建监听并完成核验；最新值的待写内容没有超过上界。

### 4.3 TER（node 测试，批次 ②）

- **V-T1 server-config 零改动**：
  - 以后 admin console 要做的操作包括：查看生效配置、查看默认值与覆盖状态、切换环境、增删改排序地址、清除覆盖、恢复全部默认。这些操作逐项只用 R-11.4 的 command 与 R-11.5 的 selector 完成，读回与操作一致；
  - command 写出的每个地址都带显式的名称与超时；调整顺序后，每个地址的名称与超时跟着地址走；
  - 重启后，持久化的选择与覆盖仍在（TR-04）；
  - 反向：装配默认值改变后，没有被覆盖的服务使用新默认值；持久化的环境已不存在时，回退到默认。
- **V-T2 只通知**：
  - 配置变化后发出 command 通知；没有订阅方也不报错；
  - 下一次 HTTP 请求使用新地址；
  - 已建立的长连接不断开；下一次建连尝试只使用新地址，旧地址不再被尝试。
- **V-T3 HTTP 多地址**：
  - 第一个地址拒绝连接：切到下一个，成功的地址成为下次的首选；
  - 第一个地址返回带业务错误形状的 4xx（例如「已取消激活」）：立即返回，不再尝试其他地址，设备随即执行 R-9.6；
  - 第一个地址返回不带业务错误形状的 404：可安全重试的请求切到下一个地址，这个地址不记为首选；
  - 可安全重试的请求遇到 5xx 或等待超时：切到下一个地址，这个地址不记为首选；
  - 不可安全重试的请求遇到 5xx 或等待超时：不换地址，原样返回；
  - 第一个地址无响应（黑洞）：按该地址的 `timeoutMs` 超时后切到下一个；没有配置 `timeoutMs` 时，按 §10 的缺省值；
  - 全部地址都不可达：有界地失败。
- **V-T4 激活与持久化**：
  - 激活成功后，身份存入 `persistSecure`；
  - 重启后身份仍在，并自动建连；连接状态与延时样本为空（TR-04）；
  - 已有身份时，激活 command 被拒，返回明确原因，没有发出任何请求。
- **V-T5 延时窗口**：用可控时钟在 2 小时边界两侧各取样本。边界内的保留，超出的丢弃；断线重连后，样本仍在。
- **V-T6 遵从服务端心跳规则**：服务端下发非默认的间隔与超时，客户端按下发值发 `PING`，并在 R-5.3 的容差内判定超时。
- **V-T7 重连与原因**：用可控时钟与可控随机源。重连节奏、地址轮转与首选属于 transport 的 node 测试；原因到反应的映射属于 terminal-data-client 的 node 测试。
  - 首次建连（启动、显式建连 command）立即尝试，不等待；
  - 重连节奏：断开或连续失败时等待 10、11、12……秒，每次加 1 秒，到 300 秒封顶；每次等待落在计算值的 100%～120% 之间，且不超过 300 秒；收到 `SESSION_READY` 后回到 10 秒；
  - 无限重试：连续失败 1000 次之后仍按 300 秒的节奏继续尝试；
  - R-4.6 的每种原因各一例，设备反应与表中一致；
  - 反向：除「已取消激活」外，其他原因下 state 重置与 `resetRuntime` 的调用次数都为 0；
  - 地址轮转，三例都要在「R-10.3 的时限 + 至多一次重连等待」之内经第二个地址收到 `SESSION_READY`：
    - 第一个地址是黑洞；
    - 第一个地址接受连接，但一直不回 `SESSION_READY`；
    - 首选地址返回服务端错误，第二个地址健康；
  - 「请改连其他节点」：按重连节奏重连，改连下一个地址。两个地址都在下线时，尝试间隔服从重连节奏，不形成紧循环；
  - 只有收到 `SESSION_READY` 之后，地址才被记为首选。
- **V-T8 本地取消激活**：测试运行时里除被测模块外，至少再装一个带持久化的真实 owner（例如 topology 或 display-context），并先写入非默认值。
  - 「已取消激活」有三种来源：关闭原因、首帧拒绝、取消激活接口的响应。三种各一次，加上一次显式的离线取消激活，每次都恰好执行一次，而且先清除存储、再调用 `resetRuntime`；
  - 已不是当前连接的旧连接上迟到的关闭原因，不触发重置；
  - state 重置失败时，不调用 `resetRuntime`，失败被报告，不形成循环；
  - 重置后重启：身份被清空；另装的那个 owner 回到初始值；server-config 与取消激活开始时生效中的配置一致；
  - 失败路径，三例都断言重启后的 server-config 与取消激活开始时一致：
    - `resetRuntime` 失败、JS 继续运行；
    - `persistSecure` 的删除失败、`persistKv` 的删除成功；
    - 清空之后、完成之前终止 runtime。
- **V-T9 设备身份不可用**：`deviceId` 不可用时不发起激活，并返回明确原因。
- **V-T10 换机**：已移到 V-E5。服务端一侧的断言，不能用 node 测试的假服务端证明。
- **V-T11 在线取消激活的失败**：
  - 网络不通时，在线取消激活以失败返回，身份保留，没有自动改走离线取消激活；
  - 业务后端回「凭证无效」或其他业务拒绝时，同样以失败返回，身份保留。
- **V-T12 已激活设备换环境**（D-15、D-16）：TDS 没有被覆盖。
  - 推荐流程：在环境 A 在线取消激活并重启后，server-config 仍是 A；切换到 B，在 B 激活成功；
  - 兜底流程：在 A 激活并建连后切换到 B，已建立的连接不断开；显式断连再建连，B 回「凭证无效」，设备保留身份、按重连节奏重连并报告，state 重置与 `resetRuntime` 的调用次数为 0；执行离线取消激活并重启后，server-config 仍选中 B；随后在 B 激活成功。
- **V-T13 激活重试的客户端一侧**（R-1.6）：假服务端先答复重试、再迟到答复原请求。激活 command 成功，身份是重试拿到的凭证；state 重置与 `resetRuntime` 的调用次数为 0。
- **V-T14 网络状态**（R-10.4，D-25、D-26；transport 的 node 测试）：注入一个可控的假网络状态端口。
  - 设备在等待重连（例如下一次尝试排在 200 秒后）时，端口通知网络恢复：立即尝试一次，重连节奏回到 10 秒；
  - 已有尝试在进行时收到网络恢复通知：不重复发起；
  - 网络变为不可用的通知不触发任何建连；
  - 反向：端口声明不可用时，只按重连节奏重试，与没有端口时的行为逐次一致。

- **V-E5 换机**（批次 ②）：两个 node 终端客户端 A、B。

  3. A 恢复联网：收到「已取消激活」，执行本地取消激活；
  4. B 的绑定与连接不受影响。

## 6 · 已知后果

1. **离线取消激活后，服务端绑定仍在**。其他设备来激活这台终端会被拒（D-5），要先后台取消激活才能换机；同一设备在清空身份后可以直接重新激活（R-1.5）。R-11.8 的兜底流程也会在原环境遗留绑定。
2. **不做防穷举**。激活码是 8 位数字，理论上可以被穷举（D-13 已接受）。这也取代了门店终端需求 §6.3 第 2、5 条「将来的激活设计必须自带防穷举」的要求。
3. **只读用户也能拿激活码激活未绑定的终端**。这是门店终端需求 §6.3 第 1 条预见的情况，从本期起真实成立。
4. **`deviceId` 不是秘密**。运营面读回不含原始 `deviceId`，也不含由它派生的值（R-3.7）。但能从设备本身取得原始 `deviceId` 的人（例如接触到设备），配合激活码，可以冒充那台设备再次激活，使原设备被清空。本期接受，不做防护（本稿写法，§10；这不属于 D-13 的范围）。
5. **设备身份与形态的稳定性没有在真机上验证过**（外部事实，UNVERIFIED）。
   - Android 上 `deviceId` 是 `ANDROID_ID`（`TerminalDeviceModule.kt`），恢复出厂设置或更换签名后可能改变；改变后设备会被当作另一台，要先后台取消激活才能重新激活。
   - 设备形态只在激活时校验（本稿写法，§10）。Android 的形态取自屏幕最小宽度，可能随系统显示设置变化。
6. **一台设备可能同时绑着多台终端**。离线取消激活后又激活了另一台终端时，旧终端仍被这台设备占着，只能靠后台取消激活释放（R-1.10）。
7. **Expo Web 没有设备身份、安全存储与 JS 重启能力**。Web 端口的 `deviceId`、`persistSecure` 与 `appControl` 默认都不可用（`dev-host/src/implementations/webPlatform.ts`）。以后接 UI 时，需要另定 Web 端的身份、凭证存放与取消激活方式。本期只做 node 测试，不涉及。
8. **运营后台已有操作的效果**。「作废」会让在线设备被断开、清空本地数据并重启 JS。「停用」不影响已建立的连接，设备下次建连时被拒（D-21）。本期界面与确认文案不变（§7）。
9. **本地取消激活会清空本机除 server-config 以外的全部持久化数据**（D-16）。除了身份，还包括双机配对（topology）、实例模式、显示角色、界面状态等 owner 的持久化。
10. **设备类型建错了，只能作废重建**（D-18）。新建的终端会有新的激活码（门店终端需求 §6.3 第 3 条）。
11. **状态只在激活与建连时校验**（D-21）。门店、终端与集团空间的停用或作废，都不关闭已建立的连接，一条长连接可能持续多日；后续业务由业务自己判断门店状态。门店停用期间，后台既看不到也不能处理该店的终端（现有规则），设备照常在线。
12. **DEV reset 之后，持旧身份的设备不会自动清空**（D-15）。它们得到「凭证无效」，按重连节奏一直重试，需要人工触发一次离线取消激活。本期只有测试客户端，由脚本自行清理。
13. **绑定代次的局限**（D-15）。
    - 服务端验证不了旧代次凭证里的秘密，所以伪造的低代次凭证也会得到「已取消激活」。这只影响提交者本人。
    - 数据库被克隆或回滚、代次分叉时，合法设备可能收到「已取消激活」而被清空。本期不处理。
14. **门店作废后，绑定不会被正式结束**。设备在下次建连时自行清空，但最新值、审计与 Doris 里都没有解绑记录。以后做统计时，要把已作废门店下的绑定视为已结束。
15. **在线状态本期只记录、不读回**（R-6.2）。
16. **持同一凭证的两个客户端会周期性地互相顶替**。被取代的一方按重连节奏重连（R-4.6），而节奏在成功建连后回到 10 秒，所以两个客户端大约每 10 秒互相顶替一次。这种情况只出现在复制了身份的设备上，Doris 历史里可见。
17. **长期被拒的设备会持续重试**（D-22 无限重试）。「凭证无效」「终端已停用」「集团空间已停用」下，重试间隔从 10 秒起每次加 1 秒，最长 5 分钟；连续失败约一小时后，间隔约 80 秒。每次尝试产生一次认证读库。
18. **心跳间隔要低于链路上的空闲超时**。默认 30 秒（D-7）低于 Nginx 与 AWS ALB 默认的 60 秒空闲超时，但与 Google Cloud 负载均衡的 30 秒、部分运营商 NAT 约 30 秒的空闲超时持平。部署在这类链路之后时，要经服务端配置调低间隔，例如 20～25 秒（D-7 已规定间隔可由服务端配置）。
19. **网络状态端口本期没有真实实现**（D-25）。真实设备上只有重连节奏生效，网络恢复后最多要等一个重连间隔（最长 5 分钟）才重连；Android 与 Web 实现补上之后，网络恢复即重连。

**已有页面的变化**：

## 8 · 交详设的事项

1. **owner 与模块**：
   - 绑定与凭证归业务后端一侧的 owner 模块（D-1）；在线最新值归 TDS 一侧的新模块；
   - 绑定放在 store-terminal 模块，还是单独建一个绑定模块，由详设比较。判据有两条：
     - TDS 要装配的模块集合：TDS 的运行时依赖只含身份判定所需的最少模块，启动不需要对象存储等与长连接无关的配置（本稿写法，§10）。store-terminal 现在依赖 organization、catalog、foundation、audit-model，catalog 又会带进 asset 与对象存储配置；
     - 模块的 COMMAND 依赖不成环（根 ADR 第 143 行；模块依赖登记表的成环检查）：作废时同事务结束绑定、终端读取带绑定状态，要求 store-terminal 依赖绑定 owner；激活按激活码找终端，又要求反方向的依赖；
   - TDS 通过绑定 owner 新增的窄判定 API 校验身份：输入身份，输出闭集结果和会话所需的最少事实，不返回实体（根 ADR 第 72～74、97 行）。
2. **凭证识别机制**（D-15）：绑定代次编进凭证；PostgreSQL 只存每台终端的当前代次与该代次的凭证摘要，绑定结束后保留该摘要（R-2.2）。
3. **激活重试**（R-1.6）：
   - 公开 POST 接口现行要求带幂等键并回放首次结果，而回放不能带凭证；
   - 详设须说明激活如何满足 R-1.6 的全部性质（包括「同一次激活操作」的边界），并用 V-B13、V-T13 证明。
4. **迁移与 Doris 表结构**：保持单一 Flyway history，TDS 不自带迁移；Doris 表结构放在哪里、如何管理。
5. **WebFlux**：阻塞式的数据库调用切到专门的线程池；心跳写库按节拍合并；事件循环阻塞检测的手段与放行名单。
6. **`LISTEN/NOTIFY`**：
   - 通道与消息形态；与业务变更同事务发出；
   - 监听连接的存活检测，以及重建后的核验范围（R-7.3）；
   - 数据库不可用时的行为（R-7.3）；
   - 通知队列写满时的行为：写满会让发出通知的事务提交失败（外部事实，UNVERIFIED）。
7. **关闭原因的契约住址**：Java 与 TS 共用一份闭集定义；WebSocket 关闭码与原因的编码方式。
8. **业务后端**：终端暴露面与终端凭证认证方式；契约生成、错误码与后台验收。
9. **受管运行**：
   - DEV 拓扑加入 TDS（批次 ②）与 Doris（批次 ③），runner 转发 TDS 端口；
   - 双端脚本读回 PostgreSQL 与 Doris 的方式，沿用现有的远端执行方式（例如 `scripts/dev/r5-reset.mjs`）。
10. **TER**：
    - 两个新包的 owner 声明、依赖图、不变量与中文 README；网络实现由注入提供；
    - WebSocket 控制器改为每次建连读取当时的有效配置，支持每个地址的建立时限，并在使用方报告就绪后才把地址记为首选；
    - 复用心跳 helper 时，修掉 `createTransportHeartbeat.ts` 里 `void options.sendPing(...)` 丢弃 Promise 的写法（TR-02 门②）；
    - 网络状态端口（R-10.4）：只建端口与默认实例，真实实现不做（D-25）；端口的命名与形态按 `platform-ports` 现有端口的写法；
    - transport 增加长连接保持的机制（R-10.3），并同步修改本包 README 的边界声明（TR-10）。
11. **双端联动脚本**：入口、夹具（DEV 固定激活码的使用与恢复）与报告。
12. **门店终端的改动**：
    - 批次 ①（D-18）：
      - 修改接口不再接受设备类型的变更，契约形态由详设定；
      - 修改接口的现有调用方同步改：前端 `storeTerminalCommands.ts` 的修改命令，以及 DEV 种子执行器 `scripts/dev/store-terminal-seed-executor.mjs` 的修改请求，两处现在都带着设备类型；
      - 编辑抽屉的设备类型改为只读展示；门店终端的交互工件与 IA 同步修订以保持一致，不单独交 Dexter 确认（D-24）；
      - 门店终端 L2 目前没有「改设备类型」的用例：新建用例 C01、C02 用到设备类型，编辑用例 E01 不涉及。D-18 会改动 store-terminal 前端目录，使 L2 准入失效，须按详设模板 §3a 重新准入；C01、C02 需要复核，E01 按 V-U1 补断言；
      - 门店终端现有后台验收里「改设备类型成功」的用例，改为断言不生效；门店终端需求的 V-1、V-16 已标注被 D-36 取代。
    - 批次 ②（R-3.7）：终端读取增加绑定状态。
13. **server-config 的保留**（D-16）：按 Dexter 所选项的说明，由 state 的重置增加 owner 声明的「保留范围」来实现，须修订 TR-09 的例外正文（R-12），并满足 R-9.6 的全部失败路径（V-T8）。
14. **验收 harness 与故障注入**（R-14）：详设逐项写明手段，并注明每项走验收环境侧（容器操作、代理、数据库锁、数据库侧终止连接），还是走生产代码里的测试接缝。走接缝的，按 `doc/platform/backend-coding-standard.md` 的 R-READ-10 声明它覆盖的边界。需要的手段：
    - TDS 与第二个业务后端实例的运行方式（同一 JVM 的独立上下文、独立进程或容器），以及资源回收；
    - 扣住或延迟某一次请求，或在处理完成后丢弃响应（V-B13）；
    - 在认证两个步骤之间设栅栏（V-S10）；
    - 扣住首帧、按原顺序转发关闭的转发器（V-S4）；
    - 让某个节点的时钟变慢（V-S4，批次 ③）；
    - 从数据库侧终止监听连接（V-S10）；
    - PostgreSQL 整体不可用（V-S12）；
    - Doris 挂起（V-B9、V-S7）；
    - 强制终止节点，使它来不及写断开记录（V-S6，批次 ③）；

    - 观测内存中待写内容的上界（V-S7、V-S12）；
    - 优雅下线的窗口（V-S9）；

## 10 · 本稿写法（你不反对即生效）

**终端与连接**

| 事项 | 本稿写法 | 位置 |
|---|---|---|
| 终端停用 | 不能激活；建连被拒；已建立的连接不关闭（D-21）；设备保留身份，按重连节奏重连 | R-8.1 |
| 终端作废 | 视同取消激活，已建立的连接以「已取消激活」关闭 | R-3.3 |
| 同一设备再次激活 | 成功；重新签发凭证，旧凭证作废。只针对已没有身份的设备；门店停用时照常 | R-1.4、R-1.5 |
| 已有身份时激活 | TER 本地拒绝；要换终端，先取消激活 | R-9.2 |
| 被新连接取代 | 按重连节奏重连（D-22 无限重试） | R-4.6 |
| 一台设备绑多台终端 | 允许，不自动释放。同一台设备上可能装着两个共用 `deviceId` 的 TER 应用，它们激活不同终端时，自动释放会误伤 | R-1.10 |
| 请求中的 `deviceId` 与绑定不符 | 按「凭证无效」拒绝 | R-4.7 |
| 设备形态的校验时点 | 只在激活时校验；D-18 原话没有限定时点 | R-1.4、§6 第 5 条 |
| 认证时限 | 首帧 10 秒；从接受连接到给出结果，总时限 15 秒；客户端已关闭的连接不登记会话；未认证连接数设上限，数值由详设定 | R-4.2 |
| 建连时限 | 每个地址的建立时限取该地址的 `timeoutMs`，缺省 5 秒；等待 `SESSION_READY` 20 秒，从连接在设备侧打开时起算 | R-10.3 |
| HTTP 等待超时的缺省值 | 5 秒 | R-10.1 |
| 重连随机量 | 每次等待在计算值上增加 0～20% 的随机量，且不超过 5 分钟。依据：不加随机量的退避会让大量客户端同步重试、成批冲击刚恢复的服务端（AWS Architecture Blog「Exponential Backoff And Jitter」）；只往上加，是为了保留 D-22「初始 10 秒」的下限 | R-10.3 |
| 重连节奏的重置 | 收到 `SESSION_READY` 后回到 10 秒；网络恢复时也回到起点（R-10.4） | R-10.3 |
| 节点下线后的重连 | 与其他断线相同，按重连节奏重连并改连下一个地址；不另设「立即改连」 | R-4.5、R-4.6 |
| 心跳配置 | 超时至少为间隔的 2 倍；超时判定的容差不超过一个间隔 | R-5.1、R-5.3 |
| 最近活动时间的更新间隔上界 | 不超过心跳超时时长 | R-6.2 |
| 监听中断 | 30 秒内发现并重建；存活探测不高于每 10 秒一次；与心跳参数无关 | R-7.3 |
| 节点下线 | 先拒新连接，再在下线窗口内关闭现有连接；窗口由详设定 | R-4.5 |
| 在线 | 本期只记录、不读回；最近活动时间取数据库时间 | R-6.2 |
| TDS 的运行时依赖 | 只含身份判定所需的最少模块；启动不需要对象存储等与长连接无关的配置 | §8 第 1 条 |

**取消激活、读回与审计**

| 事项 | 本稿写法 | 位置 |
|---|---|---|
| 离线取消激活 | 单独的显式操作；在线取消激活失败时不自动降级为离线 | R-3.1、R-3.5 |

### 11.5 第 3 轮之后：Dexter 追加的裁决与外部调研

**追加裁决**：D-22 重连节奏与无限重试、D-23 半开连接下新连接必须成功、D-24 批次 ① 的界面改动不单独确认、D-25 网络状态端口、D-26 两者的机制收进 transport，已落进 R-10.3、R-10.4，以及 R-4.4、R-4.5、R-4.6、R-9.7、§6、§7、§8、§10、§13 与 V-T7、V-T14、V-U1。

**外部调研**：Dexter 要求上网查「网络不稳定时，WebSocket 连接的管理怎样做到简单、高效、健壮」。以下是外部事实，均为 2026-09-26 查阅：
- 退避要加随机量，否则大量客户端会同步重试，成批冲击刚恢复的服务端；在 AWS 的模拟里，加随机量的退避总工作量最少。来源：[AWS Architecture Blog · Exponential Backoff And Jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/)。
- 同一身份的新连接取代旧连接，是 MQTT 规范里的强制要求（session takeover），用来解决服务端没发现旧连接已断的半开连接。MQTT 服务端在 1.5 倍保活间隔内收不到客户端消息，就断开连接。来源：[HiveMQ · MQTT Keep Alive and Client Take-Over](https://www.hivemq.com/blog/mqtt-essentials-part-10-alive-client-take-over/)。
- 浏览器的 WebSocket API 不向 JavaScript 暴露协议层的 ping/pong，所以通用做法是应用层心跳；生产系统通常两端都做探测。心跳间隔要低于链路上的空闲超时：Nginx 与 AWS ALB 默认 60 秒，Google Cloud 负载均衡 30 秒。来源：[websocket.org · Heartbeat](https://websocket.org/guides/heartbeat/)，[RFC 6455 §5.5.2、§5.5.3](https://www.rfc-editor.org/rfc/rfc6455)。
- 运营商级 NAT 的空闲超时可能短至约 30 秒。来源：搜索结果摘要，未逐页核对，按二手资料对待。
- 参照的客户端库：
  - Socket.IO 默认从约 1 秒起、翻倍到 5 秒封顶、带 ±50% 随机量、无限重试。来源：[Socket.IO · Client options](https://socket.io/docs/v4/client-options/)。
  - SignalR 默认按 0、2、10、30 秒重试四次后停止。来源：[Microsoft Learn · SignalR JavaScript client](https://learn.microsoft.com/en-us/aspnet/core/signalr/javascript-client)。
  - D-22 的节奏比两者都慢：对服务端更温和，但网络恢复后要多等。D-25 的网络状态监听正好补上这一点。

**据此采纳**：
- R-4.4 的新连接立即取代旧连接（与 MQTT 同理），D-23 的「超时淘汰」作为没有新连接时的兜底；
- 保持应用层心跳，两端都能发现断线（现有设计）；
- R-10.3 在 D-22 的节奏上加 0～20% 的随机量，并在成功建连后重置；
- 节点下线不再单列「立即改连」，统一按重连节奏重连并改连下一个地址；
- §6 第 18 条：心跳间隔要低于链路上的空闲超时。

**未采纳**：
- 服务端发协议层 ping：JavaScript 端看不到，应用层心跳已经覆盖两端探测；
- 会话续传与消息补发：本期没有数据同步；
- 分批关闭连接：DEV 只有一个 TDS，而重连随机量已经把重连错开；
- 重试若干次后停止（SignalR 的默认做法）：与 D-22 的无限重试相反。

**评审状态**：D-22～D-26 是 Dexter 的直接裁决，落稿没有再经独立子 agent 盲审。是否再做一轮，由 Dexter 决定。
