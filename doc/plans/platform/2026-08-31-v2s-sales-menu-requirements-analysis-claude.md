## 1. 销售菜单在业务上是什么

### 1.1 一句话

`[v6 §1]` 销售菜单管的是「**这些商品在门店哪个渠道绑定、什么时候、以什么销售视图被卖**」。
它不回答商品本体是什么、会员价多少、真实库存剩多少、终端是否已拿到菜单、订单是否成立。

### 1.2 v2s 的业务语言其实已经定死了 —— 这是本分析最重要的起点

`[仓内]` 语料库 **G-11** 是 `DEXTER_ACCEPTED` 的已裁事实,它已经把菜单说清楚了:

> 菜单是面向门店渠道绑定的 `SalesCollection`:商品显式编入**不可换绑**销售项 → 版本
>(草稿可改、发布冻结)→ 发布 → 门店渠道启用,才成为入口可售内容。
> 发布不等于 TDP ACK、POS 展示或外部同步成功;沽清/限售走独立可售控制,不改写菜单事实。
> 价格层为标准价 → 集合挂牌价 → SKU 挂牌价 → 营销权益价 → 支付实付。
> `ProductCatalog`、`CatalogCategory`、`SalesSection` 三义严格区分。

`[推论]` **这意味着本次需求分析不需要重新论证菜单是什么,只需要论证"在 v2s 当前阶段做到哪一步"。**
任何与 G-11 冲突的表述都应当先被判为分析错误,而不是新需求。

### 1.3 三类混淆的区分

`[v7 01.业务分析/03]` 该文开篇点出三类最常见混淆。在 v2s 语境下逐条给出区分判据:

**混淆一 · 「商品是什么」与「哪些商品在哪个门店/渠道/时间可卖」**

区分判据:**改这条事实,会不会改变别的门店看到的东西?**
会 → 属商品目录(商品名、SKU、选项、BOM、识别码、制作信息);
不会 → 属销售菜单(是否编入、分区、排序、挂牌价覆盖、是否可见、是否沽清)。

`[v6 不变量 3/5/6]` 三条硬边界:销售集合**只引用商品目录,不复制商品定义**;
**商品分类不等于销售分区**;**商品标准标价不等于销售挂牌价覆盖**。
`[仓内]` G-11 的「三义严格区分」是同一条。

**混淆二 · 「菜单发布成功」与「终端已拿到最新菜单」**

`[v6 §0/不变量 10]` 发布成功**只表示**销售集合版本校验通过、快照生成成功、写入本域 outbox。
TDP delivered/ACK、POS 本地读模型消费、外部平台同步成功**都是技术或外部可见性诊断,
不进入本域业务发布状态机**。

`[推论]` 这条在 v2s 尤其要紧,因为 **v2s 现在根本没有终端平面域**(见 §4.1)。
如果不把这条边界一开始就写死,第一版很容易把「发布」做成「推送」,
以后终端域建起来时会发现发布状态机里混进了投递事实,拆不出来。

**混淆三 · 不同发布路线是否都是同一种投影**

`[v6 §9.10]` 外部平台菜单维护有**三条不同路径**:内部发布到外部(`INTERNAL_TO_EXTERNAL`)、
外部导入为内部草稿(`EXTERNAL_TO_DRAFT`)、订单倒逼修复(`ORDER_DRIVEN_REPAIR`)。
`[v6 §0]` 而 POS/扫码/小程序走的是终端数据平面投影。**两者机制不同,不是同一种投影。**

`[推论]` v2s 第一版应当**只做内部发布产出快照**,三条外部路径与终端投影都不做 ——
但需求文档必须写明它们的存在,否则第一版的模型会被做成「只有一种下游」的形状。

## 2. 谁在用

`[v6 §9]` 按场景反推,用他们自己的任务说,不用领域实体名。

### 2.1 总公司 / 项目运营

- **做一套品牌参考菜单给门店抄**(§9.1)。关键期待:我改了参考菜单,**不会**自动覆盖门店已发布的菜单;
  门店抄过去之后是他自己的东西。`[仓内 G-11]` 已定:总部库是模板/候选来源,门店复制后本地独立生命周期,不强继承/自动合并。
- **按合同和经营范围给门店的销售项批量指定合同货号**(§9.15)。300 个销售项分到 12 个货号,
  新增的联名蛋糕手工补一个。期待:**只影响未来订单,不回改历史**。
- **要求门店整改**(§9.1 分流)。`[v6]` 明确这归运营治理,**不是**菜单域自动强制。

### 2.2 门店运营

- **只卖我卖的那部分**(§9.2):只卖中杯大杯不卖小杯;外卖只卖部分套餐。
- **不同入口卖不同东西**(§9.5):扫码点餐藏掉部分菜品,POS 全都有。
- **按时段卖**(§9.4):早餐午餐晚餐;没设时段的商品全天可售。
- **今天这个卖完了**(§9.7/9.8):沽清、每日限售、餐段限售;店员可确认超售。
  **退菜之后要不要恢复,得有人明确说了算** —— `[v6 不变量 26]` 不因退菜或退款事实自动恢复。
- **这条街的价格和那条街不一样**(§9.6):同一商品商圈 A 卖 18、商圈 B 卖 22。
- **合同还没生效,但我要先把菜单准备好**(§9.13):可创建、可发布测试快照、可供培训预演。

### 2.3 「为什么收银端看不到我刚发布的商品」—— 这是最高频的求助

`[v6 §9.14]` 给了七步排查链路,其中**第 2 到第 6 步归菜单域**:
商品是否进入销售集合 → 集合是否已发布 → 门店对应渠道是否有有效启用 →
当前渠道绑定与业务时间是否命中有效菜单候选 → 商品是否被下架/隐藏/沽清/限售。
(第 1 步归商品目录,第 7 步归终端。)

`[推论]` **这条链路应当直接变成第一版的一个用户可见能力**,而不是只当排查文档。
理由:它是唯一一个能把「发布 ≠ 可见」这条最反直觉的边界,用用户能懂的方式讲明白的界面。
没有它,门店会持续把菜单域当成故障源。

### 2.4 渠道消费方

`[v6 §0]` 本域只产出快照与期望状态,**不直接调用**终端、小程序、外卖平台或外部菜单 API。
消费方是终端数据平面域、经营渠道域、外部协作与防腐域 —— **v2s 目前一个都没有**(见 §4.1)。

## 3. v6 十六个主权事实在 v2s 当前阶段的取舍

### 3.1 取舍原则(先说判据,再说结论)

`[仓内]` v2s 现有 12 个 schema:catalog、workspace_iam、organization、platform_iam、
platform_asset、contract、collaboration、inventory、extension、business_channel、
platform_workspace、fulfillment_production。
**没有交易订单域、没有营销权益域、没有终端平面域、没有结算域。**

`[推论]` 由此得到一条清晰的判据:

> **一个事实如果它的唯一价值是「输出给某个下游域」,而那个下游域在 v2s 还不存在,
> 它就应当后置** —— 现在做出来没有消费方,形状只能靠猜,猜错的代价比晚做大。

但要小心这条判据的**误用**:按同样逻辑,「发布」也没有消费方(没有 POS 来读快照)。
所以判据要再收一层:

> **菜单自身要成立所必需的事实,即使暂无消费方也必须做**;
> **只为下游域服务、且下游不存在的,后置。**

### 3.2 逐条取舍

**必须做(菜单自身成立的最小闭环)**

| 事实 | 理由(基于用户任务) |
| --- | --- |
| `SalesCollection` | 没有它就没有「一份菜单」这个东西 |
| `SalesCollectionVersion` | `[仓内 G-11]` 已定草稿可改、发布冻结;没有版本就无法回答「我现在改的会不会立刻影响在卖的」 |
| `SalesSection` | §9.1 排序分区是门店编菜单的基本动作;且 `[v6 不变量 5]` 它与商品分类必须区分,不做就一定会被拿分类顶替 |
| `SalesItem` | `[仓内 G-11]` 「显式编入、不可换绑」;§9.2 的「只卖部分 SKU」也落在它上面 |
| `ListedSalePrice` | §9.6 同商品不同商圈不同价,是真实且高频的门店诉求;`[v6 决策 6]` 保留但不扩成价格引擎 |
| `SalesCollectionActivation` | `[仓内 G-11]` 「门店渠道启用才成为入口可售内容」;这是菜单与渠道之间**唯一**的连接点,不做则菜单无处落地 |
| `SalesPublication` | 发布动作本身 |
| `PublishedSalesSnapshot` | `[v6 不变量 4]` 发布版本不可直接修改,必须有冻结物 |
| `EffectiveSalesView` | `[v6 决策/不变量 24]` 发布阶段**持久化**生成,不是每次下单现场合并 |

**建议做,但可作第二批**

| 事实 | 理由与代价 |
| --- | --- |
| `SalesAvailabilityControl` | §9.7/9.8 沽清是门店**日常最高频**操作。它不依赖交易域即可成立(人工沽清是纯人工动作)。但「每日限售/餐段限售」需要已售数量,那来自交易域 —— 因此建议**只做人工上下架与沽清,不做限售计数**。`[v6 不变量 12]` 销售可用性意图不等于库存事实;`[仓内 G-12]` 不得由缺货推菜单下架 |

**后置(唯一消费方在 v2s 尚不存在)**

| 事实 | 后置理由 | 先不做,用户会遇到什么 |
| --- | --- | --- |
| `StoreSalesItemGoodsCodeAssignment` | §9.16 其价值是让**营销权益域**做项目权益前置判断,并供**结算域**上报;两域皆无 | 项目运营暂时无法批量分配货号。`[仓内]` 注意合同侧候选**已经存在**(见 §4.3),所以这是"暂缓",不是"缺基础" |
| `SalesOrderingConstraintPolicy` | §9.9 起售量/低消/开台必点,`[v6 决策 8]` 明确**最终执行归交易域** | 无交易域时这些约束无人执行,做出来是死配置 |
| `SalesEntryActionCapabilityPolicy` | §9.11 可展示/可加购/可提交三态,消费方是终端与交易 | 同上 |
| `SalesWindowPolicy` | §9.4 时段菜单是真实诉求,但 `[v6 §9.4]` 明确「让**终端**收到规则后自行解析」 | 门店无法做早午晚餐菜单。**这是后置项里用户损失最大的一条**,见 §7 待裁 |
| `SalesPresentationPolicy` | 分区与排序已由 `SalesSection` 覆盖;营养/过敏原/推荐展示属展示增强 | 菜单展示较朴素 |
| `StoreSalesEditPolicy` | `[v6 决策/§2 承接 6]` 起步期总部只是模板来源、**不强继承**,那么"总部锁死门店哪些字段"这件事在起步期没有语义 | 无损失 —— 起步期本就不该有 |

`[推论]` **取舍的净结果**:第一版是一条**编排 → 发布 → 落到门店渠道**的完整闭环,
加上人工沽清;所有"输出给下游"的策略事实一律后置。
这与 `[v6 决策 4]`「起步期不做多集合叠加合并器」的克制方向一致。

## 4. 与 v2s 现有能力的业务接缝

### 4.1 现状:菜单域在 v2s 是全新的

`[仓内]` 全库 105 张表跨 12 个 schema,用 menu、sales、publish、listed、section
检索建表语句**零命中**。**这是一块空地**,没有存量语义包袱,但也没有任何现成脚手架。

### 4.2 ⚠️ 渠道:一处会真实致错的术语错位

**这是本分析最需要被看到的一条。**

`[v6 §0/§2]` v6 把菜单的发布与生效目标落到 **`businessChannelBindingRef`**,
并说 `businessChannelRef` 仅作分类和统计冗余。

`[仓内]` 而 v2s 的实际形状是:

- `business_channel.business_channel_template`:项目级模板,持有
  `access_kind`(INTERNAL/EXTERNAL)、`operator_kind`(PROJECT/STORE)、
  `order_kind`(DINE_IN/TAKEAWAY/GROUP_BUY)、`dine_in_form`(POS/QR/KIOSK)、`provider_code`;
- `business_channel.business_channel`:带 `target_node_type`(PROJECT/STORE)+ `target_node_ref`
  + `template_ref`,**它本身就是"门店级落地"**;
- 该表另有一列 `binding_ref`,`[仓内]` 实测它是**外部协作侧的授权绑定**(可为 null,
  解绑时置 null),与 v6 说的 "BusinessChannelBinding" **不是一回事**。

`[推论]` 层级整体错开一级:

```
v6 的 BusinessChannel        ≈ v2s 的 business_channel_template
v6 的 BusinessChannelBinding ≈ v2s 的 business_channel
v2s 的 binding_ref           ≈ 外部平台授权绑定,v6 里归外部协作与防腐域
```

**为什么这条必须写在需求文档里**:任何人读了 v6 写下「菜单发布目标是 businessChannelBindingRef」,
到 v2s 里去找,最自然的动作就是伸手去拿 `business_channel.binding_ref` ——
那会把菜单绑到**外部授权**上,而不是渠道实例上。这个错误在设计阶段很难被发现,
因为两者都是 UUID、都叫 binding。

**需求层面的结论**:菜单启用的目标是 **v2s 的 `business_channel`(渠道实例)**。
建议在需求文档里就固定用户可见叫法与内部叫法的对照表,不要在后续文档里继续混用 v6 的词。

`[仓内]` 另注意 `business_channel` 的 `target_node_type` 允许 `PROJECT`,
即渠道可以落在项目级而不只是门店级。`[待证]` v6 的菜单模型默认落到门店渠道绑定,
项目级渠道要不要能挂菜单,v6 未直接回答,列入 §7 待裁。

### 4.3 合同:货号候选已经有了

`[仓内]` `contract.store_contract_item` 的形状是
`(contract_id, line_no, item_code, item_name)` —— **这正是 `[v6 §9.15]` 说的"合同域提供的货号候选"**。

`[推论]` 所以 §3.2 把货号分配列为后置,**不是因为缺基础**,而是因为它的消费方(营销权益、结算)
还不存在。基础侧已经就位,后续接入成本低。

### 4.4 商品目录:够用,且必须保持"只引用不复制"

`[仓内]` catalog 有 28 张表,已覆盖商品、SKU、分类、属性与 SKU 变体轴、组合、
点单选项(定义/组/值/物料)、图片、识别码、单位、字典。
`[仓内]` `SELLABLE` 在仓内已出现,G-11 明确它「只是用途能力,不是商品种类」。

`[推论]` 商品侧基础充分,菜单域**不需要商品目录做任何扩展**即可起步。
`[v6 不变量 3/8]` 两条必须守住:只引用不复制;**SKU 新增不自动进入已发布销售集合**。

### 4.5 库存:接缝方向已被 G-12 定死

`[仓内 G-12]` 「库存提示、沽清和库存状态只是销售库存视图;影响展示、加购或提交
**必须由销售集合域显式转为可售控制**」「**不得由有库存推可售、缺货推菜单下架**」
「退菜不自动恢复沽清」。

`[推论]` 与 `[v6 不变量 12/26]` 完全一致。**这条接缝没有分歧,可直接采用。**
第一版即使不接库存提示,也要把"库存事实 → 人工决定 → 可售控制"这个方向写死,
避免以后有人做成自动联动。

### 4.6 语义重叠需要先厘清的一处

`[推论]` `SalesSection`(销售分区)与 `catalog.catalog_category`(商品分类)在用户界面上
都会表现为"一组商品的分组",`[v6 不变量 5]` 与 `[仓内 G-11]` 都强调必须区分。
**需求文档必须给出用户可见的叫法差异与各自的用户任务**,否则门店会问
"我在商品那里已经分好类了,为什么菜单里还要再分一次"。

## 5. 边界:本能力不负责什么

`[v6 §0/§6/不变量 20–22]` 逐条:

1. **不负责商品本体** —— 商品是什么归商品目录。
2. **不负责真实库存** —— 余额、扣减、流水归库存域;本域只持有"销售可售意图"。
3. **不负责会员价、活动价、券后价** —— 只保留基础挂牌价覆盖,`[v6 决策 6]` 明确不扩成价格引擎。
4. **不负责终端投递** —— 不调用终端、小程序、外卖平台或外部菜单 API;
   `[v6 不变量 22]` 外部同步回执、TDP ACK、终端菜单可见**都不能反向改**发布快照或可售控制。
5. **不负责外部平台对象映射** —— 外部商品 ID、SKU、选项映射归外部协作与防腐域。
6. **不负责交易成立性** —— `[v6 不变量 15]` 合同未生效不阻止菜单准备,
   但阻止真实交易的是交易域结合合同资格判断。
7. **不负责权益是否适用** —— `[v6 §9.16 不变量]` 本域只提供当前货号与销售上下文,
   不判断"这个货号是否享受权益"。
8. **不做多集合叠加合并器** —— `[v6 决策 4]` 起步期明确不做。

`[推论]` 第一版还应额外声明**暂不负责**:时段解析、下单约束执行、动作能力分级、外部三路径。
这些不是永久边界,是**本期范围外**,措辞上要区分,否则以后要做时会被当成"推翻已定边界"。

## 7. Dexter 2026-08-31 已裁三项与衍生后果

三项均已裁定,不再是待裁项。下面记录裁定原文要点、我原倾向的对错,以及**必须跟着改的地方**。

### 裁定一 · 时段菜单:做

**Dexter 原话要点**:做。**一个渠道下可以有多个生效的菜单**,可以设置菜单的时段。
**如何判断如何使用,那是渠道的事情** —— 渠道拿到多个菜单自己做逻辑如何使用。

**与我原倾向的关系**:我倾向 B(只存放不解析),方向一致,但**Dexter 的表述更准**。
我把归属说成"等终端域建起来再消费",他直接指明是**渠道**的职责。
`[v6 §9.3]` 印证:「一个 `businessChannelBindingRef` 可以收到**多个当前有效菜单候选**;
终端按当前时间和最新发布/更新时间选择当前菜单」。**v6 与裁定完全一致。**

**推论 · 必须跟着改的三处**:

1. **`SalesWindowPolicy` 从"后置"升为"必须做"**(§3.2 已改)。时段是**菜单自身的属性**,
   不是下游的执行策略。
2. **"一个渠道多份生效菜单"升为一等需求**,不是可选形态。这条影响整个模型的骨架:
   渠道与菜单**不是一对一**。第一版就必须能表达"这个渠道下当前有 3 份生效菜单"。
3. **菜单域明确不解析"此刻该用哪一份"**。它只负责让每一份菜单带着自己的时段规则被发布出去。
   `[v6 不变量 24]` 「`EffectiveSalesView` 是发布阶段持久化快照,不是每次下单现场合并结果」——
   与裁定同向:菜单域产出候选集,不产出"当前唯一答案"。

⚠️ **需求文档必须写死的一句**:菜单域**不提供**「现在生效的是哪一份菜单」这个查询。
任何人要求它提供,就是把渠道的职责挪进来了。

### 裁定二 · 项目级渠道:当前不做项目级菜单

**与我原倾向的关系**:一致。

**推论**:`[仓内]` v2s 的 `business_channel.target_node_type` 允许 `PROJECT` 与 `STORE`,
但**只有 `STORE` 的渠道能挂菜单**。第一版遇到项目级渠道应当明确拒绝并给出可解释原因,
而不是静默忽略或当成空菜单。措辞上要写成「**当前不做**」而非「不支持」——
`[推论]` 项目统一小程序这类形态未来仍可能需要,不应把话说死成永久边界。

### 裁定三 · 可售状态:两个维度,都要支持(2026-08-31 修订)

**Dexter 的理解**:一个是本身菜单商品的**库存状态**,库存不够**自动**就不可售;
另一个是**手动对某个渠道的销售项做估清不可售**,是人工行为。**两个维度都应该支持。**

**我据 v6 与 v4 回源后的判断:这个理解是对的,而且它正好落在 v6 模型的两个格子上。**

#### 先看两边怎么做的

`[v6 §4.12]` `SalesAvailabilityControl` 是菜单域一等主权事实,两个维度都可表达:

```
targetType   = CATALOG_ITEM | SKU | OPTION_VALUE | SALES_ITEM | SALES_SECTION | SALES_COLLECTION
storeRef + businessChannelRef? + businessChannelBindingRef?
controlKind  = MANUAL_STATUS | SALE_LIMIT | INVENTORY_SOLD_OUT_HINT | EXTERNAL_STATUS_SYNC
status       = SELLABLE | OFF_SHELF | SOLD_OUT
```

v6 明写「同一商品在 POS、自助机、扫码、外卖账号上**可有不同可售状态**」,
且「`INVENTORY_SOLD_OUT_HINT` 是库存/交易/外部系统给本域的**提示或控制输入**,本域不解释其计算过程」。

`[v4]` `sales_availability_control`(`V013__sales_channel_menu_rebuild.sql` 第 257 行)实际做成:

```
sales_item_ref not null (FK → sales_item)   -- 只到销售项
store_id       not null                      -- 只有门店,没有渠道
control_type   in (SOLD_OUT, RESTORE, TEMP_DISABLED, LIMITED_QUANTITY)
target_availability boolean not null
control_reason text not null                 -- 强制留原因
effective_start_at / effective_end_at
status in (ACTIVE, EXPIRED, CANCELED)
index (workspace, store, sales_item, status, created_at desc)  -- 追加式日志,最新生效者胜
```

**关键观察**:`[推论]` v6 设计了渠道维度,**v4 没有实现** —— 表里只有 `store_id`。
同时 v4 把库存来源也丢了(`control_type` 四类不含库存)。
也就是说 v4 把一个二维问题压成了一维:只有"人工对销售项的控制"。

#### 方案:两个维度各自成立,不合并

**维度一 · 库存驱动(自动,商品/SKU 级,全渠道)**

- **真相在库存侧,菜单域不存副本。** 菜单项读取它,不持有它。
- 适用面由**库存对象是否存在**决定:`[仓内]` `inventory.stock_target` 是按商品/SKU 显式建立的,
  `[仓内 G-12]`「无 BOM 不阻断销售」。**没有库存对象的商品,这个维度不适用,永远不阻断。**
- `[推论]` **这正是 `[仓内 G-12]`「库存提示必须由销售集合域显式转为可售控制」要的那个"显式"** ——
  显式性体现在"这个商品被显式纳入了库存管理",而不是每次缺货都要人再点一次。
  这样既满足 G-12,又满足裁定"库存不够自动就不可售"。
- **不需要恢复动作**:它是**派生**的,不是存储的。库存回来了它自然回来。
- ⚠️ `[仓内 G-12]` 的「不得由缺货推**菜单下架**」仍然成立且不冲突:
  本维度让菜单项显示为**不可售**,**不是把它从菜单里移除**。下架与沽清是两件事,
  `[v6 §4.12]` 的 `OFF_SHELF` 与 `SOLD_OUT` 也是两个状态。

**维度二 · 人工估清(手动,销售项 + 渠道级)**

- **真相在菜单域**,因为它的目标就是销售项,而销售项是菜单域的事实。
- 粒度到 **(销售项, 渠道)**:可以只在扫码点餐估清,POS 照卖。
  `[推论]` 这一条采纳 `[v6]` 的渠道维度而**不采纳 `[v4]` 的省略** ——
  v4 省掉渠道是实现取舍,不是业务结论,而你的裁定明确要"对某个渠道的销售项"。
- **必须显式恢复**:`[v6 不变量 26]`「恢复必须来自明确动作,不因退菜或退款自动恢复」;
  `[v4]` 用独立的 `RESTORE` control_type 落地,这个形态可以直接借鉴。
- **必须留原因**:`[v4]` 的 `control_reason NOT NULL` 值得抄 —— 估清是对客不可售,
  没有原因就无法解释,也无法治理。

#### 为什么两个维度不合并成一个"可售"布尔

`[仓内]` v2s 已有裁定:「对象只存自身状态。owner 读时把每个相关维度的状态**各自作为事实返回**,
⛔ 不合并成一个值」。本处直接适用:

菜单项的读模型应当返回**两个独立事实**(库存维度、人工估清维度),
**由渠道自己组合**成对客展示 —— 这与你裁定一「如何判断如何使用,那是渠道的事情」是同一条原则。

`[推论]` 合并的坏处是具体的:门店看到"不可售"却不知道是**缺货**还是**被人估清了**,
处理动作完全不同(一个去补货,一个去找谁估的);而且一旦合并,
"库存回来了但人工估清还在"这种真实状态就表达不出来。

#### 恢复语义的不对称是这个方案的自然结果,不是特例

- 库存维度**派生**,无存储 → 无需恢复动作,库存回来即回来;
- 人工维度**存储**,是人的决定 → 必须由人显式撤销。

`[推论]` `[v4]` 之所以需要 `RESTORE` 这个 control_type,是因为它把两个维度都做成了存储控制。
**把库存维度改成派生之后,这个不对称自动消失**,模型反而更简单。

#### 对第一版范围的影响

`[推论]` 维度二(人工估清)在菜单域内自洽,**第一版可做**;
维度一(库存驱动)依赖库存侧已有的 `stock_target` 与余额,**接入成本低**,但需要确认
`[仓内 G-12]` 的库存状态(在库/低库存/缺货/负库存/未知)中哪些算"不够",见 §7.1。

### 7.1 裁定三衍生的两个开放项

**一 · 「库存不够」的判据要定死。** `[仓内 G-12]` 库存状态是「在库 / 低库存 / 缺货 / 负库存 / 未知」。
哪些算不可售?`[推论]` 我建议:**缺货**不可售;**低库存**仍可售(它是提示不是阻断);
**负库存**取决于该库存对象的负库存开关(G-12 明写负库存由库存对象显式开关决定);
**未知**不阻断(不能因为读不到就拦住卖)。这条需要确认,因为它直接决定门店会不会莫名卖不了东西。

**二 · 手动估清落在菜单域,那商品级的手动沽清还要不要?** 你最初的表述是"手动设为沽清",
放在商品侧;修订后的表述是"对某个渠道的销售项做估清",放在菜单侧。
`[推论]` 我建议**只保留销售项级的人工估清**,不再做商品级人工沽清 ——
理由是商品级的"没了"已经由库存维度表达,再加一个商品级人工开关会与库存维度语义重叠,
门店会分不清该用哪个。若确需"这个商品今天全渠道都别卖",可用批量估清其全部销售项表达。

`[待证]` P-01 至 P-05 是 Codex 会话内的 Dexter 裁决,我未亲历。若其中任一条与 Dexter 的本意不符,
上述更正需相应回退。

### D · Codex 的 v4 教训是我最大的空白,其中两条直接印证了裁定一

我在 §8 自标"v4 教训基本没提取"。Codex §8 补上了,以下几条我复核后认为**对需求判断有直接价值**:

**被验证有效**:多菜单、真实销售分区、批量从商品库加入菜单、菜单时段、发布状态,
以及「内部发布成功但终端未生效」的区分,在真实验收中具有用户价值;
**旧入口退役必须成为明确完成条件**,新旧并存会让用户无法判断哪套是真正经营入口。

**踩过的坑**(前两条尤其要紧):

1. **初期只加载第一份菜单,把多菜单和时段压成单菜单** → 用户误以为另一个菜单不存在。
   `[推论]` **这直接印证了 Dexter 裁定一**「一个渠道下可以有多个生效的菜单」——
   v4 正是在这里栽过,不是理论风险。
2. **把菜单启用的主语放在版本而不是菜单及经营入口** → 「当前哪份菜单生效」难以解释。
   `[推论]` 这是一条建模级教训:**启用的主语是(菜单, 经营入口),不是版本**。
3. 用"全部/未分区/智能视图"等虚拟节点污染真实销售分区 → 用户分不清筛选视图与经营结构。
4. 本地乐观排序未以服务端读回为准 → 页面顺序与实际发布顺序不一致。
5. 通用"成功"文案掩盖了到底完成了发布、对应还是同步。
6. **v4 的证据边界**:其发布证据**没有**证明真实终端应用、真实消息消费方或真实外部平台连接 ——
   不能把 v4 的"绿"扩大成所有路线已成立。

### E · Codex 对合同货号的定性比我强

我说货号后置是因为"消费方未到"。**Codex 找到的是一个四方来源冲突**:
`[v6 §10.17-19/§11.11-12]` 说销售侧维护;`[v6 00-领域地图 §9 Q26]` 仍以问题形式待确认;
`[v6 05-商品目录域 §9.11]` 说结算/外协在上报时解析;`[仓内 G-09]` 合同拥有货号清单但多份有效合同如何选择待裁。

`[推论]` **结论相同(后置),但理由强度不同** —— 它不只是"消费方未到",
而是**长期归属本身尚未收口**。这个定性更准,我采纳。

### F · 我认为我这份仍有而 Codex 稿未覆盖的

1. **§4.2 的渠道术语错位**:v6 的 `BusinessChannelBinding` ≈ v2s 的 `business_channel`,
   而 v2s 的 `binding_ref` 是外部授权绑定。Codex 稿未见此条。
   `[推论]` 这条若不写进合并稿,设计阶段极易把菜单绑到外部授权上。
2. **两个可售维度不合并成一个布尔**,理由是 v2s 已裁的「维度不合并」。
   Codex 的 P-03 只谈做不做,未谈两维度如何返回。
3. **恢复语义的不对称是派生 vs 存储的自然结果**,不是特例。

## 8. 我最不确定、最可能被推翻的判断

诚实列出,便于合并时优先对撞:

1. **§4.2 的术语错位判断**。我据 `business_channel` 建表与 owner 源码得出"层级错开一级",
