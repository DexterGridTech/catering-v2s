Latest user steering adds WebSocket compression. The supported path is RFC 7692 permessage-deflate only. TDS uses Spring Boot 4.1.0 with a TDS-only Reactor dependency override to Reactor BOM 2025.0.7: the selected graph resolves Reactor Netty HTTP 1.3.7, Reactor Core 3.8.7 and Netty 4.2.18.Final. The BOM manages Reactor Pool 1.2.7, but the current TDS runtime and test graphs do not select it, and no TDS source imports its API. Netty 4.2.18 is the patched release for the WebSocket extension handler's unauthenticated pipelined-request queue issue; see the official [Netty GHSA-2g37-3h88-55hc advisory](https://github.com/netty/netty/security/advisories/GHSA-2g37-3h88-55hc). This patch-level override is confined to the TDS runtime; business application/test classpaths stay on the Boot-managed graph. The managed TDS dependency report must prove the exact selected versions. Follow the versioned [Reactor Netty 1.3.7 WebSocket builder API](https://projectreactor.io/docs/netty/1.3.7/api/reactor/netty/http/server/WebsocketServerSpec.Builder.html) and the [Netty 4.2 permessage-deflate handshaker API](https://netty.io/4.2/api/io/netty/handler/codec/http/websocketx/extensions/compression/PerMessageDeflateServerExtensionHandshaker.html); exact-release source archives are listed in the TDS usage audit when the documentation page is a moving patch alias.

Use `ReactorNettyRequestUpgradeStrategy` with its public `WebsocketServerSpec.Builder` supplier, `compress(false)` and `maxFramePayloadLength(65_536)`. TDS handles extension negotiation below the frame codec with the Netty 4.2.18 `WebSocketServerExtensionHandler` and the `PerMessageDeflateServerExtensionHandshaker`; decoded-message size is enforced during inflation by `TdsBoundedPmdDecoder`, followed by `WebSocketFrameAggregator(65_536)`. The implementation currently limits negotiation to permessage-deflate, but the contract leaves malformed/duplicate offers and deflate-frame behavior to the WebSocket implementation. Both oversize paths close with code 1009 before ReactiveBridge, application parsing, credential lookup, actor/session registration or persistence; the shared contract does not prescribe the close reason. Exact dependency versions and official API sources are recorded in the TDS third-party usage audit. The named `TdsPmdMessageFilterProvider` bounds per-connection encoder state; its threshold is implementation detail, not a protocol assertion.

RFC 7692 opcode control frames (PING, PONG, CLOSE) are distinct from the protocol's JSON message types named PING/PONG, which are data messages. The local encoder leaves opcode control frames uncompressed and the local decoder accepts negotiated compressed client data messages. These implementation choices do not add wire-level RSV or small-message threshold assertions to V-S14. The server currently requests no-context takeover in both directions to keep compression state within the 1 MiB per-connection logical reservation; the shared protocol permits the design to choose whether to retain context.

The per-connection logical buffer/state reservation is at most 1,048,576 bytes. Its known bounded subtotal is 644,100 bytes: 65,540 bytes for the compressed-input array (65,536-byte frame plus the RFC sync-flush tail), 8,192 bytes for the inflater output scratch array, and four 65,536-byte allowances for the wire frame, decoded frame/output, complete-message aggregation and outbound message. The official [zlib memory formula](https://zlib.net/zlib_tech.html) at windowBits=15/memLevel=8 adds 268,288 bytes for deflate state and 39,936 bytes for inflate state. This leaves 404,476 bytes under the 1 MiB logical ceiling for bounded per-channel protocol/codec objects; the focused proof must measure those allocations and fail if the ceiling is exceeded. The zlib state values are sizing estimates rather than a claim about exact native allocation by the JDK. Netty allocator arenas, JVM baseline, TLS, socket and kernel memory are outside this logical per-connection bound and must be measured separately for deployment capacity. No second retained inbound or outbound message is allowed per connection. Focused V-S14 uses an unpooled allocator and allocation counters to prove retained ByteBufs, arrays, and zlib state remain within the stated accounting, both directions use no-context state, exact-boundary input succeeds, and oversized decompression/aggregation closes before application side effects. N is selected only after the managed deployment's measured excluded overhead and declared host capacity are recorded; the test cohort never determines N.

The mandatory application environment keys `V2S_TDS_MAX_UNAUTHENTICATED_CONNECTIONS` and `V2S_TDS_MAX_TRACKED_SESSIONS` are independent required decimal integers in the inclusive range 1..2,147,483,647. Missing, malformed, zero, negative, or out-of-range values fail TDS startup before readiness. DEV and backend-acceptance values come from the single checked-in `scripts/env/tds-dev-capacity.json`; the launchers read the file and inject both application keys. Under Dexter's delegation, the main agent selected an initial modest DEV budget of 512 MiB RSS, with 4 unauthenticated connections and 8 tracked sessions. The 12 configured slots reserve 12 MiB of the 1 MiB-per-connection logical budget. The managed DEV runner samples `/proc/<pid>/status` during TDS readiness and fails closed above the budget; `TdsAcceptanceProcess` records RSS at readiness and before shutdown and fails if either exceeds it. These selected values are limited to low-load DEV and are not a production capacity claim. Before selecting values for any other deployment, record its measured process baseline/increment, file-descriptor and ingress limits, then cap connection counts by the minimum of those measurements and the RSS formula. `terminal-data-server/README.md` documents the file and edit/restart procedure.

`TdsWebSocketConnection` maps application reasons through `applicationClose` and standard close codes through `standardClose`; an oversized frame or decoded message closes with code 1009, with no shared reason-string requirement. `latest_state.close_reason` persists only the exact 12 application reasons; standard close reasons are not persisted as application outcomes. `TdsConnectionCloseReasonContractTest` compares the SQL migration's check-constraint values to that application reason set.

`SessionRegistrationGate` remains the only production timing seam. Its production binding returns immediately; only the managed backend-acceptance TDS process may select the run-scoped Unix-domain control-socket gate described in §10.5. That gate delays the real post-verification/pre-actor-registration continuation and does not replace test classes, query, persistence, notification, actor or WebSocket behavior. Admission is acquired before actor/auth work and held through `SESSION_READY` or reject/timeout/client-close; actor exists before auth query and is removed only with no pending/active sessions; recovery reconciles active and pending credentials before readiness. Use four bounded workers: tds-db-worker, tds-log-worker, tds-identity-worker, and tds-codec-worker with thread ownership and queue capacity derived from deployment capacity; do not collapse them into one pool or use fixed 8/50 constants. Reactor 3.8.7 sets `queuedTaskCap` per backing thread, so U=`maxUnauthenticatedConnections` and C=`max(1,min(U,availableProcessors))` yield theoretical queued-task maxima DB `(U+2)^2`, identity `U^2`, codec `C^2`, and log `C×1024`; at DEV U=4 these are 36, 16, at most 16 and at most 4,096. Batch 2 proves the injected Node client's negotiation and decompression; Android and Expo Web compression are checked when those runtimes are wired into the app.

The full TDS third-party API-use inventory, official source links, exact resolved runtime/test versions, corrections and source-to-proof map are recorded in [`2026-09-28-v2s-terminal-activation-tds-third-party-usage-audit-codex.md`](../../review/platform/2026-09-28-v2s-terminal-activation-tds-third-party-usage-audit-codex.md). ## 1 · Business goal and solution choice

### 1.1 Structural problem

The configured terminal is only a rule today. No durable owner binds a physical device to that rule, no service authenticates the device's long-lived credential, and no live connection state can be driven by the binding owner. Adding the flow inside `store-terminal` would make the new TDS depend on the existing catalog/asset-rich module. Adding it as a second service boundary would split one binding command across PostgreSQL and a new HTTP dependency, losing the required atomic binding/audit/revocation behavior.

### 1.2 Compared options

| Option                                                                                                                                                       | Result                                                                                                                                                                                                   | Decision                                                                                                             |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| A. Put binding tables, credential verification and connection state in `store-terminal`                                                                      | Least new source, but TDS must consume an owner module with catalog/asset dependencies and broad terminal command API; TDS runtime becomes coupled to store-terminal's configuration and package surface | Reject: fails the R-4.2 minimum-TDS-runtime criterion and confuses connection ownership with terminal-rule ownership |
| B. Add a separate binding owner module; business edge orchestrates its commands with `store-terminal`; TDS uses the binding module's narrow verification API | One owner for binding facts, one PostgreSQL transaction for terminal validation/binding/audit/notification, and a small TDS business dependency; command graph remains a DAG                             | **Adopt**                                                                                                            |
| C. Make activation/TDS a third service or let TDS call business HTTP for identity                                                                            | New network and retry boundary during authentication; cannot atomically commit credential validation/session registration with binding revocation in PostgreSQL                                          | Reject: adds a deployable/API dependency while weakening the race guarantee                                          |

I choose B rather than A/C because it satisfies both delegated criteria with the fewest new runtime dependencies and preserves one transaction for each binding change. The separate owner is justified by the real TDS consumer boundary, not by a future microservice plan.

terminal-binding may directly depend on audit-model, execution-context, foundation, JDBC and JSON libraries needed for its owner. It must not depend on organization, extension, platform-admin-iam, catalog, asset, or store-terminal. The administrative edge performs requireStore authorization and passes typed actor/scope values; terminal-binding re-reads required facts through its own task-scoped SELECT in the transaction. The public TDS API exposes the owner-owned ActivationCandidate and credential verification only; it does not export organization types or the implementation module. TDS runtimeClasspath contains only terminal-binding API and explicitly allowed API dependencies; it excludes the business app, store-terminal, organization, extension, platform-admin-iam, catalog, asset, Flyway, seed and object-storage artifacts. A TDS-local ArchUnit rule checks this closure. Business ArchUnit imports only business production outputs, not TDS. Add ..app.edge.terminal.. to the peer-edge independence rule.

The shared resource requires close code `1009` when a frame or complete decoded message exceeds 65,536 bytes; it does not prescribe a reason string. Other protocol violations are handled by the WebSocket implementation, with no contractually fixed code or reason. D-42 requires these inputs to reach no authentication, registration or write, while the message and per-connection memory bounds remain enforced. `NETWORK_ERROR` is client-classified and is never emitted by TDS; `UNKNOWN` is the fallback for invalid application JSON, including a known message with invalid fields. A negotiated compressed first AUTHENTICATE frame is decompressed before JSON validation. The remaining application values map one-to-one to R-4.6; `ACTIVATION_CANCELLED` also covers terminal/store voiding and R-4.7 step 2, while `NODE_BUSY` is the configured admission-cap result. `clientTs`, `serverTs` and `serverTime` are descriptive RFC3339 UTC values only; TER measures RTT with a local monotonic clock and matching `seq`, never by subtracting clocks across devices. The resource gives Java the enum and schemas directly; the TER batch generates TypeScript types and the close-reason mapping from it. Neither side maintains a second hand-written enum.

Compression is transport framing, not an application frame or a second JSON encoding. TDS negotiates RFC 7692 `permessage-deflate` when offered by the client; no offer means no compression. The implementation uses Netty 4.2.18's `WebSocketServerExtensionHandler` with `PerMessageDeflateServerExtensionHandshaker`, a local `TdsPmdMessageFilterProvider`, and `TdsBoundedPmdDecoder`. The decoder bounds output during inflation, tracks the aggregate decoded bytes across fragments, and rejects the first byte beyond 65,536 before the frame aggregator or application codec. `WebSocketFrameAggregator(65_536)` also bounds uncompressed messages and legal decoded fragments. The server currently requests no-context-takeover in both directions to keep compression state bounded; this is an implementation choice for the 1 MiB per-connection logical reservation below, not a shared-protocol requirement. The client-visible acceptance checks only the two real offer shapes, no offer, negotiated/fallback data exchange, the exact size limit and the three over-limit paths. It does not prescribe handling or close text for malformed/duplicate offers, deflate-frame, reserved bits, or small-message thresholds. Those inputs remain under library handling; they must not reach authentication, session registration or writes, and must remain within the same decoded-message and memory bounds. The shared resource fixes 1009 for an oversized message without fixing its reason text. Batch 2 proves only the injected Node client negotiation/decompression under R-10.5; Android and Expo Web are checked when wired into the app.

The baseline Boot 4.1.0 managed Reactor Netty 1.3.6 / Netty 4.2.15 lacks the required aggregate bound during inflation. The selected stack is Reactor Netty 1.3.7 with Netty BOM 4.2.18: Netty's documented `maxAllocation` bounds an individual decompression buffer, while its standard `DeflateDecoder` can collect multiple output buffers before the application frame aggregator sees them. The implementation therefore uses `TdsBoundedPmdDecoder` with JDK 21 `Inflater(true)` and an 8 KiB scratch array; it tracks aggregate output across fragments and rejects the first byte beyond 65,536 during inflation. `WebSocketFrameAggregator(65_536)` also caps plain messages and aggregates decoded fragments. Both paths close with status 1009 before application handling; the shared contract does not prescribe a reason. Focused tests prove bounded output allocation, and the nine real-wire V-S14 cases prove offer/no-offer behavior, negotiated/fallback sessions, exact-boundary acceptance and raw/single-compressed/fragmented-compressed overflow. Protocol-edge frame and offer handling remains with the implementation and is not an acceptance tuple.

With 15-bit windows and the selected no-context-takeover behavior, the known per-connection allocation subtotal is 644,100 bytes (about 629 KiB): 65,540 bytes for a compressed-input array holding one 65,536-byte frame plus the four-byte RFC sync-flush tail; 8,192 bytes for the inflater scratch array; four 65,536-byte bounds for wire frame, decoded output frame, complete-message aggregation and outbound message; 268,288 bytes estimated deflate state and 39,936 bytes estimated inflate state per the official zlib formula. The hard logical allocation ceiling is 1 MiB per connection, leaving 404,476 bytes (about 395 KiB) for the explicitly measured bounded per-channel protocol/codec objects. JDK zlib native-state figures are sizing estimates, not exact RSS claims. JVM-wide allocator arenas, TLS, socket and kernel buffers are outside this logical ceiling and must be measured per host before selecting N. The deployment admission limit must be derived from host capacity including those excluded costs and cannot be inferred from the V-S cohort. Focused tests prove bounded inflation allocation and both compressed overflows; the managed V-S14 wire set is exactly nine cases: the two real offers, no offer, negotiated and fallback sessions, exact boundary, raw overflow, compressed single-frame overflow and compressed fragmented overflow. Both compressed overflows remain red against a frame-only cap. Oversized messages are rejected before parser/auth/actor/database effects with code 1009. Batch 2 proves only the injected Node client negotiation/decompression under R-10.5; Android and Expo Web are checked when wired into the app.

5. `terminal_connection.latest_state`, owned by the TDS-local `terminal-connection` module, with terminal ref, node/session, database connected/disconnected/last-activity timestamps, last RTT, ordered session sequence and close reason. One PK row per terminal, composite FK to the terminal identity, no history table or online boolean. The business module registry does not register this TDS-local owner as a business module.
6. `terminal_binding.command_receipt`, owned by the binding module, for successful operations-admin cancellation only. Its key is workspace + group workspace + idempotency key; the canonical request hash includes the operation and terminal target. Store only a successful typed result, never a rejection or credential/device secret. A same-key/same-request success replays that result; a hash mismatch returns the existing idempotency conflict; rejected requests write no receipt and are re-evaluated against current state.

Use PostgreSQL transaction time/database time for activated and heartbeat fields. Use one monotone database sequence to order sessions; nodes never compare their wall clocks. No backfill is required: there is no pre-existing binding source, and the terminal table's activation code remains untouched.

### 10.2 TDS write policy

Each active session holds at most one pending heartbeat value. At each T=15 seconds, write the newest RTT/activity value for dirty sessions in one batch; every heartbeat UPDATE includes `disconnected_at IS NULL` and matching terminal/session identity. When the database is unavailable, overwrite the pending heartbeat value for the same terminal instead of queuing an event. A disconnect supersedes any pending heartbeat and enters a bounded, non-droppable disconnect set; the independent `V2S_TDS_MAX_TRACKED_SESSIONS` permit remains held across the active session and until its close write is persisted, so active sessions plus pending disconnects cannot exceed the configured limit. Acquire this permit after successful credential verification and before `repository.open`. If capacity is exhausted, close only the candidate with `NODE_BUSY`, do not open or write its session state, and leave any existing active session untouched. Replacing a session temporarily requires capacity for both the new active session and the old disconnect awaiting persistence. After recovery, flush disconnects before heartbeats and release a permit only after persistence. No business-table read occurs in the steady heartbeat path. Listener health checks are separate from the notification wait and never read business tables.

`T=15s` satisfies default timeout 90 seconds, is independent of heartbeat interval, and obeys startup checks: heartbeat interval >=1s, timeout >=2×heartbeat, T<=timeout. V-S8 runs with 2s then 1s heartbeat and unchanged timeout; each snapshot interval D covers at least 2T after metric refresh settling. The run uses scenario cohort `N`; connection and pending-write capacities derive from approved deployment capacity, not test size. The oracle is writes in D <= `N × (ceil(D/T)+2)`, pending heartbeats <= N, pending disconnects <= the configured tracked-session limit and admitted tracked sessions, each session's activity advances, zero SELECTs against `platform_workspace`, `organization.store`, `store_terminal.terminal`, and `terminal_binding.latest_binding`, and no lost disconnect. V-S8 separately saturates both configured admission limits, proves a tracked-cap rejection neither writes state nor disturbs the existing session, and proves pending disconnect permits remain unavailable on write failure and release only after a successful retry. `terminal_connection` state writes and listener health checks are reported separately. Binding/status reads during connection authentication are outside the steady-heartbeat measurement interval. V-S8 also asserts the configured admission caps are respected and BlockHound detects a deliberate event-loop `Thread.sleep`; production logging, ID generation and potentially blocking serialization execute on bounded worker schedulers, while event loops only frame messages and enqueue nonblocking actor work. Any BlockHound allowance must name an exact method and pinned version, explain why it blocks, and retain a red mutation proving the event-loop detector remains active.

### 10.3 PostgreSQL notification and recovery

TDS starts one dedicated PostgreSQL listener connection on a named bounded blocking worker, executes `LISTEN terminal_binding_events`, commits that LISTEN, then marks its listener ready. The channel payload is versioned JSON `{v:1, terminalRef, revokedGeneration}` and is UTF-8 under PostgreSQL's notification payload limit; no credential, digest or device id appears. Binding owner calls `pg_notify` only inside the same transaction as a committed binding change. TDS closes local sessions whose credential generation is at or below the revoked generation; it does not close for store/group/terminal status-only notifications because those events are not sent. The dedicated worker uses Spring Boot 4.1.0-managed pgjdbc 42.7.11 and calls `PGConnection.getNotifications(1000)`; this resolved binary exposes the required overload. It drains a notification within 1 second, with a commit-to-close target of 5 seconds while PostgreSQL and TDS are healthy. Full reconnect and state reconciliation remain bounded by 30 seconds.

The listener waits/drains with `getNotifications(1000)` and issues `SELECT 1` no more than once per 10 seconds on the same dedicated connection. Mandatory bounds are Hikari `connectionTimeout=2s`, JDBC `connectTimeout=2s`, `socketTimeout=5s`, and credential-query `statement_timeout=4s`; they apply to listener and request workers. A pool/connect/read/query failure maps to `SERVER_ERROR`, registers no new session, and marks the listener unhealthy where applicable; listener recovery uses bounded 1/2/4/5 second backoff. A silent half-open connection is detected within 15 seconds; notification delivery is not implemented as polling. After a successful re-LISTEN it performs one set-based query for every local active session and pending authentication attempt, comparing only current binding active/generation state; it does not query workspace/store/terminal status. Invalidity closes only when R-4.7 step 2 establishes a revoked generation; a missing binding, a generation greater than the database generation, query error, or database identity/reset mismatch does not close a session. Invalid pending attempts are rejected before registration only when that same condition is established. Listener notifications, reconciliation results and authentication completions are serialized by the per-terminal actor, so a notification emitted during the re-LISTEN query cannot be overwritten by stale reconciliation. Recovery-to-reconciliation must finish within 30 seconds. Database outage does not close existing WS or stop PING/PONG. A pool/connect/read/query failure during first-frame auth maps to `SERVER_ERROR`; `AUTHENTICATION_TIMEOUT` is reserved for a healthy path reaching the 10s first-frame/auth deadline, and 15s is the absolute authentication deadline. Pending writes remain bounded as above.

The TDS session owner serializes first-frame authentication, registration, socket-close and revocation per terminal. It creates a pending attempt entry before starting the real credential query. The actor receives the query result and listener revocations in one order: if the socket has closed or the attempt's generation is at or below a revocation already observed, it rejects the attempt without registering or sending `SESSION_READY`; otherwise it registers and sends `SESSION_READY`, and any later matching revocation closes that session. A notification updates only an actor with a pending attempt or active session; no historical notification map is kept. The actor is removed when it has neither pending attempts nor an active session. Pending attempt count is bounded by the configured unauthenticated-connection limit. If an event races actor retirement, a later credential query reads current binding state; if a statement that began earlier returns stale success, its pending actor has not retired and consumes the revocation before registration. During listener recovery, re-LISTEN is committed before the set-based current-state reconciliation; the actor serializes that result with pending auth and new notifications. This closes the notification-before-registration gap while keeping connection validation limited to connect time and revocation events.
