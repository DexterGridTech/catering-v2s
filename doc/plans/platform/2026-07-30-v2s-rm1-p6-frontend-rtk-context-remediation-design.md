# RM1 P6 frontend RTK and context-view remediation design

## 1. Business problem and frozen inputs

An operations administrator may move from a data-rich region to a data-poor region, or change assignment. The
workspace-IAM owner returns a new session entry with monotonically increased `contextVersion`; generated list
queries correctly use that value. Before this remediation, the shared shell retained each page's local pagination
and view state, so page three could be requested in a one-page context and look like an empty business population.
The business requirement is therefore a truthful first view of the newly selected permitted population, without
changing authorization facts. The owning sources are the P6 roster, the RTK conformance review and
`WorkspaceAuthenticationService` context-selection CAS methods.

The review also establishes the repository's actual RTK model: one generated `createApi` per app; only its reducer
and middleware in the store; generated hooks for reads; generated client commands for writes; app-owned React
state for selection; and no page-local transport construction.

## 2. Exact design

1. `createObservedBaseQuery` is an app-substrate primitive only, with the two exact consumers `PlatformApi.ts` and
   `OperationsApi.ts`. `platformHttpProtocol` remains foundation-internal. Neither is a physical screen import.
2. Read screens use generated `use<OperationId>Query`; writes use the generated client through the existing
   transport command boundary. Writes refresh subscriptions via generated `[{wire, operationId}, {wire, LIST}]`
   invalidation. Context refresh is separate: every owner-scoped query receives `expectedContextVersion`.
3. `scopeRef` is retained only for operations whose contract names it as a business argument. It never substitutes
   for owner `contextVersion` increment. `identityKey` has no generated consumer and is
   `DORMANT_WITH_REASON`; no consumer is invented.
4. The operations shell keys the registered content component by `session.contextVersion`. A changed context
   remounts the selected content, resetting pagination, filters, drawers, expanded rows and other page-local view
   state. Same-version renders retain local state. The owner-selected data range and RTK query arguments are not
   changed.
5. Platform group-workspace selection remains the existing `WorkspaceScope.tsx` React state owner; no slice or
   store reducer is introduced.

## 3. Proof and red mutation

The focused architecture test reads the source composition boundary and requires the registered component to carry
`key={session.contextVersion}`. Its red mutation removes that key and must fail. This is a composition-contract
proof, not a claim of browser interaction coverage; the roster records that a future page implementation must add
an actual component/browser harness before claiming UI behavioral completion. Existing operations architecture and
TypeScript checks remain required.

## 4. Exclusions

No owner SQL, contract, generated byte, store topology, page-local request argument, new UI surface, DEV, seed,
reset or runtime environment action is in scope.
