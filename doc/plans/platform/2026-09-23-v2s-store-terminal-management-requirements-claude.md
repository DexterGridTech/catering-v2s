## 0. 术语

| 词 | 本稿中的含义 |
|---|---|
| 终端 | 门店里**服务一个点位的功能集合**。不是物理设备，但将来安装在一台物理设备上运行。由用户命名，例如「前台收银机」「热厨 KDS」 |
| 点位 | 门店里一个有固定职责的位置：前台、大厅、包房、后厨档口、出品口、外卖交接点、门口迎宾台等。**本期不建点位实体**，点位由终端的名称与范围体现 |
| 设备类型 | 终端将要安装的设备形态：台式（laptop）或手持（mobile） |
| 功能 | 终端能做的一类事，共 6 个：点餐收银、接单确认、KDS、厨打、出餐、排队叫号 |
| 范围 | 某个功能在这台终端上**管哪些桌台区、哪些单或哪些菜** |
| 桌台区 | 门店桌台与二维码页面里类型为「桌台区」的区域；桌台范围只选到这一层（D-17），另有「全部桌台区」选项（D-23） |
| 打印场景 | 一种业务单据，也就是一张纸，例如结账单、制作单、外卖商家联 |
| 打印纸类型 | 打印机装的纸：热敏 58 / 80 毫米，或某个尺寸的标签纸 |
| 连接方式 | 终端怎么连到打印机：USB、蓝牙、网口、云端、内置 |
| 订单类型 | 堂食、外卖、外带 |
| 硬约束 | 系统强制、不可绕过的规则，分两类：contract 登记的模型关系，以及数据完整性（§3.7） |
| 软约束 | 由配置的人自己决定、系统既不拦截也不提示的**业务取舍**，例如「两个厨打都管热菜」 |
| 激活码 | 每个终端一个 8 位数字码，新建时可以手填，留空由系统生成（D-29）；将来设备凭它找到自己要成为的那个终端 |
| 集团空间 | v2s 的租户边界（group workspace） |

## 1. 文档定位与真实业务问题

本文是「门店终端管理」的业务需求正本，不是详设、实施计划、代码变更或运行授权。**本期只做规则设计与规则管理**（D-14）。

### 1.1 业务背景：一家店里有很多台机器，每台做的事不一样

一家中餐正餐店，从门口到后厨大致有这些点位：

- **门口迎宾台**：客人排队取号，打出排队号票。
- **前台**：结账、处理外卖和自提，打出结账单、退款小票、取餐单。
- **大厅、包房**：服务员拿手持机点菜，打出客单、预结单。
- **后厨档口**：热厨、冷菜、吧台各做各的菜。热厨看 KDS 屏，冷菜间收制作单，吧台出杯贴。
- **出品口**：所有菜在这里出厨房，划菜员对着划菜总单核对，传菜员拿着传菜单送菜。
- **外卖交接点**：打包、核对、交给骑手，打出外卖商家联、外卖顾客联、配送单。

同一家店可能有十几台机器：台式收银机、服务员手持、厨房屏、出品口的屏。每台机器做的事不同，下挂的打印机不同，管的桌台和菜品也不同。快餐店或茶饮店简单得多：一台收银机可能同时管点单、厨打和叫号，下挂一台小票机和一台标签机。

### 1.2 要解决的问题

没有一套统一的规则，下面这些问题都答不上来：

1. **这台机器是干什么的**：它能点单收银吗？是 KDS 吗？
2. **它管哪些桌、哪些单、哪些菜**：二楼的出餐终端只该管二楼的桌；热厨的厨打只该打热菜。
3. **它打哪些纸、打到哪台打印机上**：结账单打到前台的 80 毫米小票机；杯贴打到 40×30 的标签机；热厨打印机坏了自动换到备用机。
4. **哪些配置物理上不成立**：KDS 装在手持机上没有意义；标签纸打不了结账单。

本需求要让门店的运营人员在运营管理后台**把每台终端的这些规则配置出来**，由系统拦住不成立的配置；成立、但业务上可能不合适的配置（例如两个厨打都管热菜），由配置的人自己负责调整（D-9、D-10）。

### 1.3 本期交付与不交付

交付：

- 终端规则的**硬约束登记**（contract）：设备类型、功能、范围类型、打印场景、打印纸类型、连接方式、订单类型、打印机品牌与型号，以及它们之间的支持关系。
- 终端规则的**保存与读取**：终端、功能、范围、打印机、场景配置、激活码。
- 运营管理后台「门店终端管理」的**菜单、页面与写权限**。

不交付：终端 App 读取规则、激活、TDP 推送、真正的打印、KDS 显示、订单路由（全表见 §9）。

**必须如实记录**：本期的规则**只被保存、校验和展示**，没有任何代码按它去路由订单或打印。这与门店桌台的容纳人数、是否可预约「定义了但本期无消费者」同一形态（`doc/plans/platform/2026-09-17-v2s-store-service-point-qr-requirements-claude.md` §2.1，下称「桌台需求」）。详设与实现**不得**为本期不存在的运行时编造行为，例如「保存后通知终端刷新」「检查打印机是否在线」。

### 1.4 与已建成能力的关系

| 已建成能力 | 本需求怎么用 |
|---|---|
| 门店桌台与二维码（organization 域的区域、服务点） | 点餐收银、接单确认、出餐的**桌台范围**从这里的桌台区中选 |

生产标签的这次消费，正是业务语料 CIPG-01 预留的那条路：「生产标签只作为商品级 0..1 稳定业务分类，未来生产链可在新专题中显式消费」「改变生产去向……未来确有生产路由 Journey 时必须重开需求」（`project-memory/decisions/confirmed-business-language-corpus.md`）。**本需求就是这个新专题的规则部分**：它把生产标签作为厨打、KDS 的范围值显式引用，但**本期仍不实现**生产路由本身。

## 2. 业务目标与成功结果

1. 有权限的人能在运营管理后台为所选门店新建、修改、停用、启用、作废终端。
2. 每个终端能配置名称、设备类型、至少一个功能（厨打可以多个）、每个功能的范围、打印机，以及每个功能下勾选的打印场景、每个场景的订单类型和打印机（D-30、D-31）。
3. 不成立的配置被系统拒绝（硬约束），且**后端不可绕过**；业务上的取舍不被拦截（软约束）。
4. 每个终端有一个 8 位数字激活码：新建时可以手填，留空由系统生成（D-29）；只在终端详情里明文可见（D-28）；集团空间内不重复；创建后不能修改。
5. 页面访问与编辑受角色权限约束，用户群与门店商品管理一致，有独立的写权限。
6. contract 登记的硬约束**只有一个住址**，后端的校验与前端的选项都从它来。

成功结果必须由 owner readback、HTTP contract、backend-acceptance 场景或前端 focused test 证明；本文件的静态要求不构成运行通过。

### 2.1 方案取舍与已否决的替代

| 替代方案 | 描述 | 去向与理由 |
|---|---|---|
| 终端＝物理设备 | 一台设备就是一个终端，规则跟设备走。v6 的定义大意是「装了本平台 App、能激活并建连的主机型设备才是终端」（design-v6 `01.领域设计/21-打印规则域.md` 第 7 行一带，此处是转述） | 否决：Dexter 裁定终端是「服务一个点位的功能集合」（D-1）。点位在业务上稳定，设备会坏、会换；按点位定规则，换设备时规则不动，新设备重新激活即可 |
| 门店级打印机清单，终端去引用 | 打印机在门店层维护一次，多个终端引用同一条记录；改 IP 只改一处 | **Dexter 选定不采用（D-19）**：打印机由每个终端各自定义，共用＝同一台物理打印机在多个终端里各自配置。已知代价：同一台网口打印机要在多个终端里各录一次 IP，IP 变了要改多处，系统也不知道它们是同一台 |
| 混合：网口、云端打印机放门店级，USB、蓝牙、内置跟终端 | 两处都能建打印机 | 同上，不采用（D-19） |
| 设一个「派发中心」决定哪台终端打 | 给每个场景配「由哪台终端出纸」 | 否决：Dexter 裁定没有派发（D-12），每台终端按自己的配置决定打不打，见 §3.6 |
| 场景与订单类型的对应写成硬约束 | 例如「划菜总单只对堂食」写进 contract | 否决：Dexter 裁定这是配置（D-12） |
| 桌台范围选到单张桌台，或「选中区域＝只存当时的桌台」 | 更细的粒度 | 否决：Dexter 裁定范围只选到桌台区、只存桌台区（D-17）；同时提供「全部桌台区（含以后新建）」选项（D-23） |
| 生产标签范围加「无生产标签」或「全部生产标签（含以后新建）」 | 与「无桌台」同形的兜底选项，以及自动包含以后新标签的选项 | 「无生产标签」：**Dexter 选定不加（D-20）**，没挂生产标签的商品不进任何厨打或 KDS。「全部生产标签」：**Dexter 选定加（D-24）** |
| 点餐收银的范围加「外卖」 | 让收银终端也能对外卖单结账、反结账、退款 | **Dexter 选定不加（D-21）**，后果见 R-3.7 |
| 按业态出规则模板 | 茶饮、快餐、中餐、西餐各一套默认规则 | 否决：业态不进入规则（D-11） |

## 3. 模型：为什么是这样

### 3.1 终端是「点位的功能集合」

终端描述的是「**这个点位要做什么**」。设备是载体，终端是规则。

- 前台的收银机坏了，换一台新的，前台要做的事没变：规则不动，新设备重新激活成「前台收银机」即可。
- 小店的一台收银机同时是前台、外卖交接点和出品口：一个终端承载多个功能即可。

设备类型仍是终端的属性，因为**功能对设备有物理要求**：KDS 要一块厨师看得清的屏，出餐要在出品口核对一整桌的菜，手持机的小屏做不了。所以新建终端第一步选设备类型，之后只能选这种设备支持的功能（D-1）。

### 3.2 六个功能

| 功能 | 做什么 | 台式 | 手持 | 一个终端可有几个 | 范围 | 打印场景数 |
|---|---|---|---|---|---|---|
| 点餐收银 | 店员主动开单、点菜、加菜、预结、结账、反结账、退款；桌边划菜也在这里 | ✓ | ✓ | 0 或 1 | 桌台、无桌台 | 6 |
| 接单确认 | 顾客扫码下单或外卖单进来时，店员确认接还是不接，确认后进生产 | ✓ | ✓ | 0 或 1 | 桌台、无桌台、外卖 | 0 |
| KDS | 在屏上显示要做的菜、标记做完 | ✓ | ✗ | 0 或 1 | 生产标签 | 0 |
| 厨打 | 把要做的菜打成纸交给档口 | ✓ | ✓ | **任意多个** | 生产标签 | 5 |
| 出餐 | 在出品口或交接点把一单的菜汇齐、核对、交出去，含取餐叫号 | ✓ | ✗ | 0 或 1 | 桌台、无桌台、外卖 | 5 |
| 排队叫号 | 门口来客取号、叫号 | ✓ | ✓ | 0 或 1 | 无 | 1 |

「范围」一列是范围类型（§4.4）：「桌台」范围选到桌台区，或选「全部桌台区」（R-3.1）；「生产标签」范围选指定标签，或选「全部生产标签」（R-3.8）。

一个终端**至少一个功能**：D-1 原话是「可选一个或多个，可自由组合」。

功能的业务定义来自 Dexter 的消息（冻结输入消息 1、2：「店员主动操作开单、收银」「店员需要对订单进行确认，确认后可进生产」「我把取餐叫号归属到“出餐”功能里，不管是出餐给谁」）；「桌边划菜归点餐收银」是分析稿判断（分析稿 §7.2 N1）。

**为什么厨打可以有多个**：一台收银机常常同时驱动冷菜间、吧台两台打印机，冷菜要打到冷菜间，饮品要打到吧台。如果一个终端只能有一个厨打，它的范围就是「冷菜＋酒水」，而同一个场景只有一组打印机，冷菜和饮品分不到两个地方。拆成两个厨打，各管自己的生产标签、各绑自己的打印机，问题就解决了（分析稿 §2）。

**为什么出餐只有 0 或 1 个**：多层店每层一个传菜口，Dexter 的解法是每层一个出餐终端（D-7）。在此基础上，作者的判断是（分析稿 §7.3）：每层传菜口本来就有一台台式设备，所以「常见情况给便利（厨打可多个），少见情况用多终端（出餐）」。

### 3.3 范围：两条互不相干的轴，两种含义

范围沿两条轴切：

- **桌台轴**（桌台区）：回答「**在哪操作、送到哪**」，用于点餐收银、接单确认、出餐。
- **商品轴**（生产标签）：回答「**这道菜谁做**」，用于厨打、KDS。

两条轴互不相干：热菜不管来自哪张桌都由热厨做；二楼的传菜口不管菜是哪个档口做的，都只收二楼的单。

范围在两类功能里含义不同，必须写清楚，否则详设会把它们做成同一种判定：

- **点餐收银的范围＝这台终端能操作哪些单**：哪些桌台区里的桌，加上是否能做「无桌台」的单。例：大厅服务员的手持只管大厅区；前台收银机管全部桌台区，外加「无桌台」的单（快餐、外带、自提）。这是分析稿判断（分析稿 §7.2 M1 续），与 D-2「谁操作谁打」互补；Dexter 在 D-21 选择时已按这个理解接受了它的后果。
- **接单确认、出餐、厨打、KDS 的范围＝哪些单或菜会落到这台终端**。例：热厨 KDS 只显示挂着「热菜」生产标签的菜；外卖交接点的出餐终端只管外卖单。

**无桌台**是和外卖并列的选项：快餐凭号取餐、外带、自提都没有桌台，但都不是外卖。Dexter 以「M2，我同意你的建议」同意了增加这一项（D-3）；它适用于点餐收银、接单确认、出餐三个功能，是分析稿 §7.2 的处置。

### 3.4 打印机与打印场景

每个终端可以配置多台打印机，打印机由**每个终端各自定义**（D-1、D-19）。每台打印机有名称、品牌与型号、连接方式（及其参数）和打印纸类型；纸型只能从所选型号允许的纸规格里选（D-33）。没有登记的具体型号，用对应纸规格的通用型号录入（D-35）。

选中一个功能后，这个功能的全部打印场景列出来，由配置的人全选或选一部分。每个场景声明自己支持哪些打印纸，所以**给场景挑打印机只看纸型对不对，不看怎么连**：结账单能挑热敏 58、80 的打印机，标签制作联只能挑标签打印机。

每个场景可以挑多台打印机，数量不限；这些打印机**同等地位、没有顺序、不分主备**（D-31，取代 D-1 里「作为主备」的说法）。同一功能的不同场景各自挑自己的打印机，互不影响（D-30）。运行时在集合内怎样分配或切换，属于将来的打印运行设计，本期不定义。

**同一台物理打印机可以被多个终端共用**（D-8）：服务员手持机自己没带打印机，就把大厅那台固定的网口打印机也配置成自己的打印机，「谁操作谁打」依然成立（D-2）。系统不知道这几条配置指的是同一台物理打印机（D-19 已接受这一代价）。

### 3.5 订单类型是场景上的配置

出品口的出餐终端，范围是「全部桌台区＋外卖」，勾了划菜总单和传菜单。来一张外卖单，划菜总单要不要打？

Dexter 的裁定是：配置的人选中场景后，**再选它支持哪些订单类型**（堂食、外卖、外带）（D-11、D-12）。于是划菜总单只选「堂食」，外卖单来了就不出划菜总单；传菜单选「堂食、外卖」，外卖的菜照样有人送到外卖交接点。能不能正常工作，由配置的人自己调整。

对接单确认、出餐、厨打、KDS 来说，范围与订单类型是**两条独立的轴**：范围回答「哪些单会到这台终端」，订单类型回答「这个场景对哪类单打印」。例：「无桌台」里既有快餐堂食（凭号取餐），也有外带；同一台前台终端的取餐单可以只选「堂食」，也可以「堂食、外带」都选。点餐收银的范围含义不同（§3.3），但订单类型的选法一样。

### 3.6 没有中心派发：每台终端按自己的配置决定

规则里**没有**「这张纸由哪台终端打」这个属性。Dexter 给出的四种情况（D-12）：

| # | 终端配置 | 下单之后 |
|---|---|---|
| 1 | 服务员手持：内置打印机＋点餐收银＋**勾了客单** | 打出客单 |
| 2 | 服务员手持：内置打印机＋点餐收银＋**没勾客单** | 不打客单 |
| 3 | 服务员手持：配了远端打印机＋**厨打**＋勾了制作单 | 手持也收到订单拆出的工作单，打出制作单 |
| 4 | 服务员手持不配厨打；KDS 配了打印机＋厨打＋勾了制作单 | 工作单被推到 KDS，KDS 发现它落在自己的厨打范围里，打出制作单 |

大厅 3 台手持和前台 1 台都覆盖 A3 桌，服务员在一台手持上点「预结」，**不会 4 台一起出纸**：点餐收银的纸由**本机上发生的操作**引起，别的终端上没有发生这个操作（D-2）。厨打和出餐的纸则由推送过来、落在自己范围里的数据引起。

本期不实现这些运行行为。列出它们，是为了说明**规则为什么只需要本稿这些属性**。

### 3.7 硬约束与软约束

Dexter 的总原则见 D-9、D-10：约束分硬、软两种；功能支持哪些设备类型、打印场景支持哪些打印纸类型这类是硬约束，必须在 contract 中定义好；同一个生产标签挂在两个厨打下面这类是软约束，由规则管理人自己调优；规则尽量灵活，觉得不合适就改规则。

落到本需求，系统强制的只有两类，其余全是软约束：

| 类 | 包含什么 | 系统行为 |
|---|---|---|
| **模型关系**（contract 登记，§4） | 功能 × 设备类型、功能的个数上限、功能 × 范围类型、功能 × 打印场景、场景 × 纸型、品牌 × 型号、型号 × 纸规格，以及纸型、品牌与型号、连接方式与参数、订单类型的取值清单 | 拦截，后端不可绕过 |
| **数据完整性** | 必填项；终端至少一个功能（D-1）；引用的桌台区、生产标签、打印机必须存在且属于本门店或本终端；新加入的引用必须可用；范围里「全部」与指定二选一（R-3.1、R-3.8）；同一场景的打印机集合不重复；USB、蓝牙设备标识在同一终端同一连接方式下不重复（D-34）；用于分辨的名称不重复（R-1.2、R-4.2） | 拦截，后端不可绕过 |
| **软约束** | 其余一切配置取舍 | 不拦截、**不提示** |

软约束的例子：

| 配置 | 结果 |
|---|---|
| 两个厨打都管「热菜」 | 热菜会出两张制作单，**允许** |
| 两台出餐终端覆盖同一个桌台区 | **允许** |
| 同一台网口打印机配在两个终端里 | **允许** |
| 勾了场景但没挑打印机，或没选订单类型 | 这个场景等于不打，**允许**。排队号票与订单无关，没选订单类型不影响它，没挑打印机才等于不打（R-5.5） |
| 范围为空 | 这个功能什么都不管，**允许** |
| 快餐店的堂食要不要打预结单 | 管理员勾不勾的事 |

### 3.8 业态不进入规则

茶饮、快餐、中餐、西餐等业态**不出现在规则里**（D-11）。contract 登记里只出现订单与硬件的事实：设备类型、功能、范围类型、打印场景、纸型、连接方式、订单类型、打印机品牌与型号。「预结单对快餐有没有意义」这种问法本身不成立，快餐店不打预结单就是不勾。

## 4. 硬约束登记（contract）

### 4.1 要求

- R-C.1 下列八类登记在 contract 中，**只有一个住址**。后端的保存校验、运营后台的选项与业务名称都从这一处来；不得在前端或后端手写第二份清单。
- R-C.2 这些都是**代码定义的闭集**：前端按仓内标准从 contract 得到字典，后端只存取值，**不新增词汇表接口**（`project-memory/decisions/owner-read-model-and-lifecycle-standard.md` 的 `FRONTEND_DICTIONARY_FOR_CODE_DEFINED_ENUMS`）。
- R-C.3 登记的维护方式是修改 contract，**不提供后台维护页面**。依据是 D-10（「都是需要再contract中明确定义好的」）；D-1 的「可在contract中维护」原本只修饰标签尺寸。
- R-C.4 将来修改登记使既有终端配置不再满足硬约束时（例如从某个场景的支持纸型里删掉 58 毫米），这次修改必须同时处置受影响的既有数据，不得让既有终端因此变得无法保存（本稿补充，§13）。
- R-C.5 设备类型的取值必须与终端 App 已有的设备形态取值一致：`apps/terminal/kernel/base/contracts/src/types/display.ts` 第 1 行 `export type SurfaceForm = 'laptop' | 'mobile'`，与 D-1「台式（laptop）或手持（mobile）」吻合。本期终端 App 不消费本登记，两边统一到一个住址的工作留待终端接入时处理。
- R-C.6 页面上只显示业务名称（台式、手持、结账单、热敏 80 毫米……），不显示内部取值（例如 `laptop`、`TABLE_AREA`）。这与业务语料 CIPG-01「内部枚举……均不得作为可见文案」同一口径。

### 4.9 H8 打印机品牌与型号

- 品牌、型号，以及每个型号允许的纸规格，登记在 contract（D-33）。具体型号的纸规格须有厂商资料依据，不编造兼容关系。
- 每种纸规格另有一个**通用型号**（例如通用热敏 58 毫米、通用标签 40×30 毫米），外加设备内置 58 毫米、80 毫米两个通用型号。通用型号不声称厂商兼容，只声明纸规格，保证任何打印机都能录入（D-35）。
- 型号必须属于所选品牌；型号只允许一种纸规格时纸规格固定，允许多种时由用户选定其一（D-33）。
- 首批登记哪些具体型号，由详设按厂商资料确定；以后按需在 contract 中增补（R-C.3）。

## 5. 终端的业务语义要求

### 5.1 基本信息

- R-1.1 终端属于一个门店，创建后不能换门店（本稿补充，§13）。
- R-1.2 终端名称必填，由用户起名；在**同一门店未作废的终端之间**不重复（本稿补充，§13；v4 同样是门店内唯一）。理由：列表里要靠名称分辨终端，属于数据完整性（§3.7）。
- R-1.3 设备类型必填，取值见 §4.2。新建时先选设备类型，之后只能选这种设备支持的功能（D-1）。
- R-1.4 设备类型**可以修改**，但修改后必须仍满足硬约束：所有已选功能都支持新的设备类型，否则 owner 拒绝（本稿补充，§13）。例：带着「KDS＋厨打」的台式终端直接改成手持会被拒；在同一次保存里去掉 KDS、保留厨打并改成手持，则成功。只有 KDS 一个功能的终端，要在同一次保存里把 KDS 换成手持也支持的功能（R-2.1 要求至少一个功能）。设备类型修改对将来已激活设备的影响，属于激活设计。
- R-1.5 终端带一个激活码，要求见 §6。

### 5.2 功能

- R-2.1 终端的功能从 §3.2 的 6 个中自由组合，**至少一个**（D-1：「可选一个或多个，可自由组合」）。
- R-2.2 除厨打外，每个功能在一个终端上**最多一个**；厨打可以有**任意多个**，每个厨打各有自己的范围、勾选的场景和打印机绑定（D-1）。
- R-2.3 每个厨打有**稳定的身份**：修改其中一个，不影响其他厨打；读回时各自独立，不因范围或场景相同而合并。是否给厨打起名由交互设计决定（§13）。
- R-2.4 同一终端的多个厨打之间，范围允许重叠，场景允许相同（软约束，D-10）。
- R-2.5 移除一个功能时，它的范围与场景配置随之移除；终端的打印机不随之移除。

### 5.3 范围

**桌台范围**

- R-3.1 桌台范围有两种选法，二选一：
  - **全部桌台区**：覆盖本门店现在和以后的全部桌台区（D-23）。保存的是「全部」这一个选择，不展开成当时的桌台区清单。
  - **指定桌台区**：从本门店的桌台区中多选，只选到桌台区这一层，**不能选单张桌台**；保存的就是这几个桌台区（D-17）。
  
  两种选法不能同时保存：选了「全部」，就不再单独列桌台区（数据完整性）。
- R-3.2 只有类型为「桌台区」的区域可以进入桌台范围，扫码区与扫码点不进入（D-18）。来自扫码点的单没有桌台，属于「无桌台」——这是本稿从 D-18 推出的（§13）。**已知后果**：一家店所有扫码点的单都落在同一个「无桌台」选项里，没有终端能按扫码区（例如分楼层）只接其中一部分；若将来需要按扫码区分派，属于新增范围值，要另行裁决。**owner 在服务端校验**：新加入的引用必须是本门店、类型为桌台区的区域，前端不列扫码区只是便利。**仓内事实**：区域类型为 `TABLE_AREA / SCAN_AREA`、服务点类型为 `TABLE / SCAN`（`contracts/openapi/components/organization/store-service-point-qr.schemas.json`）。
- R-3.3 选中一个桌台区，它**现在和以后**的全部桌台都在范围内：因为保存的是桌台区，以后在这个区新建的桌台自动覆盖，不需要回来改终端。选「全部桌台区」的终端，连以后新建的**桌台区**也自动覆盖（D-23）；「全部」只含类型为桌台区的区域，扫码区不算（D-18），某个区以后从扫码区改成桌台区，就自动进入「全部」。**已知后果**：选的是指定桌台区的终端，以后新建的桌台区不会自动进入它的范围，要回到终端上补选；补选之前，这个新区的单不会落到这台终端。需要比桌台区更细的划分时（例如某台手持只管包房 1 到 3 号），要在门店桌台与二维码页面把它们建成单独的桌台区（已知后果，D-17）。**仓内事实**：桌台不能跨区移动——服务点的更新命令沿用原区域（`StoreServicePointService.updatePoint`），所以桌台所属的区不会变。
- R-3.4 指定桌台区时，新加入范围的桌台区必须为**启用**。已在范围里的桌台区后来被停用、作废，或者整区桌台作废后被改成了扫码区，都**不自动移出**，保存终端时也**不因此被拒**；读取终端时如实给出它当前的状态与类型，由页面显示出来，方便管理员清理（`owner-read-model-and-lifecycle-standard.md` 的 `EXISTING_REFERENCE_EXEMPT_FROM_STATUS_CHECK` 与 `CASCADE_STATUS_IS_DERIVED_NOT_STORED`）。不再是桌台区的引用，不算作桌台范围（本稿的设计，§13）。选「全部桌台区」时没有逐个引用，桌台区的状态变化不涉及这一条；「全部」覆盖的桌台区里哪些当下可用，属于运行时判断，本期不定义。作废桌台区、生产标签时，不向操作者显示「被多少个终端引用」；终端详情里如实显示引用对象已作废，运行时由终端自己判断引用的实体是否有效，规则不需要变化（D-25）。**仓内事实**：区域在其下没有未作废服务点时可以改类型（`StoreServicePointService.updateArea`；桌台需求 R-1.2、R-1.6）。
- R-3.5 范围的候选**不看**门店经营规则开关：即使门店关闭了「是否启用桌台和二维码管理」或「是否启用商品、库存和菜单管理」，已存在的桌台区与生产标签照常可选。这是本稿对 D-15 的延伸理解，与 R-9.8 同类（§13）。**仓内事实**：门店桌台 owner 只在写命令上校验开关（`StoreServicePointService.requireCommand` 调用 `requireStoreOperatingRuleForStoreTarget`），读取区域与服务点的方法不校验；生产标签 owner 的读取（`CatalogProductionTagOwnerService.readTags`、`readTagReferencesByRefs`）只校验作用域不为空，整个服务里没有开关判断，开关约束挂在写命令的 token 上（`CatalogInventoryWorkspaceCommandTokens`）。

**无桌台、外卖**

- R-3.6 「无桌台」「外卖」各是一个是否选项；外卖不区分平台（D-1、D-3）。
- R-3.7 点餐收银没有「外卖」选项；接单确认、出餐都有（D-21）。**已知后果**（Dexter 选择时已知悉）：按 §3.3 的理解，没有任何终端能对外卖单做点餐收银的操作（结账、反结账、退款），外卖单的结账单、反结账单、退款小票也就无处可打；前台的外卖由接单确认与出餐承担。

**生产标签范围**

- R-3.8 生产标签范围有两种选法，二选一：**全部生产标签**（覆盖本门店现在和以后的全部生产标签，保存的是「全部」这一个选择，不展开成当时的标签清单，D-24），或从**本门店的生产标签**中多选**指定标签**。两种选法不能同时保存（数据完整性）。**仓内事实**：生产标签按「数据节点＋品牌」严格隔离、不向上继承——表 `catalog.production_tag_definition` 以 `data_node_ref`、`brand_ref` 定作用域（`V20260921_000000_000__catalog_production_tag_owner_cutover.sql`），读取按两者精确匹配（`CatalogProductionTagOwnerService.readTags` 与其 persistence）；门店的商品作用域是「门店＋门店自身保存的品牌」（`OrganizationTaskPathPersistence` 以 `STORE_PERSISTED_BRAND` 给出品牌判定），且门店的品牌在建店时锁定（业务语料 G-06）。所以候选就是在门店商品管理里为这家门店维护的那些生产标签。上述判定只在门店及其所属项目、大区都启用时成立（门店的任务路径查询同时要求三者启用，见 `OrganizationTaskPathServiceSql`），停用门店的处理见 R-6.5。
- R-3.9 指定标签时，新加入范围的生产标签必须为**启用**；已在范围里的标签后来被停用或作废，处理同 R-3.4。选「全部生产标签」时没有逐个引用，标签的状态变化不涉及这一条。这与业务语料 CIPG-01「停用生产标签不进入新候选，既有商品绑定继续显示并可清除」同一口径。
- R-3.10 **没有挂生产标签的商品，不会落入任何厨打或 KDS 的范围**（D-20），选了「全部生产标签」也一样：「全部」指的是全部标签，不是全部商品。0 个生产标签就表示这道菜不需要后厨制作，例如冰柜里直接拿的饮料；想让一道菜出制作单，就要给它挂上生产标签。**已知后果**（Dexter 选择时已知悉，所选选项的说明原文是「漏挂的菜不会出单，也没有提示」）：漏挂标签的菜将来不会出制作单，系统也不提示（与 R-7.4 一致）。
- R-3.11 选「全部生产标签」的厨打或 KDS，以后新建的生产标签自动覆盖（D-24）；选的是指定标签的，以后新建了生产标签要回来加选。

**通用**

- R-3.12 范围可以为空（软约束）：例如出餐终端什么都没选，就什么单都不管。
- R-3.13 不同终端之间、同一终端的多个厨打之间，范围允许重叠（软约束，D-10）。
- R-3.14 范围里的桌台区与生产标签一律**以 ref 为身份**引用，不以编码引用。**仓内事实**：桌台区与生产标签的编码都在作废后释放（`V20260917_000000_000__store_service_point_qr.sql`、`V20260921_000000_000__catalog_production_tag_owner_cutover.sql` 的排除作废的唯一索引），同一编码在不同时间可以指向两个对象（`owner-read-model-and-lifecycle-standard.md` 的 `VOIDED_RELEASES_CODE_AND_REF_IS_IDENTITY`）；生产标签 owner 的写命令按编码定位（`CatalogProductionTagOwnerService.resolveProductionTagRef`），容易诱导实现按编码存引用。

### 5.4 打印机

- R-4.1 一个终端可以配置任意多台打印机，也可以一台都不配（D-1）。打印机由每个终端各自定义（D-19）。
- R-4.2 每台打印机有名称、品牌与型号（按 §4.9）、连接方式、连接参数（按 §4.7）、打印纸类型（按 §4.6，须在所选型号允许的纸规格之内，D-33）。名称在本终端内不重复（本稿补充，§13）。理由：同品牌同型号的两台、以及内置打印机，没有别的字段可以分辨，给场景挑打印机时要靠名称，属于数据完整性（§3.7）。
- R-4.3 连接方式要求的参数必须填且格式正确；连接方式不要求的参数不得出现（D-22、D-34）。USB、蓝牙的设备标识在同一终端同一连接方式下不重复（D-34）。
- R-4.4 打印机是终端的一部分，**不单独拥有启用、停用、作废**，随终端一起编辑。
- R-4.5 同一台物理打印机可以在多个终端里各自配置（D-8、D-19）。系统**不**跨终端识别或去重物理打印机，不对 IP、设备 ID 或 USB、蓝牙设备标识做跨终端唯一。
- R-4.6 连接方式与设备类型之间**不设**硬约束，例如手持机也可以配 USB 打印机；Dexter 列出的硬约束里没有这一项。

### 5.5 打印场景配置

- R-5.1 每个功能（多个厨打各自）可以勾选这个功能名下的打印场景，全选或选一部分（D-1）；KDS、接单确认没有可勾的场景。
- R-5.2 每个勾选的场景可以选它支持的**订单类型**：堂食、外卖、外带的任意组合（D-12）；选法上所有场景一样，不设特例（§4.5），订单类型对排队号票不起作用见 R-5.5。点餐收银的场景也可以选「外卖」，虽然它的范围不含外卖（R-3.7）——D-12 要求不在 contract 里约束场景与订单类型，这里照此保留。
- R-5.3 每个勾选的场景可以从**本终端的**打印机里挑选多台，组成一个**无序集合**：同等地位、没有主备、没有顺序，数量不限（D-31）。集合按打印机的**稳定身份**引用，不按名称；打印机改名不影响绑定。同一功能的不同场景各自选择自己的打印机，互不影响（D-30）。
- R-5.4 挑选的打印机的纸型必须在该场景支持的纸型之内（模型关系，D-1、D-10）；同一个场景的集合里，同一台打印机不能出现两次（数据完整性）。
- R-5.5 勾了场景但没选订单类型或没挑打印机，允许保存（软约束）；这个场景等于不打。「没选订单类型等于不打」只适用于由订单引起的场景；排队号票与订单无关，订单类型对它不起作用，没挑打印机才等于不打（本稿推论，§13）。
- R-5.6 修改打印机的纸型、或移除一台打印机，使某个场景的绑定不再成立时，这次保存必须连同场景绑定一起改对，否则 owner 拒绝。页面怎么引导用户处理（例如移除打印机时同时从场景里拿掉它）由交互设计决定。

### 5.6 生命周期

- R-6.1 终端采用仓内三态：启用、停用、作废（`MASTER_DATA_LIFECYCLE_IS_THREE_STATES`）。新建默认启用。这三种操作是本稿按仓内标准补充的，不是 D-13 原话（§13）。
- R-6.2 停用的终端照常可以查看和编辑（`DISABLED_STAYS_EDITABLE`）；启用与停用可以来回切换。门店被停用时的情形见 R-6.5。
- R-6.3 作废是终态：作废的终端不再出现在列表里、不能编辑、不能恢复；它的名称释放，可以给新终端用；**它的激活码不释放**（R-8.4）。
- R-6.4 各状态的**运行时含义**（例如停用的终端能不能激活、能不能工作）属于激活与终端运行的设计，本期不定义。
- R-6.5 门店被停用后，门店终端管理与门店桌台与二维码、门店商品管理等其他门店级页面一样**不可读写**，本期不为终端页单独放开（D-26）。这是对仓内标准「管理编辑……只看自身状态」（`owner-read-model-and-lifecycle-standard.md` 的 `CASCADE_STATUS_IS_DERIVED_NOT_STORED`）的**明确例外**，由 Dexter 批准；平台所有门店级页面目前都是这一形态。**仓内事实**：平台默认只按启用的目标解析权限范围（`WorkspaceCapabilityScopeResolver.resolve` 走 `ENABLED_ONLY`）。停用门店的请求只在两处被放行到 owner——门店经营渠道新建（`OperationsBusinessChannelController`）与门店销售菜单发布（`SalesMenuEdgeSupport.grantForPublish`）——目的都是让 owner 返回「门店已停用」一类的类型化拒绝，不是放行业务；另有把停用对象启用回来的状态切换策略（`resolveStatusTransition`）。数据节点候选会过滤停用门店及停用项目下的门店（`OrganizationVisibilityPersistence`）；业务语料 G-08 记载「停用阻断新建合同、邀请、渠道绑定、菜单发布等」。

### 5.7 保存与校验

- R-7.1 一个终端的基本信息、功能、范围、打印机、场景配置作为**一个整体**受保护：
  - 每次写入都以整个终端为单位校验全部硬约束，要么全部生效，要么全部不生效；不得出现「打印机存上了、场景绑定没存上」的半成品。
  - 一个终端**一个版本号**；每个写命令都带着它做并发校验，版本已过期的写入被拒，不静默覆盖。
  - 写命令是一次保存整个终端还是分块保存，交详设；无论哪种，都必须满足上面两条。
- R-7.2 §3.7 的全部硬约束由 **owner 在服务端**校验；前端不给选只是便利，**不是防线**（业务语料 CIPG-01：「隐藏、禁用或即时校验不得被解释为业务防线」）。
- R-7.3 引用的桌台区、生产标签必须属于**本门店**，引用的打印机必须属于**本终端**；跨门店、跨终端、跨集团空间的引用一律拒绝。
- R-7.4 软约束一律不拦截，也**不**附加「可能重复出单」一类的解释性提示。这与桌台需求 §6.2 的口径一致：不得自行添加解释性提示，需要时由 Dexter 另行裁决。

## 6. 激活码

### 6.1 为什么需要激活码

将来一台设备装上终端 App，要先知道「**我是哪个终端**」，才能拿到自己的功能、范围和打印机规则。激活码就是这把钥匙：管理员在后台建好终端，把激活码告诉装机的人，装机的人在设备上输入它，设备就成了这个终端（D-13：「后续终端在激活的时候，就凭这个码，就找到这个终端了」）。设备激活时，会用带集团空间 key 的 URL 访问激活服务（D-16），所以激活码只需在集团空间内唯一。

为什么是这些性质：

- **8 位数字**：在收银机或手持机的数字键盘上好输，念给现场的人听也不容易听错。
- **明文**：装机的人要能直接看到、抄下、念出来；门店运营人员随时可以回后台查。
- **创建后不能改**：装机说明、交接记录里写下的码要一直有效，码一变，之前记下的就全错了。
- **集团空间内不重复**：凭码找终端，就不能有两个终端同一个码；集团空间由激活 URL 带上（D-16）。

### 6.2 要求

- R-8.1 激活码在**新建终端时**确定：用户可以手填一个 8 位数字码；不填或填空，由系统生成（D-29，取代原先「用户不能指定」的写法）。编辑与状态变更请求都不能带激活码。
- R-8.2 激活码是恰好 8 个数字字符（0 到 9）组成的**字符串**，可以以 0 开头，前导 0 必须原样保留；它不是数值。允许以 0 开头是本稿的理解（§13）。
- R-8.3 系统生成的激活码必须**随机且不可预测**（D-13「随机」）：生产环境用密码学安全的随机数生成（本稿补充，§13），不得用流水号、时间戳，或由其他字段推导。手填的码不作随机性保证（D-29）。测试需要的可控生成来源只能在测试装配里出现，手填路径不调用它（V-14）。
- R-8.4 激活码在**集团空间内唯一，已作废的终端也算在内**：一个码发出去，就永远只指向这一个终端，不回收、不复用（§13）。
- R-8.5 激活码**创建后不能修改，也不能重新生成**；修改终端的任何信息、切换状态、作废，都不改变它（D-13）。
- R-8.6 激活码**明文保存**，**只在终端详情里明文展示**、不打码（D-13「要求明文」）；终端列表不显示激活码，列表读取也不返回它（D-28，取代原先「列表与详情都显示」的写法）。能看这个页面的人都能在详情里看到，包括只读用户——这一点是本稿从「明文」推出的（§13）。
- R-8.7 并发新建终端时也不得出现重复。系统生成的码撞上已有的码时，系统自行换一个，**不把撞码当成错误抛给用户**；换码的重试次数有上限，由详设定；在一亿个可选值下耗尽上限实际不会发生，万一发生，允许这次新建失败并报错（本稿补充，§13）。**手填的码**撞上已有的码（含已作废终端的码）时，报「该激活码已被使用」，**绝不替换成别的码**（D-29）。
- R-8.8 本期**不**提供「凭激活码查找终端」的接口，也不实现激活；本期只保证 R-8.4、R-8.5 这两条让将来的查找成立的性质（D-14）。
- R-8.9 激活码**只在门店终端管理的终端读取里返回**（R-8.6）；不写入审计记录（R-9.9），也不出现在其他共享读取面或诊断产物里。激活码能让一台设备成为这个终端，按凭证类的值对待：除了终端自身的保存（R-8.6）与终端读取，不进入审计、诊断等其他持久化或输出产物，参照仓内 `DIAGNOSTIC_SECRET_FLOW_EXPLICIT` 对凭证类值的口径。唯一例外：DEV 种子数据使用固定激活码，这些码只写在非生产受管 DEV 的种子数据正本里，经新建的手填路径写入；它们同样不进入审计、回执、日志、报告或列表（D-29）。

R-8.4 与仓内「作废释放编码」的惯例（`owner-read-model-and-lifecycle-standard.md` 的 `VOIDED_RELEASES_CODE_AND_REF_IS_IDENTITY`）不同，理由：那条惯例是为**人起的编码**设计的，作废行会永久占住一个人还想用的编码；激活码由系统随机生成，有一亿个可选值，占住作废终端的码没有代价。反过来，如果回收复用，一个早已作废的终端的旧码，可能某天恰好指向一个新终端，拿着旧码的人就会激活到别人的终端上。

### 6.3 已知后果（本期不处理，但详设与后续设计不得假装不存在）

1. **只读用户也能看到激活码**，因此也能拿它去激活设备。若将来只想让有写权限的人看到，需要另行裁决。
2. **8 位数字可以被穷举**。本期没有激活入口，不构成风险；将来的激活设计必须自带防穷举措施（例如限制尝试次数），不在本期。
3. **激活码泄露后不能换**。唯一的补救是作废这个终端、新建一个（新终端有新码）。将来的激活设计可以用「一个终端同时只允许绑定一台设备」之类的规则降低风险。
4. **激活码只在集团空间内唯一**，所以将来的激活服务必须按集团空间查找；设备通过带集团空间 key 的 URL 访问激活服务（D-16），这与运营管理后台登录入口带集团空间的做法一致（`apps/frontend/operations-admin/src/features/authentication/ui/OperationsLoginPage.tsx` 以 `groupWorkspaceKey` 读取登录入口）。
5. **手填的码可能很弱**（例如 00000000、12345678）。手填不作随机性保证（R-8.3），将来的激活设计必须自带第 2 条的防穷举措施；DEV 固定码只用于非生产环境，不能用作生产激活凭证（D-29）。

**外部事实**（仅作对照）：v4 的激活码是 12 位数字、**全平台唯一**、单独成表（catering-server-v4 `backend/edge-bff-service/src/main/resources/db/migration/V043__tcp_terminal_control_management.sql` 的 `tcp_activation_code`：`activation_code varchar(12)`、`unique (activation_code)`、`unique (group_workspace_id, terminal_ref)`；`ActivationCodeGenerator` 用 `SecureRandom` 逐位生成 12 位）。表上有 ACTIVE、USED、REVOKED 三个状态值，但实现中每个终端只有一个码，只在删除终端时把码置为 REVOKED（`TcpStoreTerminalJdbcRepository`），没有写 USED、也没有重发路径。本需求按 D-13 改为 8 位、集团空间内唯一、终端的固定属性。

## 7. 授权与操作面

### 7.1 页面与菜单

- R-9.1 运营管理后台新增一个**独立的菜单项与页面**，名称「门店终端管理」（D-13）。
- R-9.2 这是门店级页面：门店由既有的全局数据节点选择器选定，页面只显示所选门店的终端。
- R-9.3 页面放在导航分组「门店经营」下（本稿建议，§13）。

**仓内事实**：门店商品管理的页面 `PG-CATALOG-STORE-ITEMS` 在导航分组 `NAV-CATALOG-SERVICES`（商品与服务）下，页面访问受管（`pageAccessManaged: true`），`requiredDataNodeType` 为 `STORE`，可授予角色为 `GROUP / REGION / PROJECT / STORE`（`contracts/catalog/admin-catalog.json`）。当前「门店经营」分组（`NAV-STORE-OPERATIONS`）只有「门店资料」一页；「商品与服务」分组有门店商品管理、门店库存、品牌商品、门店销售菜单、门店桌台与二维码五页。

### 7.2 权限

- R-9.4 页面的可访问角色与门店商品管理**一致**：集团、大区、项目、门店四类运营角色可以被授予（D-13：「面向的用户群也是一样」）。
- R-9.5 新增一个独立的写权限「编辑门店终端」，可授予角色同上，作用于所选门店，与 `EDIT_STORE_CATALOG` 的 `scopeApplicability: SELECTED_STORE_SCOPE` 同一形态（D-13：「有个单独的写权限」）。
- R-9.6 「编辑门店终端」覆盖本页面的**全部写操作**：新建、修改、停用、启用、作废。没有这个权限的人只读：能看列表和详情（含激活码），看不到任何写入口；后端对其写请求一律拒绝。
- R-9.7 门店层角色与项目层角色都必须能正常使用这个页面，两个方向各自验证（桌台需求第 R-5.5 条记录的教训：规则读取曾分别在两个方向上把一类角色挡在外面）。

### 7.3 与门店经营规则开关无关联

- R-9.8 终端能选哪些功能**不看**门店经营规则开关（D-15）。例：门店没开「是否启用排队叫号」，终端照样可以配置排队叫号功能。本页面的进入与编辑同样**不受任何门店经营规则开关约束**：门店没开「是否启用商品、库存和菜单管理」，照样可以管理终端——这一点是本稿对 D-13「用户权限什么的，跟门店商品管理类似」与 D-15「两边是两个开关」的合并理解，D-15 原话针对的是终端功能（§13）。

**连带说明**：门店商品管理受「是否启用商品、库存和菜单管理」开关约束。本页面「与门店商品管理类似」指的是**角色与写权限**，不含这个开关。**仓内事实**：`contracts/catalog/store-operating-rule-switches.json` 的 12 个开关里没有终端相关的开关；其中「是否启用排队叫号」「是否启用取餐叫号」与本需求的排队叫号功能、出餐里的取餐叫号同名，但按 D-15 互不关联。

### 7.4 审计

- R-9.9 终端的新建、修改、状态变更进入既有审计机制，不新建审计机制。**最低粒度**（本稿补充，§13）：
  - 基本信息（名称、设备类型、状态）逐字段记录变更前后的值；
  - 功能、范围、打印机、场景配置按段记录「哪一段变了」，并给出变更前后可读的摘要（场景打印机按集合的增删，D-31），允许超长截断；
  - 新建时只记录「激活码已签发」这一事实，无论码是手填还是系统生成，都**不记录激活码原值**（R-8.9）。理由：共享审计读取对门店类对象只按可见门店授权，不检查终端页面权限（`OperationsAuditHistoryController` 按实体类型分派；`OperationsAuditTaskReadService` 对门店类审计只传可见组织事实；`OrganizationAuditHistoryPersistence` 按可见门店集合授权），把原值写进审计，会让能看到门店、却没有终端页面权限的人读到它。

**仓内事实**：门店桌台的写入已接审计（`StoreServicePointService` 第 45 至 47 行登记了区域、服务点、二维码配置三类审计实体）；既有审计的变更项只收可展示的标量字符串、单值超过 2000 字符截断（`audit-model` 的 `AuditChange`），并按「实体＋动作」维护封闭的字段白名单（`AuditChangePolicy`）。终端含可变长的集合，无法逐字段照搬门店桌台的表示，所以按段摘要记录；具体的字段键与摘要形态交详设。

### 7.5 UI 与交互的强制自问

**该操作是否来自用户明确要求**：是。独立菜单与页面、名称、写权限、用户群、激活码的全部性质来自 D-13；终端的全部配置项来自 D-1 至 D-12 与 D-16 至 D-35。本稿自行补充或推出的全部条目列在 §13 的「本稿写法、你不反对就定下」表里，这里不再重复列举。

**用户在此时这样操作是否合逻辑**：合逻辑。配置顺序与业务依赖一致（D-30）：先定设备类型（决定能选哪些功能），再配打印机，然后选功能与范围，最后在每条场景里挑打印机（纸型要先有打印机才能匹配）。

**有没有更短、更自然、更少选择的路径**：有几处值得交互设计权衡，本稿不强制：

1. **配置顺序**：Dexter 已确认按「基本信息 → 打印机信息 → 功能与范围」排列，每个功能下的每条场景各自选择订单类型与打印机（D-30）。
2. **默认值**：Dexter 已确认不做默认：新建时不自动勾场景、不默认选订单类型、不自动绑定打印机（D-30）。
3. **多台相同的手持机**：一家店 10 台服务员手持的配置几乎一样，要建 10 个终端、配 10 遍。「复制终端」能大幅省事，但它是新功能，**本期不纳入**，需要的话由 Dexter 另行决定。

**不合理之处来自哪里**：两处，都来自 owner 边界，不是本需求造成的。

1. 桌台区与生产标签分别在「门店桌台与二维码」「门店商品管理」两个页面维护，终端页面只能选、不能建；门店还没建桌台区或生产标签时，范围候选为空。候选为空时，页面应当说明要先去哪个页面维护，而不是只显示一个空的选择框（与桌台需求第 R-6.6 条同一口径）。
2. 那两个维护页面各自受门店经营规则开关约束（桌台区的新建受「是否启用桌台和二维码管理」约束，见 `StoreServicePointService.requireCommand`；生产标签的新建受「是否启用商品、库存和菜单管理」约束，见 `CatalogInventoryWorkspaceCommandTokens`）。所以门店关着这些开关时，「先去那个页面维护」的指引会把人带到一个显示未开启的页面。终端页面本身不关联开关（R-9.8），但范围值的来源间接依赖开关，这是已知后果。

**是否有更少选择的做法**：范围与场景都是「勾选」，没有更少的形态；场景的订单类型是 D-12 明确要的配置，不能省。

### 8.5 「不合理」的配置照样能存

- 前台收银机的厨打②和另一台终端的厨打都选了「酒水」：酒水会出两张制作单，同一杯可能做两遍。**系统不拦**，管理员发现后去掉其中一个即可（D-9）。
- 出品口勾了传菜单却没挑打印机：这张纸不会打。**系统不拦**。

- 作废桌台区、生产标签时显示「被多少个终端引用」（D-25）。这偏离仓内标准「删除确认必须给出当前引用数」，由 Dexter 明确裁定不做：终端详情里如实显示引用对象已作废（R-3.4、R-3.9），运行时由终端自己判断实体是否有效，规则不需要变化。另注：平台现有这两处作废确认，连它们自身的引用（区下的桌台、挂了标签的商品）也没有给数（区域作废只提示保留历史资料；生产标签的关联商品数在 `CatalogProductionTagOwnerService` 里固定为 0）。

## 11. 交详设的事项

1. **owner 归属**：本稿建议终端规则成为一个**新的业务 owner**，不并入 organization 或 catalog。主要理由是职责：终端的功能、范围与打印机配置，既不属于门店的组织结构，也不属于商品；将来的激活与设备绑定也挂在它上面。依赖方向只是次要考虑：终端要同时引用组织域的桌台区与商品域的生产标签；现在 catalog 依赖 organization（`apps/backend/catering-business-server/modules/catalog/build.gradle.kts`），organization 不依赖 catalog。放进 organization 的话，直接依赖 catalog 会形成循环，但可以用 organization 自有的查找接口反转——仓内已有先例：`organization/api/QrChannelEligibilityLookup` 由依赖 organization 的经营渠道模块实现（`QrChannelEligibilityService`），organization 经 `ObjectProvider` 使用它。所以依赖方向不是决定性理由。模块命名与边界由详设确定。
2. 硬约束登记的 contract 文件形态、生成物（后端校验、前端字典与业务名称），以及与现有 contract 生成链的接法。
3. 表结构、唯一约束（终端名称在未作废范围内唯一、激活码集团空间内唯一且含作废、打印机名称在终端内唯一、USB 与蓝牙设备标识在终端内按连接方式唯一）与索引。
4. 页面 key、写权限 key 的拼写；导航分组与动作分组的落点；页面描述与禁用别名。
5. 写命令的形态（整终端一次保存还是分块保存）与幂等；无论哪种，都要满足 R-7.1 的整体校验与终端级版本。
6. 激活码生成的实现（安全随机、撞码重试、并发下的唯一保证）、手填码撞码时不替换的冲突处理（D-29）与测试装配里的可控生成来源（V-14、V-15）。Codex 第 1 轮 review 提示：唯一约束冲突后，不能在已经失败的 PostgreSQL 事务里直接重试，要用能让事务继续的冲突探测或保存点。
7. 「全部桌台区」「全部生产标签」这两个选择的存储表示；读取终端时怎样给出被引用桌台区、生产标签的当前状态与类型。**仓内事实**：organization 现有的 `StoreServicePointOwnerApi` 只有按门店分页列区域的读取，没有按 ref 读取区域（含已作废）的读取，要满足 R-3.4 的旧引用读回需新增一个窄读取；catalog 已有按 ref 读回生产标签的 `readTagReferencesByRefs`。
8. 跨 owner 引用的校验与读取的数据库访问形态，遵循 `project-memory/decisions/http-crud-efficiency-design-redlines.md`。
9. 审计实体类型、字段键与按段摘要的形态（R-9.9）。
10. 页面的信息架构与交互：列表形态、详情与编辑的抽屉、分步新建、范围与场景的配置形态、厨打实例的区分方式、§7.5 列出的更短路径；复用 `libraries/frontend/admin-ui-foundation` 的共享能力。
11. backend-acceptance 场景与前端 focused test 的清单。
12. 种子数据：D-29 已定 DEV 种子使用固定激活码，经新建的手填路径写入；造哪些终端样例由详设定。
