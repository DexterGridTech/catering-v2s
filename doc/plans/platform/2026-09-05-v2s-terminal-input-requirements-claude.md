## 1a. ⚠️ 为什么不直接用系统键盘（自审第 8 轮补）

本文早前版本从「Dexter 要一个和系统键盘行为一致的虚拟键盘」直接进入规格，
**把质量标尺当成了目的**。这留下一个明显的反问无人回答：
既然标准是「和系统键盘无法区分」，那为什么不就用系统键盘？

动因不在「一致」，一致只是**替代品的合格线**。真正的动因有三条：

| # | 动因 | 系统键盘为什么不行 |
| --- | --- | --- |
| 1 | **沉浸式全屏的完整性** | 本仓终端跑**甲档沉浸式全屏**（见 `2026-09-05-v2s-terminal-ui-capability-and-experience-requirements-claude.md` 第 51 行；当前阶段**不做** Lock Task）。第三方 IME 会自绘工具条（设置、剪贴板、表情、语音），每一个都是脱出沉浸式外壳的口子；而甲档**没有 lockTask 兜底** |
| 2 | **键位形态** | 金融键盘要大按键（戴手套、快速盲打）。系统数字键盘既不是 POS 键位，尺寸也不受我们控制 |
| 3 | **双屏** | IME 绑定在获焦窗口所在的 display 上。副屏（`TerminalPresentation`）上的输入，系统 IME 的落点不受我们支配；当前产品因此不把副屏系统 IME 作为能力前提 |

⚠️ **由此定一条默认值（Dexter 授权代裁）**：终端业务输入**默认走虚拟键盘**；
用系统键盘是**显式例外**，且须写明理由。
⚠️ 当前已认定的系统 IME 例外是**主屏中文字段**（自绘键盘无 IME 引擎）——
理由与后果见 §5.0，主屏 inset 前置依赖见 §10a。副屏当前业务路径不使用系统 IME，年龄字段必须使用虚拟键盘。
Dexter 的「每个 input 自选」裁定给的是**能力**，不是「随便选」——
若默认反过来，实施方会因为省事而普遍走系统键盘，
沉浸式外壳想拦的事就在 sample 里天天发生。

### 1a.1 ⚠️ 两种键盘共存，切换语义必须显式规定

「每个 input 自选」意味着同一个屏上会有两类输入框。**四种转移里有两种今天是错的**：

| 从 → 到 | 应有行为 | 风险 |
| --- | --- | --- |
| 虚拟 → 虚拟 | 改绑，不关不重开 | 已在 §1b.4 规定 |
| 系统 → 系统 | 系统自理 | 无 |
| **系统 → 虚拟** | 系统 IME 必须**收起**，虚拟键盘升起 | ⚠️ **不会自动发生** |
| **虚拟 → 系统** | 虚拟键盘必须**收起**，系统 IME 升起 | ⚠️ **不会自动发生** |

⚠️ ✅ 亲验 `react-native/Libraries/Components/TextInput/TextInput.js:916,935-936`：
`showSoftInputOnFocus` 只控制**获焦时要不要唤起** IME，
**不负责关掉已经开着的** IME。⇒ 焦点从系统键盘输入框移到虚拟键盘输入框时，
IME 不会自己消失 —— **两个键盘同时在屏上**，且内容区被压两次。

⇒ 硬要求：这两种转移必须显式处理。收起系统 IME 用 RN 标准的
`Keyboard.dismiss()`（✅ 亲验 `Libraries/Components/Keyboard/Keyboard.d.ts:64` 有此 API），
不引第三方。判据：构造一屏两类输入框，来回点，断言**任一时刻至多一个键盘可见**。

### 1a.2 ⚠️ `inputMode` 会静默压掉 `showSoftInputOnFocus`

✅ 亲验 `TextInput.js:935-936` 原文：

~~~
showSoftInputOnFocus={
  inputMode == null ? showSoftInputOnFocus : inputMode !== 'none'
}
~~~

⇒ **只要传了 `inputMode`，`showSoftInputOnFocus` 就被整个忽略。**

§8b 正要给 `PrimitiveInput` 加 `showSoftInputOnFocus`。
⇒ 硬要求：`PrimitiveInput` **不得同时暴露 `inputMode`**；
若将来要暴露，必须由控件自己收敛成一个语义（选虚拟键盘即 `inputMode='none'`），
不得把两个 prop 都摊给调用方 —— 那是个静默失效的坑，
表现是「明明写了不弹系统键盘，系统键盘照弹」，而且看代码看不出来。

## 1b. ⚠️ 本专题的一句话定义（Dexter 2026-09-05）

> 「不用完全参考 POC 的做法，其实我就是想要一个**能和系统键盘行为一致的虚拟键盘**。」

**这是本文的第一原则，优先级高于 POC 的任何形态。**

### 1b.1 「行为一致」具体指什么

从业务代码的角度看，**用虚拟键盘和用系统键盘应当无法区分**：

| 行为 | 要求 |
| --- | --- |
| 出现与消失 | 聚焦输入框即出现，失焦即消失 |
| 字符插入 | 插在**光标位置**，不是简单追加 |
| 退格 | 删**光标前**一个字符；有选区则删选区 |
| 光标与选区 | 输入框正常显示光标；输入后光标位置正确 |
| 大小写 | 字母布局支持 shift／caps |
| 完成键 | 与系统键盘的完成键语义一致 |
| 业务侧回调 | 业务代码**不需要知道**用的是哪种键盘 —— ⚠️ 但**不是**「`onChangeText` 逐字触发」，见下方边界 |

⇒ **业务部件写法不变**：它只声明「这个输入框用哪种键盘」，其余与今天一样。

### 1b.1a ⚠️ 「行为一致」的适用范围：只管用户可见行为，不管应用侧回调

自审第 1 轮发现原稿自相矛盾：上表曾写「`onChangeText` 照常触发」，
而 §3 又规定只在失焦与完成键时提交。两者**不能同时成立** ——
若业务回调逐字触发且业务据此派命令，性能目标当场归零。

⇒ **划清范围**：

| 面 | 是否与系统键盘一致 |
| --- | --- |
| **用户可见行为**（出现消失、光标、插入、退格、大小写、页面变矮） | ✅ **必须一致**，这是本专题的第一原则 |
| **应用侧回调契约** | ❌ **有意不同**：业务部件只收到**已提交**的值，收不到编辑中的逐字变化 |

⚠️ 这不是妥协，是 Dexter 裁定的核心：「提交的表单才应该发出 command，编辑中的不应该」。
⇒ 控件对业务暴露的回调应命名为**提交语义**（如 `onCommit`），
**不得**命名为 `onChangeText` —— 那个名字会诱导使用方以为它逐字触发。

### 1b.2 这条定义砍掉了 POC 的一大半复杂度

POC 的 FancyKeyboard 是**另一种交互模型** ——
弹出浮层、在浮层里编辑一个 `editingValue`、显示 `promptText`、
比对 `hasChanges`、按确认才写回。那不是系统键盘的行为，是一个**编辑对话框**。

⇒ 本轮**不做**：浮层内的独立编辑区、`promptText`、`hasChanges`、
键盘上的确认／取消按钮、抖动提示。

⇒ 用户看到的是：点输入框 → 键盘从下方出现 → **就在原来的输入框里打字** → 点别处收起。
和系统键盘一模一样。

### 1b.3 ⚠️ 页面变化：收缩模型（原题「照 `adjustResize` 做」，立论已被 §1b.3a 更正）

> Dexter：「系统键盘导致页面是什么变化，虚拟键盘就应该一样。」

✅ 亲验本仓现状：`assembly/android/sample-terminal/android/app/src/main/AndroidManifest.xml`
第 19 行的 MainActivity 声明 `android:windowSoftInputMode="adjustResize"`。

⚠️ **但这是「声称」，不是「行为」（自审第 13 轮更正，本条推翻本节原立论）**：

✅ 亲验 `adapter/android/dual-screen/android/src/main/java/.../TerminalDualScreenActivityHandler.kt`
的 `applyImmersiveWindow()`（第 359-374 行），它在每次 `onWindowFocusChanged(hasFocus=true)`
时无条件施加：

| API | 施加的东西 | 后果 |
| --- | --- | --- |
| 全部 | `FLAG_FULLSCREEN` ＋ `SYSTEM_UI_FLAG_LAYOUT_FULLSCREEN` ＋ `LAYOUT_HIDE_NAVIGATION`（第 359、364-365 行） | 窗口按**全屏**布局，铺到系统栏之下 |
| 30+ | **`window.setDecorFitsSystemWindows(false)`**（第 368 行） | ⚠️ 框架**不再**替内容避让 inset，`adjustResize` **被忽略** |

⇒ **`adjustResize` 在本 app 上是死声明。**

⚠️ **分清两件事（Codex 评审 S-1，已采纳）**：

| 陈述 | 档位 |
| --- | --- |
| 代码无条件施加全屏标志与 `setDecorFitsSystemWindows(false)` | ✅ **仓内事实**，已亲验 |
| 全屏窗口会忽略 `SOFT_INPUT_ADJUST_RESIZE` | ✅ **外部事实**，见 Android `WindowManager.LayoutParams` 官方文档 |
| **这台机器上系统键盘的真实表现就是覆盖** | ⚠️ **推论，本轮未运行 Android，未证** |

⇒ 前两条足以支撑「不能拿 manifest 那行声明当行为依据」这个结论，
也足以支撑下面的收缩模型裁定；但**第三条必须实测**，不得当已验事实引用。

⚠️ 另一条边界：若将来移除全屏标志或改变 edge-to-edge 配置，
上述前提就变了，本节结论须重开。

⚠️ 这是「声称 ≠ 行为」的典型：manifest 那一行是声明，
真正决定行为的是运行时那几个沉浸式标志。原稿只读了前者就下了结论。

### 1b.3a ⚠️ 由此必须重新裁定「对齐谁」（自审第 13 轮）

「行为一致」原则在这里失去了参照物 —— 本机的系统行为是覆盖，而覆盖是差的。

⇒ **代裁（Dexter 授权，原则「以最真实用户场景出发」）：不照抄坏行为，两边一起修正。**

| 决定 | 内容 |
| --- | --- |
| 虚拟键盘 | **维持收缩模型**（§1b.6 已按此设计）。⚠️ 但**理由改了**：不再是「系统就是这样」，而是「POS 上输入框被盖住不可接受」，这是**有意选择** |
| 系统键盘（仅当前允许的主屏路径） | ⚠️ **必须补主屏 IME inset 处理**，让它也收缩。否则 §5.0 划给系统键盘的主屏**姓名**字段会被真实盖住，且无自动恢复 |
| 副屏系统 IME | **不作为当前产品能力**。副屏年龄字段走虚拟键盘；Presentation 的系统 IME 可见性不再是 CP-0 或本批业务验收前提。未来若副屏出现中文/系统 IME 字段，必须另开产品裁定与实跑验证 |
| 表述 | 交付时不得再写「与系统键盘一致所以照 `adjustResize`」；应写「本机沉浸式配置下 `adjustResize` 不生效，主屏系统 IME 与各 surface 的虚拟键盘按收缩模型对齐；副屏当前只走虚拟键盘」 |

⚠️ **这是本专题的前置依赖，owner 不在 `ui/base/input`**：
`setDecorFitsSystemWindows(false)` 之后，`WindowInsets.Type.ime()` 必须由 app 自己消费，
属 adapter／assembly 层。⇒ **在它落地之前，「两种键盘行为一致」这句话不成立**，
不得在本包的交付里声称已一致。

⚠️ 若不修系统键盘那侧，退而求其次的**唯一自洽**做法是：
把 §5.0 划给系统键盘的中文字段也收回来（即本轮干脆不做中文录入），
而不是留着一个会被盖住的姓名框。**两者择一，不得两边都不做。**

⇒ 收缩模型的行为是**窗口可用高度收缩、内容区随之重排**
（可滚动内容自己滚，固定内容自己压缩）。

⇒ **虚拟键盘照做**：它占据 surface 底部一段高度，
**内容区的可用高度相应减少**，布局按减少后的高度重排。

⚠️ 由此 §9 原来的 Q-C（顶起／滚动／预留区域）**不再是开放选项** ——
答案就是**收缩模型**（§1b.3a）。业务页面**怎么排布**变矮后的可用区，
是它自己的布局问题，与键盘无关。

⚠️ **但「焦点输入框滚入可见区」不是业务页的事，必须由本包做（自审第 7 轮补）**：
上面那句「可滚动内容自己滚」描述的是 Android **在 `adjustResize` 真正生效时**的行为 ——
窗口收缩后由焦点视图的 `requestRectangleOnScreen` 链驱动祖先滚动容器把它滚进可见区，
平台自带，**不是业务页写的**。

⚠️ 而本机连这一条也拿不到：§1b.3a 已证 `adjustResize` 在沉浸式配置下失效
⇒ 那条平台链**根本不会跑**。这使下面这条要求从「补齐」变成「唯一来源」。

虚拟键盘只是个 React view，把内容区压矮**不会触发任何滚动**。
若不补，底部的输入框会被直接切出可见区 —— 用户打字看不见自己在打什么。
这是自制键盘最典型的翻车点，也直接违反 §1b「用户可见行为必须一致」。

⇒ **硬要求**：键盘出现（或焦点切换到新输入框）后，
**若该输入框存在可滚动祖先**，必须把它滚进收缩后的可见区；
**若不存在可滚动祖先**，则不做任何事 —— 这也与系统一致（系统同样滚不动）。

⚠️ 判据可证伪：构造一个内容高度超过收缩后可用高度、且底部有输入框的页面，
点该输入框，断言其在键盘出现后**仍完整可见**。
把滚动逻辑摘掉该判据必须变红。

⚠️ 机制留给详设。但需求上先钉死两件事：**责任在本包不在业务页**（业务页无从知道
自己被切了）；**RN 自带的那条链在此不生效** —— RN 的 `ScrollResponder`
是由 `Keyboard` 原生事件驱动的，虚拟键盘不发这类事件，不得假设它会自动生效。

⚠️ 不得实现成「浮层盖在内容之上」。
⚠️ **理由已按 §1b.3a 更正**：不是「与本仓声明的 `adjustResize` 不符」——
那句声明在沉浸式配置下已失效；真正的理由是**盖住输入框在 POS 上不可接受**，这是有意选择。

### 1b.4 ⚠️ 焦点跟随：键盘绑定当前焦点，不绑定打开它的那个输入框

> Dexter：「用户最开始点了 input1 弹出键盘，输入变化 input1；这时点了 input2，
> 键盘操作后输入变化应该是 input2。」

这也是系统键盘的行为。⇒ 三条硬要求：

| # | 要求 |
| --- | --- |
| 1 | 每个 surface **最多一个**键盘实例，不是每个输入框一个 |
| 2 | 键盘作用于**当前焦点输入框**；焦点切换即改绑，**不关闭、不重开** |
| 3 | 每个输入框各自保有自己的 `value`；切走不丢内容 |

⚠️ 切换焦点时**不得**把 input1 的内容带到 input2，
也不得因为切换而丢弃 input1 已输入的内容。

⚠️ **光标位置由点击位置决定**（自审第 1 轮更正）：原稿写「切走再切回光标位置保持」，
那**不是**系统键盘的行为 —— 系统上重新点入某个输入框时，光标落在**点击处**。
按「行为一致」原则，此处应随系统，不做额外记忆。

⚠️ 若 input1 与 input2 声明了**不同布局**（例如一个金融、一个字母），
切换焦点时键盘布局须随之切换 —— 同样是系统键盘的行为（`keyboardType` 变化时系统键盘会换）。

### 1b.6 ⚠️ 键盘挂载位置：与内容区**并列**，不是盖在其上（Q-B 裁定）

Dexter 授权按「最还原系统键盘行为」裁定。⇒ 结论如下，
并且它**推翻了本文早前的一句话**。

**我早前写过「键盘必须盖在所有 layer 之上，z 序是 `SurfaceRoot` 的职责」——那是错的。**
那是覆盖式的思路。本专题采用的是**收缩模型**（§1b.3a 代裁）：
键盘出现时**整个可用区变矮**，区域里的一切 —— 屏、对话框、alert —— 全都在变矮后的区域内重排。

⇒ 要还原它，键盘必须与**整个 surface 内容区并列**，而不是叠在某一层之上：

~~~
SurfaceRoot
├── 内容区（flex:1，随键盘出现而变矮）
│   ├── children
│   ├── ScreenContainer
│   └── LayerStack        ← 层也在变矮后的区域内重排，与系统键盘一致
└── 底部区（键盘占据）
~~~

⚠️ 关键推论：**`LayerStack` 也必须在变矮的区域内**。
若键盘只压缩 `ScreenContainer` 而让 alert 层仍按原高度布局，
就与系统键盘的行为不一致 —— 系统键盘会把对话框一起挤上去。

**依赖方向由此确定**：`ui.base.input` 依赖 `ui.base.render`，而 `render` **不依赖** input。
⇒ `render` **不得** import `input`。

✅ 亲验（自审第 14 轮换成实证）：`apps/terminal/ui/base/input/package.json`
的 `dependencies` 已含 `@catering-v2s/ui-base-render`（该包壳已存在，
目前只有 `src/index.ts`／`moduleName.ts`／`dependencies.ts` 三个文件，尚无实现）。

⇒ 形态是：

| 包 | 职责 |
| --- | --- |
| `render` | `SurfaceRoot` 提供一个**通用底部区插槽**与「内容区 flex:1」的布局。它只知道有个底部区，**不知道那是键盘** |
| `input` | 提供键盘宿主组件与输入控件 |
| `ui/integration` | 装配：`createSurface` 时把键盘宿主填进底部区插槽 |

⚠️ 插槽必须是**通用的**，不得命名为 `keyboardSlot` 一类 ——
一旦名字里出现键盘，`render` 就在语义上知道了 input 的存在，边界又糊了。

⚠️ **只有插槽是不够的，还差一个包裹点（自审第 7 轮补）**：
✅ 亲验 `ui/base/render/src/components/SurfaceRoot.tsx` —— 今天
`children`、`ScreenContainer`、`LayerStack` 三者是**同一个 `View` 下的兄弟**，
`children` 并不包裹另外两个。

而输入控件长在 `ScreenContainer` 与 `LayerStack` **里面**。
若只加底部插槽、把键盘宿主填进去，那些输入框**够不到宿主的 context** ——
焦点注册、按键回写全都接不上。

⇒ `SurfaceRoot` 必须让装配方同时做到两件事：

| # | 能力 | 今天为什么做不到 |
| --- | --- | --- |
| 1 | 用自己的 Provider **包裹整个内容区子树**（含 `ScreenContainer` 与 `LayerStack`） | `children` 是兄弟，包不住 |
| 2 | 在内容区**下方**放一个兄弟节点 | 没有底部插槽 |

⚠️ 具体 prop 形态（两个 prop、还是一个 `frame`-式 render prop、
还是把 `children` 改成接收内容区的函数）留给详设裁定；
需求只钉「这两件事都必须可做」与「`render` 仍不得 import `input`」。

⚠️ 这条不补的后果是可预期的：实施方会发现接不上，
最省事的补法就是让 `render` 直接 import `input` —— 正好撞上上面那条禁令。

### 1b.7 实现含义：键盘驱动的是输入框的 value 与 selection

要做到「插在光标位置」，键盘必须操作**输入框的值与选区**，
而不是维护一个平行的编辑串。

⇒ 输入控件持有 `{value, selection}`，键盘按键改的是这两个；
`TextInput` 由它们受控，并经 `onSelectionChange` 回写选区。

## 2. ⚠️ 规则修订：v13 §6.9「表单值不得存 `useState`」需精确化

### 2.1 Dexter 的裁定

> 「提交的表单才应该发出 command，而不是编辑中的，所以暂存＋确认提交才是最合理的。」

### 2.2 原规则误伤了什么

v13 §6.9 禁止清单第 2 条禁「表单值存组件 `useState`」（`requestId` 除外）。
它要防的是**表单的真相源跑到组件里** —— 那样状态就不可跨 surface、不可持久化、不可被 actor 看见。

但它把**编辑期的暂存缓冲**也一并禁了，而那是两回事：
暂存缓冲不是真相源，它的寿命只有一次编辑，确认即消灭。

### 2.3 修订后的表述

⚠️ **本节已按自审第 11 轮重写** —— 原文成稿于 Q-E 之前，
写的是「提交进 uiVariables」，而 §9a 裁定值走**命令 payload**、kernel 侧不读 uiVariables。
照原文实施，写出来的正是 Dexter 禁掉的那种东西。

**禁止**：已提交表单值的**真相源**存在组件本地。
真相源是**业务 slice**（提交后由命令 payload 落进 `pending`／`members`），
**不是** uiVariables，也不是组件。

**允许**：编辑期的**暂存缓冲**存在控件本地，但必须同时满足三条 ——

1. 提交时**一次性**读出、进**命令 payload**；取消则整体丢弃；
2. **不得**成为任何其它部件的读取源；
3. 控件卸载时缓冲随之消失，不得跨挂载存活。

⚠️ 判据要能区分两者：反例是「把暂存缓冲暴露给别的部件读」或「不经提交就有人读到编辑中的值」。

### 2.3a ⚠️ 缓冲**放在哪个组件**要钉死（自审第 11 轮）

§9a.3 只说「组件本地」，没说是**输入控件**还是**表单**。这留了个会踩红性能判据的口子：

`MemberForm` 有姓名与电话两个字段，提交按钮要同时拿到两个值 ——
最自然的写法是表单持一个 `useState<{name, phone}>`。
⇒ 敲电话会连带重渲染姓名与整张表单，**正好踩红 §6 的 PF-2**。

⇒ **硬要求**：编辑期的每次按键，**只允许当前获焦的那一个输入控件重渲染**。
表单需要在**提交那一刻**拿到全部字段值，但**不得因此在编辑期订阅它们**。

⚠️ 具体形态（表单持 ref、输入控件注册进表单、还是别的）留给详设；
需求只钉这两句 —— 它们互相拉扯，是这一处最容易做错的地方。

⚠️ **但只钉这两句留得太松（Codex 评审 S-2，已采纳）**，再补四条**结果性**要求，
形态仍不预设：

| # | 要求 | 反例 |
| --- | --- | --- |
| 1 | **提交读到的必须是原子快照** —— 一次读齐全部字段的**当前**值 | 提交时读到某个字段的**过期闭包**值：用户改了电话又立刻提交，进命令的还是旧电话 |
| 2 | **表单容器不得订阅字段值** | 容器一订阅就重渲染，直接踩红 PF-2 |
| 3 | **输入卸载时其草稿必须注销**，不得留在表单的登记里 | 字段被条件渲染移除后，提交仍带上它的旧值 |
| 4 | **提交与卸载的竞态有确定结果** | 提交进行中部件被卸载，出现半条命令或读到已注销的字段 |

⚠️ 第 1 条是本节的**核心**：§2.3 的三条约束（一次性、不外读、卸载即消失）
都没有覆盖「读到的是不是最新值」。这正是「每个字段各自局部 state ＋
提交时读闭包」这种最自然写法的失败点。

⚠️ 已被 §2.3 覆盖、此处不重复：外部部件不得读草稿（§2.3 第 2 条）、
卸载即消失（§2.3 第 3 条）。

### 2.4 连带修订：副屏不再逐字镜像（Dexter 已确认）

编辑期不派 command ⇒ store 里没有编辑中的值 ⇒ **副屏无可镜像之物**。

⚠️ **自审第 11 轮更正**：原文写「须改为**每字段确认后同步**」——
那是 §3 已废除的**逐字段提交**模型的残留。
Q-E 之后唯一的提交动作是提交按钮，中途没有任何「每字段确认」。

⇒ 正确口径：v13 §4.3 **场景 5 整个取消**（该文已按此改毕，✅ 亲验其场景表第 5 行）。
副屏在店员录入全程**无变化**，直到店员点提交才切到 `customer-member{mode:'confirm'}`（场景 6）。

⚠️ 这不是能力退化：顾客看到的从「半个名字在跳」变成「一次性的完整待确认值」，
体验更好；写入次数从每字符一次降到每次提交一次。

## 3. ⚠️ 暂存是**输入控件**的性质，不是键盘的性质

Dexter 2026-09-05 更正：**用不用虚拟键盘由每个 input 自己决定**；
业务界面上的普通 input 仍可用系统键盘。

⇒ 由此推出一条设计原则：

**暂存 ＋ 确认提交的模型必须与键盘种类无关。**

理由是 Dexter 自己的原则 ——「编辑中的不该发 command」说的是**编辑与提交的区别**，
不是**哪个键盘**的区别。系统键盘输入同样是编辑，同样不该逐字派命令。

⇒ `ui/base/input` 提供的是**带暂存语义的输入控件**；
虚拟键盘与系统键盘只是两种**录入方式**，接在同一套暂存模型下。

⚠️ **本节原稿已被 §9a 的裁定推翻**（自审第 6 轮发现）。

原稿写「失焦与完成键都触发提交」，那是**逐字段提交**模型。
而 Dexter 2026-09-05 裁定：**只有点击提交按钮才取值发命令**。

⇒ **不存在「逐字段提交」这回事**：

| 事件 | 做什么 |
| --- | --- |
| 失焦 | 只收起键盘、移交焦点。**不发任何命令** |
| 焦点切换 | 改绑键盘。**不发任何命令** |
| 键盘完成键 | **推进焦点到下一字段**；已是末字段则**关闭键盘，不提交** —— 见 §3a（自审第 9 轮更正：原文「末字段等同于点提交」与 §3a 直接冲突，Dexter 裁的是关闭键盘） |
| **提交按钮** | **唯一**从组件读值并派命令的动作 |

### 3a. 完成键的语义（Q-F 裁定）

| 情形 | 行为 |
| --- | --- |
| 后面还有字段 | **推进焦点到下一字段**，键盘保持打开、按需切换布局 |
| 已是末字段 | **关闭键盘**。⚠️ **不触发提交** |

⚠️ 末字段不提交是有意的：POS 上误触发提交的代价高，
提交必须是店员在提交按钮上的**明确动作**。

⚠️ 这与系统键盘略有差异（系统上末字段的 `returnKeyType="done"` 常配 `onSubmitEditing` 提交），
属**有意偏离**，理由如上。⇒ 交付时不得表述为「与系统键盘完全一致」，
应写「除末字段不提交外与系统键盘一致」。

**字段顺序怎么来**：沿用 RN 既有惯例 —— 由**表单**声明链（每个输入声明它的下一个，或表单给出顺序），
不是系统自动推导。RN 本来就没有自动 tab 序，这不是新概念。

⚠️ 取消语义由**业务部件**提供（如表单的取消按钮），不由键盘提供 ——
系统键盘也没有「取消」这个概念。

## 4. 第三方调研结论：可用的轮子不存在，但有可借的设计

Dexter 要求「不重复造轮子」。✅ 本轮联网调研结论如下：

| 库 | 平台 | 布局 | 状态 | 判定 |
| --- | --- | --- | --- | --- |
| `react-simple-keyboard` | **DOM only** | 多布局、可配置、成熟 | 非常活跃 | ❌ 真实 RN 上跑不了 |
| `react-kiosk-keyboard` | DOM only | kiosk 导向 | — | ❌ 同上 |
| `rn-screen-keyboard` | RN | **仅数字** | 5 星、10 次提交 | ❌ 过薄 |
| `react-native-screen-keyboard` | RN | 自定义键位 | 3 年未更新 | ❌ 停更 |
| `react-native-virtual-keyboard` | RN | 数字 | 3 年未更新 | ❌ 停更 |
| `react-native-keyboard-controller` | RN | — | 活跃、支持 Fabric | ⚠️ **本轮结论已改，见 §4a**：原判「解决的是系统键盘管理，不是自绘键盘」——而 §1b.3a 刚证明我们**正好多出一个系统键盘管理的活** |

**格局：好用的都是 DOM 的，RN 的都是玩具。** 而我们要 Android 与 Web 双端同一套形态，
DOM 方案直接出局 —— 否则两端两套实现，正是一直在防的分叉。

⇒ **自建实现，但借两样成熟的东西：**

**其一，借 `react-simple-keyboard` 的布局数据格式，不借实现。**
它的格式是被验证过的声明式规范：布局名为键、值为字符串数组、每串一行，
用 `{bksp}` 一类占位符表达功能键，另有 display 映射人类可读名。
⇒ 采用该格式可省掉自己设计格式的弯路，且将来换实现时布局数据可原样搬走。

**其二，系统键盘的抑制用 RN 标准能力**，不引第三方：
`TextInput` 的 `showSoftInputOnFocus={false}`。
⚠️ 只对**选择了虚拟键盘**的 input 生效，不是全局。

### 4a. ⚠️ `react-native-keyboard-controller` 需重新评估（自审第 14 轮）

上表把它以「不是自绘键盘」驳回。**驳回理由在 §1b.3a 之后不再成立** ——

| **新增一种功能键类型**（如 `{tab}`、`{currency}`） | ✅ 需要，且属于控件的契约变更 |

⇒ 判据自带反例：新增一个**仅由已有键类型组成**的布局若需要动 `input` 的组件源码，即违反。
⚠️ 功能键类型的集合应在设计阶段一次定清（至少 `{bksp}`／`{shift}`／`{enter}`／`{space}`），
之后新增算契约变更，不算「加一份数据」。

## 6. 性能：可证伪的判据

Dexter 的唯一强要求是 UI 性能与用户体验。⇒ 判据必须能红：

⚠️ **本表已按自审第 9 轮重写。** 原表五条全是**结构性**判据（命令流量、动画驱动），
**没有一条测输入延迟** —— 而那恰是 Dexter 唯一强要求的那件事。
按原表，一个架构干净但打字明显掉帧的键盘可以全绿通过。

⚠️ **编号用 `PF-`（performance）而非 `P-`**：`P-N` 在 sample 需求文档里
已是**设计模式判据**的命名空间（P-9、P-11 等），两份文档会一起读，不能撞。

| # | 判据 | 反例（必红） |
| --- | --- | --- |
| PF-1 | ⚠️ **按键时，键盘按键组件零重渲染** | 把当前值放进所有按键都订阅的 context／state，则每敲一次全部按键重渲染，必红 |
| PF-2 | ⚠️ **按键时，只有当前获焦的那一个输入框重渲染** | 让同屏其他输入框或表单容器跟着重渲染，必红 |
| PF-3 | **编辑期间零 command 派发** | 编辑中出现任意一次 dispatch，必红 |
| PF-4 | **一次提交恰好一条命令** | 一次提交出现两条或零条，必红 |
| PF-5 | 取消后 uiVariables **一字未变** | 有任何写入，必红 |
| PF-6 | 键盘显隐动画**不跑在 JS 线程上** | 改成 JS 线程驱动，必红。⚠️ **判的是结果不是 API（自审第 14 轮）**：原文写「走 native driver」是 RN `Animated` 的说法，而 ✅ 亲验本仓 `ui/integration/sample-console` 已依赖 **`react-native-reanimated` 4.5.1**（`ui/base/input` 尚未声明它）。⇒ 判据按「动画不占 JS 线程」写，`Animated` 的 `useNativeDriver` 与 reanimated 都可满足；**优先用已有依赖**，不为此引新库 |

### 6.1 ⚠️ 代理判据证明不了目标（Codex 评审 M-1，已采纳）

⚠️ **先说清 PF-1～PF-6 覆盖不到什么**，否则会拿它们全绿去宣称「已满足 UI 性能要求」：

| 漏网情形 | 为什么代理判据抓不到 |
| --- | --- |
| 只重渲染一个组件，但 `onCommit`／按键路径里做了同步重活 | 重渲染计数为 1，PF-1／PF-2 全绿 |
| 重渲染的组件多但个个极轻 | 计数不达标而用户其实无感 —— 假红 |
| 动画不占 JS 线程，但布局或 native bridge 掉帧 | PF-6 全绿 |

⇒ **PF-1～PF-6 是架构保护，不是性能证明。** 二者不可互相替代。

⇒ **补两条，但不建采集管线**（本阶段要求分钟级、零基建）：

| # | 判据 | 怎么落 |
| --- | --- | --- |
| **PF-7** | 在 Expo Web 段与真机段各做一次**连打观察**：按住／快速连点一串字符（不少于 20 个），字符出现必须跟得上手，无可见滞后或成批跳出 | 跑段人工观察，不建 harness。⚠️ 这是**目前唯一直接面向延迟**的判据 |
| **PF-8** | 按键处理路径上**不得有同步重活**（正则回溯、大数组重建、逐键 measure、逐键序列化） | 评审逐行看按键路径，不是机器判据 |

⚠️ **PF-7 是主观判据，我明确承认这一点。** 但它比「有 p95 数字」更适合当前阶段：
建一套帧率／延迟采集是真基建，与「一人 ＋ 两 AI 快速迭代」不成比例。
⚠️ 若将来 PF-7 反复出现争议，再升级为带数字的判据 —— **那时才建，不提前建**。

⚠️ **交付表述硬要求**：PF-1～PF-6 全绿只能说「架构上没有已知的逐键放大」，
**不得**说「UI 性能达标」。后者要 PF-7 支撑。

⚠️ **PF-1／PF-2 是延迟的可测代理**：键盘按键数量在 30 上下，
「每敲一个字符重渲染 30+ 个组件」正是 POC 的病
（✅ 亲验 `FancyKeyboardContextV2.tsx` 拆了三个 context 想治它，
又在第 65、228-231、234 行保留一个合并的 legacy context 把治疗抵消掉）。
用重渲染计数而不是设备计时，是为了让判据能落在测试里而不是靠手感。

⚠️ **PF-4 的口径（自审第 9 轮更正）**：原文写「每个**字段**一条命令」并注
「多字段表单会有多条，那是正常的」—— **反了**。
✅ 亲验 `kernel/feature/sample-member-registry/src/commands.ts:7`：
`submitMemberCommand<Readonly<{name: string; phone: string}>>`
是**一条命令带两个字段**。新模型下一次提交就是一条命令，多字段不产生多条。

⚠️ **原「值未改变时不提交」一条已删**：它判的是**失焦触发提交**，
而 §3 已明确「失焦不发任何命令」。留着还有二义 ——
会被读成「提交按钮在内容没变时应当空转」，那是另一回事，且多半是错的：
店员按了提交就该提交。

⚠️ ✅ 亲验现状作为对照：`MemberForm` 目前每敲一个字符调
`dispatchWithRequestId(setUiVariablesCommand, …)`，而该命令 `visibility: 'public'`，
按 P-11 必须带 `requestId` ⇒ **每字符一条命令、一次 ledger 写入、两棵 surface 树通知、
一次持久化 debounce 重置**。本专题要把这条链从「每字符」降到「每字段一次」。

## 7. 双屏纪律

### 7.0 ⚠️ 原纪律已被 Dexter 2026-09-05 的新场景推翻

原文写：「虚拟键盘只出现在 PRIMARY，永不出现在 SECONDARY。副屏是顾客视角，**顾客不录入**。」

> Dexter 2026-09-05：「店员输入用户资料（无年龄）后给消费者确认，
> 消费者需要补充自己的年龄（数字键盘），然后再点确认（也可以不补充），
> 而且要同时支持单屏和双屏。」

⇒ **顾客要录入。** 原纪律作废。

### 7.1 替代纪律：键盘属于**承载输入控件的那个 surface**

⚠️ **新规则比旧规则更简单，且单屏／双屏自动成立**：

| 形态 | 年龄输入在哪 | 键盘在哪 |
| --- | --- | --- |
| 双屏 | SECONDARY 的 `customer-member{mode:'confirm'}` | **SECONDARY** |
| 单屏 | PRIMARY 的 `customer-member{mode:'handheld-confirm'}` | **PRIMARY** |

**同一个部件、同一段代码**，键盘跟着部件走。
⇒ 不需要为单屏／双屏写两套，也不需要「哪个 surface 允许键盘」的白名单。

⚠️ **2026-09-06 产品边界**：这里的“键盘跟着 surface”在当前产品中指虚拟键盘。
双屏的 SECONDARY 只挂虚拟键盘宿主，不要求也不宣称 Presentation 能显示系统 IME；
单屏 `handheld-confirm` 在 PRIMARY，同样挂虚拟键盘宿主。主屏中文字段的系统 IME 仍由
主屏 adapter/assembly 的 inset contract 承担。若将来要把中文或其他 system-keyboard 字段
放到 Presentation，必须重新做产品裁定与独立运行验证。

⇒ **装配层要求随之改变**：键盘宿主必须填进**每一个** surface 的底部区插槽，
不再是「只填 PRIMARY」。§1b.6 的插槽与包裹点要求对 PRIMARY 与 SECONDARY **同等适用**。

⚠️ 判据自带反例：把 SECONDARY 的宿主拿掉，则双屏下顾客点年龄框弹不出键盘，必红。

### 7.2 ⚠️ `Dimensions.get('window')` 从「不该读」升级为**会真的错**

⚠️ 键盘的尺寸与遮挡计算**不得读 `Dimensions.get('window')`** ——
✅ 亲验 POC V2 正是这么做的，而在副屏 Presentation 上该 API 返回的是**主窗口**尺寸。
⇒ 屏幕事实必须来自 surface 自身的声明尺寸与 `display-context`。

⚠️ **这条的严重度按 §7.1 升级**：原来键盘不上副屏，读错也只是隐患；
现在键盘**真的会渲染在 Presentation 上**，读错就是**尺寸直接算错**。
⇒ 判据必须在双屏下真实覆盖，不能只在主屏验。

### 7.2a ⚠️ 键盘高度：全文原本没规定（自审第 18 轮）

键盘占多高，本文原稿**一个字都没写**。而 §7.1 让键盘上了副屏之后这条不能再空着：
主副屏的尺寸与长宽比可以差很远，同一个「占 50%」在两块屏上是完全不同的结果。

⇒ **三条最小约束**（具体数值留给详设）：

| # | 约束 |
| --- | --- |
| 1 | 高度必须由**该 surface 自身的声明尺寸**推出，不得用 `Dimensions.get('window')`（§7.2），也不得两个 surface 共用一个常量 |
| 2 | 必须有**上限**：键盘收缩内容区之后，承载部件的**关键操作必须仍可见可点** |
| 3 | 同一 surface 上不同布局的键盘高度应一致，避免切布局时页面跳动 |

⚠️ 约束 2 不是排版建议，它就是 sample 需求 §4.5.2a 与判据 S-37 的来源：
顾客点不到「确认」，流程就断在副屏上，而店员还在主屏等。

⚠️ **这条是 S-37 可评估的前提**：高度不定，「按钮是否仍可点」就没有确定答案。

⇒ **补第 4 条约束（Codex 评审 S-3，部分采纳）**：

| 4 | 必须声明**内容区最小可用高度** —— 键盘收缩之后内容区不得低于它；低于则该 surface 上**不允许**弹出虚拟键盘 |

⚠️ 这条属需求层：它是**产品保证**（顾客一定够得着确认），不是排版参数。

### 7.2b ⚠️ 内容区不足以容纳键盘时，用户怎么继续（Codex 复核 S-3，已采纳）

上面第 4 条只规定了「低于最小可用高度就**不允许**弹出虚拟键盘」，
**没说这时用户还能干什么** —— 那会留下一个死状态：
输入框看着能点，点了没反应，也没有别的路走。

⇒ **补三条结果语义**（属需求层，不是详设公式）：

| # | 要求 |
| --- | --- |
| 1 | 键盘不弹出时，**该字段仍保持它原有的可选／必填语义** —— 年龄仍可不填，不得因为键盘弹不出就把它变成阻塞项 |
| 2 | 该 surface 上的**决策动作仍可直接操作** —— 确认、拒绝、单屏的交还店员照常可点 |
| 3 | **不得出现「已获得焦点但无法输入、也无法继续」的死状态**：要么不给焦点，要么给了焦点就得有路可走 |

⚠️ 第 3 条是这三条里的**硬约束**：前两条描述能力，第 3 条描述**不许出现的状态**。
⇒ 判据自带反例：构造一个内容区不足的窄 surface，点该输入框，
若出现焦点已给、键盘没有、且无任何提示或出路的状态，必红。

⚠️ 与 S-37 的分工：S-37 管**键盘已经出现之后**按钮还在不在；
本节管**键盘压根出不来**时流程还走不走得下去。两者互不覆盖。

⚠️ **未采纳的部分及理由**：Codex 建议在此补一张
「surface 尺寸 × 键盘高度 × 内容最小高度 × 按钮可见性」的计算表。
**那属详设**，Codex 自己的表述也是「建议在详设中补」。
需求层把公式钉死会过度约束实现，且本文其余部分一贯把数值留给详设（§5、§8b）。
⇒ 本文只钉**四条约束与 S-37 这个结果**；计算表在详设产出，届时按 S-37 验收。

### 7.3 顾客录入期间，主屏看不到

双屏下顾客在副屏输年龄时，店员的 PRIMARY 是 `member-list` ＋ `waiting-confirm` 层。

⚠️ 按 §9a（编辑值不进 store），年龄草稿**在顾客点确认之前对主屏不可见**。
这是 §2.4「副屏不再逐字镜像」的**镜像情形**，方向相反、规则相同。

⚠️ 不得为了「让店员看到顾客在填」而给年龄开逐字同步的口子 ——
那会把 Q-E 从另一头破掉。

## 8b. ⚠️ Q-D 的连带后果：`PrimitiveInput` 需要**四个**加法 prop（自审第 3 轮起，数量经第 19 轮与 Codex 评审两次更正）

裁定是「包装」，但**包装做不到「契约一字不动」** ——
✅ 亲验 `PrimitiveInput` 当前 props 只有
`testID`／`accessibilityLabel`／`editable`／`onChangeText`／`secureTextEntry`／`value`。

而 §1b.7 要求键盘驱动**输入框的 `value` 与 `selection`**（否则「插在光标位置」做不到），
这需要三个当前**都不存在**的 prop（⚠️ §8b.1 收口后**共四个**，第四个是 `maxLength`）：

| prop | 用途 | 现状 |
| --- | --- | --- |
| `selection` | 受控光标与选区 | ✗ 缺 |
| `onSelectionChange` | 用户点击改光标时回写 | ✗ 缺 |
| `showSoftInputOnFocus` | 选虚拟键盘时抑制系统 IME | ✗ 缺 |

⇒ **精确表述**：既有六个 prop 的**语义与必填性一字不动**，
本专题**加法新增**上述三个**可选** prop。

⚠️ 这与上一专题 `PrimitiveContainer` 新增可选 `layout` 是**同一类加法**，
当时评审判定「是加法不是改契约」，本处沿用同一把尺子。

⚠️ 这些 prop 必须**全部可选**：不用虚拟键盘的既有调用点一行不改。
⇒ 判据：现有所有 `PrimitiveInput` 调用点保持原样仍可编译且行为不变。

### 8b.1 ⚠️ 「三个」这个数字站不住（自审第 19 轮）

sample 需求 §4.5.2b 规定年龄**最多 3 位**（防 20 位数字撑爆 `number`）。
✅ 亲验 `PrimitiveInputProps`（`ui/base/primitives/src/components.tsx:39-45`）
**没有 `maxLength`**。⇒ 长度限制得有个落点，而本节上表只列了三个 prop。

**两条落点，各有代价，须在详设裁定**：

| 落点 | 做法 | 代价 |
| --- | --- | --- |
| 包装层自己截断 | 本包的输入控件在 `onChangeText` 里截断 | ⚠️ 对**系统键盘**输入是「先显示再截掉」，会闪一下；对虚拟键盘无所谓（按键由我们发） |
| `PrimitiveInput` 加第四个可选 prop `maxLength` | 透传给 `TextInput`，由原生拦住按键 | 多一个加法 prop |

⚠️ **已收口（Codex 评审第 6 点，采纳其建议）**：取**第二条** ——
`PrimitiveInput` 增加可选 `maxLength?: number`，透传给 RN `TextInput`，由原生拦住按键。

理由：① 比 JS 侧截断简单；② 避免系统键盘那侧「先显示再截掉」的闪烁；
③ `maxLength` 是**输入约束**不是业务词汇，放在 primitive 的公共面不构成业务泄漏 ——
与既有的 `secureTextEntry`、`editable` 同类。
⇒ 年龄的业务包装层只传 `3`，`PrimitiveInput` 不知道那是年龄。

⇒ **加法 prop 由三个变为四个**：`selection`、`onSelectionChange`、
`showSoftInputOnFocus`、`maxLength`，**全部可选**，既有调用点一行不改。

⚠️ **但布局选择不需要新 prop**：Q-D 裁定是「包装」⇒ 用哪套键盘布局、
用不用虚拟键盘，都由 `ui/base/input` 的包装控件接收并向下转成
`showSoftInputOnFocus`，`PrimitiveInput` 不感知布局概念。
⇒ 本节上表三个之外**只有 `maxLength`**，且已收口 ⇒ 加法 prop 共**四个**，不会再冒出更多。

⚠️ 另一条边界：`showSoftInputOnFocus` **只对选择了虚拟键盘的 input 传入 `false`**，
不得在控件内部写死 —— 否则普通 input 也用不了系统键盘，违反 Dexter 的更正。

✅ 亲验双端可用：`react-native-web` 已实现该 prop，
映射为 HTML 的 `virtualkeyboardpolicy='manual'`。

## 9a. Q-E 已收口：编辑值不进 store，提交才发命令（Dexter 2026-09-05）

### 9a.1 裁定原文

> 「input 里面的 value 不进 state，如果之前有这个规范，请修改这个规范。
> input 变化的内容都不通过 command 发送。只有点击提交按钮，才从 input 里面取值然后发送 command。
> APP 崩溃重启不需要保证未提交的 input 的内容还原。」
>
> 「`sample.login.operator-name` 持久化没问题，但一定不是边输入边持久化。」

### 9a.2 由此消失的问题

我自审第 5 轮担心的「未提交缓冲与提交动作的竞态」**不再存在** ——
因为编辑值**从头到尾就在组件里**，提交动作直接读同一个对象，中间没有任何异步发布环节。

✅ 亲验它可行：`submitMemberCommand` 的签名是
`defineCommand<{name: string; phone: string}>` ⇒ 值**走 payload**，
kernel 侧不读 uiVariables。⇒ 提交时把本地 draft 传进去即可，不需要任何契约变更。

⚠️ 我原先提的「三层：缓冲 → 发布 uiVariables → payload」中间那层**被这条裁定删掉了**。
更简单，且没有编辑期的不一致窗口。

### 9a.3 形态

| 阶段 | 值在哪 | 是否发命令 |
| --- | --- | --- |
| 编辑中 | **组件本地**（编辑期唯一真相源）⚠️ 放在**哪个**组件有硬要求，见 §2.3a —— 放错会踩红 §6 的 PF-2 | ❌ 零命令 |
| 点提交 | 从组件读出，进命令 payload | ✅ 一条 |
| 提交后的跨屏可见 | 由业务事实承载（如 `pending`） | — |

⚠️ **崩溃重启不还原未提交内容**（Dexter 明确）⇒ 编辑缓冲无需持久化，
`§2.3` 的「卸载即消失」没有例外。

### 9a.4 唯一的例外：`operator-name` 的「记住工号」

`sample.login.operator-name` 的持久化策略是 `'owner-only'`，
✅ 亲验 v13 §6.4 注为「记住工号」—— 这是真实功能，变量必须留在 store。

⚠️ 但**写入时机必须是登录成功之后**，不是编辑期（Dexter 明确）。

⇒ 建议再加一条边界：**登录失败不写** —— 失败时的工号可能本来就是打错的，
记住它反而每次都要先删掉重打。

⇒ 形态：登录表单本地 draft 编辑 → 提交派 `loginCommand` →
**成功**后写 `operator-name` 变量 → 下次启动时表单以该变量为初值。
