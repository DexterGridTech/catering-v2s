## 2. 真实业务目标与方案选择

### 2.1 真实目标

让项目管理员可以控制“哪些门店可以从一个 STORE 经营渠道模板创建新渠道”，同时保留已经创建的门店渠道作为历史/运行事实。可见范围是模板候选资格的一部分，不能成为渠道状态的隐式级联源。

### 2.2 三种方案

| 方案 | 形态 | 优点 | 被拒原因 |
| --- | --- | --- | --- |
| A. 模板 scope + owner 关系表 | 模板持有 ALL_PROJECT_STORES/SELECTED_PROJECT_STORES；部分模式持有 (templateRef, storeRef) 关系；候选用 ALL OR EXISTS | 语义直接；候选和既有 channel 可完全分离；可用 CAS/事务统一切换 | 需要一次 migration、契约扩展与关系 read |
| B. 每个门店复制一份模板 | 创建项目模板时按门店复制 template | 查询简单 | 破坏“同一模板”身份；名称、状态、审计、编辑会分叉；无法表达项目范围动态语义 |
| C. 从 business_channel 是否存在推断可见 | 已建过渠道的门店自动可见，未建过不可见 | 无新关系表 | 把历史行为伪装成授权；无法让管理员预先开放给尚未建渠道的门店，也违反可见性与既有渠道分离 |

选择 A。它以最小新增事实表达需求，并把候选资格、渠道实例、模板生命周期分别留在各自 owner 事实中。

## 3. 领域模型与不变量

### 3.1 持久化事实

business_channel.business_channel_template 增加可空 store_visibility_scope：

- operator_kind=STORE：必须为 ALL_PROJECT_STORES 或 SELECTED_PROJECT_STORES。
- operator_kind=PROJECT：必须为 NULL，不可发送或保存门店关系。

新增 business_channel.business_channel_template_store_visibility：

~~~text
template_ref UUID NOT NULL -> business_channel_template.template_ref
store_ref UUID NOT NULL -> organization.store.id (opaque cross-owner reference; no FK)
PRIMARY KEY (template_ref, store_ref)
~~~

关系表不重复保存 project_ref、门店名称或门店状态；项目归属由 template 的 owner 事实与 organization task read 在命令/候选读取时复核。关系表中的 store ref 是 business-channel owner 的 opaque reference，不取得 organization 写权限。

### 3.2 全部与部分的语义

- ALL_PROJECT_STORES 是动态 project membership 规则，不展开关系行；当前及之后属于该项目、且满足候选门店 `status=ENABLED` 条件的门店可成为候选。
- SELECTED_PROJECT_STORES 是显式关系集合；最终集合允许为空，空集合表示当前没有门店可以从该模板新建渠道，不等于模板停用。
- scope 切换与关系集合变更在同一个 template REQUIRED command transaction 内完成。
- scope 变更不触碰 business_channel 行、channel status、channel version、binding 或任何下游状态事件。

“全部”动态覆盖未来项目门店、部分集合允许为空、VOIDED 关系可在保存时保留、整体替换和 visible-store 读取 filter 均已由 Dexter 裁决；本稿只保留实现约束。当前仍需 Claude 对修订后的当前字节做 follow-up review，但这不构成实施授权。

## 6. Contract and edge design

### 6.1 Existing route extensions

不新增项目/门店页面 route；扩展现有 operation 的 request/response：

| operation | request/response change |
| --- | --- |
| createOperationsBusinessChannelTemplate | request 增加 required storeVisibilityScope: enum|null 与 visibleStoreRefs: uuid[]；PROJECT 必须 null + []，STORE 按 scope 校验 |
| updateOperationsBusinessChannelTemplate | request 增加 required storeVisibilityScope: enum|null、最终 `visibleStoreRefs: uuid[]`、expectedVersion；以 desired scope + final set 原子修改 |
| getOperationsBusinessChannelTemplates | view 增加 storeVisibilityScope: enum|null 与 visibleStoreCount: integer；对于 PROJECT/ALL 返回 0，对于 SELECTED 返回 owner 关系表中非 VOIDED 门店的数量；前端不从当前 table 行数推导 |
| getOperationsStoreBusinessChannelTemplateCandidates | operation/path 保持；owner SQL 增加 scope predicate；候选 edge/owner 同时显式复核目标门店 `status=ENABLED`；响应复用 view 的 scope/count 但只返回合格模板 |
| getOperationsBusinessChannelTemplateVisibleStores | 新增项目模板下的 selected-store cursor Page；同一 operation 通过 `storeStatusFilter=NON_VOIDED|ALL` 服务只读详情和编辑 Drawer；仅项目模板管理上下文可读；返回 storeRef、storeName、storeCode、storeStatus，不返回 raw-only 行 |

新 operation 的 route 建议为：

~~~text
GET /api/operations/group-workspaces/{groupWorkspaceKey}/business-channel-templates/{templateRef}/visible-stores
~~~

它只解决 selected-store readback；不承担候选资格，不允许门店用户用它读取整个项目的可见名单。edge 应先解析模板所属 project，再按项目读 scope 调用 owner；scope/owner 不匹配 typed deny。

### 6.2 Wire shape

~~~json
{
  "storeVisibilityScope": "ALL_PROJECT_STORES | SELECTED_PROJECT_STORES | null",
  "visibleStoreRefs": ["uuid"]
}
~~~

Update 使用：

~~~json
{
  "templateName": "...",
  "expectedVersion": 3,
  "storeVisibilityScope": "SELECTED_PROJECT_STORES",
  "visibleStoreRefs": ["uuid-a", "uuid-c"]
}
~~~

契约必须保持 additionalProperties=false、enum closed set、UUID format，数组元素唯一语义由 owner 再校验。生成物只能由既有 generator 生成，禁止手改 generated Java/TypeScript。

### 6.3 Typed problem catalogue

| problem code | 触发条件 | 状态/不泄漏 |
| --- | --- | --- |
| BUSINESS_CHANNEL_STORE_VISIBILITY_SCOPE_REQUIRED | STORE 模板 scope 为 null/未知 | 422；不写 template/relations |
| BUSINESS_CHANNEL_STORE_VISIBILITY_NOT_APPLICABLE | PROJECT 模板带 scope 或任何 store refs | 422；不把 PROJECT 当 ALL |
| BUSINESS_CHANNEL_STORE_VISIBILITY_DUPLICATE | `visibleStoreRefs` 数组重复 | 422；不做静默去重 |
| BUSINESS_CHANNEL_STORE_NOT_IN_PROJECT | store ref 不属于 template project/workspace | 422/404 按当前 owner policy；problem 不带 foreign identity |
| BUSINESS_CHANNEL_STORE_VISIBILITY_STALE | create channel 时 template 当前不再对 store 可见 | 409；提示刷新候选，不创建 channel |
| BUSINESS_CHANNEL_TEMPLATE_NOT_CANDIDATE | disabled/voided/non-STORE template 用于 STORE create | 沿用/扩展 owner typed validation |
| VERSION_CONFLICT | template/channel version 已变化 | 409；不覆盖他人更新 |

具体 HTTP 映射必须与当前 edge problem registry/既有命名逐字对账后再实现；不得为了让前端通过而复用不相干 problem code。

## 7. Owner command/read 细设

### 7.1 Create template

1. edge 读取 session、project target grant；owner 再 requireScope、校验四维和 scope cross-field。
2. canonical request 加入 scope 与排序后的最终 `visibleStoreRefs`；refs 先做重复检查，随后用 explicit organization task read 一次确认同 workspace/project membership。门店状态不参与保存校验，VOIDED ref 可以被保存。
3. 在 command receipt transaction 内检查 templateCode、插入 template；STORE+SELECTED 批量插入关系，STORE+ALL/PROJECT 不插关系。
4. audit 记录 scope 与 canonical sorted visible store refs（不记 raw request）；从数据库 readback template + count 返回。
5. 任一步失败整体 rollback；idempotent replay 返回原完整 readback。

### 7.2 Update template

1. edge 传入 templateName、desired scope、最终 `visibleStoreRefs`、expectedVersion；owner 锁定 template 后以锁定行 projectRef 复核项目 grant。
2. 拒绝未知/重复 refs；读取当前关系集合只用于与最终集合比对和审计，不将客户端列表以外的事实当作成功依据。
3. 计算 final set：PROJECT 必须 null/empty；ALL 清空关系；SELECTED 直接使用最终 `visibleStoreRefs`，允许为空；所有最终 refs 必须属于 template project，门店 status 不参与保存校验，VOIDED ref 可以被保留。
4. 用同一事务删除该 template 的全部旧关系并插入最终集合，更新 scope、version+1、audit；不写 channel 表。整体替换依赖编辑 Drawer 的 ALL 读取，不得隐藏 VOIDED 关系行。
5. 从 committed rows 重新组装 Template readback；旧 version 或失败回滚保持原 scope/relations/channel。

### 7.3 Candidate page

现有 pageStoreTemplateCandidates 的基础谓词保留：workspace/key/project/operator=STORE/template status=ENABLED。新增：

~~~sql
AND (
    t.store_visibility_scope = 'ALL_PROJECT_STORES'
    OR (
        t.store_visibility_scope = 'SELECTED_PROJECT_STORES'
        AND EXISTS (
            SELECT 1
            FROM business_channel.business_channel_template_store_visibility v
            WHERE v.template_ref = t.template_ref
              AND v.store_ref = CAST(? AS uuid)
        )
    )
)
~~~

实际 SQL 必须将 t 别名、参数顺序、count query 和 data query 同步；cursor identity 必须包含 storeRef，避免把一个门店的 cursor 用到另一个门店。候选 query 不能 join business_channel。

当前 business-channel 候选 controller 的 `requireStoreProjectPair` 只证明门店存在、项目归属和 session scope，不证明门店 `status=ENABLED`；不得把它当作状态策略。候选 operation 必须在 edge/owner 的明确边界调用现有 organization owner/task read（当前可复用的状态事实入口为 `OrganizationOwnerApi.requireSalesMenuStore` 返回的 store status，或经源码对账后同等 named task read），并在 candidate owner 继续前要求 `status=ENABLED`。DISABLED/VOIDED 目标门店必须 fail closed（typed scope/status deny 或空候选，按当前 edge registry 对账），任何情况下不得返回模板候选。该要求是本设计对当前缺口的实现约束，不声称现有 production source 已经闭合。

### 7.4 Visible-store page

owner 新增只读 page：从 relation join template scope，并 task-shaped join organization.store 读取 name/code/status；拒绝 PROJECT/非当前 project template；按 stable storeCode, storeRef 排序，返回 nextCursor/total。该同一 operation 接受 `storeStatusFilter=NON_VOIDED|ALL`：项目只读详情使用 `NON_VOIDED`，编辑 Drawer 使用 `ALL`；响应均带 storeStatus，门店状态仅是 readback 独立事实；不在该 read 中改变关系。

### 7.5 Store channel create and existing read

- STORE createChannel 在同一 command transaction 锁/重读 template，验证 template ENABLED、operator STORE、目标 store 当前 ENABLED、store 属于 template project、scope 为 ALL 或 relation EXISTS；失败返回 BUSINESS_CHANNEL_STORE_VISIBILITY_STALE、目标门店状态/范围 typed validation，或现有等价问题。
- visibility update 与 channel create 都锁同一 template aggregate：谁先提交决定新建是否可行；已经先成功创建的 channel 不因之后范围移除而被修改。
- listSalesMenuEligibleChannels、channel detail、channel page SQL 不增加 visibility relation predicate。模板 status、store status、channel status 仍按既有 owner status dimensions 读取。

## 8. Database/migration design

计划 migration 路径：

apps/backend/catering-business-server/src/main/resources/db/migration/V20260908_000000_003__business_channel_template_store_visibility.sql

执行顺序：

1. ALTER TABLE business_channel.business_channel_template ADD COLUMN store_visibility_scope VARCHAR(32)。
2. 现有 operator_kind=STORE rows 回填 ALL_PROJECT_STORES；PROJECT rows 保持 null。
3. 添加 cross-field CHECK：PROJECT→NULL；STORE→两个闭集 enum；不在 DB CHECK 中伪造 relation count。
4. 创建 relation table、template FK、workspace FK（如当前 owner 表形态适用）和 (store_ref, template_ref) 查询索引；store ref 不加 organization FK。
5. 为 migration 自身提供下列 rollback/readback 断言设计：既有 STORE 模板全部有 scope；PROJECT 全部 null；relation 无 template 外键悬挂；scope 与 relation 集合符合 owner invariants。SELECTED 空集合是合法状态，migration 不设置集合数量下限。

“全部没有关系行”是关系形态约束；SELECTED 允许零关系行，不存在集合数量下限。scope 与关系集合的合法组合由 owner command 和 acceptance red fixture 证明，不能用触发器偷偷改变 owner 边界。

## 9. Cross-owner write matrix

| 业务动作 | 第一个 owner command | 第二个 owner command | 事务 | 失败时回滚 |

不得让 organization 反向调用 business-channel command；不得由 operations-admin 直接写任一 owner schema。

### 13.2 UI action ownership

“添加门店”是本地草稿操作，不是 organization 写；“保存”才调用 business-channel owner command。删除已选门店同样只改变草稿，取消回到旧 readback。编辑 Drawer 必须加载全部关系行并标注 VOIDED，不能把编辑读取误用为只读详情的非作废过滤。候选区必须以 useCursorCandidates 的 debounce/accumulate/dedup 行为实现，不能把全量 stores 预加载到页面。

### 13.3 TestId/L2 admission

- 后端 acceptance 只在未来获得明确动态授权后运行；本批不执行。

## 15. Seed design（只设计，不执行）

seed 需要按 owner command 顺序构造：workspace/project/stores → project creates STORE template with ALL/SELECTED → visible relation through owner command → store creates channel → project updates visibility removing store → readback verifies channel retention；另将一个已关联门店转为 VOIDED，执行编辑全量读取、保留关系的无关保存、主动剔除三步。必须有两家同项目 ENABLED store，另保留 DISABLED/VOIDED candidate negative，候选 negative 不能被 seed 省略。

## 17. Stop conditions

停止实施并回到 Dexter 的条件：

- 当前裁决与需求/owning source 仍存在未解释冲突，且实现必须选择不同业务结果；
- current owner/contract source 与本稿操作/字段/状态不一致；
- 不能在同一 REQUIRED transaction 中证明 scope、关系、version、audit 的原子性；
- visible-store/organization candidate 集合边界无法写成可观察的 Page 行为；
- foundation 无法覆盖新 UI primitive，且替代会复制共享行为；
- 任意 fresh review 给出 OPEN 的业务/owner/contract 设计缺口。

## 18. 三维对账要求

在任何实施开始前，fresh 独立 reviewer 必须逐条比较：

1. 需求/本 Journey 的目标、四条需求、已接受与未接受边界；
2. 本文、IA、UI interaction 与 future owning source 的行为、形态、动作、关系、文案、失败/恢复、焦点和集合；
3. 六维 routed project-memory 全部命中原文与适用 backend/frontend/foundation/review 标准。

结论只允许 MATCHED 或 OPEN；有 OPEN 不得进入 implementation。实施完成后还要再次逐代码与详设对账，再进入动态测试；动态测试仍另行区分 CONTRACT、BUSINESS、cleanup，不由本文静态内容代替。
