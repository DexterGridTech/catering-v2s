## 1. 要解决的本质问题

当前问题不是个别字号、间距或按钮位置，而是商品库长期按数据结构和组件复用组织界面，导致用户任务失去边界：

1. 查看、编辑、创建、配置、复制和治理共用大组件，用户无法判断自己是在读事实还是改事实。
2. 禁用表单被当成详情或无写权限的替代，灰色控件同时可能代表只读、锁定、无权限、加载中或不可用。
3. 简单字典、父子字典和复杂定义被塞进同一大弹窗，复杂定义再叠抽屉，滚动、焦点和返回路径失控。
4. 技术模型泄漏为用户信息架构，列表与详情出现原始枚举、内部粒度、引用身份和工程说明。
5. 商品详情和编辑文件承担过多职责，局部修改会触及宿主、查询、草稿、弹层和多个事实族。
6. focused proof 能证明控件或分支存在，却不能证明用户能完成查找、阅读、恢复、失败处置和返回。

目标不是继续装饰旧壳，而是让用户在商品库这个唯一工作区内稳定完成任务，并让查看、编辑、配置和专题任务
各有一种可学习、可恢复、可验证的交互形态。

## 2. 业务边界

### 2.1 商品库回答什么

- 商品目录回答“这是什么”：身份、类型、规格、价格基础事实、条码与标识、属性、点单设置和制作信息。
- 库存摘要回答“销售或使用时怎样扣减、用到什么”；实际余额与流水仍在门店库存管理。
- 引用摘要回答“正在被哪里使用，因此哪些动作受限”。
- 品牌商品是门店复制的候选来源，不是门店商品的强继承上游。

### 2.2 不得推导什么

- 商品启用不等于已发布、已上架、当前可售或终端已生效。
- 有库存对象、有 BOM 或库存充足不等于当前可售。
- 总部商品变化不等于门店自动同步。
- 制作单显示名称不等于打印机、打印模板或后厨设备已配置。
- 详情能读取跨 owner 摘要，不等于 catalog 可以直接修改另一 owner 的全部事实。

### 2.3 V4、V6 与当前 V2S 的使用方式

- V4 只证明读写组件分离、规格表和主从任务面曾经可行，不提供目标页面答案。
- V6 提供业务角色、事实边界与用户任务，不直接规定 Drawer、Modal 或布局。
- 当前 V2S 的业务模型是本批必须遵守的运行事实；本批优化交互，不回退单值分类、单位、库存/BOM、
  条码标识、制作信息、属性或点单选项规则。

## 3. 用户与八类 Journey

### 3.1 Actor

| Actor | 此刻要解决的问题 | 主要读写性质 |
| --- | --- | --- |
| 总部商品资料维护者 | 维护品牌商品模板和可复用定义，供门店显式复制 | 读写 |
| 门店商品资料维护者 | 维护门店商品身份、规格、价格基础事实和运营配置 | 读写 |
| 门店库存维护者 | 核对并维护商品或规格的扣减方式与用料规则 | 读写，余额流水另页 |
| 门店店长 | 快速审视状态、价格、配置完整度和危险动作影响 | 读多写少 |
| 后厨/出品人员 | 读取当前有效制作信息、规格差异和做法加料影响 | 只读 |
| 库存员 | 读取库存扣减方式、单位和用料摘要 | 只读为主 |
| 治理处理人 | 补全外部临时商品、处置冲突并转正 | 专题写 |

后厨与库存员是详情首屏内容选择的具名消费者。详情不能只为编辑者服务。

### 3.2 Journey 分母

| Journey | 任务 | 成功结果 |
| --- | --- | --- |
| `J-CATUI-01` 查找商品 | 按范围、分类、标签、状态、来源或关键词定位商品 | 结果可比较，列表位置与筛选稳定 |
| `J-CATUI-02` 查看商品 | 不改变事实，回答商品是什么、怎么做、怎样扣库存、被谁使用 | 纯业务陈述，无禁用表单 |
| `J-CATUI-03` 新建商品 | 以最少身份建立商品草稿，再继续完善 | 原子创建成功后进入该商品编辑抽屉 |
| `J-CATUI-04` 编辑商品 | 跨适用事实族修改一个商品并整单保存 | 草稿、区段、错误和保存结果均可恢复、定位 |
| `J-CATUI-05` 维护商品配置 | 维护六类复用定义 | 在配置抽屉中按复杂度完成，不叠抽屉 |
| `J-CATUI-06` 批量整理 | 批量改分类、标签、状态或归档 | 提交前知情、提交中可见、提交后逐项报告 |
| `J-CATUI-07` 复制 | 从品牌复制到门店，或把已有商品设置复制到当前商品 | 来源、目标、覆盖范围、冲突和结果清晰 |
| `J-CATUI-08` 生命周期与治理 | 启用、停用、归档、作废重建或临时商品转正 | 只显示可执行动作，失败后已存事实不变 |

## 4. 已裁目标交互架构

### 4.1 唯一页面与同层互斥

商品库工作台是本专题唯一页面。关于商品的所有操作均从该页面发起并在该页面上下文内完成，不跳转到独立
配置页或独立编辑路由。

```text
商品库工作台（目录树 + 结果表）
 ├─ 第一层 Drawer：查看 | 编辑 | 配置 | 复制向导 —— 同时只允许一个
 │   └─ 第二层：编辑子任务面 | 小型原子 Modal
 │       └─ 第三层：仅 confirm
 ├─ 直接原子 Modal：新建商品、分类小型输入
 └─ 直接批量 Modal：提交前摘要 → 提交中 → 逐项结果
```

任何工作台直接任务面都与四种第一层 Drawer 互斥。任意时刻叠层深度不超过三；第三层只允许确认，
不得包含表单、候选选择或另一条业务分支。

### 4.2 商品工作台

目录树总体方式保留：智能视图、商品形态、商品标签、商品分类与结果表联动；新增同层一级节点“生产标签”，
其二级节点为全部生产标签并可筛选商品。本批不重画目录树的层级、交互和视觉基线，只扩展这一项已裁业务分支。

`U-CATUI-06=DEXTER_ACCEPTED` 冻结两个现有区域，优化不得改名、移动、合并或重组：

1. 顶部工作台工具区保持“树表视图 / 仅表格”切换，右侧保持“商品元数据 / 从品牌复制 / 新建商品”；
   控件顺序、主次关系、相对位置和现有任务语义不变。“商品元数据”继续打开本批重做后的配置抽屉，
   “从品牌复制”继续进入复制任务，但不得借重做内部 surface 改掉入口。
2. 结果域筛选区保持第一行“当前结果域：〈当前树节点或视图〉”，第二行保持当前结果域内搜索、状态、来源、
   重置；控件顺序、相对位置、结果域提示与重置语义不变。搜索和筛选仍共同作用于当前结果域。
3. 本批的父商品/规格子行 Table、列模型和 Drawer 优化只发生在这两个冻结区域下方或由其既有入口打开的
   surface 内；不得为了新 Table 重画工具区或筛选区。

结果表必须支持横向比较。按规格管理商品采用 **商品父行 + 规格子行** 的树形表格：父商品可展开或收起，
每个 SKU 在同一张表、同一列模型中独占一行；用户界面称“规格”，不得把多个 SKU 拼进一段文字、卡片或
嵌套表格。普通销售商品、称重商品等没有 SKU 的商品只显示父行，不出现无意义展开箭头。

目标实现采用 V4 `CatalogItemListTable` 已验证的 Ant Design 原生 `Table` tree-data 形态：

- 行模型是 `ITEM / SKU / SKU_PLACEHOLDER` 的有限闭集；
- `childrenColumnName`、受控 `expandedRowKeys` 与 `onExpand` 承担父子展开；
- 展开父行时只读取该商品的 SKU 行摘要，不在初始列表读取全量 SKU 或逐商品详情；
- 加载中、失败与继续加载均占据一条规格子行，列宽不跳变；
- SKU 子行不参与商品级批量选择，选择列保留对齐占位；
- 商品筛选、排序、游标分页的分母仍是父商品；展开的 SKU 不改变当前结果域或分页数量；
- 关闭查看/编辑 Drawer 后回到同一结果域时保留展开状态；改变筛选、排序、分页或范围后清理失效展开项；
- 父行 key 使用商品编码，子行 key 使用商品编码与规格编码的稳定组合，禁止使用 index。

当前 `ProTable.expandedRowRender` 的“展开一整块内容”形态明确退役。`ProTable` 只有在实现期可复现实验同时证明
上述父子同列、懒加载、父行选择、占位、键盘与精确滚动全部成立且没有平行适配层时才可保留；默认且推荐的
实施基线是复用 V4 同款普通 Ant Design `Table<CatalogItemListRow>`，不为保留 ProTable 牺牲用户表达。

`U-CATUI-08/09/12=DEXTER_ACCEPTED`：横向滚动是承载完整信息的正常交互，不得用“首屏放不下”删除、隐藏、
合并或压缩业务列。业务列从左到右固定为：**商品、商品形态、价格和单位、规格或选项、商品属性、制作信息、
库存与 BOM、更新时间、状态、来源**。十列默认全部显示；此前“来源默认隐藏/显示列只控制来源”的设计被本裁定
替代，不再建立列显隐偏好或“显示列”入口。

禁止斜杠复合列、重复表头、原始枚举和工程说明。父行和规格子行共享同一表头；每个业务单元格最多四行文字，
超长单行省略并用 `EllipsisTooltip` 提供全文，超出四行的集合在第四行显示“还有 N 项”，Tooltip 展示完整有序清单。
任何单元格都不得通过无限换行抬高整行。**规格或选项列例外于“还有 N 项”的集合摘要：该列始终显示实际业务内容的前四行，
不以数量行替换任一规格或点单选项；超出部分只在 Tooltip 中按 owner 给定业务顺序完整显示。**

| 列与最小宽度 | 商品父行 | 规格子行 | 视觉与空值规则 |
| --- | --- | --- | --- |

父商品显示展开按钮。表头高 44px，父行和规格行最大内容高度均为四行文字；父行使用正常背景，规格行用极浅
层级底色、24px 缩进和连续层级引导，不能靠字号变小区分。加载中、失败、重新加载和“加载更多规格”各占一条
规格行：提示只出现在商品列，其余列保留空单元格和既有宽度，禁止 `colSpan` 生成第二套列模型。

V4 只提供已验证的父子同表、固定身份列、父行选择和懒加载参照。本批明确改进四点：删除 V4 的技术/风险列；
不复制 V4 的第二条 range 滚动控件；使用 Ant Design Table 自带横向滚动与 sticky scrollbar；按上述业务列最小宽度
计算 `scroll.x`，不把列压进可视区。页面本身不横向滚动，只有表体横向滚动；滚动时商品列保持固定，父子行与表头
始终对齐。窄屏不退化成卡片，不丢列、不改变父子层级。

`U-CATUI-10=DEXTER_ACCEPTED` 的价格边界：商品标准价和规格标准价都是可选商品资料，`null` 是合法事实；商品库
不再把未设置价格呈现为红色风险、配置完整度或生命周期阻断。菜单项进入销售时必须有价，但那是菜单/销售集合
owner 的准入责任；本批不把菜单定价校验搬进 catalog owner，也不从商品是否有价推导可售。现行
`missingPriceCount` 是把合法空值命名为缺陷的派生字段，本批从商品列表/详情 read contract 与 UI consumer 退休；
保留 `standardSalePrice` 的 nullable 语义，不用 fallback 补零。

点击规格名称打开该父商品的查看 Drawer，并定位到“规格与价格”区段及该规格；不创建第五种第一层 Drawer。

### 4.2.1 生产标签导航与筛选

目录树在“商品标签”同层新增一级节点“生产标签”。其二级节点按生产标签业务顺序列出全部定义；启用与停用标签
都可见，停用项显示“已停用”但仍可筛选既有绑定，只有后续编辑候选排除停用项。节点计数是当前 scope/brand 下
绑定该生产标签且未作废的**父商品去重数**，规格不另计数。

选择某生产标签后，父商品列表只返回 `productionTagRef` 等于该标签的商品；展开规格仍显示该父商品全部规格，
不按规格再次过滤，因为生产标签属于商品而非规格。该筛选进入父列表 query identity；切换节点时清父行选择、
失效展开和游标，保持冻结的状态/来源/关键词筛选协议。前端不得把 production tag 混入商品标签 `tagRef`，也不得
抽取全部商品后本地过滤。导航与列表 owner 必须以集合查询返回标签、状态、父商品去重计数及匹配结果，禁止 N+1。

### 4.2.2 单一生产标签业务模型

`U-CATUI-11=DEXTER_ACCEPTED`：用户术语由“制作处理标签”统一改为“生产标签”；每个商品允许未设置，设置时最多
一个。生产标签是商品级事实，不是规格级或点单选项级事实：

1. 商品编辑使用可清空的单选候选控件；新绑定只能选择启用标签，既有停用绑定继续显示且可清除。
2. 规格可继续选择使用商品默认或单独设置制作单显示名称、预计制作时长和制作说明，但不能覆盖生产标签；规格行
   展示同一商品生产标签。
3. 点单选项的制作变化只保留非负制作时长增量和按业务顺序追加的制作说明，不得增加、移除或替换生产标签。
4. contract 使用单值 `productionTagRef: UUID|null`；owner、数据库和 copy/readback 同时强制单值。数组、多值请求、
   规格标签字段或选项标签字段均是退役输入并由 closed schema/typed problem 拒绝，不能由前端隐藏代替。
5. “未来生产流程会按生产标签路由”只解释为何现在必须保证单值。本批**不实现**生产工作台、路由规则、分派命令、
   队列、KDS、打印、兜底路由或无标签处置；不得从单值字段反推这些能力已存在。
6. 生产标签定义本身不再有“类型”这一第二分类器。旧 `tagKind` 及其六值枚举不对应任何已批准的用户任务或本期
   路由语义，必须从 contract、owner、持久化、复制、seed、界面和测试一并退役；这不删除生产标签，也不改变商品
   0..1 的绑定语义。

### 4.3 商品查看抽屉

查看抽屉与编辑抽屉是不同 surface、不同组件。查看抽屉只回答“当前是什么”，不注册编辑 Form，
不渲染 disabled `Input`、`Select`、`Radio`、`Switch`、`InputNumber` 或 `TextArea`。

标题区显示主图、商品名称、商品编码、商品形态、来源和状态；主动作最多一个“编辑商品”。当前合法普通动作
可见，低频与危险动作进入“更多”，不可执行原因由 contract readback 解释，不保留一排灰按钮。

首屏概览必须优先回答：

- 商品身份、价格与规格摘要；
- 后厨关心的有效制作信息与规格差异；
- 库存员关心的扣减方式、消费单位和用料摘要；
- 店长关心的状态、来源、配置缺口和引用限制。

后续区段按商品形态裁剪：基础与图片、条码与标识、规格与价格、点单选项、商品属性、制作信息、
库存扣减与用料、套餐内容、引用关系。空区段遵守“还没有 X + 影响说明 + 当前任务下一步动作”。

### 4.4 超宽商品编辑抽屉

完整编辑使用全高超宽 Drawer，不建独立路由。内部是“抽屉里的工作区”：

- 标题持续显示商品名称、商品编码、状态和草稿恢复提示位。
- 左侧是九类事实族区段锚点；按商品形态隐藏不适用项，每项可显示未保存与错误徽标。
- 右侧是唯一内容滚动区；常驻保存栏不得遮住被聚焦字段，滚动定位必须预留保存栏偏移。
- 保存与取消持续可见；一次整单保存语义不变，不把区段拆成多次业务保存。
- 创建后不可修改或被治理锁定的事实显示为文本摘要和原因，不伪装成禁用输入框。
- 保存失败保留非秘密草稿；版本冲突、已知业务拒绝和结果未知分别给出可执行处置。

九类事实族为：

1. 基础资料与图片；
2. 条码与标识；
3. 规格与价格；
4. 点单选项；
5. 商品属性；
6. 制作信息；
7. 库存扣减与用料；
8. 套餐内容；
9. 引用关系与治理摘要。

### 4.5 意外关闭/刷新草稿恢复与编辑内元数据子任务

整单草稿持久化到 `sessionStorage`，身份键为商品编码与用户打开时看到的版本。必须保存：

- typed 区段值；
- 每区段未保存状态；
- 每区段错误；
- 当前区段；
- 能稳定恢复任务所需的区段滚动位置。

编辑抽屉意外关闭或页面刷新后，用户重开同一商品时看到“检测到未保存草稿”，可选择恢复或放弃；恢复后
回到原区段、原草稿与错误位置。深链和浏览器后退不在本批目标内，不得作为恢复替代品。

编辑中缺少单位、标签、属性或选项定义时：

1. 编辑抽屉保持打开，整单草稿、当前区段、错误与滚动位置始终留在编辑工作区；
2. 在编辑抽屉之上打开一层“维护商品元数据”子任务面，并定位对应库；
3. 子任务中的字典写入只由对应 owner 完成；成功后只失效相关候选，绝不改写商品草稿；
4. 关闭子任务立即回到原编辑区段和触发控件；当前商品的未保存修改保持原样；
5. 编辑内打开、维护与关闭商品元数据的过渡路径禁止读写过渡 session、`returnToEdit` 或工作台“继续编辑”状态；异常关闭或页面刷新后的整单草稿恢复仍只由独立草稿机制负责，且不得由该子任务触发。

工作台直接打开“商品元数据”仍是一个互斥的第一层配置 Drawer；从编辑发起的维护是编辑子任务，不是第二个第一层任务。

### 4.6 编辑子任务面

编辑 Drawer 之上只允许一层专注子任务面：规格行详情、BOM 组件选择、套餐组件选择、选项值物料、编辑内“维护商品元数据”。
候选列表、搜索、选择和已选摘要必须在该子任务面内完成；子任务面不得再打开候选 Drawer。

子任务面之上只允许 confirm。关闭子任务面回到触发区段和触发控件；失败保留当前选择，不能把焦点送回页面顶部。

### 4.7 商品配置抽屉

用户可见的“商品元数据”入口保持在商品库工作台。承载为全高配置 Drawer，左栏固定六库导航：商品标签、计量单位、规格维度、
生产标签、商品属性、点单选项。右栏按复杂度只使用三种形态：

| 形态 | 适用实体 | 右栏结构 | 唯一允许的附加面 |
| --- | --- | --- | --- |
| 简单字典 | 商品标签、计量单位、生产标签 | 搜索/筛选 + 列表即详情 | 新建、改名、状态或删除确认的小 Modal |
| 父子字典 | 规格维度与可选值 | 主从两列，左维度、右当前值 | 新建/改名小 Modal |
| 复杂定义 | 商品属性、点单选项 | 右栏内列表与详情编辑同栏切换 | 必要 confirm，不开新 Drawer |

简单字典不建详情页。列表必须显示用户识别、比较和预判动作所需的完整事实；编辑面尺寸与字段数量匹配。

简单库的搜索输入仅在当前库界面本地暂存；维护者提交名称/编码搜索或改变状态筛选后，筛选值必须作为当前库 owner query 事实，重置该库游标并参与 cursor identity。商品标签、生产标签属于分页集合，计量单位虽有 99 条上限仍使用同一 owner 筛选协议；不得只对已加载行做前端过滤而漏掉后续结果。切换库、scope 或品牌时清空该库未提交输入和已应用筛选，不影响其它库。
配置 Drawer 之上禁止打开任何 Drawer。

### 4.8 候选选择只保留两种标准形态

- 有限候选：单位、标签、属性值等小闭集，在当前任务面内以统一列表/选择器呈现，可搜索但不分页。
- 搜索候选：BOM 组件、套餐组件等大集合，复用 cursor 搜索、稳定已选和加载更多形态。

五类候选任务必须归入其中之一，禁止第三种临时 `Select`、临时 Picker 或 Picker Drawer。

`U-CATUI-07=DEXTER_ACCEPTED`：商品分类是分级树，不是平铺字典。凡任务语义是“选择一个商品分类或目标父分类”，
包括新建商品、编辑商品、批量移动分类、分类挪父以及后续新增的同类控件，必须使用**单选树形选择器**：

- 展开层级并显示当前选中分类的完整路径，搜索命中子分类时仍显示祖先路径；不得用普通平铺 `Select`、
  Radio、Autocomplete 或自由文本代替。
- 候选树由 catalog owner 的 task read 返回稳定分类身份、父子关系、名称、编码、业务顺序、是否可选及
  不可选原因；UI 不得从平铺列表自行猜父子关系。
- 是否允许选择非叶分类由 owner/contract 声明，UI 不自行实施“只能选叶子”或“父节点都可选”。
- 分类挪父时，当前分类及其全部后代必须不可选并显示业务原因；owner 在 command 内再次拒绝自环、后代环、
  越范围和版本漂移。
- 树形选择器是“搜索候选”在层级业务对象上的标准呈现，不构成第三种临时 Picker。

### 4.9 新建、批量、复制和治理

- 新建商品使用匹配字段量的小/中 Modal，只建立最小身份；其中商品分类使用单选树形选择器。成功后关闭
  Modal 并打开该商品编辑 Drawer。
- 批量任务有三态：提交前对象与影响摘要、提交中进度和防重复、提交后成功 N/失败 M 与逐项原因。
  请求失败保留选择与目标动作；部分失败保留权威逐项结果，刷新失败单独可见。
- 从品牌复制与复制已有商品设置都使用复制向导 Drawer，但标题、来源、目标、覆盖范围和结果必须可区分。
- 外部临时商品治理从查看 Drawer 发起专注子任务，先显示缺口并检查是否可转正，再补全并确认；不与普通编辑混成一张表单。
- 生命周期动作只显示当前可执行集合；普通确认与危险确认按正本 3-K-6 分级。
- 分类挪父确认必须显示受影响子分类数量、商品数量和查找路径影响。

## 6. Contract、owner 与 UI 的责任

### 6.1 Contract 必须声明

1. 商品形态、适用区段、规格粒度和字段准入。
2. 列表可比较摘要和详情业务展示事实，含有效制作信息、库存扣减与用料摘要、引用摘要；父商品页另返回
   owner 计算的 `categoryPathLabels`，UI 不从当前可见 navigation tree 猜完整路径。
3. 当前动作可用性与不可用原因；UI 不从状态或权限字段自行拼动作矩阵。
4. 创建/编辑 typed 结构、必填、闭集、单值/多值和稳定错误定位。
5. 两类候选的查询、分页/不分页和稳定业务身份；商品分类候选必须保留父子层级、完整路径、业务顺序、
   可选性和不可选原因，供统一树形选择器消费。
6. 保存、批量、复制、治理所需的 typed problem 与结果 readback。
7. 父商品列表摘要中的 `hasSkuChildren`、规格数量、已设置价格的可选区间与规格维度摘要；
   `missingPriceCount` 从商品列表/详情 read contract 退休。
8. 按父商品懒加载的规格行摘要：稳定规格身份、名称/编码、属性组合、价格、状态、默认标识、库存扣减摘要、
   图片与更新时间；数量超过单次返回上限时提供 cursor，UI 用“加载更多规格”子行继续读取。

### 6.2 Owner 必须负责

1. 在当前范围、权限、状态、引用和版本下最终复核命令。
2. 拒绝篡改请求；UI 隐藏、禁用和本地校验不构成业务防线。
3. 维护各 owner 的事务与事实主权；UI 同页不意味着 owner 合并。
4. 失败时保证已保存事实与未命中命令不被错误改变，并返回可定位问题。

### 6.3 UI 必须负责

1. 选择本文件已裁 surface，组织任务、层级、焦点、草稿和返回。
2. 只消费 contract 声明的动作、区段和展示事实，不猜业务准入。
3. 所有用户文案使用业务语言；不得显示 `shapeKey`、owner、ref、UUID、profile、effect、manifest、
   problem code、raw exception 或原始枚举。商品编码等真实业务编码是明确反例。
4. 区分加载、空、失败、无权限、业务不可修改、脏、提交中、已知失败、未知结果和成功。
5. 精确刷新列表、详情和候选，不自造与 foundation 平行的提交或刷新生命周期。
6. 所有商品分类赋值控件消费同一层级候选协议并使用单选树形选择器；不得在某个 surface 退回平铺下拉。

### 6.4 控制权分界必须可逐控件对账

“后端定义规则、前端负责交互”不是可实施的分界。每个控件必须在 IA 中同时声明“显示什么、值住哪里、谁能
改变、上游变化清什么、提交时谁再核验”，并遵守以下唯一分工：

| 责任层 | 必须拥有 | 明确不得拥有 |
| --- | --- | --- |
| contract | 字段是否适用、必填/闭集/数量边界、单值/多值、动作可用性及原因、候选业务身份/层级/路径/顺序/可选性及原因、分页与版本、typed problem 的稳定定位、权威 readback | Drawer/Modal、焦点、滚动、dirty、临时展开等纯界面状态 |
| owner | 当前会话、范围、权限、状态、引用、版本与跨 owner 不变量的最终复核；失败后事实未变 | 要求 UI 以隐藏按钮或本地校验代替服务端守卫 |
| generated RTK / App 业务状态 | `currentData` 承载服务端事实；`useCatalogItemDraft` 承载整单草稿；工作区 reducer 和局部 hook 承载界面瞬态 | 把服务端 page/detail/action/candidate 镜像进 `useState`；从状态或枚举重建动作矩阵、候选资格或 shape 准入 |
| admin-ui-foundation | Drawer/Modal 生命周期、脏关闭、提交幂等机械件、overlay lock、cursor 候选、统一刷新、safe logger | catalog 业务草稿、分类资格、商品形态准入或业务文案 |

contract 未声明业务规则时，前端保持 `GAP` 并停机补设计；不得用灰控件、平铺候选、本地 switch 或 fallback
临时补义。前端可以为了及时反馈重复做格式校验，但 owner 必须按同一 contract 规则最终拒绝篡改请求。

### 6.5 用户可见语言与流程连续性

1. 用户界面统一说“规格”，不显示 `SKU`；统一说“检查影响/重新检查”，不显示“预检”；统一说“结果已保存，
   列表暂未更新，可重新加载”，不显示“重新读取失败”。技术词可存在于代码、contract 和设计说明，不能进入
   标题、label、help、空态、错误、按钮或结果表。
2. `shape`、`scope`、owner、contract、ref、UUID、profile、effect、payload、readback、problem code、manifest、
   raw exception、原始状态枚举均属于禁用词；“商品编码、规格编码、条码、PLU、BOM”是已确认业务词。
3. `U-CATUI-06` 冻结的“商品元数据”和“当前结果域”是 Dexter 明确保留的历史入口文案，仅作为两项具名例外；
   不得据此把“元数据、结果域”扩散到 Drawer 正文、帮助、空态或新增动作。配置抽屉标题下必须补业务说明
   “维护商品共用的标签、单位、规格、生产标签、属性和点单选项”。
4. 八条 Journey 均须定义入口、当前对象、主动作、成功去向、失败原位恢复、取消/关闭焦点归还和下一步；用户
   不得因一次失败被迫关闭任务、重新搜索商品或丢失已填内容。复制和治理的“检查影响”不写数据；只有用户在
   确认面执行明确业务动作才允许写入。

## 7. 跨批一致性

本批逐字引用 `doc/platform/frontend-coding-standard.md#3-K`，不在此复制第二份七族规范。所有 surface 必须
逐项应用：表单、弹层、动作命名、提示反馈、空态、确认和状态 Tag。

本批特化只包括：

- 四种第一层 Drawer 同层互斥；
- 最大叠层深度三；
- 编辑 Drawer 的意外关闭/刷新草稿恢复，以及编辑内元数据子任务不进入恢复链；
- 商品生命周期 Tag 使用正本统一色义；
- 商品详情绝不以 disabled 表单呈现。

## 8. 工程结构硬要求

以下是可验收需求，不是实现建议：

1. 宿主文件只做装配、路由到 surface 与生命周期编排，目标不超过 300 行。
2. 九类事实族各自独立文件；同一事实族的 `View` 与 `Editor` 分文件，不能用 `readOnly` 切换同一控件树。
3. `useCatalogItemDraft` 是整单草稿唯一业务 hook，负责 typed 区段、dirty、error、sessionStorage 与恢复。
4. `useCatalogConfigLibrary` 是六库列表、当前库、筛选和选中事实的唯一业务 hook。
5. 有限候选与搜索候选各有一个标准 hook；禁止第三套候选生命周期。
6. 提交、幂等、精确刷新和 Drawer 表单生命周期复用 `admin-ui-foundation` 既有能力，不自造平行版本。
7. 状态只有三个住址：服务端事实只住 RTK `currentData`；整单草稿只住 draft store；展开、选中、滚动等
   UI 瞬态只住组件本地。
8. 新增一个区段字段时，改动只落在该区段 View、Editor 与 draft 类型；宿主文件零改动。做不到即结构未达标。
9. 商品列表拆为专用 `CatalogItemListTable` 与纯 presenter；普通 AntD Table 承担树形行，工作台宿主只装配
   查询、筛选、批量和 surface 生命周期，不把异构父子行重新塞回宿主。

## 9. testId 与 L2 设计要求

### 9.1 testId 单一真相源

- 未来实施新建 `catalogTestIds.ts`，商品工作区全部 testId 从该模块导出。
- 每个可交互控件、surface、区段、行动作和确认按钮均有常量 testId。
- 命名使用 kebab-case、`catalog-` 前缀；动态列表行使用业务码，不使用 index。
- 组件引用、常量导出与 locator bindings 三方 exact-set 一致；字符串散写、未使用常量和漏绑定均失败。

### 9.2 扩既有 L2 链

只扩 `contracts/policy/catalog-inventory-l2-case-blueprint.json` → P1 → generated scenarios →
locator bindings 的既有链，不建第二套。

双分母必须同时清零：

1. 业务分母：八类 Journey 各自的成功、失败和恢复路径；
2. 控件分母：`catalogTestIds.ts` 的交互控件全集。

门必须证明：声明 Journey 路径减 blueprint 映射为空；声明 testId 减 L2 实际触达为空。差集非空时点名漏项。

每个 case 的 oracle 至少断言一项业务结果：readback 值、列表行变化、草稿恢复内容、错误文案逐字、
焦点归还位置。元素存在或页面打开不算 oracle。每个写场景有负 case，断言失败后版本和业务值不变。
至少跨两个不同 surface 对照七族一致性。L2 执行仍需 Dexter 单独授权，静态或 focused proof 不能代称。

### 9.3 L2 当前就绪度与激活条件

截至本需求修订时，L2 **不具备本批执行条件**，必须分别报告而不能笼统写“已有 Playwright”：

| 能力 | 当前事实 | 结论 |
| --- | --- | --- |
| 浏览器与静态骨架 | operations-admin 已有 Playwright 配置、旧 catalog-inventory policy/locator/fixture validator | `PARTIAL`，只能复用基础，不证明本批可运行 |
| 受管运行入口 | `scripts/` 下没有拥有本机 Spring Boot、双 Vite、Playwright、HTTP/资产 tunnel、远端隔离 DB/资产命名空间与两侧 cleanup 的 browser L2 runner | `NOT_READY` |
| 本批用例 | 现行 generated 分母仍为旧 18 scenario / 41 case，execution profile 为 `FRAMEWORK_ONLY` 且 active case=0 | `NOT_READY` |
| 本批测试数据 | 现有 fixture catalog 未声明本批 24 case 的 before/action/expected/unchanged facts | `NOT_READY` |
| 本批诊断 | 尚无 case/action/testId 到 requestId、后端 completion、DB section 和 cleanup 的 join artifact | `NOT_READY` |
| 受管凭据与会话 | 尚无 browser L2 的 run-scoped 0600 credential/session 文件、有限 secret allowlist、按子进程最小注入与跨 run 绑定校验 | `NOT_READY` |

实施必须扩展既有单链而不是建第二套框架。只有以下条件全部为 PASS，execution profile 才可从
`FRAMEWORK_ONLY` 原子切换为本批 24 case 的明确 exact-set：

1. 受管 runner 建立每 run 隔离的远端非生产 DB 与资产命名空间，本机启动 Spring Boot、两个 Vite 与
   Playwright，经受管 tunnel 连接远端中间件；不得使用长期 DEV、DEV seed、远端 Vite 或远端浏览器。
2. runner manifest 记录本机 PID+OS start token、远端 host/PID/boot id/start ticks、tunnel identity、资源预算、
   phase/heartbeat/log path、firstFailure/lastKnownGood/brokenBoundary、business 与本机/远端 cleanup。
3. 本批 TEST fixture 只经 owner HTTP commands 创建，不读取 DEV seed/report；24 case 各有确定的 preState、
   action input、expected owner readback 与失败后 unchanged oracle，setup 失败禁止启动浏览器。
4. 24 case、47 surface、interactive control concrete testId、locator binding 和 L2 touched 集合双向 exact-set 均闭合；
   affected-L2 registry 能精确选择商品库 surface，不依赖全量 fallback。
5. business PASS 后仍必须证明只清理本 run 拥有的本机 process tree、远端 DB/资产命名空间与 tunnel；cleanup 非
   PASS 整体不得完成。是否实际执行 L2 仍需 Dexter 单独授权。
6. runner 的凭据与会话只来自受管 host trust/bootstrap 与本 run 新生成材料，写入 `0700` runtime 目录中的 `0600`
   文件；Spring Boot、Vite、Playwright、provision/cleanup 各自只接收最小字段。缺失、额外、格式错误、过期、跨 run、
   错 DB/资产命名空间或任何日志/manifest 泄露都必须在 `fixture-setup` 前 fail closed；临时 cookie/storageState 和
   credential 文件属于本 run cleanup，不能复用 DEV 凭据或输出 raw 环境变量。

### 9.4 L2 测试数据与业务 oracle

本批测试 fixture 至少形成以下互相可组合、但身份稳定的事实集；fixture 名称和值是测试数据，不得依赖 DEV seed：

- 深度至少 3 的分类树、同名不同路径、可分配节点、不可分配节点、分类挪父的当前节点与后代；
- 一个父商品下 3 个规格且规格页可翻页、一个无规格商品、一个长名称/长说明商品、一个合法空区段商品；
- 九事实族均有非空 readback 的商品，以及针对条码、单位、属性、点单选项、制作信息、库存扣减/BOM、套餐、
  引用的可编辑/锁定/拒绝对照；
- 六库的简单、父子、复杂三形态，含被引用不可删除、已停用但既有绑定可见、可合法新建的定义；
- 批量至少含先成功项、旧版本失败项和引用阻止项；复制含兼容来源、语义冲突、旧检查结果失效；治理含可转正
  与缺口/旧版本/引用阻止对照；
- 有权限、只读、越范围身份，以及本 run 资产对象和失败后可核对的 baseline version/fact digest。

每个 case 必须按 `Given fixture → 用户动作 → 用户可见结果 → owner readback/unchanged → 焦点/恢复 → 日志关联`
写清；只断言元素存在、按钮可点、HTTP 2xx 或 toast 均不算业务 oracle。失败 case 必须同时断言错误业务文案、
当前任务仍可恢复、版本与业务值不变；写入成功 case 必须用 owner readback 证明，不从 DOM 自证。

### 9.5 诊断与首败定位

每条 L2 动作必须产生不含业务值的关联行：
`runId → caseId → actionId → testId → generatedOperationId → requestId/correlationId → backend phase → DB section`。
后台自动刷新允许标为 `BACKGROUND`，但不得成为无法归属的请求。每个 action 声明预期新增的 Playwright step、
前端 lifecycle/request log、后端 completion、DB operation rows 和 runner heartbeat；应有而没有时立即报
`NO_NEW_EVENT:<source>` 或 `LOG_NOT_AVAILABLE:<source>`，不得盲等或延长 timeout。

当 completion 的 `databaseOperationCount>0` 时，必须存在同 run/request/operation 的 DB rows，且 row section
聚合与 completion `sectionCounts` 一致。日志严禁记录搜索词、商品/人员名称、识别码原值、draft、request/response
body、SQL/bind raw 值、token、cookie、Authorization 或资产签名。每次运行报告独立给出 first failure、last known
good、broken boundary、business 和 cleanup；日志或 join 断链本身就是首败，不得由测试名或 exit code代替。

## 10. 可证伪验收场景

1. 只读用户按目录树找到拿铁，打开详情读到三个规格、有效制作信息和库存扣减摘要，全程无灰色输入框。
2. 可写用户从查看抽屉进入编辑；查看 Drawer 已关闭，任何时刻不并存两个第一层 Drawer。
3. 编辑抽屉修改两个区段后意外关闭；重开同商品可恢复原区段、字段值、dirty 和 error。
4. 页面刷新后重开同商品，恢复提示与草稿身份仍按商品编码+原版本准确匹配；选择放弃后无草稿残留。
5. 编辑中缺单位、标签、属性或选项定义时，在编辑之上维护对应元数据；关闭后仍处于原编辑区段，候选更新而草稿不变。
6. 编辑子任务内完成 BOM 组件搜索与选择，不打开第二个候选 Drawer；第三层只有确认。
7. 新建普通销售或称重商品后不出现规格维护；新建按规格商品后可进入规格矩阵。
8. 商品详情标题不同时显示启用和停用，不出现三个以上同级主动作。
9. 制作信息空态的主动作直接进入制作信息编辑；缺生产标签时才提供编辑内元数据子任务。
10. 库存扣减查看态只显示业务摘要和用料表；编辑态才出现方式与数量控件。
11. 配置抽屉的简单字典列表即详情；三字段对象不打开超宽 Drawer。
12. 规格维度在同一右栏呈现主从两列；点单选项在同栏完成列表与详情编辑，不叠 Drawer。
13. 有限候选与搜索候选各只有一种交互；新增第三种 Picker 时机械与设计 review 均失败。
14. 批量改分类只能选零或一个目标；提交后逐项显示成功和失败，失败项事实未变。
15. 分类挪父确认显示受影响子分类数和商品数；看不到数量时不允许确认。
16. 从品牌复制持续说明门店事实独立；复制已有商品设置持续说明会覆盖当前商品哪些分区。
17. 无写权限用户看到完整详情，但看不到编辑入口；不能进入一张全灰表单。
18. 任何用户文案不出现内部技术词、UUID、raw exception 或原始状态枚举。
19. 工作台列表没有复合列和重复表头；规格展开可以逐列比较，不显示工程说明。
20. 每个写场景失败后，owner readback 的版本和业务值不变；未知结果先读回而不是盲目重试。
21. 任取两个不同批次 surface，七族约定无业务理由差异为零。
22. 删除一个 testId 绑定或一个 Journey case 时，L2 双分母门必须真实变红并点名差集。
23. 展开一个按规格商品后，每个 SKU 在父行下独占一行且共享表头；收起后全部子行消失，父行位置不变。
24. 初始列表不请求 SKU 明细；展开父商品只请求该商品的规格摘要，失败显示可重试子行且其它父行不受影响。
25. 商品级批量选择只能选择父行；SKU 子行复选位置保留对齐但不可选，不能被计入“已选择 N 项”。
26. 点击规格子行名称打开父商品详情并定位对应规格；关闭后回到原父行、展开状态与滚动位置。
27. 顶部工作台工具区与当前实现逐项一致：两个视图切换和三个右侧动作的文案、顺序、位置与主次关系零差异。
28. 结果域筛选区与当前实现逐项一致：结果域提示、搜索、状态、来源、重置的两行结构、顺序和重置结果零差异。
29. 新建商品、编辑商品和批量移动分类三个场景逐一打开分类控件，均能展开同一棵分类树、搜索并显示完整路径；
    任一场景出现平铺下拉即失败。
30. 分类挪父的树形选择器中，当前分类及其后代不可选且原因可见；篡改请求仍由 owner 拒绝，树与版本不变。
31. 任取一个写控件，能够逐项说出 contract 业务约束、前端 state 住址、foundation 生命周期与 owner 最终复核；
    任一规则同时住两处或无人负责即失败。
32. 用户可见字符串扫描与人工逐屏审查均不出现 §6.5 禁用词；“商品元数据/当前结果域”只在冻结入口出现，
    “预检/重新读取失败/SKU”在用户可见 copy 中为零。
33. 在 L2 profile 仍为 `FRAMEWORK_ONLY`、本批 fixture/runner/join 任一未就绪时，启动本批 browser L2 必须 fail closed，
    不得把 0 active case 或旧 41 case 报成本批通过。
34. 删除一个 case fixture 的 unchanged oracle、一个 action-request join 或一个 DB section row 后，对应 red fixture
    必须在浏览器执行前或运行中首个相关阶段变红并点名断链。
35. 删除一个必需 secret、加入一个未声明 secret、把 required secret 改为格式非法值、把 binding metadata 的
    expires epoch 改为已过期、复用旧 run cookie/credential、绑定错误命名空间或把 secret-shaped 字段写入
    manifest/log/join artifact，runner 必须分别以 `L2_SECRET_FORMAT_INVALID`、`L2_SECRET_STALE` 等对应 code 在
    fixture/browser business 前失败；cleanup 仍删除本 run 已创建的 credential/session，并以文件不存在和远端
    命名空间零残留 readback 证明。
36. 十个业务列及顺序精确为商品、商品形态、价格和单位、规格或选项、商品属性、制作信息、库存与 BOM、
    更新时间、状态、来源，全部默认常显；删除、隐藏、换序、斜杠合并或出现“显示列”入口时 focused/L2 必须变红。
37. 商品父行商品列严格为名称、编码、分类路径、标签四行；规格子行严格为名称、编码两行。分类路径在所有
    结果域都存在；名称不拼编码；标签最多两个加 `+N`。任一行超四行、缺 Tooltip 或显示内部 ref 即失败。
38. 价格和单位同时展示所有存在的“销售单位/基础计量”并标类型；规格或选项直接列业务内容；商品属性、
    制作信息、库存与 BOM 均以最多四行的业务摘要呈现，不得用数量占位替代规格/选项内容。
39. 在 1280px 和更窄视口中，表格以自身横向滚动完整呈现十列；商品列固定，父商品与规格行始终共享列宽。
    压缩到小于声明最小宽度、改卡片、出现第二条 range 滚动控件或父子错列时 focused/L2 必须变红。
40. 商品和规格价格均为空的合法 fixture 在列表/查看/编辑中显示中性“未设置”，仍可创建、保存、启用和维护
    其它事实；DOM、用户文案和动作原因中无“缺价/缺少价格/缺价数”。本用例不得反向宣称菜单项可无价格。
41. 保存商品时 `productionTagRef` 为空或单值均可；数组、两个不同标签、规格标签覆盖、选项标签增删任一请求
    由 contract/owner 拒绝且商品 version、制作信息和引用事实不变。
42. 规格单独设置只改变制作单显示名称、预计制作时长和制作说明；保存/readback 后所有规格仍显示商品的同一个
    生产标签。点单选项只能增加非负时长和追加说明，不能改变有效生产标签。
43. 目录树“生产标签”列出启用与停用定义；选择任一标签后父列表只含绑定商品，计数按父商品去重，展开显示
    该父商品全部规格且父 total 不变；删除专用筛选参数、混用商品标签参数或前端本地过滤必须变红。
44. 生产标签没有绑定时不伪造默认路由；本批代码、contract、用户文案与测试不得声称生产工作台、路由或分派
    已实现。出现 fallback 标签、默认队列或按规格/选项猜路由即失败。

## 11. 已知边界与非目标

- 不建商品配置独立页面，不建商品编辑独立路由；深链与浏览器后退随裁定放弃。
- 保留目录树现有交互和既有节点；只按 U-CATUI-11 新增“生产标签”一级节点及其二级标签筛选，不重画目录树。
- 不新增销售集合、发布、可售、扫码销售解析、打印机、KDS、生产工作台、生产路由、任务分派、重供应链或导入导出能力。
- 不把库存余额和流水搬进商品 owner。
- 不把 UI 同页理解为 owner、缓存、事务或命令合并。
- 不把当前 focused test、静态 markup 或 testId 存在性写成 browser L2 已通过。
- 本文件不授权 contract、代码、migration、测试执行、DEV、reset、seed、browser L2、UAT、部署或数据操作。

   且两个冻结工作台区域无非授权变化。

6. 工程拆分、state 三住址、testId exact-set 与 L2 双分母均成为可验收要求。
7. contract/owner/generated RTK/App/foundation 的控制权逐控件可对账，无业务规则住在前端猜测层。
