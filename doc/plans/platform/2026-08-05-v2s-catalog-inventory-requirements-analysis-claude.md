# v2s 商品目录与门店轻库存 · 需求分析

## 0. 真相层级（本文所有内容按此优先级取舍）

1. **Dexter 已拍板且要求尊重的裁决**（最高，不重开）：
   v1 catalog Q1–Q6（2026-06-30）、v1 inventory Q1–Q6（2026-07-01）、step4 D-1~D-6（2026-07-08，D-6 按 A12 代码坐实修正版）。
2. **v2s 语料 G-11/G-12**（2026-07-25 正典）——业务叫法与边界锚点。
3. **v6 领域文档 05/07**（业务含义主真相源）+ 06（仅作消费方边界）。
4. **v4 实证**（UX 黄金基线 + 真库数据形态）——交互与数据参照，不是模型权威。
5. v2s 六 kernel 与设计规范——架构落地约束。

冲突处理原则：业务含义以 v6 为准；模型取舍以 v1 拍板为准；架构表达以 v2s kernel 为准；交互手感以 v4 为准。四者冲突且无既有裁决的，列入 §9 开放问题，不擅自裁定。

## 1. 业务问题：为什么现在建、给谁建

**用户任务**：
- 总公司运营者：为品牌维护标准商品库（模板/候选来源），供门店复制。
- 门店管理员：维护本店商品（含规格、选项、套餐、条码、单位），配置本店库存对象与 BOM，执行入库/盘点/人工调整，查看库存现状与变化记录。
- 普通店员：查看库存提示（本期只到管理后台展示；无 POS）。

**为什么是现在**：v2 atlas 已锁定「四域完成并切流后，首个 v2-native 后继领域固定为 `catalog-and-inventory`」。v2s 四域（空间/组织/合同/IAM）已交付并经 R5/RM1 收敛，上游事实（门店、品牌、总公司、任职、数据范围）全部就绪。carryover manifest `:91` 亦已预留：「商品目录/销售集合/库存(v6 05/06/07)按 v6 的合并映射进入业务 app 作为**模块**——不是新服务」。

**核心业务边界一句话**（Dexter Q5 原话，本文全程遵守）：

> **「商品目录是门店组织商品用的；菜单是对商品的重新组织，菜单才是对客的。」**

即本期交付的一切都是**内部组织与管理**能力；对客表达（菜单/可售/沽清消费端）属 06，不在本期。

## 2. 范围裁定

### 2.1 In（本期需求分母）

> **本期的"不能卖"不是缺陷，是边界**：本期不做菜单 → 不产生销售项 → 商品无法被售卖。
> 交付的是**两条完整可用的内部管理线**：商品主数据组织，与门店物料库存管理（建物料、配配方、
> 入库、盘点、看现状与消耗、反查哪些商品在消耗它）。第二条不依赖菜单即可独立跑通。

**Catalog（05）**：
1. 商品库双 owner：总公司品牌库（`HEAD_COMPANY + BRAND`，模板/候选）与门店库（`STORE + BRAND`）；门店从品牌库**pull 复制**（Q6=B，非 push 下发）。
2. 商品 7 形态（v4 UX 精华）：普通销售 / 按 SKU 管理 / 称重销售 / 原材料·半成品·包装物 / 商品型套餐 / 服务·费用 / 权益商品壳（**本期禁用**，仅保留 itemKind 枚举位）。
3. 分类树（一二级管理分类）、静态标签、销售单位字典、商品识别码（条码/PLU/助记码/店内码）。
4. SKU：销售属性维度字典 + 值字典（D-1 保留实体）→ 实时笛卡尔矩阵生成 SKU；商品级标准价硬必填、SKU 行缺价软提醒（A8）。
5. 点单选项：结构化选项组/值（v6 4.10）。**注意**：v1 D-5 裁定 per-item `optionsJson`（v4 实证每商品内联无跨品复用），但 v4 真库案例 C 显示选项组/值是**可复用字典**（凯撒沙拉 3 组共享机制）——两处记录矛盾，列 §9-Q7 求证。
6. 商品型套餐：分组（固定包含/单选/多选）+ 组件（商品或具体 SKU + 数量 + 加价 + 默认）；先禁套餐套套餐。
7. 结构快照契约（读模型）：商品摘要投影（列表工作台/候选选择器）+ 结构快照（供未来 06/11 冻结用，本期只建产出）。
8. 引用完整性：软删不物删、归档预警、`CatalogItemReference` 瘦边表 O(1) 反查（D-6 配套裁决）。
9. 治理状态与来源模式建模保留（`sourceMode` 枚举含 `HEADQUARTER_COPIED` 等；外部同步/导入的**执行**不在本期）。

10. **生产标签**（`ProductionTagDefinition`，归生产域但本期建全，见 DR-6）+ 商品/SKU/选项值三层引用。

**Inventory（07 交易前）**：
1. 门店级库存对象 `StockTarget`（`CATALOG_ITEM | SKU`；**OPTION_VALUE 不能当库存对象**）：消耗单位（引商品计量单位快照）、可选盘点单位+换算（`1 包 = 250 g` 形态，规则见 v6 4.1 第 9–12 条）、允许负库存、低库存阈值。
2. `StockBalance` 当前态读模型（stockState 派生：在库/低库存/缺货/负库存/未知）+ `StockChangeLedger` append-only 流水（幂等=唯一约束；**余额可由流水重建**；无静默重算来源）。
3. `ProductBom / ProductBomLine`（D-2 独立表）：owner 可为商品/SKU/**选项值**（「加珍珠扣珍珠、换燕麦奶」机制）；`lineSign` 保留（Q5=A）；按 SKU 管理商品的主壳不配库存/BOM（A11）。
4. 库存与 BOM 配置**随商品保存一次提交**（D-6 坐实版）：前端 whole-save 携 `inventoryBomRules[]`，后端在**同一事务**内拆分落 catalog 与 inventory 两个 owner，每节点带 `expectedProductBomVersion + expectedStockTargetVersion` 双 CAS，整体成败。可配态依赖后端 `inventoryBomWorkbench` snapshot 读模型（treeNodes/nodeRules.allowedModes/bomComponentCandidates）。
5. 入库（增量）、盘点（存量覆盖）、人工调整——全部落流水；门店库存现状页（v4 六分类：全部/需处理/低库存/无库存/负库存/未知）。
6. 库存提示产出侧：`stockState/displayStockQty` 作为**余额派生读**（v1 裁定砍独立 SalesStockView 表），供未来 06 消费；本期无消费者。
7. `StockDeductionPlan / StockRestorePlan` 两族：**建模保留、interface-reserved，不建执行**（等交易域）。

## 3. 业务概念与术语（对齐 G-11/G-12 与 v6 术语表）

沿用语料正典叫法：商品（`CatalogItem`）、商品库（`ProductCatalog`）、SKU（规格单元）、选项（怎么做/加什么）、套餐（商品型组合）、库存对象（`StockTarget`）、库存流水、BOM、库存提示。

**禁用词**（G-11 明令 + v6 废弃词表）：`WEIGHED_ITEM`、`BENEFIT_PRODUCT`、`OPTION_ITEM`、`MATERIAL_ITEM`、`SEMI_FINISHED_ITEM`、`PACKAGING_ITEM`、`product_kind`、`menu_release`。称重是 `measureMode=WEIGHED`；原材料/半成品/包装物是 `STANDARD_ITEM + materialRole + usageCapabilities`。

历史同义异名（G-12）：v4 `isolation_context_ref` ≡ v2s `group_workspace` 语境，**不得并用**；`is_key_material_for_sales_stock_view` 只作历史参考。

**新增封闭集合清单**（按本仓 closed-set-single-source 纪律，设计期必须逐个声明规范源与 owner；这是从 RP-12 教训直接继承的要求）：

## 3.5 业务事实（实现不得搞错的语义；每条都有出处）

本节是给实现看的业务真相清单。**每一条都是"搞错了会做出错误模型"的**，不是背景介绍。

### 3.5.1 商品与"卖"的关系 —— 最容易搞错的一条

**商品不卖东西。卖的是菜单里的销售项。**

- 销售项（`SalesItem`）**必须且只能引用一个商品**，但它有**自己的身份**：
  菜单商品行的业务锚点是 `salesItemRef + salesSectionRef`，**不是 `catalogItemRef`**（v6-06 §4.4）。
- **同一个商品可以在不同菜单版本、不同分区、甚至同一版本的不同集合里形成多个销售项**，
  各自有自己的：开放哪些规格、开放哪些选项、展示名/图/摘要覆盖、挂牌价覆盖、排序、可见性、动作能力。
- 销售项创建后**不允许换绑到另一个商品**；选错商品只能删掉重建。
- 商品目录新增 SKU **不会自动进入已发布的菜单**。

**推论（实现必须遵守）**：

1. **商品上不存在"卖不卖"字段，也不许加。** 一个商品在两个菜单里可以一个卖一个不卖，
   任何挂在商品上的布尔都表达不了，加了就是错误模型。
2. 商品的 `ACTIVE/INACTIVE` 只回答"这个商品还能不能被引用"，**不回答"卖不卖"**（v6-05 §6）。
3. 本期不做菜单 → 不产生销售项 → **本期不存在"可售"这一概念**，无需也不得为它预留开关。

### 3.5.2 商品的价格只是"标准标价"，不是成交价

价格是**分层**的（G-11 语料）：标准价 → 集合挂牌价 → SKU 挂牌价 → 营销权益价 → 支付实付。

- 商品目录只拥有**标准标价**（默认价/基准价）。
- 会员价、活动价、团购价、渠道价、时段价**一律不在商品域**。
- 商品级标准价与 SKU 级标准价是**两个层级**：v4 实测商品级标准价**硬必填**（缺则保存失败），
  SKU 行缺价只是**软提醒**（黄徽标可存草稿）。

### 3.5.3 总部品牌库与门店库：是"复制"，不是"下发"

- 总部/品牌商品库起步期只是**资料模板库和候选来源**，
  **不承担强下发、字段锁死、必售项、强继承**（v6-05 §4.1、v1 Q6=B）。
- 门店从品牌库**复制**后形成门店本地商品，**拥有独立生命周期**；
  总部商品后续变化**不自动影响**已复制的门店商品。
- 总部商品**停用只表示不再作为新复制候选**，不影响已复制门店商品和已发布菜单。
- 系统只维护**来源关系**（用于追溯与人工参考）：**不自动提醒、不自动生成差异、不自动下发、不做字段锁死**。
  总部要门店跟进，靠**人工通知**，门店自行决定是否复制来源内容。
- **总部的库存/BOM 只能是"规则模板"**：可以表达"这个标准商品建议怎么建库存对象、配什么组件、消耗多少"，
  但**不产生任何实际库存对象、余额、流水或门店实际 BOM**（v6-07 §2.3）。
  复制到门店时必须**显式映射为门店本地事实**；不能共享总部库存对象，总部模板不参与门店扣减。

### 3.5.4 原材料、半成品、包装物"也是商品"

- **不存在独立的物料模型**。原材料、半成品、包装物统一用
  `STANDARD_ITEM + materialRole + usageCapabilities[]` 表达（v6-07 §2.2、v6-05 §4.2）。
- `materialRole` 首批三值：`RAW_MATERIAL / PACKAGING_MATERIAL / SEMI_FINISHED`；
  当能力含 `STOCK_MANAGED / BOM_COMPONENT / PRODUCIBLE` 任一时**必填**。
- 物料**默认不作为普通销售项**；确需零售化必须显式具备 `SELLABLE` 并通过发布校验。
- **能力是要被校验的，不是描述**：创建销售项必须校验被引商品含 `SELLABLE`；
  BOM 行引用组件必须**硬校验组件含 `BOM_COMPONENT`**（v1 §0.1 明列）。

### 3.5.5 规格（SKU）与点单选项是两件事，且互斥

- **SKU 回答"规格单元"**（大杯/中杯/小杯、大份/小份、整箱/单瓶）；
  **选项回答"怎么做、加什么"**（做法、口味、温度、甜度、熟度、加料、餐盒、备注）。
- SKU 由**销售属性维度 + 值字典**组合生成（如维度「饮品杯型 DRINK_SIZE」× 值「小/中/大杯」）；
  同一商品下启用中的 SKU 属性值组合**必须唯一**。
- **强 SKU 矩阵模式与点单选项互斥**：商品一旦进入按 SKU 管理，
  **不能再维护选项**，前端必须隐藏入口、后端必须拒绝矛盾 payload（v6-05 §4.8）。
  v4 实测这一点体现在 **tab 层**——按 SKU 管理商品根本没有"点单选项"这个页签。
- 选项值若产生库存消耗，**不靠 `linkedCatalogItemRef` 绕行**，
  必须由库存域配 `ProductBom(owner=OPTION_VALUE)`（v6-05 §4.10）。

### 3.5.6 生产标签属于生产域，商品只是引用它

**这是一个生产域拥有的完整对象，不是商品上的一个标签字段。**

```
ProductionTagDefinition            （v6-13 §4）
  productionTagRef
  projectRef              ← 项目级定义
  storeRef?               ← 门店可覆盖
  tagCode / tagName
  tagKind  = PRODUCTION | PACKAGE | LABEL | HANDOFF | REVIEW | OTHER
  scope    = PROJECT_DEFAULT | STORE_OVERRIDE
  enabled / version
```

- 定位：**商品与处理面之间的稳定语义纽带**。
  商品目录**可以引用**生产标签，但**不能直接绑定工作台、队列、KDS、打印机或履约 topic**（v6-13 设计判断 1）。
- **停用标签必须校验是否仍被启用规则引用**；历史工作单只能按已冻结快照解释（v6-13 §798）。
- 商品侧的承接对象是 `PreparationProfile`，可挂在**商品 / SKU / 选项值**三个层级：
  `stationTags[]`、`printTags[]`、`estimatedDuration?`、`preparationNotes?`（v6-05 §4.13）。
  v4 前端实际字段亦为 `productionTagOptions`（候选来源）/ `stationTags` / `printTags` /
  `estimatedPreparationSeconds` —— 证明前端就是从标签定义集合里挑选。
- **商品页不能直接选择工作台、队列、KDS、打印机或 topic**（v6-13 §1112）。

### 3.5.7 称重：重量是下单时的输入，商品上只做声明

- 称重**不是独立商品类型**，是 `measureMode=WEIGHED`（v6-05 §4.2；G-11 禁用 `WEIGHED_ITEM`）。
- **真实使用场景在 POS**：店员选中菜单里的称重销售项（它关联一个称重商品），
  **必须同时输入重量或从电子秤读取**，才产生最终价格。
- 因此：**商品上永远不存重量**；价格 = 单价 × 重量，计算发生在下单时刻。
- 商品域这一侧要做的**全部**就是：声明按重量卖、给出计价单位、以及识别码（PLU/条码）。
  管理后台**没有称重交互可做**。
- 时价同理**不是商品类型**，是销售入口的动作能力；实际录入价格属订单输入证据。

### 3.5.8 单位是三层，不能混

| 单位 | 归属 | 作用 |
| --- | --- | --- |
| **销售单位** | 商品目录 | 按份/杯/瓶/斤/kg/次/小时卖 |
| **消耗单位** | 库存 | **库存真相单位**；余额、BOM 消耗、低库存阈值、库存提示**一律按它计量** |
| **盘点单位** | 库存 | **仅录入便利**（1 包 = 250 g）；不改变余额单位、不参与扣减、不让 BOM 改用它 |

- 消耗单位**来自商品计量单位快照**，**不得另建一套库存专用单位**（v6-07 §4.1 规则 7）。
- 盘点录入 2.2 包 → 流水保留原始录入「2.2 包」+ 换算快照，余额更新为 **550 g**（v6-07 §3.7）。
- 换算规则必须是**正数、有限小数或分数**；**禁 0、负数、无限精度、自由文本**。
  盘点单位与消耗单位相同时应**关闭盘点单位**，而不是配一条自我换算（v6-07 §4.1 规则 12）。
- **单位或换算变更只影响后续流水**；历史流水与计划**必须冻结当时的单位与换算快照**，不得重解释历史数量。

### 3.5.9 库存的事实结构

- **流水是事实，余额是读模型**：成功的扣减/恢复/覆盖/人工调整**必须先写流水，再更新余额**；
  余额可由流水重建，日常查询不回放（v6-07 §4.2）。
- **没有"系统重算"这种流水来源**；重算只重建视图，不改变库存事实（v6-07 §4.3 规则 3）。
- 库存状态五值：在库 / 低库存 / 缺货 / **负库存** / 未知。
  **负库存由库存对象上的显式开关决定**，不允许时扣到负应当拒绝而非静默记负。
- 余额更新用 `stockTargetRef + version` **乐观锁**，冲突短重试并追加正确流水。
- **库存对象固定到门店**；同一商品/SKU 在不同门店是不同的库存对象和余额。
  **不做总部跨店共享库存、不做跨店调拨、不做集团仓库**（v6-07 §2.3）。
- **选项值不能成为库存对象**，只能作为 BOM owner 去消耗别的库存对象（v6-07 §4.4 规则 8）。
- BOM 行支持**正负数量**（`lineSign`），用于「加珍珠」「不加珍珠」「换燕麦奶扣回普通牛奶」。
- **BOM 合并顺序**：SKU BOM 或商品默认 BOM → 选项/加料 BOM → 经营入口覆盖 BOM（v6-07 §4.4 规则 4）。
- **无 BOM 不阻断销售**，预检可返回"未配置 BOM"（v6-07 §4.4 规则 6）。
- 按 SKU 管理商品的**主商品壳不能配库存或 BOM**，配置落在 SKU 上
  （v6-07 §3.1；v4 实测拿铁根节点为"无库存控制"，三个 SKU 各配 14/18/24 克咖啡豆）。

### 3.5.10 库存提示不是可售

- 库存域可以输出库存状态与提示，但**不能**直接改菜单、改发布、形成可售控制、阻断订单或履约（v6-07 §2.5）。
- **07 说"没货了"（事实），06 决定"下不下架"（意图）**；**低库存不自动下架**。
- **不得由有库存推可售、缺货推菜单下架、库存流水推订单或结算**（G-12）。
- 已成立的订单**不因库存变化改写**；退菜**不自动恢复沽清**。

### 3.5.11 删除即归档

- 已被订单、菜单快照、库存流水、BOM、识别码或外部映射引用的商品与 SKU
  **不得物理删除，只能停用或归档**（v6-05 §4.2、§4.9）。
- 已被计划或流水引用的库存对象同理（v6-07 §4.1 规则 4）。
- 权威配置**不能物理删除**，历史计划必须可审计（v6-07 §4.5 规则 5）。
- **BOM 行引用组件时，不得自动创建组件的库存对象**（v6-07 §4.1 规则 3）——
  库存对象只能由独立库存控制、初始化导入或受控维护流程创建。

## 4. 领域模型需求（数据侧）

### 4.1 规模基线（来自 v4 真库数据分析，非估算）

v4 UAT 真库：catalog_item=73、stock_target=20。三个代表商品实测：拿铁（SKU 变体）v4 需 **17 行/9 表** → 新模型 **11 行/5 表**；套餐 4 行结构表 → 1 个 JSON 列 + N 行引用边；双份真相（SKU 坐标表 label）被消除。商品详情查询触及表数 ~9→~4。**新模型的存储/效率优势已被真库数据验证，不需重新论证。**

### 4.2 目标表族（v1 拍板规模，v2s 表达）

- **catalog ≈ 10 owned 表 + 1 派生投影**：ProductCatalog / CatalogItem（JSON 折叠：displayJson〔描述/媒体 ref/自由属性/生产提示〕、variantDimensionRefs、compositeJson、optionsJson 或 optionRefs〔见 §9-Q7〕、tagRefs）/ ProductSku（attributeValueRefs JSON）/ CatalogSkuSalesAttribute + Value（D-1 字典）/ CatalogCategory / CatalogTag / SalesUnit / ProductIdentifier / CatalogItemReference（边表）+ 摘要投影（含搜索）。
- **inventory 5 表**：stock_target / stock_balance / stock_change_ledger / product_bom / product_bom_line；+ interface-reserved 的 plan 四表**建表不建执行**（v6 §10「模型初始化必须完整，功能分阶段开放」）。
- JSON 折叠判据沿用 Dexter 定的原则：参与实时判断/需排序搜索过滤唯一约束/跨聚合 ref 引用 → 关系列；否则 JSON（形状在 contract 定义，非裸 map）。**这与 v2s「JSONB 装一组 key 是被偏好的」记忆一致。**

### 4.3 v2s 架构映射（v1 微服务假设 → v2s 单 deployable 的改写）

这是 v1 拍板到 v2s 落地**唯一需要系统性改写**的层面，且全部是简化：

| v1/v6 假设 | v2s 表达 |
| --- | --- |
| catalog、inventory 两个微服务 | **两个 owner 模块**（`modules/catalog`、`modules/inventory`），各占 schema，单库单 Flyway |
| D-6 跨服务编排 + 双 CAS | **同一 `REQUIRED` 事务**内 edge 编排调用两个 owner 的公开 typed command，双 CAS 语义保留（`COMMAND_REQUIRED_TRANSACTION` kernel 天然满足，比 v1 更简单可靠） |
| 事件驱动扣减（11→07 MQ） | **不建 MQ**（kernel `NO_MQ`）；未来交易模块在同一事务内调用 inventory 公开 command——扣减计划模型不变，触发机制换为同步 typed command |
| hint 经 topic 发布 | 无 topic；hint = 余额派生**读投影**，未来 06 直接查询 |
| shard by gw + 派生祖先键 | 无分片；祖先链（project/store）作为普通列满足「按项目/门店查」任务读 |
| catalog 结构快照「跨服务契约查询」 | 保留**公开 typed API 不直连表**的边界（kernel `TASK_READ_JOIN` + module-dependency-registry 声明），实现为模块间接口 |

### 4.4 与 v2s 既有机制的接点

1. **媒体资产**：商品图片走既有 platform-asset（staging→bind grant→claim）；`mediaRefs[]` 存 **assetRef 有序列表 + 主图标记**，绝不存 URL。CDN 就绪性与红线见 **DR-3**；claim 语义与图片约束见 **Q10/Q11**。
2. **审计**：全部写操作入既有 audit 机制（v6 §9「所有写操作都必须落审计」；沿用 v2s AuditChangeJson——其 writer 统一是全工程终稿 P2-3.1 的既有建议，本域实施时受益）。
3. **授权**：新增 capability（`product.catalogItem.*`、`inventory.*` 族）+ 新页面进 admin-catalog；门店页面 data scope=STORE，总部品牌库页面 scope=HEAD_COMPANY（v2s 三层 scope 模型现成）。
4. **扩展字段**：v2s extension 机制 host 现为 8 值——商品**不建议**成为 extension host（理由见 §9-Q2 的推荐项）。
5. **可观测**：全部新 operation 自动进入 S2 已建的 completion observer（154→+N）；分母对账纪律（RP-02 教训）：新增 operation 时 scenario facts/诊断分母同步跟随。
6. **计量单位**：catalog `SalesUnit` 是销售单位字典；inventory 消耗单位**引用商品计量单位快照**（v6 4.1 规则 7：不得另建库存专用单位）。

## 8.5 Dexter 已裁决（2026-08-05，本轮）

### DR-1｜`shapeKey` 入库，且 **shape 作为契约约定前后端能力**

Dexter 原话：「shapeKey 入库，shape 应该作为契约约定前后端的能力」。

这比"存一个字段"强得多。它确立的是：**商品形态是一份契约产物，前后端从同一个生成源读取**。

**落点**：`contracts/catalog/` 层（v2s 既有的静态业务目录层，与 `openapi/`(wire)、`protocol/`、`policy/` 并列），
新增一份 shape manifest，由既有 generator 生成 Java 与 TS 两侧，走 `--check` 字节比对 + count 断言。
v4 已证明该形态可行（其 `catalog-item-editor-manifest.ts` 就是 generated）。

**该契约必须约定的能力面**（逐条都是"前后端必须一致否则出 bug"的）：

| 契约内容 | 前端消费 | 后端消费 |
| --- | --- | --- |
| `shapeKey` 全集（7 值） | 形态下拉与说明文案 | 入库校验、拒绝未知值 |
| shape → `itemKind`/`measureMode`/`usageCapabilities`/`skuMode` 派生 | 只读展示派生字段 | 落库时按 shape 推导，**不接受前端传入派生值** |
| shape → tab 集 | 渲染哪些 tab | 拒绝该 shape 不该有的 payload（如按 SKU 管理商品提交 `optionGroups`） |
| shape → 字段可见性/必填 | 表单渲染与校验 | 服务端同规则复校 |
| shape → 库存/BOM 可配节点类型与允许模式 | 节点树 enable 态 | `inventoryBomRules` 合法性校验 |
| shape 的固定性（创建后不可改；配了下游数据即锁） | 编辑态置灰 | 变更命令拒绝 |

**由此获得的性质**：
- "按 SKU 管理商品与点单选项互斥"从**运行时报错**升级为**契约层事实**（v4 已在 tab 层体现，v2s 把它写进契约）；
- 前后端能力漂移变成**编译期/生成期可检测**，而不是靠人对齐；
- 新增形态是一次契约变更 + 重新生成，不是散落多处的 if 分支。

**约束**：shape manifest 是**静态业务目录**，不是 wire 契约——它不进 OpenAPI，
与 D3 裁定的"owner 内部封闭集合不上 OpenAPI"一致。`shapeKey` 本身作为字段出现在 wire 上，但其**语义表**在 catalog 层。

### DR-2｜商品描述属性用自由 map

Dexter 裁定：`CatalogItem.attributes_json` 自由 map（用户自定义、纯展示、不校验），
沿用 v1 Q2 原话「每店每品类差异极大，定义 schema 不现实」。

**与 v2s extension 机制的分界必须写进设计**（防未来混用）：

| | 自由 map（本域） | extension definition（既有机制） |
| --- | --- | --- |
| 谁定义 | 运营者自己边用边加 | 运维在 platform-admin 预先定义 schema |
| 是否校验 | 否，纯展示 | 是，按定义校验 |
| 适用 | 商品描述性属性 | 组织/合同/门店等治理类实体 |

**需要筛选的属性不进自由 map**（自由 map 无法高效筛）——过敏原一类走 `CatalogTag`。

### DR-3｜CDN 就绪 + 商品多图 + 未来菜单复用商品图

Dexter 裁定：「需要未来能无缝或很少代价支持 CDN，但本期仅在本机 DEV 和 UAT 运行」
「商品支持多个图片上传」「后续做菜单时，菜单 item 的图片可以从商品中选择已有图片」。

**好消息：CDN 能力当前已经具备，本期只需不破坏它。** 我核实了现有字节：

```
MinioAssetObjectStorage:88   publicUrl(key) = publicBaseUrl + "/" + bucket + "/" + validKey(key)
V20260726_090000:28          group_workspace.logo_asset_ref VARCHAR(128)   ← 业务侧存 ref，不存 URL
```

URL 是**读时现算**、base 可配；业务表存 `assetRef`。→ **换 CDN = 换 `publicBaseUrl` 配置**，零代码改动。

**因此本期的真实要求不是"建 CDN"，而是三条不许破坏的红线**：

1. **任何地方都不得持久化 URL**——商品 `mediaRefs[]` 存 assetRef，JSON 内也是 assetRef；
2. **未来菜单发布冻结快照时，冻结 `assetRef` 而不是 URL**。这是最容易犯的错，
   因为"冻结快照"的直觉是冻结当时看到的一切。一旦快照里冻了 URL，CDN 迁移就会打断历史菜单；
   → 本期虽不做菜单，但**结构快照契约（§2.1-7）现在就要把这条写进契约注释与红测**；
3. **前端不得拼接或缓存 URL**，一律用后端返回的 `publicUrl` 字段。

**多图需求**：`mediaRefs[]` 有序列表 + 一张主图标记（v4 实见「拿铁咖啡主图」标签）。
另需约定单商品图片数上限。注意既有 `asset_content.size_bytes <= 5242880`（5MB/张）。

**⚠️ 「菜单复用商品图」触发一个必须现在裁决的约束（见 §9-Q10）**：
我核实 `staged_asset` 的 claim 模型是 **1:1**——

```
staged_asset:      claimed_by_type VARCHAR(64), claimed_by_id UUID     ← 单一 claimer
asset_bind_grant:  asset_ref UUID PRIMARY KEY                          ← 每资产一张 grant，消费即止
```

即**一个资产只能被一个业务对象 claim**。菜单 item 要复用商品已有图片时，它无法再 claim 同一资产。
这不是本期功能，但**本期的资产语义选择会决定未来是否要改表**。

### DR-4｜asset 的 claim 语义 = 归属，引用 = 使用

Dexter 2026-08-05 采纳推荐项 A。

**语义定义**（必须写进 asset 模块文档与本域设计，防未来两种理解打架）：

- **claim 表达"这份字节归谁所有、生命周期跟谁走"**，保持现表的 1:1
  （`staged_asset.claimed_by_type/claimed_by_id`、`asset_bind_grant.asset_ref` PK 均不改）；
- **"谁在使用"由业务侧的引用表达**——未来菜单 item 存**同一个 `assetRef`**，但**不重新 claim**；
- **删除保护靠引用反查**：商品图片被其他业务对象引用时不可删；`ON DELETE RESTRICT` 已现成，
  引用反查沿用 `CatalogItemReference` 同一思想（瘦边表 O(1) 反查）。

**因此不改资产核心表。** 本期落地要求只有一条：
商品的 `mediaRefs[]` 与未来快照都存 `assetRef`，使"多处引用同一资产"天然成立。

### DR-5｜商品图片约束现在就定

Dexter 2026-08-05 采纳推荐项 B。

- **张数上限**：单商品主图 1 张 + 附图上限 N（N 建议 5，最终由 IA 详设按列表/详情实际布局定）；
- **单张大小上限**：建议 ≤2MB（现有 `asset_content` 硬上限 5MB 保持不变，本域取更严值）；
- **缩略图策略**：本期**不生成缩略图**，但列表读模型只返回主图 `assetRef`，
  不返回附图，避免列表页拉全部图片；
- **理由**：上限属于"数据进来后再收紧就有存量问题"的一类，必须前置；
  缩略图生成属"很少代价支持 CDN"的后续项，可随 CDN 一起做。

### DR-6｜生产标签要有一整套能力

Dexter 2026-08-05 裁定：「生产标签属于生产域，但要关联在商品上。本期虽然没做完整的生产域，
但是**要有生产标签的一整套能力**」。

**因此本期建的是 `ProductionTagDefinition` 这个完整对象**（结构见 §3.5.6），而不是一个平面标签字典：

- **项目级定义 + 门店覆盖**（`projectRef` / `storeRef?` / `scope=PROJECT_DEFAULT|STORE_OVERRIDE`）；
- **六种标签类型**（制作/打包/标签/交接/复核/其他）；
- **启停与版本**；
- **停用时校验是否仍被引用**；
- 商品侧在**商品 / SKU / 选项值**三个层级引用它（`stationTags[]` / `printTags[]`），
  另有预估制作时长与制作提示。

**明确不建的是它下游的生产运行时**：处理面、待办队列、工作单生成规则、路由、现场动作、
叫号、交接、出餐策略、KDS、打印机绑定。

**红线**（v6-13 §1112）：**商品页不得直接选择工作台、队列、KDS、打印机或 topic**——
商品只能挂标签，由标签在未来连接处理面。

### DR-7｜商品与库存分为两个 owner

Dexter 2026-08-05 确认：分开。

配套要求（防重演此前的跨模块声明缺失）：库存校验"某商品能否作为 BOM 组件"必须走
**商品侧的公开 typed 接口**（v1 原话「经 catalog 轻契约 `GetCatalogItemCapability`，不直连 catalog 表」），
并在 `module-dependency-registry` 中**主动声明**这条依赖，不得等门报红再补。

用户感受不受影响：商品保存仍是**一个按钮、整体成败**（DR 之外的 D-6 双 CAS 形态不变）。
