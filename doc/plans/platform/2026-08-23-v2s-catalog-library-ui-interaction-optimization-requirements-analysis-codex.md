## 0. 结论先行

当前商品库的问题不是 14 张截图中的若干间距、字号或按钮问题，而是一套错误交互模型在所有页面中反复出现：

1. 页面以 contract 字段和 CRUD 实体为中心组织，不以用户任务组织。
2. 查看、编辑、创建、治理和复制被塞进同一 Drawer 或 Modal，用户无法稳定判断自己是在“看事实”还是“改事实”。
3. 为了复用编辑器，部分查看态直接把表单控件全部禁用；无写权限时，一些编辑 Drawer 也只是把整张表单禁用。**禁用表单不是详情展示，必须作为全局反模式退役。**
4. 简单字典、父子字典和复杂业务定义都被塞进 1200px 的六 Tab Modal；复杂定义再从 Modal 上叠加宽 Drawer，形成上下文、焦点和滚动层级混乱。
5. 商品详情 Drawer 在标题区同时展示编辑、启用、停用、归档、作废并重建、复制等动作，互斥或不可用动作也持续占位。
6. 商品列表、规格展开行和详情大量暴露 `SKU`、内部枚举、代码拼接、斜杠复合列、技术说明和过小文本，无法支持运营人员快速扫读。
7. 当前源码已出现业务规则和 UI 形态漂移：商品分类已裁定为可空单值，但批量改分类仍使用多选控件；“制作信息”空态给出的主要入口却是“管理制作处理标签”，没有直接完成当前任务。

推荐的统一目标不是继续逐页美化，而是建立以下交互体系：

```text
商品库工作台
  ├─ 目录树 + 商品结果表：找商品、比较商品、发起批量任务
  ├─ 商品详情 Drawer：快速阅读已保存事实，纯展示，不挂表单
  ├─ 商品编辑工作区：完整编辑一个商品，独立于详情展示
  ├─ 商品配置页面：维护标签、单位、规格维度、制作处理标签、商品属性和点单选项定义
  └─ 专题向导：从品牌导入、复制其他商品设置、治理转正
```

核心规则固定为：

- 详情只回答“现在是什么”，使用业务摘要、说明列表、状态标签、只读表格和空态，不渲染禁用的 `Input`、`Select`、`Radio`、`Switch` 或 `Form`。
- 编辑只回答“我要改什么”，明确进入、明确保存/取消、显示未保存状态、按业务分区定位错误。
- 没有独立详情任务的简单字典，列表行本身就是只读事实；编辑时再打开尺寸与内容匹配的输入面，不制造一张禁用表单。
- Modal 只承担短小原子输入或确认；复杂、持续、多步任务使用页面或专用工作区；Drawer 只承担快速详情或中等复杂度的单对象任务。
- 用户界面只用业务语言；contract 声明机器结构与准入，owner 最终复核，UI 不靠隐藏或禁用承担业务防线。

## 1. 本稿的证据分母

### 1.1 用户反馈分母

Dexter 标注的 14 张界面截图是高价值问题样本，但不是本稿的页面分母。它们覆盖：

- 商品配置六个 Tab；
- 商品属性、点单选项、规格维度的新建或编辑弹层；
- 商品列表与规格展开行；
- 商品详情基础、规格和制作信息；
- 库存与 BOM 内容。

本稿按 Dexter 后续要求扩展到当前商品库完整 UI 闭包，不因某个界面未截图就跳过。

### 1.2 当前 V2S 源码分母

当前 `apps/frontend/operations-admin/src/features/catalog-management/ui` 有 12 个生产源码文件：11 个 TSX 共 13,577 行，另有 1 个候选读取 hook TS 共 78 行，合计 13,655 行；此外有 3 个 focused test 文件。主要复杂度集中在：

- `CatalogItemDrawer.tsx`：5,677 行；
- `CatalogDictionaryDrawer.tsx`：2,031 行；
- `CatalogWorkbenchPage.tsx`：1,742 行；
- `LocalCatalogCopyDrawer.tsx`：1,260 行；

- `BrandCatalogCopyDrawer.tsx`：755 行；
- `CatalogInventoryBomWorkbench.tsx`：604 行。

代码行数不是业务结论，但这里能解释一个可见事实：单个组件已经同时承担宿主、查询、详情、编辑、创建、确认、字典跳转、复制和治理，多种用户任务被迫共享同一视觉和生命周期。

### 1.3 V4 与 V6 的使用方式

- V4 只是只读参照用例，不是目标方案、视觉基线或交互模板。它只能帮助回答“过去怎样处理过这个任务、哪些做法已经暴露问题、某个拆分是否具备可行先例”；本稿的推荐方案必须重新从 V6 业务本质、当前用户 Journey、任务复杂度和 V2S 真实反例推导。`CatalogItemDrawerReadonlySections`、`CatalogSkuMatrixTable`、`OrderingOptionsReadonlyTable` 仅证明“读写分离、规格表和任务型组件可行”，不因此成为必须沿用的页面形态。
- V6 是业务模型与 owner 边界来源，不直接规定页面长相。商品目录回答“这是什么”；销售集合回答“怎样卖、在哪里卖、何时发布”；库存域回答库存对象、余额、流水和 BOM。商品库 UI 不得把商品启用解释成已上架、可售、已发布或库存充足。
- 当前 V2S 已接受的商品单位、库存/BOM、条码与标识、制作信息、商品属性库和点单选项库语义继续有效；本稿优化交互，不回退这些业务规则。

## 2. 用户是谁，真正要完成什么

### 2.1 主要 Actor

1. 总部商品资料维护者：维护品牌商品模板和可复用定义，供门店复制使用。
2. 门店商品资料维护者：维护门店自己的商品事实、规格、条码与标识、属性、点单设置和制作信息。
3. 门店库存维护者：在可写范围内维护商品/SKU 的库存扣减方式和用料规则；实际余额与流水在门店库存管理查看。
4. 只读运营人员：快速查找商品、理解当前配置、确认差异和引用，不应被带进禁用编辑器。

### 2.2 八类用户任务

| Journey | 此刻任务 | 成功结果 |
| --- | --- | --- |
| `J-CATUI-01` 查找商品 | 按分类、标签、状态、来源或关键词找到目标商品 | 结果域清晰，能快速比较名称、规格、价格、状态和配置完整度 |
| `J-CATUI-02` 查看商品 | 不改变数据，理解一个商品当前是什么、有哪些规格和关联 | 所有事实用业务语言展示，当前状态与来源可解释，没有禁用表单 |
| `J-CATUI-03` 新建商品 | 建立最小商品身份，再继续补完整资料 | 最小信息原子创建草稿，随后进入明确的编辑工作区 |
| `J-CATUI-04` 编辑商品 | 修改一个商品的完整资料并一次保存 | 只看到适用于当前商品类型的分区；草稿、错误和保存结果可定位 |
| `J-CATUI-05` 维护商品配置 | 维护商品会复用的标签、单位、规格维度、属性和点单选项定义 | 在稳定、可返回、可搜索的管理入口完成，不干扰商品列表上下文 |
| `J-CATUI-06` 批量整理 | 对已选商品批量改分类、标签、状态或归档 | 提交前看清目标和影响，提交后逐项知道成功与失败 |
| `J-CATUI-07` 复制或导入 | 从品牌库创建门店商品，或把已有商品设置复制到当前商品 | 来源、目标、覆盖范围、冲突和结果始终清晰 |
| `J-CATUI-08` 生命周期与治理 | 启用、停用、归档、作废重建或治理外部临时商品 | 只展示当前可执行动作，危险动作有影响说明和 owner readback |

### 2.3 不得从商品库推导的结果

- 商品“启用”不等于已进入销售集合、已发布、终端已生效或当前可下单。
- 有库存对象或有 BOM 不等于当前可售；库存不足也不直接等于菜单下架。
- 总部商品变更不等于门店自动继承；品牌复制是显式任务。
- 制作单显示名称不等于已配置打印机、打印模板或 KDS。
- 详情中显示关联事实，不代表商品 owner 可以编辑该关联 owner 的全部事实。

## 4. 十一类共性问题与根因

### 4.1 查看态和编辑态没有稳定边界

`CatalogItemDrawer` 用 `mode` 在同一宿主切换读写；`CatalogInventoryBomWorkbench` 更直接用 `readOnly` 禁用同一组输入控件；定义库在无写权限时仍允许进入编辑 Drawer，只把控件禁用。用户因此把“灰掉”理解成字段当前不可改、自己没权限、数据还没加载或这就是详情，感知不一致。

根因是把“复用组件”误当成“复用用户界面”。正确复用点应是数据 presenter、字段描述、业务格式化和候选读取，不是把编辑表单灰掉。

### 4.2 Surface 选择按开发方便，而非任务复杂度

六个定义库被放入一个 Modal；Modal 上再开 Drawer；商品 Drawer 上再开 Modal 或另一个 Drawer；三字段属性也使用 1024px 宽 Drawer。界面尺寸与任务持续时间、信息量和是否需要深链/返回完全不匹配。

### 4.3 技术模型泄漏成用户信息架构

`SKU`、`BOM`、`shape` 派生标签、内部枚举、`owner`、`readback`、`按需读取不改变结果域` 等实现语言持续进入界面。用户真正关心的是“规格”“如何扣库存/使用哪些原料”“来自哪里”“能否继续操作”。

### 4.4 一个位置同时承担太多动作

详情标题区堆编辑、启用、停用、归档、作废重建、复制；字典行堆编辑名称、停用、删除、作废并重建；选项行堆上移、下移、删除。动作数量没有按高频、状态、危险级别和当前任务分层。

### 4.5 数据密度和控件密度失衡

列表用大量 `size="small"`、12px 辅助字和 text/link 按钮；编辑 Drawer 又留下大片空白。既没有真正的高密度表格，也没有舒适的表单节奏。控件小不等于信息密度高，空白大也不等于清晰。

### 4.6 列表不支持快速比较

复合列把多个问题压在一起，规格展开行又变成自由文本串。用户无法顺着同一列比较商品，异常信息也混在价格或库存摘要中。

### 4.7 空态没有给出当前任务的下一步

“尚未设置制作信息”后给“管理制作处理标签”；“暂无内容”常只是一行文本；空态没有说明为什么重要、是否适用于当前商品、应点击什么完成。

### 4.8 只读权限通过禁用控件表达

权限应决定入口和可执行动作；详情仍应正常阅读。把整个表单禁用会让只读用户得到最差的详情体验，也让“权限不足”和“业务不可修改”混为一谈。

### 4.9 业务单值和 UI 多选漂移

批量分类仍使用 `Select mode="multiple"`，说明历史交互组件没有随已裁定业务模型一起收敛。这个反例证明 UI 优化必须逐项对账 contract，不能只换皮。

### 4.10 旧决策被当成永久页面形状

2026-08-17 与 2026-08-20 的既有决策明确选择了四 Tab、后扩成六 Tab 的统一商品配置 Modal；当时解决的是“入口散乱和事实分离”，并不证明六个持续维护任务长期适合 Modal。当前真实体验已经提供了新的反证，本轮需要重新裁定 surface，而不是被旧 Modal 决定锁死。

### 4.11 测试证明组件存在，没有证明用户能顺畅完成任务

当前 focused proof 擅长断言 testId、分支和 refresh 边界，但截图暴露的层级、密度、焦点、滚动、空态、动作优先级和禁用表单问题没有共同的行为判据。后续必须把“查看态不挂表单”等规则变成可证伪观察。

## 5. V4 参照结论：只取证，不继承答案

### 5.1 可作为正向证据的做法

1. 列表先按分类/筛选缩小范围，再进入商品详情。
2. 快速详情不离开列表上下文。
3. 查看使用 `CatalogItemDrawerReadonlySections`、只读表格和摘要组件，与编辑字段组件分开；这只证明“禁用表单并非唯一实现”，目标态仍由本稿重新设计。
4. 规格用维度和矩阵表达，不把口味、做法、加料混成规格。
5. 点单选项查看与编辑使用不同组件；复杂编辑使用主从结构。
6. 库存/BOM 以商品结构节点为入口，不手工堆无主节点。

### 5.2 不照搬的历史壳

1. 统一字典 Modal 不是目标态证据；V2S 当前六 Tab 版本已经证明其扩展到复杂定义后不可用。
2. V4 只读表仍出现 SKU、打印名称、范围等旧技术/越界词，不能照抄文案。
3. V4 同一 `CatalogItemDrawer` 仍可用 Form 包裹所有 Tab；V2S 应保留读写组件分离，进一步分离宿主 Journey。
4. V4 的总部/门店权限、初始化、旧状态和旧商品类型不构成 V2S 业务答案。

### 5.3 目标方案的第一性推导

目标交互不按“V4 有什么组件”或“V2S 已经写了什么组件”决定，而按以下顺序推导：

1. **先确定用户此刻只想完成一个什么任务。** 查找、阅读、编辑、配置、复制、治理是六种不同心理模型，不能因为共享一个 `CatalogItem` 就共用一个编辑壳。
2. **再判断信息是否可在当前上下文一次读完。** 快速阅读且需要保留列表上下文，适合详情 Drawer；跨九个分区、存在草稿和子任务的完整编辑，需要独立工作区。
3. **再判断任务中断和误操作的代价。** 商品完整编辑、复制覆盖、治理转正的失败代价高，必须有稳定身份、保存边界、离开保护和结果确认；不能放进可轻易关闭的临时弹层。
4. **再判断是否需要反复搜索、比较和深链。** 商品配置是长期管理任务，包含简单字典、父子字典和复杂定义，需要可路由页面；一个 Modal 无法可靠承载搜索、恢复、主从和复杂编辑。
5. **最后才选择组件。** Modal、Drawer、Page 是任务承载手段，不是复用代码的起点；数据 presenter、格式化器和字段规则可以复用，但查看界面和编辑表单不能因 DRY 被强行合并。

衡量“最优”采用当前产品阶段的六项排序：任务是否能完成、是否容易犯错、状态是否可理解、上下文是否可恢复、信息是否可比较、实现是否保持 owner/contract 边界。视觉新颖度和少写几个组件不进入前六项。

## 6. 推荐目标交互架构

### 6.0 方案比较与选择理由

| 用户任务 | 备选方案 | 选择 | 原因 | 放弃方案的失败点 |
| --- | --- | --- | --- | --- |
| 找商品、比较商品 | 纯表格；纯卡片；目录树 + 结果表 | 目录树 + 结果表 | 商品分类层级稳定，用户先缩小范围再横向比较；Dexter 的真实使用也证明目录树有效 | 纯表格丢失分类上下文；纯卡片难比较价格、状态和配置差异 |
| 快速查看商品 | 跳转详情页；详情 Drawer；编辑器只读态 | 详情 Drawer | 阅读时间短，常需连续比较多个商品，保留列表范围和滚动位置收益最高 | 跳页增加往返；只读编辑器让事实难读并混淆权限/锁定/加载状态 |
| 完整编辑商品 | 原 Drawer 切模式；全屏 Modal；独立可路由工作区 | 独立可路由工作区 | 九个业务分区、规格子任务、候选配置、草稿和错误恢复需要稳定 URL、空间与离开保护 | Drawer 空间不足并持续叠层；全屏 Modal 仍缺路由、恢复和浏览器返回语义 |
| 维护商品配置 | 六 Tab Modal；六个分散页面；统一配置页面 | 统一可路由配置页面 | 六类事实共享“商品配置”入口，但复杂度不同；统一导航保住可发现性，分区工作区允许各自采用列表/主从/复杂编辑 | Modal 无法承载长期管理；六个完全分散入口难找、难返回 |
| 编辑简单字典 | 每项详情页；宽 Drawer；列表 + 匹配内容的输入面 | 列表即详情，编辑用小/中型输入面 | 完整事实一行可读，用户主要任务是比较和快速维护 | 独立详情页增加无价值跳转；宽 Drawer 造成巨大空白 |
| 编辑复杂定义 | 通用三字段表单；无限 Card；主从工作区 | 列表 + 当前定义主从编辑 | 点单选项存在组选项、当前值、原料与顾客效果，多层关系需要稳定当前项 | 通用表单容不下关系；Card 套 Card 难扫读、难定位 |
| 复制与治理 | 普通表单直接提交；分步专题 | 分步专题 | 用户必须持续看见来源、目标、覆盖范围、冲突和结果，错误代价高 | 直接提交无法形成知情确认，也无法解释部分结果 |

这些选择不是对 V4 的翻版：V4 只能为“某种拆分曾经可行”提供旁证；推荐结论即使完全移除 V4 代码参照，也能由上表的用户任务和失败代价独立推出。

### 6.1 商品库工作台：保留树表，重做结果表达

`RECOMMENDED`：保留当前目录树 + 结果表的主布局，因为它符合“先缩小范围、再比较商品”的任务；目录树继续拥有分类、标签和智能视图。优化重点在右侧结果和顶部任务栏。

结果表默认列建议为：

1. 商品：图片、名称、商品编码、短名；名称进入详情。
2. 商品类型：面向用户的类型名称，不展示 shape key。
3. 规格：普通商品显示“单一规格”，按规格商品显示启用规格数量与维度摘要。
4. 标准价：商品与规格价格可不设置；有值显示价格，无值中性显示“未设置”，不得当作风险或配置缺口。
5. 库存扣减：不参与、直接扣本品、按用料扣减，或“各规格分别设置”的摘要。
6. 状态：草稿、已启用、已停用、已归档等业务状态。
7. 来源：自主维护、品牌导入、外部临时等业务来源。
8. 更新时间。

不再使用“形态 / 规格”“价格 / 粒度”“库存 / BOM”斜杠复合标题。规格展开采用真正的子表，禁止把内部枚举直接拼成一句话。

### 6.2 商品详情：快速、纯只读、可解释

`RECOMMENDED`：列表点击名称打开宽详情 Drawer。Drawer 保留列表上下文，但只渲染查看组件。

标题区：

- 图片、名称、商品编码、业务类型、状态；
- 一个主按钮“编辑商品”；
- 当前合法的普通动作；
- 低频、危险动作进入“更多”，不展示一排灰色按钮。

内容区：

- 首屏是概览，回答商品身份、销售方式、价格、规格、库存扣减、制作和配置完整度；
- 后续按业务任务分区，商品类型不适用的分区不显示；
- 每个分区使用只读表格、Descriptions/详情行、状态 Tag、摘要 Card 或业务空态；
- 没有任何 disabled 输入控件；不可修改原因写成事实说明。

### 6.3 商品完整编辑：独立工作区，不在详情 Drawer 原地变形

`RECOMMENDED`：点击“编辑商品”进入可路由的完整编辑工作区；新建草稿后也进入同一工作区。

理由：商品编辑包含最多九个分区、规格矩阵、图片、点单设置、制作信息、库存用料和套餐组件，已经超出普通 Drawer 的中等复杂度。用户需要稳定 URL、充足宽度、分区定位、保存反馈和离开保护，而不是保持背后列表可见。

编辑工作区必须：

1. 顶部持续显示正在编辑的商品、状态和来源。
2. 分区导航只显示当前商品类型适用项；用户称“规格”，不称 SKU。
3. 显示哪些分区有未保存修改、哪些分区有错误。
4. 保存与取消固定可见；未知提交结果先 readback，不重复提交。
5. 锁定/不可修改事实显示为只读摘要，不显示 disabled Input。
6. 候选字典缺项时可去“商品配置”维护，返回后保持当前草稿和位置。

### 6.4 商品配置：从六 Tab Modal 升级为独立页面

`RECOMMENDED`：把“商品元数据”改称“商品配置”，成为 operations-admin 内可路由页面。它不是新的 owner，也不改变六类事实，只改变承载方式。

页面左侧或顶部稳定导航：

- 商品标签；
- 计量单位；
- 规格维度；
- 制作处理标签；
- 商品属性；
- 点单选项。

页面具备深链、搜索、状态筛选、返回商品库和保存后原位置恢复。六类数据仍各自调用自己的 owner/operation，不因为同页而合并缓存或命令。

按复杂度分三种交互：

| 类型 | 实体 | 推荐形态 |
| --- | --- | --- |
| 简单有限字典 | 商品标签、计量单位、制作处理标签 | 页面列表就是只读详情；新建/编辑用小或中型输入面；状态动作确认 |
| 父子字典 | 规格维度与可选值 | 保留主从面板；左侧维度、右侧值；小型新建/改名输入面 |
| 复杂定义 | 商品属性、点单选项 | 列表 + 独立详情/编辑区；点单选项使用选项值主从编辑，不用 Card 无限嵌套 |

### 6.5 Modal、Drawer、Page 的统一准入

| Surface | 允许承担 | 禁止承担 |
| --- | --- | --- |
| Modal | 短小原子创建、单字段/少字段编辑、确认、从有限候选中选择 | 六类长期管理、复杂定义、五步向导、整商品编辑 |
| Drawer | 快速详情、中等复杂度的单对象选择/编辑、在父任务中临时完成的聚焦子任务 | 用 disabled 表单冒充详情、在 Modal 上叠超宽 Drawer、九分区整商品编辑 |
| Page/工作区 | 高频列表、复杂定义、多分区编辑、多步且需要深链/恢复的任务 | 用页面壳代替缺失的 owner/contract 事实 |

## 7. 关键专项要求

### 7.1 禁用表单不得冒充详情

硬规则：

1. 查看商品、查看库存扣减、查看定义、只读权限、生命周期锁定均不得通过整张 disabled 表单表达。
2. 详情 DOM 不渲染 `Form` 以及用于修改事实的 disabled `Input/Select/Radio/Switch/InputNumber/TextArea`。
3. 无写权限时，页面保留完整可读详情，但不显示编辑入口；不能打开编辑 Drawer 后把控件全灰。
4. 编辑态的不可修改字段显示为“字段名 + 已保存值 + 不可修改原因”的只读信息，不伪装成输入框。
5. 只有真实交互控件在异步提交、候选加载或依赖未满足时可以临时 disabled，并必须有原因或状态提示。

明确反例：`CatalogInventoryBomWorkbench.tsx` 当前 `readOnly` 分支仍渲染并禁用库存方式 Radio、负库存 Switch、阈值 Input、盘点单位 Select 和 BOM 行控件，目标态必须拆成独立 read component。

### 7.2 动作层级

- 每个页面/Drawer 只有一个当前主操作。
- 只有当前状态可执行的动作才显示；为了说明不可执行原因而保留的入口不超过一个，并使用 Tooltip/说明，不形成一排灰按钮。
- 低频动作进入“更多”。
- 删除、归档、作废重建、覆盖配置分开确认，不能与保存并列成同级主按钮。
- 表格行内最多保留一个高频入口和“更多”；不堆“编辑名称/停用/删除/作废并重建”。

### 7.3 控件、字号和布局一致性

需求层不自造新的像素体系，后续 IA 必须复用 Ant Design 与 `admin-ui-foundation` 的尺寸 token，并满足：

1. 页面主要输入和主要按钮使用默认尺寸，不因表格密集而普遍降为 `small`。
2. 仅图标按钮和文字动作必须有不小于默认控件高度的点击热区；不能靠 12px 文本承担主要操作。
3. 商品主行要容纳 48px 图片、两行主信息和状态，不把所有内容压成微型文字。
4. 表单内容设可读最大宽度；三字段表单不得铺满 1024px；复杂矩阵才使用宽工作区。
5. 一个 surface 只有一个纵向滚动祖先；弹层不出现双滚动，Modal 上不再叠宽 Drawer。
6. 长名称截断并提供完整提示，不能把列撑宽；代码与名称按“名称”和“编码”分别呈现。
7. 本条已被 `U-CATUI-09` 修订：窄屏仍保持父商品/规格同表，表体横向滚动；页面本身不横向滚动，不删列、不退化卡片。
8. 弹层打开后焦点进入标题或第一个可操作项；关闭、取消或保存后焦点回到原触发点，不能把键盘用户丢回页面顶部。
9. 所有主操作、行操作、Tab、树节点和“更多”菜单均可用键盘到达；错误摘要可把焦点带到对应分区/行/字段。
10. 同类任务保持同一感知：查看面的标题、摘要和动作区一致；编辑面的字段标签、帮助文案、保存栏和错误位置一致；确认面只承担确认，不嵌入另一张编辑表单。

### 7.4 业务语言

用户可见主叫法：

| 禁用或降级用语 | 用户用语 |
| --- | --- |
| SKU | 规格；需要区分时用“规格编码” |
| 商品元数据、字典与关联维护 | 商品配置 |
| shape、商品形态 key | 商品类型 |
| 库存 / BOM、BOM 模式 | 库存扣减与用料、按用料扣减 |
| production profile、override、source | 制作信息、使用商品默认、单独设置 |
| owner/ref/readback/problem code | 不显示；改成业务对象、保存结果和可恢复动作 |

商品编码、规格编码、单位编码、标签编码仍是业务编码，可以显示；UUID、内部枚举值和 raw exception 不显示。

## 8. Contract、owner 与 UI 的分工

### 8.1 Contract 必须定义

1. 商品类型、适用分区、规格粒度和字段准入。
2. 查看 readback 所需的业务展示事实、状态、来源、动作可用性与不可用原因。
3. 创建/编辑字段、闭集、必填、长度、单值/多值、稳定错误定位。
4. 条码与标识、制作信息、库存扣减、用料、套餐、属性和点单设置的 typed 结构。
5. 列表与详情需要的摘要，避免 UI 为展示逐项猜测或 N+1 查详情。

### 8.2 Owner 必须负责

1. 在真实事务事实下重新判断类型、状态、引用、权限和动作准入。
2. 拒绝篡改请求；UI 隐藏、禁用和本地校验不构成业务防线。
3. 返回可定位、可转成业务文案的 typed problem 和保存 readback。
4. 不因 UI 合并为一个页面而合并 owner 主权。

### 8.3 UI 必须负责

1. 选择正确 surface，组织用户任务、信息层级和业务语言。
2. 区分查看、编辑、创建、确认、复制和治理状态。
3. 即时提示、草稿、错误定位、离开保护、焦点和恢复。
4. 只展示 contract 已声明且当前类型适用的内容；不从技术字段猜业务含义。
5. 通过详情组件展示只读事实，而不是禁用编辑器。

## 9. 交互状态完整性

每个列出的 surface 后续 IA 都必须逐项定义：

- 初始加载：骨架与稳定容器，旧对象不得闪入新对象。
- 空态：说明当前为空意味着什么，并给出适用于当前任务的下一步。
- 读取失败：保留已确认内容、筛选和草稿；提供原地重试。
- 无权限：详情仍可读；编辑入口消失或解释为何不可用。
- 业务不可修改：展示当前事实和原因，不渲染禁用表单。
- 编辑脏态：切分区不丢稿，关闭/离开确认，取消恢复已保存事实。
- 提交中：防重复提交，主操作有进度。
- 已知失败：定位到分区/行/字段，保留草稿。
- 未知结果：先 owner readback，再决定成功、失败或重试。
- 保存成功：详情、列表和相关候选只刷新精确范围，返回用户原位置。

## 10. 防再犯的可证伪判据

以下判据必须在后续设计、focused test 和获授权 browser L2 中分别落位；写不出失败条件的判据不收。

1. 打开任一商品或配置定义的详情，在未点击“编辑”前，详情内容中不存在编辑 Form 或 disabled 输入控件。
2. 只读账号打开同一对象，看到的业务事实与可写账号详情一致；差异只在动作入口，不是字段被灰掉。
3. 点击“编辑商品”后进入独立编辑工作区；取消返回原详情且没有草稿残留，保存返回 owner readback。
4. 商品详情标题区不会同时出现启用和停用，也不会展示三个以上同级主动作。
5. 商品结果表没有斜杠复合列、重复表头、内部枚举或“按需读取不改变结果域”等技术说明。
6. 按规格商品的展开行能按列比较三个规格；普通/称重商品不出现规格入口。
7. 批量改分类只能选择零或一个分类；篡改多分类请求由 owner 拒绝。
8. “尚未设置制作信息”空态的主操作能直接进入制作信息编辑，而不是只去管理标签。
9. 库存扣减查看态不挂 Radio/Input/Select/Switch；编辑态才显示允许的方式和字段。
10. 商品配置不再是六 Tab 1200px Modal；从商品编辑去配置后可回到原商品、原分区和未保存草稿。
11. 商品属性纯文本定义的编辑面不产生大面积无意义空白；点单选项复杂编辑也不被压进同样尺寸的简单表单。
12. 无写权限不能打开商品属性或点单选项编辑 Drawer；列表和详情仍可正常阅读。
13. 所有用户文案扫描不出现 `SKU`、`owner`、`readback`、`shapeKey`、`problem code`、UUID 或 raw exception；业务编码是明确反例。
14. Modal 上不叠加宽 Drawer；任何页面只有一个主纵向滚动容器。
15. 从品牌导入与复制其他商品设置的标题、目标和结果可区分，用户不会误以为总部模板会自动同步。
16. 商品启用、库存充足、发布成功和终端生效四种状态不互相代称。

## 11. 本轮待确认项

以下不是与旧 UI 裁定做兼容取舍。按 Dexter 最新指令，除目录树外旧 UI 形态均已退出本专题约束；这里仅记录本轮新方案在独立评审后仍需 Dexter 最终确认的产品体验选择。

### `U-CATUI-01` 商品配置承载面

历史实现曾把六类配置放在统一 Modal，但该页面形态本轮不再享有保留推定。当前六类任务包含简单字典、父子主从和复杂定义；Modal 上叠 Drawer、内容高度和宽度失衡，真实体验失败。

`RECOMMENDED`：本轮接受后，以可路由“商品配置”页面取代六 Tab Modal；owner 和接口边界不变。

### `U-CATUI-02` 商品完整编辑承载面

历史实现曾在最小商品创建后进入宽 Drawer 完整编辑，CIPG 也沿用了该宿主，但这一页面形态本轮不再享有保留推定。当前编辑已扩展到九类分区和多个子弹层，Drawer 同时承担快速详情和大型工作台，标题、滚动和嵌套 overlay 均出现问题。

`RECOMMENDED`：保留详情 Drawer；完整编辑改为独立可路由工作区；新建成功和“编辑商品”都进入该工作区。

### `U-CATUI-03` 简单字典是否需要详情页

`RECOMMENDED`：不建详情页。标签、单位、制作处理标签的完整事实可在列表行展示；列表就是只读视图，编辑才打开输入面。这符合此前“单位不建详情页”的裁定，也避免为形式统一而过度设计。

### `U-CATUI-04` 目录树范围

Dexter 已明确目录树实现较好。

`RECOMMENDED`：本轮不重做目录树的业务结构，只修搜索、动作菜单、分类弹层和右侧列表衔接；任何后续方案不得为了统一视觉而拆掉树表工作台。

## 12. 非目标

1. 不改变商品、单位、库存/BOM、条码与标识、制作信息、属性和点单选项的已确认业务模型。
2. 不新增销售集合、发布、可售、POS、扫码解析、打印机、KDS 或重供应链能力。

5. 不授权 contract、代码、migration、测试、DEV、reset、seed、browser L2、UAT 或部署。

3. 商品配置页面（简单字典、父子字典、复杂定义三个代表态）；
4. 批量与复制专题。

线框确认后再写 IA 和 implementation-facing design；本稿本身不授权实现。

## 14. 需求验收场景草案

1. 只读用户从目录树筛选到拿铁，打开详情并看清三个规格、标准价、制作差异和库存扣减摘要，全程没有灰色输入框。
2. 可写用户从同一详情点击编辑，进入独立工作区；修改基础资料和一个规格后取消，返回详情仍是原值。
3. 新建普通销售商品，只填写最小身份创建草稿，进入编辑工作区；普通商品不出现规格维护。
4. 新建按规格商品，规格区先选规格维度，再维护规格表；用户界面不出现 SKU。
5. 制作信息为空时，用户从空态直接进入制作信息编辑；若缺制作处理标签，可去商品配置创建后返回原草稿。
6. 查看“库存扣减与用料”时只看到当前方式和明细；点击编辑后才出现方式选择和输入控件。
7. 批量改分类只能选择一个分类；逐项结果明确成功 N 项、失败 M 项及业务原因。
8. 商品配置页切换六类配置不会丢失搜索、选中项或滚动位置；复杂点单选项编辑不叠加在 Modal 之上。
9. 无写权限打开商品属性和点单选项定义时，只显示可读事实，没有“保存”按钮和禁用表单。
10. 从品牌导入创建门店独立商品；页面明确说明后续品牌修改不会自动改门店商品。
11. 从已有商品复制设置时，持续显示来源和当前目标，提交前列出会覆盖的分区。
12. 商品停用后，详情说明“后续不能被新配置选择”等真实影响，不声称商品已从所有菜单下架。

## 15. 完成定义

本需求讨论只有在以下条件同时成立后，才可收敛为正式需求：

1. Dexter 对 `U-CATUI-01` 商品配置页面和 `U-CATUI-02` 独立商品编辑工作区作出裁定。
2. 47 项 surface 清单经 current tree 复核无遗漏；新增用户可达 surface 必须补入而不是藏在实现中。
3. “详情不得渲染禁用表单”成为正式、可执行、带反例的交互规则。
4. 用户术语与 G-11/G-12/CIPG-01 逐字对账，界面不泄漏技术模型。
5. 后续 Journey 与低保真线框先获 Dexter 确认，再进入 IA 和 implementation-facing design。
