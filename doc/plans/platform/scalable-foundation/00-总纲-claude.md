## 2. 如何开发

### 2.1 单个变更点(CP)的执行循环

```text
① 取件      从 LEDGER 取下一个「未开始」CP;属原子组则整组取
② 前读      重开该 CP 的 owning source 原文 + 本册条目 + 需求正本对应条
③ 核 BEFORE 逐字比对;不一致 → 停(§2.4)
④ 执行      只按 ACTION 动词做 AFTER 描述的事
⑤ 跑证据    按 PROOF 声明的档位跑,留可打开的产物
⑥ 后读      用②的同一组原文回读改动处
⑦ 回填      LEDGER 填状态 + 证据路径 + 后读结论
```

一次只做一个 CP。

### 2.2 只用单义动词

⛔ 禁用:统一 · 优化 · 梳理 · 完善 · 处理 · 接入 · 增强 · 重构 · 清理 · 调整
✅ 只用:`删除` · `新增` · `替换` · `移动` · `改值` · `重命名`

「统一 X」至少有四种实现(抽函数 / 抽基类 / 复制成一致 / 建配置),实施 agent 会挑一个而不会问。

### 2.3 CP 的字段

```text
FILE / LOCATE / BEFORE / AFTER / ACTION / FORBID / INVARIANT / PROOF / DEPENDS
```

**`FORBID` 必填** —— 写不出 FORBID 说明这条还没想清楚。
**`BEFORE` 必须逐字**,且必须是**源码里真实存在的连续片段**。

⚠️ 第一版在这里栽过:把跨 `+` 拼接的 SQL 引成一整行,导致 BEFORE 在源码里根本搜不到。
本版所有 SQL 类 BEFORE 均按**源码真实的分行与拼接**引用。

### 2.4 停止条件 —— 停下来问,不得自行决定

1. BEFORE 对不上
2. AFTER 照做后编译不过或既有测试变红,且不在该 CP 的 `FORBID` 预告范围内
3. 发现文档写错(行号不存在、方法不存在、逻辑不成立)
4. 两个 CP 冲突
5. 涉及产品语义 / Journey / 用户可见行为的取舍
6. 需要新增依赖
7. **原子组中间态的报错与声明的预期报错不符** —— 说明理解错了

⛔ 不允许:自己选一个「合理的」做法继续 · 留 TODO 继续 · 缩小范围报完成 · 加兼容层绕过。

### 2.5 原子组

若干 CP 必须同时落地、中间态仓库必然是坏的时,声明为原子组,并写明:
**组内顺序 · 中间态预期的报错原文 · 整组完成后才跑证据**。

**为什么必须声明**:实施 agent 见红会以为自己做错,于是回滚、或**自己发明一个兼容层**。
这是本项目已观察到的走偏模式。

⚠️ 第一版在这里也栽过:声明的「预期报错」经核实不会发生(被删的字段零消费者)。
**本版每个原子组的预期报错都标注了它的验证状态。**

## 3. 如何验收

### 3.1 证据四档 —— 每个 CP 声明最低档位,实际不得低于声明

| 档 | 名称 | 只证明什么 |
|---|---|---|
| 0 | 编译 | 语法与类型 |
| 1 | 静态门 | **该门那一条命题** |
| 2 | focused 测试 | 被测代码的行为 |
| 3 | 行为测试 | **用户可见的**业务行为(真实 HTTP / 真实容器) |

⛔ 禁止下移:用档 0 冒充档 2(「编译过了说明改对了」);用档 1 冒充档 3(「门绿了说明业务对了」)。
⛔ 产物必须可被第三方打开 —— 命令 + 输出,不接受「已完成」「符合设计」。

### 3.2 门的三件套 + 反例栏(缺一不算门)

1. **不变量** —— 一句机械可判定的命题
2. **红夹具** —— 人为制造违反,**真跑,确认真的变红**
3. **负控制** —— 声明一条它预期抓不到的变异
4. **反例栏** —— 「能通过这道门但违反命题的写法是 ____」

**反例栏写不出「无」以外的东西,这道门就是纸糊的。**

先例(本项目真实发生):逐控件对账门核的是 testId 存在,声称守的是控件形态 —— 两者不是同一件事。

⚠️ 第一版有 15 道门,四路盲审判定 **14 道可被绕过**。
本版把门砍到**只保留能写出可执行检测方式、且反例栏不致命的**那几道。

### 3.3 三层验收

| 层 | 判据 | 谁做 |
|---|---|---|
| L1 变更点 | 该条 `PROOF` 的档位与产物;`INVARIANT` 逐项复核 | 实施者自证 |
| L2 分册 | 分册末尾的分册门 | 实施者自证 |
| L3 全局 | **方案对不对、有没有过度设计** | **fresh 独立子 agent 对抗审查,不得由实施者自判** |

⚠️ L1/L2 全绿不构成 L3 通过。机器门只证明「1+1 确实等于 2」,不证明「用户要的是 1+1」。

## 4. 如何对账

**只做一件事:需求覆盖。**

需求正本 28 条,每条必须指向:一个 CP-ID · 或「本轮不做」清单 · 或「待盘点后决定」清单。
**三者之外即为条目静默消失。**

⛔ 本版**不做**:文件反向索引 · 锚点检查 · 收口九项台账。
**理由**:`AGENTS.md` 第 56 行已退役 evidence 台账、package entry/exit、六类 source 分母、
changed-path/incremental receipt set equality、hash-chain、manifest Part B/C/D。
第一版把这一整类做法用中文重建了一遍(四路盲审逐项对上七处),
且改为人手维护后比被退役的脚本版更贵、更易漂 —— 作者本人同步一次就漏了 16 条。

「改的是不是就是说的」这一层,靠:**编译 + 既有测试 + 分册门 + L3 独立审查**。
逐字 diff 是 Dexter 随时可用的工具,不是本流程的前置条件,也不由本流程替代。

## 6. 第一版为什么作废(留档,防再犯)

四路独立盲审的一致判定,以及**根因**:

| 类别 | 具体 | 根因 |
|---|---|---|
| **偷工** | 21 个调用点 CP 共享**一个模板**,没逐条打开方法体 ⇒ 模式 B 三条全判错、8 个入口的锁会落在既有 recheck **之后**、3 条插进 `OWNER_READ` try 块、3 条插在赋值语句中间**编译不过** | **文档要求的严谨,文档自己没付钱**:00 写着「BEFORE 必须逐字,缺一即不可实施」,却给 20 个 CP 发了没有 BEFORE 的共享块 |
| **打错目标** | P-3 去动 `dictionary_kind` 字符串,真病灶是两个 service 里逐字节复制的三个魔数;P-7 的参数化 emitter **本来就存在**,真实目标是 10 不是 9;P-4 漏掉 `DomainControlKind`,做完 5174 行还在 | 从需求条目的**文字**推导动作,没有回到源码确认那个动作打在哪 |
| **未知分母写精确计划** | 03/04/05 的核心分母全部未知(自己在每册末尾都写了),却给出精确 CP 计数,而且五册**全部数错** | 精确的形式掩盖了未知的内容 |
| **过度设计** | 逐字 BEFORE + 反向索引 + 锚点检查 + 收口九项 + W1-W10 + 15 道门 = 已退役 compliance-control 的中文重建 | 把成本花在可精确化的地方,而不是风险大的地方 |
| **漏继承** | 需求 §3.2 处置表里 **14 条 ⚠️/⛔** 没进分册 | 重写时以「我理解的意思」为源,没有逐条比对原文 |

**本版据此做的收缩**:只写分母已知的两册 + 盘点;门只留能写出检测方式的;砍掉全部台账类机制;
每条 CP 的 BEFORE 都按源码真实分行引用。
