## 0. 术语表（先读这个）

> 这些词**行业里没有统一定义**，三家厂商各叫各的，同一个词在不同家还指不同东西。本稿前几版混用过，这里统一。`【自我修正】`

### 0.1 只有三件事是真的

```
① 菜在哪儿做          —— 物理位置
② 菜从哪儿交出去      —— 物理位置
③ 系统里"这道菜的单打到哪台机／显示在哪个屏"  —— 一个虚拟的路由对象
```

其余所有词，都是这三件事的别名或组合。看到生词先问：它说的是 ①、② 还是 ③。

### 0.2 物理世界的词（厨房里真实存在）

| 词 | 指什么 | 属于 |
|---|---|---|
| **厨房** | 一个封闭制作空间。多层店可能有多个（一楼厨房、宴会厨房） | ① |
| **专间** | **法规概念**：凉菜间、裱花间、备餐间、分装间。有硬性要求（≤25℃、独立空调、紫外线、预进间） | ① |
| **工种／岗位** | 炉头、砧板、上什、烧腊、点心、**打荷**、水台——是**人的分工**，不是地点 | ① |
| **灶台／工位** | 具体设备位置 | ① |
| **出品台／地哩台** | 厨房交给前厅的窗口，打荷放这儿 | ② |
| **备餐间／备餐台** | 前厅侧暂存，传菜员放这儿、服务员取 | ② |
| **传菜口** | 某层/某区的传菜起点，多层店每层一个 | ② |
| **划菜台／划菜间** | 核对整桌菜是否齐的位置 | ② |

> ⚠️ 本稿前几版用过「**出品口**」——这个词在三家厂商文档里**零命中**，是我从厨房行业资料里带进来的物理词。系统里没有这个对象。`【自我修正】`

### 0.3 系统里的词：同一件事，三家各叫各的

| 这件事 | 美团 | 客如云 | 银豹 | v4/v6 |
|---|---|---|---|---|
| **③ 打印路由对象** | **档口**（480 次）<br>分三种：后厨出品档口 / 标签出品档口 / 收银打印配置 | **出票口**（140 次） | **厨打机**（24 次）<br>——直接就是那台机器，没有中间对象 | 作业面 `processingSurface` |
| **③ KDS 显示单元** | 档口（同一个对象） | **出品堂口** / **传菜口** | 电子厨显 | — |
| **菜品→路由的绑定方式** | 菜品选档口，或档口勾菜品 | 出票口配"商品出单限制" | 商品资料里一组"厨打开关" | 商品打 `productionTag`，作业面收标签 |
| **整单汇总票 vs 分档票** | 整单打印 / 分单打印 | **厨总单** / **堂口单** | 一单一切 / 一品一切 | `ONE_TICKET_PER_SURFACE_ORDER` / `ONE_TICKET_PER_PRODUCT_LINE` / `ONE_TICKET_PER_UNIT` |

**三个陷阱** `【厂商文档】`：

1. **「档口」在不同家指不同东西**。美团用它指打印路由单元；**银豹和客如云用「档口」指供应链里的仓库/采购单元**（银豹："门店有多个档口或操作区域"是在讲库区管理；客如云的两次命中是"档口仓库"）。跨家读文档时这个词会骗人。
2. **「堂口」只有客如云用**（15 次），美团和银豹零命中。它≈档口，粤菜厨房的老叫法。
3. **银豹根本没有中间对象**——商品直接绑到具体那台厨打机。没有"档口"这一层。

### 0.4 动作词（这些是动作，不是地点）

| 词 | 谁做 | 是什么 |
|---|---|---|
| **传菜** | 传菜员（后厨编制，通常不见顾客） | 把菜从出品台送到前厅备餐台 |
| **上菜** | 服务员 | 从备餐台端上餐桌 |
| **划菜／划单** | 划菜员 / 领班 / 传菜员 / 服务员（视店大小） | **把菜标记为"已出/已上"**。客如云定义：「将菜品标记为已经上菜」 |
| **起菜／叫起** | 服务员 | 让此前"等叫"的菜开始做 |
| **催菜** | 服务员 | 催后厨加快 |
| **打荷** | 打荷师傅 | **既是工种名也是动作**：接砧板的料、分给炉灶、收回装盘、送出品台 |

## 1. 怎么读这份全景

我把"一次打印"拆成六个互相独立的问题。**任何一张纸都同时回答这六个问题**，而行业里的差异，绝大多数出在后三个而不是前三个。

| # | 问题 | 这一维的取值范围 |
|---|---|---|
| ① | **谁在看这张纸** | 顾客 / 服务员 / 厨师 / 划菜员 / 传菜员 / 打包员 / 收银 / 店长 / 财务 / 跨部门 |
| ② | **它在业务上顶什么用** | 凭证 · 核对 · 指令 · 识别 · 追溯 · 交接 · 存档 |
| ③ | **什么时候打** | 见 §5 的触发点全景 |
| ④ | **打到哪台机** | 见 §6 的路由全景 |
| ⑤ | **什么介质** | 见 §7，热敏小票 / 标签 / 页式纸 / 电子（短信、邮件、小程序） |
| ⑥ | **多少份、几联、内容一样吗** | 份数 · 多联（内容不同） · 整单/分单 · 一品一切/一单一切 |

**一个判断题可以检验清单是否完整**：拿任意一张纸问"不打会怎样"。答案只有四种——顾客会有疑问（凭证类）、现场会做错（指令类）、事后查不到（追溯类）、法规或流程不允许（合规类）。答不上来的，多半是行业惯性而不是真需求。`【推论】`

### 2.4 传菜 / 划菜 / 出品口的纸

> **先分清三个词：两个是动作，一个是地点。** 我在初稿里把它们并排当成同一层，是错的。

| 词 | 是什么 | 谁做 | 一句话 |
|---|---|---|---|
| **传菜** | **动作** | 传菜员（属后厨编制，**通常不与顾客见面**）`【外部】` | 把做好的菜从厨房出品台送到前厅备餐台 |
| **上菜** | **动作** | 服务员 | 从备餐台端到顾客桌上 |
| **划菜 / 划单** | **动作** | 视规模而定：大店有专职划菜员，中小店由领班、传菜员或服务员兼 `【外部】` | **把菜标记为"已经出了/已经上了"**。客如云的定义最干净：「将菜品标记为已经上菜」`【厂商文档】` |
| **出品口 / 出品台 / 地哩台** | **地点（工位）** | 打荷把菜放这儿，传菜员从这儿取 | 厨房与前厅的物理交接窗口 |
| **备餐间 / 备餐台** | **地点** | 传菜员放这儿，服务员从这儿取 | 前厅侧的暂存位。大型宴会厅就近设，高档包间设专门备餐间 `【外部】` |

**完整链路有四次交接**，不是一次 `【外部】`：

```
水台/砧板(初加工、配菜) → 炉灶(烹调) → 打荷(装盘、摆盘、加装饰)
   → ① 出品台/地哩台 → 传菜员取走
   → ② 前厅备餐台 → 服务员取走
   → ③ 顾客餐桌（上菜）
   → ④ 划菜：在某个点上把这道菜标记为已出/已上
```

中餐厨房七大工种：炉头、砧板、上什、烧腊、点心、**打荷**、水台 `【外部】`。打荷位于砧板线与炉头线之间，是"把菜交出去"的那一环。

**"划"字来自纸质时代**：点菜单上已出的菜用笔划掉，剩下没划的就是还没出的。所以划菜天然是**逐菜品**的，且天然需要一张**列全了所有菜的总单**作底稿——这就是划菜总单存在的原因。`【推论】`

**系统里的划菜比纸上复杂得多** `【厂商文档】`：

- **划菜的粒度有三级**：单菜品划 / 整单划（"划单"）/ **分批划**。美团为烧烤业态做了分批划菜——「20 串羊肉串，先出 5 串，再出 15 串」，还分两种交互方案（点数量 vs 点菜品图）。
- **划菜可以发生在三个环节**：美团 KDS 的设置里，**配菜设置 / 制作设置 / 传菜设置**各有一个"分批传菜"开关。也就是说同一道菜在配菜、制作、传菜三段各被划一次。
- **划菜可以撤销**：客如云 KDS 传菜模式里「已划菜品可撤销」。
- **划菜有业态变体**：客如云列了五种——**标准划菜、火锅划菜、串烤划菜、粉面划菜、西餐划菜**。
- **划菜可以扫码完成**：美团支持在票据样式里配置**划菜一维码 / 划菜二维码**，打在标签上，扫完订单中所有菜品后触发叫号。
- **划菜工位有自己的显示形态**：客如云传菜模式有四种展示方式——订单模式、分类模式、商品列表模式、商品卡片模式，按传菜口配置该显示哪些菜品。


| 单据 | 顶什么用 |
|---|---|
| **划菜总单 / 厨总单** | 划菜员核对整桌菜是否出齐。国际术语叫 **expo ticket / expediter ticket**，"one consolidated ticket for the full order" `【外部】` |
| **传菜单** | 按楼层/区域出单，传菜员只管自己那层。银豹演示：二楼打印机只勾二楼区域，三楼只勾三楼，**传菜口一般选"一单一切"** `【厂商文档】` |
| **出品 / 起菜通知** | 通知可以上菜了 |

> 客如云把这一层叫"厨房出票种类"，明确区分**堂口单**（一纸一菜/一纸多菜）与**厨总单** `【厂商文档】`。这是"制作指令"和"核对汇总"两种不同用途，不是同一张纸的份数差异。`【推论】`

### 2.6 贴在物体上的标签

| 标签 | 贴在哪 | 触发点 | 关键内容 |
|---|---|---|---|
| **杯贴** | 杯身/包装 | 制作时 | 银豹演示两种规格：**40×30 小标签**（古茗款）与 **40×60 大标签**（喜茶款）。参数含**排号（取餐号）、页码（第几杯/共几杯）、logo、商品名、加价、口味、销售时间、店名、电话、会员姓名、配送方式、验码** `【厂商文档】` |

| **商品条码标签 / 吊牌** | 商品本体 | 入库、上架 | 零售/服装形态 |
| **套餐子菜标签** | 每个子菜 | 制作时 | 客如云有独立设置"标签打印机仅打印套餐子菜" `【厂商文档】` |

> **效期标签和称重标签的触发点不在订单链路上。** 一个由"后厨做了一批半成品"触发，一个由"把东西放到秤上"触发。这两类在以订单为中心的模型里没有位置。`【推论】`

## 4. 打印时机全景

> 把所有观察到的触发点摊开。**注意有三类触发点根本不在订单链路上。**

### 4.1 订单链路上的触发点

```
下单 → 加菜/追加 → 退菜 → 催菜 → 等叫 → 叫起
开台 → 转台/并台/拆台 → 清台
预结 → 结账 → 反结账 → 退款
制作开始 → 制作完成 → 出品 → 叫号 → 取餐 → 交接 → 配送
打包 → 封装
```

### 4.2 不在订单链路上的触发点 `【厂商文档】`

| 触发点 | 打什么 | 为什么它不在订单链路上 |
|---|---|---|
| **生产制作动作** | 效期标签 | 后厨做一批珍珠、奶油、茶汤，还没有人买 |
| **称重动作** | 称重/预包装标签 | 东西放到秤上就打，可能永远不卖出去 |
| **上架 / 调价** | 价签 | 商品维护动作 |
| **班次 / 营业日结束** | 交接班单、日结单 | 时间驱动，不是订单驱动 |
| **盘点 / 报损 / 收货** | 对应单据 | 库存动作 |
| **预订成立 / 收定金 / 派工** | 预订单、定金收据、EO 单 | **提前数天**，宴会尤其 |
| **报表查询** | 营业概览等 | 人在看报表时顺手打印 |

### 4.3 两种特殊触发方式 `【厂商文档】`

- **定时 / 提前打印**：客如云 KDS 有"设定较前定时打印"，配合商品超时预警。用于需要提前备料的菜。
- **人工补打**：几乎所有单据都能补打，但**入口不统一**。银豹中餐：补厨打要选桌台勾菜品，补压桌单/日结单/标签走"更多操作"，补收银小票要去"销售单据"列表。美团：订单列表→选单→打印小票→**选单据名称**（超 30 天 POS 打不了，只能后台查）。

### 4.4 一个容易漏的维度：按来源决定打不打 `【厂商文档】`

客如云的后厨出票规则里有一条"**按照来源限制出单**"——例如设置扫码点餐下单的，厨房不出单。美团的收银打印配置里也有"**订单来源**"选项。

**这说明"打不打"不只取决于场景，还取决于订单从哪来。** `【推论】`

## 5. 路由与分单全景（三家厂商的真实做法）

这是行业里最复杂、各家差异最大的一块。三家做法并列：

### 5.1 美团：三种"档口"并列 `【厂商文档】`

```
收银打印配置   ← 品牌、名称、合并相同菜、菜品展示顺序、订单来源、票据类型(不打印/1-3份)
后厨出品档口   ← 合并相同菜、菜品展示顺序、打印方式(整单/分单:按菜切 或 按分类切)、
                套餐切单方式、票据类型与份数
标签出品档口   ← 档口名、打印区域(桌台区域)、关联菜品、打印份数
                注:"标签制作联是堂食,外卖标签制作联是外卖"
```

配置在**总部后台创建 → 下发到门店 → 门店端打印机勾选关联档口**。总部改了必须重新下发才生效。

### 5.2 客如云：一个出票口，四维规则 `【厂商文档】`

```
① 厨房出票种类：堂口单(一纸一菜/一纸多菜) 或 厨总单，及打印份数
② 按来源限制出单：例如扫码点餐不出厨房单
③ 商品出单限制：哪些商品在这台机出票(热菜机只出热菜)
④ 下单区域/桌台限制：哪些桌台不出厨房单
```

打印机属性：连接方式（网口/USB）、IP、**打印机用途**（后厨小票/前厅票据/标签）。

### 5.3 银豹：两种厨打模式，可并存 `【厂商文档】`

```
模式一 按商品分类：小吃、煮食、冷菜、酒水分工明确时用
模式二 按区域/楼层：一楼桌台的菜从一楼传菜口出，二楼的从二楼出
                  → 二楼打印机只勾二楼区域,三楼只勾三楼
打印方式：一品一切 / 一单一切（传菜口一般用一单一切）
商品绑定：批量把某分类的商品绑到某台机；传菜口要绑全部商品
```

### 5.4 国际做法 `【外部】`

Toast 的打印机功能分三档：**Kitchen Tickets / Both（顾客小票+厨房票）/ Item Labels**。站点划分为 **kitchen、bar、expo、pickup、online orders**，"apps to cold prep, entrées to the grill, drinks to the bar"。

### 5.5 三家的共同结构 `【推论】`

抽出来看，所有人都在表达同一件事，只是命名不同：

```
一台打印机  ←绑定→  一个"出票口/档口"  ←承载→  若干票据类型
                        ↑
            由四类条件决定哪些内容进来：
            商品维度（分类 / 具体商品 / 套餐子菜）
            位置维度（区域 / 楼层 / 桌台）
            来源维度（堂食 / 扫码 / 外卖 / 平台）
            形态维度（整单还是切单，一品一切还是一单一切）
```

**没有任何一家把这些条件放在"打印规则"里，全都放在"出票口/档口"这个中间对象上。** `【推论】`

---

### 5.6 「出品口有几个」——三个不同基数的东西别混

这是最容易混淆的一处。现场其实有**三层对象，基数完全不同** `【推论】`：

| 层 | 叫什么 | 基数由什么决定 | 典型数量 |
|---|---|---|---|
| **制作地点** | 档口 / 专间 / 灶台 | 分工与**法规** | 凉菜间 1 个、热菜若干灶、烧腊 1、点心 1、水台 1 |
| **交接地点** | 出品口 / 传菜口 / 备餐间 | **楼层与区域** | 每层一个，宴会厅和高档包间各自再设 |
| **系统对象** | 打印档口 / 出票口 | 运营怎么配 | 任意，与上面两层都不是一一对应 |

**为什么凉菜通常只有一个制作点**——这是法规不是习惯 `【外部】`：

凉菜间属于「**专间**」（处理或短时间存放直接入口食品的专用操作间，含凉菜间、裱花间、备餐间、分装间）。《餐饮服务食品安全操作规范》要求专间：

- 温度**不高于 25℃**，需独立空调；
- 每餐使用前紫外线消毒，**无人时开启 30 分钟以上并记录**；紫外线灯功率**不小于 1.5W/m³**、强度**大于 70μW/cm²**；
- 中型以上餐馆、快餐店、学校食堂、供餐 50 人以上单位食堂、集体用餐配送单位、中央厨房，专间入口须设**通过式预进间**（洗手、消毒、更衣）。

一间合规凉菜间的造价和管理成本都不低，所以**绝大多数餐厅只建一个**。规范本身**没有规定数量**，只要求"进行凉菜配制操作的，应设置相应专间"——也就是说建两个不违规，只是没人愿意。`【外部】`

**多层酒楼的通行解法是"集中制作 + 分层交接"** `【外部】`：

- 厨房与餐厅**同层最优**（缩短流程、保温、防交叉污染、省设备投资）；
- 不同层则**另设食梯（传菜电梯）**，且须按**生、熟、洁、污分设**，并加保温传送设备；
- 大型宴会厅就近设备餐间，高档包间设专门备餐间，**备餐间入口宜与包间入口分开，出口不应正对餐桌**。

所以："同样是凉菜，1 楼做、2 楼也做吗？"——**物理上通常不是**（一个凉菜间做完，经传菜梯分送到各层传菜口）；但大型酒楼、宴会中心确有分层设独立厨房的，尤其宴会厅自带厨房。两种都真实存在。`【推论】`

**系统里两种都能表达，而且是多对多** `【厂商文档】`：

- 美团明确写着「**菜品可以同时在多个档口出单**，在进行出品档口的分配时请注意选择，**避免因为误操作导致重复出单**」——同一道凉菜挂到"1楼凉菜口"和"2楼凉菜口"两个档口，两边都会打。
- 美团还有「**一个档口关联多个设备**」。
- 银豹的做法最能说明两个维度是**正交**的：**档口按"商品分类"绑**（海鲜类商品批量绑到海鲜机），**传菜口按"区域"绑但要绑全部商品**——「所有的传菜口都需要绑定全部的商品……因为我们的商品，不管是二楼或三楼的顾客都是可以下单的」，再用区域勾选把二楼订单只打到二楼传菜口。

**一句话**：档口回答"这道菜谁做"，按**商品**收敛；传菜口回答"这道菜送去哪"，按**区域**收敛。同一道菜在前者里通常只属于一个，在后者里属于全部。`【推论】`

### 5.7 友商没有「生产标签」这一层

在客如云、美团、银豹三家全部资料里检索 `生产标签` / `厨房分类` / `出品分类` / `制作分类` / `厨打分类` / `后厨分类`，**零命中** `【厂商文档】`。

名字相近但**不是**路由用途的三个概念：

| 概念 | 实际用途 | 举例 |
|---|---|---|
| **菜品标签** | **营销展示** | 客如云：热门、赠品、特价、推荐、新品、招牌，用于小程序热门菜推荐 |
| **菜品做法** | **点单属性** | 客如云：去冰、常温、少冰、冷、热、糖 |
| **加料** | **点单属性 + 计价** | 加珍珠 |

**三家都是「菜品」直接绑「档口」，中间没有抽象层。** 银豹的绑定形态是一组开关——商品资料里"开启海鲜类厨打开关""开启对应的厨打名称"，取消勾选即不厨打。美团是在档口配置里勾菜品，或在菜品上选档口。

没有中间层带来的运维负担，三家各自用工具兜底 `【厂商文档】`：

- **默认档口**：美团有"新增菜品时自动关联默认档口"，"减少新添加菜品忘记勾选档口而不出单的情况"；且分「后厨默认档口」和「标签默认档口」两套，可同时生效。
- **置灰保护**：创建菜品选档口时，**未绑定打印机的档口置灰不可选**。
- **批量工具**：美团有"菜品打印配置"功能，批量查看和修改菜品↔档口绑定；外卖菜品另有一套。
- **状态日志**：可查看打印机档口、菜品关联打印机的**状态变化日志**，用于定位"为什么这个菜不出单"。

### 5.8 一个（非套餐）菜品其实只对应一个档口——多值是建模债，不是业务需求

> **本节已重写。** 初版据美团那句「菜品可以同时在多个档口出单」得出"多对多是常态"，**结论过头了**。逐条复核后，那些理由大多不成立。`【自我修正】`

#### 逐条复核初版列的五条理由

| 初版理由 | 复核结果 |
|---|---|
| ① 后厨档口 / 标签档口 / 收银配置三套并列 | **不成立**。这是三个**不同的轴**（介质用途），每轴上仍是一个菜品一个档口 |
| ② 传菜口按区域绑全部商品 | **不成立**。传菜口是**交接工位**不是制作档口，属区域轴 |
| ③ 渠道分别绑定（店内/美团外卖/饿了么） | **不成立，且我读反了**。美团的外卖菜品与堂食菜品是**两套独立实体**，靠「外卖门店菜品关联堂食门店菜品」建立映射，后台还有「菜品未关联列表」。所以是**两条菜品记录各绑一个档口**，不是一个菜品绑两个 `【厂商文档】` |
| ④ 多楼层 / 多厨房 | **不成立**。给定（菜品，区域）后仍唯一解析出一个档口，这是**带上下文的解析**，不是多值 |
| ⑤ 套餐子菜各自绑 | 成立，但 Dexter 已排除套餐 |

#### 反过来，有三条证据说明厂商自己在往 1:1 收敛 `【厂商文档】`

1. **强制一个档口只能被一台打印机绑**：美团 5.14「多收银端网络打印机档口选择优化」——「若主收银选择了名称为"A"的后厨档口，副收银再选择档口时，则**不可选择后厨档口 A，显示置灰状态，且不可编辑**，编辑时弹框提示"该档口已被 xx 打印机绑定"」。
2. **重复出单被定性为故障而非特性**：官方文档《为什么打印机重复出单》的首要原因是「同一个打印机 IP 地址添加多次」——配置错误。
3. **连重试都要标记以免被误认为重复**：5.14「票据样式增加"手动重试"字样」——「用于区分打印失败重试成功的打印任务，**避免商家误认为是重复出单**」。

#### 唯一真实的「两个档口」命中，方向是反的

全库检索 `两个档口` 只命中一处：「该打印机需要同时出前台小票和凉菜后厨小票，那么就勾选已经设置好的前台和凉菜这两个档口」——这是**一台打印机绑两个档口**，不是一个菜品绑两个档口。`【厂商文档】`

#### 修正后的结论

**在同一个轴上，一个非套餐菜品 → 一个档口，是函数不是关系。** `【推论】`

数据模型上是多值，是因为"档口"这一个对象被迫同时承担了四件事：

```
制作分工（这道菜谁做）      ← 真正的档口语义
区域分流（送去哪一层）      ← 应该是传菜口/区域
介质分流（小票还是标签）    ← 应该是票据类型
渠道分流（堂食还是外卖）    ← 美团用两套菜品实体解决了
```

四件事压在一个维度上，用户就可能在同一轴上勾两次，于是需要「避免因为误操作导致重复出单」这句警告，以及默认档口、置灰、批量工具、状态日志一整套运维兜底。**多值是没拆维度的债，代价由运维承担。**

残余的真·同轴多值极薄，且都有更合适的归属 `【推论】`：一鱼两吃（更接近套餐拆项）、水台备料单+炉灶制作单（属票据类型轴）、高峰期负载均衡（运行时选一个，不是同时两个）。

### 5.9 美团 KDS 的「工序模式」：比档口更细的一层

档口与设备是 **1:多**，但设备侧是 **多:1**——「目前 KDS 设备仅允许关联一个档口，不允许关联多个档口，当商家有多个档口需求时，可以使用多个设备关联多个档口」`【厂商文档】`。

同一档口下挂多台设备时，每台设备有**工序模式**，可单选或全选：

```
配菜 → 制作 → 传菜
```

菜品在档口内部按状态机流转 `【厂商文档】`：

```
待配菜 →(点一下)→ 待制作 →(点一下)→ 待传菜 →(点一下)→ 已完成
                    ↑ 可撤销
```

「当收银端下单之后，该菜品/订单会先进入到工序模式为【待配菜】的设备，当配菜完毕之后才会进入【待制作】的设备，制作完毕之后才会进入【待传菜】的设备。」

**"划菜"就是推进这个状态机的那一次点击**——美团把"划菜、撤销划菜、叫号"并列为 KDS 的本地操作。而 §4 提到的分批划菜（20 串先出 5 串）就是允许这次点击只推进一部分数量。`【推论】`

### 5.10 「一道菜在多个档口」的三种含义，和档口之间到底怎么交接

「多个档口」这个说法混了三件完全不同的事 `【推论】`：

#### A. 串行跨工位——一道菜依次经过几个岗位（中餐厨房常态）

中餐厨房七大工种本身就是**流水线**，不是并列出品单元 `【外部】`：

```
水台(宰杀、刮鳞、去腮、初加工) → 砧板/配菜(改刀、上浆、腌制)
   → 炉灶(烹调) 或 上什(蒸、炖、汤) 或 烧腊(烧、卤) 或 点心(蒸、炸)
   → 打荷(装盘、盘饰、浇汁) → 出品台
```

举例：**清蒸鱼** 走 水台→砧板→上什(蒸柜)→打荷(浇汁摆盘)；**烧腊拼盘** 走 烧腊档(提前挂炉烧好)→斩件→打荷(摆盘)；**老火汤** 走 上什(几小时前炖上)→打荷(分盅)。

> 这一类在系统里**通常只给最后一个出品岗位打单**。前面的水台、砧板靠备料单/配菜单，很多店根本不打，靠口头和料头盘。`【推论】`

#### B. 组合商品——一个商品的构成部件分属不同档口（系统里真正的多档口）

| 商品 | 拆到哪些档口 |
|---|---|
| **套餐** | 凉菜档 + 热菜档 + 主食档 + 汤档。美团明写「**套餐内容其实是普通菜，可以在收银系统编辑普通菜的界面中为套餐内菜品设置打印档口**」`【厂商文档】` |
| **火锅一桌** | 锅底档（鸳鸯锅要出**双格备料单**）+ 涮品（冷柜/砧板）+ 小料台 `【外部】` |
| **烤鱼** | 烤档（鱼）+ 热菜档（配菜、底料） |
| **宴会套餐** | 美团有独立的「宴会套餐」形态，**退子菜时要选桌台和份数**——「可以将 1 号桌中的 C 菜退菜 2 份，可以将 2 号桌中的 C 菜退菜 1 份」，即一个套餐横跨多桌 `【厂商文档】` |

#### C. 并行同菜——同一道菜哪个档口都能做

- **多楼层独立厨房**：1 楼 2 楼各有热菜档，同一道宫保鸡丁两边都能做。
- **高峰期多炒锅**：由**荷王**动态分配——「要让哪个炒锅炒，基本上都是由荷王管控的」`【外部】`。
- **堂食 / 外卖分线**、**明档 + 后厨**。

---

#### 厨房里的交接：靠打荷这个中枢，不是靠档口直连

`【外部】`

1. **打荷是路由器**：「负责传递砧板师傅切好的配料给炒锅师傅」，炒好后收回装盘，「端出去给服务员或者传菜员」。
2. **荷王是调度**：「根据楼面反馈安排好什么时候上前菜汤品，什么时候上热菜大菜，要让哪个炒锅炒」。
3. **出品台/地哩台是缓冲区**：各档口的成品都放这儿，由传菜员取走。
4. **上菜节奏有量化标准**：冷盘用去三分之二时上第一道热菜；**每道菜间隔原则不超过 5 分钟**；**出主菜前间隔不超过 8 分钟**。

> 注意：**档口之间没有直接交接**。砧板不把料交给烧腊，热菜不把菜交给凉菜。所有横向流动都经过打荷，所有纵向汇聚都在出品台。`【推论】`

#### 系统里的交接：三家厂商全都不管

在客如云、美团、银豹全部资料里检索 `上游档口` / `下游档口` / `档口流转` / `档口之间` / `转档口` / `档口顺序` / `跨档口`——**零命中**（唯一"二次加工"命中是报表导出，无关）`【厂商文档】`。

系统只提供三种**看起来像交接、其实不是**的能力：

| 能力 | 实际作用域 | 说明 |
|---|---|---|
| **KDS 工序模式** | **档口内部** | 待配菜→待制作→待传菜→已完成，同一档口下多台设备按工序接力。**不跨档口** `【厂商文档】` |
| **等叫 / 起菜 / 催起** | **前厅 → 后厨** | 节奏控制。场景是「人还没到齐，要求等人齐之后再上菜」。美团 5.10 把起菜和催菜合并为**催起**：未起菜则自动起菜，已起菜则催菜 `【厂商文档】` |
| **划菜 / 划单** | **出品侧汇聚** | 确认一桌菜齐没齐 |

> **结论：档口之间是"扇出—汇聚"，不是流水线。** 一张订单扇出到 N 个档口并行下单、并行打印、并行制作；然后在出品台由人重新汇聚成一桌菜。系统里**没有档口 A → 档口 B 的有向边**，齐套判断也不在系统里，在划菜员眼里。`【推论】`

#### v4 的形态：同样是扇出—汇聚

v4 的作业面 fixture 印证了同一结构 `【v4代码】`。以「太原万象城多档口履约」为例：

```
WORKSTATION 太原热厨档口   tags=[热菜]   units=[MAKE]  grouping=ONE_TICKET_PER_SURFACE_ORDER
WORKSTATION 太原冷菜档口   tags=[冷菜]   units=[MAKE]  grouping=ONE_TICKET_PER_PRODUCT_LINE
WORKSTATION 太原烘焙档口   tags=[烘焙]   units=[MAKE]  grouping=ONE_TICKET_PER_PRODUCT_LINE
HANDOFF     太原综合取餐交接点            units=[HANDOFF]
```

三个制作作业面并列（各收各的标签），末端一个 HANDOFF 汇聚点。**但 v4 的 `HANDOFF` 指的是"交给顾客或骑手"**（其他场景里是"顾客取餐交接点""长沙骑手交接点"），**不是档口之间的交接**。作业面的 `supportedWorkUnitKinds` 取值是 `MAKE` / `PACK` / `HANDOFF`，表达的是"制作→打包→交付"三段主流程，每段一个作业面。

所以 v4 与三家厂商在这一点上是同构的：**并行扇出 + 末端交付汇聚，中间没有工位间流转**。`【推论】`

### 5.11 「待配菜→待制作→待传菜」是几个屏幕、怎么操作

**答案是"由店自己决定"**：工序不是三个写死的屏幕，也不是一个屏幕里三个写死的 tab，而是**每台设备登录时勾选自己承担哪几道工序**。`【厂商文档】`

#### 设备侧：勾工序

美团 KDS 开机进入"选择工作模式"界面，**配菜 / 制作 / 传菜，支持单选也可以多选**。之后也能在【设置】-【基础设置】-【本机工作模式】随时改。官方给了三个例子：

| 业态 | 勾什么 | 理由 |
|---|---|---|
| 正餐地方菜 | 配菜 + 制作 + 传菜（全勾） | 有完整三段需求 |
| 烧烤 | 制作 + 传菜 | 「只经营烤串，不需要进行配菜」 |
| 快餐 | 只勾传菜 | 「菜品全部由客人自选，无配菜和制作需求」 |

所以：

- **三台设备各勾一道** → 就是三个屏幕，订单在设备之间流转；
- **一台设备全勾** → 就是一个屏幕，左上角显示当前工序模式，**点击不同流程模式切换**。

官方的三设备例子写得很直白：「热菜档口关联了 ABC 三个设备，分别负责配菜制作划菜……订单会先进入到设备 A 的【待配菜环节】，设备 B、设备 C 无订单信息；当设备 A 配菜完毕之后，**设备 A 不再展示 12 号桌的菜品/订单信息**，菜品/订单会进入到设备 B，处于【待制作】状态」。

> 注意这条约束：**一台 KDS 设备只能关联一个档口**。档口决定这台设备**能看到哪些菜**（关联热菜档口就只收到鱼香肉丝、宫保鸡丁，冷菜档口的拍黄瓜根本不出现），工序决定**什么时候看到**。两者正交。`【厂商文档】`

#### 用户侧：点一下推进一格

```
待开始 → 待配菜 → 待制作 → 待传菜 → 已完成
        ↑ 每点一次前进一格，可撤销
```

- 官方原话：「芹菜腐竹目前为待配菜状态，点击之后，该菜品会切换至待制作状态（**此时可以进行撤销操作**），再次点击会切换至待传菜状态，再次点击会切换至已完成状态」。
- 有批量入口：「也可以点击【确认全部配菜完成】进行全部确认」。
- **"待开始"是可选的第四个状态**：基础设置里开【记录开始时间】后，「需先在待开始划菜，再在待配菜/待制作划菜，**记录更精准的配菜和制作时长**」。默认关闭。
- **分批推进**：点菜品数量（方案一）或直接点菜品卡片（方案二）→ 弹窗填数量。「20 串羊肉串，先出 5 串，再出 15 串」。
- 其他设置：设备名称（多设备区分）、语音提醒（新订单/加菜/**叫起**）、退菜通知弹窗开关、超时设置（堂食与外卖分别设，1–120 分钟）。

#### 划菜状态会反向同步回前厅（5.14）`【厂商文档】`

收银端【收银基础设置】-【先用餐后结账】里有「同步 KDS 划菜信息」开关，默认关闭。开启后：

- 收银端**不再支持手动划菜**，划菜按钮**置灰不可点**；若当前订单已有手动划菜记录，**会被 KDS 记录覆盖**；
- 点餐助手的"划菜""取消划菜"按钮**隐藏不展示**；
- 显示形态：部分划显示「划 5」，超过 99 显示「99+」，全部划完显示「全划」；
- **称重菜不支持部分划菜**；
- 套餐：子菜按数量显示，全部划完后在**套餐名称前**展示划菜，子菜信息不再展示；
- 断连兜底：「已划菜品继续展示，未划菜品因无法获取 KDS 状态，则不会展示后续 KDS 划菜信息」。

> 这是一个很干脆的产品决策：**一旦接入 KDS，划菜的唯一真相源就是 KDS，前厅侧的手动划菜能力被直接关掉**，而不是两边都能改再去合并。`【推论】`

#### 客如云的做法：设备角色二选一，且操作步骤可配 `【厂商文档】`

客如云不是勾工序，而是开机选**设备角色**：

| 角色 | 操作 |
|---|---|
| **出品设备** | 点【开始制作】→【制作完成】；展示方式可选商品模式或订单模式 |
| **传菜设备** | 单菜品划菜 / 已划可撤销 / 划单 / 叫号；展示方式四选一（订单、分类、商品列表、商品卡片） |

而且「出品堂口」配置里勾的不只是菜品，还包括**操作步骤**——步骤本身是可配的。

**两家的共同点**：设备先声明自己是干什么的，再决定看到什么、能点什么。屏幕数量是部署选择，不是模型固有属性。`【推论】`

## 7. 容错与运维全景

这块在设计文档里最容易被忽略，但在现场是高频问题。

| 机制 | 厂商真实做法 |
|---|---|
| **备用打印机** | 客如云：后厨票据机可加备用机，**多台可互为备用**；主机连接异常或状态异常（**缺纸、开盖**）时，**系统重试 1 分钟后自动切换**，并在票据上方印"xx打印机已断开，切换至备用打印机出票"。主机若正作为他人备用，禁用前必须先解除；删出票口时主备一起删。 `【厂商文档】` |
| **补打** | 见 §4.3。美团限制 30 天。 |
| **打印机发现** | 客如云支持"自动搜索打印机"找出空闲打印机；非本品牌打印机可能搜不到，需手动添加。要求**网口机与收银机同网段**。 `【厂商文档】` |
| **配置生效** | 美团：后台改配置后收银端要做"数据更新"才生效；总部配置要"下发"。 `【厂商文档】` |
| **常见故障** | 出白纸、不出单、舱门无法开关、新增菜品不出单、内容显示不全或对不齐 —— 客如云和美团都有专门文档。 `【厂商文档】` |

**"重试 1 分钟后切备用机"是一个非常具体的产品决策** —— 不是立即切，也不是不切。`【推论】`
