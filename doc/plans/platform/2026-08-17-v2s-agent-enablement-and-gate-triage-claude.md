# 让实施 agent 一次做对 —— 完整方案

- 作者:Claude(独立评审侧)

## 0 · 目标与判据

> **一切工作只为一件事:提高实施 agent「一次做对」的概率。**
> —— Dexter 定。不是系统自洽,不是治理完备。

由此得到四条判据,全文逐条套用:

| # | 判据 |
|---|---|
| J1 | 不会改变 agent 做法的知识是**噪音**,哪怕它是真的 |
| J2 | 遵守一条规矩的成本,**不得超过**它防住的返工 |
| J3 | 门只守「**知道也会漏**」的事;「知道就不会犯」的做成随手可得的背景 |
| J4 | **不产生过程垃圾**:取代者落地即标记被取代者 |

**证据纪律**:全文数字为我本人跑过或读过源码得到。子 agent(含盲审)的断言一律标注,
未经我复核的**不作为依据**。本文前一版违反过这条,已在 §9 登记。

## 1 · 五层与接缝规则

给 agent 的东西分五层。**每层装什么、接缝处不许重复,是本方案的骨架。**

| 层 | 装什么 | 触发时机 | 长度 |
|---|---|---|---|
| **入口文件** | 开场必知的硬边界 + **情境→skill 调度表(正本)** | 会话开始一次 | 应大幅缩短 |
| **skill** | 每类情境的**完整走法** | 被指名时 | 已有 9 个,不动 |
| **脚本** | 单点事实查询 | 被调用时 | 已有,降低调用成本 |
| **任务模板** | **一行指针 + 本批特有信息** | 每次派活 | 极短 |
| **详设 `RECALL` 字段** | **这一项**动手前要重开什么 | **每进入一项之前** | 三五行 |

**接缝规则(违反即产生第二真相源)**:

- 调度表**正本在入口文件**,任务模板只放**指针**。重复指针零成本,重复内容必漂移。
- `RECALL` 字段只写**这一项特有**的,通用纪律指向 skill,不复述。
- skill 已有的内容(如 `cs-memory-recall` 第 5 步的「写前重开」),**任何其他层不得复述**。

**为什么 `RECALL` 是关键的一层**:Dexter 观察到「会话一长、任务一长,agent 就忘」。
机械原因是——`SessionStart` hook 只在开场触发一次、`UserPromptSubmit` 在自主实施时不触发、
`Stop` 太晚。**没有任何东西在「进入第 7 项之前」响。**
而 agent 做每一项时**必然会重读那一项的详设条目** —— 把提醒挂在他必读的位置上,
触发率 100%,零新增机制,零噪音。

### 2.6 一个反复出现的结构缺陷:单向闭包

同一个形状已经出现**三次**,每次都让「B 里有而 A 里没有」在设计上不可检测:

| 位置 | 缺口 | 实测后果 |
|---|---|---|
| `project-memory` 登记 | `cli.mjs` 零 `readdir`,只读清单 | 12 个条目飘在体系外,含 Codex 实际需要的那条 |
| B1 需求的回执分母 | 只枚举「私有方法」这一种语法形态 | 漏掉「专用 receipt service 类」一族 |
| **`runtime-environment-keys` 门** | **只验 policy 里的 15 个在别处存在,不扫代码里的 `V2S_*` 是否都在 policy 里** | **门的扫描集(scripts+tools)内 46 个不同键,policy 登记 15 ⇒ 31 个未登记,而门是绿的** |

⚠️ **原写「57 个 / 42 未登记」是错的** —— 那是拿 `apps scripts tools` 三处算的,
而该门的扫描集只有 `scripts` 与 `tools`。**门内正确数是 46 vs 15。**
`apps/` 里的 `V2S_*`(57−46=11 个)**根本不在门的射程内**,那是另一个缺口,不能混算。

**共同形状**:分母按**语法形态**枚举,或闭包只做**单向**。

⚠️ **修法不是新建门。** 后两处都已经有门/有分母,**它们只是少验一个方向** ——
补反向扫描是在既有门里加几行,不是加控制面。第一处同理(§10 保留的那 10 行)。

⚠️ 这一条同样适用于**我自己写的分母**:CP-INV-7 的覆盖范围只列了 ObjectNode 的五个方法,
漏了 `Map.of(...)` 这一族,于是 `ManagedInvitationBootstrap` 的 5 个跨界字段名不在分母内。
已在详设中更正。

## 3 · 入口文件优化

**实测**:`AGENTS.md` 95 行 / 19,750 字节;四份入口文件合计 **53,174 字节**,全部要求开场读完。
`CLAUDE.md` 非空行 **66**,其中与 `AGENTS.md` 逐字重合的行 **14–16**
(区间是因为口径不同:我按「长度 >25 字符」过滤得 14,盲审按 >20 字符得 16)。

⚠️ **本节最重要的事实不是字节数,是四份入口文件对同一件事给出四个说法** ——
见 §3.1。

**问题不是写得不好,是职责错配。** `AGENTS.md` 同时装着五种生命周期不同的东西:
会话入口链 · 约 50 条长期工程约束 · 当前 Roadmap 状态与授权 · 协作边界 · 退役登记。
而仓内那几处矛盾(它自己对 `index.md` 定位前后打架、与 BLUEPRINT 在 backend-acceptance 上互斥)
**全部是复制导致的漂移**。

### 3.1 四份入口文件对 backend-acceptance 给出四个说法(实测)

| 文件 | 它说的 |
|---|---|
| `PLATFORM-BLUEPRINT.md` | 只验证 `getPublicInvitationView` · **197** 个 provider |

一个 fresh agent 按 `AGENTS.md` 规定的顺序读,**第 1–2 步就会读到一个完全失真的模型**。
**这发生在 100% 的会话里。** 而 41 道未接线的红门,在接线之前对实施 agent 的影响是 **0**。

⇒ **这是全文对「一次做对」伤害最直接的一处**,因此在 §11 中排为第 1 步。

**判别式**:**这一条如果 agent 在需要它的那一刻才知道,会不会已经晚了?**

## 5 · 任务模板(每次派活粘贴)

```
━━━ 本批任务 ━━━
目标:<一句话>
详设:<仓库根相对路径>
本批范围:<CP 编号>。范围外的东西看到也不要动,报告即可。
已知红门(与本批无关,撞到不要修,报告即可):<当前红门清单>

━━━ 每进入一项之前 ━━━
按该项详设条目里的 RECALL 字段走一遍。字段为空 ⇒ 详设有缺陷,停下来问。

━━━ 什么时候必须停(两类,第二类更重要)━━━

第一类 · 你自己不确定 ⇒ 停。
第二类 · **上游给你的东西,和你看到的源码/裁决对不上 ⇒ 停,以源码为准。**
  上游包括:详设 · 评审 finding · 我给的分母与数字 · 任何"权威"结论。
  ⛔ **不因为它来自设计方或评审方就采信** —— 它们都是待验证输入。

停的时候不要做这四件事:
  自己选一个"合理的"做法继续 · 加兼容层 / fallback / TODO 绕过 ·
  缩小范围报完成 · 为了让门变绿而改代码。

报告给三样:你看到的原文事实 · 两种候选理解 · 你倾向哪个及为什么。
只说"卡住了"会多走一个来回。

━━━ 完成之后 ━━━
1. 用 RECALL 里那份原文逐项回读:做出来的,和它写的是同一件事吗?
```

## 7 · hook 裁定:不放开 `PreToolUse`

**现状(我实测)**:三个 hook,`SessionStart` 与 `UserPromptSubmit` 均 0 处阻断分支,
`Stop` 有 3 处;`scripts/check/agent-lifecycle` 第 96 行硬禁 `PreToolUse`/`PostToolUse` 键存在。

**裁定:不放开。** 理由:

1. `PreToolUse` 对**每次工具调用**触发,一个会话几百次。哪怕每次一行,也是几百行注入 ——
   结果是**训练 agent 忽略它**,和入口文件被遗忘是同一个机制。
2. 要有用就得选择性触发 ⇒ 需要一张映射表 ⇒ 要人维护 ⇒ 漂了就漏报误报。**这是会长大的负担。**
3. 它必然长回阻断(上一个就是这么长成控制面的),防回归又要配门配红夹具。
4. **证据为零**:`prompt-route` 已是建议式推荐器,无任何证据表明有人照它做过。

**替代**:§6 的 `RECALL` 字段。

⚠️ **它不是等效替代,前一版说「零成本、100%」是错的**,现予更正:

- **覆盖面不等效**:`PreToolUse` 在每次工具调用触发,含**设计者没想到的那次**;
  `RECALL` 只覆盖详设作者**写下来的**那些。
- **不是零成本**:现有详设有 28 个 CP ⇒ 28 条新的、手写的、且被规定为**阻断性**的断言
  (「字段为空 ⇒ 停下来问」)。按我自测的错误率,每条写错都比没有更糟 ——
  这正是我在 §4 亲笔写的「填错会把 agent 指到错的地方,比没有表更糟」。
- **「100% 触发」是循环论证**:前提是「会话一长 agent 就忘」,而该机制假定他在第 7 项
  必然认真重读该项详设。若这个假定成立,他本来也不会忘。

⇒ **仍然选它**,但理由是**代价形态更可接受**(28 条可评审的静态文本 vs 一个每次工具调用
都注入、必然长回阻断、且需要一张会漂移的映射表的运行时机制),不是「等效」。
**写错时的处置**:`RECALL` 内容与源码不符 ⇒ 按 §5「第二类停机」处理,以源码为准。
