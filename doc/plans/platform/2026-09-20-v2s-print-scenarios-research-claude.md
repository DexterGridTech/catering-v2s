## 1. 结论速览

1. **v4 已实现一套完整打印域**，场景闭集 **19 个**，全部 `ACTIVE`；渲染路线 2 条（ReceiptLine 17 个 / LabelCanvas 2 个）；纸型 6 种，纸张类别只有 **热敏小票** 和 **标签** 两类。`【v4代码】`
2. **v6 打印规则域的场景闭集与 v4 完全一致，也是这 19 个，一个不多一个不少。** v6 的增量全部在**治理结构**（集团库/项目库/门店库三层、场景治理模式、纸型模板政策），不在场景覆盖面。`【v4代码】``【v6设计】`
3. **v2s 仓内目前零打印实现**：全仓只有两处文档性提及（终端规范里把「打印/HID」列为可能不可用的能力、后台规范里「原样打印」是个比喻），没有任何 printScene、PrintRule、模板或打印契约。`【v2s代码】`
4. **最重要的架构事实：分单/档口路由不在打印域。** v4 把它放在履约与生产域，形态是 `生产标签(productionTag) → 作业面(processingSurface) → 出单分组策略(productionOutputGroupingPolicy)`。打印规则域被刻意做窄，v6 明文排除条件、优先级、时段、渠道、终端用途、备用打印和重试策略。`【v4代码】``【v6设计】`
5. **对照四类业态，19 个场景有明确缺口**，且缺口分两种性质：一种是**场景没有**（划菜总单、加菜单、转台通知单、纸质叫号票、预订/定金/宴会类），一种是**维度不够**（无页式纸型、无多联单模型、出单分组只有 3 种、一模板只绑一场景）。**后者比前者更难补**，因为它改的是模型形状而不是清单长度。`【推论】`
6. **v6 明确把宴会挡在门外**：`06-销售集合与发布域` 第 1292 行写「预订、宴会订单、定金和菜单锁定归 `11` 或外部系统协作」，第 458 行写「预约/预订/宴会订单生命周期不在本域」。也就是说 **v6 从未设计过宴会链路，自然也没有宴会打印**。v2s 若要兼容宴会，这是新建而非移植。`【v6设计】`

### 2.3 纸型闭集（这是最硬的约束）

| paperProfileRef | paperKind | 用在哪些场景 |
|---|---|---|
| `THERMAL_58` | THERMAL_RECEIPT | 17 个小票类场景全部必备 |
| `THERMAL_80` | THERMAL_RECEIPT | 17 个小票类场景全部必备 |
| `LABEL_40X30` / `LABEL_50X30` | LABEL | 仅 `CUP_LABEL` |

小票类场景的 `paperTemplatePolicies` 都是 58 和 80 **双份 required**，且 v6 明文规定「同一纸型缺模板时发布诊断必须定位到具体纸型，不能自动用 80mm 模板兜底 58mm，或反向兜底」。`【v6设计】`

### 2.4 分单与路由：不在打印域

v4 的履约生产规则 fixture 揭示了真实形态：`【v4代码】`

```
productionTag   生产标签    例：HOT-DISH(热菜制作) / PACKING(外带打包)，kind ∈ {PRODUCTION, PACKAGING, ...}
processingSurface 作业面    例：开放热厨工作台 / 大厅开单收银岗 / 打包台 / 交接台
                            kind ∈ {WORKSTATION, ORDER_CASHIER, PACKING, HANDOFF, PRODUCTION, PACKAGING}
                            acceptedProductionTagKeys[]  ← 作业面接哪些标签
                            supportedServiceModes[]      ← DINE_IN / PICKUP / TAKEAWAY / DELIVERY
                            productionOutputGroupingPolicy ← 出单怎么分组
```

出单分组策略在 fixture 中出现 3 种取值：`ONE_TICKET_PER_SURFACE_ORDER`（一作业面一订单一张）、`ONE_TICKET_PER_PRODUCT_LINE`（一商品行一张）、`ONE_TICKET_PER_UNIT`（一份一张）。`【v4代码】`

**这意味着「菜品怎么分流到哪台打印机」= 商品打生产标签 → 标签匹配作业面 → 作业面绑终端 → 终端下挂打印机（TCP 的 `TerminalPrinterConfig`，其"用途"本质就是它能承接的 printScene 集合）。打印规则域完全不参与。** `【推论】`

## 3. v6 打印规则域的设计（与 v4 的差异）

### 3.1 v6 新增的治理结构（v4 有部分实现，v6 写成正式模型）

- `PrintConfigLibrary`：`ownerScopeKind ∈ {COMMERCIAL_GROUP, PROJECT, STORE}` 三层库，`sourceLibraryRef` 只记来源**不做字段级继承**，集团库变更**不自动推送**。
- `PrintSceneGovernancePolicy`：`governanceMode ∈ {PROJECT_LOCKED, STORE_CUSTOMIZABLE}`。对客票据建议项目锁定，后厨单/杯贴/标签建议允许门店自定义。**不做字段级/区块级可改范围控制**，要么整个场景锁，要么整个场景放开。
- `PrintRule` 起步期字段：`printScene` · `ownerLevel` · `governancePolicyRef` · `paperTemplates[]` · `enabled` · `copies` · `allowReprint` · `failurePolicy` · `version/status`。
- `failurePolicy ∈ {PROMPT_ONLY, RECORD_AND_CONTINUE, BLOCK_LOCAL_FLOW}`。
- `StoreEffectivePrintConfigSnapshot`：**终端只消费最终有效快照，不在本地合并**；`storeRef + printScene` 唯一。`【v6设计】`

### 3.2 v6 的硬边界（12 条设计红线里最关键的 5 条）

1. **打印机不是终端。** POS/KDS/叫号机才是终端；小票机、厨打、标签机、叫号打印机、云打印机都只是所属终端下的 `TerminalPrinterConfig`。打印机不激活、不登录、不订阅 topic、不建 TDP session、不 ACK、不拥有 read model。
2. **所有业务打印动作都由终端业务逻辑本地发起。** 后台业务域**不通过 TDP 下发打印命令**，`command_outbox` 只承载 TCP 控制命令。
3. **打印规则不引用任何打印机**（不引用打印机、打印机组、IP、USB、云打印 SN、`TerminalPrinterConfig`、terminal purpose）。`copies` 只表示份数，不表示打印到哪些设备。
4. **打印成功/失败不是 TDP ACK，也不自动等于业务成功/失败**，不污染源业务事实。
5. **一个 `PrintTemplate` 只能绑一个 `printScene`**；相似场景要复用样式应复制模板，不做跨场景共享模板。`【v6设计】`

### 3.3 v6 明确不做的

> 「起步期不支持条件、优先级、时间段、渠道、终端用途、备用打印策略或重试策略。」
> 「起步期不允许 `PrintRule` 自己配置订单状态、支付状态、履约状态、时间段、渠道或终端用途条件。」`【v6设计】`

**这是一个有意识的窄化，不是遗漏。** 代价是：任何"什么情况下打什么"的条件，都必须表达成**另一个 printScene**，或者下沉到履约生产域的 tag/surface 模型。`【推论】`

## 5. 差集分析：19 个场景覆盖不到什么

### 5.1 A 类：场景清单缺口（补一条注册表就能解决）

| # | 缺的场景 | 属于哪类业态 | v4/v6 现状 | 严重度判断 |
|---|---|---|---|---|
| A-1 | **划菜单 / 传菜总单** | 中餐、大餐 | 19 个里没有。`KITCHEN_TICKET` 是给制作岗的分单，不是给划菜/传菜岗的**汇总核对单** | 高——中餐正餐的标准岗位，缺了就不是完整中餐 |
| A-2 | **加菜单 / 追加单** | 中餐、大餐 | `KITCHEN_TICKET` 触发时机只写「订单下发到厨房时」，**不区分首次下单与追加** | 中——可复用 KITCHEN_TICKET，但厨房要能一眼看出是追加 |
| A-3 | **转台 / 并台 / 拆台通知单** | 中餐、大餐 | `TABLE_HOLD_TICKET` 时机含「换台」，但那是**重打桌台识别单**，不是给后厨/传菜的**变更通知** | 中——后厨不知道菜要送到哪桌是真实事故 |
| A-4 | **纸质叫号票 / 排队号票** | 小餐 | v6 把叫号建成履约事实 `RecordPickupCall` + 屏显，**无打印场景**。`PICKUP_TICKET` 是支付后的取餐凭证，不是排队等位号票 | 中——取决于是否做等位排队 |
| A-5 | **预订单 / 预订确认单** | 宴会、大餐 | v6 明确「预订、宴会订单、定金和菜单锁定归 `11` 或外部系统协作」，**未建模** | 高（若做宴会）/ 无（若不做） |
| A-6 | **定金收据** | 宴会、大餐 | 订金在 v6 里是**支付事实**（无单收款/订金收退），没有对应打印场景 | 同上 |
| A-7 | **宴会菜单 / 席卡 / 台型图** | 宴会 | 无。且 `06-销售集合与发布域` 把"宴会菜单锁定"推给 `11` 或外部系统 | 同上 |
| A-8 | **EO 单（宴会任务单）** | 宴会 | 无。多部门分发单据，形态与小票完全不同 | 同上 |
| A-9 | **日结单 / 营业日报** | 全业态 | 只有 `SHIFT_HANDOVER_RECEIPT`（班次口径）。v6 明确「交接是班次经手口径，不是营业收入、到账或结算主账」 | 中 |
| A-10 | **挂账单 / 签单** | 大餐、宴会 | 无。v6 有挂账还款的支付事实，无打印场景 | 低-中 |
| A-11 | **反结账 / 作废通知单** | 中餐、大餐 | 无。反结账在 v6 里只作为财务口径差异出现 | 低-中 |
| A-12 | **称重标签** | 自助餐、生鲜、熟食 | `CUP_LABEL` 和 `PRICE_TAG` 都不是按重计价的现场称重标签 | 低（取决于业态范围） |

### 5.2 B 类：模型维度缺口（补清单解决不了，要改模型形状）

| # | 缺的维度 | 证据 | 为什么补清单解决不了 |
|---|---|---|---|
| **B-1** | **页式纸型（A4/A5）** | `paperKind` 闭集只有 `THERMAL_RECEIPT` 和 `LABEL`；6 个 profile 全是热敏或标签 `【v4代码】` | 宴会 EO 单、宴会菜单、盘点长清单、营业日报都是页式。加一个 `PRICE_TAG` 式场景没用，**渲染引擎（ReceiptLine 是面向字符列的）、纸型模型、预览、校验链整条都要扩**。ReceiptLine 的 `cpl`(每行字符数) 概念在 A4 上不成立 |
| **B-2** | **多联单（一次打印、多联内容不同）** | `PrintRule.copies` 只是份数；v6 明文「一个 `PrintTemplate` 只能绑一个 `printScene`」`【v6设计】` | 中餐四联单（收银联/厨房联/划菜联/存根联）**内容不同**。当前模型下只能建成 4 个场景 + 4 个模板 + 4 条规则，语义上它们其实是**同一个业务时机的四个副本**。三联/五联结账单同理 |
| **B-3** | **出单分组策略只有 3 种** | fixture 中仅见 `ONE_TICKET_PER_SURFACE_ORDER` / `ONE_TICKET_PER_PRODUCT_LINE` / `ONE_TICKET_PER_UNIT` `【v4代码】` | 中餐要的是「**按菜品分类拆**（冷菜一张热菜一张）」「**按楼层/区域拆**」。前者可以靠"一个分类一个 productionTag、一个 tag 一个 surface"绕出来，**但那会让作业面数量随分类数膨胀**；后者当前模型里没有承载点 |
| **B-4** | **打印规则零条件** | v6 明文排除条件、优先级、时段、渠道、终端用途、备打、重试 `【v6设计】` | 「大厅打这台、包间打那台」「午市打、晚市不打」「外卖渠道多打一份」全部无处表达。**只能通过增加 printScene 或增加作业面来模拟**，两者都是把条件维度压进枚举维度 |
| **B-5** | **无"打印机故障转移"** | v6 §12 待确认第 3 条：「多终端、多打印机下的本地选择策略、备用打印机切换和重试策略放在终端执行规范还是 TCP」——**悬而未决** `【v6设计】` | 厨打机坏了菜就不做了，这在正餐是停业级事故。当前设计里这个责任没有 owner |
| **B-6** | **场景与业态无关联** | 19 个场景是平铺的，没有"这个业态用哪些场景"的表达 `【v4代码】` | 茶饮店的配置页会看到「压桌单/预结单/划菜单」，正餐店会看到「杯贴」。**门店首配的噪音**，也让"默认打开哪些"无处表达 |

### 5.3 一个反直觉的观察

**v4 的 19 个场景里，`FULFILLMENT`(履约) owner 占 10 个，超过一半。** 而 `TRANSACTION` 只有 5 个。`【v4代码】`

这说明 v4/v6 的打印域重心在**后厨与履约执行**，不在收银。但四类业态调研显示，**业态差异主要体现在履约侧**（茶饮=标签、中餐=分单划菜、宴会=预订EO），**收银侧反而高度同质**（都是预结+结账+退款）。

**推论：v2s 若要兼容全业态，压力会集中在履约与生产域的 tag/surface 模型，而不是打印规则域本身。打印规则域照抄 v6 大概率够用；真正要重新设计的是它上游的生产路由模型。** `【推论】`

## 6. 如果 v2s 要兼容所有餐饮业态，需要什么

> 本节是**候选方案**，每一档都标了代价，供讨论，不是建议直接做。

### 6.1 场景层：建议的场景闭集

**第一档（照搬 v6 的 19 个）** —— 覆盖茶饮、快餐、外卖、标准中餐的主干。
**第二档（+4，补中餐正餐岗位）**：`EXPEDITE_SUMMARY_TICKET`(划菜总单) · `ADDITION_KITCHEN_TICKET`(加菜单) · `TABLE_TRANSFER_TICKET`(转台通知单) · `DAILY_CLOSING_RECEIPT`(日结单)。
**第三档（+4~6，补宴会）**：`RESERVATION_CONFIRMATION`(预订确认单) · `DEPOSIT_RECEIPT`(定金收据) · `BANQUET_MENU`(宴会菜单) · `BANQUET_EVENT_ORDER`(EO 单)。**前置条件是先有预订/宴会订单的业务模型**，而 v6 把它推给了交易域或外部系统 —— 这一档**不是打印问题，是业务域缺口**。
**第四档（按需）**：`QUEUE_TICKET`(排队号票) · `CREDIT_SLIP`(挂账签单) · `VOID_NOTICE`(反结账通知) · `WEIGHT_LABEL`(称重标签)。

### 6.2 时机层：我建议把触发时机显式分类

v4 的 `triggerTiming` 是**自然语言散文**，每个场景自己写一句。这导致无法回答"还有哪些时机没覆盖"。建议改成**分类学 + 散文**双轨：`【产品判断】`

| 时机类 | 含义 | 该类下的场景 |
|---|---|---|
| **订单生命周期点** | 开台/下单/预结/结账/退款/反结账 | 压桌单、预结单、收银小票、退款小票 |
| **菜品生命周期点** | 下发/追加/退菜/催菜/等叫/叫起/出品/打包 | 后厨单、加菜单、退菜单、催菜单、等叫单、叫起单、打包单、划菜总单 |
| **桌台生命周期点** | 开台/转台/并台/拆台/清台 | 压桌单、转台通知单 |
| **交付与取餐点** | 取号/叫号/取餐/交接 | 取餐小票、排队号票 |
| **班次与经营周期点** | 交接班/日结/盘点 | 交接班小票、日结单、盘点清单 |
| **资产维护点** | 上架/调价/换签 | 价签 |
| **预订与筹备点** | 预订/收定金/确认/派工 | 预订确认单、定金收据、宴会菜单、EO 单 |
| **人工补打** | 任何场景的手动重打 | 由 `allowReprint` 控制，**不是独立场景** |

这张表的价值是：**它自带反例**。任何一个业务动作，问"它落在哪一类"，落不进去就是分类学有缺口；落进去但没有对应场景，就是场景清单有缺口。

### 6.3 内容层：字段库

v6 的 `PrintFieldLibraryRef` 模型（字段分组、必填/可空/可重复、格式化器、废弃标记、sample pack、版本 pin）**设计是完整的，建议照搬**，不需要重新发明。`【v6设计】`

需要注意的是 v6 的一条判断：「已发布字段库版本不可变；字段库升级只生成新版本，不自动修改已发布模板」。这条在 v2s 的"不为向后兼容长期保留废弃方案"原则下**可能需要重新裁决** —— 版本不可变 + 不自动升级，等价于长期保留多版本。`【待裁决】`

### 6.4 核心建议：三个维度正交拆分

我认为 v2s 要兼容全业态，关键不是把场景表拉长，而是**把现在混在一起的三个问题拆开**：`【推论】`

```
维度一  场景(WHAT)  ：打什么内容 —— printScene + 字段库 + 模板
维度二  路由(WHERE) ：打到哪台机 —— 生产标签 → 作业面 → 终端 → TerminalPrinterConfig
维度三  规则(HOW)   ：打不打/几份/能否重打/失败怎么办 —— PrintRule
```

v4/v6 已经把 **一 和 三** 放在打印域、**二** 放在履约生产域 + TCP，这个切分是对的。问题在于：

- **维度二的表达力不够**（B-3、B-4）：中餐的"按分类/楼层/区域分单"在当前模型里只能靠作业面数量膨胀来模拟。
- **维度一里混进了维度三的东西**（B-2）：多联单本质是"同一时机打多份不同内容"，是规则问题，却被迫表达成多个场景。

**如果只改一处，我会改维度二**：给作业面的 `productionOutputGroupingPolicy` 增加按商品分类/按区域的分组能力，而不是给 `PrintRule` 加条件。理由是前者不破坏 v6 的"打印规则零条件"红线，后者会。`【产品判断】`

## 7. 需要 Dexter 裁决的问题

1. **v2s 的业态边界到哪里？** 宴会（预订/定金/EO/宴会菜单）是**业务域缺口**不是打印缺口 —— v6 明确把它推给交易域或外部系统。要做宴会，得先决定预订与宴会订单的归属，打印是最后一步。**不做宴会的话，第三档场景全部不用考虑，B-1（页式纸型）的紧迫性也大幅下降。**
2. **页式打印（A4/A5）进不进？** 这是 B 类里成本最高的一条，牵动纸型模型、渲染引擎、模板编辑器、预览与校验链。除宴会外，营业日报和长盘点清单也会想要。建议明确 yes/no，不要留"以后再说"。
3. **多联单怎么建模？** 三个选项：(a) 一联一场景（照当前模型，清单变长）；(b) 扩 `PrintRule`，让一条规则挂多个"联"，每联一个模板（破坏"一模板一场景"的干净度，但语义最准）；(c) 不支持多联，靠 `copies` 打多张相同内容（最省，但中餐四联单内容不同，做不到）。我倾向 (b)，但它改的是 v6 已冻结的模型。
4. **分单路由的表达力要不要扩？** 即 §6.4 的建议。扩在履约生产域（我倾向）还是扩在打印规则域（会破 v6 红线）。
5. **打印机故障转移谁负责？** v6 §12 明确悬而未决。正餐场景下这是停业级风险，不宜继续悬着。
6. **起步期做多少？** v2s 当前零打印实现。整个打印域（v4 是 10,148 行 + 19 个字段库 + 19 个样例包 + 18 个模板组件 + 契约生成器）是**一个完整的大批次**，不是能顺手塞进现有批次的东西。
