## 0. 这份需求为什么只剩一条

本需求原为「apps/backend 与 apps/frontend 可读性整改」，含七条需求。经三轮独立评审（两轮 fresh 盲审子 agent + Codex），**每一轮都判 NO-GO，且每一轮的核心缺陷是同一类：我测了一个样本，却把需求写成了总体。**

| 轮次 | 被推翻的范围 |
| --- | --- |
| 第 1 轮 | 目录段频次把构建镜像目录算入；前端「禁 ui 层 HTTP」影响面从「8 个 feature」实为 **97 个文件** |
| 第 2 轮 | SQL 字面量判据对 Java text block 全盲（2 个文件今天即假绿）；平台模块判据所依赖的注册表只有 13 条而 Gradle 有 17 个模块 |
| 第 3 轮 | SQL 禁令范围从「4 个 owner service / 791 行」实为 **129 个文件 / 2,906 行**；前端位置门可被未枚举的 client 标识符绕过；operation budget 的「整改前基线」根本不存在 |

三轮之后的结论不是「文档再修一版」，而是**原范围本身不成立**。Dexter 2026-09-11 接受将本批砍到单一需求。

### 0.1 砍掉了什么

| 原需求 | 处置理由 |
| --- | --- |
| 全量 SQL 归位 `persistence/` | 实为 129 文件 / 2,906 行，是**后端持久化方式的重构**，不是可读性整改。应单独立项、单独评审。 |
| 后端 SQL 位置门 | 范围与迁移不匹配 ⇒ 门永远绿不了；且 129 文件的门等于把整改绑死在一道恒红的门上。 |
| 前端数据模块位置门 | 三轮下来没有一个既完整又不过度捕获的判据：按 client 名枚举会漏（`catalogInventoryClient` 等）；按 `app/api` import 判又过度捕获（31 个文件中多数只引类型）。 |
| 强制各模块补 `domain/` | `application/` 94 个文件中 80 个 import Spring、49 个带 `@Transactional`，迁移必须先剥离耦合 —— 改变执行边界的架构重构。 |
| 后端测试文件切分 | `CatalogAcceptanceScenarios` 有 125 个 helper、83 个被多处调用，`readItem` 被调 116 次；而 scenario 由注解发现、按 id 排序，找它不靠文件位置。 |
| operation budget 三步比对 | 其 verifier 只在全量 acceptance 中执行，且不存在「整改前基线」这个产物。 |

### 0.2 砍掉之后消失的问题

Codex 那轮的三条 M **全部是关于「门」的**：门的范围对不上、门可被绕过、门的基线不存在。**本批没有新门，三条同时消失。**

## 3. 需求 · 按职责拆分五个 God class

### 3.1 判据

**一个类只能有一个事务入口族。**

拆分依据是**聚合**，不是行数：`CatalogOwnerService` 的 74 个 public 方法覆盖 item、category、sku、attribute、option、bom、inventory 协同等多个聚合，这才是拆它的理由。

⚠️ `CatalogInventoryCoordinator` 的跨 owner 协调落在后端规范 2-C（网络 I/O 不得在 `@Transactional` 内）的敏感区，拆分须同时复核该条。

### 3.2 SQL 的去向（拆分的副产品，不是独立需求）

这五个文件里的 977 行 SQL，随其所属聚合迁入该聚合的持久化类，目录段命名为 `persistence`。

⛔ **不扩展到这五个文件之外。** 其余 124 个含 SQL 的文件本批不动。

### 3.3 行为钉住前置（Dexter 裁决庚）

拆类改变执行边界，**必须先证明行为被测试钉住**。

判据：每个将被移动的 public 方法族，存在覆盖正向与至少一条负向路径的现存测试；缺口在动结构**之前**补齐并跑绿。

⚠️ 本前置适用于全部五个文件，不只 `CatalogOwnerService`。

### 3.4 不这样做的代价

打开 `CatalogOwnerService` 无法知道它负责什么；任何一处业务变更都要在 74 个 public 方法里定位；多个聚合的事务边界混在同一个类里，无法从结构上判断一次提交会碰到什么。

### 3.5 验收判据（可证伪）

1. **拆分前**已完成 §3.3 的行为钉住，为补缺口新增的测试先行跑绿；
2. 每个产物类的 `@Transactional` 公开入口只覆盖**一个聚合**（review 判定）；
3. 拆分前后 owner 行为测试**逐条不变且全绿**；
4. **不改变任何 operation 的对外契约与错误码**；
5. 拆分后跑一次全量 backend acceptance，`assertPerformanceOperationBudgets` 与 `requireClosedPerformanceCount` 全绿。

⚠️ 判据 5 只要求该次 run 自身全绿，**不要求与任何「整改前基线」比对** —— 该基线产物不存在。

## 4. 规范落地

后端规范新增 **1 条**：单一事务入口族。

⛔ **该条标 `R` 档，不得做成门。**「一个聚合」在仓内没有机器可读的声明源，做成正则就是假门。

目录词表（`api` / `application` / `domain` / `persistence`）写入规范作为**命名约定**，同样是 `R` 档：有这类内容才建、必须叫这个名字，⛔ **不接门**。

⚠️ 前端规范**不新增条目**。本批不涉及前端。

---

## 5. ⚠️ 本批的防线只有 review —— 显式声明

Dexter 裁决丙要求「改存量 + 防增量」。**本批只做到改存量。**

三轮评审证明：能可靠机器判定的位置规则，要么范围大到变成架构重构（129 个文件），要么判据不完整可被绕过（前端 client 标识符枚举）。

**为「防增量」装一道会漏或会恒红的门，比没有门更糟** —— 它给虚假的安全感，且会在 `scripts/verify` 里长期恒红或长期空转。

⇒ **本批不新增任何门。防线是 review。** 本文不假装它是门。

Dexter 2026-09-11 已接受该削减。

## 6. 明确不做

- 不设行数门，不设任何数值代理门（如「单类事务入口数阈值」—— 它编码的是「不要太大」而非「一个聚合」）。
- 不建违规基线、豁免清单或棘轮。
- 不动这五个文件之外的 SQL（124 个文件）。
- 不动前端。
- 不动测试文件。
- 不动 L2 spec。
- 不引入新抽象层、框架、基类。
- 不做统一格式化、import 排序、命名大扫除。
- 不搬 `generated/` 与 `contracts/` 产物。
