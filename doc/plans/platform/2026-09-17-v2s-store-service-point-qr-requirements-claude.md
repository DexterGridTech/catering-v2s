## 1. 文档定位与真实业务问题

本文是业务需求正本，不是详设、实施计划、代码变更或运行授权。

门店在现场承接顾客时需要两类空间资源：**桌台**（顾客落座、后续承载桌台服务）与**扫码点**（无需落座的自助下单入口）。当前 v2s **完全没有这类资源的任何模型**——后端 18 个模块中没有对应域，契约与迁移中也不存在区域、服务点、桌台语义的实体（`ServicePoint`、`DiningTable`、`TableArea`、`seat_capacity`、`qr_code` 等命名均无命中）。唯一形似的 `Zone` 出现在 `contracts/catalog/catalog-inventory-read-models.json` 的 `sixInventoryDetailZones` 与 `detailZone`，指的是库存详情的**读区**，与物理空间无关。门店因此无法维护自己的桌台与扫码点，也就无法生成扫码点单的二维码。

本需求建设这块的**后台配置层**：区域、服务点、二维码配置项三个实体，以及它们在运营管理后台的维护页面。不建设运行时（桌台会话、扫码会话、取餐任务）。

### 1.1 与已建成能力的关系

- 页面进入受门店经营规则开关约束，复用上一批建成的开关机制与未开通空态形态。
- 二维码指向的渠道来自已建成的经营渠道域，本需求只新增模板的一个属性，不改渠道模型。
- 服务点的纯展示描述字段接入已建成的扩展字段机制，不新造第二套自定义字段能力。
- 桌台图片走已建成的资产链路，不新建存储机制；扫码点不提供图片字段或图片上传功能。

## 2. 业务目标与成功结果

1. 有权限的人能在运营管理后台维护某门店的区域与服务点。
2. 区域与服务点的类型级联成立：桌台区下只能有桌台，扫码区下只能有非桌台。
3. 桌台可维护容纳人数、形态、是否可预约与图片；纯展示性的描述由扩展字段承载，可在运维管理后台按集团空间定义。
4. 门店可配置是否开启二维码下单，并指定一个「内部接入 + 到店点餐 + 扫码」类型的门店渠道。
5. 开启后，服务点列表与详情可查看二维码；**二维码 URL 不被存储**，由渠道模板的 URL 规则追加参数派生。
6. 页面访问与编辑受角色权限与门店经营规则开关双重约束，且后端不可绕过。

成功结果必须由 owner readback、HTTP contract、focused test 或后续受管验收证明；本文件的静态要求不构成运行通过。

### 2.1 方案取舍与已否决的替代

**本批唯一有真实消费者的是二维码。** 桌台的容纳人数、形态、是否可预约在本批**没有任何代码读取**——预约、桌台会话、并桌都不在范围。这与上一批「定义 12 个开关但只实现 1 个消费者」是同一形态，处理方式也相同：**定义它们，但不为它们编写业务判定**。这一点必须诚实记录，避免详设为无消费者的属性编造校验规则。

已比较并否决的替代方案：

| 替代 | 描述 | 否决理由 |
| --- | --- | --- |
| 去掉区域，服务点直接挂门店 | 区域只有名称、编码、类型、顺序四项，其类型唯一作用是约束服务点类型。去掉后服务点自带类型，级联约束随之消失，模型少一个实体 | **这是技术上更小的方案**，但被否决：Dexter 明确要求三个实体；v4 与 v6 两代都有独立区域；且分组展示、排序与将来的区域码都需要落点。**此处记录清楚：区域的存在是用户明确要求与业务惯例，不是技术必需** |
| 二维码配置并入门店经营规则 JSON | 少一个实体 | 见 R-6.3：会把上级授权与门店自配置混成一个住址 |
| 为 URL 规则新建 provider config 层 | 对齐 v6 的 owner 归属 | v2s 无该实体，为一个字符串新建一层是过度设计，见 §6.2 |

**被上一批逼出来的额外成本**：R-5.9 要求把既有 gate 与 token 标志泛化为按开关键判定。这不是本需求的业务需要，而是上一批把 gate 硬编码成商品管理开关留下的欠账。本批必须付这笔成本，但应记为机制补齐而非新功能。

## 3. 范围盘点

### 3.1 三个实体

| 实体 | 业务含义 | 归属 | 本期消费 |
| --- | --- | --- | --- |
| 区域 | 门店内的空间分区，是服务点的容器 | 门店 | 是 |
| 服务点 | 顾客在门店内被承接的具体位置 | 区域 | 是 |
| 二维码配置项 | 门店级单例，决定是否开启二维码下单及指向哪个渠道 | 门店 | 是 |

### 3.2 两个类型闭集

| 闭集 | 取值 | 说明 |
| --- | --- | --- |
| 区域类型 | 桌台区、扫码区 | 决定其下可建的服务点类型 |
| 服务点类型 | 桌台、非桌台 | 与所属区域类型一一对应 |

**外部事实**：v4 的 `onsite_dining_area` 与 v6 的 `DiningArea` **都没有类型字段**；区域类型是本需求新增的抽象。

### 3.3 服务点属性的三层切分

判据一句话：**会被代码读来做判断的进独立属性，只给人看的进扩展字段。** 这条规则本身要写进详设，后续新增属性按它归位。

| 层 | 内容 | 适用类型 |
| --- | --- | --- |
| 核心属性 | 所属区域、编码、名称、类型、顺序、状态 | 全部 |
| 需系统判断的独立属性 | 容纳人数、桌台形态、是否可预约、图片 | 仅桌台 |
| 纯展示描述 | 由扩展字段承载，例如最低消费说明、服务费说明、位置说明 | 全部 |

**外部事实**：v4 与 v6 都把最低消费、服务费明确标注为「仅说明，不参与系统约束、计价或下单校验」（v4 的 `dining-table-upsert-request.schema.json` 字段 description 与 v6 §5.4 判断 7 一致）。本需求据此把它们归入扩展字段。

**桌台形态**归入独立属性而非扩展字段，理由是它会影响预约策略与计价说明的适用；若仅作展示，后续代码读不到。取值闭集由详设确定，至少覆盖大厅、包间、卡座、户外。

**外部事实**：v4 的 `serviceTags` schema 写的是 `"items": {}`（无枚举），v6 也只写 `serviceTags[]`，两代都没有把这个集合收敛。本需求要求收敛成闭集。

### 3.4 本期消费面

运营管理后台新增一个页面「门店桌台与二维码管理」，与门店商品管理同属门店级页面。

运维管理后台的扩展字段配置页新增一类宿主，用于定义服务点的扩展字段。

### 3.5 明确不在本次范围

- 桌台会话、扫码会话、开台换桌并桌清台等运行时事实（v4 与 v6 的 `TableVisitSession` / `ScanEntrySession`）。
- 候位排队、取餐任务、叫号通知。
- 服务模型的草稿与发布版本化、空间策略子模型（v4 的 `store_service_model` 与 `spatial_policy`）。
- 区域码、取餐点码（v6 明确不进起步期）。
- 二维码图片的生成、下载与批量导出；本期只做「查看」。
- 服务点列表接入扩展字段的动态列与类型化搜索（2026-09-17 裁决 D-9：本批不接入）。
- 终端消费这些配置。
- 经营规则开关的树形、默认值与键的任何改动；本期只改一处标签，见 §5.3。
- 扩展字段机制本身的改造；本期只新增一类宿主并接入。
- 经营渠道模型的改动；本期只给模板新增一个属性，见 §6.2。

## 4. 实体的业务语义要求

### 4.1 区域

- R-1.1 区域属于门店，含名称、编码、类型、顺序四项业务属性。
- R-1.2 区域类型是 §3.2 的闭集，创建后**在其下已有服务点时不得修改**；要修改须先清空该区域下的服务点。
- R-1.3 区域编码在同一门店的**未作废范围内**唯一；作废后编码可被复用。
- R-1.4 区域采用仓内三态生命周期（启用 / 停用 / 作废），不采用 v6 的「不用就删」。
- R-1.5 区域非启用时，其下所有服务点**一律不可用**，无论服务点自身处于什么状态；判定按祖先链计算，不改写服务点自身的状态值。
- R-1.6 R-1.2 中「其下已有服务点」**只计未作废的服务点**；该区域下全部服务点作废后，区域类型可以修改。
- R-1.7 R-1.2 所说的「清空」是**把未作废服务点转为作废**，**不是物理删除**。作废行保留其原类型与扩展字段值；若为桌台，其图片引用也保留，扫码点不涉及图片。
- R-1.8 区域类型修改后，**已作废的历史服务点不参与当前类型一致性校验**，也不出现在当前分组与列表中；它们保留写入时的原类型，用于审计与历史追溯。
- R-1.9 新建区域的默认状态为**启用**。

R-1.5 的形态与上一批经营规则开关的生效判定同构：**祖先不可用则后代不可用，但后代的存储值保持不变**。这样区域重新启用后，其下服务点原样恢复，不会因为一次停用而丢配置。

R-1.6 的必要性：若已作废的服务点也计入，区域类型将永久锁死，而作废本就是「不再使用」的表达。

R-1.2 的理由：服务点类型按 R-2.2 冗余存储，若允许级联修改区域类型，会让一批服务点的属性含义突然改变。禁止修改是最小且无歧义的做法。

R-1.4 的取舍：**外部事实**——v6 §5.4 判断 7 明确「区域和桌台不维护启用/停用/锁定状态；不再使用时直接删除」，v4 则有含 `LOCKED` 的三态。本需求两者都不照抄，采用 v2s 全仓一致的三态，理由是删除会丢失历史引用。

### 4.2 服务点

- R-2.1 服务点必须属于一个区域；不存在不属于任何区域的服务点。
- R-2.2 服务点**存储自己的类型**，即使它可由区域类型推导。
- R-2.3 owner 必须在写入时校验服务点类型与所属区域类型一致，**不得只靠前端不给选**。该一致性**只约束未作废的服务点**。
- R-2.3a 新建服务点的默认状态为**启用**。
- R-2.4 服务点编码在同一门店的**未作废范围内**唯一（门店内唯一，不是区域内唯一）；作废后编码可被复用。

**仓内事实**：作废后编码可复用是 v2s 的通行惯例，实现形态是带 `WHERE status <> 'VOIDED'` 的部分唯一索引，见 `V20260815_010000_000__catalog_voided_item_code_release.sql`、`V20260816_020000_000__catalog_sku_voided_code_release.sql`、`V20260816_030000_000__catalog_dictionary_tag_voided_code_release.sql` 与 `V20260827_010000_000__base1_three_state_lifecycle.sql` 第 386 至 407 行。R-1.3 与 R-2.4 对齐该惯例。**外部事实**：v4 的区域与桌台也是门店内唯一（`unique (group_workspace_id, store_id, area_code)` 与 `unique (group_workspace_id, store_id, table_code)`），但 v4 没有作废态，因此不照搬其无条件唯一。
- R-2.5 类型为桌台时可维护 §3.3 第二层的独立属性；类型为非桌台时这些属性不适用，不得要求填写，也不得展示为空值占位。
- R-2.6 服务点采用与区域一致的三态生命周期。
- R-2.7 服务点**不存储二维码 URL**，也不存储任何码实体引用。
- R-2.8 服务点自身非启用、或其所属区域非启用时，**不展示二维码**。已印制物料在现场被扫描后的行为属于运行时，不在本期范围。
- R-2.9 服务点的状态变化**不删除**其扩展字段值；桌台的图片引用也不删除，重新启用后原样可见。扫码点不涉及图片。

R-2.2 是 2026-09-17 裁决：冗余存储换取「直接按类型判断、免级联查询」。R-2.3 是这个反规范化的必要代价，两者必须同时成立。

R-2.7 的依据：**外部事实**——v4 在 V051 迁移中删除了三张扫码实体表并从桌台上删掉了码引用，注释原文是「码不再绑定经营入口或服务流程。桌台码由 DiningTable + URL 模板即时派生」；v6 §5.4 判断 6 同义。两代都收敛到同一结论。

### 4.3 桌台图片

- R-3.1 桌台类型的服务点支持上传图片。
- R-3.2 桌台图片走既有资产链路（暂存、释放、保存时认领），不新建存储机制、不新建资产表；扫码点不进入这条图片流程。
- R-3.3 保存失败不得产生孤儿资产。

**外部事实**：v4 与 v6 的桌台都没有图片，这是本需求新增的。

### 4.4 是否可预约

- R-4.1 服务点的「是否可预约」是桌台自身属性。
- R-4.2 它与门店经营规则开关中的预约开关**不联动、不互相校验**。实现时不得自作主张建立联动。

R-4.2 是 2026-09-17 裁决的原话要求。

## 5. 授权与操作面要求

### 5.1 页面与权限

- R-5.1 运营管理后台新增一个菜单与页面，承载区域、服务点与二维码配置项。
- R-5.2 该页面的可访问角色与门店商品管理、门店库存管理**一致**。
- R-5.3 新增一个编辑权限；持有该权限者可编辑，未持有者只读。
- R-5.4 页面是门店级页面，门店由既有的全局数据节点选择器选定。

**仓内事实**：三个门店页在 `contracts/catalog/admin-catalog.json` 中的可授予角色是 `GROUP / REGION / PROJECT / STORE`，`requiredDataNodeType` 为 `STORE`，导航组为 `NAV-CATALOG-SERVICES`，对应编辑能力的 `scopeApplicability` 为 `SELECTED_STORE_SCOPE`。新页面与新编辑能力按同一形态注册。

- R-5.5 门店层角色与项目层角色都必须能正常使用该页面，两个方向各自验证。

R-5.5 是上一批的教训：规则读取一度分别在两个方向上把一类角色挡在外面。

### 5.2 经营规则开关约束

- R-5.6 与门店商品管理一样，只有门店开启了对应开关，才能查看或编辑本页面的内容。
- R-5.7 开关为关闭时，页面显示未开启文案且**不发起列表请求**；**后端所有会改变该门店区域、服务点、二维码配置的写入口必须拒绝**。
- R-5.8 关闭开关**不删除任何已有数据**；重新开启后原有区域、服务点与二维码配置原样可见。

**仓内事实**：开关 `tableManagementEnabled` 已存在（`contracts/catalog/store-operating-rule-switches.json` 第 13 行），父键 `catalogManagementEnabled`，默认 `false`。

- R-5.9 本需求新增的写入口自成 gate 分母，**不并入上一批 catalog / inventory / sales-menu 的 52 条分母**；详设必须为本域交付同样形态的完整映射，不得抽样。

**仓内事实与连带要求**：既有的 owner gate 公共 API 是 `StoreOperatingRuleGate.requireCatalogManagementForStoreTarget(...)`，方法名与语义**硬编码为商品管理开关**；中央 token 的标志 `storeOperatingRuleGateRequired` 也是一个不带开关标识的布尔。本需求需要按 `tableManagementEnabled` 判定，因此详设必须**把 gate 与 token 标志泛化为按开关键判定**，不得复制一份桌台专用实现。这是共用机制，应一次做对。

### 5.3 开关标签修改

- R-5.10 把 `tableManagementEnabled` 的**标签**改为「是否启用桌台和二维码管理」。
- R-5.11 **键不变**。键是稳定技术标识，已有数据不可改。
- R-5.12 不改变该开关的父子关系、默认值与子开关归属。

R-5.10 是 2026-09-17 裁决，用于解决「只做扫码点餐、不用桌台的门店进不了本页面」的语义错配。

**连带事实**（不需处理，仅记录）：键名与标签自此不完全对应，这符合仓内「键是技术标识、不是用户文案」的既有口径；历史审计行保存的是当时的标签快照，改名不回改历史记录。

### 5.4 UI 与交互的强制自问

仓内规范要求任何 UI 承载的需求逐项回答以下问题，本节在需求层回答一次，细节仍交详设与交互设计。

**该操作是否来自用户明确要求**：是。新增菜单与页面、编辑权限、三类对象共页、二维码查看位置（列表后与详情抽屉），均为 Dexter 2026-09-17 明确指定。

**用户在此时这样操作是否合逻辑**：合逻辑。维护桌台与扫码点的人，与配置二维码下单的人是同一批门店运营者；三类对象共页避免了「配完桌台再去另一个页面开二维码」的跨页往返。

**有没有更短、更自然、更少选择的路径**：有一处值得详设权衡——**区域与服务点是否必须分两步创建**。按 R-2.1 服务点必须先有区域，若门店只有一个大厅，仍要先建区域再建服务点。更短的路径是建首个服务点时允许内联创建区域。本稿不强制，列为交互设计的取舍项。

**不合理之处来自哪里**：一处。二维码的可用性依赖「门店已开通一个内部接入、到店点餐、扫码类型的渠道」，而渠道在另一个页面维护。这不是本需求造成的，而是渠道域的既有边界；R-6.6 要求候选为空时明确指向渠道页去开通，就是对这条边界的交互补偿。

**是否有更少选择的做法**：二维码配置只有一个开关加一个渠道选择，已是最少。渠道候选按 R-6.4b 走 bounded owner read，**带固定的来源上限**；上限值与超限时的呈现由详设确定。满足 R-6.4 四维谓词的门店渠道通常只有个位数，因此这个上限在可预见范围内不会成为体验问题，但详设不得假装它不存在。

## 6. 二维码要求

### 6.1 二维码配置项

- R-6.1 二维码配置项是**门店级单例**，不是集合。
- R-6.2 它含两项事实：是否开启二维码下单、指向哪一个门店渠道。
- R-6.2a 初始状态为**未开启且未选渠道**。**允许**保存「未开启」而渠道为空；**不允许**保存「已开启」而渠道为空——开启即必须选定一个满足 R-6.5 的渠道。
- R-6.3 它**独立存储**，不得并入门店经营规则开关的 JSON。

R-6.3 的理由：经营规则开关是上级组织对门店的授权，二维码配置是门店自己的功能配置；上一批已把这两件事分清，不应重新混成一个住址。

- R-6.4 可选渠道的判据：属于**当前门店**的渠道实例中，其模板同时满足接入方式为内部接入、经营主体为门店、下单场景为到店点餐、堂食形态为扫码的那些。四个维度缺一不可。
- R-6.4a 该候选读取必须由 **owner 在服务端完整落实**上述谓词，**不得由前端过滤**，也不得靠「取回全部再筛」。
- R-6.4b 本需求需要一条**二维码专用的 owner 读取**：或新增独立 operation，或在既有门店渠道读取上新增一个用途维度。**不得改变既有两个用途的语义**。该读取沿用既有 bounded read 形态即可，不需要游标分页。
- R-6.4c 保存二维码配置时，owner 必须对提交的渠道**重新校验**门店归属、上述四个模板维度与当前状态；前端传什么都不能绕过。

**仓内事实（本轮更正）**：既有 `getOperationsStoreBusinessChannels` **无法承载**本需求的候选读取，三点原因——控制器 `OperationsBusinessChannelController` 的 `storeChannels` 对 `BUSINESS_CHANNEL` 用途**显式拒绝 `cursor` 与 `pageSize`**，只有 `SALES_MENU` 用途走游标；`BusinessChannelService.pageChannels` 第 157 至 177 行是 bounded read，`nextCursor` 恒为 `null`，且**不做任何模板属性过滤**；销售菜单候选的谓词只有内部接入、门店经营主体、到店点餐或外卖，**没有堂食形态条件**。此外 `dineInForm` 虽然**已在读取投影与结果映射中**（例如 `BusinessChannelQuerySupportSql` 第 15 行的 `t.dine_in_form AS template_dine_in_form`、`BusinessChannelPersistence` 第 345 行的结果集读取），但**没有任何 SQL 谓词过滤它**。这反而降低了实现成本：字段已经在读模型里，新增堂食形态谓词不需要改 join。

**仓内事实（本轮更正）**：渠道分类闭集为 `accessKind ∈ {INTERNAL, EXTERNAL}`、`operatorKind ∈ {PROJECT, STORE}`、`orderKind ∈ {DINE_IN, TAKEAWAY, GROUP_BUY}`、`dineInForm ∈ {POS, QR, KIOSK, null}`；门店层渠道实例在 `business_channel.business_channel` 表中以 `target_node_type='STORE'` 表达。**渠道与模板自身的状态闭集都是 `ENABLED / DISABLED / VOIDED`**；`stop_reasons` 列已由 `V20260827_010000_001__base1_business_channel_derived_facts.sql` 删除，契约中零命中，**不得重新引入**。渠道视图另有独立维度 `bindingStatus ∈ {NOT_REQUIRED, UNBOUND, BOUND}`，以及派生的 `statusDimensions` 与 `blockers` 两个列表——**后两者按 D-12 在本需求中完全不消费**，此处列出只为说明「存在但不用」，不是实现输入。

**候选层与生成层是两个不同的谓词范围，必须分开冻结**，否则详设会把它们混成一条，从而在两个相反方向上都可能出错。

**候选层**（决定哪些渠道可被选中）：

- R-6.5 只允许选择**渠道自身状态为启用、且其模板状态为启用**的渠道。
- R-6.5a **内部接入渠道的绑定维度为「不需要绑定」，不构成阻塞**，不得因为未绑定而把它排除在候选之外。
- R-6.5b 候选层**只用** R-6.4 的四个模板维度加 R-6.5 的两个状态，**不得隐式引入 owner 返回的其他状态维度做过滤**，也不含 URL 规则是否为空（见 R-6.9c）。
- R-6.6 候选为空时必须说清原因并指向门店渠道页去开通，**不得只显示一个空下拉**。

**生成层**（决定已选渠道的二维码生不生成）：

- R-6.7 二维码能否生成，**只看最终拼出来的 URL 是否合规**，与渠道、模板、门店、经营租户、品牌等**任何状态都无关**。
- R-6.7a 已选渠道后来被停用或作废，**不影响二维码继续生成**，也不清空配置。
- R-6.7b 页面上只有三种不出二维码的情形：未开启二维码下单、未选渠道、URL 不合规。前两种是配置态，各用固定的配置文案；第三种按 D-10 显示「暂未生成二维码」。**不得引入任何以状态为由的第四种情形。**

以上是 2026-09-17 裁决，原话：「二维码能不能生成，只看最终拼出来的 URL 是否合规。跟所有状态都无关。」

**这条裁决同时收掉了一处过度设计**：Codex 第 2 轮的 S-01 与我给出的修法，都在讨论「哪些阻塞维度应当停止二维码」，并为此准备了一张两层矩阵。裁决把生成层收成**单一谓词**，矩阵不再需要。owner 返回的阻塞维度集合**在本需求中完全不消费**——既不用于候选过滤（R-6.5b），也不用于生成判定。详设不得以「更严谨」为由把它重新引回来。

**候选层仍按状态过滤（R-6.5），与生成层口径不同，这不是矛盾**：选择是一次配置动作，不应让人新选一个已停用的渠道；而已经选定的配置不因状态变化而失效，与 R-5.8「关闭开关不销毁数据」同向。**这是本稿对裁决范围的理解**——裁决原话针对的是「能不能生成」；若你的意思是连候选层的状态过滤也一并去掉，一句话即可，R-6.5 随之删掉状态条件。


### 6.2 渠道模板的 URL 规则属性

- R-6.8 渠道模板新增一个 URL 规则属性，类型为字符串。
- R-6.9 该属性**只对**接入方式为内部接入、下单场景为到店点餐、堂食形态为扫码的模板有意义；其他模板必须为空，由 owner 校验。

R-6.9 是必要约束，否则它会成为一个谁都能填、谁都不读的自由字段。

- R-6.9b 目标类型模板的 URL 规则**允许为空**，模板可以正常保存。
- R-6.9c 合法性**不在候选层判，也不在配置保存层判**：URL 规则为空或不合法的渠道**照常进入候选、照常可以被选中、二维码配置照常可以保存**。
- R-6.9d 判定发生在**每个服务点生成二维码时**：对该服务点按 R-6.10 至 R-6.12 拼接出的 URL 做合法性判定，**不合法就不生成**，显示固定文案「暂未生成二维码」。
- R-6.9e 合法性判定必须与 R-6.12 的拼接规则在**同一住址**，不得前后端各判一次，也不得判定与拼接用两套规则。

以上四条是 2026-09-17 裁决，原话：「允许为空。但是每个服务点二维码需要判断 URL 是否合法，不合法就不生成。显示『暂未生成二维码』」。

**已知后果**（不需处理，但详设与交互不得自作主张消除）：门店运营者可以选中一个 URL 规则为空的渠道，此后该门店所有服务点的二维码都显示「暂未生成二维码」，而这句文案**不解释原因**；而 URL 规则挂在渠道模板上、属项目级，门店层的人未必有权限去补。这是裁决明确选择的形态——**不得**因此在候选层预先过滤掉这类渠道，也**不得**自行添加解释性提示；若将来需要更具体的提示，由 Dexter 另行裁决。

- R-6.9a 该属性属于**经营渠道域**，由渠道模板既有的编辑权限与流程维护，**不受门店经营规则开关约束**，也不进入 R-5.7 与 R-5.9 的本域 gate 分母。

R-6.9a 必须明说，否则详设可能给渠道模板的写入口误加门店开关校验——而模板是项目级事实，与某一家门店开没开桌台无关。

**已知代价与取舍**：**外部事实**——v6 §8.1 把 URL 模板判给 `BusinessChannelProviderConfig`。但 **v2s 没有这个实体**（provider 相关只在 collaboration 域做启用登记），为放一个字符串新建一层属于过度设计，因此本需求把它放在模板上。代价是同一模板下所有项目与门店共用一条 URL 规则；若将来需要按项目差异化，届时再下沉，本期不预留。

**仓内事实**：模板的更新请求当前只允许改名称、版本号与门店可见范围，新增该属性要同时动创建与更新两个请求。

### 6.3 二维码 URL 的派生

- R-6.10 二维码 URL 由渠道模板的 URL 规则**追加查询参数**得到，不采用占位符替换。
- R-6.11 追加两个参数：集团空间编码与服务点标识。参数名固定在契约中。
- R-6.12 拼接必须正确处理以下全部形态：模板 URL **本身已带查询串**；带**片段标识**（`#` 之后的部分，参数须落在片段之前）；以 `?` 或 `&` **结尾**；模板中**已存在同名参数**；参数值需要**百分号编码**。模板 URL 为空或本身不是合法地址时，**不拼出坏地址，也不抛错给用户**，而是按 R-6.9d 判定为不合法、不生成二维码。
- R-6.13 拼接规则**只有一个住址**；同一规则不得在前后端各实现一次。

R-6.10 与 R-6.11 是 2026-09-17 裁决。R-6.12 是最容易被写死成固定连接符的地方。R-6.13 是上一批的教训：同一闭集散落多处必然两端漂移。

- R-6.14 二维码**只在开启二维码下单后**出现在服务点列表与详情中。开启后若按 R-6.9d 判定为不合法，**位置仍然保留**并显示「暂未生成二维码」，不是把二维码入口整个隐藏——否则用户无法区分「没开启」与「开启了但生成不出来」。

## 7. 扩展字段宿主要求

- R-7.1 服务点成为扩展字段的一类宿主，其纯展示描述字段在**运维管理后台**定义，与项目、门店、合同同一形态。
- R-7.2 服务点**本批不需要**进入平面宿主集合。
- R-7.3 服务点的扩展字段值变更纳入审计，与既有四类实体**同一表示**（四态、标签快照、超长截断）。

**仓内事实**：宿主闭集当前 8 类（`contracts/openapi/components/extension/extension.schemas.json` 的 `ExtensionEntityType`）。`ExtensionHostTypes.java` 第 17 行的 `FLAT_VALUES` 当前含 5 类，但它**不控制能否存值**——全仓仅两处引用，唯一使用点是 `ExtensionDefinitionService.java` 第 760 至 765 行的 `normalizedFlag`，用于规范化 `listDisplay` 与 `searchable` 两个标志（平面宿主给真假、树宿主给 null，即「不适用」）。

因此 R-7.2 成立：既然 D-9 裁定本批不接入动态列与类型化搜索，服务点就不需要这两个标志，也就不需要进入 `FLAT_VALUES`。**将来若反转 D-9，再把服务点加入该集合。**能存值的前提是服务点自身具备扩展值列并接好 owner 读写，即 R-7.1 与 §9 第 7 项，与该集合无关。

- R-7.4 扩展字段定义的粒度是**集团空间级一套**，管该集团空间下所有门店的所有服务点，不按门店差异化。

**仓内事实**：扩展字段定义表主键为 `(group_workspace_key, entity_type)`。R-7.4 是 2026-09-17 裁决对该既有粒度的接受，不是新增能力。

**已知限制**（由 R-7.4 的粒度直接推出，不需处理，但详设与交互不得假装不存在）：扩展字段按**宿主类型**定义，不区分服务点的桌台与非桌台类型。因此为桌台定义的展示字段也会出现在扫码点的表单上。若这成为体验问题，只能靠字段命名与排序缓解，或将来把服务点拆成两类宿主——后者不在本期。

| # | 判据 | 反例构造 |
| --- | --- | --- |
| V-1 | 开关关闭的门店，页面显示未开启文案且不发列表请求 | 正向对照必须用**固定的非空夹具**：开关开启时同一页面必须出现预期的区域与服务点行；只证明「开启后不报错」或列表恒空也算通过，即无效 |
| V-2 | 开关关闭时，**本域全部写入口被后端拒绝**，覆盖率对照详设交付的完整映射 | 绕过前端直接调用写接口必须失败；抽样覆盖不算通过；只证明前端空态不算通过 |
| V-3 | 关闭开关不改变任何已有数据，重新开启后原样可见 | 关闭前后对比区域、服务点、二维码配置的行数与内容必须一致 |
| V-4 | 类型级联成立 | 负向：「桌台区下建非桌台服务点」与「扫码区下建桌台服务点」两个请求，owner 必须各自拒绝；只证明前端不给选不算通过。**正向对照**：两种合法组合必须各自成功——缺这一半，一个「永远拒绝」的实现也能通过 |
| V-5 | 区域类型在其下有服务点时不可修改 | 正向对照：清空服务点后必须可以修改 |
| V-6 | 服务点不存储二维码 URL，且 URL 真的是派生的 | 结构判据：持久化结构不含该字段。**行为判据（更强，必须做）**：修改渠道模板的 URL 规则后，已有服务点的二维码**立即随之改变**；只证明结构里没有字段，无法排除「读取时快照一次」的假实现 |
| V-7 | URL 追加参数正确 | R-6.12 列出的**五种合法形态各验证一次**：不带查询串、已带查询串、带片段标识、以 `?` 或 `&` 结尾、已存在同名参数，外加值需百分号编码一例。**另有两条不合法输入**：URL 规则为空、URL 规则非法——两者都必须走 R-6.9d，即不生成且显示「暂未生成二维码」，**不得抛错、不得拼出坏地址** |
| V-8 | URL 规则属性在非目标类型模板上必须为空 | **四个维度逐项验证**：分别构造只在接入方式、经营主体、下单场景、堂食形态上不满足的模板各一个，填写该属性都必须被拒；再构造完全满足的模板，填写必须成功。只用一个外卖类负例无法证明四维各自生效 |
| V-9 | **只有三种情形不出二维码**：未开启、未选渠道、URL 不合规；渠道状态变化**不在其中** | 三种各验证一次，原因彼此可区分；URL 那种按 D-10 固定显示「暂未生成二维码」，且该渠道**仍在候选中**、配置**仍可保存**。**关键反例**：把已选渠道先置为停用、再置为作废，两次二维码都必须**仍然正常生成**——只要停止生成即为失败，说明实现偷偷引入了状态判据；且配置**未被清空** |
| V-10 | 新编辑权限的可授予角色与三个门店页一致 | **四类角色逐项验证**：集团、大区、项目、门店各自验证一次可用性；只验证其中两类不算通过 |
| V-11 | 服务点扩展字段可在运维后台定义、在服务点上存取，且变更进审计 | 审计表示与既有四类实体一致：四态、标签快照、超长截断各验证一次 |
| V-12 | 桌台图片走既有资产链路，扫码点不提供图片能力 | 负向：桌台保存失败时不留下孤儿资产。**正向对照**：桌台保存成功时资产被正确认领并可读回；扫码点表单与请求均不得出现图片入口或图片字段——缺任一半，一个「永远不认领」或误给扫码点加入口的实现也能通过 |
| V-13 | 区域非启用时其下服务点一律不可用，**无论服务点自身处于什么状态**，且服务点自身的存储值不被改写 | 区域的**停用与作废各验证一次**；每种再覆盖服务点自身的**启用、停用、作废三种状态**——缺作废这一格就无法独立证伪 R-1.5 的「无论服务点自身处于什么状态」；再构造「停用区域 → 不可用 → 重新启用 → 原样恢复」，恢复后配置丢失即为失败 |
