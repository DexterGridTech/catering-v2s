## 1. 双方一致的结论（A 类，已收敛）

这些两份独立得出同一结论，可信度最高，后续讨论不必重开：

1. **本期是交易前的基础，不是菜单系统，也不是小型 ERP。** 交付商品目录、门店轻库存、商品处理标签定义三块。
2. **卖的不是商品。** 商品只回答"是什么"；上架、可售、沽清、最终价都不在本域。
3. **三个 owner 分立**：商品目录、轻库存、商品处理标签各自持有事实；页面可以组合，真相不合并。
4. **商品形态持久化并进契约**，由契约统一约束前后端的能力、页签、字段与结构互斥。
5. **门店从总公司显式 pull 复制**，复制后本地独立，不强继承、不自动跟随、不字段锁死。
   （**注**：总公司持有的不是"模板"，而是真实的商品、库存对象与 BOM 实体，只是没有余额与流水；见 §5.6.1。）
6. **一次保存、两个 owner**：用户只按一个保存按钮；服务端同一事务内分别调用两个 owner 的命令并各自 CAS，整体成败。禁止前端串两个保存请求，禁止 catalog 直接写 inventory schema。
7. **库存：流水是事实、余额是可重建的当前态**；先写流水再更新余额；无"系统重算"这一流水来源。
8. **库存提示不是可售**；低库存不自动下架。
9. **选项值不能成为独立库存对象**，只能作为 BOM owner。
10. **按 SKU 管理商品的主商品壳不能配库存或 BOM**。
11. **本期不建扣减/恢复的执行逻辑**（表按模型完整原则建，见 §5.5.2 重判四）；
    不建外部 ERP/权益权威适配；不建供应链全家；不触发 TDP。
12. **归档不物删**，被引用对象只能停用或归档。
13. **v1 的微服务/MQ 表达不继承**，只继承 owner、幂等、不可变事实等业务语义。
14. **v4 页面的保留项**：形态驱动页签、SKU 维度到即时矩阵、左树右详情加检查面板三栏范式、库存对象详情的关联商品反查、六分类库存现状、dirty 关闭守卫。
15. **v4 不搬项**（按业务边界给理由，**不再用「有无消费者」作裁剪依据**）：
    Excel 批量导入导出（本期未证明该用户任务）；菜单与渠道摘要（06 不在本期，展示会造出不存在的事实）；
    外部 ERP 与权益权威适配（已裁定本期只做内部轻库存）；扣减/恢复的执行逻辑（本期是交易前范围）；
    图表面仅保留能由真实流水解释的库存变化。

## 3. 结论冲突的裁定（C 类，附证据）

### 3.1 `SalesStockView` 建不建表 —— **不建，采 Claude/v1**

**冲突**：Codex §6.3 把 `SalesStockView` 列为轻库存 owner 的实体。

**决定性证据**（v1 step4 essence `:41`，Dexter 已拍板的模型骨架）：

> inventory 5 表（交易前）：stock_target / stock_balance / stock_change_ledger / product_bom / product_bom_line。
> interface-reserved：StockDeductionPlan/RestorePlan（不建执行）。
> **hint = balance 派生读（砍 v4 SalesStockView 断链表）。**

**裁定**：库存提示是**余额的派生读**，不建独立表。理由不只是省一张表——
v4 的病正是"建了 `SalesStockView` 表却零消费者"，派生读天然不会产生这种断链。

**保留 Codex 的正确部分**：hint 的**产出边界**要建模（谁能读、读到什么形状），只是它的实现是查询而非表。

### 3.2 跨 schema 读的边界 —— **双方各对一半，合并表述**

**冲突**：Codex §11.5 主张"显式任务型读可跨 schema join"；我原稿主张 BOM 组件能力校验必须走 catalog 公开 API。

**核实 kernel 原文**：

```
TASK_READ_JOIN         跨 schema 读取只用于显式任务型 join
OWNER_RECHECKS_COMMAND owner 在命令事务内复核授权、状态和当前事实
```

**裁定：按读写路径分开表述，两条都成立。**

- **读路径**（列表、详情、编辑视图组装）：**允许显式声明的任务型跨 schema join**，
  避免进程内 API 逐条调用造成 N+1。Codex 对，我原稿过严。
  但必须在 `module-dependency-registry` **主动声明**，不得等门报红再补。
- **写路径的跨 owner 事实校验**（inventory 写 BOM 行时校验组件商品具备 `BOM_COMPONENT`）：
  **必须走 catalog 的公开 typed 判断**。理由不是"不许 join"，而是
  **能力语义的解释权属于 catalog**——inventory 自己 join 表并解释 catalog 的能力字段，
  等于把 catalog 的业务规则复制到 inventory，是第二份真相。

一句话：**join 只能取事实，不能替 owner 做判断。**

### 3.3 选项值的库存模式 —— **只能 BOM，采 Codex**

**冲突**：v1 A12 记「可配节点含 `OPTION_VALUE`」并列出三态模式，读起来像选项值也能配独立库存；
Codex 主张选项值只允许 BOM。

**决定性证据**（我从 v4 generated 契约 `catalog-item-editor-manifest.ts` 解析出的 `modeRules` 全量）：

```
CATALOG_ITEM  condition=HAS_SKU   allowedModes = [NONE]
CATALOG_ITEM  condition=NO_SKU    allowedModes = [NONE, INDEPENDENT_STOCK, BOM]
SKU           condition=None      allowedModes = [NONE, INDEPENDENT_STOCK, BOM]
OPTION_VALUE  condition=None      allowedModes = [NONE, BOM]        ← 无 INDEPENDENT_STOCK
```

与 v6 §4.4 规则 8「`OPTION_VALUE` 不能作为独立库存对象，只能作为 BOM owner 消耗其他可用库存对象」**完全一致**。
v4 实现与 v6 规范交叉验证成立。

**裁定**：采 Codex。并且这四条 `modeRules` 应当**原样成为 v2s 形态契约的一部分**——
它同时精确表达了"按 SKU 管理商品主壳不能配"（`HAS_SKU → [NONE]`），
比用文字描述可靠得多。

### 3.4 `PreparationProfile` 是实体还是折入 JSON —— **折入 JSON，采 Codex**

**冲突**：v1 Q4=A（2026-06-30）原文说「`SalesUnit` / `ProductIdentifier` / `PreparationProfile`
都是实体（不退化为 json）」；但 v1 step4 essence（2026-07-08，**更晚**）的 catalog 10 表清单里
**没有 `PreparationProfile`**，而 `CatalogItem` 的 `displayJson` 明写含「描述/媒体/自由属性/**生产提示 prep**」。

**裁定**：采后出的修正版——生产提示（预估时长、制作说明）折入商品结构 JSON；
**商品处理标签本身是 typed ref，不得降成 JSON 字符串**。

**但我要补一条 Codex 未处理的**：v6 §4.13 的 `PreparationProfile` 可挂
**商品 / SKU / 选项值**三个层级。折入 JSON 后，SKU 级与选项值级的生产提示应各自落在
**对应对象的结构 JSON 内**，而不是全塞进商品的 `displayJson`。这一点需要在契约设计时明确。

## 4. 我对 Codex 开放问题的裁决（Dexter 授权）

### O-01 本期可见商品形态 → **B：模型七种，首期 UI 不开放权益商品壳**

两份一致。权益规则、额度、发放归权益域，本期任何分母都不含它；
开放一个无法闭环的空壳只会产生误导性数据。`itemKind` 枚举位保留，UI 入口不开放。

### O-02 SKU 与点单选项的互斥范围 → **A：仅强 SKU 矩阵互斥**（附风险说明）

v6 有**两处表述不完全一致**，我都读了：

- §4.8：「`skuMode=REQUIRED_MATRIX` 的按 SKU 管理商品与点单选项互斥」——**限定了 mode**；
- §4.9：「**目标态**同一商品不能既作为按 SKU 管理商品，又维护点单选项」——**未限定 mode**，且用了"目标态"。

**裁定 A**，理由是业务的：`OPTIONAL_TABLE` 的语义是"可维护少量简单 SKU"。
真实场景如「牛肉面：大份/小份（简单 SKU）+ 加蛋/加面（选项）」是合理且常见的，
没有业务理由禁止。§4.9 用"目标态"措辞，说明那是一个方向性期望而非当前约束。

**风险与后手**：若将来产品判断认为 `OPTIONAL_TABLE` 也应互斥，收紧比放宽容易
（收紧只需拒绝新数据 + 治理存量），所以先按 A 不会造成不可逆后果。
**这条我标为可复议**——如果你（Dexter）对餐饮实际用法有不同判断，请直接推翻。

### O-03 SKU 商品价格校验 → **B：按 priceGranularity 决定激活校验**

v6 §4.8 明写：`priceGranularity=SKU` 时 SKU 标准价是主要销售标价，
商品级标准价"只做兜底、摘要或导入提示，不作为 SKU 矩阵的主要输入"。

**规则**：草稿态可不完整；**激活时**——`ITEM` 粒度要求商品级价齐，
`SKU` 粒度要求每个启用中的 SKU 有价。不无条件复刻 v4 的"商品级价硬必填"。

### O-04 图片上限 → **主图 1 + 附图 ≤ 5（共 6），且上限可配置**

Codex 建议 9，我原建议 5，此处统一为 **6**。理由：餐饮商品不是电商 SKU，
运营真实会维护的通常是 1–3 张；上限的作用是防止列表与详情被拖慢，不是提供余量。
**关键是上限做成配置项而非硬编码**，将来放宽不需改模型——这一点比具体取值重要。

单张大小上限 ≤2MB（既有资产层硬上限 5MB 不变，本域取更严值）。
本期**不生成缩略图**，但**列表读模型只返回主图**，附图仅在详情返回。

### ~~O-05 商品处理标签的门店覆盖~~ → **问题因作用域裁定而重述**

我原来的裁决理由是「v6 的 `scope` 就是 `PROJECT_DEFAULT | STORE_OVERRIDE`，'覆盖'一词本身就超出'只能新增'」。
**这个理由在 §5.6.2 的门店级裁定之后已经失效**——`scope` 那组取值取消了，
门店与总公司之间**不是"覆盖"关系，而是"复制后各自拥有"**。

**重述后的结论**：门店持有的是**自己的标签定义**（自建或从总公司复制而来），
因此门店对它有完整权限：可新增、可改展示名、可停用。**不存在"覆盖总公司定义"这种关系**，
总公司的定义在复制那一刻就与门店的脱钩了，与商品、库存对象完全同构。

**保留 Codex 的一条约束并重新表述**：复制过来的标签**沿用总公司的 `tagCode` 作为去重 key**
（这正是 §5.6.3 按编码去重所依赖的），门店可以改展示名但**不应改编码**——
改了编码会让下次复制误判为不存在而重复复制。

### O-06 允许负库存后是否仍提示 → **A：仍归"需处理"，提示但不阻断**

写入策略与余额健康是两回事。`allowNegative` 表达的是"不阻断业务继续做"，
不是"负库存正常"。店长仍需要知道哪些对象已经欠账。

### O-07 本期的"消耗趋势" → **改造，而非二选一**

Codex 给的是"显示空/零"与"隐藏"二选一，**我认为两个都不是最好的**。

拆开看：v4 那一栏叫"消耗"，指的是**销售扣减**。本期没有订单，销售消耗恒为 0，
显示它确实是伪指标——这一点 Codex 对。

但**库存本期真的会变化**：盘点覆盖、库存增加、人工调整都产生流水。
店长很需要知道"这个料最近动过没有、动了多少"。把整块隐藏会丢掉真实且有用的信息。

**裁定方向**：本期这一区块**改名为"库存变化"，展示真实的流水聚合**，

### 5.2 形态契约要携带的内容（在 §1 第 4 条基础上具体化）

形态契约（`contracts/catalog/` 层，生成 Java 与 TS 两侧，走字节比对与 count 断言）至少包含：

  （**后端按形态推导，不接受前端传入派生值**）；
- 形态 → 页签集；
- 形态 → 字段可见性与必填（含 O-03 的价格激活规则）；
- **形态 → 库存/BOM 可配节点与允许模式**，即 §3.3 那四条 `modeRules`；
- 形态的固定性：创建后不可改、配了下游事实即锁。

#### 能力（capability）的编辑性 —— 照搬 v4（Dexter 2026-08-06 裁定）

Codex 的 M-04 担心"精确派生会封死物料零售、半成品生产等合法组合"。
**我去 v4 generated 契约里核了字段规则，这个担心有一半不成立**：

```
shapeKey            control=radio            readonlyWhen=[edit, view, referenced]  requiredWhen=[create]
itemKind            control=readonlySummary  readonlyWhen=[create, edit, view]
measureMode         control=readonlySummary  readonlyWhen=[create, edit, view]
usageCapabilities   control=readonlySummary  readonlyWhen=[create, edit, view]     ← 三态全只读
materialRole        control=select           readonlyWhen=[view]  requiredWhen=[MATERIAL]  ← 可编辑
```

**v4 的答案很干净：`usageCapabilities` 完全只读派生，用户在任何时候都不能增减。**
因此不存在 required／allowed／default／forbidden 四层结构——**这一层在 v4 里不需要**。
唯一可编辑的是 `materialRole`（且仅 MATERIAL 形态必填）；
`shapeKey` 只在创建时可选，编辑、查看、已被引用后一律只读。

**那 Codex 举的三个场景怎么办？**

- **"物料要零售"** → 不该建成「原材料/半成品/包装物」形态，应建成「普通销售商品」。
  **形态就是意图声明**，不是靠事后加能力来改变意图。
- **"普通销售商品要独立管库存或配 BOM"** → **不需要 `STOCK_MANAGED` 能力**。
  这是 `modeRules` 管的：`CATALOG_ITEM` 在 `NO_SKU` 条件下 `allowedModes=[NONE, INDEPENDENT_STOCK, BOM]`。
  **能力与库存模式是两套独立机制**：能力声明"可被哪些下游域引用"，
  `modeRules` 决定"这个节点能配什么库存模式"。
- **`BOM_COMPONENT` 的作用**是"能不能被别人当组件引用"——原材料有，普通销售商品没有。
  这是对的：不会拿一个成品披萨当另一道菜的原料。

**但 Codex 指出的另一半是真问题，必须补**：

1. **`HAS_SKU` 的判据已按 v4 源码定死为「存在任一非归档 SKU」**。
   我上一版倾向「存在启用中的 SKU」是**错的**，去读 v4 源码后更正：

   ```
   catalog-item-inventory-bom-state.ts:241   skus = ...filter(status !== "ARCHIVED")
   catalog-item-inventory-bom-state.ts:335   hasSku = flattenTreeNodes(...).some(nodeType === "SKU")
   ```

   即**先滤掉已归档的 SKU，再看树中还有没有 SKU 节点**——
   **停用（INACTIVE）的 SKU 仍然算数，只有归档的不算**。

   **为什么这个判据更好**（也是必须按 v4 的实质理由）：
   若按"启用中"判断，门店把最后一个 SKU 停用后，主商品会**重新获得独立库存与 BOM 的配置能力**，
   于是可能与那些历史 SKU 遗留的库存对象、BOM 并存——**节点结构会随状态切换而漂移**。
   按"非归档"判断则不会：归档是不可逆的收尾动作，结构只会单向收敛。
2. **`modeRules` 只按节点类型分，不按形态分**，所以服务/费用商品、权益商品壳
   （`skuMode=NONE` → 走 `NO_SKU` 分支）会错误地获得三态库存模式。
   v4 靠"这些形态没有「库存与 BOM」页签"在 UI 层挡住了，
   **但 v4 的 tabs 定义里没有 per-shape 可见性规则**——这一层在 v4 是隐式派生的。
   **v2s 必须把它显式化**：契约里要有「形态 → 允许出现哪些节点类型」这一层，
   位于 `modeRules` 之上。两层关系是：

   ```
   形态  决定  这个节点能否存在
              ↓
   modeRules  决定  已存在的节点允许哪种模式
   ```

   **因此 §3.3 那四条 `modeRules` 可以原样进契约，但不能脱离形态准入矩阵单独使用。**

### 5.3 业务事实清单（合并后完整清单，本文自足）

两份原稿的事实清单**没有互相矛盾的条目**，只有详略差异。以下为去重合并后的完整版，
每条都是"搞错了就会做出错误模型"的那类。

**关于"卖"**

1. **商品不卖东西，卖的是菜单里的销售项。** 销售项必须且只能引用一个商品，
   但它有自己的身份——菜单商品行的锚点是 `salesItemRef + salesSectionRef`，**不是 `catalogItemRef`**。
   同一商品可在不同菜单版本、不同分区形成**多个**销售项，各有各的开放规格、开放选项、
   展示覆盖、挂牌价覆盖、排序、可见性、动作能力。销售项创建后**不允许换绑商品**。
   商品目录新增 SKU **不会自动进入已发布菜单**。
   → **推论：商品上不存在也不许加"卖不卖"字段。** 本期不做菜单即不产生销售项，不存在"可售"概念。
2. 商品的 `ACTIVE / INACTIVE` 只回答"能不能被引用"，**不回答"卖不卖"**。
3. `SELLABLE` 只是**用途能力**，表示允许创建销售项，不表示已上架、可售、库存足或价格有效。

**关于价格**

4. 价格分五层：标准价 → 集合挂牌价 → SKU 挂牌价 → 营销权益价 → 支付实付。
   **商品目录只拥有标准标价**；会员价、活动价、团购价、渠道价、时段价一律不在商品域。
5. **价格粒度由形态决定**：`priceGranularity=ITEM` 时要求商品级价，`=SKU` 时要求每个启用 SKU 有价。
   不无条件复刻 v4 的"商品级价硬必填"（会产生 `0.00` 假基准）。
6. **金额一律整数分**；数量用明确 decimal 精度，不用浮点。

**关于总公司与门店**

7. **目录 owner 只有「总公司 + 品牌」或「门店 + 品牌」，品牌本身不是 owner。**
   同一品牌在不同总公司下形成不同目录。
   **一个门店只归属唯一一个品牌**——门店侧的 `brandRef` 由门店确定，不是可选维度；
   **品牌切换器只存在于总公司商品库**（总公司可被授权多个品牌）。
8. **门店从总公司显式复制，复制后本地独立。** 总公司后续修改不自动跟随；
   总公司商品**停用只表示不再作新复制候选**，不影响已复制门店商品与已发布菜单；
   系统**不自动提醒、不自动生成差异、不自动下发、不做字段锁死**，总公司要门店跟进靠人工通知。
9. **总公司持有真实的库存对象与 BOM，但没有余额与流水**，也没有盘点/增加/调整；
   总公司的库存对象**永远不参与扣减**（§5.6.1）。

**关于商品结构**

10. **原材料、半成品、包装物就是商品**，不存在独立物料模型——
    它们是「原材料/半成品/包装物」这个**形态**，该形态精确派生
    `usageCapabilities = [STOCK_MANAGED, BOM_COMPONENT]` 且 `materialRole` 必填。
    **物料要零售就不该建成物料形态，应建成「普通销售商品」**——
    **形态即意图声明，不能靠事后给物料加 `SELLABLE` 来改变意图**（能力不可编辑，见 §5.2）。
11. **能力是要被校验的，不是描述**：创建销售项须校验 `SELLABLE`；
    BOM 行引用组件须**硬校验** `BOM_COMPONENT`。
    校验的是**形态派生出来的能力**，用户无从绕过。
    **`PRODUCIBLE` 在当前七形态中不被任何形态派生**——按"模型必须完整"保留为枚举位，
    等生产域进入时再由相应形态派生，本期不产生该值。
12. **SKU 回答"规格"，选项回答"怎么做、加什么"**。SKU 由销售属性维度 × 值字典组合生成，
    同一商品下启用中的属性值组合必须唯一。**只有强 SKU 矩阵与点单选项互斥**
    （`OPTIONAL_TABLE` 可与选项共存，见 §6-M2 的证据）。
13. **选项值产生库存消耗时必须配 BOM**，不靠 `linkedCatalogItemRef` 绕行。
14. **商品形态是 source fact**，必须持久化并进契约；创建后固定，配了下游事实即锁；
    `itemKind` / 能力 / `materialRole` / `measureMode` / 状态 / 来源是**不同维度**，
    不得用一个 `product_kind` 表达全部。
15. **商品型套餐是稳定组合**；团购套餐、储值套餐、权益包不是同一概念。
16. **多图只存 `assetRef`**，有序 + 主图标记，任何地方不持久化 URL。

**关于商品处理标签**

17. **标签属于生产域，商品只保存引用。** 商品页**不得直接选择工作台、队列、KDS、打印机或 topic**。
18. 标签只描述**商品处理方式**，不按岗位、设备或单个商品来建标签。
19. 停用标签**不物理删除历史商品引用**，但阻止新增引用。

**关于称重**

20. **重量是 POS 下单时的输入**（店员录入或电子秤读取），价格 = 单价 × 重量。
    **商品上永远不存重量**，管理后台无称重交互可做。商品域只声明"按重量卖 + 计价单位 + 识别码"。
21. 称重不是独立商品类型，是 `measureMode=WEIGHED`；时价同理不是商品类型。

**关于单位**

22. **单位三层**：销售单位（商品域）／**消耗单位（库存真相单位）**／盘点单位（仅录入便利）。
    余额、BOM 消耗、低库存阈值、库存提示**一律按消耗单位计量**。
23. 消耗单位**来自商品计量单位快照**，不得另建一套库存专用单位。
24. 换算规则必须**正数、有限小数或分数**；**禁 0、负数、无限精度、自由文本**。
    盘点单位与消耗单位相同时应**关闭盘点单位**，而不是配一条自我换算。
25. **单位或换算变更只影响后续流水**；历史流水与计划必须冻结当时的单位与换算快照。

**关于库存事实**

26. **流水是事实，余额是可重建的当前态**：成功的扣减/恢复/覆盖/人工调整**必须先写流水再更新余额**。
27. **没有"系统重算"这一流水来源**；重算只重建视图，不改变库存事实。
28. 库存状态五值：在库 / 低库存 / 缺货 / 负库存 / 未知。
    **"需处理"只是工作台派生视图，不进领域枚举。**
29. **负库存由库存对象上的显式开关决定**；不允许时扣到负应当拒绝，而不是静默记负。
30. 余额更新用 `stockTargetRef + version` 乐观锁，冲突短重试并追加正确流水。
31. **库存对象固定到门店**（总公司侧的定义除外，见第 9 条）；同一商品在不同门店是不同对象和余额。
    **不做总部跨店共享库存、不做跨店调拨、不做集团仓库。**
32. **选项值不能成为独立库存对象**，只能作为 BOM owner；
    **按 SKU 管理商品的主商品壳不能配库存或 BOM**。
33. BOM 行支持**正负数量**（加珍珠 / 不加珍珠 / 换燕麦奶扣回牛奶）。
    **BOM 合并顺序**：SKU BOM 或商品默认 BOM → 选项/加料 BOM → 经营入口覆盖 BOM。
34. **无 BOM 不阻断销售**，预检可返回"未配置 BOM"。
35. **BOM 行引用组件时不得自动创建组件的库存对象**；库存对象只能由独立库存控制、
    初始化导入、受控维护流程或**显式复制动作**创建。

**关于边界**

36. **库存提示不是可售**：库存域不能直接改菜单、改发布、形成可售控制、阻断订单或履约。
    **07 说"没货了"（事实），06 决定"下不下架"（意图）；低库存不自动下架。**
    不得由有库存推可售、缺货推菜单下架、库存流水推订单或结算。
37. **已成立的订单不因库存变化改写**；退菜不自动恢复沽清。
38. **归档不物删**：被订单、菜单快照、库存流水、BOM、识别码或外部映射引用的商品与 SKU、
    被计划或流水引用的库存对象、权威配置，**一律只能停用或归档**。
39. **商品与库存是两个 owner**，同屏不等于同表；catalog 不得直接写 inventory schema。
40. **生命周期状态与业务结果分离**：计划的 `status` 只有 `CREATED / EXECUTING / EXECUTED`，
    结果从执行行推算——interface-reserved 建模时即遵守。

### 5.4 资产：claim 语义与 CDN 就绪（Claude 独有，需并入）

**已核实的既有字节**：

```
MinioAssetObjectStorage:88   publicUrl(key) = publicBaseUrl + "/" + bucket + "/" + validKey(key)
V20260726_090000:28          group_workspace.logo_asset_ref VARCHAR(128)
staged_asset                 claimed_by_type / claimed_by_id     ← 单一 claimer
asset_bind_grant             asset_ref UUID PRIMARY KEY          ← 每资产一张 grant
```

**结论一**：URL 是读时现算、base 可配，业务侧存 ref——**切 CDN 就是换配置，零代码**。
本期不需要建 CDN，只需守住三条：任何地方不持久化 URL；
**未来菜单发布冻结快照时冻结 assetRef 而不是 URL**；前端不拼接不缓存 URL。
第二条最易踩，因为"冻结快照"的直觉是冻结当时看到的一切。

**裁定**（Dexter 已采纳）：**claim 表达字节的归属与生命周期，"谁在使用"由业务侧引用表达**。
菜单存同一 `assetRef` 但不重新 claim；删除保护靠引用反查。**不改资产核心表。**

## 5.5 模型规模纪律：能 JSON 化的必须 JSON 化，能契约化的必须契约化

Dexter 2026-08-06 明确要求：**产品模型不希望实体和关系特别多，能 JSON 化的应该 JSON 化，
必要的除外；能契约化的必须契约化。**

这与 v1 已拍板的折叠原则是同一条，本文把它升为**合并模型的验收纪律**：

> 某信息落**关系列/独立实体** ⟺
> （参与实时业务判断）∨（需排序、搜索、过滤、唯一约束、索引）∨（跨聚合或跨域按 ref 引用做完整性与反查）；
> 否则**折进 JSON**，且**形状必须在契约中定义，不得是裸 map**。

**两条不可分割**：JSON 化不是放松约束——**折叠换来的表数减少，必须用契约定义的形状换回类型安全**。
本域唯一允许的裸 map 是商品描述属性（Dexter 已裁，纯展示、不校验、不承担业务判断）。

### 5.5.0 统一 owner 表达（Dexter 2026-08-06 裁定，全模型适用）

> 「不止库存对象，所有的商品、标签、库存对象都会有这个问题。
> 建议统一用 **总公司ref+品牌ref / 门店ref+品牌ref** 来表达。」

**所有归属型对象一律用同一组 owner 表达**：

```
ownerType = HEAD_COMPANY | STORE
ownerRef                            （总公司 ref 或 门店 ref）
brandRef                            （两种情况均必填）
```

**适用对象**：商品库、商品、商品处理标签、库存对象、BOM，
以及被商品引用的全部字典（商品分类、商品标签、销售单位、SKU 销售属性与属性值）。

**不适用对象**：`StockBalance` 与 `StockChangeLedger` **保持既有的 `storeRef`，不加 owner 维度**。
理由：它们**只可能存在于门店侧**（总公司无余额无流水），加一个恒为 `STORE` 的 `ownerType`
是无意义的开销，还会让每条查询多一层无用判别。
`brandRef` 也不必重复携带——它可由所属库存对象取得。

**为什么这样比"给 `storeRef` 加可空"好**（我原先的推荐是后者，Dexter 的方案更优）：

1. **它不是库存对象一家的问题**。总公司要维护商品、标签、字典、库存对象、BOM，
   每一类都面临"没有 store 怎么表达归属"。逐个打补丁会产生五种不同的写法。
2. **它把 v6 已有的规则推广开**，而不是新造。v6 §4.1 对商品库本来就规定了
   `HeadCompanyCatalogOwner = headCompanyRef + 必填 BrandRef` 与
   `StoreCatalogOwner = StoreRef + 必填 BrandRef`——**本裁定只是把同一形态用到其余对象上**。
3. **`brandRef` 两侧都必填是关键**。v6 明写「门店目录也必须带 `brandRef`，
   不能用裸 `StoreRef` 表达目录归属」。统一后，"同品牌复制"这件事在数据层天然成立：
   门店与总公司的 `brandRef` 相同即为可复制来源。

**重要前提（Dexter 2026-08-06 明确）：在 v2s 的模型里，一个门店只归属唯一一个品牌。**

因此门店侧的 `brandRef` **由门店本身确定，不是一个可选维度**——它使 owner 表达在形状上保持统一，
但门店用户不会面对"选品牌"这件事。品牌切换器**只存在于总公司商品库**（总公司可被授权多个品牌）。

**推论**：门店的可复制来源**唯一确定**为「该门店品牌对应的总公司商品库」，
§5.6.5 的来源判定因此不需要任何额外规则，也不需要来源选择器。

### 5.5.2 精简的依据是业务分析，不是有无消费者（Dexter 2026-08-06 裁定）

> 「模型必须完整，该建的都要建，不要因为目前没有人消费就省略。
> 但是建，也要根据对业务的分析和理解进行精简，**不是根据有没有人消费而精简**。」

**因此我此前以"本期零消费者"为由提出的削减全部作废**（原 M1/M4/M5 三条），
保留并强化的是以**业务分析**为依据的削减。逐条重判如下。

**重判一：总部库存/BOM —— 我原来的"折进 JSON"作废**

原因不是消费者，而是**前提变了**：Dexter 裁定「总公司**可以有库存对象**（跟生产标签一样），
我说的总公司没有库存，是指**没有盘点、增加库存这些库存建设的逻辑**」。

所以总公司持有的不是"模板 JSON"，而是**真正的 `StockTarget` 与 `ProductBom` 实体**，
只是它们**没有 `StockBalance` 与 `StockChangeLedger`**，也没有盘点/增加/调整这些操作。
门店从总公司复制时，得到的是自己的库存对象与 BOM，然后才有余额与流水。

**这个形态比"模板 JSON"更好**：总公司与门店用**同一套模型**，差别只在有没有余额与流水这一层，
不需要维护两套形状相似的东西。**不新增实体，而是给既有实体加 owner 维度。**

**与 v6 的差异必须显式登记**：v6 §2.3 写的是「总部商品库可以维护……库存控制规则模板和 BOM 规则模板，
但这些只是目录侧模板，**不产生实际库存对象、余额、库存流水或门店实际 BOM**」。
Dexter 的裁定与此不同。**产品裁决优先**；v6 那条真正要防的是"总部跨店共享库存"，
而本形态下总公司的库存对象**永远没有余额、永远不参与扣减**，该风险仍被排除。

**重判二：`CatalogItemRelation` —— 建，但按业务分析删掉两个关系类型**

原七个类型：替代品、相似品、`MATERIAL_OF`、`PACKAGING_OF`、权益壳关系、报表归并、人工链接。

**`MATERIAL_OF` 与 `PACKAGING_OF` 应当删除**——这是业务分析结论，不是消费者论证：
BOM 已经完整表达了"这个商品消耗那个物料、每份多少、正向还是负向、按什么顺序合并"。
再用一条关系说一遍，**信息量严格更少而语义重复**，是第二份真相。
两者不一致时无从判断谁对。

其余五类保留。**净减两个关系类型，不减实体。**

**与 `CatalogItemReference` 不合一**：引用边表是**归档守卫的安全机制**（系统派生、防止删掉在用对象），
关系表是**用户维护的业务数据**。把用户可写的数据混进安全表会削弱守卫，
省一张表不值这个代价。

**重判三：`ExternalCatalogIdentity` —— 建**

我此前主张"折进 provenance"，其中"零消费者"的部分作废。
但**业务分析上它也确实该独立**：它承载 **SKU 级映射**（`externalSkuId`）与**同步状态**
（`syncMode`、`lastSyncedAt`），这两类都不是"商品的来源痕迹"，provenance 装不下；
且外部 ID → 内部商品的反查需要唯一约束与索引。**保留为实体。**

**重判四：`StockDeductionPlan` / `StockRestorePlan` 两族 —— 建**

四张表（两个计划 + 两个执行行）本期建全，不建执行逻辑。
`StockChangeLedger` 的 `planRef` / `planLineRef` 可直接建为真实外键。

### 5.5.4 契约化清单（"能契约化的必须契约化"）

以下**全部**必须是契约产物，生成前后端两侧并走字节比对与 count 断言，不允许任一侧手写：

1. **商品形态 manifest**：形态全集、派生字段、页签集、字段可见性与必填、固定性规则；
2. **库存/BOM 的 `modeRules`**：§3.3 那四条（节点类型 × 条件 → 允许模式）；
3. **每一个折叠 JSON 的形状**：点单选项、套餐结构、生产提示、媒体、能力、维度 refs；
4. **全部封闭集合**：`itemKind`、`usageCapabilities`、`materialRole`、`measureMode`、`skuMode`、
   `stockState`、流水来源、库存控制方式、商品处理标签 `tagKind`、目录/库存对象的 owner 类型、
   商品状态、治理状态、来源模式；
   （**不含** `scope`——门店级裁定后 `PROJECT_DEFAULT | STORE_OVERRIDE` 已取消，见 §5.6.2）
5. **错误码与可恢复动作**；
6. **金额单位（整数分）与数量精度**。

不能成为"其他地方也可以放裸 map"的先例。

## 5.6 总公司商品库与复制（Dexter 2026-08-06 新增范围）

这一块 v4 未实现到位，**按全新设计**，不以 v4 为参照基线。

### 5.6.1 总公司持有什么

- **商品库按「总公司 + 品牌」定位**（与 v6-05 §4.1 的商品目录 owner 定义一致）。
  界面与门店商品库类似，**多一个品牌切换器**；
  品牌候选来自**该总公司已获授权的品牌**（v2s 已有总公司-品牌授权，不新建授权机制）。
- **总公司维护**：商品、BOM 关系、**库存对象**、商品处理标签，全部按「总公司 + 品牌」维度。
- **总公司不维护**：盘点、库存增加、人工调整——即**没有余额与流水，没有库存建设逻辑**。

**模型表达**：`StockTarget`、`ProductBom`、商品处理标签定义均按 §5.5.0 携带统一 owner，
取值为**「总公司 + 品牌」或「门店 + 品牌」**（两侧 `brandRef` 均必填）。
**总公司侧的库存对象没有 `StockBalance` 与 `StockChangeLedger`**，
且**永远不参与任何扣减**。不新增平行的"模板"实体。

### 5.6.2 商品处理标签的作用域 —— 总公司+品牌 与 门店 两级，不设项目级

**v6 与实际实现不一致，此处采实现 + Dexter 裁定。**

- v6 §4 的 `ProductionTagDefinition` 字段是 `projectRef` + 可选 `storeRef`，
  作用域为 `PROJECT_DEFAULT | STORE_OVERRIDE`；
- **v4 活环境实测是门店级**：「履约生产规则管理 → 商品处理标签」页面的上下文是
  「项目 深圳万象城 / 门店 炉边西餐深圳万象城店」，实见两条标签
  （热菜制作 `HOT-DISH`／制作提示、外带打包 `PACKING`／包装提示）；
- **Dexter 裁定：就是门店级。**

**最终形态**（与商品库、库存对象完全同构）：
**总公司 + 品牌持有标签定义（供复制），门店持有自己的标签定义**（可自建，也可从总公司复制而来）。
**不设项目级作用域**，`scope = PROJECT_DEFAULT | STORE_OVERRIDE` 这组取值随之取消。

**保留 v4 的两条边界说明**（页面原文，写得很准，建议进 v2s 文案）：

1. 「标签只描述**商品处理方式**，不要按岗位、设备或单个商品来建标签」；
2. 「商品维护页只引用这里的标签；字段和列表顺序由**同一份 contract** 约束，避免两边说法不一致；
   停用标签不会物理删除历史商品引用」——这条正是"能契约化的必须契约化"的现成实证。

**维护入口（Dexter 2026-08-06 裁定）**

> 「商品处理标签是**生产履约域的实体**，与商品字典**概念和业务含义都不同**，
> 但**入口可以放在一起**，同时也要支持用户在**编辑商品的过程中快速创建**，
> **总公司和门店可以统一**。」

三条要求，逐条落地：

1. **概念不合并，只是入口放在一起。** 标签的事实归属仍是**生产履约 owner**，
   **不得改归 catalog**。入口标签写「**商品处理标签**」，
   **不要用"生产配置"这类模糊叫法**，也不要让用户以为它是商品字典的一部分。
   页面调用的是 production-tag owner 的接口，不是 catalog 的。
2. **支持在编辑商品的过程中快速创建。** v4 已有这个机制——
   generated 契约里 `skuVariantDimensions` 字段带 `quickManage`
   （"销售属性字典 / 维护颜色、尺码、容量等"，`refreshScope=CURRENT_FIELD`）。
   **把同一机制扩展到商品处理标签字段**，属照搬 v4 做法而非新造。
3. **总公司与门店入口统一**：两侧都在商品库的「商品字典」入口内维护，
   都支持编辑商品时快速创建。**门店不再单独走「履约生产规则管理」那条路**
   （该页面的其余部分——现场岗位、订单生产流程、叫号交接、模拟试跑——本期均不建）。

### 5.6.3 复制：门店从总公司（同品牌）复制 N 个商品

**复制什么**：用户选中 N 个商品；**所有与被复制商品相关的对象都一并按编码去重复制**
（Dexter 2026-08-06 裁定：「跟这个复制商品相关的东西，都按 key 去重复制」，
并于同日澄清「key 等同于编码」）。范围包括：

- 关联的其他商品（BOM 组件物料、套餐组件商品）；
- 商品处理标签；
- **库存对象与 BOM 关系**（总公司侧已有，见 §5.6.1）；
- **被引用的字典**：商品分类、商品标签、销售单位、SKU 销售属性与属性值。

**去重规则**：按**编码**判断，门店**已存在则沿用门店版本**（不覆盖、不强继承），不存在则一并复制。

#### 判同键统一为「编码」（Dexter 2026-08-06 澄清）

> 「key 等同于编码，是我的口语化带来的误解。后面应该统一用**编码**来表达。」

**复制判同语义全文不再使用「key」，统一称「编码」**（Dexter 原话引用与 `publicUrl(key)` 这类代码符号不在此列）。
每类对象的判同键就是它的**编码**，v4 实证每类对象都有编码：
商品 `PIZZA-PEPPERONI-001`、分类 `APPETIZER`、标签 `SIGNATURE`、销售单位 `PORTION`／`CUP`、
SKU 销售属性 `DRINK_SIZE`、属性值 `SMALL`／`MEDIUM`／`LARGE`、SKU `SKU-001`、
商品处理标签 `HOT-DISH`／`PACKING`。

#### 复制闭包：唯一算法（回应 Codex M-01／M-02／M-03／S-03）

上一版只写了"递归一层"这种含糊措辞，对 `A → B → C → D` 的 BOM 链会有三种读法。
本节把它定义成**唯一算法**。

**算法：对批准的正向边求传递闭包直到不动点。**

```
visited = {}                                   // 键为 (objectType, sourceRef)
queue   = 用户选中的 N 个商品
while queue 非空:
    obj = queue.pop()
    if (obj.type, obj.ref) in visited: continue        // 环终止
    visited.add((obj.type, obj.ref))
    for edge in 批准的正向边(obj):                      // 见下表，仅此几类
        queue.push(edge.target)
    if |visited| > CLOSURE_OBJECT_LIMIT:
        throw COPY_CLOSURE_TOO_LARGE(实际计数, 上限)    // 不截断，整体失败
```

**批准的正向边**（只有这几类会扩张闭包，其余一律不扩张）：

| 源对象 | 正向边 | 目标 |
| --- | --- | --- |
| 商品 | `CATEGORY` / `TAG` / `SALES_UNIT` / `SKU_ATTRIBUTE` / `PRODUCTION_TAG` | 对应字典（叶子） |
| 商品 | `COMPOSITE_COMPONENT` | 组件商品（**继续展开**） |
| 商品 / SKU / 选项值 | `BOM_COMPONENT` | 组件物料商品（**继续展开**） |
| 商品 | `SKU` | 其 SKU（叶子，但其属性值走 `SKU_ATTRIBUTE_VALUE` 边） |
| 商品 / SKU | `STOCK_TARGET` | 库存对象（叶子） |
| SKU 属性 | `SKU_ATTRIBUTE_VALUE` | 属性值（叶子） |

**叶子类型**（进入闭包但不再外扩）：分类、标签、销售单位、SKU 属性与属性值、
商品处理标签、库存对象、SKU、BOM 与 BOM 行。

**三条硬边界**：

1. **反向引用绝不扩张闭包**——"谁引用了我"不跟着复制；
2. **`CatalogItemRelation` 不是批准的边**（替代品、相似品等业务关系不跟随复制），
   否则一次复制会沿关系网扩张成接近整个商品库；
3. **`visited` 以 `(objectType, sourceRef)` 为键**，天然终止循环与重复依赖。

**两个独立上限，缺一不可**（回应 S-03）：

- `SELECTED_ITEM_LIMIT`：用户一次可选的商品数；
- `CLOSURE_OBJECT_LIMIT`：**展开后的闭包对象总数**。
  只限前者不够——一个套餐商品可能展开出大量组件与字典。

超限返回 typed failure `COPY_CLOSURE_TOO_LARGE` 并**回报实际计数**，
**不得截断后继续复制**。

**预检的分母就是 `visited` 集合**——不多不少，可复算。

#### 全图引用重写（回应 Codex M-02）

上一版只定义了 BOM 行的库存对象引用重写，**这是不够的**：复制出来的门店商品
如果继续引用总公司的分类、标签、单位、属性值或标签，就破坏了门店的独立生命周期与 owner 隔离。

**统一映射表**：复制过程维护一张 `(objectType, sourceRef) → targetRef` 映射，
闭包内**每一个**对象在写入前都要把自己的全部 outbound 引用按该表重写。

**逐类必须重写的引用**：

| 对象 | 需重写的 outbound 引用 |
| --- | --- |
| 商品 | 分类 ref、标签 refs、销售单位 ref、SKU 属性维度 refs、商品处理标签 refs、套餐组件的商品与 SKU refs（在 typed JSON 内）、点单选项内的商品处理标签 refs |
| SKU | 所属商品 ref、属性值 refs |
| 库存对象 | 所属商品或 SKU ref |
| BOM | owner ref（商品／SKU／选项值） |
| BOM 行 | 组件库存对象 ref |

**写入前后各有一道断言**：目标对象图中**不得出现任何指向总公司 owner 的 ref**；
任何未能在映射表中解析的引用**整体失败**，不允许留空或留原值。

#### 结构兼容矩阵（回应 Codex M-03）

上一版只把"消耗单位不同"定为结构不兼容，其余同编码冲突未归类。逐类补齐：

**判别标准**：该差异是否会**改变语义**。改变语义的阻断；只影响展示或组织方式的可确认后复用。

| 对象 | 判同编码 | 结构判别位（不同即**阻断**） | 可确认后复用的差异 |
| --- | --- | --- | --- |
| 商品 | 商品编码 | **商品形态**；**SKU 结构指纹**（按 `skuCode` 排序后，逐项绑定排序后的 `(attributeCode,valueCode)` 组合） | 名称、短名、说明、图片、标签、**所属分类** |
| 分类 | 分类编码 | —— | 名称、排序、**父分类路径** |
| 标签 | 标签编码 | —— | 名称、颜色/分组 |
| 销售单位 | 单位编码 | **`unitKind`** | 名称、**`precision`** |
| SKU 销售属性 | 属性编码 | —— | 名称、展示顺序 |
| SKU 属性值 | 属性编码 + 值编码 | **所属属性维度** | 展示名、排序 |
| 商品处理标签 | 标签编码 | **`tagKind`** | 名称 |
| 库存对象 | 所属商品/SKU 编码 | **对象形态（商品 vs SKU）**、**消耗单位** | 低库存阈值、允许负库存 |
| BOM | owner 编码 | **owner 类型**（商品／SKU／选项值） | 版本备注 |

**两处我未采纳 Codex 的建议，理由如下**：

- **分类父路径不阻断**。总公司把「披萨」挂在「主食」下、门店挂在顶层，
  复用后商品仍然被归类为「披萨」，**语义没变，变的是门店自己的组织方式**——
  而门店本就有权按自己的习惯组织分类树。这与消耗单位那种"10 克变成 10 个"性质完全不同。
- **销售单位只按 `unitKind` 阻断，`precision` 不阻断**。
  `unitKind` 从 `COUNT` 变 `WEIGHT` 会改变计量语义，必须拦；
  而 `precision` 只影响显示与舍入位数，不改变"这是多少"。

**判别位不同一律阻断该项复制，不提供"接受并忽略"。**

**冲突处理 —— 复制前预检（Dexter 裁定）**：

> 「可以在执行复制之前就做一下判断，给用户列出所有差异，如果用户选择接受，就忽略差异。」

即：**先做 pre-flight 差异比对并把全部差异展示给用户**，**用户明确接受后才执行**，
执行时按"已存在则沿用门店版本"处理。不静默、不覆盖。
（**但结构不兼容项不适用"接受即忽略"，直接阻断**——见 §5.6.6。）

#### 预检与执行之间必须有一致性闭环（采纳 Codex M-03）

**预检结果不能直接当写入授权。** 用户从看到差异到点击执行之间，
来源商品、门店字典、库存对象或 BOM 都可能被别人改动——这是典型的 TOCTOU：
用户确认的是 A，最终复制的可能已经是 B。

**因此**：

- **预检属于读路径**，由应用查询协调器发起，允许**已登记的任务型跨 schema join**；
  但**判同与兼容性分类仍由各 owner 提供**，不能由 join 自行发明业务判断（§3.2 的规则在此适用）；
- 预检返回：**完整闭包 + 来源与目标的 version + 映射预览 + `preflightDigest`**；
- **执行属于写路径**，命令必须携带 `preflightDigest`、各对象的 expected version 与幂等键；
- catalog、inventory、商品处理标签**三个 owner 在同一 `REQUIRED` 事务内各自重新复核**
  （kernel `OWNER_RECHECKS_COMMAND`），整体成败；
- 检测到漂移返回 typed 失败 `STALE_COPY_PREFLIGHT`，要求用户重新预检，**不得静默按新状态执行**；
- **一次复制的商品数 N 必须有上限**，避免单个事务无限扩张（具体取值在契约设计时定）。

**这同时回答了"预检算读还是算写"这个我先前没说死的问题：预检是读，确认执行是写。**

**复制的结果**：门店商品的 `sourceMode = HEADQUARTER_COPIED`，
provenance 记录来源商品 ref，**仅用于追溯**——总公司后续修改不自动跟随，
系统不自动提醒、不自动生成差异、不自动下发（§5.3 事实第 8 条的既有语义不变）。

**与"从已有商品复制配置"的区别（必须用不同名字与入口）**：

| | 总公司 → 门店 | 门店内商品 → 商品 |
| --- | --- | --- |
| 跨库 | 是（跨 owner） | 否 |
| 建立来源关系 | 是 | 否 |
| 一次多个 | 是（N 个） | 否（单个） |
| 带字典与标签去重 | 是 | 不需要（同库已存在） |
| 差异预检 | 需要 | 不需要 |

**复制后的库存对象状态**：由于总公司侧已持有库存对象定义，复制过来即成为门店的库存对象，
**BOM 不会悬空**。门店侧该对象的余额从 0 起，需门店自行盘点或增加库存。
这一条同时解决了 v6 §4.1 规则 3「BOM 行引用组件时不得自动创建组件库存对象」的张力——
库存对象不是被 BOM 隐式创建的，而是**被显式的复制动作带过来的**。

### 5.6.4 复制来源：只能是门店自己所属的总公司 + 品牌（Dexter 裁定）

门店**不需要来源选择器**——来源可从既有表**直接读出**，无需任何推导：

```sql
organization.store
  brand_id        UUID NOT NULL REFERENCES organization.brand(id)      ← 门店品牌唯一，表级强制
  head_company_id UUID          REFERENCES organization.head_company(id)  ← 可空
```

`brand_id` 是 **NOT NULL 单值**，这就是「一个门店只归属唯一一个品牌」的表级实证；
`head_company_id` 直接给出所属总公司。**来源库 = `head_company_id + brand_id`，一次读取即得。**

跨总公司或跨品牌复制在业务上不成立：门店卖的就是它签约的那个总公司+品牌的东西。

**边界：没有总公司的门店（Dexter 2026-08-06 裁定）**

`head_company_id` **可空**，因此存在没有关联总公司的门店。
这类门店**不显示「从总公司商品库复制」这个按钮**——不是灰掉、不是点了报错，是**入口不出现**。
其余商品与库存能力不受影响，门店照常自建商品。

> **命名提示**：该动作全文统一叫「**复制**」，**不要叫"导入"**。
> v4 商品库顶部另有一个「导入商品」（Excel 批量导入），本期已明确 Out；
> 两者同名会让用户和实现都混淆。

### 5.6.5 权限：一个"编辑商品库"权限管全部写操作（Dexter 2026-08-06 裁定）

> 「权限上，不需要分那么细，只要有"编辑商品库"的权限，就可以做所有写操作。」

**不为商品、SKU、选项、套餐、库存对象、BOM、商品处理标签、复制、盘点、库存增加、
人工调整分别设置能力**——它们同属一个"编辑商品库"能力。

**仍然生效的两条边界**（这是 scope 不是 capability，两者不可互相替代）：

1. **数据范围**：总公司用户只能写自己总公司+品牌的库，门店用户只能写本店的库。
   这由 v2s 既有的 owner scope 机制承担，**不因权限合并而放松**。
2. **owner 复核**：命令仍须在事务内由 owner 复核当前事实与授权（kernel `OWNER_RECHECKS_COMMAND`）。

**推论**：总公司用户**不能替门店执行复制**——不是因为缺权限，而是因为复制的写入目标是门店的库，
超出总公司用户的数据范围。

### 5.6.6 复制时 BOM 行的引用重写（Dexter 裁定：映射表方案）

**这是复制功能最容易出错的地方，必须在设计中写死。**

总公司的 BOM 行指向**总公司的**库存对象；复制到门店后必须指向**门店的**库存对象。
采用**有序复制 + 映射表重写**：

1. 先复制物料商品（按编码去重）；
2. 再复制/解析对应的库存对象，建立「总公司库存对象 ref → 门店库存对象 ref」映射表；
3. 最后复制 BOM 与 BOM 行，**按映射表重写每一行的组件引用**。

**否决的替代方案**：让 BOM 行改存商品/SKU ref、由库存域在使用时解析成当前 owner 的库存对象。
理由是它改动了 BOM 行的基本定义（v6 明确 BOM 行引用 `stockTargetRef`），
并把解析代价放到未来扣减的热路径上——复杂度应留在复制过程内部，而不是渗进运行时。

**消耗单位不一致必须阻断，不能"确认后忽略"（Dexter 2026-08-06 裁定，采纳 Codex M-02）**

当门店已存在同编码的物料、且两边**消耗单位不同**时（总公司「披萨饼底」按克、门店按个），
BOM 行的 `quantityPerUnit` 是**按组件库存对象的消耗单位解释**的——
把「10 克」原样改指一个按「个」计量的对象，就变成了「10 个」。
**这不是用户确认差异，是数量语义被改写**，会产生看起来复制成功、实际配方已损坏的静默错误。

**因此差异分三类处置**：

1. **相同** → 直接复用；
2. **非结构差异**（名称、短名、图片、描述不同）→ 展示后允许用户确认并复用；
3. **结构不兼容** → **禁止"接受并忽略"，直接阻断该项复制**。

**消耗单位不一致属第三类，本期直接阻断，不做换算**（Dexter：「不支持换算，阻断就好了」）。

理由：支持换算会让复制功能顺带长出一个单位迁移系统，而单位换算一旦引入
就要处理精度、审计、历史冻结等一整套问题——那是另一个范围。
门店应先把自己的物料单位调整一致，再执行复制。

### 5.6.7 总公司侧的页面：不做库存现状，靠左树看清单（Dexter 裁定）

**总公司不需要看库存**——没有余额，也没有盘点/增加/调整。

**总公司要看"定义了多少物料"，走商品库左侧树的智能视图与商品形态分类**，
不另建"库存对象清单页"。点左树的「原材料/半成品/包装物」形态节点即得全部物料及其计数。

> **Dexter 特别强调：左树的智能视图与形态分类是 v4 的亮点，必须继承，
> 而且不只是为了总公司这个场景。** 它同时服务门店的日常任务
> （待治理、缺图、已停用、已归档、最近修改等入口）。
> 本条已从"v4 保留项"升格为**明确需求**，见 §5.6.8。

**总公司的库存对象与 BOM 只在商品详情的「库存与 BOM」页签里维护**，
结构与门店侧完全一致（同样的节点树、同样的三态控制方式、同样配组件与消耗数量），
**差别只是没有余额、没有库存状态、没有盘点/增加/调整动作**。

**库存对象不能脱离商品单独创建**（Dexter 裁定：以 v4 为准）。
v4 实证：库存对象与 BOM 都在商品抽屉的「库存与 BOM」页签里建，
**没有独立的"新建库存对象"表单**（`CREATE_STOCK_TARGET` 从未被调用）。
本期沿用此形态，总公司与门店两侧**均无"新建库存对象"这样的独立入口**。

**但"无独立入口"不等于"只有一条创建路径"**（此前措辞会引起误读，本轮澄清）。
库存对象的合法创建路径共两条，**都是受控的**：

1. 在商品详情的「库存与 BOM」页签里，为某节点选择"独立库存控制"或"BOM 规则"；
2. **门店从总公司复制商品时随之带过来**（§5.6.3）。

**被禁止的是"隐式创建"**——v6 §4.1 规则 3 的原意是防止 BOM 行引用组件时静默生成组件的库存对象。
复制是一个用户明确发起、且经过差异预检确认的动作，**不属于隐式创建**。

### 5.6.8 左树能力（从"v4 保留项"升格为明确需求）

商品库左侧树是**三段并列**，均带计数：

1. **商品分类树**（一二级管理分类，带 code）；
2. **智能视图**：待治理、外部订单临时商品、已停用、已归档、最近修改、自动同步；
3. **商品形态**：七种形态各自的计数。

**它同时承担三类真实任务**：按分类找商品（日常）、按治理状态找待处理（运维）、
按形态找某一类对象（如"我定义了多少物料"——总公司与门店都会用）。

**「自动同步」与「外部订单临时商品」两个视图全部保留并展示**（Dexter 2026-08-06 裁定）

> 「模型该有的东西必须有，**不能因为场景未到就忽略**，要重点把这块的业务含义参照 v6 描述一下，
> **保留视图和模型**。」

因此**否掉两条此前的处置**：我原先写的「自动同步保留字段但不展示入口」，
以及 Codex S-05 建议的「本期一并隐藏外部订单临时商品」——**两者都不采纳，视图与模型全部保留**。

按 v6-05 描述其业务含义（这是保留它们的意义所在，而不是留一个空壳）：

- **自动同步**：商品可由集团 ERP 或门店自有 ERP 持续同步，
  同步来源对该商品的对应字段**拥有字段主权**——`sourceMode=AUTO_SYNC` 后
  **人工维护被禁止**，人工只能治理映射或补充非同步字段。
  这个视图让运营者一眼看出"哪些商品我改不了、得去上游改"。
- **外部订单临时商品**：外部订单已经推送进来、但内部暂时没有商品壳时，
  系统自动创建 `EXTERNAL_ORDER_TEMP_ITEM`——它**前端可见但不可编辑**，
  **不可创建销售项、不可发布**，治理补全后可转为正式商品，
  但**历史订单仍按原订单快照回放**。这个视图是治理待办入口。

两者本期都**不建同步执行链与外部订单接入链**，但**模型、枚举、视图位、业务含义全部就位**。

### 5.6.9 图片与资产

复制商品时**引用同一 `assetRef`，不重新 claim**（与 DR-4 的 claim 语义一致）。
这使复制成为 claim 语义的第一个真实验证场景，不必等做菜单。

### 5.7.1 商品列表工作台 —— 保留

**页面骨架**：标题 + scope 标签条（项目 / 门店 或 商品库范围）+ 左树 + 右侧筛选栏与表格。

**scope 标签条**是独立一行的胶囊标签，不是面包屑：
门店侧显示「项目: 深圳万象城 / SZ-MIXC」「门店: 炉边西餐深圳万象城店 / STORE-SZ-MIXC-FIRES...」；
总公司侧显示「商品库: 品牌标准商品库 / 炉边西餐总公司 / HC-FIRESI...」。
**名称与编码同时显示、编码在斜杠后**，这个格式全站一致，值得保留。

**左树三段**（§5.6.8 已定为明确需求，此处补细节）：
顶部有「+ 新建分类」按钮与「搜索分类编码或名称」输入框；
「全部商品 67」「未分类 0」两个总入口在最上；
智能视图与商品形态两组都**带计数徽章**，计数为 0 的项**仍然显示**（如「称重销售商品 0」）——
这让运营者知道"这类存在但我没建"，与"隐藏空事实"不冲突，因为它是**能力清单**不是数据展示。

**筛选栏**：商品编码/名称/短名搜索框（带独立放大镜按钮，不是回车即搜）+ 商品状态 + 治理状态 +
来源 + 标签 + 重置。

**表格**：左上「已选择 N 项」+「批量操作」下拉（仅对父行生效），右上「列设置」。
列为：商品 / 形态与规格 / 价格 / 菜单与渠道 / 套餐引用。

**商品列的单元格是复合的**：复选框 + 展开箭头（仅 SKU 商品有）+ 缩略图 + 商品名（蓝色可点）+
第二行编码与短名 + 第三行标签徽章。

**形态与规格列**：形态徽章 + 状态徽章（启用/草稿）+ 治理徽章（正常）；
SKU 商品第二行显示「2/2 个 SKU · 披萨尺寸」——**分子分母 + 维度名**，信息密度很高。

**价格列**：普通商品「78.00 元 / 商品定价」；SKU 商品「68.00 元 - 88.00 元 / SKU 定价」——
**区间价 + 定价粒度**同时显示，一眼看出这个商品按什么粒度定价。
缺价时追加黄色徽章「2 个 SKU 缺价」。

**「菜单与渠道」「套餐引用」两列是引用反查**（如「已加入菜单草稿 1 处 / 1 个销售项 · 0 个渠道」
「已加入 1 个套餐 / 1 个套餐」）。**本期 06 不在范围，这两列不展示**（§1 第 15 条），
但**反查这个设计思想必须保留**——它与库存对象详情的「关联商品」是同一个思想。

### 5.7.2 商品详情与编辑 —— 保留

**载体是右侧宽抽屉**（约 1024px，占屏 65%），左侧列表仍可见。**不是全宽页面**
（v1 文档记错，我实测更正）。

**查看与编辑是同一抽屉内切换**，靠右上角按钮：查看态显示「编辑商品」，编辑态显示「查看模式」。
两态的顶部操作条都还有：「从已有商品复制配置」、启用（当前态不可用则灰）、停用、归档（红色）。

**查看态是键值对表格**，两列布局，不是 disabled 表单。
字段顺序：商品形态|商品编码 → 商品名称|短名 → 商品类型|计量方式 → 使用能力 →
权益参与|标准价 → 销售单位|分类 → 标签 → 商品图片 → 商品说明。

**编辑态底部固定操作条**：「关闭」+「保存商品」（主按钮）。

**每个字段都有帮助文案**，且**是面向业务而非技术的**，例如：
商品形态「先选择商品形态；创建后固定不再修改，它会决定后续要填写的页签和字段，
例如普通菜品选普通销售商品，多规格奶茶选按 SKU 管理商品」；
商品编码「用于后端检索、导入导出和对账；建议使用集团或门店统一编码，例如 DRINK001」；
短名「用于小票、标签或窄屏展示，例如拿铁」；
使用能力「用于核对当前商品可参与的业务场景，例如可销售、可作为库存对象、可作为 BOM 组件或可生产」。
**这套文案质量很高，建议直接沿用其风格（都带"例如"举例）**，不要换成干巴巴的字段名重述。

**只读派生字段用 `readonlySummary` 呈现**（商品类型、计量方式、使用能力），
不是 disabled 输入框，视觉上就与可编辑字段区分开。

### 5.7.3 点单选项 —— 保留，这是设计得最好的一屏之一

**三栏**：左「点单分组」列表 + 中分组详情 + 右「点单预览」。

**左栏**：分组卡片显示「点单分组 1 / 可用 / 可选单选 · 0 个可选项」+ 上下移动箭头；
空态是「暂无点单分组」+ 居中的「+ 新建分组」按钮。

**中栏**：基础设置（分组名称、分组类型=自定义）→ 选择规则（**选择方式是两张卡片式 radio**：
「单选 / 本组只能选 1 个可选项」「多选 / 本组可以选多个可选项」，不是普通 Radio）→
必选开关 + 最少选 + 最多选 + 状态 → 可选项表（编码 / 可选项 / 小票·后厨名 / 加价（元））。

可选项区上方有说明「名称、加价、小票/后厨名和制作影响会跟随保存商品一起提交」——
**主动告知提交边界**。

**右栏「点单预览」是本屏的精华**，三件事：

1. **三个计数**（分组 / 可选项 / 必选）+ 状态徽章（绿「检查通过」或黄「1 个待处理」）；
2. **实时结构校验且给出具体原因**：黄框「保存前需要处理：启用分组至少需要一个可用选项」——
   **不是"保存失败请检查"这种无信息量的提示**；
3. **「顾客点单看到的层级」表**（层级 / 规则·加价）——让运营者看到顾客视角；
4. **「扣料摘要」块**，并明写「这里只展示可选项扣料状态。**扣料规则仍在"库存与 BOM"页维护**」——
   **在用户最可能误解的地方主动说明"这件事不在这里做"**。这条跨页签边界提示非常值得学。

### 5.7.4 库存与 BOM —— 保留

**两栏**：左「库存/BOM 节点树」+ 右「库存/BOM 规则详情」，
右上角常驻标注「**随保存商品一起提交**」。

**节点树带类型徽章**：可配节点标「可配」，目录节点标「目录」并置灰。
实见层级：`意式辣香肠披萨 / PIZZA-PEPP...【可配】` → `商品选项 / 1个选项类...【目录】`
→ `点单分组1 / 0个选项...【目录】`。
拿铁（SKU 商品）只读态实见：`拿铁咖啡【主商品】无库存控制` → `商品 SKU / 3 个 SKU【目录】`
→ `小杯拿铁【商品 SKU】BOM` / 中杯 / 大杯。

**库存控制方式是三个并排按钮**（无库存控制 / 独立库存控制 / BOM 规则），选中态蓝色高亮，
不可用的模式置灰。

**BOM 组件的可写字段只有两个**（v1 D-2 的裁定是「编辑 UI 只有组件与消耗数量」，
**`lineSign` 仍保留在模型与只读面**，本期只是不提供独立编辑控件——不要理解成从模型删字段）。
表为两列 + 操作：BOM 组件（下拉，显示「披萨饼底 / ERP-MAT-PIZZA-DOUGH / 个」
——**名称 + 编码 + 单位三段**）、消耗数量（`1.0000`，四位小数）、删除。
**起步的可写字段就这两个，不要加**。

**只读态是一张平表**：商品结构 | 库存控制方式 | 独立库存 | BOM 组件，
每行显示节点及其规则，BOM 列显示「意式咖啡豆 / ERP-MAT-COFFEE-BEAN / 克 x 14」。
拿铁三个 SKU 分别 x14 / x18 / x24——**同一物料按规格差异化消耗**，一眼看清。

### 5.7.5 库存现状与库存对象详情 —— 保留（本期展示口径先照搬 v4）

> Dexter 2026-08-06 对展示口径的裁定：「**建议先复制 v4**」。
> 因此本期指标集合与 v4 一致，只把"消耗"改名为"库存变化"（D-11），不另立指标。

**列表页**：标题「商品库存管理」+ scope 标签条；右上「导出库存现状」「怎么看」；
状态分类 tab **带计数**（全部 20 / 需处理 19 / 低库存 1 / 无库存 17 / 负库存 1 / 未知 16）；
筛选为 全部分类 + 全部库存来源 + 名称或编码搜索。

**列**：库存对象 | 当前库存 | 状态 | 低库存提醒 | 消耗（→改名库存变化）| 最近变化 | 库存来源。

**导出边界**：v4 右上角的「导出库存现状」**本期不做**，与商品的 Excel 批量导入导出一并 Out。
理由是它会引出格式、权限、全量还是当前筛选、大数据量分页这一串问题，而本期未证明该用户任务；
它是易于后加的只读能力，不影响任何模型。

**几个细节值得保留**：

- 库存对象列三行：名称 / 编码 · 对象形态 / 物料标记（如「意大利面」「ERP-MAT-SPAGHETTI / 商品」「物料」）；
- **低库存提醒列直接把差额算好并标红**：「200 克 / **差 230 克**」——不让用户自己减；
- 状态徽章按语义配色（负库存红、无库存黄）；状态下方可追加「未知」小字；
- **变化量列按今日 / 7 天 / 30 天三档**（v4 原为「今日 0 克 / 7 天 0 克 / 30 天 0 克」）；
- 最近变化列两行：事件名 + 时间戳（「库存余额更新 / 2026/6/27 00:40:15」）；
- 库存来源列两行：权威 + 对象类型（「内部轻库存 / 商品库存对象」）。

**库存对象详情抽屉**——顶部三动作「存量盘点 / 增量入库（→改名库存增加）/ 快捷配置」，
内容**六块**（我上一版只滚了半屏、漏记两块，本轮据源码补全）：

1. **当前状态**：库存对象|对象形态、当前库存|状态、低库存阈值|库存来源、盘点单位|最近变化；
2. **消耗趋势（→改名库存变化）**：周期 | 变化量，按周期分行；
3. **盘点与入库历史（→改名盘点与库存增加历史）**：来源 | 原因 | 变化前 | 变化量 | 变化后 | 时间；
4. **关联商品与扣减规则**：来源层级 | 来源对象 | 每份消耗 | 扣减时机——
   实见「商品 | 番茄罗勒意面 / PASTA-TOMATO-BASIL-001 | 120 克」等三行；
5. **变化记录**：业务化的流水明细，**普通门店用户可见**；
6. **高级诊断**：幂等键、水位、执行行等，**仅有诊断权限时渲染**。

**第 5、6 两块是本轮补回的**（源码实证：`sales-inventory-status` 下
「变化记录」出现 3 次、「高级诊断」出现 5 次）。
两者的区别是**可见性**而不只是文案：**第 6 块对普通用户直接不渲染**，
不是"换一套业务化说法给所有人看"。这与 §5.7.7 第 6 条的降噪要求是同一件事的两面。

**第 4 块是全域设计最好的一处**：站在物料上反查**谁在消耗我、每份多少、什么时机扣**。
它回答的是运营者真会问的「这个料为什么在掉」，而 BOM 正向配置永远回答不了。**必须保留。**

### 5.7.6 全局交互 —— 保留

- **dirty 关闭守卫**：居中 Modal「关闭商品详情？/ 未保存的商品资料将丢失。确认关闭商品详情抽屉吗？」
  + 「继续编辑」「放弃并关闭」（后者为主按钮）。v2s foundation 已有同形能力。
- **保存成功入草稿态**，不是直接启用；徽章体系：草稿 / 正常 / 手工维护（来源）/ 形态。
- **缺失项用软徽章提示而不阻断**：「缺少商品图片」「2 个 SKU 缺价」「未分类」。

### 5.7.7 必须改的（v4 做得不好或不适合 v2s）

1. **基础资料页签的校验反馈太粗**。v4 保存失败是顶部红条「商品保存失败，请检查后重试」
   **不指明字段** + 字段标红，用户得自己找红框。
   **而 v4 自己在点单选项页签已经做到了具体原因**（「启用分组至少需要一个可用选项」）——
   说明它是实现不一致，不是设计取舍。
   **v2s 统一按细颗粒度做**：首错摘要 + 页签级错误计数 + 字段级定位。
2. **商品级标准价硬必填不应无条件复刻**。按形态的 `priceGranularity` 决定激活校验（§4 O-03）。
3. **「怎么看」帮助入口**：需要一屏帮助说明，通常意味着信息架构不够自解释。
   **v2s 先尝试把状态语义做直观**，而不是照搬一个帮助弹窗。
4. **「增量入库」改称「库存增加」**，避免供应链单据暗示（§2.1）。
5. **「需处理」只是工作台派生视图**，不进领域状态枚举（§2.1）。
6. **高级诊断降噪**：幂等键、水位、执行行这些留在授权诊断区，
   门店日常看到的是业务化的变化记录（Codex §7.2 建议，采纳）。
7. **多图能力升级**：v4 商品图片是单图，v2s 要多图有序 + 主图标记（DR-3）。

### 5.7.8 不搬的

- **Excel 批量导入/导出**（商品库顶部「导入商品」「导出当前筛选」，以及库存现状页的「导出库存现状」）
  ——本期未证明这些用户任务；
  且与「从总公司复制」同名会混淆（§5.6.4 命名提示）。
- **「菜单与渠道」「套餐引用」两列**——06 不在本期，展示会造出不存在的事实；
  但**反查思想保留**（§5.7.1 末）。
- **形态派生后又允许手改 `itemKind` / 能力的重复控件**——v4 本身就是只读的，
  不要在 v2s 反而放开（§5.2 已定）。
- **v4 卡片/列表视图切换**——本期只做列表，卡片视图未证明用户任务。

## 5.9 与 v6 的差异登记 —— **本次决策为唯一需求真相**

> Dexter 2026-08-06：「凡是我们现在决策与 v6 有差异的地方，
> 你都重点标注**以此次决策为唯一需求真相**。」

以下每一条都**与 v6 领域文档不同**。实现、评审、后续设计**一律以本文为准**，
v6 相应条款在本域**不再适用**。凡有人引用 v6 原文与本表冲突，以本表为准。

### D-01｜商品处理标签的作用域

- **v6 §4（13 域）**：`ProductionTagDefinition` 带 `projectRef` + 可选 `storeRef`，
  作用域 `scope = PROJECT_DEFAULT | STORE_OVERRIDE`。
- **本次决策**：**总公司+品牌 与 门店 两级，不设项目级**；`scope` 这组取值**取消**。
  门店持有自己的定义（自建或复制而来），**不是"覆盖"总公司**。
- **依据**：v4 活环境实测标签维护在门店 scope 下；Dexter 裁定门店级。

### D-02｜总公司持有真实的库存对象与 BOM

- **v6 §2.3**：总部商品库只能维护"库存控制规则模板和 BOM 规则模板"，
  「**不产生实际库存对象、余额、库存流水或门店实际 BOM**」。
- **本次决策**：总公司持有**真实的 `StockTarget` 与 `ProductBom` 实体**，
  只是**没有 `StockBalance` 与 `StockChangeLedger`**，也没有盘点/增加/调整。
  **不新增任何"模板"类实体。**
- **风险仍被排除**：v6 那条真正要防的是"总部跨店共享库存"，
  而本形态下总公司的库存对象**永远没有余额、永远不参与扣减**。

### D-03｜owner 统一表达推广到全模型

- **v6 §4.1**：只对 `ProductCatalog` 规定了 `headCompanyRef + brandRef` / `storeRef + brandRef`。
- **本次决策**：**同一形态推广到商品、商品处理标签、库存对象、BOM 及全部被引用字典**
  （`ownerType` + `ownerRef` + 必填 `brandRef`）。
- **推论**：门店**只有其唯一品牌对应的一套 owner 数据**（`organization.store.brand_id` 是 NOT NULL 单值）；
  多品牌只发生在总公司获得多个品牌授权的场景。复制来源由 `brandRef` 天然确定。

### D-04｜`SalesStockView` 不建表

- **v6 §4.9 + §10**：`SalesStockView` 是独立对象，并列入起步期数据表建议清单。
- **本次决策**：库存提示是**余额的派生读**，**不建表**（承 v1 拍板）。
- **依据**：v4 建了此表却零消费者，派生读天然不产生断链。

### D-05｜`PreparationProfile` 折入商品结构 JSON

- **v6 §4.13**：`PreparationProfile` 是独立对象。
- **本次决策**：生产提示（预估时长、制作说明）**折入商品/SKU/选项值各自的结构 JSON**；
  **商品处理标签本身仍是 typed ref，不得降成 JSON 字符串**（承 v1 step4 修正版）。

### D-06｜库存权威降为库存对象上的字段

- **v6 §4.5**：`InventoryAuthorityConfig` 是独立实体，含门店默认 + 对象覆盖、失败处理模式等。
- **本次决策**：降为 `StockTarget` 上的 `authorityType` 字段，**默认且仅 INTERNAL**；
  外部 ERP 与权益服务权威**整体延后**（承 v1 Q4）。

### D-07｜商品描述属性是自由 map，不做 schema

- **v6 §4.5**：`CatalogAttributeDefinition` 是可维护的属性定义实体。
- **本次决策**：`CatalogItem.attributes_json` **自由 map、纯展示、不校验**
  （承 v1 Q2 + Dexter 2026-08-05 裁定）。**需要筛选的属性不进 map**，走商品标签。
- **这是本域唯一允许的裸 map**，必须作为显式例外声明，不得成为先例。

### D-08｜点单选项是每商品内联，不建共享字典

- **v6 §4.10**：`OptionGroup` / `OptionValue` 是可跨商品复用的结构。
- **本次决策**：**per-item typed JSON**，不建跨商品共享选项库（承 v1 D-5）。
- **依据**：v4 活环境实测「点单选项」页签为每商品内联新建分组，**无任何跨商品引用入口**。

### D-09｜外部库存权威整体不做

- **v6 §3.2 / §3.3 / §4.8**：外部 ERP 与内部权益服务作为库存权威，含调用审计、覆盖水位、失败处理。
- **本次决策**：**本期只做内部轻库存**，不建外部适配、不建调用审计表（承 v1 Q4）。

### D-10｜库存对象不能脱离商品单独创建

- **v6 §4.1 规则 3**：库存对象可由「独立库存控制、库存初始化导入或**受控库存对象维护流程**」创建——
  措辞允许存在独立维护入口。
- **本次决策（以 v4 为准）**：**不允许脱离商品的独立创建入口**；
  合法路径有两条——商品详情「库存与 BOM」页签内配置，
  或**经差异预检确认的总公司复制**随商品带过来（§5.6.3）。
  被禁止的是**隐式创建**（BOM 行引用组件时静默生成组件库存对象）。
- **依据**：v4 实证 `CREATE_STOCK_TARGET` 从未被调用。

### D-11｜"消耗"改为"库存变化"（v4 差异，非 v6）

- **v4**：库存对象详情有"消耗趋势"、列表有"消耗"列。
  **v6-07 只定义库存变化流水，并没有"消耗趋势"这一指标**——
  所以这是一条 **v4 UI 改造，不是 v6 差异**（此前归类有误，本轮更正）。
- **本次决策**：本期**改为"库存变化"**，展示真实的流水聚合（盘点、增加、人工调整）；
  真正的销售消耗待交易域接入后另加。
- **限定**：**"不出现消耗字样"只针对原来的销售消耗指标**，
  **不波及**"消耗单位""BOM 消耗""每份消耗"这些正确且必须保留的领域用词。

### D-13｜商品形态是持久化的 source fact

- **v6-05 §4.8**：明写「`shapeKey`、页面模板或前端选项**不是 source fact**；
  SKU 管理策略才是商品目录 source fact」。
- **本次决策**：**形态入库，且作为契约约定前后端能力**（Dexter 2026-08-05 裁定）。
  形态决定 `itemKind` / `measureMode` / `usageCapabilities` / `skuMode` 的派生、页签集、
  字段可见性与必填、库存节点准入；创建后固定，配了下游事实即锁。
- **影响分母**：契约、数据库列、前后端生成物三处都因此改变。

### D-13b｜能力由形态精确派生且只读，取消能力变更行为

- **v6-05**：`usageCapabilities[]` 是可独立维护的能力集合，
  §8.2 明确提供 `ChangeCatalogItemUsageCapabilities(command)`，
  §8.2 约束 8 还规定该命令须校验生命周期、治理状态与已有引用。
- **本次决策**：**能力由形态精确派生，创建与编辑态一律只读**（照搬 v4），
  **取消 `ChangeCatalogItemUsageCapabilities` 这类能力变更命令**。
  要改变意图就改建成另一个形态，而形态创建后固定——即**意图在创建时一次性确定**。
- **影响分母**：命令清单少一组；商品编辑面少一个可写字段；
  v6 §8.2 约束 8 与 §8.9 的 `CatalogCapabilityConflictDetected` 治理信号在本域失去触发源。

### D-13c｜规范编码成为复制判同的一等事实

- **v6-05**：商品的店内编码归 `ProductIdentifier(identifierType=INTERNAL_CODE)`，
  是识别码之一而非商品自身字段；`CatalogCategory`、`CatalogTag`、`SalesUnit`
  的字段概念中**都没有规定编码**。
- **本次决策**：商品、分类、标签、销售单位、SKU 销售属性与属性值、SKU、
  商品处理标签、库存对象**各自拥有稳定编码字段**，
  且**编码是跨 owner 复制的判同依据**（§5.6.3）。
- **依据**：v4 实证每类对象都有编码并在 UI 上"名称 / 编码"成对展示。
- **配套要求**：唯一约束建议为 `ownerType + ownerRef + brandRef + 编码`；
  SKU、属性值等子对象再叠加父对象范围。
  **编码创建后可否修改需在契约设计时定死**——它同时是判同键，改了会让下次复制误判。
- **影响分母**：数据库唯一约束、契约字段、复制判同三处都依赖它。

### D-14｜删除 `MATERIAL_OF` / `PACKAGING_OF` 两类商品关系

- **v6-05 §4.12**：`CatalogItemRelation.relationType` 明确保留
  `SUBSTITUTE | SIMILAR | MATERIAL_OF | PACKAGING_OF | BENEFIT_SHELL_OF | REPORTING_GROUP | MANUAL_LINK`。
- **本次决策**：**删去 `MATERIAL_OF` 与 `PACKAGING_OF`**，其余五类保留。
- **理由**：BOM 已完整表达"消耗什么、每份多少、正负、合并顺序"，
  关系再说一遍信息量严格更少且语义重复，两者不一致时无从判断谁对（§5.5.2 重判二）。
- **影响分母**：枚举取值由 7 减为 5。

### D-15｜扣减/恢复只建表，不建创建与执行能力

- **v6-07 §5.1**：把 `CreateStockDeductionPlan`、`ExecuteStockDeductionPlan`、
  `CreateStockRestorePlan`、`ExecuteStockRestorePlan` 定义为**本域 command 能力**。
- **本次决策**：四张表按"模型必须完整"建全，
  但**本期不建计划创建与执行逻辑，也不暴露对应 command 与 API**（interface-reserved）。
- **理由**：触发方（订单、履约）不在本期范围；建了无调用者的 command 会让契约面说谎。
- **影响分母**：命令与 API 清单少四组；数据库表不少。

### D-16｜商品复制的结构兼容包含 SKU 结构指纹

- **v6-05**：定义商品、SKU 与 SKU 属性语义，但没有定义跨 owner 复制时同编码商品的结构兼容算法。
- **本次决策**：商品的结构判别位除商品形态外，再包含稳定的 SKU 结构指纹：按 `skuCode` 排序，
  每个 SKU 绑定排序后的 `(attributeCode,valueCode)` 组合；任一不一致即结构阻断。
- **理由**：只比较商品形态会把来源 `SKU-001=小杯` 误映射到目标 `SKU-001=大杯`，继而把 14 克等
  SKU 级 BOM 静默挂到错误规格。该风险与“10 克改写成 10 个”同属数量语义静默损坏。
- **边界**：SKU 结构指纹不是第十类兼容对象，不改变 SKU 的 canonical matching tuple，也不沿反向引用
  扩张复制闭包；它只是九类矩阵中“商品”这一行的第二个结构判别位。
- **影响分母**：预检 compatibility、商品 structural negative fixture、复制执行复核与 digest 必须使用同一算法。

### D-12｜架构表达（v1 差异，非 v6，一并登记）

v1 的微服务、MQ、事件驱动扣减、分库分表假设**全部不继承**。
v2s 是单业务 deployable、单 PostgreSQL、多 owner schema、单 Flyway history；
跨 owner 写调用目标 owner 的公开 command 并加入同一 `REQUIRED` 事务，不建 MQ/outbox。

### M2 已由证据消解，不需裁决

我原以为 v6 §4.8 与 §4.9 冲突。再查发现 **§4.8 结尾定义了术语**——
「按 SKU 管理商品……它通常落在 `CatalogItemSkuPolicy(skuMode=REQUIRED_MATRIX)`」，
所以 §4.9 里的"按 SKU 管理商品"**就是指强矩阵**，两处说的是同一件事。

**v4 契约的形态派生独立印证**（我从 generated manifest 解析）：

```
普通销售商品      STANDARD_SALE_COUNTED      skuMode=OPTIONAL_TABLE   price=ITEM
按 SKU 管理商品   SKU_VARIANT_SALE_COUNTED   skuMode=REQUIRED_MATRIX  price=SKU
称重销售商品      STANDARD_SALE_WEIGHED      skuMode=OPTIONAL_TABLE   price=ITEM
原材料/半成品/包装物 MATERIAL                   skuMode=NONE             price=ITEM
商品型套餐        COMPOSITE                  skuMode=OPTIONAL_TABLE   price=ITEM
服务/费用商品     SERVICE                    skuMode=NONE             price=ITEM
权益商品壳        BENEFIT_SHELL              skuMode=NONE             price=ITEM
```

而 v4 活环境里**普通销售商品有「点单选项」页签、按 SKU 管理商品没有**——
即 `OPTIONAL_TABLE` 与点单选项**共存**，只有 `REQUIRED_MATRIX` 排斥它。
规范与实现一致，**O-02 采 A 是事实而非判断**。

**附带收获**：上表的 `priceGranularity` 也独立印证了 O-03——
v4 契约本身就按形态决定价格粒度，不是"商品级价无条件硬必填"。
**这张表应整体进 v2s 的形态契约。**
