# 终端规则模型：记录与覆盖分析

> **本稿性质**：讨论用分析稿，**不是需求稿**。记录 Dexter 2026-09-23 提出的终端规则模型，并对照 `2026-09-23-v2s-terminal-function-print-mapping-claude.md`（下称**对应稿**）的业务模型检查覆盖。
> **会话出处**：续接会话，Claude 主 agent 自行分析，未经独立盲审。
> **证据档位**：`【厂商文档】`本会话亲验 · `【推论】`。
> **本稿只讨论规则，不讨论实现。**

## 1 · 模型记录（Dexter 原述，结构化）

### 1.1 终端

| 属性 | 定义 |
|---|---|
| 是什么 | **服务一个点位的功能集合**。不是物理设备，但安装在物理设备上 |
| 名称 | 用户自起，如「前台收银机」「热厨 KDS」 |
| 设备类型 | 二选一：台式（laptop）/ 手持（mobile） |
| 功能集合 | 从 6 个功能中选一个或多个，自由组合 |
| 打印机 | 可定义 N 台 |

### 1.2 功能

| 功能 | 支持的设备类型 | 每个终端可有几个 | 范围 |
|---|---|---|---|
| 点餐收银 | 台式、手持 | 0 或 1 | **桌台**（树形选择，最终落在桌台） |
| 接单确认 | 台式、手持 | 0 或 1 | **桌台 + 外卖**（外卖是一个选项，不区分平台——外卖的特点是没有桌台） |
| KDS | **仅台式** | 0 或 1 | **生产标签** |
| 厨打 | 台式、手持 | **N 个** | **生产标签** |
| 出餐 | **仅台式** | 0 或 1 | **桌台 + 外卖** |
| 排队叫号 | 台式、手持 | 0 或 1 | 无 |

- **新建终端第一步选设备类型**，之后只能选该设备类型支持的功能。
- **生产标签**在商品域定义；每个商品属于 0 或 1 个生产标签（如冷厨、热厨、水吧）。

### 1.3 打印机

| 属性 | 取值 |
|---|---|
| 连接方式 | USB、蓝牙、网口、云端；各自带详细参数（网口→IP，云端→ID） |
| 打印纸类型 | 热敏（宽 58mm、80mm）；标签（40×30、40×60、50×30、60×40、80×50……，在 contract 中维护） |

### 1.4 打印场景与打印机的绑定

1. 终端选定功能后，列出这些功能的全部打印场景，用户可全选或选部分。
2. 每个打印场景声明自己支持的打印纸类型（如压桌单支持热敏 58 / 80，标签制作联支持各种标签尺寸）。
3. 选中一个场景后，从本终端的 N 台打印机里**按打印纸类型匹配**挑选，**不看连接方式**。
4. 每个场景可选**多台打印机作主备，数量不限**；打印时遇故障自动切换到下一台重试。

## 4 · 发现的问题

### M1 · 模型只说了"终端**能**打什么"，没说"一件事发生时**哪台**终端打"

**现象**：同一个桌台可以同时落在多台终端的范围里。模型没有规定打印事件怎么找到终端，于是有两种读法，各有一种错：

| 读法 | 含义 | 错在哪 |
|---|---|---|
| **本机打** | 谁操作，谁打 | 服务员的手持机不带打印机时，预结单就打不出来 |
| **按范围打** | 所有范围覆盖这张桌、选了这个场景的终端都打 | 大厅 3 台手持 + 前台 1 台都覆盖 A3、都选了预结单——服务员在一台手持上点预结，**4 台一起出纸** |

**根因**：「范围」这个词在不同功能里其实是两种意思——
- **点餐收银的范围**是"这台终端**能操作**哪些桌"（权限）；
- **厨打、KDS、出餐的范围**是"哪些菜 / 哪些单**会被送到**这台终端"（路由）。

模型用同一个词表达了两件事。

**建议方向**：
1. 按功能区分派发方式：**点餐收银、排队叫号＝本机打**（操作发生在哪台就在哪台出）；**厨打、KDS、出餐＝按范围打**（菜和单被送到范围覆盖的终端）。
2. 对"按范围打"的功能，**要有重叠规则，而且要按场景定**：
   - **制作单不允许重叠**——同一个生产标签落在两个厨打里，就是同一道菜做两遍。美团就是这么管的：主收银选了后厨档口 A，副收银再选时「**不可选择后厨档口 A，显示置灰状态**」`【厂商文档】`；这也和 Dexter 之前的裁定"一个非套餐菜品只对应一个档口"一致。
   - **划菜总单允许重叠**——多层店里出品口出一张全场的、楼层传菜口出一张本层的，这是有意为之（对应稿 §5.4）。

**需要 Dexter 裁决**：派发方式按上面分，是否成立；以及"手持机没带打印机时，点餐收银的纸去哪"。

### M2 · 「没有桌台」不等于「外卖」

**现象**：模型的范围选项是"桌台 + 外卖"，前提是"外卖的特点是没有桌台"。这句话正着说是对的，**反过来不成立**——快餐堂食（凭取餐号）、自提、外带，都没有桌台，但都不是外卖。

**影响**：
- **取餐单**（对应稿点餐收银的一张）服务的正是快餐和自提——它们没有桌台，也不属于外卖，在现在的范围里无处落位。
- **快餐的取餐叫号**归出餐（对应稿裁定 4），但出餐的范围只有桌台和外卖，快餐单路由不到任何出餐终端。
- **厂商也把自提和外卖分开**：美团的出餐二维码「结账单支持店内下单、手机点餐、**自提**叫号出餐；**外卖商家联 / 顾客联**支持自营外卖叫号出餐」`【厂商文档】`——自提用结账单，外卖用外卖两联，两者出不同的纸。

**建议方向**：范围里再加一个选项，例如「**无桌台**」（覆盖快餐、自提、外带），与「外卖」并列。「外卖」内部仍不区分平台，这一点不变。

**需要 Dexter 裁决**：是否要覆盖快餐和自提。若当前只做中餐正餐，可以先不加，但要在模型里写明这个边界。

### S1 · 缺份数

每个场景在每台终端上打几份，模型里没有。三家都有：美团可以设「**不打印或打印 1–3 份**」，场景例子就是「结账单需要打两份，不打印客单」`【厂商文档】`。
**建议**：场景与终端的绑定上加「份数」。

### S2 · 只有厨打能加 N 个，出餐也需要

**现象**：银豹的多层店配置是「二楼的打印机只勾选二楼区域，三楼的打印机只勾选三楼区域」`【厂商文档】`——由一台主机驱动两台按楼层分开的传菜口打印机。在本模型里，这要求一台终端上有两个出餐（范围分别是二楼、三楼），但出餐只能有 0 或 1 个。
**原因**：与厨打需要 N 个的道理完全相同——**一台终端要按范围把纸分到不同打印机上**时，就需要多个实例。厨打按生产标签分，出餐按楼层分。
**建议方向**：二选一——出餐也允许 N 个；或者允许一台物理设备上装多个终端（见 N4）。

### S3 · 缺切单方式

制作单是一单一张、一道菜一张，还是按分类一张；套餐的子菜是合一张还是各一张——三家都在打印档口上配这件事。美团：「打印方式：可选择**整单打印**……或者**分单打印**（同一批次下单的菜品可一菜一切或者按分类切单）」，另有「**套餐切单方式**」`【厂商文档】`。
对应稿里这已被定为制作单的"切单方式"（裁定 12），但本模型没有地方挂它。
**建议**：挂在厨打实例上（每个厨打实例各自决定怎么切）。

### S4 · 打印机的连接方式缺「内置」，纸型缺「针式」

- **内置**：三家都有内置打印机（POS 一体机、手持机）。美团排队原话「可通过连接**内置打印机**或蓝牙打印机实现」`【厂商文档】`。手持机上的点餐收银、排队叫号大多用内置打印机。
- **针式**：美团明确提到商家在用，并且给了一条**规则级的约束**——「**针式打印机打印出来的一维码不支持识别**，商家需要使用热敏打印机打印小票」`【厂商文档】`。
  - 这意味着：**带扫码用途的场景只能用热敏**。外卖商家联 / 顾客联上的「出餐二维码」要被出餐宝扫描（对应稿 §1.4），它们的纸型必须限定为热敏。现在的"场景声明支持的纸型"机制正好能表达这条约束——前提是纸型里先有针式这一类。
  - 针式常用宽度，三家文档里未见。

### N1 · 出餐仅台式，但桌边划菜在手持上

对应稿 §5.2 ③：大厅、包房的"出餐尾段"是服务员在手持机上把菜标记为已上——掌上客如云「选择【桌台】→在菜品上往左滑动→点击【上菜】」`【厂商文档】`。它不出纸，所以不影响打印，但按本模型，手持机上不能有出餐。需要决定：桌边划菜算点餐收银的一部分，还是出餐允许手持。

### N2 · 传菜单的美团做法表达不了

美团的传菜单是「**制作完成后**自动打印传菜单，开启后需配置 **KDS 打印机**」——由做完菜的那台 KDS 自己出，只出它做完的菜。本模型里传菜单属于出餐，出餐的范围是桌台，没法表达"只出这台 KDS 做完的菜"。
能表达的是另一种做法：**出品口的出餐终端统一出所有传菜单**。选这一种即可，但要知道和美团不同。

### N3 · 同一台物理打印机被两个终端定义

打印机是按终端定义的。若同一台网口打印机（同一 IP）在两个终端里都被定义并选中同一场景，就会重复出单——美团《为什么打印机重复出单》的首要原因就是「**同一个打印机 IP 地址添加多次**」`【厂商文档】`。需要决定：一台物理打印机是否只能归一个终端。

### N4 · 终端与物理设备的对应关系没定

"终端安装在物理设备上"——一台设备能装几个终端，一个终端能装在几台设备上，模型没说。这会影响 S2 的解法，也会影响 N3。

### N5 · 所有打印机都失败时怎么办

主备全部失败时的规则没有。v4 / v6 有 `failurePolicy`：只提示 / 记录后继续 / 阻断本地流程 `【v4代码】`。例如杯贴打不出来时是否允许继续出杯。本次只讨论规则，这属于规则层。

### N6 · 厨打只按生产标签分，两种少见情况表达不了

- **外卖专线**：同一个生产标签，堂食送 A 厨房、外卖送 B 厨房。美团的后厨出品档口可以分别勾选「店内菜品 / 美团外卖菜品 / 饿了么外卖菜品」`【厂商文档】`，所以能做到；本模型的厨打范围只有生产标签，做不到。
- **分层独立厨房**：同一道菜 1 楼的单送 1 楼厨房、2 楼的单送 2 楼厨房（全景稿 §5.6 讨论过，属少数）。

这两种都少见，可以先不支持，但要写明边界。

## 5 · 做得好的地方

| 设计 | 为什么对 |
|---|---|
| 终端＝功能集合，不是设备 | 与厂商做法一致：美团 KDS「配菜、制作、传菜……支持单选也可以多选」；客如云收银机可开排队模块，另有专用排队手持 `【厂商文档】` |
| 按设备类型限制可选功能 | 简单有效；KDS、出餐需要大屏，放在手持上没有意义 |
| **范围按两个维度分：桌台（区域）与生产标签（商品）** | 正是全景稿 §5.6 得出的结论——**档口回答"这道菜谁做"，按商品收敛；传菜口回答"送去哪"，按区域收敛**。本模型把点餐收银、接单确认、出餐放在桌台维度，把厨打、KDS 放在生产标签维度，两条轴完全正交 |
| 生产标签在商品域定义，每个商品 0 或 1 个 | 与 Dexter 的裁定"一个非套餐菜品只对应一个档口"一致；也与刚完成的 ProductionTagDefinition 迁入 catalog、以及 catalog 的「商品级最多一个生产标签」事实一致 |
| 打印机按纸型匹配，不看连接方式 | 把"纸对不对"和"线怎么接"分开，干净 |
| 主备不限数量、故障自动切换 | 与客如云一致：「多个后厨网口打印机可**互为备用**」，主机「连接异常或状态异常（缺纸、开盖）时系统重试 1 分钟后将自动切换至备用打印机出票」`【厂商文档】` |
| 厨打可 N 个 | 见 §2，这是一台主机驱动多台厨打机的必要条件 |

## 7 · 第一轮处置（Dexter 2026-09-23）

### 7.1 建模范围（Dexter 裁定）

本次建模**只定义终端的能力、范围、路由规则、硬件**。具体场景的业务规则（如打印机全坏了怎么办）与打印规则（如打几份、怎么切单）是后续的事，**不在本范围**。

### 7.3 关于多层出餐与"终端装在哪台设备上"

每层一个出餐终端，最自然的部署是**每层传菜口一台台式设备**——出餐本来就仅限台式，传菜口通常本来就有屏。这样不需要回答"一台设备能否装多个终端"。

只有当有人想**用一台主机带多层的打印机**（银豹那种）时，才需要回答它。那时要注意：v6 的定义是「安装本平台 app、能激活并与 TCP / TDP 建连的主机型设备才是终端」，而本模型把终端定义为"服务一个点位的功能集合，不是物理设备"——**一台设备装多个终端，意味着激活与建连的单位从设备变成了终端**，会牵动终端控制面。建议届时单独讨论，不在本轮。

同理，厨打可以挂 N 个而出餐只能 0/1，这种不对称是合理的：**常见情况给便利**（小店一台 POS 带热厨、冷厨、水吧三台打印机，极其普遍），**少见情况用多终端**（多层店每层一台）。

### 7.4 打印机共用之后，重复出纸只剩一个来源

打印机允许共用后，"同一台打印机被定义两次"本身不再是问题。点餐收银是谁操作谁打，也不会重复。**剩下唯一的重复来源是路由范围重叠**：

- 两台终端上的厨打都覆盖了「热厨」，又都绑了同一台（或各自一台）打印机——热厨的制作单就会出两次，**同一道菜做两遍**。

这正是美团《为什么打印机重复出单》排第一的原因在本模型里的样子，也是美团 5.14 做"主收银选了档口 A，副收银再选时 A 置灰不可选"的原因 `【厂商文档】`。它属于**路由规则**，在本次建模范围内。

### 7.6 模型总原则：硬约束与软约束（Dexter 2026-09-23 裁定）

> **约束分为硬约束和软约束。**
> - **硬约束**：什么功能支持什么终端设备类型、什么打印场景支持什么打印纸类型……这些都是硬约束，**必须在 contract 中明确定义**。
> - **软约束**：例如同一个生产标签挂在两个厨打下面，由**规则管理人自己调优**。
> - 规则尽量灵活：合理的规则配出合理的做法，不合理的规则配出不合理的做法；觉得不合适，修改规则即可。

（Dexter 确认：指「**什么功能支持什么设备类型**」，例如 KDS 功能肯定不支持手持。）

#### 7.6.1 contract 中要定义的硬约束全集

| # | 登记对象 | 要声明的属性 | 来源 |
|---|---|---|---|
| H1 | **功能**（6 个） | 支持的设备类型；每个终端可有几个（0/1 或 N）；范围类型；下属打印场景 | §1.2、7.2 M1、M2 |
| H2 | **打印场景** | 所属功能；支持的纸型 | §1.4 |
| H3 | **纸型** | 热敏 58 / 80；标签 40×30、40×60、50×30、60×40、80×50…… | §1.3（Dexter：「可在 contract 中维护」） |
| H4 | **连接方式** | USB、蓝牙、网口、云端、内置；各自的参数项（网口→IP，云端→ID……） | §1.3、7.2 S4 |
| H5 | **设备类型** | 台式、手持 | §1.1 |
| H6 | **范围类型** | 桌台（树形）、无桌台、外卖、生产标签、无 | §1.2、7.2 M2 |
| H7 | **订单类型清单** | 堂食、外卖、外带——**只定义有哪些**，不约束场景与订单类型的关联 | 7.6.2 |

**软约束（规则管理人配置，不拦截）**：终端名称；选哪种设备类型；勾哪些功能；范围取哪些值（具体哪些桌、哪些生产标签）；范围是否重叠；勾哪些打印场景；**每个场景支持哪些订单类型**；定义哪些打印机及连接参数；场景挂哪些打印机、主备顺序；打印机是否被多个终端共用。

**先例**：v4 就是这么做的——`contracts/registry/print-scenes.json` 为每个场景声明 `supportedPaperProfiles`、`compatiblePrinterCapabilityRefs`，另有 `print-paper-profiles.json`、`tcp-printer-capability-definitions.json`；v6 也写明「printScene 是固定、可穷举、可版本化的 contract 常量」`【v4代码】【v6设计】`。

#### 7.6.2 打印场景 ↔ 订单类型：是配置，不是硬约束（Dexter 裁定）

**问题的来源**：出品口的出餐终端范围是「全部桌台 + 外卖」，勾了划菜总单与外卖商家联——来一张堂食单，外卖商家联要不要打？来一张外卖单，划菜总单要不要打？

**Dexter 裁定**：场景与订单类型的关联**不在 contract 里约束**。配置用户选中一个场景后，**再选它要支持哪些订单类型**。能否正常工作由用户自己调整。

- **订单类型的取值**：堂食、外卖、外带（Dexter 裁定）。这份**清单**作为可选项登记在 contract（H7），与纸型清单同理；**场景选哪些**是配置。

| 场景 | 参考：常见的订单类型 |
|---|---|

| 取餐单 | 堂食、外带 |
| 配送单、外卖商家联、外卖顾客联 | 外卖 |

#### 7.6.3 没有"派发"：每台终端按自己的配置决定打不打（Dexter 裁定）

**撤回**：此前提出的「出纸终端」（原称"派发方式"）属性。它隐含了"由一个中心决定哪台终端来打"，而本模型没有这个中心。

**本模型的做法**：TDP 把服务器端的实时数据推送给所有终端，**谁想处理谁处理**——每台终端按自己的"功能 × 范围 × 勾选的场景 × 下挂的打印机"决定这张纸打不打。Dexter 给出的四种情况：

| # | 终端配置 | 下单后 |
|---|---|---|
| 1 | 服务员手持：内置打印机 ＋ 开单功能 ＋ **勾了客单** | 打出客单 |
| 2 | 服务员手持：内置打印机 ＋ 开单功能 ＋ **没勾客单** | 不打客单 |
| 3 | 服务员手持：远端打印机 ＋ **厨打功能** ＋ 勾了制作单 | 手持也收到订单拆出的工作单，调用厨打打出制作单 |
| 4 | 服务员手持**不配厨打**；KDS：打印机 ＋ 厨打 ＋ 勾了制作单 | 工作单经 TDP 推到 KDS，KDS 发现它在自己的厨打范围内，打出制作单 |

**与 v6 完全一致**：「TDP……**不向打印机投递任何数据，也不下发业务打印命令**」；「**所有业务打印动作都由终端业务逻辑发起**。终端基于业务任务或业务状态、打印规则快照、模板资源和 `TerminalPrinterConfig`，在本地渲染并调用打印机」；「TDP 没有"打印命令 topic"」`【v6设计】`。

**为什么大厅 4 台终端不会一起打客单**（M1 的原例子）：各功能的打印由什么引起，本来就不同——点餐收银的纸由**本机上发生的动作**引起（在这台终端上开单、预结、结账），厨打和出餐的纸由**推送过来、落在自己范围里的数据**引起（工作单、出餐状态）。这是每个场景自身的含义，**不需要另设属性**。

#### 7.6.4 范围不调整（Dexter 裁定）

**撤回**此前"把范围与订单类型对齐为 桌台 ＋ 堂食（无桌台）＋ 外带 ＋ 外卖"的建议。范围保持 M2 处置后的样子：**桌台（树形）＋ 无桌台 ＋ 外卖**（点餐收银、接单确认、出餐）；生产标签（厨打、KDS）；无（排队叫号）。

范围回答"哪些单会到这台终端"，订单类型回答"这个场景对哪类单打印"——两者是两条独立的轴，由管理员组合配置。

#### 7.6.5 业态不进入规则（Dexter 裁定）

茶饮、快餐、中餐、西餐等**业务属性不体现在规则中**——配置管理员按实际情况配置，属于软约束。硬约束里只出现订单类型、桌台、生产标签、设备类型、纸型等**订单与硬件的事实**，不出现业态。

例：预结单适用于堂食是硬约束；"快餐店的堂食要不要打预结单"是管理员勾不勾，属软约束。此前以业态提问（"预结单对快餐有没有意义"）的问法本身不成立，已按订单类型改写。
