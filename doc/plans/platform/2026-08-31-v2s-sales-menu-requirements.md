## 1. 目标

让门店拥有一份**属于自己的、可编排、可发布、可落到具体经营入口**的销售菜单,
并让需要由本系统自行维护菜单的堂食、外带内部经营渠道拿到各自的有效销售视图。

**这一版的价值命题是「把菜单这件事的真相建起来并真的被入口消费」**,
不是「做一个菜单管理页面」。

## 2. 销售菜单是什么

### 2.1 定位

`[v6 §1]` 销售菜单回答「**这些商品在门店哪个经营入口、什么时候、以什么销售视图被卖**」。

它**不回答**:商品本体是什么、会员价多少、真实库存剩多少、终端是否已拿到菜单、订单是否成立。

### 2.2 仓内已定的业务语言(G-11,`DEXTER_ACCEPTED`)

> 菜单是面向门店渠道绑定的销售集合:商品**显式编入、不可换绑**销售项 → 版本
>(草稿可改、发布冻结)→ 发布 → 门店渠道启用,才成为入口可售内容。
> 发布不等于 TDP ACK、POS 展示或外部同步成功;沽清/限售走独立可售控制,不改写菜单事实。
> 价格层:标准价 → 集合挂牌价 → SKU 挂牌价 → 营销权益价 → 支付实付。
> `ProductCatalog`、`CatalogCategory`、`SalesSection` 三义严格区分。

**本文不重新论证菜单是什么,只界定 v2s 当前阶段做到哪一步。**

### 2.3 必须区分的三类混淆

`[v7 01.业务分析/03]`

**混淆一 · 商品是什么 vs 哪些商品在哪个入口/时间可卖**

判据:**改这条事实,会不会改变别的门店看到的东西?**
会 → 商品目录;不会 → 销售菜单。
`[v6 不变量 3/5/6]` 销售集合**只引用不复制**商品定义;商品分类 ≠ 销售分区;商品标准价 ≠ 挂牌价覆盖。

**混淆二 · 菜单发布成功 vs 终端已拿到菜单**

`[v6 §0/不变量 10]` 发布成功**只表示**版本校验通过、快照生成、写入本域 outbox。
终端投递、POS 展示、外部同步成功**都是可见性诊断,不进入发布状态机**。
`[v4]` 该区分在真实验收中被证明有用户价值,且 v4 的发布证据**明确没有**证明真实终端应用与外部平台连接。

**混淆三 · 不同发布路线不是同一种投影**

`[v6 §9.10]` 外部平台有三条路径(内部发布到外部 / 外部导入为草稿 / 订单倒逼修复),
与终端数据平面投影机制不同。本版仅做内部发布产出快照(见 §7 P-02)。

## 3. 用户与任务

### 3.1 总公司 / 品牌运营不是菜单用户

- `[裁定]` 品牌和总公司不创建、不编辑、不发布菜单，也不向门店提供参考菜单或菜单复制来源。
- 总公司仍可维护品牌侧商品信息/资料模板；门店从自己的可用商品中独立编排门店菜单。
- 要求门店整改属于运营治理，**不是菜单能力，也不得借此恢复品牌菜单功能**。

### 3.2 门店运营
- 只卖自己卖的那部分商品与规格。
- 不同入口卖不同内容(扫码点餐藏掉部分菜品,POS 全有)。
- 按时段卖(早/午/晚餐;未设时段的全天可售)。
- 同商品不同商圈不同价。
- 今天这个卖完了 —— 人工估清,并能明确恢复。
- 合同还没生效,先把菜单准备好。

### 3.3 内部渠道的消费方(POS / 扫码 / 自助机 / 自营外卖)

`[裁定]` 本批只做 `access_kind=INTERNAL` 且 `order_kind ∈ (DINE_IN, TAKEAWAY)` 的渠道,
**菜单不区分入口形态** —— 下面的任务对这几类入口是同一份。

- 拿到**当前这个渠道下的有效菜单**(可能有多份,各带自己的时段)。
- 菜单里每个销售项:卖什么(引用哪个商品/规格)、叫什么、多少钱、在哪个分区、什么顺序。
- 每个销售项的**两个可售维度事实**(库存驱动、人工估清),**各自返回不合并**,
  由该渠道自己组合成对客展示。
- 销售项级的下单约束(起售量、订购倍数),由该渠道在下单时执行。

⚠️ **本批不提供按入口形态区分的动作能力**(可展示 / 可加购 / 可提交 / 需店员协助)。
理由见 §4.3:菜单不区分入口形态。若未来确有"同一销售项在扫码不可提交、在 POS 可以"
的真实业务诉求,再单独重开需求。

### 3.5 发布结果与终端可见性的边界

`[v6 §9.14]`「为什么收银端看不到我刚发布的商品」确有一条跨 owner 排查链路，
但 `[裁定 · Dexter 2026-08-31]` **本批菜单页不建设第 2–6 步诊断面板，也不从操作记录进入诊断抽屉**。
该界面对门店日常编排属于过度设计。

本批只要求两件事：

- 发布结果使用准确文案，说明本系统已经生成前台菜单，不声称终端已获取；
- 第 2–6 步所需的普通事实分别留在已有任务面：草稿/前台菜单、菜单生效与时段、前台菜单的库存状态与销售状态；不再把它们重复拼成诊断链路；
- 操作记录只记录何时、谁、对哪份菜单做了什么以及结果，不承担诊断工作台职责。
- `[Dexter 2026-09-01 裁定]` 按经营入口查看操作记录时，同时展示该菜单的菜单级记录（`channel_ref IS NULL`）与所选经营入口的渠道级记录；菜单级操作影响菜单整体，因此在各经营入口记录中均可见。本批不另建菜单级操作记录入口。

需要继续定位第 7 步终端获取与应用时，留待终端消费与跨 owner 可观测能力具备后再设计；
不能因为本批没有诊断界面，就把“发布成功”改写成“终端已经可见”。

## 4. 需求条目

### 4.1 菜单编排

| 需求 | 说明 |
| --- | --- |
| 门店拥有自己的菜单 | 一个门店可有多份菜单,不能拿商品库或渠道列表冒充 |
| 版本与发布冻结 | `[仓内 G-11]` 草稿可改、发布冻结。门店要能在不影响营业中菜单的前提下准备下一版,并知道当前发布的是哪版 |
| 销售分区 | `[v6 不变量 5]` 与商品分类严格区分。⚠️ `[v4 坑]` **不得用「全部/未分区/智能视图」等虚拟节点污染真实销售分区** —— 筛选视图与经营结构必须分开 |
| 销售项 | `[仓内 G-11]` 商品**显式编入、不可换绑**。同一商品可被重复编入多个销售项，既可位于不同菜单或不同分区，也可在同一分区重复出现；每个销售项独立选择销售规格、展示、价格和顺序 |
| 规格收窄 | 只卖部分规格。`[v6 不变量 8]` **商品目录新增规格不自动进入已发布菜单**。选择方式必须随商品形态变化；无规格商品不得出现虚假的规格选择 |
| 基础挂牌价覆盖 | `[Dexter 2026-09-01 对 v2s 的产品收窄]` 无规格商品在销售项公共区维护挂牌价；按规格管理商品不使用公共挂牌价，改为对每个已开放规格分别维护 SKU 菜单挂牌价。两种形态都对照各自商品默认价，不扩展为价格引擎 |
| 展示覆盖 | 门店可覆盖该销售项在本菜单中的展示名与图(如商品叫「美式咖啡(冰)」,菜单上叫「冰美式」);未覆盖时使用商品目录中的默认展示名与图。图片覆盖的操作与商品图片编辑一致，支持上传和排序；本批只开放这两项覆盖,推荐位、营养/过敏原等编排后置 |
| 从商品库批量加入 | `[v4 已验证有效]` |

### 4.2 时段与多菜单

`[裁定 · Dexter 2026-08-31]` **做。一个渠道下可以有多个生效的菜单,可以设置菜单的时段。
如何判断如何使用,那是渠道的事情** —— 渠道拿到多个菜单自己做逻辑。

| 需求 | 说明 |
| --- | --- |
| 菜单可设时段 | 时段是**菜单自身的属性**,随菜单发布与冻结 |
| 一个入口多份生效菜单 | **一等需求**。渠道与菜单**不是一对一** |
| 菜单域不解析"此刻用哪一份" | ⚠️ **菜单域不提供「现在生效的是哪一份」这个查询。** 任何人要求它提供,就是把渠道的职责挪进来了 |

⚠️ `[v4 坑]` v4 初期**只加载第一份菜单,把多菜单和时段压成单菜单**,用户误以为另一个菜单不存在。
**这不是理论风险,是 v4 实际栽过的地方。**

⚠️ `[v4 坑]` v4 曾**把菜单启用的主语放在版本**而不是菜单与经营入口,导致「当前哪份菜单生效」难以解释。
**启用的主语是(菜单, 经营入口)。**

`[v6 决策 4]` 起步期**不做叠加合并器**(把多份合成一份)—— 与"一个入口多份生效菜单"是两件事,不要混。

### 4.3 落到经营入口

| 需求 | 说明 |
| --- | --- |
| 菜单启用到门店经营入口 | `[仓内 G-11]`「门店渠道启用才成为入口可售内容」。这是菜单与渠道之间**唯一**的连接点。`[裁定]` 本批只挂 `access_kind=INTERNAL` 且 `order_kind ∈ (DINE_IN, TAKEAWAY)` 的渠道 |
| 只支持门店级入口 | `[裁定]` **当前不做项目级菜单**。`[仓内]` v2s 的渠道 `target_node_type` 允许 PROJECT 与 STORE,遇到项目级入口应**明确拒绝并给出可解释原因**,不静默忽略。措辞用「当前不做」而非「不支持」 |
| 入口动作能力 | **后置。** `[裁定]` 菜单不区分入口形态(POS / 扫码 / 自助机同属内部渠道),因此不为形态差异建模。见 §7 `P-01` |

⚠️ **术语错位警告(合并稿必须保留)**

`[v6]` 把菜单目标说成 `businessChannelBindingRef`。`[仓内 实测]` v2s 的层级**整体错开一级**:

```
v6 的 BusinessChannel        ≈ v2s 的 business_channel_template(项目级模板)
v6 的 BusinessChannelBinding ≈ v2s 的 business_channel(带 target_node_type + target_node_ref)
v2s 的 business_channel.binding_ref ≈ 外部平台授权绑定(v6 里归外部协作与防腐域)
```

**菜单启用的目标是 v2s 的 `business_channel`(渠道实例)。**
`[仓内 实测]` `INTERNAL` 渠道不得设置 `binding_ref`,由 `BusinessChannelPolicy` 的 owner
业务策略与命令路径保证,**不是数据库 CHECK**;`DINE_IN` 必为 `INTERNAL` 也由 owner 策略保证。
`[推论]` 若只看到本批渠道的 `binding_ref` 恒为空,设计者可能误以为 v2s 缺少
`BusinessChannelBinding` 这一层并另造一层模型。真正的菜单目标已经是上述 `business_channel` 渠道实例。

### 4.4 发布

| 需求 | 说明 |
| --- | --- |
| 发布动作 | 把草稿变成已确认的销售结果 |
| 发布快照 | `[v6 不变量 4]` 发布版本不可直接修改,必须有冻结物;出现争议时能解释当时发布了什么 |
| 有效销售视图 | `[v6 不变量 24]` **发布阶段持久化生成**,不是每次下单现场合并 |
| 发布与生效的区分 | 门店必须能区分「内部已发布」与各入口「已应用」。`[v4 已验证]` 该区分有真实用户价值 |
| 失败定位 | 用户要知道失败发生在发布前还是下游。⚠️ `[v4 坑]` **通用「成功」文案掩盖了到底完成了发布、对应还是同步** |

### 4.5 可售状态:两个维度,不合并

`[裁定 · Dexter 2026-08-31]`「一个是本身菜单商品的**库存状态**,库存不够**自动**就不可售了;
另一个是**手动对某个渠道的销售项做估清不可售**,是人工行为。**两个维度都应该支持。**」

`[推论]` 这两个维度正好落在 `[v6 §4.12]` `SalesAvailabilityControl` 的两个格子上
(`controlKind=INVENTORY_SOLD_OUT_HINT` + `targetType=CATALOG_ITEM`,
与 `controlKind=MANUAL_STATUS` + `targetType=SALES_ITEM` + 渠道范围)。
`[v4]` v4 只实现了后者,且**丢掉了渠道维度**(表里只有 `store_id`)。

**维度一 · 库存驱动(自动,商品/SKU 级,全渠道)**

- 真相在库存侧,**菜单项读取而不持有**。
- 适用面由**库存对象是否存在**决定:`[仓内]` `stock_target` 是按商品/SKU 显式建立的;
  `[仓内 G-12]`「无 BOM 不阻断销售」。**没有库存对象的商品,本维度不适用,永不阻断。**
- `[推论]` 这正是 `[仓内 G-12]`「库存提示必须显式转为可售控制」要的那个"显式" ——
  显式性在于「该商品被显式纳入库存管理」,不是每次缺货都要人再点一次。
- **不需要恢复动作**:它是**派生**的,库存回来即回来。
- `[裁定]` **「库存不够」的判据**:**缺货**不可售;**低库存**仍可售(是提示不是阻断);
  **负库存**取决于该库存对象的负库存开关;**未知**不阻断(不能因读不到就拦住卖)。
- ⚠️ `[仓内 G-12]`「不得由缺货推**菜单下架**」仍成立且不冲突:本维度让菜单项显示为**不可售**,
  **不是把它从菜单移除**。`[v6 §4.12]` 的 `OFF_SHELF` 与 `SOLD_OUT` 也是两个状态。

**维度二 · 人工估清(手动,销售项 + 渠道级)**

- 真相在菜单域,目标是销售项。
- 粒度到 **(销售项, 经营入口)**:可以只在扫码点餐估清,POS 照卖。
  采纳 `[v6]` 的渠道维度,**不采纳 `[v4]` 的省略** —— v4 省掉渠道是实现取舍,不是业务结论。
- **必须显式恢复**:`[v6 不变量 26]` 不因退菜或退款自动恢复。
  `[v4 值得借鉴]` 用独立的 `RESTORE` 控制类型落地,而不是"把估清删掉"。
- **必须留原因**:`[v4 值得借鉴]` `control_reason NOT NULL` ——
  估清是对客不可售,没有原因无法解释也无法治理。
- `[裁定]` **不再做商品级人工沽清**。商品级的"没了"已由维度一表达;
  要全渠道停售,用批量估清其全部销售项表达。

**两个维度不合并成一个"可售"布尔**

`[仓内 已裁]` `project-memory/decisions/owner-read-model-and-lifecycle-standard.md`
的 assertion `CASCADE_STATUS_IS_DERIVED_NOT_STORED` 规定:「对象只存自身状态,owner 把每个维度的状态
**各自作为事实返回**,⛔ 不合并成一个值」。
菜单项读模型返回**两个独立事实**,**由渠道自己组合**成对客展示 ——
与 §4.2「如何使用是渠道的事情」同一条原则。

`[推论]` 合并的坏处很具体:门店看到"不可售"却不知道是**缺货**还是**被人估清了**,
处理动作完全不同;且「库存回来了但人工估清还在」这种真实状态表达不出来。

**恢复不对称是自然结果,不是特例**:派生维度无存储 → 无需恢复;存储维度是人的决定 → 必须人撤销。
`[推论]` v4 之所以需要 `RESTORE`,是因为它把两个维度都做成了存储控制;
把库存维度改成派生后,这个不对称自动消失。

### 4.6 销售项级下单约束

`[裁定 P-04=B]` 开放**与单个销售项直接相关**的约束,初始闭集固定为**起售量**与**订购倍数**。
低消、开台必点、服务费提示等**整单 / 桌台级**约束后置。

`[裁定 · Dexter 2026-08-31]`「下单约束分两段,一段是**约束规则**,一段是**约束执行**。
销售菜单定义的是**销售规则**,POS 端、小程序端定义的是**约束执行**,
不可能把所有的渠道终端都开发好了之后再开发约束规则。」

**这条同时纠正了本文早先的一个判断错误。** 早先版本以「v2s 无交易域、起售量存下来无人执行」
为由建议整体后置。该论证不成立,反例是**挂牌价**:挂牌价同样由交易域在下单时执行,
但没有人会因此说"等交易域建好再做价格"。**因为价格是销售规则,不是下游服务。**
起售量与挂牌价是同一类事实。

`[推论]` **判据应当是「这是谁的规则」,不是「谁来执行」:**

> 属于"这东西**怎么卖**"的事实 → 菜单域定义,即使执行方尚未存在;
> 属于"**执行时如何校验、如何留痕**"的事实 → 终端与交易域,不进本域。

**为什么整单 / 桌台级仍然后置**:低消按桌、开台必点依赖开台会话 ——
它们需要**菜单之外的概念**(桌台、会话)才能表达,不是"执行方没建好",
而是**规则本身的主语不是销售项**。`[v6 §9.9 分流]` 亦把桌台与开台会话归 `02/11`。

#### 约束清单的承载机制(Dexter 2026-08-31 裁定)

`[裁定]`「在 contract 里定义好这个清单,然后销售项里用 JSON 把这个内容保存和展示,
销售端也会按 contract 里的内容做解析。**不用过度设计做成复杂的规则版本和数据版本等**,
所有端都用**最新的 contract 定义**去解析,即使销售项里面的数据是老的也没关系,
**使用端能解析出哪条就用哪条**。」

**这条把"有限清单"放到了正确的地方**:清单的正本在**契约**,不在需求文档。
需求只给初始成员,以后增减由契约管。

**机制要求**:

1. **契约声明闭集**。约束类型的有限清单由契约定义。
   `[仓内]` 与后台编码规范 **1-O**「代码定义的闭集必须在契约里声明为 enum」一致 ——
   声明为 enum 后,前端字典可从生成的联合类型派生,新增成员时前端编译不过直到补上文案。
2. **销售项用 JSON 承载**。JSON 的键就是契约声明的那些,不是自由字段包。
   `[仓内]` 该形态是仓内既有模式(`catalog_item.attributes` / `sections`、
   `stock_bom.rows`、`extension_definition.definitions` 均为 JSONB),不新造轮子。
3. **不做规则版本与数据版本**。所有端按最新契约解析。
4. **宽容解析**:解析得出哪条就用哪条;老数据里没有的键,当作未设置;
   从未进入受支持契约的未知键不能触发销售约束。
5. **约束键有退役生命周期,但没有版本。** 一个已发布的键停止使用时,先停止新配置;
   已有销售项中的该键继续由所有受支持消费方按冻结语义解析。只有确认存量数据已经清零、且没有受支持消费方
   继续依赖后,才允许从契约中物理移除。整个过程不引入版本号、不保留新旧双解析路径、也不按消费方分支。

⚠️ **使"不做版本"安全的唯一前提 —— 键的语义一经发布不可改变。**

`[推论]` 宽容解析有一个失败模式必须挡住:若某个键的**含义**变了
(例如 `minQuantity` 从"份"改成"克"),而键名不变,所有端会用新语义去解释老数据,
**静默算错且无人报错**。因此:
**新增语义必须用新键;旧键只能停用,不能改义。** 这条是"不做版本"的代价对冲,
不写死就会在第一次语义调整时出问题。

**初始成员(已由 Dexter 2026-08-31 裁定)**:

| 键 | 业务含义 | v6 对应 |
| --- | --- | --- |
| 起售量 | 该销售项最少买几份 | `MIN_ITEM_QUANTITY` |
| 订购倍数 | 必须按几份的倍数买 | `QUANTITY_STEP` |

后续若调整成员,属于契约变更,不构成需求返工;已发布键仍须遵守上面的冻结语义与退役生命周期。

`[推论]` v6 §4.13 同节其余五项(`MIN_ORDER_AMOUNT`、`TABLE_MIN_SPEND`、
`REQUIRED_ITEM_SELECTION`、`SERVICE_FEE_HINT`、`ORDER_BEFORE_TABLE_REQUIRED`)
主语都不是销售项,不在本清单内(理由见上文整单/桌台级的后置说明)。

**发布冻结与本机制并存**:`[仓内 G-11]` 发布冻结 —— 销售项的约束 JSON 随快照冻结;
消费端用最新契约解析被冻结的老 JSON,正是本裁定描述的形态。

## 5. 本能力不负责什么

`[v6 §0/§6/不变量 20–22]`

1. **商品本体** —— 归商品目录。
2. **真实库存** —— 余额、扣减、流水归库存域。
3. **会员价、活动价、券后价** —— 只保留基础挂牌价覆盖。
4. **终端投递** —— 不调用终端、小程序、外卖平台或外部菜单 API。
   `[v6 不变量 22]` 外部同步回执、TDP ACK、终端菜单可见**都不能反向改**发布快照或可售控制。
5. **外部平台对象映射** —— `[裁定 P-02=A]` 本版不开放平台商品对应、外部导入或出站同步。
   已有外部经营渠道只作边界事实,**不能由此推导菜单已在平台生效**。
   ⚠️ `[v4 已验证]` 外部对象对应应保留在**外部协作主语**下,不因页面入口相邻就变成商品或菜单事实。
6. **交易成立性** —— `[v6 不变量 15]` 合同未生效不阻止菜单准备,阻止真实交易的是交易域结合合同资格。
7. **权益是否适用** —— 本域不判断"这个货号是否享受权益"。
8. **多集合叠加合并器** —— `[v6 决策 4]` 起步期不做。
9. **合同货号** —— `[裁定 P-05=C]` 本版不提供。长期归属冲突见 §9。
10. **团购与外部平台的商品对应** —— `[裁定]` 它们的维护逻辑是**做对应关系**,不是维护菜单;
    `[v4 已验证]` 应保留在外部协作主语下,不因页面入口相邻就变成菜单事实。
11. **「现在生效的是哪一份菜单」** —— 见 §4.2,那是渠道的职责。
12. **按入口形态区分的动作能力** —— `[裁定]` 菜单不区分入口形态。见 §4.3。
13. **品牌/总公司菜单** —— `[裁定]` 本系统只有门店菜单；不提供品牌参考菜单、参考版本、门店复制菜单或品牌菜单发布。

**本期范围外但非永久边界**(措辞需区分,以免以后被当成推翻已定边界):
外部平台三条路径、整单/桌台级下单约束、每日/餐段限售、超售确认、项目级菜单。

## 10. v4 教训清单(防再犯)

`[v4]` 以下为 v4 真实踩过的坑,本版需求应逐条避免:

1. **只加载第一份菜单,把多菜单和时段压成单菜单** → 用户误以为另一个菜单不存在。(对应 §4.2)
2. **把菜单启用的主语放在版本**而不是菜单与经营入口 → 「当前哪份菜单生效」难以解释。(对应 §4.2)
3. **用虚拟节点污染真实销售分区** → 用户分不清筛选视图与经营结构。(对应 §4.1)
4. **本地乐观排序未以服务端读回为准** → 页面顺序与实际发布顺序不一致。
5. **引用名称解析不完整时向用户暴露内部标识**;**通用「成功」文案**掩盖了完成的是发布、对应还是同步。(对应 §4.4)
6. **外部平台工作做成表格导入**,没有表达「平台当前事实 → 待对应 → 人工确认」的用户心智。

`[v4 已验证有效,应保留]`:多菜单、真实销售分区、批量从商品库加入菜单、菜单时段、
发布状态、「内部发布成功但终端未生效」的区分、外部对象对应保留在外协主语下、旧入口退役作为完成条件。
