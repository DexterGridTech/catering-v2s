## 0. 合格性判据

**每一条只能是两种状态之一:**

| 标记 | 含义 | 实施者做什么 |
|---|---|---|
| **`[已定]`** | 决定已下,给出可执行的目标形态 | **照做**,结果唯一 |
| **`[未定]`** | 决定未下 | **⛔ 不得改码**。按判定程序产出结论,回 Dexter |

**第三种合法状态**:`[已定 · 本轮不执行]` —— 目标形态已确定,但执行归后续批次。
与 `[未定]` 的区别是**决定已下**,后续批次直接照做,不必重新推导。

⛔ **不允许第四种** —— 看起来像指令、实际是没想清楚的描述。
**判别方法**:读完这一条,两个人做出来的东西一样吗?不一样即失格。

⚠️ 典型失格句式:「需求是真的,但走 X」·「逐个判」·「须先判定」·「二选一,实施者定」。

## 2. 执行规则

### 2.1 循环(七步,不跳步)

```text
① 取件  从 §5 总账取下一个「未开始」CP
② 前读  重开该 CP 的 owning source + 本文对应条 + 需求正本对应条
③ 核 BEFORE  逐字比对;不一致 → 停
④ 执行  只按 ACTION 动词做 AFTER 描述的事
⑤ 证据  按 PROOF 档位跑,留可打开的产物
⑥ 后读  用②的原文回读改动处
⑦ 回填  §5 总账填状态 + 证据路径 + 后读结论
```

### 2.2 定位与动词

**`LOCATE` 一律用方法签名或逐字锚点。⛔ 不用行号** —— 行号只进括号作参考。
多数 CP 会改变文件长度,用绝对行号指认自己即将移动的目标必然失效。

⛔ **禁用**:统一 · 优化 · 梳理 · 完善 · 处理 · 接入 · 增强 · 重构 · 清理 · 调整
✅ **只用**:`删除` · `新增` · `替换` · `移动` · `改值` · `重命名`

⚠️ 该仓 SQL 被 `palantir-java-format` 自动断行,三个 owner 的切点各不相同
(`"resp"+"onse"` / `"request_has"+"h,re"` / `"operation_i"+"d,re"`)
⇒ **以方法签名定位、逐字读当前源码,不得照抄本文引文**。

### 2.3 CP 字段

`[已定]` 类:`FILE / LOCATE / BEFORE / AFTER / ACTION / FORBID / INVARIANT / PROOF / DEPENDS`
`[未定]` 类(盘点):`产物 / 分母 / 覆盖范围 / 判定程序 / FORBID / PROOF`

**`FORBID` 必填** —— 写不出说明还没想清楚。

⚠️ **零动作条目**(标 `[已定 · 零动作]`):`FILE` 写「无」,`ACTION` 写「无(确认)」,
其余字段照填 —— **`PROOF` 仍必填**,确认也要有证据。

### 2.4 停止条件

BEFORE 对不上 · AFTER 照做后编译不过或既有测试变红且不在 FORBID 预告内 ·
文档写错 · 两 CP 冲突 · 涉及产品语义/Journey/用户可见行为 · 需要新增依赖

⛔ 不允许:自己选一个「合理的」做法继续 · 留 TODO 继续 · 缩小范围报完成 · 加兼容层绕过

⚠️ **前端 CP 的 BEFORE 会因 DEV 期修改而漂移**(2026-08-17 已发生一次:
Codex 按 Dexter 的 DEV 体验改了 8 个 catalog 前端文件,`CP-11` 的六处正则站点全部消失)。
⇒ 凡 `FILE` 落在 `apps/frontend/**` 的 CP,**取件时先重取 BEFORE**:
  BEFORE 对不上且改动方向合理 ⇒ 按「源码已变」处理,**重取后继续**并在总账记录;
  BEFORE 对不上且改动方向可疑 ⇒ 才按停止条件 1 停。
⛔ 后台与迁移类 CP **不适用**本条,它们的 BEFORE 对不上一律停。

### 2.5 证据四档

`0 编译` · `1 静态门` · `2 focused 测试` · `3 行为测试(真实 HTTP/容器)`

⛔ 禁止下移。产物必须可被第三方打开。
✅ **`reset` / `seed` 是现阶段常规操作**(Dexter 2026-08-17 明确):该做就做,**不需要单独授权**。
focused Testcontainers 同样实施者可自取。

### 2.6 全局禁止

⛔ 新增第三方依赖(**唯一例外**:foundation 加 `spring-boot-starter-jdbc`,见 CP-01)
⛔ 为「未来可能需要」预留配置或扩展点
⛔ 向后兼容层 / fallback / 迁移期双写 —— 无业务数据,每次 reset + seed
⛔ 修改 `terminal-data-server` · 修改 Heritage 仓
⛔ runtime/测试的目录、包、文件、类名出现 Journey ID
⛔ 引入 MQ / 通用 outbox / 内部 OpenAPI client / 常态轮询
⛔ 记录 password/hash · OTP · token · cookie · Authorization · 手机号 · 登录名 · 原始 IP · raw payload

## 3. `[已定]` 变更点

### 3.1 背景:两个缺陷,严重度差一个量级

**缺陷 A(今天每次重放都 500,不需要并发)** — `ExtensionCommandReceiptService`:
`@Transactional` 方法内 INSERT 无 `ON CONFLICT`,冲突抛 `DuplicateKeyException`,
`catch` 之后在**同一个已 abort 的事务**里 SELECT。PG 语句报错即事务 abort(后续查询一律 `25P02`)
⇒ **重放分支实际不可达**。

**缺陷 B(要并发才坏)** — 三个 owner 的私有 `replay()`:
`SELECT ... FOR UPDATE` 后 `if (rows.isEmpty()) return null;`。
首用时结果集为空 ⇒ **`FOR UPDATE` 一行都没锁到**
(PG `explicit-locking.html` §13.3.2:锁的是 "the rows **retrieved**")。

**分母 22 个入口**:catalog 8(`replayTyped` 357/398/688/736 + `replay` 452/1018/1425/1713)·
inventory 8(212/249/285/321/1689/1723 + 633/717)· production 5(145/172/199 + 385/565)· extension 1。
全仓 12 个 `command_receipt` owning source,另外 8 个均已 lock-first 或 insert-as-claim。

**机制:advisory lock 放进私有 `replay()` 内。** 仓内先例是 C4 的第 450 行取锁 → 第 452 行 replay,
本设计把它从调用点下沉到 `replay()` 内部,一次覆盖 22 个入口 ⇒ **调用点零改动**。

| 判据 | **本方案** | insert-as-claim | advisory lock 在 21 个调用点 |
|---|---|---|---|
| 调用点改动 | **0** | 0 | 21 |
| DDL / 新列 | **零** | 迁移 + `state` 列 + `response` 可空 + 2 条 CHECK | 零 |
| 返回契约 | **不变** | 需三态 | 不变 |
| 新错误码 | **不需要** | 需要(全仓 0 命中,须过整条契约链) | 不需要 |
| 无事务时 | 锁失效,退化成无保护。⚠️ **但 CP-05 删 catalog 的 `ON CONFLICT` 会让该路径从「静默吞掉」变成「抛异常」** ⇒ 必须配 CP-18 | **claim 行永久残留 ⇒ 该幂等键永久 500** | 同左 |
| 仓内先例 | **有** | 只有注释,零并发测试 | 有 |

**第四候选「锁 scope 父行」**:更便宜,但把同 scope 的所有命令串行化 —— 否决理由恰是本项目目标。

⚠️ 本方案**确实引入一把持续整条命令时长的行锁**。死锁结论(穷举验证):
除三个 owner 的 `replay()`/`saveReceipt()` 外无路径触碰这三张表 ⇒ 无死锁。
连接池压力是新的:C4 最多 100 item 各占一条连接、外层一条、被阻塞者一条。

**无事务路径:生产侧本轮修掉,测试侧登记**

⚠️ 上一版判「本轮不修、不构成回归」是**错的** —— `CP-05` 删掉 catalog 的 `ON CONFLICT` 之后,
无事务路径上的重复写入从「静默吞掉」变成「抛 `DuplicateKeyException`」。
`transitionCatalogItemStatuses` 是**生产代码**且无 `@Transactional` ⇒ 这是一条生产路径。
⇒ 新增 `CP-18` 给它补 `@Transactional`(一行),把生产侧的洞堵上;
两个便捷构造器与 34 处裸 `JdbcTemplate` 测试是测试侧,登记 `HANDOFF.md`。

**原文(测试侧部分仍成立)**:`CatalogOwnerService` 两个便捷构造器传 `transactions = null`,
两处 `if (transactions == null)` 退化;`transitionCatalogItemStatuses` 无 `@Transactional`;
三个 owner 的测试共 34 处裸 `JdbcTemplate` ⇒ Spring 代理失效。
这些路径上 `xact` 锁语句结束即释放。**不构成回归**(今天同样无保护),生产路径安全。
⇒ 进 `HANDOFF.md`。

### CP-04 · 三个 `replay()` 加锁并去掉无效的 `FOR UPDATE` `[已定]`

```text
FILE      CatalogOwnerService · InventoryOwnerService · ProductionTagOwnerService
LOCATE    方法签名 private JsonNode replay(...)
BEFORE    三处方法体首条语句均为
          jdbc.query("SELECT operation_id,request_hash,response::text FROM
                      <schema>.command_receipt WHERE ... FOR UPDATE", ...)
          ⚠️ 三处 SQL 字符串切点各不相同 ⇒ **以方法签名定位、逐字读当前源码**
AFTER     ① 方法体第一条语句之前插入:
             AdvisoryLock.acquire(jdbc, "<owner>-receipt", <scopeArg>, <keyArg>);
             namespace 取 "catalog-receipt" / "inventory-receipt" / "production-receipt";
             实参用该方法已有的两个形参(catalog 是 dataNodeRef/key;另两处是 scope/key)
          ② SELECT 去掉 FOR UPDATE(缺行锁无效,锁已由 ① 提供)
          ③ 其余逐字不变
ACTION    新增 + 删除
FORBID    ⛔ 不得改方法签名、返回类型、任何既有分支
          ⛔ 不得在三处各写一份 SQL —— 用 CP-01 的共享工具
          ⛔ 不得保留 FOR UPDATE 作「双保险」—— 对不存在的行无效,留着让人误以为有保护
INVARIANT ① 返回值语义逐字节不变(有回执返回 response,无回执返回 null)
          ② IDEMPOTENCY_MISMATCH 的触发条件与响应逐字不变
          ③ 事务传播行为不变
PROOF     档 2:CP-06 的三个并发测试类
DEPENDS   CP-01
```

**去掉 `FOR UPDATE` 的行为分析**:READ COMMITTED 下它对已存在且已提交的回执行只多做一次行锁,
replay 之后无语句依赖它(`saveReceipt` 是 INSERT 不是 UPDATE);
advisory lock 提供更早、且覆盖缺行的串行点。**仅当锁与业务写同事务时成立**(见 §3.1 无事务路径)。
