## 2 · 收口说明

### 2.1 厨打：不属于"标注"的反例

退菜单、催菜单、起菜单：都发生在制作单**已经打出之后**，内容是对已下单菜品的动作通知，不是"做这些菜"；三家都做成独立票。它们保持独立场景。

### 2.2 反结账与退款：是两件事，但只有一种纸

| | 反结账 | 退款（美团叫「退单」） |
|---|---|---|
| **本质** | **状态事件**：把已结的账**重新打开**，改完再结一次 | **金钱事件**：把钱**退回**给顾客 |
| 美团原话 | 「把原本已经结帐完毕的帐单**重新恢复到结帐前的状态**」 | 「将菜品全部退掉且**退回所有支付方式**」 |
| 能干什么 | 退菜、加菜、换菜、换结账方式、退回多收的钱——退款只是其中一种 | 整单退、部分退菜 |
| 钱怎么动 | 「仅操作退菜，**不会自动退款**，只有在右侧支付方式后点击"撤销"，才会退款」；改完必须平账（实收＝应收）才能重新结账 | 直接原路退回 |
| 订单结局 | 重新结账，出一张**新的结账单** | 订单标「**已退单**」 |
| 打什么纸 | **没有自己的纸**——重新结账时出的是结账单 | **退单小票**（可选再出后厨退菜单） |

**两家对这两个词的用法是反的**：银豹的「反结账」恰恰是美团的「退单」——「直接反结账则**整单退货，单据作废**」；银豹那种"打开重改"的操作叫「**作废并复用**」（作废原单，把商品重新加进购物车再下单）。

**厂商里只有一种纸**：银豹的反结账小票、美团的退单小票，都是「钱退回去了」的凭证，即退款小票；美团的「打开重改」本身不出纸，结果是一张新的结账单。

**Dexter 裁定两者分开（裁定 16）**：反结账与退款是不同的业务动作，各自出纸。因为厂商没有「打开重改」意义上的票据先例，反结账单的内容要由 v2s 自己定，且必须**与结账单、退款小票都不重叠**——它记录的是**一次对已结账单的更正**：原结账单号、反结账原因（美团要求必选）、操作人与时间、改动前后的应收 / 实收差额。重新结账后另出的新结账单仍是结账单，不是反结账单。

两个旁证：
- 美团把两者当兄弟操作管：同一组设置「结账 24 小时后 / 7 天后 / 交班后 / 跨营业日**不允许反结账 / 退单**」「选择对应设置后可对反结账、退单**同时生效**」`【厂商文档】`。
- 退单打不打后厨退菜单是**可选的**——菜已经上桌吃完了，就没必要通知厨房。这说明"退菜"有两层意思：**上菜前**的退菜是厨打的事（停止制作，出退菜单）；**结账后**的退菜只是账上不收钱，不出厨房的纸。

## 5 · 中餐全场景：点位 × 功能 × 纸

> 输入：Dexter 2026-09-23 提出的六个点位（前台、大厅、包房、后厨档口、出品口、外卖点）。本节核对它是否成立、是否漏了功能。

### 5.1 结论

**布局基本成立，补三处；"出品"没有漏纸，漏的是点位。**

- **划菜总单、传菜单这两张纸本来就在清单里**（归出餐）——它们正是出品口的纸：划菜员在出品口拿总单逐道核对，传菜员在出品口拿传菜单出发。
- **但本稿从没说过它们在哪个点位出**。Dexter 的布局把出餐放在大厅、包房、外卖点，出品口没有任何功能——这就把问题暴露出来了。
- **建议不新增功能，由出品口承载出餐**，理由见 5.3。

### 5.2 补三处

| # | 补什么 | 依据 |
|---|---|---|
| ① | **排队等号没有点位**——通常在门口迎宾台，也可以直接放在前台 | 客如云：收银机本身可开排队模块，另有专用排队手持 `【厂商文档】` |
| ② | **吧台 / 水吧没有列出**——它是厨打的点位（出酒水饮品、杯贴），但物理上常在前厅 | 银豹按分类厨打的例子就是「小吃、煮食、冷菜和**酒水**分工明确」`【厂商文档】`；「酒水饮料则需另开一份订单交吧台」`【外部】` |
| ③ | **大厅、包房里的"出餐"只是尾段**：服务员上菜、在桌边划菜（标记已上菜），**不出纸** | 掌上客如云「将菜品标记为已经上菜……选择【桌台】→在菜品上往左滑动→点击【上菜】」；美团点餐助手「自动同步 KDS 菜品的划菜状态」`【厂商文档】` |
| ④ | **楼层传菜口 / 备餐间（多层或大型店才有）**——出品口在厨房，菜经传菜梯送到各层，每层有自己的交接点；它**出本层的整单** | 银豹「二楼和三楼都有传菜口……二楼的订单，就只会在二楼的传菜口打印……传菜员各自负责自己的区域」，且「一单一切」`【厂商文档】`；多层酒楼「集中制作 + 分层交接」见全景稿 §5.6 `【外部】` |

**已核查、不是缺口**：海鲜池 / 活鲜三家零命中；称重菜在美团里是「麻辣烫、串串、海鲜等需要根据菜品或签子重量来计算价格的菜品」，做法是电子秤接在收银机上、点餐时读重量，**不出单独的纸** `【厂商文档】`——海鲜池只是点餐收银多接了一台秤，不是新点位。

### 5.3 为什么出品口承载出餐，而不是新增"出品"功能

1. **厂商把出品口做成一个设备角色，而且这个角色同时管叫号。** 客如云的「传菜设备」做的是单菜划菜、划单、叫号（「在传菜模式点击叫号」）；美团 KDS 的工序是「配菜 / 制作 / **传菜**」，传菜就是出品口那一段 `【厂商文档】`。
2. **出品口和外卖点干的是同一件事**：把一张订单从几个档口出来的菜**汇齐、核对、交给下一个人**——堂食交给传菜员，外卖交给骑手。区别只在交给谁。
3. **Dexter 已裁定"取餐叫号归出餐，不管出餐给谁"**（裁定 4）。若把出品口单列为"出品"，等于按去向（堂食 / 外卖）把出餐拆成两个功能，与这条裁定相反。

**若 Dexter 希望按岗位区分**（出品口是划菜员 / 传菜员，外卖点是打包 / 交接员），也可以拆成两个功能；代价是违背裁定 4，需要重新裁定。

### 5.4 完整点位表

| 点位 | 什么店才有 | 承载的功能 | 在这里出的纸 |
|---|---|---|---|
| 门口 / 迎宾台 | 有排队时；小店与前台合一 | 排队等号 | 排队号票 |
| 前台 | 都有 | 点餐收银、接单确认（外卖、自提、小程序） | 结账单、**反结账单**、退款小票、预结单（到前台付款时）、取餐单（快餐 / 自提时） |
| 大厅 | 都有 | 点餐收银、接单确认（本区扫码点单）、出餐尾段 | 客单、预结单、结账单、压桌单；出餐尾段不出纸 |
| 包房 | 有包房时 | 同大厅 | 同大厅 |
| 后厨档口 × N | 都有 | 厨打 | 制作单、退菜单、催菜单、起菜单 |
| 吧台 / 水吧 | 有酒水饮品时 | 厨打 | 制作单、标签制作联 / 杯贴 |
| 出品口 | 都有；小店与后厨合一 | 出餐（**所有菜在这里出厨房**；堂食在这里汇集、划菜） | 划菜总单（全场）、传菜单 |
| 楼层传菜口 / 备餐间 | **多层或大型店** | 出餐（本层汇集） | 划菜总单（本层） |
| 外卖点 | 有外卖且单设交接点时；小店与前台合一 | 出餐（外卖在这里汇集、核对、打包、交接） | 外卖商家联、外卖顾客联、配送单 |

> **外卖单经过出餐两次**（Dexter 2026-09-23 追问）：外卖的菜也从出品口出厨房，再传到外卖点。出品口对外卖订单只是**过路**——外卖不上桌，不需要划菜总单；真正的汇集与核对在外卖点做，用的就是外卖商家联（v4 自述其用途「帮助……打包和交接人员核对履约状态」）。所以外卖订单的纸都在外卖点出。若出品口启用了传菜单，它对外卖订单的作用是把菜送到外卖点，而不是送到某张桌。

**覆盖检查（逐项）**：点餐收银 7 个——客单、预结单、结账单、压桌单落在大厅 / 包房，结账单、反结账单、退款小票、预结单、取餐单落在前台；厨打 5 个落在后厨档口与吧台；出餐 5 个落在出品口、楼层传菜口与外卖点；排队 1 个落在门口。**18 / 18**。接单确认在三个点位承载、不出纸，与 §1.2 一致。

**最小店的样子**：一个柜台同时是迎宾台、前台、外卖点、出品口，后厨一个档口——还是这 5 个功能，只是全部落在两个点位上。

### 5.5 这个布局暴露的一个通用规律

**同一个功能会在多个点位上承载，每个点位只管一部分范围**：
- 接单确认：前台管外卖，大厅管本区扫码，包房管包房扫码——**按来源 / 区域分**；
- 出餐：出品口管堂食，外卖点管外卖——**按订单流向分**；
- 厨打：每个档口管自己的菜——**按商品分**（全景稿 §5.6–5.10）。

这就是厂商"档口 / 出票口"那一层在功能上的对应物。本节只指出规律，不展开路由设计。

## 6 · 假设分析：如果加上预订（宴会随之覆盖）

> **本节是假设，不改变 §0 的裁定 6（暂不管预订与宴会）**。
> **v11 重写**：v10 把"订单提前几天到"当成宴会的根本差异，是错的——那是**预订**的特征，普通中餐也有；而宴会甚至可以不预订。Dexter 2026-09-23 指出这一点，证据支持。

### 6.1 宴会与普通中餐：在功能和纸上没有本质区别

在 POS 这一层，**宴会＝预订 ＋ 联台 ＋ 套餐**，三样普通中餐都有：

| 看起来像宴会特有的 | 实际上 | 证据 |
|---|---|---|
| 提前预订 | 正餐也预订。美团「智能预订」是**同一个方案**服务两类商家：「为**正餐和宴会类**商家提供的，在预订环节提效降本的整体解决方案」；收银端两个入口【正餐预定】【宴会管理】展示同样的汇总（金额、桌数） | `【厂商文档】` |
| 订单先于客人到 | **宴会可以不预订**。美团宴会管理有「**立即开台**」，场景原话：「家里老人过生日，**临时决定**去店里吃个寿宴，一家十几个人要坐两桌，点两份长寿宴套餐」 | `【厂商文档】` |
| 多桌一起下单结账 | 联台不是宴会专属。客如云：联台「用于团餐集中下单、集中结账场景，例如**宴会、团建等**」 | `【厂商文档】` |
| 固定菜单 | 就是套餐；宴会套餐与普通套餐走同一套厨打逻辑（§1.3 的切单方式、标签规则已覆盖） | `【厂商文档】` |

**所以 v10 说的"餐前阶段"属于预订，不属于宴会。** 一旦纳入预订，正餐预订和宴会同时被覆盖；联台、套餐已在现有场景里（联台只改变预结单 / 结账单的合并范围，套餐已并入制作单的切单方式），不需要为宴会再加任何功能或纸。

### 6.2 真正剩下的差别：只在酒店宴会这个量级，而且不在 POS 里

| 纸 | 说明 |
|---|---|
| EO 单 / 宴会任务单 | 跨部门派工（厨房、宴会厅、工程、保安、财务、销售），A4，签批存档 `【外部】` |
| 宴会菜单 / 席卡 / 桌卡、台型图 / 桌次表 | 每桌摆放、摆台引导 `【外部】` |

**三家 POS 厂商都没有这类文书**——它们属于酒店宴会管理系统，是另一类产品，而不是餐厅 POS 里"宴会比正餐多出来的东西"。

另一个差别在**管理**而不在纸：美团的宴会预订有「接单人（负责人 / 提成人）」「添加宴会预定时支持选择连锁跨门店**销售员**」「订单明细表支持导出宴会类型和销售员」`【厂商文档】`——宴会是由销售卖出去、按人提成的。这影响报表和提成，不影响终端功能和打印。

### 6.3 所以真正要决定的是：要不要纳入「预订」

若纳入，变化如下（正餐与宴会同样适用）：

| 项 | 内容 | 证据 |
|---|---|---|
| **新功能：预订** | 建预订、锁桌台、收订金、短信确认；操作人是预订台或销售经理，设备可以是 POS、手机 APP、智能电话机 | 美团创建预订字段含摆台桌数、订金（在线支付）、接单人；操作「创建预订 / 预订并短信」`【厂商文档】` |
| 接单确认多一个来源 | 线上预订，可人工确认或自动接受 | 客如云「自动接受移动门店预订单」`【厂商文档】` |
| **新纸：预订单** | 预订凭证；功能＝预订 | 美团「智能预订台打印预订单」，有独立模板 `【厂商文档】` |
| **新纸：预订通知单（带位单）** | 餐前准备与带客入座；功能＝预订 | 美团：预订通知单「**用于后厨前台等做餐前准备工作，比如备菜、场地布置等**」，「打印带位单：仅 POS 端支持」`【厂商文档】` |
| 新点位：预订台 | 可与前台合一 | |

**预订通知单就是 EO 单在餐厅 POS 里的轻量版**：同样是"让各岗位据此做餐前准备"，一个是酒店多部门的 A4 工单，一个是餐厅的一张小票。纳入预订，就等于用餐厅的方式覆盖了 EO 单的核心职责。

**带位单与排队号票是一对**：都在迎宾处出，一个给订了位的客人，一个给临时来排队的。

### 6.4 未验证

- 美团「正餐预定」与「宴会管理」两个入口背后是否同一套数据模型，文档只显示两者汇总口径相同，未写内部差异。
- 宴会的起菜是否"按道次全场同时起"：客如云联台「在联台组内集中管理桌台菜品的增删」支持这个方向，但三家都没写具体做法；即便成立，它也是**联台**的行为（团建同样适用），不是宴会特有。`【推论】`
- 订金：美团的订金是在线支付，未见订金收据打印。
