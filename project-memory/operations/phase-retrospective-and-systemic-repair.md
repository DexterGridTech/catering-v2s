# Phase retrospective and systemic repair

- `SYSTEMIC_REPAIR_BEFORE_NEXT_PHASE`: 开发、测试或 Dexter 指出的可迁移问题必须在阶段结束前抽象为失败模式，扫描有限批准分母和同源上下文；下一阶段 preflight 必须把未关闭项转为 obligation，不能以局部修补代替系统性修复。
- `PHASE_RETROSPECTIVE_FINITE_DENOMINATOR`: 每项必须记录命中范围、根因层、`FIXED/ALREADY_CORRECT/NOT_APPLICABLE` 处置、设计规则、适用的机械 gate、fresh evidence 与 `MEMORY_DELTA`；反思状态不替代 business 或 cleanup closure。
- `PHASE_RETROSPECTIVE_R4_GATE_PENDING`: R4 前不复制 all-v2 `phase-retrospective` runner；R4 先按建门三问确定 v2s 原生、单 deployable 适用的最小 gate，并以真实 red mutation 证明，不通过不得把本 memory 当成已闭合门。
- `IDENTIFIED_FINDING_GENERALIZATION_REQUIRED`: 每个已确认的设计、实施、测试或验证问题在关闭前都必须形成不依赖具体文件名的通用失败模式、根因层、有限适用分母、反例边界与可复用最小解；局部代码修复本身不是完整关闭。
- `IDENTIFIED_FINDING_PREVENTION_DESTINATION_REQUIRED`: 每项必须落到 `PROJECT_MEMORY`、满足建门三问且有 production red mutation 的 `EXISTING_MACHINE_CONTROL`、`REVIEW_CHECKLIST` 或有具体反例的 `NOT_APPLICABLE_WITH_REASON`。implementation package exit 对已识别问题集合与预防处置集合做 set equality；hook 不伪造语义判断。
- `USER_REPORTED_PROBLEM_FAMILY_DISCOVERY_REQUIRED`: 用户点名的文件、字段、字符串或失败信号只是问题族入口。修改前必须给出通用根因、有限分母、检索面、同根命中、反例边界和 findings/prevention set equality；不得头疼医头、脚疼医脚。
- `PROBLEM_FAMILY_DENOMINATOR_BEFORE_FIX`: UserPromptSubmit 只落 prompt hash intake，PreToolUse 在源码修改前机械要求 disposition 与问题族证据存在，package-exit 枚举全部 intake。hook 不读 prompt 正文、不查询或注入上下文，也不宣称能判断语义穷尽。
- `EXECUTION_DEVIATION_ROOT_CAUSE_MEMORY_REQUIRED`: 不管执行偏差是由 Codex 自检、脚本或测试、独立 reviewer，还是 Dexter 指出，只要确认存在偏差，就必须先重新打开 `AGENTS.md`、六维路由命中的项目记忆、对应原始业务/IA、详设与 owning evidence，再查清根因层；随后归纳为不依赖具体文件名的通用失败模式，记录有限适用分母、反例边界、预防去向与可复用最小修复，并把根因总结沉淀到项目记忆。只记录症状、只做局部止血、凭本地直觉切换路径或只在本轮口头提醒都不算关闭。
- `GOVERNING_SOURCE_RECALL_IS_ROOT_CAUSE_NOT_PATH_LABEL`: 当仓库已提供正确运行、测试或实施路径时，错误地选择本地、替代或临时路径只是症状；根因必须如实记为遇到问题后未先从 `AGENTS.md`、路由项目记忆、资料包/详设和适用本仓 skill 检索答案。纠偏先恢复这些 governing sources、再诊断并选择路径；不得把“没有使用远端服务器”等路径标签误记为根因。
- `PACKAGE_INPUT_PARAMETER_AUTHORITY`: 受管检查的参数不得由 Roadmap 名称、当前工作单元或调用者猜测；先读取 active package input 的显式参数（例如 `standardsPhase`），再执行既有检查。若 Roadmap 的 `CURRENT_STEP` 和 package 参数属于不同词表，前者只说明工作状态，后者才是该检查的有效入参；`UNKNOWN_PHASE` 是 source-recall 缺失的首败信号，必须诊断而非重试猜测参数。
- `ACTIVE_PACKAGE_CONTROL_PLANE_MUST_BE_RECOVERABLE_AND_SCOPE_BASED`: 将 `allowedChangeSurfaces` 同时当作“证据文件精确集合”和“全部未来实现授权”会把实现期发现的同根 owner/test 文件误判为越界，并在 active package 自身格式损坏时把诊断与恢复一起锁死。根因层是授权集合与证据集合耦合、且控制面没有恢复通道；有限分母是所有带 active package 的受管 implementation package，反例是明确只允许单文件且没有后续实现发现面的 control-only package。最小解是保留 exact surface 作为人工 package-exit 文件清单，另以 `changeSurfaceScopes` 声明批准的 module/source 根；scope 外继续 fail-closed，语义与契约风险交由 typecheck、focused/generated/red gates 和独立 review；active package 解析失败时只允许固定的 recovery request + schema/hash/manifest 校验，禁止借恢复通道修改业务源码。
- `MANAGED_ENTRYPOINT_BEFORE_COMMAND`: 受管构建、测试或运行命令的入口不得由常见目录约定或 shell 习惯猜测；先从 `scripts/README.md`、active package 和适用本仓 skill 恢复唯一入口及其验证阶段。缺失 wrapper、未知 task 或本地 runtime 尝试都是 source-recall 缺失的首败信号；保留命令输出，回读入口规则后再决定是否允许执行，不能换命令碰运气。
- `STATIC_VALIDATION_MUST_NOT_IMPORT_MAIN_BEARING_RUNNER`: 对带有顶层 main 调用的受管 runner，动态 import 不是静态 smoke，会在调用进程所在环境启动真实执行面。根因层是把“验证脚本可解析”误当成“可用 import 验证”，且未先回读 `scripts/README.md`、active package 与受管运行详设来确认唯一允许入口。有限分母为所有带顶层 main 的 managed `.mjs` runner；反例是仅导出纯函数、且明确没有顶层执行的模块。最小复用解是只用 `node --check <runner>` 做语法验证；任何受管运行只从批准的 CLI entry 启动，并在 source review 中检查 main guard。预防去向为本 memory、U11 package 的 implementation review checklist 和既有 managed-entrypoint source recall；这不产生 business 或 cleanup 证据。
- `SHELL_EXECUTION_ENVIRONMENT_NON_SHADOWING`: 执行 receipt、验证或受管脚本时，局部变量不得覆写 `PATH`、`HOME`、`SHELL`、`PWD` 等运行环境名称；循环使用 `targetPath` 等语义化变量，并以每个预期 action 的明确 PASS 输出核对循环真的执行。命令未找到或单条 receipt 缺失必须当作首次失败，先修复并重跑该有限分母，不能假定后续动作已完成。
- `UI_DYNAMIC_PROOF_MUST_NOT_AUTHORIZE_PENDING_IA`: 后端或契约的动态/受管 PASS 只能证明其自身 owner、edge、数据库和 cleanup 边界；只要 UI control-level final alignment 仍为 `PENDING`，不得把该结果表述为 UI L2 PASS，也不得以 backend evidence 替代 IA 逐控件准入。任何发现执行顺序越过该区分时，必须先回读 AGENTS、IA、路由 memory、详设和 owning evidence，记录根因与有限分母，再把 backend proof 与 UI admission 分开落证。
- `UI_CONSUMER_DENOMINATOR_TEST_EXCLUSION`: UI IA baseline 与 `requiredConsumerPaths` 的有限分母只包含实际 production `.tsx` physical consumer，绝不包含 `*.test.tsx` 或 `*.spec.tsx`；focused-test 分母另由其 own evidence/index 管理。metadata sync 因基线新增可添加真实 consumer；仅当 active 误留且 baseline 不含的前端测试路径时，才可在同一 metadata-only receipt 中受控移除。任何 production consumer、非 UI 测试路径或未知路径的移除均 fail closed。反例是把测试与 UI consumer 混作“源码路径”而造成 admission self-deadlock；最小防线是 `isUiImplementationSource` 对 baseline/active 双向校验、strict test-only reconcile、post deep equality 与 `RED_METADATA_SYNC_TEST_PATH_LEAK` 真红。
- `SUCCESSOR_ADMISSION_SURFACE_FREEZE_BEFORE_HANDOFF`: 一旦 active package 已声明 successor admission，admission 的 exact activation surface set 就是冻结的 handoff contract；随后企图修改 active admission 而不是实际激活 successor 会被 hook 拒绝。根因不是 hook 阻断，而是作者在 admission 前没有完成 future package 的测试/证据路径分母。最小解是在 admission 前完成完整 source denominator、反例 proof 位置和 exact surface set；若遗漏，只能在不修改 active admission 的前提下改用已批准路径中的等价 proof，或在下一轮重新建立 successor—not bypass, broaden or relabel the frozen set.
- `ENVIRONMENT_TOPOLOGY_MUST_COME_FROM_GOVERNING_SOURCE`: 运行位置不能从“远端中间件可用”“本机缺少工具”或旧 package 标题推导。每次 DEV、浏览器 L2、UAT 或远端 Testcontainers 前，必须重开 AGENTS、运行详设、scripts README 与 package input，按显式环境矩阵选择执行面。有限分母为四种运行类别；反例是远端 Testcontainers 的 JVM/Docker 技术验证，它不等于浏览器 L2。最小解是受管 runner 记录本机 process/tunnel 与远端 namespace，并按类别证明 cleanup；预防去向为 project memory、scripts README、AGENTS 与 U11 设计 review。
- `RETIRED_CONSUMER_REQUIRES_RETAINED_CAPABILITY_DENOMINATOR`: 删除一个旧页面的唯一 importer 不能推出该 capability 已退役。修改前必须从 approved Journey/IA、face operation、generated client 和所有剩余宿主详情建立“应删除 consumer”与“应保留 capability/consumer”两个互斥有限分母；删除 receipt 必须同时证明后者仍有实际入口。反例是 capability、contract 与 owner dispatch 一并退役且 approved source 明确无 retained target。最小解是 capability-to-host matrix、双向 importer scan 与禁止把 retained consumer 写成 `doesNotMatch` 的 focused test；预防去向为 project memory、U11 implementation review 和 current problem-family evidence。
- `LATE_SURFACE_ADMISSION_REQUIRES_PRECHANGE_BASELINE`: 当一个已存在的 contract、generated projection 或 focused proof 在 package baseline 之后才被发现并纳入 `allowedChangeSurfaces`，其普通 baseline 是 `ABSENT`，即使该文件本身已有早期 package 的真实 receipt；直接修改会正确触发 incremental receipt fail。根因层是先扩当前 package surface、后补写前字节分母，而不是 hook 失效。有限分母是所有 late-admitted existing file；反例是 baseline 后新建的文件，它应保持 `ABSENT→current` 的普通 receipt。最小解是复用既有 `package-owner-scope-baseline-addendum`，先精确锚定该文件的写前 hash（前代 generated output 另声明其原 controlled receipt），再以当前 package 的真实 pre/post 或 generator-controlled receipt 续接；禁止伪造前代 receipt、用历史 recovery 掩盖普通新写入，或仅扩大 allowlist。预防去向为本 memory、active package baseline-addendum validation、implementation review 的 surface-before-write 核查与 package-exit set equality。
- `CONTROLLED_UI_AND_STATIC_PROOF_COEVOLE`: 详情级 overlay、lock、route-preservation 或 error-preservation 的 UI 实现变更，必须同步审视所有同一 consumer 的 static/focused proof；否则旧正则或源码结构断言会变成“既不代表当前 IA，也不覆盖新控制”的误绿/首败。根因层是把 production consumer 与其 proof 视为不同交付物，而非一个 IA control 的双向证据。有限分母是每个被修改 consumer 的直接 focused/static test 与 architecture test；反例是只覆盖不相关 feature 的测试文件。最小解是把 proof 纳入同一 changed-path list，写后运行它并确认断言精确表达新的 IA state（例如 overlay lock 同时覆盖 detail、command 与 audit modal）。预防去向为本 memory、U11 implementation review 和 focused proof denominator。
- `MANAGED_LOCAL_L2_RUNTIME_WIRING_MUST_BE_CONFIG_DERIVED_AND_AWAITED`: 已确认的受管本机 L2 失败模式是 runner 把 Vite URL/端口写成历史常量、把 cleanup 的异步 action 当同步 action、并假定容器镜像 entrypoint 是 shell；这会使 READY、终止回读或远端资产回收在真实执行面首败。根因层是 runner 的真实运行依赖未从 owning config/CLI/进程状态重建，而不是服务启动慢。有限分母是所有同时管理本机 app/browser 与远端中间件 namespace 的 runner：每个本机 URL 必须从相应 app 的 Vite config 派生，每个 cleanup promise 必须在能记录失败的 boundary 内 await，每个容器工具命令必须使用该镜像实际 entrypoint。反例是纯同步、无进程/远端资源、且没有 app URL 的 static checker。最小可复用解是 config-derived local URL、fixed bounded PID disappearance readback，以及按真实 `mc` entrypoint 传入 run-scoped object prefix；继续保留 business/cleanup 分账和首败日志。预防去向为本 memory、U11 runner self-test、受管 L2 preflight review 与 package-exit findings/prevention set equality。
- `MANAGED_BROWSER_L2_SHARED_IDENTITY_WORKER_BOUNDARY`: 已确认的受管浏览器 L2 失败模式是同一 exact spec batch 被 Playwright 默认并发执行，但这些 spec 复用 fixture 创建的登录身份与本机 source；owner 正确地在相同 identity/source 的 rate-limit bucket 上持有事务锁，并把 BCrypt 校验和 session 写入包含在锁期内，导致部分正确登录仍在固定 UI 断言期限内未完成。根因层是 runner 未从 fixture 身份分母和 owner 认证一致性边界推导 worker 策略，而不是凭据错误、限流规则错误或服务启动慢。有限分母是每一个复用同一身份或同一受保护 source bucket 的 managed browser batch；反例是已证明使用独立身份且 owner bucket 不重叠的 batch。最小可复用解是在受管 runner 中对该 batch 显式 `--workers=1`，同时保持 owner 锁、限流和 fixture 身份数不变；不得加 timeout、关闭锁/限流或临时造账号。预防去向为本 memory、U11 详设、runner source review 和 fresh managed L2 business/cleanup evidence。
- `COMMAND_FIXTURE_IDEMPOTENCY_KEY_SINGLE_ORIGIN`: 已确认的 owner-command fixture 失败模式是 helper 为 HTTP header 生成一个 idempotency key，同时 call site 又为 request body 生成另一个 key；对要求 header/body 精确相同的 command 会在 owner-edge 的 validation 处 422，且后续同形 command 都潜伏相同问题。根因层是 fixture helper 与 caller 各自拥有同一 command identity，而不是 owner command 拒绝合法业务。有限分母是全部同时有 `Idempotency-Key` header 和 body `idempotencyKey` 的 fixture request；反例是 GET、明确禁用幂等或 contract 仅要求其中一个载体的 operation。最小可复用解是 helper 优先以 body 的既有 key 作为 header，缺失时只生成一次并只作为 header；不得让 caller 和 helper 各生成一个 key。预防去向为本 memory、U11 fixture command readback、现有 platform fixture `idempotentBody` 参考和 package-exit findings/prevention set equality。
- `L2_REQUEST_WAITER_MUST_SHARE_THE_TRIGGER_PROMISE`: 已确认的浏览器 L2 失败模式是同一用户动作前分开创建多个 request waiter、再在动作之后逐个 await；首败会表现为某个 waiter 在测试 deadline 处超时，掩盖“控件—请求”边界是否真的被触发。根因层是事件等待与触发动作没有组成一个可观察的原子 proof，而不是 owner/edge 没有收到业务请求。有限分母是一个 UI action 同时产生两个或以上需要断言的浏览器请求；反例是单请求或明确串行、前一请求响应决定后续控件可用性的 journey。最小可复用解是用 `Promise.all([waitForRequest(...), ..., triggerClick])` 绑定同一动作，并继续断言每个请求的 method/path/body/header；不得通过延长 timeout、重复点击或放宽谓词掩盖缺失请求。预防去向为本 memory、L2 spec review checklist 与 U11 §5.3 request-body proof。
- `RETIRED_HTTP_FIXTURE_DEPENDENCY_MUST_USE_OWNER_BOOTSTRAP_NOT_FACE_RESTORATION`: 当批准设计已退休某个 HTTP face，而受管 fixture 仍以该 face 建立 L2 前置事实时，404 不是恢复旧 controller/OpenAPI 或以 SQL 绕过 owner 的授权。根因是 fixture 把适配层误当成 capability owner。有限分母是该退休 face 的所有 fixture consumer、face root OpenAPI refs 与 owner service command；同根扫描必须区分当前受控 package 的 consumer 和其他 package 的留存 consumer。反例是批准来源同时退休 capability/owner command，或正式业务 Journey 明确保留该 HTTP face。最小可复用解是短生命周期 `WebApplicationType.NONE` 显式 launcher：先由 workspace owner `requireEnabled`，再调用保留的 owner command，以闭集 target type 的单一 intent 创建事实，token 仅写入 run-scoped `0600` private output；不得注册 controller、暴露 OpenAPI、写业务 SQL 或记录 token。预防去向为本 memory、U11 OpenAPI static proof、focused bootstrap test 与 implementation review 的 retired-face consumer scan。
- `MANAGED_L2_TUNNEL_FAILURE_MUST_BE_DIAGNOSED_AT_THE_BOUNDARY`: a transient SSH forwarding drop during local Spring Boot startup surfaced only as a generic readiness deadline and then as Flyway PostgreSQL EOF. The bounded denominator is every managed L2 runner that starts a remote tunnel (currently `scripts/dev/r5-dev-runner.mjs`); the reusable rule is to read the tunnel log and process identity before retrying, classify the first failure as remote-tunnel/middleware rather than business, and keep business/cleanup separate. A successful cleanup does not convert the business run to PASS. This is an execution-boundary finding, not permission to weaken the runner's fixed deadline or to retry blindly.
- `OWNER_SCOPE_PROBE_MUST_NOT_CATCH_REQUIRED_NOT_FOUND`: an owner read path must not probe multiple target families by calling a throwing `REQUIRED` transactional API and then catch each expected not-found in the caller. The finite denominator is every consumer that resolves one persisted target id across a closed target-type set; the failure mode is a caught owner exception leaving the shared transaction rollback-only and surfacing later as `UnexpectedRollbackException`, even when the eventual target is valid. Counterexamples are owner APIs that return a non-throwing availability set or bounded batch result, and callers whose expected absence is handled inside the owner transaction. The reusable fix is to select exactly one valid target family through the owner non-throwing availability/batch contract, then perform one bounded path read; do not add retries, `REQUIRES_NEW`, broad exception swallowing or frontend fallbacks. Prevention is the U11 implementation review checklist plus focused owner proof and fresh managed candidate-readback evidence.
- `PROFORM_CONNECTED_SUBMIT_PATH_MUST_BE_PROVEN`: a mounted `LoginFormPage`/ProForm consumer can silently lose its command path when it creates an external Ant Design form instance, relies on the ProForm submitter to call `onFinish`, and also remounts or imperatively resets a field during the same interaction. The observed failure boundary is a disconnected-form warning followed by a rendered submit click with no generated owner request; it is not evidence that the owner rejected the command. The finite denominator is consumers combining an external form instance, a ProForm submitter and imperative/remount field reset; a plain Ant Design form, or a ProForm consumer whose connected submit path is independently demonstrated without that reset shape, is a counterexample. The minimal reusable fix is to consume the connected `onFinish(values)` payload as the single command input, use declarative/local state or a keyed field remount for non-secret reset, and keep one submit trigger; do not add a second click handler or repeat the command to mask a missing callback. Prevention is a focused source proof plus a fresh browser request assertion for the affected IA control, with no Redux-internal assertion.
- `DETAIL_ACTION_HANDOFF_MUST_RETAIN_PENDING_ACTION_UNTIL_AFTER_CLOSE`: a detail-first page can visibly close its owner detail Drawer without opening the requested independent edit/status/action surface when a read-only detail Drawer is destroyed during its close motion before the `afterOpenChange(false)` handoff is delivered. The finite denominator is every page that queues an action from a detail Drawer and opens the next Drawer/Modal only from `afterOpenChange(false)`; a page with a single surface or no queued handoff is a counterexample. The minimal reusable fix is to keep the read-only detail surface mounted through its close animation, consume the queued action exactly once from the post-close callback (a ref may guard the pending value), and retain the IA rule that the detail surface must finish closing before the next surface opens. Add a focused source proof that the detail surface is not `destroyOnHidden` plus a fresh browser proof for the rendered action control; do not open both surfaces concurrently or hide the defect with a test-only delay.

## Generated contract semantics

- wire 生成必须从 face 可达的 OpenAPI 路径、组件、错误集、参数与 header 闭包派生；不得从全局词表或 schema-name fallback 扩张某个 face。
- `pageDesignKey`、action capability、静态中文导航与安全 Problem 文案属于 generated semantic catalog；业务 feature 不得从 wire 模块或手写字符串建立第二来源。
- `CATALOG_IDENTIFIER_REFERENCE_CLOSURE`: generated semantic catalog 已提供 pageDesignKey 或 operation-id 常量时，production 与 source-inspection focused test 都必须引用该常量，不能以“只是断言源码”保留裸字符串。根因是测试源码与生产源码同属前端架构扫描分母，裸字符串既会绕开单一真相，也会让同一静态门在后续逐个首败；有限防线是生成常量 import、全树 literal scan 与既有 `R5_FRONTEND_*_LITERAL` red fixtures。反例：非 catalog 业务 copy、test-id 与 IA 已批准的可见文案不适用本条。
- generic `request<unknown>`、手写 `operationId`、原始 `fetch` 与未校验的 implementation catalog 都是 typed generated client 的逃逸面，必须由既有前端架构控制机械拒绝。
