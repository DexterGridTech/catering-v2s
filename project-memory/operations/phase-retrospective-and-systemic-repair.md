# Phase retrospective and systemic repair

## Dexter mandated managed R5 reset and full-seed discipline

- `MANAGED_RESET_SEQUENCE_NO_COMMAND_GUESSING`: 受管 reset 不得猜测命令、环境或替代路径。必须在仓根按以下顺序执行：

  ```bash
  scripts/dev/check
  scripts/dev/reset --dry-run
  R5_RESET_CONFIRMATION=EXPLICIT_R5_RESET scripts/dev/reset
  scripts/dev/start
  ```

  dry-run 必须先 PASS，并确认目标为允许的 DEV 数据库；`R5_RESET_CONFIRMATION=EXPLICIT_R5_RESET` 是 reset 的强制确认，缺失必须拒绝。只有真实 reset 输出 `R5_DEV_RESET=PASS`，才允许 start。reset 实现必须自行取得声明的受管远端控制面；调用者不得因实现缺口而提前启动 DEV、手工建立 tunnel、手工删库、按端口杀进程或改用本地 Docker/数据库。当前实现若不能满足该序列，是 reset runner 的受控阻断，不能以替代命令宣称 reset 成功。

- `MANAGED_START_READBACK_REQUIRED_AFTER_RESET`: start 返回成功不足以声明 DEV 可用。start 后必须读取 `.runtime/r5/run-manifest.json`、四个受控进程的 PID+start token、run-scoped 日志和端口健康；只有这些运行证据与 start 输出一致，才能称为 DEV ready。DEV 的应用执行面仍在本机，数据库与对象存储仅经 manifest 所属的受管 tunnel 连接远端非生产中间件。

- `R5_FULL_SEED_DRY_RUN_AND_BLOCKER_DISCIPLINE`: reset/start 后先执行：

  ```bash
  scripts/dev/seed --profile r5-full --dry-run
  ```

  `scripts/dev/seed --profile r5-full --dry-run` 必须同时验证基础 R5 与 catalog/inventory 两个静态计划；正式入口以 `owner-command` → `catalog-inventory` 顺序执行，并以组合 report 关闭。不得把旧 seed report、bootstrap SQL 或受管 L2 fixture 冒充 full `r5-full` seed，也不得绕过 wrapper 直写数据库。任一子阶段失败必须保留 first failure、子报告与父 receipt，部分状态由下一次显式 reset 清理；不得只复跑 catalog 阶段或把其当成完整体验数据。

- `FORMAL_SEED_TERMINAL_STATES_MUST_BE_EXPLICITLY_REALIZED`: fixture 详设中的每一个 terminal state 必须在正式 executor 设计时逐项落地，不得先假设存在用户 command。有限分母是所有标记为 `REAL_COMMANDS_OR_TERMINAL_FIXTURE` 的 fixture：先用真实 owner HTTP command 产生可达前态；仅当状态由时间或系统终态导致、owner command 明确不可达时，才能在 formal profile 的受管私有 terminal adapter 中按精确 allowlist 更新最小 owner 状态，并写同 owner `SYSTEM` audit 与 scoped receipt 后经既有 read API 回读。terminal adapter 不是 OpenAPI、edge、capability、UI 或通用直写入口；默认 profile、生产 marker、错误 namespace、未列 key 与任何越出合同列集的 mutation 必须 fail closed。每项必须记录不可达理由、前态、允许列、拒绝矩阵和 readback。反例：可由 create/cancel/reissue/complete 等 owner command 达到的状态，及为“方便 seed”新增 HTTP command 或推进全局固定时钟。

- `SYSTEMIC_REPAIR_BEFORE_NEXT_PHASE`: 开发、测试或 Dexter 指出的可迁移问题必须在阶段结束前抽象为失败模式，扫描有限批准分母和同源上下文；下一阶段 preflight 必须把未关闭项转为 obligation，不能以局部修补代替系统性修复。
- `BACKEND_API_CLOSURE_BEFORE_FRONTEND_L2`：后台开发阶段必须在 backend implementation package 内完成 owner/edge/契约与生成物核对、后端单元/聚焦测试和后台 API 测试的 business/cleanup 闭环；未闭环不得进入前端 L2。前端实现必须先完成 IA/详设逐控件静态对账，再在 frontend package 内完成 L2 的业务与 cleanup 闭环；DEV reset/seed 只能在两者都闭环后用于 Dexter 体验。
- `DEV_SEED_AFTER_TEST_CLOSURE`：DEV seed 是体验数据装载，不是 API/L2 fixture；只有 API 与 L2 各自闭环后才允许执行。seed 保留 DEV business state，破坏性数据库与媒体清理由受管 reset 负责；seed contract、runner 和 evidence 必须写清这两个角色，不能让旧 cleanup 文案重新制造第二真相。
- `L2_MUST_NOT_EXECUTE_API_SUITE`：L2 可以由浏览器动作自然触发业务 HTTP 请求，但不得调用、等待或读取 API 测试套件、API runtime report、API run 数据库/会话/资产状态。API、L2、seed 只能共享静态 contract/scenario/fixture definition，不得共享运行态事实；各自使用独立 runId、namespace、报告与 cleanup。
- `PHASE_FAIL_FAST_AFTER_SHARED_BARRIER`：共享 fixture、应用 ready 或权限前置失败后必须保留 firstFailure、lastKnownGood 和 broken boundary，跳过后续 case 循环并进入 cleanup；不能吞异常跑完整分母制造噪声。L2 每个 case 必须有 START 和终态日志，终态带 `completed=X/Y` 与 current case；API 也必须保留首败和分母对账。
- `UPSERT_CONFLICT_TARGET_FOLLOWS_INDEX`：任何 `ON CONFLICT DO UPDATE` 必须显式使用与真实唯一约束/唯一索引逐字等价的 conflict target；表达式唯一索引必须使用表达式推断目标。每个新增 upsert 至少有同 identity 重复写 focused proof；不得以裸 target、猜测列清单或 constraint 名替代索引事实。
- `STAGE_IDENTITY_MUST_INCLUDE_ALL_DIMENSIONS`：stage、receipt、映射和分组 key 必须保留所有能区分业务对象的维度；不能用 `a || b || fallback` 把 SKU、选项值或 owner 维度压成单值。新增复合 identity 必须有同名/碰撞反例的 focused proof。
- `HELPER_NAME_MUST_MATCH_RUNTIME_ROLE`：只提供 generated operation registry 或静态能力的共享模块，不得用 `seed-report` 这类运行态名称；名称、import 和独立性门必须让读者能区分静态定义、API report、L2 sidecar 与 DEV seed report。
- `RUNTIME_EVIDENCE_MUST_BIND_CURRENT_BYTES`：源码、契约、runner 或 fixture 改动后，旧 runtime report 只能作为历史证据；受影响阶段必须重新运行，或标记 `UNVERIFIED_REQUIRES_EVIDENCE`，不得改 hash/分母或只重跑静态门来伪造当前字节 PASS。seed 保留 DEV business state，破坏性数据库/媒体 cleanup 由 reset 负责。
- `PHASE_RETROSPECTIVE_FINITE_DENOMINATOR`: 每项必须记录命中范围、根因层、`FIXED/ALREADY_CORRECT/NOT_APPLICABLE` 处置、设计规则、适用的机械 gate、fresh evidence 与 `MEMORY_DELTA`；反思状态不替代 business 或 cleanup closure。
- `PHASE_RETROSPECTIVE_R4_GATE_PENDING`: R4 前不复制 all-v2 `phase-retrospective` runner；R4 先按建门三问确定 v2s 原生、单 deployable 适用的最小 gate，并以真实 red mutation 证明，不通过不得把本 memory 当成已闭合门。
- `IDENTIFIED_FINDING_GENERALIZATION_REQUIRED`: 每个已确认的设计、实施、测试或验证问题在关闭前都必须形成不依赖具体文件名的通用失败模式、根因层、有限适用分母、反例边界与可复用最小解；局部代码修复本身不是完整关闭。
- `IDENTIFIED_FINDING_PREVENTION_DESTINATION_REQUIRED`: 每项必须落到 `PROJECT_MEMORY`、满足建门三问且有 production red mutation 的 `EXISTING_MACHINE_CONTROL`、`REVIEW_CHECKLIST` 或有具体反例的 `NOT_APPLICABLE_WITH_REASON`。implementation package exit 对已识别问题集合与预防处置集合做 set equality；hook 不伪造语义判断。
- `USER_REPORTED_PROBLEM_FAMILY_DISCOVERY_REQUIRED`: 用户点名的文件、字段、字符串或失败信号只是问题族入口。修改前必须给出通用根因、有限分母、检索面、同根命中、反例边界和 findings/prevention set equality；不得头疼医头、脚疼医脚。
- `PROBLEM_FAMILY_DENOMINATOR_BEFORE_FIX`: UserPromptSubmit 只落 prompt hash intake，PreToolUse 在源码修改前机械要求 disposition 与问题族证据存在，package-exit 枚举全部 intake。hook 不读 prompt 正文、不查询或注入上下文，也不宣称能判断语义穷尽。
- `EXECUTION_DEVIATION_ROOT_CAUSE_MEMORY_REQUIRED`: 不管执行偏差是由 Codex 自检、脚本或测试、独立 reviewer，还是 Dexter 指出，只要确认存在偏差，就必须先重新打开 `AGENTS.md`、六维路由命中的项目记忆、对应原始业务/IA、详设与 owning evidence，再查清根因层；随后归纳为不依赖具体文件名的通用失败模式，记录有限适用分母、反例边界、预防去向与可复用最小修复，并把根因总结沉淀到项目记忆。只记录症状、只做局部止血、凭本地直觉切换路径或只在本轮口头提醒都不算关闭。
- `GOVERNING_SOURCE_RECALL_IS_ROOT_CAUSE_NOT_PATH_LABEL`: 当仓库已提供正确运行、测试或实施路径时，错误地选择本地、替代或临时路径只是症状；根因必须如实记为遇到问题后未先从 `AGENTS.md`、路由项目记忆、资料包/详设和适用本仓 skill 检索答案。纠偏先恢复这些 governing sources、再诊断并选择路径；不得把“没有使用远端服务器”等路径标签误记为根因。
- `DOCKER_BACKED_TESTS_MUST_FAIL_CLOSED_BEFORE_LOCAL_DISCOVERY`: Docker-backed JVM tests must not reach Testcontainers provider discovery from a developer workstation. The finite denominator is every Gradle test task whose `src/test` imports or constructs Testcontainers; pure unit/static tests are counterexamples. The root cause is an unguarded direct Gradle/verify path (historically including a hard-coded local Colima socket), not a missing Docker daemon. The minimum reusable fix is the root Gradle source-marker guard plus the approved `scripts/test/r5-remote-testcontainers.mjs` entry exporting `V2S_TESTCONTAINERS_EXECUTION_PLANE=remote`; direct local execution must fail with an actionable remote-runner message before `DockerClientProviderStrategy`. The verify orchestrator must call that remote runner and must never probe local Docker for cleanup. Prevention is this memory, `build.gradle.kts`, `tools/verify-gates/verify.mjs`, and `scripts/README.md`.
- `PACKAGE_INPUT_PARAMETER_AUTHORITY`: 受管检查的参数不得由 Roadmap 名称、当前工作单元或调用者猜测；先读取 active package input 的显式参数（例如 `standardsPhase`），再执行既有检查。若 Roadmap 的 `CURRENT_STEP` 和 package 参数属于不同词表，前者只说明工作状态，后者才是该检查的有效入参；`UNKNOWN_PHASE` 是 source-recall 缺失的首败信号，必须诊断而非重试猜测参数。
- `ACTIVE_PACKAGE_CONTROL_PLANE_MUST_BE_RECOVERABLE_AND_SCOPE_BASED`: 将 `allowedChangeSurfaces` 同时当作“证据文件精确集合”和“全部未来实现授权”会把实现期发现的同根 owner/test 文件误判为越界，并在 active package 自身格式损坏时把诊断与恢复一起锁死。根因层是授权集合与证据集合耦合、且控制面没有恢复通道；有限分母是所有带 active package 的受管 implementation package，反例是明确只允许单文件且没有后续实现发现面的 control-only package。最小解是保留 exact surface 作为人工 package-exit 文件清单，另以 `changeSurfaceScopes` 声明批准的 module/source 根；scope 外继续 fail-closed，语义与契约风险交由 typecheck、focused/generated/red gates 和独立 review；active package 解析失败时只允许固定的 recovery request + schema/hash/manifest 校验，禁止借恢复通道修改业务源码。
- `MANAGED_ENTRYPOINT_BEFORE_COMMAND`: 受管构建、测试或运行命令的入口不得由常见目录约定或 shell 习惯猜测；先从 `scripts/README.md`、active package 和适用本仓 skill 恢复唯一入口及其验证阶段。缺失 wrapper、未知 task 或本地 runtime 尝试都是 source-recall 缺失的首败信号；保留命令输出，回读入口规则后再决定是否允许执行，不能换命令碰运气。
- `REMOTE_MIDDLEWARE_RESET_MUST_USE_DECLARED_REMOTE_EXECUTION_PLANE`: 受管 DEV reset 的数据库与对象存储属于声明的远端中间件执行面，reset runner 不得把本机工具缺失改写成 Docker/本地数据库方案。有限分母是所有会破坏性重建远端 DEV namespace 的 reset/seed 前置入口；反例是明确声明本机数据库且由环境详设授权的纯本地测试。最小可复用解是先从仍存活的 run-scoped manifest 校验 remote host binding、tunnel identity 与精确数据库 allowlist，再只调用既有受管 reset entry 完成 terminate/drop/create，并保留原始首败；同时由受管 start 负责 migration readiness。若该受管 entry 依赖本机可执行的 `psql`，它只能作为控制客户端，经该 manifest 所属的受管 SSH tunnel 访问远端 PostgreSQL；它绝不表示本机数据库、不得连接本机实例、不得自建 tunnel，也不得以本地 Docker 替代。当前 DEV 的本机 `127.0.0.1:25432`→远端 PostgreSQL、`127.0.0.1:29000`→远端对象存储只是受管 SSH tunnel 入口，不是本机中间件；任何 manifest、stdout 或报告都必须显式标记 `LOCAL_APPLICATIONS_REMOTE_NON_PRODUCTION_MIDDLEWARE`，并记录 remote host binding 与 tunnel identity。预防去向为本 memory、`scripts/README.md`、managed-runtime review checklist 与 reset runner self-test；不得用一次性手工命令掩盖入口缺陷或把 reset PASS 误报为脚本自身 PASS。
- `STATIC_VALIDATION_MUST_NOT_IMPORT_MAIN_BEARING_RUNNER`: 对带有顶层 main 调用的受管 runner，动态 import 不是静态 smoke，会在调用进程所在环境启动真实执行面。根因层是把“验证脚本可解析”误当成“可用 import 验证”，且未先回读 `scripts/README.md`、active package 与受管运行详设来确认唯一允许入口。有限分母为所有带顶层 main 的 managed `.mjs` runner；反例是仅导出纯函数、且明确没有顶层执行的模块。最小复用解是只用 `node --check <runner>` 做语法验证；任何受管运行只从批准的 CLI entry 启动，并在 source review 中检查 main guard。预防去向为本 memory、U11 package 的 implementation review checklist 和既有 managed-entrypoint source recall；这不产生 business 或 cleanup 证据。
- `SHELL_EXECUTION_ENVIRONMENT_NON_SHADOWING`: 执行 receipt、验证或受管脚本时，局部变量不得覆写 `PATH`、`HOME`、`SHELL`、`PWD` 等运行环境名称；循环使用 `targetPath` 等语义化变量，并以每个预期 action 的明确 PASS 输出核对循环真的执行。命令未找到或单条 receipt 缺失必须当作首次失败，先修复并重跑该有限分母，不能假定后续动作已完成。
- `UI_DYNAMIC_PROOF_MUST_NOT_AUTHORIZE_PENDING_IA`: 后端或契约的动态/受管 PASS 只能证明其自身 owner、edge、数据库和 cleanup 边界；只要 UI control-level final alignment 仍为 `PENDING`，不得把该结果表述为 UI L2 PASS，也不得以 backend evidence 替代 IA 逐控件准入。任何发现执行顺序越过该区分时，必须先回读 AGENTS、IA、路由 memory、详设和 owning evidence，记录根因与有限分母，再把 backend proof 与 UI admission 分开落证。
- `UI_CONSUMER_DENOMINATOR_TEST_EXCLUSION`: UI IA baseline 与 `requiredConsumerPaths` 的有限分母只包含实际 production `.tsx` physical consumer，绝不包含 `*.test.tsx` 或 `*.spec.tsx`；focused-test 分母另由其 own evidence/index 管理。metadata sync 因基线新增可添加真实 consumer；仅当 active 误留且 baseline 不含的前端测试路径时，才可在同一 metadata-only receipt 中受控移除。任何 production consumer、非 UI 测试路径或未知路径的移除均 fail closed。反例是把测试与 UI consumer 混作“源码路径”而造成 admission self-deadlock；最小防线是 `isUiImplementationSource` 对 baseline/active 双向校验、strict test-only reconcile、post deep equality 与 `RED_METADATA_SYNC_TEST_PATH_LEAK` 真红。
- `SUCCESSOR_ADMISSION_SURFACE_FREEZE_BEFORE_HANDOFF`: 一旦 active package 已声明 successor admission，admission 的 exact activation surface set 就是冻结的 handoff contract；随后企图修改 active admission 而不是实际激活 successor 会被 hook 拒绝。根因不是 hook 阻断，而是作者在 admission 前没有完成 future package 的测试/证据路径分母。最小解是在 admission 前完成完整 source denominator、反例 proof 位置和 exact surface set；若遗漏，只能在不修改 active admission 的前提下改用已批准路径中的等价 proof，或在下一轮重新建立 successor—not bypass, broaden or relabel the frozen set.
- `ENVIRONMENT_TOPOLOGY_MUST_COME_FROM_GOVERNING_SOURCE`: 运行位置不能从“远端中间件可用”“本机缺少工具”或旧 package 标题推导。每次 DEV、浏览器 L2、UAT 或远端 Testcontainers 前，必须重开 AGENTS、运行详设、scripts README 与 package input，按显式环境矩阵选择执行面。有限分母为四种运行类别；反例是远端 Testcontainers 的 JVM/Docker 技术验证，它不等于浏览器 L2。最小解是受管 runner 记录本机 process/tunnel 与远端 namespace，并按类别证明 cleanup；预防去向为 project memory、scripts README、AGENTS 与 U11 设计 review。
- `RETIRED_CONSUMER_REQUIRES_RETAINED_CAPABILITY_DENOMINATOR`: 删除一个旧页面的唯一 importer 不能推出该 capability 已退役。修改前必须从 approved Journey/IA、face operation、generated client 和所有剩余宿主详情建立“应删除 consumer”与“应保留 capability/consumer”两个互斥有限分母；删除 receipt 必须同时证明后者仍有实际入口。反例是 capability、contract 与 owner dispatch 一并退役且 approved source 明确无 retained target。最小解是 capability-to-host matrix、双向 importer scan 与禁止把 retained consumer 写成 `doesNotMatch` 的 focused test；预防去向为 project memory、U11 implementation review 和 current problem-family evidence。

The minimum repair is a sibling scan and a written boundary decision that chooses complete retirement or retained compatibility, followed by IA/baseline/test alignment and a production-source scan proving no stale UI consumer remains. Prevention is this memory, the current UI reconciliation ledger, and implementation review checklist.

## IA reconciliation lessons from the 94-screen rescan

### IA_RECONCILIATION_FAMILY_SUMMARY_CANNOT_CLOSE_PHYSICAL_SCREEN

- `IA_RECONCILIATION_FAMILY_SUMMARY_CANNOT_CLOSE_PHYSICAL_SCREEN`: The previous IA reconciliation reported a smaller family denominator (38/36/36) and synthetic OTP/shell summaries, so a green aggregate did not prove the actual 94 physical screen IDs. Root cause is denominator transformation and summary propagation: the reviewer reconciled capability families and source bindings, then treated that projection as the physical contract. The finite denominator is the exact 94 physical screen IDs in the current physical-screen contract plus independently mounted shared shell/auth/foundation controls; a non-rendered generated type is a counterexample. The minimal reusable fix is a physical-contract-driven one-ID record with exact-set checks, explicit source/consumer and focused proof, and a separate runtime status; no summary field may upgrade a missing row. Prevention is the current v2 ledger, memory, and implementation-review checklist.

- `IA_RECONCILIATION_SOURCE_BINDING_IS_NOT_SEMANTIC_REVIEW`: A source path binding, import-equality check, or focused test can prove registration and static shape while missing rendered AntD semantics such as hierarchy, icon, placement, copy, timing, loading/error state, and browser-observable result. The finite denominator is every user-observable control/state transition in both admin apps; a pure generated DTO consumer is a counterexample. The minimal reusable fix is row-level semantic review against the IA anchor, then focused proof and (where behavior is dynamic) runtime proof; static exact-set or AntD CLI output remains adjunct evidence. Prevention is the v2 ledger and a sibling scan requirement, not another aggregate gate.

- `ANTD_BATCH_PATCH_MUST_PRESERVE_ONE_CONTROL_ONE_RENDER`: A mechanical AntD API migration can insert duplicate JSX returns or malformed prop fragments even when the intended API replacement is correct; the resulting typecheck failure is a signal of patch-shape corruption, not a reason to weaken the proof. The finite denominator is every automated or batched JSX/API migration across both admin apps; a hand-reviewed single-control edit is a counterexample. The minimal reusable fix is one control/one render per diff hunk, immediate app typecheck after each bounded batch, and a duplicate-return/invalid-prop scan before proceeding. Prevention is the current focused proof and implementation checklist.

### IA_RECONCILIATION_CATALOG_COPY_SCAN_MUST_INCLUDE_SHELL
- `IA_RECONCILIATION_CATALOG_COPY_SCAN_MUST_INCLUDE_SHELL`: Page-only catalog scans can miss shell brand, parent-menu, account-menu, and authentication-entry titles even though users observe them as menu/page chrome. The finite denominator is every user-visible title/label that acts as page or menu entry in both admin shells and public/auth entry surfaces; field validation copy and non-catalog explanatory prose are counterexamples. The minimal reusable fix is to include shell copy in the same catalog model, generate its projection, and scan both production consumers and IA rows; do not use an unrelated page title as a substitute. Prevention is this memory and the current v2 ledger.

### IA_RECONCILIATION_SOURCE_BINDING_IS_NOT_SEMANTIC_REVIEW
### ANTD_BATCH_PATCH_MUST_PRESERVE_ONE_CONTROL_ONE_RENDER

- wire 生成必须从 face 可达的 OpenAPI 路径、组件、错误集、参数与 header 闭包派生；不得从全局词表或 schema-name fallback 扩张某个 face。
- `pageDesignKey`、action capability、静态中文导航与安全 Problem 文案属于 generated semantic catalog；业务 feature 不得从 wire 模块或手写字符串建立第二来源。
- `CATALOG_IDENTIFIER_REFERENCE_CLOSURE`: generated semantic catalog 已提供 pageDesignKey 或 operation-id 常量时，production 与 source-inspection focused test 都必须引用该常量，不能以“只是断言源码”保留裸字符串。根因是测试源码与生产源码同属前端架构扫描分母，裸字符串既会绕开单一真相，也会让同一静态门在后续逐个首败；有限防线是生成常量 import、全树 literal scan 与既有 `R5_FRONTEND_*_LITERAL` red fixtures。反例：非 catalog 业务 copy、test-id 与 IA 已批准的可见文案不适用本条。
- generic `request<unknown>`、手写 `operationId`、原始 `fetch` 与未校验的 implementation catalog 都是 typed generated client 的逃逸面，必须由既有前端架构控制机械拒绝。

- `INVITATION_OWNERSHIP_MUST_CLOSE_BOOTSTRAP_AND_CROSS_NODE_GOVERNANCE`: 不能仅依据某一份 IA 的“邀请归属”句子退役平台邀请入口。若平台管理员需要创建首个运营用户，或需要跨任意组织节点治理邀请，则平台必须保有永久邀请中心；L2 owner bootstrap 只能是受管测试辅助，不能替代真实产品任务。失败模式是把邀请发起限制到 operations 局部 target 页面后，生产系统无法产生首个运营用户、平台无法治理跨节点邀请，而静态退役 gate 仍可能全部通过。有限分母是所有 invitation create/list/candidate/cancel/reissue consumer 与 public acceptance flow；公开接受仍是 operations/public 反例，不应被平台邀请中心吞并。最小可复用修复是统一 workspace-IAM owner command/readback，由 platform-admin 提供跨节点入口、operations-admin 提供范围内入口，二者都使用 opaque organization ref、role id、CAS/idempotency 和 owner recheck；在替代真实入口、契约、focused proof 与首个用户闭环未完成前，禁止删除平台 invitation Tab/HTTP face。根因是把“重复入口”误判成“禁止入口”，且没有将 bootstrap 业务链路纳入 ownership review。防再犯：IA 评审必须同时回答首个业务对象如何产生、跨节点治理如何完成、哪个 consumer/owner 负责每个 command，并对退役 package 做 bootstrap/readiness negative proof。

### PLATFORM_SUPER_ADMIN_MUST_NOT_ENTER_WORKSPACE_CAPABILITY_MODEL

- `PLATFORM_SUPER_ADMIN_MUST_NOT_ENTER_WORKSPACE_CAPABILITY_MODEL`: 平台端功能会在生成 manifest、contract 或 catalog 的统一“capability”措辞下被错误投影为运营角色权限，导致平台邀请等本应由已启用平台管理员直接治理的功能被错误要求新增 capability。根因是将“所有写操作都必须 capability 化”的错误全称假设写入生成器和不变量门。有限分母是全部 `platform-admin` mutating operation、其 manifest requirement、`WorkspaceCapabilityRequirementCatalog` 生成输出和所有 `operations-admin` authenticated operation；公开 OTP/凭据/邀请接受是 owner protocol 反例，运营后台已认证操作是唯一允许 capability 投影的正例。最小可复用解：平台操作必须是 `AUTHENTICATED_PLATFORM_SUPER_ADMIN`、`PLATFORM_SESSION_ENABLED_ADMIN`、无 `capabilityKey/capabilityMapping` 且使用 `x-required-platform-authorization`；workspace capability catalog 仅由 `AUTHENTICATED_WORKSPACE` requirements 生成。防再犯：`tools/capability-invariants/cli.mjs` 对 platform capability、错误 authorization mode 和 workspace catalog projection 均 fail closed，并以向平台 requirement 注入 capabilityKey 的真实 red mutation 自测；蓝图与当前 IA/implementation review 同时重开。不得以此删除 operations role/page/action capability 或 public owner protocol。

### CATALOG_INVENTORY_SCOPE_BOUND_WRITE_CAPABILITY

Cross-owner whole-save clarification: a capability follows the approved user task, not every fact owner invoked by that task. A coordinator may use a catalog whole-save grant for another owner only when the operation policy names the finite command set, keeps it in the same REQUIRED transaction, and binds the grant to the exact originating requirement. The target owner must reject generic catalog grants, wrong-operation grants, inventory grants on that coordinated path, and any direct inventory command carrying the catalog grant. Direct inventory workbench workflows retain their independent inventory capability.

- `CATALOG_INVENTORY_SCOPE_BOUND_WRITE_CAPABILITY`: A capability must denote one user-initiated write workflow over one owner-compatible target scope; it is neither page access nor a read privilege. The finite denominator is every catalog-inventory operation policy, platform role entry, workspace session projection, edge dispatch, owner command, API/L2/DEV fixture and migration that mentions a catalog or inventory capability. Public asset reads, ordinary scoped diagnostic GETs and page admission are counterexamples. The root failure is collapsing a dual-scope session selector, UI visibility hint and server command authorization into one coarse key: Store-first fallback can reject a valid Head Company request, while a UI-only key can leave a direct write unprotected. The minimum reusable repair is an explicit data-node selector matched against the corresponding persisted selection, a generated type-to-write-capability mapping for every mutation, live role/assignment/task-path resolution, and a server-minted owner grant verified before replay or mutation. Distinct owner write targets stay distinct keys; a role with only page access and no write keys is valid. Prevention is the P1/P2/capability invariant gates with red mapping/GET mutations, focused dual-selection and revocation tests, and the review checklist in `doc/decisions/2026-08-08-v2s-catalog-inventory-scope-specific-write-capabilities.md`.

### CROSS_LAYER_CONTRACT_CONSUMER_CLOSURE

- `CROSS_LAYER_CONTRACT_CONSUMER_CLOSURE_BEFORE_DYNAMIC_RUN`: A change to scope selection, authorization, header, request/response field, generated wire, owner command or fixture can be locally correct while one reachable consumer still sends the old shape. The root cause class is a **cross-layer denominator omission**: starting from a visible page or a failing API case instead of first enumerating the authoritative operation family and its complete declaration→propagation→consumption chain. The finite denominator is each operation sharing the changed predicate plus, for every operation, the contract schema, root/path OpenAPI parameter or header, generated Java/TypeScript projection, edge/controller parser, coordinator/owner recheck, all production consumers, API/L2/DEV fixture callers and their focused proof. A test-only caller is not a production consumer but remains in its own proof denominator; a single-target operation whose controller explicitly derives one unambiguous scope is a counterexample only when both contract and negative proof record that omission is valid. The minimum reusable repair is a pre-dynamic matrix, exact-set scan, owning-generator regeneration, compile/typecheck, and real red mutation for both missing and wrongly-required/accepted variants. Prevention destination is `PROJECT_MEMORY` plus the applicable existing machine control: current catalog-inventory P1 enforces all seven HEAD_COMPANY+STORE GET selector schemas and query parameters with missing/required red mutations; the remaining semantic consumer coverage is the Blueprint cross-layer checklist and implementation review. Dynamic API/L2/DEV runs then confirm business and cleanup rather than discover statically enumerable omissions.

- `CATALOG_TYPED_REFERENCE_MUST_NOT_STORE_CODE`: A field named `*Ref` may look typed while it persists a business code. This makes code reuse, hard deletion and copy closure unsafe even if the table itself already has a UUID primary key. The root cause is treating the display/natural key as relationship identity and then extending that shortcut through JSON, copy closure, owner reads and inventory identities. The finite denominator is the declared physical rows in `contracts/policy/catalog-inventory-reference-path-matrix.json`: category hierarchy and item categories; catalog dictionary/tag/SKU/component/BOM relation paths; production-tag relations; and inventory StockTarget/BOM relationship identity. `assetRef`, inventory `targetRef` and ledger target refs are UUID counterexamples and must not be migrated. The minimum reusable repair is an explicit path registry—not key-name heuristics—where every opaque field persists/validates a UUID in owner scope, read models supply separate `code/name` labels, migrations fail closed on zero or multiple matches, and copy rewrites `(objectType, sourceRef)->targetRef` before insertion. Before an opaque-ref change, inspect every contract, generated projection, owner read/write/copy path, consumer and API/L2/DEV fixture in the declared row; after it, prove a real red mutation rejects a business code and accepts the matching UUID. Category deletion additionally locks the subtree and concurrent item save locks referenced category UUIDs in the same order, so no dangling reference can commit. Prevention is this memory, the matrix, focused owner/contract/UI tests and the implementation-review checklist; UI-only hiding, code fallback and recursive JSON-key inference are prohibited.
- `FIXTURE_REFERENCE_ALIAS_MUST_CLOSE_THROUGH_OWNER_READBACK`: Static fixture identifiers such as a source `productSkuRef` are lookup aliases, not persisted identities and not necessarily equal to a user-facing SKU code. The finite denominator is every DEV/API/L2 runner that takes a fixture relationship alias and later emits an opaque relation, inventory node or BOM owner command. The required chain is `fixture alias -> declared business code -> owner detail readback UUID -> persisted request UUID`, while the code remains only a display/owner-lookup label. A code equal to the fixture alias is a counterexample that must not hide the mapping requirement. Minimum proof is a non-equal alias/code case plus a real owner HTTP composite/BOM save and readback; falling back to the alias or code in a `*Ref` field is prohibited.
- `DEV_SEED_DISPLAY_LABEL_MUST_NOT_DERIVE_FROM_TECHNICAL_KEY`: A DEV seed can preserve correct owner identities yet still produce an unusable Chinese business experience when it copies fixture keys, source file names, enum tokens or role keys into persisted display fields. The finite denominator is every owner command field rendered as a business name, short name, label, option group, unit, role name, account display name, administrator display name, extension display value or free-form item attribute; codes, login names, UUIDs, route/operation identifiers, status enums and external media provenance are counterexamples and remain technical. The minimum reusable repair is an explicit fixture-owned label map with exact-set coverage for every code that must be presented, owner HTTP readback of created labels, and a separate display name on each role/account/admin; never derive display text from fixture keys. Existing DEV-only static checks must reject a missing, non-Chinese or technical-code display label, while the API and L2 fixtures stay independent and do not become the DEV label authority.
- `ASSET_PHYSICAL_CONTENT_MUST_NOT_COLLAPSE_LOGICAL_LIFECYCLE`: A content-addressed `bucket_name + object_key` identifies immutable physical bytes, while `asset_ref` and its one-time grant identify an owner-governed logical lifecycle. Identical bytes may therefore back multiple workspace-logo assets; only `CATALOG_ITEM_IMAGE` deliberately reuses one logical reference by content. The finite denominator is Logo staging, catalog staging/restage, bind grants, object cleanup, database constraints, all HTTP consumers, Testcontainers fixtures and owner-command seed fixtures. Public reads of one existing active ref are counterexamples. The minimum repair is a catalog-only partial uniqueness rule, a fresh Logo ref/grant for every stage, per-object serialization before stat/put/row creation, reference-aware deletion, and separate owner-invariant versus storage-I/O exceptions. An active-reference read derives the immutable public URL from owner metadata and must not turn every workspace/login/session read into an object-storage health check; storage health belongs to staging and managed diagnostics. Historical evidence that made fixture bytes distinct to satisfy global storage-key uniqueness records the old faulty assumption and must not be copied as a production invariant. Prevention is same-byte dual-Logo and Logo/catalog Testcontainers coverage plus a seed that stages identical physical bytes through independent Logo lifecycles.
