# 该复用现有读模型,还是新建一个

**触发时刻**:要给一个新页面/新区域取数据,不确定是复用已有接口还是新建。

> ⚠️ **本文 2026-08-26 按 Dexter base-1 裁定修订。** 修订前的版本要求"只返回消费者实际用到的字段闭集"、"首屏读模型收窄到当前区真实字段" —— 那条教条正是造成读接口按屏裁剪、前端每改一点全线跟改的成因,**已推翻**。下面区分保留与推翻两部分。

## 一、仍然成立的

1. **接口按可复用的业务读模型定义,不按 UI 结构定义。** ⛔ 不为每个屏幕/组件另造接口。
2. 若 A 要 `X.M`、B 要 `X.N`,且二者在**同一 scope、授权、生命周期、新鲜度**下都需要同一个稳定实体 `X` ⇒ **一个完整的 `X` task read 同时服务它们**。
3. 若 C 需要**不同的关系闭集、不同授权、或独立的 loading/恢复** ⇒ 它不是 A/B 的同一个读模型。
4. **无界集合走自己的分页**:流水、日志、可无限递归展开的关系,以及被显式裁定为懒加载的子集合(如商品的规格子行)。这是集合语义,不是字段裁剪。
5. **父组件已有的数据,子组件不再各自订阅一遍。** 父级已有 ⇒ prop 下传。

## 二、已推翻的(不要再照做)

❌ **按消费者实际用到的字段闭集裁剪返回值。** 「列表页只用五个字段,就只返回那五个」——这正是让展示决定长进契约的做法。展示要哪几个字段是前端的事,owner 只负责给出该实体完整的业务结构。

❌ **首屏读模型收窄到"当前区真实字段"。** 收窄的正确对象是**无界集合**,不是**字段**。

## 三、"mega endpoint"的真正判据

反对 mega endpoint 仍然成立,但它的问题**不是**"一个实体返回了它的完整关联结构",而是:

> 把**不同实体、不同授权、不同新鲜度**的东西塞进同一个接口。

- ✅ 商品读模型返回该商品的分类实体、标签实体、属性实体、制作信息结构 —— 同一实体的关联闭包,**正确**
- ❌ 一个接口同时返回商品、当前用户的待办、和平台公告 —— 三种授权与新鲜度,**错误**

## 四、判别式(修订后)

- 旧判别式「消费者用到的字段闭集,和读模型返回的是不是同一个」**作废**。
- 新判别式两问:
  1. 我返回的,是不是**这个实体自身的业务结构**(而不是某一屏的取景框)?
  2. 我裁掉的,是不是**无界集合或另一实体**(而不是字段)?

两问皆是 ⇒ 形状正确。任一为否 ⇒ 我在把展示决定写进契约。
